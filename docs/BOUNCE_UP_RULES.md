## 1. 規則

- **盤**: 論理盤面は **360×640**(Sky Fighter §1・Overtake §1 と同じ大きさ)。上が上。座標は §2。
- **主人公**は 1 つ(自作の形 — §7)。**足場に乗るたびに自動で跳ねる**。乗れるのは、**落ちている間に足場の
  上面を上から横切ったときだけ**で、下からはすり抜ける(上昇中は足場を通り抜けて上へ出る)。
- **左右の端は反対の端へつながる**(折り返し)。右の端から出ると左の端から入る。足場は折り返さない(盤の
  中に収まる — §3)。
- **カメラは主人公が登ったときだけ上へ進み、下がらない**(§2「カメラ」)。**画面は自動では上へ流れない** —
  同じ足場で跳ね続ければ、いつまでも落ちない。急かす仕組みは持たない
  ([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md)「タイマープレッシャーを既定にしない」)。
- **終わり**: 主人公の体が**画面の下端より完全に下へ落ちたら** `over`(§2)。ライフ・コンティニュー・復活は
  無い。
- **難しさを決めるのは、高さとともに伸びる足場の間隔と、足場の種類だけ**(§3)。速さ(重力・初速・最高水平
  速度)はランの間も高さでも変えない。
- **スコア = 到達した最大の高さ**を点にしたもの: `floor(最大の高さ(論理 px) / 10)`(係数 10 は初期値 —
  §4「スコアと高さ」)。点に単位の語(m など)を付けない。
- **足場は 3 種類**(§3): 動かない足場(static)、左右に往復する足場(moving、段 40 から)、1 回跳ねたら
  消える足場(vanishing、段 60 から)。はねる足場(高く跳ばせる足場)は v1 では作らない(計画)。
- **助け**: Undo と Hint は作らない。遊びの中身がリアルタイムの反射で、盤面に隠れた情報も無いから
  (Bunny Hop §8・Snake §9 と同じ理由)。代わりの無料・無制限の助けは、**即時リトライ**(確認も待ち時間も
  広告も無い — §4)と **Wide**(足場の幅 1.5 倍 — §3)。コンティニュー・復活・パワーアップ・ジェットパック・
  時間で消える足場は作らない。
- **モード**: Endless だけ。デイリーは作らない(Bunny Hop §13 と同じ理由。生成は seed で決まるので後から
  足せる)。設定は足場の幅 **Normal / Wide** の 1 つだけで、記録は幅ごとに分ける(§5)。

## 2. 物理

`game/` の Pure TypeScript(`game/physics.ts`)。React・DOM・時計・`Math.random` を読まない。

### 単位と数の規則

- **固定ステップ 1/120 秒**。位置は **1/120 px 単位の整数**(`SUB = 120`)、速度は **px/s の整数**。
  したがって 1 ステップの移動量は速度の数値そのもの(v px/s × 1/120 秒 = v/120 px = v 単位)。
  Overtake §1 と同じ形。
- 縦の座標 y は**高さ**(上向きが正。床の上面が 0)、横の座標 x は盤の左端 0 から右端 360 px(`[0, 360 × 120)`
  単位)。主人公の位置は**足元の中心**(x, y)で持つ。
- `step`・生成・ボットは**整数だけ**で計算し、`Math.sin` / `cos` / `pow` / `sqrt` を使わない(V8 と
  JavaScriptCore で golden がずれないように)。割り算は整数どうしの `Math.floor(a / b)` と、定数が割り切れる
  ことを保証している商だけを `exactDiv`(`game/arith.ts`、割り切れなければ例外)で。浮動小数を扱ってよいのは
  入力の写像(`game/input.ts` — CSS px のポインタ座標と盤の倍率)とフレームの時間の換算だけで、どちらも
  物理へ渡す前に整数へそろえる(§4「入力」)。

### 定数(すべて初期値。`game/constants.ts` に 1 か所だけ置く)

### 1 ステップの順序(`step(state, input)`、`running` の間だけ)

1. **時刻**: `tick` を 1 進める(動く足場の位置は `tick` から決まる — §3)。
2. **目標の x**(§4「入力」): キーと ◀ ▶ を押していればその向きへ、押していなければドラッグの移動量を足す。
   目標は体から `LEAD_MAX` より離れない。
3. **横**: x を目標へ最大 600 単位動かす(加速なし)。動いた後の x が盤の外なら、x と目標を同じ量だけ
   360 px の倍数ずらして x を `[0, 360)` に戻す(折り返し。目標は x からの差を保つ連続の座標)。
4. **縦**: 速度 vy から 15 を引き、足元の y に vy を足す(半陰的オイラー)。
5. **乗る**: vy < 0(落ちている)なら、このステップの前の足元 y₀ と後の足元 y₁ の間(y₀ ≥ t ≥ y₁)に上面 t が
   あり、横に重なる(下)まだ消えていない足場のうち、**最も高い 1 枚**に乗る: y = t、vy = 760。消える足場
   なら消す(§3)。上面を**前後のステップの線分で横切ったか**で判定するので、どれだけ速く落ちてもすり抜け
   ない(1 ステップで動く量に依らない — Phase 2 のテストが毎秒 6,000 px と 60,000 px の落下で、上面の位置を
   1 ステップの中で 37 単位ずつずらした 1,786 通りと両端を確かめる)。**両端を含む**: 足元がステップの終わりに
   ちょうど上面にある(t = y₁)なら乗り、上面が y₁ の 1 単位下、または y₀ の 1 単位上なら乗らない(同じテスト)。
6. **記録**: 最大の高さ `maxHeight` を更新する。カメラを上げる(下)。
7. **終わり**: 体の上端(y + 28 px)がカメラの下端以下なら `over`。
8. **生成と片付け**: 画面の上端の 160 px 上まで足場を足し、画面の下端より 64 px 以上下の足場を捨てる
   (§3「仕事量」)。

- **横の重なり**: 体の中心 x が `[足場の左端 − 10, 足場の右端 + 10]` に入れば重なる(`FOOT_HALF`)。体は
  28 px なので、両側の 4 px ずつは足場の外に出ていても乗らない — 「見た目の 1 px の重なりで乗る」ことを
  避け、同時に「足の下に足場があるのに乗らない」を避ける幅(初期値)。折り返しのため、x と x ± 360 px の
  3 通りで調べる(端をまたいで描かれている体は、端の向こうの足場にも乗れる)。
- **カメラ**: `cameraBottom = max(cameraBottom, y − 280 px)`(下がらない)。足元が画面の下端から 280 px より
  上に来たときだけ上がる。したがって主人公の上には常に少なくとも 360 px が見え、足場の段差は 128 px 以下
  (§3)なので、**主人公の上に足場が 2 段以上見える**(算術では。計画の下限の条件)。
- **`over`**: 足元ではなく体の上端で判定する — 画面の下端で体が半分見えているうちは終わらない。
- **乗った位置**: 足元を上面の高さに置き直す(横切った分だけ下にめり込んだ足元を戻す)。乗ったステップでは
  横の位置はそのまま。

### フレームとステップ(持ち越しの上限)

- UI の RAF は経過時間をステップへ換算し、1 フレームに**最大 6 ステップ**だけ回す(Sky Fighter・Overtake と
  同じ `MAX_STEPS_PER_FRAME = 6`)。換算はロジックの純関数 `frameSteps(carry, dtMs)`(`game/frame.ts`)が
  受け持つ: 時間を 1/120,000 秒単位の整数に丸め(1 ステップ = 1,000 単位)、持ち越しと足した量を
  6 ステップ分で頭打ちにし、回すステップ数と次の持ち越し(1 ステップ未満)を返す。**頭打ちを超えた時間は
  捨てる**ので、背景から戻った直後・遅い端末で、大量のステップをまとめて回すことは無い(遅い端末では時間が遅れる
  — 世界がゆっくりになるだけで、すり抜けや飛ばしは起きない)。
- 有限でない経過時間・負の経過時間は 0 と読む(閉じる側に倒す)。
- `ready` / `paused` / `over` ではループ自体を止める(§4)ので、`frameSteps` は `running` の間だけ呼ばれる。
  走り始め・再開の最初のフレームは経過時間 0 として数える(止まっていた時間を持ち込まない — UI の責任。
  `ui/components/BounceStage.tsx` は状態が変わるたびにループの時計を捨て、次のフレームは時刻を取るだけにする)。

## 3. 生成

### 決定性

- 各段の乱数は `${seed}:seg:${i}`、区間の形は `${seed}:phrase:${block}` から作るPRNGだけで決まる。乱数は整数。生成は時計・プレイヤーの入力・再試行を読まない。
- `gen` は次の段番号、直前の鎖の高さ、名目中心を保持する。動く鎖の名目中心は往復範囲の中央。直前の移動範囲は同じ区間seedから定数回で再構成するので、保存やカーソルの欄を増やさない。
- 段差は段の最初の乱数で決まる。Normal/Wideは同じseedなら高さの列と区間の形が同じで、横配置・足場幅が違う。新しいランは新しいseed。同じseedと入力列なら同じラン。

### 短い挑戦と休息

- 段0は幅360pxの静止した床。段1〜19は通常の生成。
- **段20から8段を1区間**とする。最初の**3〜5段**を挑戦、残り**3〜5段**を休息にする。挑戦の長さと最初に向かう左右は区間seedで決まり、挑戦中は目標の左右を交互に切り返す。
- 挑戦の名目中心は `180 ± (60〜76)` pxを目指し、前段から届く範囲と盤内に収まる範囲へ切る。最初の段で整列し、続く段は左右交互へ進む。足場幅は常にNormal 64px / Wide 96px。
- 挑戦の段差は基本ランプの下端を最低90px、上端を最低110pxへ上げる。**挑戦には追加足場を置かない**。
- **段40以降の挑戦区間の中央1枚をmoving**にする。最初の必須movingは段45または46(区間44の長さによる)。段20・28・36の区間は静止ジグザグを先に教える。movingの前後は必ずstatic。
- 必須movingは**往復幅96px、速度60px/s**の三角波。位相は段の乱数で決まる。Normalの足の判定幅84pxより往復幅が大きいため、全位相を同じ横位置だけで覆えない。Wideの広さは助けとして保つ。
- **必須movingを飛ばせない**: 前後の静止足場の高さの差は最低180pxで、実際の跳躍高157.29pxを超える。movingへ入る段差にも出る段差にも追加足場がないので、区間境界の追加足場からも迂回できない。
- 休息では鎖はstaticで、名目中心の横移動は最大70px。ここでは同じ足場で跳ね続けて先を見られる。カメラは自動で進まず、時間で消える足場もない。

### 基本ランプと追加足場

`ramp(a,b,i) = floor((a × (180 − k) + b × k) / 180)`、k = min(max(i,0),180)。すべて調整可能な初期値。

| 量                                    | 開始     | 段180以降 |
| ------------------------------------- | -------- | --------- |
| 基本段差                              | 48〜72px | 96〜128px |
| 鎖の移動範囲全体での直接距離上限 D(i) | 110px    | 170px     |
| 休息・序盤に追加足場が出る確率        | 600‰     | 350‰      |

- 追加足場は0〜1枚で、鎖2枚の高さの中間。static/moving/vanishingの重みは段1〜39で1/0/0、40〜59で2/1/0、60以降で2/1/1。挑戦区間では追加足場を抑止するため、初出はこの下限以後の休息段になる。
- 追加movingの往復幅96〜224px、速度40〜80px/sは従来どおり。往復の全範囲が盤内に収まる。vanishingは一度跳ねたときだけ消える。
- movingの位置は `u = (tick × speed + phase) mod (2 × span)`、左端は `lo + (u <= span ? u : 2 × span − u)`。全種類で着地時の跳躍速度は同じ。

### 不変条件と到達性

1. **段差は実際の頂点の82%以下**: 最大128px ≤ 128.975px。これは静止・動く鎖の両方に適用する。
2. **どの位相でも直接距離が D(i) 以下**: 前の名目中心からの候補範囲を `D(i) − 前の移動半幅 − 今の移動半幅` に制限する。必須movingの半幅は48px。したがって離陸時と着地時の位相が違っても、中心間の距離は最大170px。折り返しを必要としない。
3. **必要水平速度は最高速の70%以下**: 上記の移動範囲全体で最悪の距離を、離散物理でその高さへ降りてくるまでの時間に割る。最大段差128pxでは72ステップ、最悪170pxなので283.3px/s(最高速600の47.2%)。静止時だけの距離で保証したことにはしない。
4. **種類と配置**: 必須movingの前後はstatic、挑戦中の追加足場はなし。vanishingは鎖へ入れない。各区間に3〜5段の静止した休息を確保する。
5. **盤に収まる**: 静止足場もmovingの全移動範囲も `[0,360]` px内。Normal/Wide双方で成り立つ。

`game/generate.test.ts` が1,000 seed ×2幅 ×2,000段(400万段)の不変条件と決定性を検査する。別の40 seed ×2幅では初出・区間長・交互の切り返し・静止した休息・movingを跳び越す経路がないことを検査する。

`game/bot.test.ts` は実際の `step` で、参照ボット200 seed ×2幅を2,000段まで走らせる。botは最高速の75%で次の鎖の現在位置を追う。8万本の鎖を70%速度で単独に跳ぶ検査も保持し、最初の着地が次の鎖であることを要求する。

**位相・復帰を独立に検査**: 移動範囲全体の距離170px、段差90/128px、左右両側、Normal/Wideの端点形を手で組み、位相0の往復1周期384tickを全走査する。生成で取りうるサブピクセルの全位相を実stepで総当たりしたわけではない。任意の位相での到達性は上記の全移動範囲の解析条件が保証し、この検査は周期内の位置・方向・折り返し・復帰を物理で裏付ける。実際のカメラ・足場の除去・落下終了判定を使い、70%速度で進入・退出・前の静止足場への帰還・同じmovingへの再着地を確かめる。中心からの4経路には150msの反応待ちも入れる。端に着地した後の退出は反応待ちなしで検査する。前進と同じmovingへの再着地は**最初の着地**で成功する必要があり、低い足場への帰還だけはmovingが通り過ぎるまで跳ね直してよい(800ステップの上限)。これは完全な位置追従による到達性の証明で、人の手触りの検証ではない。

### 仕事量

- 生成は再試行・経路探索をせず、区間用2個のPRNGと段用1個のPRNGを定数回使う。1段で最大12回の整数乱数。
- 画面上端の160px先まで生成。1ステップ最大4段、開始時最大40段で止め、残りは次のステップへ。画面下端より64px下の足場は捨てる。ランが長くなっても保持する塔全体を積み直さない。
- 既存の `MAX_STEPS_PER_FRAME = 6` は変更しない。数値・物理・入力・保存スキーマの変更はない。

## 4. 状態と操作

### 状態

`ready` → `running` ⇄ `paused` → `over`(`RunStatus`)。

- **`ready`**: 主人公は床の中央に立ち、世界は止まっている。**最初の入力(盤の押下・ドラッグの開始・
  ← → / A D・◀ ▶ の押下・Space・上部バーの ▶)で `running`**(`start`)— 跳ね始める(vy = 760)。ゲームを
  開いただけで 1 回分を失うことは無い(Bunny Hop §2)。
- **`running`**: `step` が世界を進める。
- **`paused`**(`pause`): `running` からだけ入る。**押しっぱなしの入力(キー・◀ ▶・ドラッグの遅れ)を捨てる**:
  目標の x を体の x にそろえ、押している向きを 0 にする。UI も押しているキー・◀ ▶・指の記録と、まだステップに
  渡していない指の移動量を捨てる。再開(`resume`)は**プレイヤーの操作だけ** — 盤のタップ・Resume のボタン・
  Space。**← → / A D と ◀ ▶ では再開しない**(押しっぱなしのまま戻って、意図せず動き出さないように。Phase 3 で
  決めた)。止める理由と再開の規則は下の「止まるとき」。
- **`over`**: 体が画面の下へ落ちた。`step` は何も変えない。
- `ready` / `paused` / `over` の間、`step` は**同じ状態のオブジェクトをそのまま返す**(遅れて着いたフレームが
  止まった世界を動かさない — Snake §6)。`start` / `pause` / `resume` も、当てはまらない状態では同じ
  オブジェクトを返す。

### 幅(Normal / Wide)

- **選ぶ場所はゲームのホームだけ**: Normal / Wide の 2 択の切り替えを置く(`ui/screens/HomeScreen.tsx`)。盤の上・上部バー・
  結果カードには置かない。選んだ幅は `bo.prefs` に残る(§5)。
- **次のランから効き、ランの途中では変わらない**: 幅はランを作るとき(`createRun(seed, width)`)に決まり、
  ランの状態が持つ。途中保存が無く、ホームへ戻ればランは終わる(下の「止まるとき」)ので、走っているランの
  幅を変える経路は無い。
- **↻ と結果カードのリトライは、いまのランの幅で**新しい seed の `ready` を作る。幅を変えられるのはホームだけで、
  ホームへ戻ったときにランは終わっているので、いまのランの幅は `bo.prefs` の幅と同じになる(違うのは `bo.prefs`
  の書き込みに失敗したときだけで、そのときもプレイヤーが選んだまま遊べる側に倒す)。
- **既定は Normal で、選ばなくても始められる**(Snake §7 と同じ。最初から選択を強制しない)。初回の Quick Rules
  の後はそのまま Normal の `ready` の盤が開き、最初のタップで走り出す — 幅を選ぶ手順は挟まない。
- 記録は幅ごとに分ける(§5)。

### 止まるとき(バックグラウンド・blur・Back・❚❚)

- **バックグラウンド**(`visibilitychange` の hidden・native の pause): `running` なら `paused`。**復帰しても
  タップまで再開しない**(Snake §6 と同じ)。Bunny Hop の盤面は画面が見えると走りを再開するので、ここは
  意図的な差分(§9)。バックグラウンドに入るときは、そこまでのプレイ秒と到達高を計上する(§5)。
- **ウィンドウがフォーカスを失ったとき**(`window` の `blur`)も `paused` にする(Snake §6 と同じ。PC の
  キーボードの人が別のウィンドウへ移り、戻ったら落ちていた、を起こさない)。アーケード 4 本(Brick Breaker /
  Sky Fighter / Bubble Pop / Bunny Hop)は blur で止めないので、意図的な差分(§9。§12 の決定)。
- **❚❚**(上部バー): 無料・無制限・確認なしで `paused`(Snake §6 と同じ)。同じ位置の 1 つのボタンが、
  `running` の間は ❚❚(Pause)、`paused` では ▶(Resume)、`ready` では ▶(Start)になる(Overtake と同じ形)。
  キーでは **P と Esc** で止める(Overtake・Snake と同じ。この画面にはダイアログが無いので、Esc が答えるものは
  他に無い)。再開は盤のタップ・Resume・Space。Space はボタンにフォーカスがあるときはボタン自身のキー操作に
  任せる(Bunny Hop §3)。キーの押しっぱなしの繰り返し(`repeat`)では、始める・再開する・止めるのどれも起きない。
- **Back**(§12 の決定):
  1. **ゲーム内の ←** と **Web のブラウザの戻る**(Root のアンマウント)は、そこまでの到達高と秒を計上して
     からランを終え、**確認なしで**ゲームのホーム(← の場合)/ コレクション(ブラウザの戻るの場合)へ戻す。
     途中保存が無いので、離れればランは終わる(Sky Fighter §10・Bunny Hop と同じ)。到達高は記録に入る(§5)。
  2. **ハードウェア Back**(Android。唯一の持ち主は GameContext)は、`running` 中の 1 回目では `paused` に
     するだけにし、`paused`(と `ready`・`over`)から押したらホームへ。横ドラッグが画面端からのスワイプの
     「戻る」と重なりうるので、1 回の誤操作でランを失わないようにする。**これは正式収録の後の native だけの
     挙動で、Web ベータには当てはまらない**(Web ベータでは native のビルドの扉が開かない —
     `app/gameChannel.ts`)。Web ベータで効くのは 1 だけ。
- **↻**(上部バー): **確認なしの即時リトライ**(新しい seed・いまのランの幅の `ready` — 上の「幅」)。`tryAgain` のラベルも `RestartDialog`
  も使わない(Bunny Hop の `bunnyRunAgain` と同じ。`src/test/restartDialogWiring.test.ts` がアーケードに許して
  いる形)。捨てるランの到達高と秒は、同じ 1 本の計上で記録に入れてから始める(§5)。失うのは数十秒の
  そのランだけ。

### 入力(`game/input.ts` と `step` の入力)

`step` の入力は 1 ステップに 1 つ: `{ drag, dir }`。

- `drag`: このステップに渡す**指の横の移動量**(1/120 px 単位の整数、正が右)。
- `dir`: 押している向き(−1 = 左、0 = なし、1 = 右)。← → / A D と ◀ ▶ から作る。

**相対ドラッグ**(Sky Fighter §3 の形を左右だけにしたもの):

- 指の横の移動量を、**盤面上の見た目で 1:1** に目標の x へ写す: 論理 px = CSS px の移動量 ÷ 盤の倍率
  (CSS px / 論理 px)。`dragUnits(dxCss, scale)` が整数の単位へ丸める(`Math.round`)。倍率が 0 以下・有限で
  ない(レイアウト前の盤)・移動量が有限でないときは 0 を返す(閉じる側に倒す — Overtake §1 と同じ)。
- 体は目標の x を**最高水平速度で**追う(§2 の手順 3)。**目標と体の差は `LEAD_MAX` = 48 px を超えない**
  (超えた分の指の動きは捨てる)。指を止めれば、体は最大 48 px 進んで止まる(Phase 2 のテストで実測: 9 ステップ = 0.075 秒) — 指を止めた
  後も体が流れ続けることを防ぐ(計画)。指を止めた位置と体が止まる位置の差も 48 px を超えない。
- 盤の**どこから触れてもよい**(指が主人公を隠さない)。押下の位置は使わない — 移動量だけを使う。
- **折り返しをまたぐときの目標**: 目標は折り返さない連続の座標で持つ(§2 の手順 3 で、体が端を越えたときに
  体と目標を同じ量だけずらす)。指を右へ動かし続ければ、体は右の端から出て左の端から入り、そのまま右へ
  進む。描画と当たり判定のときだけ幅の剰余を取る。
- 1 フレームに複数のステップを回すときは、そのフレームまでにたまった移動量を**最初のステップに全部**渡し、
  残りのステップは 0 を渡す(移動量を捨てず、二度数えない)。

**キーと ◀ ▶**:

- ← → / A D と ◀ ▶ は**押している間だけ**動く: 押している間、目標の x を「体の x + 向き × 48 px」に置く
  (体は最高速で動く)。**離したステップで目標を体の x にそろえる**(押している間にたまった遅れで流れない)。
  両方を押せば 0(動かない)。
- キーとドラッグを同時に使ったときは、押している向きがあるステップではキーが勝つ(ドラッグの移動量は
  そのステップでは捨てる)。
- ◀ ▶ は**タッチ端末でだけ**盤の下の左右の角に重ねて出す(押している間だけ動く、名前付きのボタン「Move left」
  「Move right」)。出す条件は CSS の `@media (any-pointer: coarse)` で、JS で判定しない(§12。キーボード付きの
  iPad と、タッチ付きの PC で実際に見て確かめる — 未検証)。DOM にはいつもあり、CSS が隠すだけ。
- ◀ ▶ の**キーボード・支援技術のクリック**(押下を伴わないクリック、`detail === 0`)は、目標をその向きへ
  `LEAD_MAX`(48 px)だけ 1 回動かす(押している間だけ動くボタンを、押し続けられない操作でも使えるように。
  Overtake の ◀ ▶ の 1 段と同じ考え)。押下の後に残るクリックは使い済みとして捨てる(押している間にもう動いて
  いるので、二度動かさない)。ステップが読む前に離された押下の後のクリックは、その 1 回分として働く。
- ポインタの契約([ARCHITECTURE.md](ARCHITECTURE.md)「指を取り上げられたときの契約」「押下の記録は誰のものか」。
  Phase 3 で実装): ドラッグ(canvas)と ◀ ▶ は、`onPointerUp` を聞く要素で `onPointerCancel` と
  `onLostPointerCapture` も聞き、どれも同じ後始末をする。押下の記録に `pointerId` を持たせ、2 本目の指は 1 本目の
  記録を上書きしない(ドラッグを握らない)。`setPointerCapture` を使う(失敗しても動く)。マウスの左ボタン以外の
  押下は無視する。cancel の後には `click` が来ないので、使い済みの印も取り消す。

### スコアと高さ

- 高さは**床の上面からの足元の高さ**(論理 px)。最大の高さ `maxHeight` は、上昇中の頂点も含めて、ランの間に
  足元が届いた最も高い位置(`running` の間の `step` だけが更新する)。
- **スコア = floor(maxHeight / 10 px)**(`SCORE_PX = 10` は初期値)。1 段の段差 48〜128 px は 4〜12 点に
  当たる(算術)。床で跳ねているだけでも頂点の 157 px で 15 点になる(算術。0 点のランは、開いて何もしない
  まま離れたときだけ — `ready` では高さが増えない)。
  - 単位の語(m など)を付けない理由: 訳が要り、実寸でもないため(計画の推奨)。
  - 係数 10 の理由: 段差 1 つが 1 桁の点(4〜12)になり、1 回の跳ねの違いが点に表れる。Bunny Hop の
    40 px = 1 点では、1 段が 1〜3 点になって段ごとの違いが読めない。数字は 5 桁に収まる見込み(旧生成の算術では段 1500
    でおよそ 1.3 万点。Phase 2 のテストで実測: 参照ボットが段 2,000 に乗った時点で 18,330〜18,528 点 — §3)。
- **到達した段** `reachedSegment`: 乗った足場の段の番号の最大(鎖でも追加でも)。記録には使わず、参照ボットの
  踏破とテストに使う。
- **自己ベストの線**(§7): ランの開始時点のその幅の自己ベスト(点)× 10 px の高さに、盤を横切る細い線を
  描く(Bunny Hop のコース上の数字と旗とは形を分ける — 計画)。ランの途中で記録が伸びても線は動かない。
  `bestLineHeight(bestScore)`(`game/score.ts`)が高さを返す。線は点から戻した高さなので、本当の最高の高さ
  より最大 9 px 低い(線を越えた時点では、まだ記録を抜いていないことがある — 抜いたかは点で決まる)。

## 5. 保存と統計

**Phase 3 で実装した**(`storage/keys.ts`・`storage/schemas.ts`・`state/statsLogic.ts`・`state/GameContext.tsx`。
`src/app/gameKeys.test.ts` の自分の行も同じコミットで 3 キーにした)。

- **保存キーは 3 つ**: `bo.stats` / `bo.flags` / `bo.prefs`。他ゲームのキーには触れない。
- **ランの途中保存は作らない**(Bunny Hop §10 と同じ)。空中の実時間の状態は、マス目の離散状態のようには
  正直に戻せない(Snake との違い — §9)。そのため `saveGame` も `storage/gamePersistence.ts` も無く、Root は
  `entry` を受け取らない(ショートカットはゲームのホームへ。`src/test/shortcutResumeWiring.test.ts`)。
  デイリーが無いので 2 スロット規則は関係しない。

| キー       | 形(v1)                                                                                                           | 既定       |
| ---------- | ---------------------------------------------------------------------------------------------------------------- | ---------- |
| `bo.stats` | `{ schemaVersion: 1, played, best: { normal, wide }, total: { normal, wide }, totalPlaySeconds }` — 0 以上の整数 | すべて 0   |
| `bo.flags` | `{ schemaVersion: 1, tutorialCompleted }` — 真偽                                                                 | `false`    |
| `bo.prefs` | `{ schemaVersion: 1, width }` — `'normal'` か `'wide'`。ホームで選ぶ。次のランから効く(§4「幅」)                 | `'normal'` |

- **`played`**: `ready` → `running` で 1 回数える(Snake §10)。↻ の後のランも、動き出せば 1 回。
- **幅ごとの最高**(`best`): その幅のランのスコアの最大。
- **累計**(`total`): その幅の**各ランのスコアの和**(計画の推奨)。何回登ったかではなく、どれだけ登ったか。
- **`totalPlaySeconds`**: `running` の間だけ数える(`ready`・`paused`・結果の画面は数えない)。
- **途中で離れたランの到達高も、最高と累計に入れる。**Bunny Hop(§10)も Sky Fighter(§10「離れた場合、
  そのランは破棄される」)も離れたランの点を捨てるので、アーケードのどの前例とも違う意図的な差分(§9)。
  バックグラウンドでも、そこまでの秒と到達高を書く(OS がそのまま終わらせても失わないため)。
- **計上は 1 本**: 到達高も秒と同じ bookedRef 方式で、**計上済みの点との差分だけ**を累計に足し、最高は
  max で更新する(何度呼んでも二重に数えない)。終局・↻・退出・バックグラウンド・blur・❚❚・アンマウントは、
  同じ 1 本の計上を呼ぶ([GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「計上の経路を増やさない」)。計上の置き
  場所は、スキャフォールドが `state/GameContext.tsx` に置いている `useOnUnmount(syncActiveGame)` の 1 本にし、
  ランの状態とプレイ時計も Provider が持つ(Overtake §9 と同じ形 — 盤面の cleanup の `flushSeconds()` は
  持たない。門は `src/test/unmountBookingWiring.test.ts`)。毎フレームは書かない。
  - 差分の計上の純関数 `bookRun(booked, score)`(`game/score.ts`): 計上済みの点 `booked` と今のスコアから、
    累計に足す差分と新しい `booked` を返す。スコアは単調に増える(`maxHeight` は下がらない)ので差分は 0 以上。
- **受け入れない記録**(fail-closed。`storage/schemas.ts`): 版が 1 でない・型が違う・負や小数の数・範囲外
  (回数と最高は 10⁹ まで、合計と秒は 10¹⁵ まで)・幅が `normal` / `wide` 以外・幅ごとの値が欠けている。さらに
  **遊びから生まれえない記録**も受け入れない: ある幅の最高がその幅の合計より大きい(最高のランも合計に入って
  いるはず)、合計が 0 より大きいのに `played` が 0(点は数えたランにしか付かない)。どれもレコードごと既定値に
  倒す(共有の `loadRecord` の扱い。フィールドを継ぎはぎしない)。保存の失敗はゲームを止めない。
- **ランの状態と計上の置き場所**: 世界(体・足場・押している入力)は盤のコンポーネントの ref にあり、Provider は
  状態(`ready` / `running` / `paused` / `over`)とプレイ時計と点の計上を持つ。盤はスコアが変わるたびに
  `noteScore` で Provider の ref に知らせ(再描画しない)、落ちたステップで 1 回 `finishRun` を呼ぶ。Provider の
  `syncActiveGame` が唯一の計上の経路で、`running` なら `paused` にしてから、計上済みの秒(`bookedRef`)と点
  (`bookedScoreRef`)との差だけを `applyBooking`(`state/statsLogic.ts`)で 1 回の書き込みにする。
- **結果カードの自己ベストとの差**は、ラン開始時点のその幅の最高と比べる(バックグラウンドの計上でランの途中に
  最高が上がっていても、差はランの前の記録に対して言う)。
- **レビュー依頼**(`recordGameCompleted()`)は呼ばない — 「クリア」が無い(Bunny Hop と同じ)。

## 7. 画面と寸法

**Phase 3 で実装した**(`ui/`)。寸法は CSS の式からの**算術**と、**ヘッドレス Chromium で測った**値の両方を
書く(下の「測った寸法」)。jsdom はレイアウトを持たないので vitest では測れない。実機では測っていない。

### 描画とループ

- **描画は Canvas + RAF**(アーケード 4 本と同じ。`ui/components/BounceStage.tsx`)。**RAF は `running` の間だけ回す**。
  `ready` / `paused` / `over` / バックグラウンドではループを止め、状態が変わったとき・テーマや大きさが変わったときに
  1 回描くだけにする。状態が変わるたびにループの時計を捨て、次のフレームは時刻を取るだけにする(止まっていた時間を
  持ち込まない — §2)。
- フレームは `frameSteps`(§2)で固定ステップに換え、そのフレームまでにたまった指の移動量を最初のステップに渡す
  (`frameInputs`)。指の移動量は CSS px のまま足しておき、整数の単位にならない端数は次のフレームへ持ち越す。
- アンマウントで RAF・キーのリスナー・resize のリスナー・ResizeObserver・MutationObserver・色の変化の購読・DEV
  シーム `__boFrame` / `__boState` を解放する(`ui/BounceUpRoot.leak.test.tsx`)。
- 色はすべてトークン(`--surface` / `--line` / `--ink` / `--ink-soft` / `--accent` / `--accent-soft`)を computed
  style から読む。`ui/bounce-up.css` にも `ui/draw.ts` にも色の値は書かない(jsdom 用の代わりの値だけ)。Chromium 88 を
  下限に、角は二次曲線で作る(`roundRect` を使わない)。

### 盤の大きさ

- `.bo-stage` の幅 = `min(100%, 540px, (100svh − 104px − 予約) × 9/16)`(`100svh` を知らない端末には `100vh` の
  同じ式)。104px はヘッダ 64・状態の行 24・盤の上下の余白 16。Web の広告予約は `:root[data-sg-web-ads]` のとき
  116px、アプリでは 0。高さは `aspect-ratio: 9 / 16` で幅から決まる(縦につぶれない)。上限 540px は論理の 1.5 倍
  (初期値)。canvas の裏の画素は表示の幅 × devicePixelRatio(2 まで)で、ResizeObserver が追う。
- 算術では:
  - **360×640・Web(予約 116px)**: 盤は 236×420 CSS px(倍率 0.66)。主人公の上に見える 360 論理 px は約 236 CSS px で、
    段差は 128 px 以下なので、主人公の上に足場が 2 段以上見える(§2「カメラ」。計画の下限)。
  - **360×640・アプリ(予約なし)**: 301×536 CSS px(倍率 0.84)。
  - **広い画面**: 幅 540px(高さ 960px)で止まる。
  - **横向きの電話・Web(568×320)**: 予約を引くと使える高さは 100px で、盤は 56×100 CSS px(倍率 0.16)。遊べる
    大きさではない(下の「横向きの電話」)。
- ◀ ▶ は盤の下の**左右の角に重ねる**(盤の外に行を足さない)。そのため ◀ ▶ を出しても盤の大きさは変わらない。
  1 つの幅は `min(64px, 盤の幅の半分 − 15px)` で、盤が 158px より狭いと縮み、2 つが重ならない(横向きの電話で

- **受け入れる(遊べる形にはしない)** — Overtake §11 と同じ決定。盤は 9:16 の縦長で、高さから幅が決まる。
  568×320 の広告予約ありでは 56×100 になり見えも操作もできないが、ページは崩れずスクロールも出ず、◀ ▶ は
  縮んで重ならない。回転を促す案内は出さない(翻訳の要る文を 1 つ足し、盤の代わりに出す状態をもう 1 つ持つ
  ことになる。アプリは縦向き固定で、横向きは Web だけの形)。予約を外す形も作らない(広告の予約はシェルの
  決まりで、ゲームが外すものではない)。横向きで遊べるかは、正式収録の前に実機で見直す。

### 盤の上のもの(色だけに頼らない)

- **足場**はどれも雲の形: 上の辺は平らで(乗る判定の線 — §2)、下の辺は波形。種類は輪郭と塗りで分かれ、色は補助:
  - static: アクセントで塗りつぶした雲。床(段 0)も static で、盤の幅いっぱい。
  - moving: アクセントの淡い色で塗り、アクセントの縁取り。**両端の外に外向きの三角**(往復の記号。インク色)。
  - vanishing: **破線の輪郭だけ**(塗らない。インクの淡い色)。1 回跳ねるとその場で消える(消える演出は無い)。
    `ui/draw.test.ts` が、3 種類の描画の呼び出し(塗り・縁・破線)が違うことを確かめる。
  - **ヘッドレス Chromium で見た**(2026-10-22。`ui/draw.ts` の `drawRun` を、参照ボットと同じ狙い方で Wide の段
    20・320・650・700・820・940・1000・1300 まで登った状態で、360×640 の Web の盤の大きさ 236 CSS px・DPR 2 で
    描いた): 3 種類は、明るいテーマ・暗いテーマ・Chromium の色覚の模擬(1 型・2 型・3 型・全色盲)のどれでも
    形(塗りつぶし / 淡い塗りと両端の三角 / 破線の輪郭)で見分けられた。**暗いテーマの vanishing の破線は
    地とのコントラストが低く、細くて薄い**。自己ベストの破線も同じインクの淡い色だが、盤を横切り両端に
    三角があるので短い足場とは形が違う。人の目・実機の画面での見分けやすさは未検証(§10)。
- **主人公**は自作の形(§9.4): 角の丸い滴の形の体(インク色、28×28 px)に、目 2 つ(地の色の小さな四角)と頭の
  芽(茎とアクセントの葉 1 枚)。四本足の生き物ではない。跳ねた後の 8 ステップだけ横 1.14 倍・縦 0.82 倍につぶして
  描く(飾り — Reduced Motion では描かない)。左右の端をまたぐときは、反対の端にも描く(`wrappedCentres`)。
- **背景**は地の色の無地。方眼の罫線も雲の点描も描かない(§9.4)。
- **自己ベストの線**: ランの開始時点のその幅の自己ベスト(点)× 10 px の高さに、盤を横切る破線と、両端の内向きの
  小さな三角。自己ベストが 0 なら描かない。ランの途中で記録が伸びても線は動かない(§4)。
- 盤の上に文字・数字は描かない。

## 9. 意図的な差分

### 9.1 「急かさない」の整理

- 画面は自動では上へ流れない。同じ足場で跳ね続ければいつまでも落ちない。時計・時間制限・カウントダウンは
  無い。消える足場は時間ではなく「1 回跳ねたら」消える(§3)。ランの難しさは高さ(段の番号)だけで決まり、
  経過時間では変わらない。
- 「落ちたら終わり」はリアルタイムの反射の遊びそのもので、ライフやコンティニューで薄めない。代わりに
  即時リトライが無料・無制限・確認なし。

### 9.2 既存の収録ゲームとの違い

- **Bunny Hop**(エンドレス記録型・自動の動き): **復帰で再開しない**(Bunny Hop の盤面は画面が見えると
  走りを再開する — §4)、**離れたランも記録する**(§5)、**左右の相対ドラッグ**(Bunny Hop は跳ぶ 1 つの入力)、
  **blur で止まる**。記録の見せ方はコース上の数字と旗ではなく、上部バーの数字と盤を横切る線。
- **Snake**(エンドレス記録型・止まる規則が同じ): **途中保存をしない**(空中の実時間の状態は、マス目の離散
  状態のようには正直に戻せない)。↻ は RestartDialog ではなく確認なしの即時リトライ。
- **Sky Fighter**(相対ドラッグ・同じ 360×640): 左右だけで、射撃・ライフ・強化・ボスが無い。離れたランの
  点を捨てない。
- **Overtake**(固定ステップ・Canvas・同じ 360×640): 面が無くエンドレス。結果は高さで、ライバルも着順も
  無い。
- **離れたランの到達高を数える**のはアーケードのどの前例とも違う(Bunny Hop §10 と Sky Fighter §10 は
  捨てる。近いのは Sky Fighter §9 の「失敗したランの得点も立つ」だが、あれは終わったランの話)。理由:
  ゲームの外の出来事(電話・通知・OS の終了)で、登った高さを失わせない。途中保存が無い代わりに、離れた
  時点の到達高を正直に記録する。
- **blur で止まる**のはアーケード 4 本と違う(Snake と同じ)。
- **↻ は確認なしの即時リトライ**(アーケードの慣例。Bunny Hop と同じ形)。

### 9.3 このジャンルの他の実装と合わせないもの

- コンティニュー・復活・ライフ・パワーアップ(プロペラ・ジェットパック・ばね・トランポリン)・敵・射撃・
  コイン・ショップ・はねる足場は作らない(はねる足場は v1 では作らない — 計画)。
- 画面が自動で上へ流れる形(時間の圧力)は作らない。時間で崩れる足場も作らない。
- デイリー・オンラインランキングは無い。

### 保存・状態・画面・文言のテスト(Phase 3。jsdom で確かめた — 数は測っていない)

画面のテストは、2D の文脈を差し替えた canvas の上で本物のループを回し、jsdom 自身のフレームを止めて、DEV
シーム `__boFrame` だけを時計にする(`ui/test-driver.ts`。1 フレーム = 1000/120 ms = ちょうど 1 ステップ)。
プレイ時計は `Date.now` を止めて手で進める。seed は `Date.now` と `Math.random` から作られる(§3)ので、
`Math.random` も決まった列に置き換える(`holdEntropy`。k 回目に k·φ の小数部 — 呼ぶたびに違う値なので、
やり直しは別の seed になる)。どのテストも、走らせるたびに同じ塔を登る。jsdom には matchMedia が無く
Reduced Motion と読まれるので、結果カードは落ちたフレームに出る。

  より大きい・`played` 0 で点がある、をレコードごと拒み、読み込みでは既定値に倒れる。

  返す、計上済みの点を下げない、NaN の秒は 0、出てくるレコードはどれもスキーマが受け入れる。
- **⑦ 主要操作の UI**(`ui/BounceUpRoot.test.tsx`、21 件):
  - Quick Rules の 3 ステップ(図の canvas・← → の文)から Normal の `ready` の盤へ、`bo.flags` が書かれる。
    幅の選択が `bo.prefs` に残り次のランが Wide になる(足場の幅 96 px)。保存した Wide と幅ごとの記録がホームと

    1 回だけ(一時停止と再開では増えない)。上部バーのスコアは床で 1 回跳ねて 15 になる。
  - キー: 押している間 1 ステップ 600 単位、離したステップで止まる、A と D の両押しは動かない。P と Esc で止まり、
    ← → では再開せず、Space で再開する。フォーカスのあるボタンの Space と押しっぱなしの繰り返しには答えない。
  - ドラッグ: 指の 10 px で目標が 10 px(1:1)、体は 1 ステップ 600 単位で追う。2 本目の指は握らない。
    `pointercancel` でジェスチャーが終わり、その指の移動は効かない。次の指は握れる。一時停止中の指の移動は捨てられ、
    盤の押下で再開する。
  - ◀ ▶: 押している間だけ動き、`pointerup` と `pointercancel` で止まる。押下の後のクリックは使い済み(二度動かない)、
    押下を伴わないクリックは目標を 48 px 動かす。`ready` では押下で始まり、`paused` では再開しない。

    フレームを回してもステップが進まない。

    記録は `played`・幅ごとの最高と合計・秒がそれぞれ 1 回ずつ増える。Climb again で同じ幅の新しい seed の `ready`。
    途中のバックグラウンドで計上した後に落ちても、合計は最後の点だけ(足し直さない)。↻ は確認なしで新しい seed の
    `ready` にし、捨てたランの点を計上する。← ホームとアンマウント(ブラウザの戻る)も 1 回ずつ計上し、
    マウントし直しても増えない。
