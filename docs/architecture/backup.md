# バックアップと復元

docs/ARCHITECTURE.md から参照される全文(2026-09-08 追加、issue #160)。索引と要約は [../ARCHITECTURE.md](../ARCHITECTURE.md)。

実装は `apps/simple-games/src/backup/`。UI は設定画面の `Backup & Restore` 節だけ。

## なにを解決していて、なにを解決していないか

Simple Games はアカウント・クラウドセーブ・バックエンドを持たない。持たないと決めた
以上、**機種変更・端末初期化・ブラウザのサイトデータ削除で進行がすべて消える**という
摩擦は、こちらで引き受けるしかない。30 本ぶんのレベル進行・記録・デイリー履歴・
中断中の局が積み上がった段階で、これは無視できる大きさではない。

引き受け方は 1 つだけ: **ユーザーが自分でファイルを書き出し、自分で運ぶ。**

したがって、この機能は次のどれでもない。追加もしない。

- account / login / authentication backend
- cloud database / synchronization service / background sync
- conflict resolution / per-game merge
- backup history manager / 定期バックアップの催促 / 未バックアップ警告バッジ
- 暗号化・パスワード UI(初期版)

> Simple Games はデータの転送サービスを持たない。持ち出せる形だけ提供する。

転送手段(AirDrop / Quick Share / ドライブ / メール / USB)はユーザーが選ぶ。
アプリは書き出したファイルを OS へ渡した時点で手を離し、**どこへ行ったかを知らない。**
`docs/PROJECT_CONTEXT.md`「ゲームデータを端末外へ保存しない」に反しない — 端末外へ
出すかどうかを決めるのも、出す先を選ぶのもアプリではなく利用者だからである。

## ファイル形式(長期互換の contract)

```json
{
  "formatVersion": 1,
  "createdAt": "2026-09-08T09:30:00.000Z",
  "appVersion": "1.2.2",
  "platform": "android",
  "data": {
    "sg.settings": { "schemaVersion": 1, "language": "ja" },
    "sd.progress": { "schemaVersion": 2, "highestUnlocked": 12 }
  }
}
```

| 項目            | 決定                                                                                                                                |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 拡張子          | **`.json`**。専用拡張子は作らない。ピッカー・メール・ドライブが既に扱いを知っている形が、機種変更当日にいちばん壊れにくい           |
| ファイル名      | `simple-games-backup-YYYY-MM-DD.json`(日付はローカル日付。読む人のためのもので、正確な時刻は `createdAt` にある)                    |
| `formatVersion` | **容器の版**。ゲームの save schema の版とは無関係で、容器の形が変わったときだけ上がる                                               |
| `createdAt`     | ISO 8601。復元の確認ダイアログに出す                                                                                                |
| `appVersion`    | 参考情報。**復元の可否を決めない**                                                                                                  |
| `platform`      | 参考情報。`android` / `ios` / `web`。**OS で復元を制限しない** — Android ↔ iOS ↔ Web は同じファイルで行き来できることが目的そのもの |
| `data`          | 「ストレージキー → そのレコードのパース済み JSON」。二重エンコードしない。人間が開いて読める                                        |

`data` のキーがストレージキーそのものなのは、所有の宣言が既に 1 か所
(`app/registry.ts` の `storageKeys`)にあるからである。バックアップ用の別名を
発明すれば、正しく保ち続ける対象が 2 つになる。

## なにを入れ、なにを入れないか

**入れる**: `app/registry.ts` が宣言する全ゲームの全キー(レベル進行・統計・記録・
デイリー履歴・中断中の局・ゲーム固有設定)と、シェル側の `sg.settings` /
`sg.favorites` / `sg.recent`。

**入れない**(`src/backup/keys.ts` の `SHELL_KEYS_LEFT_BEHIND` に理由ごと書いてある):

| キー        | 理由                                                                                                                                                                                                                                                                         |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sg.iap`    | **規則。判断の余地はない。** 広告削除の entitlement は Play / App Store が与えるもので、ここにあるのはその答えのキャッシュにすぎない。ファイルはコピーできるので、これを入れた設計は「コピーできる買い切り」になる。機種変更時はストアから購入を復元する(docs/ADS_POLICY.md) |
| `sg.review` | ストアレビュー導線の間隔。**このインストールで何が起きたか**を数えており、答えたら二度と出ない。持ち込めば、答え済みの質問が復活するか、まだ訊いていない質問が黙って消える                                                                                                   |

将来 platform-owned な entitlement が増えた場合も、同じ理由で入れない。

**構造的な門**: `src/backup/keys.test.ts` が「`STORAGE_KEYS` の全キーが、運ぶ側か
残す側のどちらかに必ず載っていること」を検査する。新しい共有レコードを足したら、
どちらかを選ぶまでテストが赤になる — 黙っていることが決定に見えてしまうのを防ぐ。

## 検証は各レコードの持ち主が行う(バックアップ層は save を解釈しない)

30 本の save 形式を理解するバックアップは、その 31 本目のコピーである。そしてその
コピーは腐る — ゲームが schema を変え、そのゲームの migration は追随し、
バックアップが密かに持っていた「そのゲーム像」だけが取り残される。

そこで、レコードの検証は**そのレコードの `SchemaDef`** が行う。`validate` は
throw せず、古い版なら migration も兼ねるので、**古いバックアップは各ゲーム自身の
migration を通って入る**(`src/backup/backup.test.ts` に Sudoku の v1 progress で
実例がある)。

スキーマへの到達経路はレジストリである。`GameDefinition.loadStorageSchemas` は
**必須フィールド**で、31 本目のゲームを `loadStorageSchemas` なしで足すことは
コンパイルエラーになる。シェルが `src/games/` へ静的にも glob でも踏み込めない
(`src/test/importBoundaries.test.ts`)以上、これがレジストリ経由で一本化する唯一の形で
あり、同時に「入れ忘れ」を型で潰す形でもある。`src/backup/keys.test.ts` は逆側から、
宣言された全キーが実際に schema へ解決することを確かめる。

読み込むのは**ファイルが実際に言及しているゲームだけ**。4 本しか遊んでいない人の
復元は 4 本ぶんのチャンクしか触らない。

## 復元の安全性(この機能でいちばん重要な部分)

原則は 4 つ。

1. 検証が終わるまで、現在のデータへ 1 バイトも書かない
2. 部分適用を許さない
3. 未知 / 壊れた / 新しすぎる payload を黙って適用しない
4. 途中で失敗したら、元データを壊さない

これを型で表しているのが `readBackup` と `applyBackup` の分割である。`readBackup` は
何も書かず、成功したときだけ**書き込む文字列まで用意し終えた** `PreparedRestore` を
返す。`applyBackup` はそれ以外を受け取れない。「確認は検証の後」「書き込みは確認の後」
が、呼ぶ順番の約束ではなく型の性質になる。

### 検証項目

- 容器全体のサイズ上限(4MB)。**パースする前に測る**
- root が object であること、`formatVersion` が 1 以上の整数であること
- `createdAt` が日付として読めること、`appVersion` / `platform` が文字列であること
- `data` が配列でない object であること
- **危険なオブジェクトキー**(`__proto__` / `prototype` / `constructor`)の拒否
- **strict known-key validation** — このビルドが所有していないキーが 1 つでもあれば拒否
- レコードごとに持ち主の `validate` を通し、1 件でも通らなければ**復元全体を拒否**
- レコード 1 件あたりのサイズ上限(256KB)

### 版の互換

| 状況                            | 挙動                                                                                      |
| ------------------------------- | ----------------------------------------------------------------------------------------- |
| 古いバックアップ → 新しいアプリ | 各ゲームの既存 migration を通して読む                                                     |
| 新しいバックアップ → 古いアプリ | **拒否する**(`newer`)。理解できない部分を黙って捨てて「復元成功」と言うことを禁止する     |
| 未知のキー                      | 初期版は **strict reject**。ほぼ確実に「まだ持っていないゲーム」なので `newer` として扱う |

未知キーを保存して素通しする案(forward compatibility 寄り)は採らなかった。
Simple Games は「保存領域の所有者を明確にする」側の設計であり、所有していないキーは
検証もできない。検証できないものを書くくらいなら、アプリを更新してくださいと言うほうが
正直である。

### トランザクション

1. `backupKeys()` の全キーについて、現在の文字列を snapshot する
2. 書く。ファイルにあるキーは値を、**ファイルに無いキーは削除**を
3. 全キーを読み直す
4. 1 件でも書いたものと違えば、snapshot を書き戻して `failed` を返す

3 が必要なのは、ストアが自分の失敗を飲み込むからである(`preferencesKV` は
「保存に失敗してもゲームは止めない」ためにそう作られている)。**書けたかどうかは、
読み直して見る以外に確かめようがない。**

読み書きはすべて `repo.ts` の `loadRaw` / `saveRaw` を通り、キーごとの直列化キューに
載る。宙に浮いていた保存が復元の後から着地してレコードを復活させる、という
「ローカルデータ削除」で一度実物を見た事故を、復元で繰り返さないため。

### merge は無い

復元の意味は「バックアップ時点へ戻す」で統一する。**ファイルに無いキーは消す** —
残せば「元の状態でも新しい状態でもない何か」ができあがる。2 台ぶんの進行を突き
合わせるには「どちらの記録が本物か」を決める規則が要り、それを発明することが、
ローカルのファイルを同期サービスに変える最初の一歩である。

`sg.iap` などバックアップが所有しないキーは、復元の世界の外にある — 読まれず、
書かれず、消されない。他人のバックアップを復元しても、この端末が買った広告削除は
そこに残る。

## プラットフォームとファイル

| 方向    | Android / iOS                                              | Web                                 |
| ------- | ---------------------------------------------------------- | ----------------------------------- |
| Export  | アプリ自身のキャッシュへ書き、URI を OS の共有シートへ渡す | Blob をブラウザのダウンロードへ渡す |
| Restore | `<input type="file">`(WebView のドキュメントピッカー)      | `<input type="file">`               |

- **新しい権限を要求しない。** `@capacitor/filesystem` と `@capacitor/share` は結果
  カードの共有で既に使っており、どちらも Android の manifest が空。取り込みは
  `<input type="file">` なので、ユーザーが 1 ファイルを手渡す形になり、アプリが
  端末の中を見て回ることはない
- 書き先は Cache。OS がいつ回収してもよく、読み返すものは無く、権限も要らない。
  ユーザーの手元に残るのは共有シートが置いた先のコピーである
- 共有シートを閉じた(キャンセルした)ことは失敗ではない。ファイルは作られており、
  置き場所を選び直しただけ。`shareGame` がキャンセルを扱うのと同じ読み方
- **オフラインで完結する。** Export にも Restore にも通信は無い。ユーザーが
  AirDrop やドライブを選んだ後の通信は Simple Games の責任範囲外で、アプリは転送先を
  認識しない(docs/OFFLINE_POLICY.md)

## UI で足さないもの

通知・バッジ・未バックアップ警告・定期バックアップの催促は追加しない
(docs/PRODUCT_PRINCIPLES.md)。設定画面に 2 つのボタンと短い説明があり、操作の後に
1 行だけ結果を言う。Export 成功時は何も言わない — 共有シートやダウンロードが
そのまま受領証であり、その上に出すトーストはアプリが自分を褒めているだけになる。

拒否のメッセージは 3 つに分けてある(`backupFileUnreadable` /
`backupFileNewer` / `backupFileDamaged`)。「復元できませんでした」1 本だと、
アプリを更新すれば直る人が同じファイルを選び直し続けることになる。

平文であることは書く(`backupPrivacyNote`)。暗号化していないものを、暗号化されて
いるように読める文面で配らない(docs/PRODUCT_PRINCIPLES.md)。
