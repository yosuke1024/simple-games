## 1. 盤面と対局者

- 8×8 の 64 マス。内部の番号は `a1 = 0`、`b1 = 1`、…、`h8 = 63`(段優先。`game/types.ts` の `squareOf` /
  `fileOf` / `rankOf`)。座標の名前は代数式(`e4` など)で、読み上げと保存の符号に使う。
- 駒は 6 種(ポーン・ナイト・ビショップ・ルーク・クイーン・キング)× 2 色(白・黒)。内部の値は種類(1〜6)と
  色のビット(黒 = 8)の和で、空は 0(`game/types.ts`)。
- 初期局面は標準の 1 つだけ(FEN の `rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq - 0 1`)。生成も
  シャッフルも無い。シードは CPU の同点の決めと Easy の揺らぎにだけ使う(§5)。
- **白が先手。**プレイヤーは白(先手)か黒(後手)を選ぶ(ホーム。既定は白)。選択は `ch.prefs` に置き、
  **次の対局から**適用する。進行中の対局には触らない(Reversi §1)。ボタンには「白(先手)」「黒(後手)」と
  書く — 色と先後の対応を知っている前提に立たない。
- **盤は常に自分が手前。**黒を選んだ対局では盤を 180° 回して描く(a1 が右上)。内部の番号は回さない —
  回すのは絵だけである。
- **駒は物理色(明 / 暗)で塗る。**Reversi / Gomoku の黒白と同じ側で、Checkers §11 / Connect Four §1 の役割色
  (自分 = アクセント)の**例外**である。チェスでは「白」「黒」が規則の語(先手・後手、昇格の向き、記録)そのもので、
  役割色にすると「白(先手)」のボタンと盤の駒の色が食い違う。アクセント(茜色)は選択・合法手の点・最後の手の
  印・クロムにだけ使い、駒とマスには使わない(§9)。
- 対局相手は CPU だけ。難易度は Easy / Normal / Hard(最初から全部選べる)。デイリー・時計・レーティング・
  ストリーク・オンライン対戦・ローカルの対人戦は無い。

## 2. 一手の解決(規則)

駒の動きは FIDE のとおり。`game/engine.ts` の合法手の生成器(`generateLegalMoves`)が唯一の規則で、画面・CPU・
保存の再生・テストのすべてがこれを読む(探索用の速いコピーを持たない — 計画「CPU」)。

1. **ナイト**は L 字(2 + 1)に跳ぶ。間の駒は関係ない。
2. **ビショップ**は斜め、**ルーク**は縦横、**クイーン**はその両方に、駒に当たるまで何マスでも進む。相手の駒に
   当たればそのマスで取れる。
3. **キング**は周り 1 マス。
4. **ポーン**は前へ 1 マス(前が空のとき)。初期位置(白は 2 段目、黒は 7 段目)からは 2 マスも選べる(間と
   行き先が両方空のとき)。取るのは斜め前 1 マスだけ。
5. **アンパッサン**: 相手のポーンが 2 マス進んだ直後の 1 手に限り、その横にいる自分のポーンは、相手のポーンが
   通過したマスへ斜めに進んで、それを取れる。次の手を指せば権利は消える。
6. **昇格**: 最奥段(白は 8 段目、黒は 1 段目)へ進んだポーンは、その手でクイーン・ルーク・ビショップ・ナイトの
   どれかに替わる(4 択。キングとポーンにはならない)。取りながらの昇格も同じ。生成器は昇格の手を 4 つの別の手
   として返し、順序はクイーン・ルーク・ビショップ・ナイト(ピッカーの並びと同じ — §4)。
7. **キャスリング**: キングが 2 マス横へ動き、同じ側のルークがキングを跳び越して隣に並ぶ(白の短い側は
   `e1g1` で h1 のルークが f1 へ、長い側は `e1c1` で a1 のルークが d1 へ。黒も同じ形)。次の**すべて**を満たす
   ときだけ合法:
   - その側のキャスリング権が残っている。権利は、キングが一度でも動くと両側とも、ルークが初期位置から動くか
     そこで取られると、その側が消える(`CASTLE_MASK`)。
   - キングとルークの間のマスがすべて空(長い側は b・c・d の 3 マス)。
   - キングがいま王手を受けていない。
   - キングが通過するマス(短い側 f、長い側 d)と行き先(g / c)が相手に利いていない。**長い側の b のマスは
     空であればよく、利いていてもよい**(キングが通らないため)。
8. **自分のキングが取られる形になる手は非合法**(ピンされた駒の手・王手の放置・キングが利きへ入る手・
   アンパッサンで自分のキングの横の筋が開く手を含む)。生成器はまず駒の動きとして可能な手(疑似合法手)を作り、
   それぞれを盤の上で実際に指して(`makeMove`)自分のキングが利きにあるかを確かめ、戻す(`unmakeMove`)。
   取り除く理由を個別に数え上げる作り方(ピンの検出・王手の種類分け)はしない — アンパッサンの横のピンのような
   稀な形を、数え漏らす余地を作らないためである。

**手番は交互で、パスは無い。**手番は着手の数から導出し、保存しない(§7)。

## 3. 終了条件

着手のたびに、指した後の局面で次の順に判定する(`game/rules.ts` の `outcomeAfterMove`)。先に当たったものが
終局理由で、終局は一度だけ起きる。

1. **チェックメイト** — 手番の側に合法手が無く、キングが王手を受けている。指した側の勝ち。
2. **ステイルメイト** — 手番の側に合法手が無く、王手を受けていない。引き分け。
3. **駒不足** — 盤の上の駒が次の 4 形のどれか。引き分け。
   - キング対キング。
   - キング + ビショップ 1 対キング。
   - キング + ナイト 1 対キング。
   - キングのほかはビショップだけで、そのビショップがすべて同じ色のマスにいる(数・持ち主を問わない。上の
     2 つめはこの特別な場合)。
   - FIDE の「デッドポジション」(どう指しても詰みが起こりえない局面)全体ではなく、この 4 形に限る(§11)。
     キング + ナイト対キング + ナイトや、キング + ビショップ対キング + ナイトは、協力すれば詰みがありうるので
     引き分けにしない。
4. **同形(三回)** — 指した後の局面が、対局の始めから数えて 3 回目に現れた。引き分け。**同じ局面**とは、
   盤の駒の配置・手番・両者のキャスリング権(その時点で権利が残っているか。いまキャスリングできるかではない)・
   **アンパッサンの可否**(手番の側がいま合法にアンパッサンできるか)がすべて同じこと。2 マス進んだ直後でも、
   取れる相手のポーンがいない(または取るとキングの横の筋が開くので取れない)ならアンパッサンの可否は「無し」で、
   2 マス進まずに同じ配置になった局面と同じ局面である。
   - 判定は**局面の鍵**(Zobrist の 32bit × 2 語。BigInt を使わない — ビルドの target の es2018 へ下げられない)で
     候補を絞り、**鍵の一致した局面どうしを、局面そのもの(64 マス + 手番 + 権利 + アンパッサンの可否の文字列)で
     比べ直す**。鍵の衝突で誤って引き分けにしない(`game/rules.ts` の `countRepetitions`)。比べるのは、最後に
     ポーンが動くか駒が取られてからの局面だけ(それより前の局面には、駒の数かポーンの位置が違うので戻れない)。
5. **50 手規則** — ポーンの手も取る手も無い手が**双方 50 手 = 100 プライ**続いた(`FIFTY_MOVE_PLIES` = 100)。
   引き分け。カウンタはポーンの手か取る手でゼロに戻る。**100 プライ目の手が詰みなら詰みが勝つ**(上の順の 1 が
   5 より先)。Checkers の `DRAW_QUIET_PLIES` は 50 プライで、数え方が違う。

- **FIDE との差 — 自動の引き分け。**FIDE では三回同形と 50 手は**申請**で引き分けになり(自動で終わるのは
  5 回同形と 75 手)、駒不足は「デッドポジション」全体で自動に終わる。この遊びは申請の操作を作らない代わりに、
  早いほう(3 回・50 手)を自動にする(§11)。
- 勝敗は**チェックメイトだけ**で決まる。投了・時間切れ・引き分けの提案は無い(§6)。
- 結果は「白の勝ち / 黒の勝ち / 引き分け」と終局理由(`checkmate` / `stalemate` / `insufficient` /
  `repetition` / `fifty`)の組で、画面ではプレイヤーから見た勝ち / 負け / 引き分けと、**終局理由の 1 行**で示す
  (§9)。ステイルメイトには専用の文言を使う(§10 — 「詰み」と訳されて勝敗を取り違えないため)。
- 同じ手の中で 2 つ以上の条件が重なることは、規則から考えると 1 と 5、2 と 3、2 と 5、4 と 5 の組だけで起こり
  うる(駒不足は取る手の後にしか生まれず、取る手は 50 手のカウンタを戻し、それまでに無かった駒の数の局面を作る
  ので、3 は 4・5 と重ならない。4 形ではどれも詰みの局面が作れないので、3 は 1 と重ならない。詰みやステイルメイトの
  局面が 3 回目に現れることは、1 回目で終わっているので無い。キング + ビショップ対キングのステイルメイトはありうるので
  2 と 3 は重なる)。そのときは上の順で先のものを理由にする — 2 と 3 はどちらも引き分けで、理由の 1 行はステイル
  メイトになる。

## 4. 操作

- **タップ 2 回**: 自分の駒 → 行き先の点。別の自分の駒をタップすれば選び直し、同じ駒か点の無いマスをタップすれば
  選択を外す。
- **合法手の無い駒は選べない**(ピンされて動けない駒、王手を受けられない駒)。点も、叱る通知も、音も出さない
  (Checkers §6「無効な操作を叱らない」)。
- 行き先の点は、空のマスへの手は小さな点、取る手(アンパッサンを含む)は形の違う印(マスの縁の輪)で示す。
  アンパッサンの行き先は空のマスだが、取る手なので取る印を出す。キャスリングは**キングの行き先(2 マス先)**の
  点で示す(ルークをタップしてもキャスリングにはならない)。
- **昇格は 4 択のピッカー**(クイーンが先頭で、開いたときにフォーカス)。開いている間は盤を `inert` にし、Escape や
  取り消しでは**着手しない**(`useDialogDismiss` — 選択は残り、別の手を選べる)。
- 盤のマスはボタンで、Tab / Enter / Space で操作する。Undo は Ctrl/Cmd+Z(`useGameKeys`。Checkers と同じ)。
- **ドラッグは v1 では作らない**(タップだけ)。足すなら `src/test/pointerContractWiring.test.ts` の配線
  (`pointercancel`、ドラッグの後のクリックの打ち消し)が要る。Web ベータの反応を見てから決める(§14)。
- CPU の手番の間は盤を押せない(押しても何も起きない。叱らない)。
- 画面が読む規則の窓口は `game/session.ts`: 選べるマス(`selectableSquares` — 合法手を 1 つ以上持つ自分の駒。
  ピンされた駒と王手を受けられない駒は入らない)、マスごとの行き先(`legalTargets` — 行き先ごとに 1 つで、昇格の
  4 手は 1 つの行き先。取る手・昇格・キャスリング・アンパッサンの印つき)、着手(`applyPlayerMove` — 昇格の手は
  駒の種類を渡さないと拒む。ピッカーで選んでから渡す)。`session.test.ts` が確かめる。

## 5. CPU

`game/cpu.ts`(`decideCpuMove` / `chooseCpuMove`)。**値はこの段(2026-10-22)で決めた** — 評価の値と形・探索の
形・Normal の深さ・Easy の揺らぎは自己対局で順序が出たので確定(§5.1・§13)。Hard のノード上限は**段 1 の Node の
暫定値**で、出荷済みの hard との同じ環境での比較で仮に決めた(§5.3)。段 2(Web の CDP 6 倍)・段 3(実機)は
行っておらず、**製品オーナーの確認待ち**(§14)。

- 探索は**プレイヤーの着手を起点にだけ**、`CPU_DELAY_MS`(450ms)の 1 本のタイマーの中で同期に走る(Worker も
  先読みもポーリングも無い。盤面 4 本と同じ — [GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「CPU 探索」)。タイマーは
  画面の層(`state/`)が張り、`game/` は待たない — `game/session.ts` の `applyCpuMove` を、張ったタイマーの中で
  呼ぶ。例外は前例と同じ 1 つで、CPU の手番で離れた対局を再開したとき(ショートカットからも)、450ms 後に 1 手
  ぶんの探索が走る(§7)。着手が現れるのは概ね **450ms + 探索時間**である(Reversi §5)。
- **バックグラウンドではタイマーを張らない。**タイマーの effect は、画面・セッションに加えてページが見えているか
  (`visibilitychange`)も依存に取る。隠れるとタイマーは外れ(探索は始まらない)、対局と経過秒はその場で保存
  される。**戻るとタップなしに 450ms を最初から張り直す** — Nested Tic-Tac-Toe §4 と同じ形で、同じ**暫定の
  例外**(「復帰しても勝手に再開しない」からの外れ。盤面 4 本の effect は可視性を読まない — GAME_LIFECYCLE.md
  「CPU 探索」)。文字どおりに読めば「次のタップまで CPU は指さない」になるが、CPU の手番ではプレイヤーに押せる
  マスが無く、対局が止まったように見える。どちらにするかは**製品オーナーの確認待ち**(§14)。
  `ui/ChessRoot.test.tsx` が、隠れている間は 450ms × 4 待っても指さず、戻ってから 449ms では指さず 450ms で
  指すことを確かめる。
- **ルールは `game/engine.ts` の 1 セットだけ。**探索は合法手の生成器と同じ `generatePseudoLegalMoves` /
  `makeMove` / `unmakeMove` / `isSquareAttacked` を使い、手の合法性も生成器と同じやり方(指してみて、自分の
  キングが利きにあれば戻す — §2.8)で決める。違うのは**その確かめを 1 手ずつ、指す直前にする**ことだけで、
  α–β で切った手の確かめは払わない。探索は呼び出し側の局面を写して(`clonePosition`)その上で make / unmake し、
  盤を作り直さない(Reversi §5)。呼び出し側の局面は変えない(`cpu.test.ts` が確かめる)。終盤データベースと
  定石集は積まない(issue #26)。置換表も v1 では持たない(自己対局で順序が出たため — §13)。
- CPU は気軽に指す人向けで、強さを売りにしない。画面と公開文面に「強い」「AI」と書かない(§10)。

### 5.1 難易度ごとの読み

3 つとも、まず次の 3 段を同じに行う(`decideCpuMove`)。

1. **合法手を seed の順に並べる**: `createRng(`${seed}:cpu:${moveCount}`)`(`moveCount` は指された手の数)の
   乱数で、合法手(生成器の順)を Fisher–Yates で並べ替える(`shuffled`。Checkers と同じ)。以後の「同じ値なら
   先のもの」はこの順を指す(§5.4)。
2. **根の静的な見(根の手ごとに 1 回)**: 根の手を 1 つずつ指し、**規則の判定をそのまま当てる** — 相手に合法手が
   無く王手なら**詰み**、合法手が無く王手でなければ**ステイルメイト**(引き分け)、駒不足・同形の 3 回目(ゲームの
   履歴を含めて)・50 手(カウンタが 100)なら**引き分け**(値 0)、どれでもなければ**指した後の静的評価**
   (§5.2。CPU から見た値)。この見は探索関数を呼ばないので**ノードに数えない**(合法手 1 つにつき 1 回で、合法手は
   多くても 218 — 仕事量は合法手の数で頭打ちになる)。
3. **1 手詰めがあれば必ず指す**(上の順で最初の詰みの手)。**合法手が 1 つなら、探索せずにそれを指す**(ノード 0)。
   どちらもノード上限と関係なく働く — 上限が 1 でも 1 手詰めは取る(`cpu.test.ts`)。

その先が難易度で分かれる。

- **Easy** = 1 手読み + seed の揺らぎ。**探索も静止探索もしない。**上の 2 の値に、根の手ごとに同じ乱数の続きから
  `⌊r × 151⌋`(0〜`EASY_JITTER` = 150 センチポーン、一様)を足し、最大の手を指す(同じ値なら先のもの)。詰む手は
  3 で先に取っているので、揺らぎは**詰まない手の間でだけ**働く。引き分けで終わる手は値 0 に揺らぎを足したもので、
  負けている局面では引き分けを選び、勝っている局面では選ばない(`cpu.test.ts` — 同形・50 手・ステイルメイト)。
  相手の応手は読まない — **取った駒を取り返される手も、2 手先の詰みの狙いも見えない**。それを弱さとする。
- **Normal** = 反復深化 α–β + 静止探索で、深さの上限 `NORMAL_MAX_DEPTH` = **2 プライ**(確定)。Hard と同じ
  ノード上限の内側で走る。初期局面では 94 ノードで深さ 2 を終える(`compatibility.test.ts` の固定局面の行)。
  計画の推奨は「2〜3」で、2 で自己対局の順序が出た(Normal が Easy に 40 局 40 勝 — §13)ので 2 にした。3 にする
  理由(Easy に勝てない・Hard との差が無い)は出ていない。
- **Hard** = 反復深化 α–β + 静止探索で、深さの上限 `HARD_MAX_DEPTH` = 6、ノード上限 `HARD_NODE_LIMIT` =
  **80,000**(段 1 の Node の暫定値 — §5.3)。上限に達したら、**その反復を丸ごと捨てて、完了した最も深い反復の最善手を指す**。完了した
  深さは、bench の 8 局面で 4〜6、計測の 200 局面(探索した 198)で 3〜6(1 局面だけ 1 — 下)である(§13)。
- **深さ 1 も上限の内側で走る**(計画の「深さ 1 は必ず完了する」から外れた — §14)。深さ 1 を上限の外に置くと、
  静止探索の木の大きさだけ上限の外の仕事ができ、上限が上限でなくなる。代わりに、**深さ 1 が終わらなかったときは
  上の 2 の静的な見の最善(深さ 0)を指し、`capped` を立てる**。上の 3 の 1 手詰めはその場合も取る。bench・計測・
  自己対局のどの局面でも、上限 80,000 で深さ 1 は終わった(bench と計測は完了した深さを固定し、自己対局は探索した
  返答ごとに深さ 1 以上を判定する — §12。上限を 10 にしたときに深さ 0 へ落ちることは `cpu.test.ts` が確かめる)。
- **反復を早く止めるのは 1 つだけ**: 完了した反復の最善値が詰みの値(§5.2 — どちらかの詰みを読み切った値)なら、
  それ以上深くしない(Hard・Normal とも)。詰みを読み切ったのだから、深い読みでは変わらない。このときは `capped`
  を立てない。計測の 200 局面のうち 1 局面で、深さ 1 で詰み(どの手も詰まされる)を読み切って止まった(§13)。
- **`capped` は正直に返す**: `decideCpuMove` の結果は手と、`kind`(`mate` / `only` / `easy` / `search`)・訪問ノード数・
  完了した深さ・`capped`(上限で反復を捨てたとき、そのときだけ true)・選んだ手の値を返す。bench はノード数が
  上限ちょうどの返答と `capped` が一致することを確かめる。
- Normal と Hard は同じノード上限・同じ探索で、違うのは深さの上限だけなので、**Hard が Normal より浅く読むことは、
  詰みを読み切って止まった局面の外には無い**(bench の 8 局面と計測の 198 局面で確かめた — §13)。順序は自己対局で
  測った: **「順序が出る」とは、組ごとに、強いほうの勝ちが弱いほうの勝ちより多いこと**(引き分けは数えない。
  各組 40 局、着手列が同じ対局は 1 局に数える — Nested Tic-Tac-Toe §4.1 と同じ定義)。結果は §13。

### 5.2 探索と評価(値は確定)

**評価**(`evaluate`。手番の側から見た値で、整数だけ — 同じ局面ならどの機械でも同じ値)。駒の価値と位置の値の和の
「自分 − 相手」に、キングの位置と、裸のキングを追う項を足す。**位置の値は表を手で打たず、次の式で作る**
(`cpu.ts` の `PST`。式と表がずれないように)。`f` は筋(a = 0 … h = 7)、`r` は段(1 段目 = 0)、`c(i)` =
min(i, 7 − i)(端 0・中央 3)、`rel` はその駒の側から数えた段(白は `r`、黒は 7 − `r`)。

| 項                       | 値(センチポーン)                                                                                                                                            |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 駒の価値                 | ポーン 100・ナイト 320・ビショップ 330・ルーク 500・クイーン 900(キングは 0)                                                                                |
| ポーン                   | `rel` ごとに 0, 0, 4, 8, 16, 32, 56, 0。d・e 筋はさらに `rel` ごとに 0, −10, 4, 16, 12, 0, 0, 0(初期位置に残ると −10、中央で +16)                           |
| ナイト                   | 6 × (c(f) + c(r)) − 18(隅 −18 … 中央 +18)                                                                                                                   |
| ビショップ               | 4 × (c(f) + c(r)) − 12(隅 −12 … 中央 +12)                                                                                                                   |
| ルーク                   | 7 段目(`rel` = 6)で +20、ほかは 0                                                                                                                           |
| クイーン                 | 2 × (c(f) + c(r)) − 6(隅 −6 … 中央 +6)                                                                                                                      |
| キング(中盤)             | `rel` = 0 なら筋ごとに 10, 20, 10, −5, −5, 0, 20, 10(キャスリングした先を好む)、離れると 1 段ごとに −20                                                     |
| キング(終盤)             | 8 × (c(f) + c(r)) − 24(隅 −24 … 中央 +24)                                                                                                                   |
| 中盤と終盤の混ぜ方       | 局面の段階 `p` = ナイト・ビショップ 1、ルーク 2、クイーン 4 の和(上限 24)。キングの値 = trunc((中盤 × p + 終盤 × (24 − p)) / 24)                            |
| 裸のキングを追う(mop-up) | 一方がキングだけで、他方にキング以外の駒があるとき、駒のある側に 10 × (6 − c(f) − c(r))(裸のキングが端ほど大)+ 4 × (7 − 両キングの距離)(距離はチェビシェフ) |

- 表の値は `cpu.test.ts` が式どおりか照合する(ナイト a1 −18 / d4 +18、ビショップ h8 −12、クイーン e5 +6、
  ルーク a7 と黒の a2 +20、ポーン e2 −10 / e4 +24 / 黒の d5 +24 / a7 +56)。手で数えた局面の値も 1 つ照合する —
  白キング e1・白ナイト e4・黒キング e8 は **368**(ナイト 320 + 18、キングは段階 1 で両方 0、裸のキングを追う項 30)、黒の手番なら −368。初期局面は 0。**色と盤を入れ替えた局面は同じ値になる**ことを、ランダム対局の 300 局面で
  確かめる。
- 値は筆者が自前で置いたもの(既存のエンジンや文献の表を写していない)。調整は自己対局で順序が出たので行って
  いない(§13)。
- **詰みの値** `MATE_VALUE` = 100,000。根から `p` プライ先で詰ます手は 100,000 − `p`、詰まされる手はその負。早い
  詰みを好み、遅い負けを好む。**引き分けは 0**(どちらが駒得でも — 勝っている側が引き分けに歩み寄らないため。
  Checkers §4 と同じ)。

**探索**(negamax の α–β)。

- **ノード**: 探索関数(主探索と静止探索)の 1 回の呼び出しを 1 ノードと数える。カウンタは CPU の 1 手につき
  1 本で、**反復深化の全反復にまたがって累積する**。呼び出しの前に `ノード数 ≥ 上限` を調べてから数えるので、
  カウンタは上限を超えない(Checkers / Connect Four と同じ)。上限に達したら例外で反復を抜け、その反復を捨てる。
- **局面の終わりを探索の中でも読む**(計画「探索は引き分けも終局として読む」): 各ノードで、駒不足(取る手か昇格の
  直後 — 駒の数が変わるのはそのときだけ)、**同形の 3 回目**(ゲームの履歴と探索の経路を合わせて数える。規則と
  同じ数)、50 手(カウンタ 100 — ただしその局面が詰みなら詰み)なら、引き分け 0 か詰みの値で閉じる。同形は
  **鍵だけで比べる**(§3.4 が探索に許したとおり。局面の文字列は作らない)。鍵はゲームの履歴と同じ作り方で、
  アンパッサンは**合法に取れるときだけ**鍵に入れる — 探索の経路の局面が、ゲームで現れた局面と一致しうるように
  するため。比べるのはカウンタの窓の中の、手番が同じ局面(1 つおき)だけ。合法手が無ければ王手なら詰み、
  そうでなければステイルメイト(0)。`cpu.test.ts` が、負けている側が 3 回目を取ること、勝っている側が 3 回目を
  避けること、カウンタ 99 で勝っている側がポーンを動かすこと、カウンタ 98 でも Normal と Hard が相手の引き分けの
  応手を見てポーンを動かすこと、100 プライ目の詰みは詰みとして指すこと、カウンタ 98 で Normal と Hard が相手の
  100 プライ目の詰みを詰まされる手として読み、相手に 1 手詰めを残さないこと、勝っている側がステイルメイトの手を
  指さないことを、3 つの難易度で確かめる(98 は Normal と Hard だけ — Easy は応手を読まない)。
- **静止探索**(深さが尽きた先): **取る手(取りながらの昇格を含む)だけ**を読み、手番の側は静的評価の値で止まって
  よい(stand-pat)。深さの上限 `QUIESCENCE_MAX_PLIES` = 6 プライで、そこでは静的評価を返す。**王手を受けている
  局面では stand-pat をせず、取る手に限らず全応手を読み、合法手が無ければ詰み**とする(王手の中で打ち切ると、
  王手を放置した評価になる)。`cpu.test.ts` が確かめる: 守られたポーンは取らない(値は静的評価と同じ)、ただの
  ポーンは取る、詰んでいる局面は駒の差によらず詰みの値、王手を受けて唯一の応手が静かなキングの手の局面は
  詰みにしない。王手でない局面のステイルメイトは静止探索では見ない(取る手しか作らないため。主探索では見る)。
  取らない昇格は静止探索で読まない(計画「取る手のみ」のとおり)。
- **手の順序**(枝刈りのためで、値は変えない): 取る手を先に、取られる駒の価値の大きい順、同じなら昇格の駒
  (クイーンが先)、さらに同じなら取る駒の価値の小さい順(MVV-LVA。価値は駒の種類の番号で比べる — ポーン 1・
  ナイト 2・ビショップ 3・ルーク 4・クイーン 5・キング 6。アンパッサンで取られるのはポーン)。次に取らない昇格(クイーンが先)、次に
  その深さで直前に枝刈りを起こした静かな手 2 つ(キラー手)、残りは生成器の順。並べ替えは必要になった分だけ
  1 つずつ選ぶ(同じ値なら先のもの — 安定)。
- **根**: 1 回目の反復の根の順は、上の静的な見の値の大きい順(同じなら seed の順)。2 回目からは、前の反復の
  最善手を先頭に回し、残りは前の順のまま。根では α を上げていき(窓 (α, +∞))、**値が厳密に大きい手だけが
  最善を置き換える** — 同じ値の手は先に読んだ手が残る。
- 順序・キラー手・根の扱いは枝刈りを通じてノード数と、上限の下で終わる深さと選ぶ手を変えるので、
  `compatibility.test.ts` のゴールデンと `cpu.bench.test.ts` のノード数はこの形を前提に固定する。

### 5.3 ノード上限(`HARD_NODE_LIMIT` = 80,000 — 段 1 の Node の暫定値)

**決め方は Nested Tic-Tac-Toe §4.3 の段 1 と同じ手順**(計画の未決事項「Hard のノード上限の測り方」の推奨 —
出荷済みの hard との同じ環境での比較)。値を選ぶには出荷済みの hard を同じ環境で動かす必要があるが、
`src/games/chess/` の下のテストは他のゲームを import できない(`src/test/importBoundaries.test.ts` の規則 1)。
そこで計測は**リポジトリの外の作業ディレクトリのスクリプト**で行い(Nested と同じ扱い。スクリプトはリポジトリに
入れていない)、手順・環境・結果をこの節に書く。ゲームのテスト(`cpu.bench.test.ts`)が見るのは、決まった値の
下でのノード数の決定性と上限と、完了する深さだけである。**下の表の時間は計測の値で、テストは再現しない**
(「数値の出所を分ける」から外れる — §14)。局面の数・完了する深さは決定的なので、テストが同じ局面を作り直して
固定する。

- 手順: 同じ Node の 1 つのプロセスで、出荷済みの hard 5 本(Reversi 12,000 / Connect Four 30,000 / Checkers
  26,000 / Gomoku 8,000 / Nested Tic-Tac-Toe 40,000 — 各ゲームの `game/` のソースを直接読み込む)と、候補をはめた
  Chess の Hard を順に測った。局面は、ゲームごとに seed `measure-<id>-1`〜`40` の 40 局(両者とも合法手から一様に
  選ぶ)の手数 4・12・20・28・36 の局面(その手数までに終局していれば除く)。Nested は §4.3 の 213 局面。Chess は
  200 局面(どの対局も手数 36 までに終わらなかった — 局面の数はテストで実測、`cpu.bench.test.ts`)。各局面で hard
  の 1 手(CPU の選択の関数 1 回)を 3 回測って中央値を取り、局面数ぶんの中央値の **p95**(最近傍順位)を出す
  (最初の 5 局面で先に 1 回ずつ温めてから測った)。**候補(5,000 / 10,000 / 20,000 / 40,000 / 80,000)のうち、
  Chess の Hard の p95 が、アプリに出荷済みの hard 4 本(Reversi / Connect Four / Checkers / Gomoku)の p95 の最大を
  超えない最大の値を選ぶ**(Nested と同じ基準。Nested 自身はその基準で選ばれた値なので、参考として並べる)。
- 環境: この作業環境のコンテナ(Linux 6.18、Intel Xeon 2.80GHz の仮想 4 コア、メモリ 15GB)の Node v22.22.0。
  開発機でも実機でもない。**同じ機械で別の作業(他のゲームの作業)が並行して走っていた**(load average は 1 回目
  の後半から 2 回目にかけて 5〜11)。だから値はこの負荷の下のもので、Nested §4.3 の表(2.10GHz の機械、並行なし)と
  直接は比べられない。比べたのは同じプロセスの中の相対である。

### 5.4 決定性と seed

- seed は対局ごとに 1 つで、`chess-<token>`(`<token>` は時刻の 36 進 + 乱数 — `game/session.ts` の
  `newSeedToken`。盤面 4 本と同じ形)。使うのは §5.1 の根の並びと Easy の揺らぎだけ。初期局面は標準の 1 つなので、
  生成もフォールバックも要らない。
- **同じ局面・同じ履歴・同じ seed・同じ手数・同じ難易度なら、CPU は必ず同じ手を、同じノード数で返す**(値は整数、
  順序はすべて決まった規則、時計を読まない)。`compatibility.test.ts` が固定する — 難易度 3 つ × プレイヤーが白の
  16 プライの対局と、Normal でプレイヤーが黒の対局(CPU の手の列と最後の局面)、§12 の perft の 5 局面での 3 つの
  難易度の返答(手・ノード数・完了した深さ)。**戻して同じ手を指せば同じ手が返る**(§6)ことは `session.test.ts` が
  確かめる。
- **同じ値の手の間は seed が決める**(計画の共通要件の「複数解」)。`cpu.test.ts` が 3 つを確かめる — Easy は
  初期局面の返答が seed で変わる。Normal と Hard も、初期局面で 8 つの seed から 2 つ以上の返答が出て、seed ごとに
  同じ返答を繰り返す(Hard はテストの時間のためノード上限 2,000 で、それでも Normal の深さ 2 より深く読む)。1 手詰めが
  2 つある局面(Ra8 と Rb8)では、3 つの難易度とも 8 つの seed で両方が出て、seed ごとに同じほうを指す。

## 6. Undo と助けの形

- **Undo は無制限・無料。**CPU の応手と自分の 1 手をまとめて戻す — 自分の直前の決定点へ(Reversi §6 /
  Checkers §5)。CPU の手番の途中(450ms の間)に押せば、自分の直前の 1 手だけが戻り、予定していた CPU の手は
  破棄される。
- 後手で始めた対局の CPU の初手は、自分の決定点が無いので戻らない(初手だけが盤にあるときは Undo を押せない)。
- **戻して同じ手を指せば、CPU は同じ手を返す**(§5 の決定性)。
- **再開した対局でも Undo できる**(盤面 4 本との意図的な違い — §11)。保存が着手リストなので、追加の保存なしで
  初手まで戻せる。「Undo は無制限」をそのまま守る。
- 終局した対局は Undo できない(結果カードは New game / Home だけ)。
- 実装は `game/session.ts` の `canUndo` / `undo`: 終局しておらず、いまより前に自分の手番の局面があるときだけ
  戻せる(白なら 1 プライ以上、黒なら 2 プライ以上)。戻すときは 1 プライ戻し、自分の手番になるまで続ける —
  自分の手番なら CPU の応手と自分の手の 2 プライ、CPU の手番(450ms の間)なら自分の手の 1 プライになる。
  セッションは不変の値で、戻すたびに記録を写してから戻す(`cloneGame` — 手を 1 つも生成しない写し)。
  `session.test.ts` が、2 プライの組・450ms の間の 1 プライ・黒で CPU の初手だけのときに戻せないこと・終局後に
  戻せないこと・戻して同じ手を指せば同じ応手が返ること・再開した対局で初手まで戻れることを確かめる。
- **合法手の点は規則の可視化であって、最善手の提案ではない**(Reversi §7)。
- **作らない**: Hint・評価バー・棋譜解析・「取られる」警告・投了・引き分けの提案。盤面はすべて見えているので、
  次の一手を教えれば CPU がプレイヤーの側でも指すことになる(Connect Four §6 と同じ判断)。投了の代わりは新しい
  対局で、負けには数えない(§7)。
- Undo を広告視聴や課金に結び付けない([ADS_POLICY.md](ADS_POLICY.md))。

## 7. 保存と統計

保存キーは `ch.saveGame`(1 スロット)/ `ch.stats` / `ch.flags` / `ch.prefs` の 4 つ(`storage/keys.ts`。この順が
registry の `storageKeys` の順 — `app/gameKeys.test.ts` の Chess の行と `storage/schemas.test.ts`)。画面の段で
scaffold の `stats` / `flags` に `saveGame` と `prefs` を足した。デイリーが無いので 2 スロット規則はかからない。
ベータの間はスキーマを凍結しない(冒頭)。scaffold の `ch.stats`(`{ schemaVersion: 1, played }`)は難易度の
キーを持たないので、開発中の端末に残っていても既定値(全部 0)として読む。

### 7.1 `ch.saveGame` — 中断中の対局(途中保存する)

ターン制なので、保存して開き直した盤面は保存した瞬間と同じである(GAME_2048_RULES §10 と同じ理由)。

- 中身は**着手リスト**と、先後・難易度・seed・経過秒。**手番は保存せず**、手数から導出する。
- 着手リストは 1 つの ASCII の文字列で、各手は UCI の形(`e2e4`、昇格は `e7e8q` — 昇格の文字は小文字の
  `q` / `r` / `b` / `n`)、手と手の間は**半角空白 1 つ**(`game/serialize.ts` の `encodeMoveList`)。初期局面のまま
  (後手を選び CPU がまだ指していない)なら空文字列。
- **手数の上限 `MAX_PLIES` = 12,700 プライ。**算術では、50 手規則を自動で当てるとき、ポーンの手か取る手が無い手は
  100 プライ続かない(100 プライ目で終わる)。取る手は高々 30 回(キング以外の 30 駒)、ポーンの手は高々 96 回
  (16 本 × 6 段 — 2 段目から 8 段目まで、2 マス進みも 1 手)なので、カウンタを戻す手は高々 126 回で、対局は
  126 + 126 × 99 + 100 = **12,700 プライ**を超えない(取りながらのポーンの手を 2 回に数えているので、実際の上限は
  これより小さい)。この上限は規則上ありうる対局を拒まない。文献値として「50 手規則のもとでの最長は約 5,900 手
  (約 11,800 プライ)」と聞く(計画の推奨)が、**出典は未確認**で、定数には使わない — 使うのは上の算術の上限である。
- 文字列の長さの上限は 12,700 × 6 − 1 = 76,199 文字(算術。昇格を含むすべての手が 5 文字 + 空白)。
- **読み込みでは、同じ engine で初期局面から再生する**(`decodeMoveList`)。次のどれかがあれば保存を読み捨て、
  ホームへ戻る(fail-closed。黙って新しい対局を始めない):
  - 文字列でない、長さの上限を超える、空白の並びが正しくない(先頭・末尾の空白、2 つ続く空白、空白以外の区切り)。
  - 形の合わない手の記号(`[a-h][1-8][a-h][1-8][qrbn]?` に合わない。大文字・`O-O`・SAN は拒む)。
  - その局面で合法でない手(昇格の手に昇格の文字が無い、昇格でない手に昇格の文字がある、を含む)。
  - **終局した後の手**(終局の後に続く記号がある)。
  - `MAX_PLIES` を超える手数。
  - **終局済みの対局そのもの**(最後の手で終局している保存)— 中断中の対局ではないので、`state/` の復元で拒む。
- 再エンコードしたものが元の文字列と一致すること(正規の形が 1 つ)も確かめる。
- **保存の形**(`storage/schemas.ts` の `PersistedGame`): `{ schemaVersion: 1, seed, difficulty, side: 'white' |
'black', moves, elapsedSeconds, savedAt }`。検査は 2 段で、**どちらかが拒めば保存は無い**(ホームへ。新しい対局は
  始めない): ① スキーマの `validate` が形を見る(型・範囲・seed は 1〜64 文字・`moves` は文字列で
  `MAX_MOVE_LIST_LENGTH` 以下)。② `storage/gamePersistence.ts` の `loadSavedGame` が `restoreSession` で着手
  リストを再生する(上の拒否の一覧と、終局済みの拒否)。再生をスキーマに入れないのは、長い保存では再生が
  読み込みの重い部分で(§13)、読み込みが 2 回払うことになるため。バックアップの書き戻しはスキーマだけを見るので、
  形は正しいが再生できない着手リストは書き戻しを通り、次に開いたときに読み捨てられる(Checkers の盤面の文字列と
  同じ扱い)。
- **終局した対局は保存しない。**最後の手で終局したらスロットを消し(`saveGame` は終局したセッションでは
  `clearSavedGame` になる)、結果を 1 度だけ記録する。
- **着手リストが局面の履歴そのものなので、保存を挟んでも三回同形の判定を失わない。**Checkers §11 は「局面の
  履歴を保存形式に持ち込む」ことを理由に三回同形を見送ったが、ここではそれが要件になり、保存の形がそれを満たす。
- 再生の仕事量は手数に比例する(1 手ごとに合法手を 1 回生成する)。最長の上限での読み込みの時間は §13。
- CPU の手番で離れた対局は、再開の 450ms 後に CPU が指す(ショートカットからも同じ — GAME_LIFECYCLE.md の例外)。
  スロットが 1 つなので、ショートカットは中断中の対局へ直接入る(`entry` と `storage/gamePersistence.ts`。
  `src/test/shortcutResumeWiring.test.ts`)。
- 初回の Quick Rules を終えると、中断中の対局があればそれを再開する(新しく始めて上書きしない — Checkers §8)。

### 7.2 `ch.prefs` — 先後だけ

- `{ playerIsWhite: boolean }`(既定 `true`)。**難易度は入れない**(計画の未決事項 — §14)。盤面 4 本の prefs も
  先後だけで(Reversi `playerIsBlack`、Checkers / Connect Four `playerGoesFirst`、Gomoku `playerIsBlack`)、難易度は
  ホームの難易度ボタンがそのまま対局を始める形(進行中の対局があれば先に確認する)である。

### 7.3 `ch.stats` / `ch.flags`

- 統計は難易度別の `played`(開始で数える)/ `wins` / `losses` / `draws` と、全体の `totalPlaySeconds`
  (bookedRef、`useOnUnmount(syncActiveGame)`)。終局理由ごとの数は持たない。ストリークは数えない。
- **放棄は負けに数えない**(Reversi §8 / Checkers §7)。記録されるのは実際に終局した対局だけ。
- `ch.flags` は Quick Rules を見たか(scaffold のまま)。

  駒の色はテーマで入れ替えない(物理色 — §1)。ダークはマスだけを 1 段暗くする。

- アクセントはクロム・選択・合法手の点・最後の手の印・王手の輪だけで、駒とマスには使わない。
- **印は形で分ける**(色だけに頼らない): 静かな手の行き先は**小さな丸い点**、取る手(アンパッサンを含む)は
  **マスの縁の丸い輪**、持っている駒は**マスの縁の四角い枠**(実線)、王手のキングは**破線の丸い輪**、最後の手は
  移動元と移動先の**左上の角の小さな四角**。キーボードのフォーカスは**マスの縁の点線の四角**で、アクセントではなく
  インクで描く(点線とインクはどの印も使わないので、駒を持っていないときに「持っている」とは読めない)。持っている駒の
  マスにフォーカスがあるときは、枠が点線の幅だけ内側に寄り、両方が見える(枠はフォーカスの輪の上に描かれるため)。
  Quick Rules の図(1 マス約 25px)では、選択の枠・取る輪・王手の輪を盤より細く描く(線 2px・halo 1px、マスの中に
  収める)。盤の太さのままだと、ステップ 3 の詰まされたキングの外側を輪が覆い、外側の halo が図の縁で切れていた
  (レビュー 3 のスクリーンショット)。
- **王手**は手番行の文言(「Check — your king is attacked」/「Check — CPU’s turn」)と、キングのマスの破線の輪で
  示す。`--warn` は使わない(選択のアクセントと並ぶため。形 — 実線の枠と破線の輪 — で分ける)。読み上げも
  「e8, black king, in check」になる。詰みで終わった局面でも、詰まされたキングに輪が残る。
- **最後の手**は、移動元と移動先に印を付ける(CPU の手を見失わないため)。再開・Undo の直後は付けない(盤は
  「置かれた」もので、指されたものではない)。
- 手番行(`role="status"`)は高さを固定する(王手・CPU の手番・終局のどれを言っても盤面が跳ねない)。
- 駒の移動は、距離に応じた transform のスライド(1 マス 60ms、上限 240ms — 初期値。Checkers §10)。キャスリングは
  キングとルークが同時に動く。Reduced Motion(アプリの設定か OS)では動かさない(`ch-board-still`)。
- **決着から結果カードまでは約 1 秒置く**(`useResultReveal`)。Reduced Motion では即時。
- 結果カードは題に勝ち / 負け / 引き分け(「You win」/「The CPU wins」/「Draw」)、本文に**終局理由の 1 行**
  (チェックメイト / ステイルメイト / 駒不足 / 同形 / 50 手 — 理由ごとの別キー)、その下に事実 3 つ(難易度・
  自分の色・手数 — 手数は白の手の数で数える、`⌈プライ ÷ 2⌉`)。ボタンは New game / Home / `ShareAction`
  (共有に載せるのはカードの事実 3 つと同じ値で、盤面や棋譜は載せない。勝ちだけ `completed`)。負けを叱る文言・
  勝ちを褒める文言は書かない(スキャフォールドの "Nice work" は置き換えた)。
- ヘッダの ↻ は盤面 4 本と同じ `newGame` + `ConfirmDialog`(`RestartDialog` の門は `tryAgain` の ↻ にだけかかる —
  `src/test/restartDialogWiring.test.ts`)。
- **時計は出さない。**経過時間は統計にだけ残る。
- 効果音は既存の合成音(`services/sound.ts`)だけ: 着手で `select`、取る手で `match`(どちらの手でも)、Undo で
  `undo`、勝ちで `clear`、負け・引き分けで `gameOver`。駒を持つ・置き直す・無効なマスでは鳴らさない。

  王手を受けている / ここへ動かす / ここで取る / ここへ動いて横のポーンを取る)を読む。盤の縁には座標の文字を
  置かない(盤面 4 本と同じ)。盤は `role="group"`、名前は「Chess board」。
- **キーボード**: マスはボタンなので Tab で押せるマスだけに止まり、Enter / Space で押す。Ctrl/Cmd+Z は Undo の
  ボタンと同じ条件で働き、↻ の確認・昇格のピッカー・結果カードの間は `useGameKeys` を外す。
- **モーダル**: ↻ の確認(`ConfirmDialog`)・昇格のピッカー・結果カードの間は `.game-content` を `inert` にする
  (`src/test/modalIsolationWiring.test.ts`)。ピッカーは `useDialogDismiss` で、Escape・枠の外のタップ・
  キャンセルは**着手しない**(ポーンは持ったまま)。ピッカーの 4 つのボタンは駒の絵で、名前は駒の読み上げのキー
  (「white queen」など)。開いたときクイーンにフォーカスする。
- **ホーム**: 難易度のボタン 3 つ(Easy / Normal / Hard。押せばその対局が始まる。中断中の対局と同じ難易度なら
  再開、違えば `ConfirmDialog` で確かめる)、先後の 2 つのボタン(`role="radio"`。「White (moves first)」/
  「Black (moves second)」と、その色のキングの絵)、統計、遊び方、`WebBetaNotice`。難易度のボタンには勝ち・
  引き分け・負けの数を小さく添える(1 局でも終局したら)。統計の画面は難易度ごとに played / wins / draws /

## 11. 意図的な差分

**FIDE の規則との差**

- **三回同形と 50 手規則を自動の引き分けにする**(FIDE は申請制で、自動は 5 回同形と 75 手)。申請の操作は、
  CPU 相手では「いつ申請できるか」を知っている人だけが使える機能になるので作らない。その代わり早いほうを自動に
  する(§3)。
- **駒不足は 4 形に限る**(FIDE の「デッドポジション」全体ではない)。全体の判定は一般には探索を要し、規則の
  判定を探索に頼らないため。4 形の外のデッドポジション(ポーンが組み合って動けない局面など)は、50 手規則か
  同形で終わる。
- **時計・投了・引き分けの提案が無い。**時間切れの規則(FIDE 第 6 条)はこの遊びに無い。
- 規則の外の FIDE の条文(記録・タッチムーブ・不正な手の罰など)は、画面が合法手しか受け付けないので当てはまら
  ない。タッチムーブは無い(選択はいつでも外せる — §4)。

**ブランド原則により合わせないもの**

- Undo・難易度・Hint を広告や課金に結び付けない。難易度は最初から全部選べる。
- レーティング・ランキング・オンライン対戦・対人戦は無い。記録は端末の中だけ(§7)。
- デイリー・ストリーク・パズルの日課で毎日呼び戻さない。
- 時計を出さない。

**設計判断として合わせないもの**

- **再開した対局でも Undo できる**(盤面 4 本は Undo の履歴を保存せず、再開した対局はその局面から始まる)。保存が
  着手リストなので、追加の保存なしで「Undo は無制限」を守れる(§6)。
- **Hint・評価バー・棋譜解析・「取られる」警告を作らない**(§6)。
- **駒を役割色にしない**(物理色 — §1。Checkers / Connect Four との差)。
- **ドラッグで指せない**(v1 はタップだけ — §4)。
- **変則ルール(Chess960 など)・ハンデ・タクティクス問題・定石の練習を作らない。**v1 は標準の 1 つだけ。
- **最強 CPU を作らない。**Hard は上限付きの探索で、終盤データベースも定石集も積まない(§5、issue #26)。
