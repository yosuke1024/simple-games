# Simple Games — Web 版

`https://pixapps.ai/simple-games/play/` で配信するブラウザ版の方針。
ネイティブアプリの約束(バナー広告 1 枠のみ・買い切りで広告削除・初回起動から
オフライン)は**アプリのもの**であり、Web 版はここに書く別の約束を持つ。
その約束は Android と iOS で同じ — 2026-08-28 に iOS 版が出たあとも、この文書が
分けるのは Web とアプリの 2 つだけで、OS ごとの列は作らない。

## 役割分担

|            | Web 版                                                                           | アプリ版(Android・iOS)                                                                        |
| ---------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 位置づけ   | すぐ遊べる無料版。新作の先行公開。PixApps への入口                               | 静かに長く遊ぶための完成版                                                                    |
| 導入       | インストール・アカウント不要                                                     | ストアから導入、ホーム画面から起動                                                            |
| 広告       | ディスプレイ広告ほか([ADS_POLICY.md](ADS_POLICY.md)「Web 版」。既定は無効)       | Anchored Adaptive Banner 1 枠のみ                                                             |
| 課金       | なし(完全無料)                                                                   | $3.99 買い切りで広告永久削除                                                                  |
| 計測       | サイト共通のページ解析(下の「計測」節。実装済み・既定は無効)                     | なし — Analytics を入れないことがアプリの約束([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md)) |
| ゲーム内容 | 30 ゲームすべて+先行公開中の新作(下の「先行公開」節)。正式収録ゲームに機能差なし | 30 ゲームすべて。新作は先行公開で検証後に収録                                                 |

**Play instantly on the web. Play quietly and offline in the app.**

ゲーム機能に差を付けない。広告視聴でも課金でも解放される機能は、どちらの版にも
存在しない(`docs/PRODUCT_PRINCIPLES.md`)。新作の**収録タイミング**だけは版で
異なる(Web が先 — 下の「先行公開(ベータ)」)。これは無料の先行であって、
支払い・広告視聴・アカウントの対価ではない。

## 配信構成

- **Cloudflare Pages の静的アセット配信のみ**。Pages Functions / Workers / D1 / KV /
  Durable Objects / R2 / 独自 API / 認証 / クラウドセーブ / サーバー側生成 /
  定期実行ジョブを一切使わない。追加の固定インフラ費を発生させない。
- 成果物はこのリポジトリの `vite build --mode web`(`apps/simple-games/dist-web/`)。
  `base: './'` の相対パスなので、サブパス配下にそのまま置ける。native 用の `dist/`
  ではない — AdSense 統合は web ビルドにしか入らず、その分離は
  `check-dist-ads-separation.sh` が成果物で機械検証している。
- 配置先は別リポジトリ `pixapps-landing` の `public/simple-games/play/`
  (`pages_build_output_dir: "public"`。2026-08-08 にリポジトリ直下配信から
  `public/` 配下へ移った)。同期は landing 側の `npm run sync:simple-games`。
  **`public/simple-games/play/` は生成物**であり、手で編集しない。直すのは
  このリポジトリのソース。
- GitHub Pages でも配信できる純静的構成を維持する(ホスティング固有機能に依存しない)。

## URL(ゲーム別の入口)

**`?game=<game-id>` で対象ゲームを直接開ける**(2026-08-30 実装、issue #83)。
集客はゲーム単位・継続はコレクション単位、という役割分担を URL の側で成立させる
ためのもので、ゲーム別ガイドを読んだ人が 30 ゲームの一覧からもう一度そのゲームを
探さずに済む。

```text
https://pixapps.ai/simple-games/play/             → コレクションホーム
https://pixapps.ai/simple-games/play/?game=sudoku → Sudoku
```

- 受理するのは `app/registry.ts` の `GameId` だけ。不明値・空値・廃止済み ID は
  **エラー画面を出さず**コレクションホームを開き、パラメータだけを住所から落とす
  (画面と URL を食い違わせないため)。他のパラメータ(リンク元が付けた
  `utm_source` など)とフラグメントは残す — `URLSearchParams` を通すので
  パーセント符号化の見た目は変わりうるが、値は変えない。
- パス(`/play/sudoku/`)ではなくクエリなのは、配信が静的ファイルのコピーで
  あって `index.html` へ書き戻す rewrite が無いこと(上の「配信構成」)、および
  Capacitor WebView のための `base: './'` がパス配下で `./assets/…` を 1 階層
  深く解決してしまうため。hash でもないのは、**ガイドページからリンクとして
  指す**のが目的であり、hash はリンク先の区別として扱われないため。
- **URL は入口であって保存場所ではない。** レベル・デイリー・盤面・セーブは
  URL に出さない(共有された URL が他人の盤面を決めない)。
- 対象ゲーム以外の chunk を先読みしない。直接アクセスでもロードされるのは
  そのゲームの `game-<id>` 1 つだけ(`app/lazyRoots.ts`)。
- **アプリの結果画面の「共有」が配るのはこの URL である**(issue #86)。
  `packages/brand` の `WEB_PLAY_URL` に `?game=<id>` を付けるだけで、短縮 URL も
  リダイレクタも作らない。したがって共有リンクは Web 版・アプリ版のどちらから
  配られても同じ 1 本の入口に落ちる —— アプリを持っていない受け手が、何も
  インストールせずにそのゲームを開ける、というのがこの導線の全部である
  ([ARCHITECTURE.md](ARCHITECTURE.md)「レイヤー規則」)。共有される URL に
  盤面・レベル・成績が乗らないのは上の「URL は入口であって保存場所ではない」
  そのままで、共有のために例外を作らない。結果(時間・スコア等)は共有**文と
  画像**に載るのであって URL には載らない —— 「URL は入口であって保存場所では
  ない」はそのまま。

**履歴の扱い —— 「外から来た」と「コレクションから入った」を区別する。**

- コレクションからゲームを開く → 履歴を 1 つ進める。ブラウザの戻るで
  コレクション、進むでゲームへ。
- ゲームからコレクションへ戻る操作 → 自分が積んだ履歴があるなら `history.back()`
  で**戻る**(進むが生きたまま、往復のたびに履歴が伸びない)。無いなら住所を
  書き換えるだけにする。ガイドページから直接来た人の「戻る 1 回でサイトの外」は
  そのまま残す —— ここを潰すと、サイト内の戻ると外への戻るが同じ操作になる。
- 何段目に居るかは `history.state` の `sgRouteDepth` に持つ。リロードしても
  「コレクションが 1 つ後ろに居るか」を忘れないため。
- **URL に出るのはゲームだけ。設定画面は出さない。** したがってブラウザの戻るは
  設定を閉じず、サイトの外へ出る —— この機能を入れる前と同じ挙動で、増えても
  減ってもいない。設定に住所を与えるのは、この Issue が引いた契約の外側。
- 計測(`game_open` / `game_close`)は直接アクセス・戻る・進むでも、タイルの
  タップと同じく 1 回ずつ。二重送信しない。送るものは増えていない —— 下の
  「計測」節の範囲そのままで、測定 ID が無ければ 1 リクエストも出ない既定 OFF も
  変わらない。ただし**ドキュメントごと去るときは `game_close` が出ない**
  (タブを閉じたときと同じ。直接アクセスしたゲームからブラウザの戻るを押すと
  この経路になる)。これは以前からの計測の穴で、この変更で広がってはいない —
  以前は戻る操作が常にこの経路だった。

**native では動かない。** 実装は `app/webRoute.ts` と `app/App.tsx` にあり、
`Capacitor.isNativePlatform()` の**実行時ガード**で切る(下の「実装上の約束」の
原則どおりで、ビルド時ゲートの例外 3 つは増やしていない)。アプリには住所欄が
無く、同じ操作はハードウェア戻るボタンが既に持っている
([ARCHITECTURE.md](ARCHITECTURE.md)「ハードウェア戻るボタン」)。
App Links / Universal Links は導入しない。

Android アプリのホーム画面ショートカット(issue #110)は、この同じ住所を
Intent の中に運び、同じパーサで読み戻す——`app/shortcutLaunch.ts` が
`?game=<id>` を組み立て、`gameIdFromHref` で読む。ゲーム別の入口はブラウザと
ショートカットで 1 本の契約のまま増えていない。上の「履歴の扱い」
(`history.back()` / `sgRouteDepth`)はそれでもアプリでは一度も動かない——
住所欄も `history` も無い native の世界であることは変わらず、画面の切り替えは
`app/App.tsx` の `appUrlOpen` リスナーが直接行う。

ガイド側の「ブラウザで遊ぶ」CTA は landing リポジトリの
`tools/build-game-guides.js` が全 30 ゲーム × 10 言語ぶんを生成する。手で 300 枚を
直さない。

## オフラインの扱い(アプリとの決定的な違い)

- **Web 版は初回アクセスにアセットのダウンロードが必要**であり、アプリの
  「初回起動から完全オフライン」とは**同一ではない**。この差を曖昧にした表現を
  Web 版・Landing Page・ストア文言のいずれでも使わない。
- 読み込み後のプレイ自体はブラウザ内で完結する(盤面生成・Daily・保存・統計・
  言語・テーマ)。通信が切れてもゲームは止まらない。
- 再訪時のオフライン動作(PWA / Service Worker)は M3 で導入予定。導入後、
  「2 回目以降はオフラインで動作」をここに追記する。**そのとき、下記のホーム画面の
  タグラインを Web 版で出すかどうかを併せて判断する。**
- オフライン時、広告は静かに出ないだけ。エラーを出さず、リトライループも作らない
  (`docs/OFFLINE_POLICY.md` と同じ原則)。

## 広告

**正式な方針は [ADS_POLICY.md](ADS_POLICY.md)「Web 版」節が定める**(この節が
唯一の記述だった期間は 2026-08-02 の Phase A 実装で終了)。要点だけ再掲する:
形式はディスプレイ / アンカー / Vignette を制限付きで、**広告視聴や課金でゲーム
機能を解放しないことだけが版をまたぐ絶対原則**。
[PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md) の「Banner ads only」と
ADS_POLICY.md の禁止フォーマットは**アプリのスコープ**であり、この方針は
それを上書きするのではなく別スコープを定めている。

実装状況(2026-08-02):

- **実装済み**: 2 モードビルド(`--mode web` → `dist-web/`。AdSense 統合は
  このビルドだけに同梱され、native 側は成果物検査で不在を保証)、
  **アンカー(Auto ads)の起動時ブートストラップ + 全画面の下端退避余白**
  (プレイ中も出てよい — 2026-08-02 決定。`services/ads/web/boot.ts` +
  `data-sg-web-ads`)、ホーム画面のディスプレイ 1 枠(`WebAdSlot`)、
  **リザルト画面のディスプレイ 1 枠 — 3 局に 1 回のみ**(`ResultAdSlot` +
  `resultCadence.ts`。セッション最初のリザルトには出さない)、テスト用
  プレースホルダ(AdSense に公式テスト ID がないため、通信ゼロのローカル表示)、
  GitHub Actions「Web build」での test / production / disabled 切り替え。
- **既定は広告なし**: `VITE_ADSENSE_CLIENT` が注入されるまで、本番ビルドでも
  何も出ない(枠も余白も確保しない)。**配信中の Web 版に広告はまだ 1 つも
  出ていない**(本番有効化の前提となる人間作業は ADS_POLICY.md「Web 版」の
  一覧どおり。プライバシー文言の追記と「Auto ads はアンカーのみ有効化」も
  そこに含まれる)。
- **未実装**: デスクトップサイドレール(保留)、About の支援文言、Vignette。
  「アプリへの送客ブロック」もここに並んでいたが、**2026-08-30 に実装した** —
  広告とは独立した導線として、下の「アプリへの送客」節が持つ(issue #85)。
  Vignette の前提として書いていた
  「hash ナビゲーション」は、上の「URL(ゲーム別の入口)」がクエリパラメータ +
  History API で満たした(hash ではない形で)。**Auto ads が SPA の History
  ナビゲーションを区切りとして拾うかは未検証**で、そこは
  [plans/2026-07-31-web-play.md](plans/2026-07-31-web-play.md) M4 のまま残る。

## 計測(アナリティクス)

**「Analytics なし」はアプリの約束であり、Web 版は対象外とする**(2026-08-03 決定。
[PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md)「適用範囲」の版差分に明記)。
pixapps.ai はトップ・ハブ・ゲームガイドの全ページでサイト共通の
Google Analytics(GA4)を使っており、Web 版もその対象に含める —
play だけをサイト計測の空白にしない。計測の第一の用途は、先行公開した新作を
正式収録するかの判断である(下の「先行公開(ベータ)」)。

版をまたいで変わらないのは**ゲームデータがローカルに留まること**。盤面・セーブ・
記録・個人のプレイ内容は、どちらの版でも送信しない。Web 版が送るのは利用の集計 —
ページビューと、どのゲームを開いた / 閉じたかのシェル層イベント — だけである。

実装の規律(広告と同じ。実装済みで、以後も守る):

- `--mode web` ビルドのみに同梱し、native 成果物には**不在**。分離は
  `.github/scripts/check-dist-ads-separation.sh` が計測マーカー
  (`googletagmanager` / `simple_games_play` / `game_open` / `game_close` /
  `G-...`)でビルド成果物から証明する(ソースの規約だけにしない)。
  同じスクリプトは web 側で**送信できる形**であることも見る — 下の
  実装状況の `push(arguments)` 検査。
- 測定 ID はソースに書かない。ビルド時に環境変数(`VITE_GA_MEASUREMENT_ID`)で
  注入し、未設定なら計測コードを 1 バイトも読み込まず、リクエストも送らない
  (`VITE_ADSENSE_CLIENT` と同じ既定 OFF)。
- オフライン時は読み込まない・リトライしない。計測のあらゆる失敗はゲームを
  止めない([ADS_POLICY.md](ADS_POLICY.md) / [OFFLINE_POLICY.md](OFFLINE_POLICY.md)
  と同じ原則)。
- イベントを送るのはシェル(起動時のページビューは `main.tsx`、ゲームの
  出入りは `app/App.tsx`)だけ。`games/*/game/` は Pure TypeScript のまま、
  ゲーム側コードに計測を書かない。
- 計測モジュールが持つリスナーは **`visibilitychange` の 1 本だけ**で、
  初期化が成功したときにページ寿命で 1 度だけ張る。音サービスと同じ
  「シェル常駐」の枠であり([GAME_LIFECYCLE.md](GAME_LIFECYCLE.md))、
  **ゲームごとの effect に畳み直さない** — 畳むと前面時間が二重に数えられる。

有効化の前提(人間作業 — AdSense 本番有効化と同じ束で行う):

1. 公開ページ <https://pixapps.ai/simple-games/privacy> の改定(**2026-08-03 実施済み**)。
   旧文面は「ゲームのページは意図的に Google Analytics の対象外にしている」と明言して
   おり(2026-08-02 公開)、この決定はその**撤回**にあたる。黙って差し替えず、
   改定として明記した — 日英とも当該段落に「2026-08-03 の改定までは対象外にしていた」
   と残してある。**開示が先、収集が後**の順序をとる(逆は許されない)。同ページの
   AdSense の説明も、実際の掲載より先に現在形で書いてある既存の前例に揃えた。
2. GDPR 同意は AdSense と共通の CMP(Privacy & messaging / consent mode)で扱う。
   同意処理の失敗でゲームを止めない・遅らせない。
3. **landing 側のテストガードを同じ PR で更新する。** `pixapps-landing` の
   `tests/ui.test.js` は同期後の `simple-games/play/index.html` に
   `googletagmanager` / `gtag(` が含まれないことを検査しており
   (「the game build must ship none」)、計測を入れた web ビルドを同期した瞬間に
   **赤くなる**。これは事故ではなく、旧方針をそのまま機械化したものなので、
   ガードの意図を「native 成果物に不在」へ書き換える必要がある。
   このリポジトリ側の `check-dist-ads-separation.sh` 拡張と対になる作業。
4. **GA4 プロパティの「拡張計測機能 → 履歴イベントに基づくページの変更」を確認する**
   (2026-08-30 追加)。上の「URL(ゲーム別の入口)」でゲームの開閉が `pushState` /
   `popstate` を出すようになったため、この既定 ON の設定が生きていると、こちらが
   送っていない `page_view` が 1 開閉ごとに増える。送るイベントを増やさないという
   この節の約束はコードの側の話であり、プロパティ設定でそれを崩さないこと。

**運用 — 何をどう読み、次にどのゲームを直すかは
[GROWTH_MEASUREMENT.md](GROWTH_MEASUREMENT.md) が定める。**この節が持つのは
方針(何を送る / 送らない、どこに置く)であり、GA4 と Search Console の
読み方・判断手順・限界はあちらにある。

実装状況(2026-08-30): **実装済み・本番で受信を確認した。ただし 2026-08-30
に直すまで、本番へは 1 件も届いていなかった。** 実装は `services/analytics/web.ts` で、`--mode web`
ビルドから dynamic import される。イベントは `window.dataLayer` に積まれて
いたが、Google タグはキューの要素を **`arguments` オブジェクトのときだけ**
コマンドとして実行し、独自シムが積んでいた**通常の配列は黙って捨てられて
いた** — 成果物にはイベント名も測定 ID もあり、ユニットテストも緑で、
`collect` リクエストだけが 1 件も出ていない状態だった(issue #84)。公式
スニペットと同じ `dataLayer.push(arguments)` に直し、**中身ではなく形**を
テストと成果物検査(`check-dist-ads-separation.sh` の `push(arguments)`)で
固定した。修正版を公開したのち、本番ページでゲームを開閉して GA4 Realtime に
`game_open` / `game_close` / `page_view` が出ることを確認している
(2026-08-30。以後の運用と未実施の一覧は
[GROWTH_MEASUREMENT.md](GROWTH_MEASUREMENT.md)「実装状況」)。

2026-08-03 の「実装は AdSense 本番有効化と同じマイルストーンで行う」は
**撤回する**。実際には計測が先に入り、AdSense 本番はまだ来ていない
([ADS_POLICY.md](ADS_POLICY.md)「Web 版」)。黙って前提を落とさず、束が
崩れたことをここに記録する。上の「有効化の前提」2(GDPR 同意を AdSense と
共通の CMP で扱う)には**実施の記録がこのリポジトリに無い** — 同じ束の
ADS_POLICY.md 側の項目 3 にも 実施済み の印は付いていない。**ここは
「たぶん済んでいる」で通さない。**

3(landing 側のテストガード)は **実施済み**(2026-08-30 に実物を読んで確認)。
この節はかつて「計測を入れた web ビルドを同期した瞬間に赤くなる」と書いて
いたが、landing 側は既に作り直されていた — `tests/ui.test.js` が禁じるのは
`play/index.html` の**インライン**タグだけで、計測は lazy chunk に入るため
該当しない。別ファイル `tests/simple-games-play-analytics.test.js` が測定 ID と
イベント名の**存在を要求**し、公開ワークフローが
`EXPECT_SIMPLE_GAMES_ANALYTICS=1` でそれを回している。**ガードの意図は
「native 成果物に不在」へ書き換え済みである。**

## 先行公開(ベータ)

**Web 版は新作の先行公開チャンネルである**(2026-08-03 決定)。新しいゲームは
アプリ収録より先に Web 版に入り、実地の反応を見てから正式収録する。ベータなのは
**個々の新作ゲームだけ** — Web 版全体と既収録 30 ゲームはベータではない
(ストア版と同一コードの完成品であり、AdSense の審査もこの品質で受ける)。

- **「先行」であって「限定」ではない。** 先行公開ゲームは正式収録後も Web 版から
  消えない。期間限定はやらない(期間限定イベントは
  [PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md) の禁止パターン)。
  Coming Soon 表示の禁止もそのまま — 遊べないものを予告しない。先行公開はその逆で、
  **遊べるものだけを出す**。
- **無料の先行であって、対価ではない。** 支払い・広告視聴・アカウントで解放される
  先行アクセスを作らない(版をまたぐ絶対原則のまま)。
- 公開文言は目的の形で書く: 「先行公開で反応を見て正式収録を決めます。計測は
  そのためです」。データと引き換えという交換の形にしない
  ([BRAND.md](BRAND.md) の「静かに、正直に」)。

表示:

- 該当ゲームのタイトルカード等に言語非依存の「BETA」バッジを付ける。
- セーブが消える可能性の説明文は、削除に関わる高リスク文言なので **en / ja のみ**
  ([I18N_POLICY.md](I18N_POLICY.md))。他言語ではバッジのみ出す。
  (かつてここは「アプリへの送客ブロックと同じ扱い」と書いていた。送客のほうは
  2026-08-30 に 14 言語へ出す形になり、**もう同じ扱いではない** — 下の
  「アプリへの送客」を参照。あちらは文面から価格・購入・広告を落とせたので門を
  通す形にできたが、こちらの「セーブが消える」は落としようがない。)

保存データ(互換契約の唯一の例外):

- **ベータ中のゲームに限り**、スキーマ変更によるセーブのリセットを許容する。
  ただし黙って消さない — 上記の説明文で先に告知した上で。既収録ゲームの
  「移行する・再解釈しない」契約には一切触れない。
- **正式収録 = スキーマ凍結点。** そこから通常の互換契約(移行のみ・**保存スキーマの
  永続化ラウンドトリップテスト**の作成)が始まる。`game/compatibility.test.ts`(盤面/
  配札/ウェーブの golden テスト)は生成の決定性を守るものであり、これだけでは
  保存データの生存を検証できない — 要件は
  [RELEASE_CHECKLIST.md §0](RELEASE_CHECKLIST.md) が定める。Web のベータセーブも
  凍結点からは契約データであり、以後は移行する。下の基準 1 により、凍結される
  スキーマは直近 2 週間実地で生き延びたものになる。
- `storageKeys` は先行公開の時点で registry に登録する(「Reset Local Data」が
  Web でも嘘をつかないため)。

正式収録の基準(2026-08-03 決定。満たしても自動では収録しない — アプリ収録は
リリース作業であり、明示的な人間の判断で行う):

1. **直近 2 週間の安定稼働。** スキーマ変更(セーブを消す変更)・既知のクラッシュ・
   進行不能なしで 2 週間。壊す変更を入れたら時計は巻き戻る。
2. **計測で滞在時間が十分であること。** シェル層イベント(どのゲームを開いた /
   閉じたか+滞在時間)で確認する。しきい値の数字は決め打ちしない — 判断は人間が
   行い、既収録ゲームの滞在時間を参照点にする。この確認のために「計測」節の範囲を
   広げない(盤面・プレイ内容は送らない)。

実装状況(2026-08-03): **方針のみ・未実装**。先行公開中のゲームは現在ない。
出し分けは registry のエントリでチャンネルを宣言し、シェルの実行時ガードで行う
予定(「実装上の約束」どおりビルドは分岐させない。native バンドルに先行公開
ゲームのコードが含まれるのは許容 — 公開ソースで元々見える。ストア掲載文には
正式収録まで出さない — `apps/simple-games/store/listing.md` の既存ルール)。

## サイトクローム(グローバルヘッダー)

Web 版の位置づけ「PixApps への入口」(上の役割分担表)を実装するもの。
pixapps.ai の全ページが載せている共通ヘッダー(`/global-header.js` +
`/global-header.css`。landing リポジトリの持ち物)を、Web 版でも出す
(2026-08-04 決定。計画は [plans/2026-08-04-web-site-chrome.md](plans/2026-08-04-web-site-chrome.md))。

**出す画面 / 出さない画面 —— 判断軸は「スクロールする画面か、固定ビューポートの
盤面か」。**

- **出す**: コレクションホーム / 設定 / 30 ゲームすべてのホーム。
- **出さない**: 盤面(プレイ中)・リザルト・ゲームのロード画面。
- 盤面に 64px のヘッダーを足すと、下端のアンカー退避(116px + safe area)と
  合わせて**盤面そのものが縮む**。ホーム系はスクロール面なので、同じ 64px の
  コストが「スクロールが少し深くなる」に変わる — 普通の Web ページと同じ代償で、
  こちらは許容する。この軸だと設定 / About は自動的に「出す」側、リザルト
  (盤面上のダイアログ)は自動的に「出さない」側に落ちる。

**配置はインフロー(スクロールで流れて消える)。** landing の `position: fixed`
常時 64px 専有は SPA では採らない。専有コストが実質ゼロになり、遊び始めたら
視界から消えるほうがこの製品の「静けさ」に合うため。実装は landing の CSS を
SPA 側で中和する(`.sg-web-chrome` スコープで `position: relative`、
`html body` の詳細度で `padding-top: 64px !important` を打ち消す)。

**ヘッダー DOM は 1 つをページ寿命で保持し、画面ごとに移し替える。**
ヘッダーのスクリプトは初期化時にリスナーを多数張るため、画面遷移のたびに
作り直すとリスナーが積み上がる。`WebChromeSlot` はマウント時にヘッダー要素を
自分の中へ取り込み、アンマウント時に body へ戻す(スクリプトは 1 回しか
実行しない)。スロット自身はリスナー・タイマー・RAF を持たない
([GAME_LIFECYCLE.md](GAME_LIFECYCLE.md))。

**言語。** ヘッダー文言はサイトの持ち物で **ja / en のみ**。アプリの 14 ロケールとは
独立しており、それ以外の言語の画面には英語のヘッダーが載る(割り切り)。
アプリが解決したロケールから**単一ロケール構成**を組み立てて渡すので、
ヘッダーの言語スイッチャーは構造的に出ない(アプリの言語設定と二重に
なることを防ぐ)。**この機能で i18n キーは 1 つも増やさない** —— 増やすと
14 言語ぶんの翻訳と高リスクキーの門が発生するため([I18N_POLICY.md](I18N_POLICY.md))。

**オフラインと失敗。** オフライン時はスクリプトも CSS も読み込まず、リトライも
しない(次のページロードで再試行 — [OFFLINE_POLICY.md](OFFLINE_POLICY.md) と同じ)。
読み込み失敗・実行失敗はすべて静かに握りつぶす。**ヘッダーが出ないだけで、
ゲームは一切影響を受けない。** インフロー配置なので、出ないときに空隙も残らない
(広告枠と違って場所を予約しない)。
**「出ない」を部分失敗でも守る**: ヘッダーを画面へ渡すのは、スクリプトが構築を
終え、**かつ**サイト側の CSS が読み終わった時だけ。こちら側の CSS は位置決めしか
持たない(見た目はサイト側の CSS が持つ)ので、スクリプトだけで渡すと、CSS の
取得失敗が「ヘッダーなし」ではなく**素のままのナビゲーションの塊**として出てしまう。

**ヘッダーの開いた面は、ヘッダーと一緒に画面を去る。** モバイルのドロワーは
`<body>` 直下に作られるためヘッダーを退避させても付いてこず、CSS でも隠せない。
開いたまま残ればサイトクロームを出さないはずの盤面を覆うので、退避時にドロワーと
ドロップダウンを閉じる。

**native には不在。** `--mode web` のビルド時ゲートに置き、native 成果物への
不在は `check-dist-ads-separation.sh` が広告・計測と同列に検査する。

計測を本番有効化すると、ヘッダーのクリックは landing の `trackClick` が
`navigation_click` として送る(`window.gtag` があるときだけ動く実装なので、
こちら側の追加実装は不要)。

  残る約束を門に載せろ」** が現在の規則である。次に同じ判断をする人は、
  まず上の 1 を満たせるかを見ること — 満たせないなら、答えは以前と同じく

## アプリへの送客

Web 版には「もっと静かに遊びたい人向けにアプリがある」という案内を置く
(**2026-08-30 実装、issue #85**)。広告を嫌がらせとして使わない — 「広告が嫌なら
出ていけ」ではなく「より快適な選択肢がある」という案内にする。

**体験の前に求めない。** 実際に遊んだあとの自然な区切りで、1 度だけ案内する。

- **Web 版のみ。** 実行時ガード(`Capacitor.isNativePlatform()`)で、上の
  「実装上の約束」どおりビルド時ゲートの例外は 3 つのまま増やしていない。
  native では表示も、カウントも、保存も、追加の通信も**一切ない**。
- **2 回ゲームからコレクションへ戻ったあと**に eligible になる。初回訪問と
  1 ゲーム目には出ない。数えるのはシェルの `exitGame` 経路だけで、ゲーム側の
  コードは 1 行も知らない。
- **ただし `?game=<id>` で「ゲームの上に着地した」訪問だけは 1 回で出す**
  (2026-09-04、`WEB_APP_PROMPT_FROM_LINK_AT`)。共有された結果やガイドから
  来た人は、**もう人に勧められて来ている**うえ、送られた 1 本を遊んで帰ることが
  多い。2 回待つと、その人には一度もアプリの存在を伝えないまま終わる ——
  共有導線を作っておいて着地点で何も言わないのは筋が通らない。
  自分でコレクションを開いた人は今までどおり 2 回。**0 回にはしない**
  (体験の前に求めない)し、1 度きりであることも変えない。
  「どう着地したか」はセッション内の事実として持つだけで、保存も送信もしない。
- コレクションホームの**インラインカード**として出す。位置は「最近遊んだ」より下、
  全ゲーム一覧より上。モーダル・全画面・toast・自動遷移・カウントダウンは使わない。
- **表示した時点で `shown` を確定する。** 閉じても、ストアリンクを押しても、
  タブを落としても、そのブラウザで 2 度目はない。
- **オフラインでは出さない**(`isOnline()`)。ストアリンクが何も開けない状態で
  1 度きりのカードを使い切らないため。リトライループも再接続監視も作らない —
  次の通常起動・次の帰還で普通に再判定される。
- ストアリンクは User-Agent で出し分ける: Android → `PLAY_STORE_URL`、
  iPhone / iPad → `APP_STORE_URL`、Desktop・判定不能 → 両方。**判定に使うだけで、
  送信も保存もしない。** URL は `packages/brand` の定数を再利用し、取得のための
  通信は増やさない。
- 状態は独立スキーマ `sg.webAppPrompt`(`gameExits` / `shown`、schemaVersion 付き)。
  `sg.review` は流用も変更もしない — ストアレビュー導線の頻度と意味を、別の導線の
  副作用にしないため。「ローカルデータを削除」の対象に入る(共有キーは
  `Object.values(STORAGE_KEYS)` で列挙されるので、自動的に含まれる)。
  **削除するとカードは復活する** —— 2 回遊び直せばまた出る。データを消した
  ブラウザは「まだ案内していないブラウザ」であって、案内済みの記録だけを
  残すのは削除が半分嘘をつくことになるため(レビュー導線も同じ扱い。
  [REVIEW_PROMPT_POLICY.md](REVIEW_PROMPT_POLICY.md)「保存」)。
- **計測は増やさない。** 表示もクリックもイベントを送らない(「計測」節の範囲は
  ページビューとゲームの開閉のままである)。

文面(`webAppPromptTitle` / `webAppPromptBody`):

```text
A quieter way to play, offline from the first launch.
The app opens from your home screen and keeps your progress on your device.
```

```text
もっと静かに、最初から完全オフラインで。
アプリなら、ホーム画面からすぐ起動でき、進行状況を端末内に保存できます。
```

**書けるのは、アプリに本当に存在する差だけ。** 初回起動から完全オフライン
(上の「オフラインの扱い」)と、ホーム画面からの起動である。書かないもの:
Web 版に機能制限があるような表現、アプリ限定ゲーム・限定機能(存在しない)、
「今すぐ」「見逃す」「残り」等の緊急性、「広告なし」(買い切り前はバナーがある)、
アカウント同期・クラウド保存(どちらの版にも無い)。

**掲出は 14 言語すべて。** かつてここは「en / ja のみ」と書いていた —— 理由は
価格・購入・削除・プライバシーに関わる文言の機械翻訳を [I18N_POLICY.md](I18N_POLICY.md)
が禁じていることだった。**その理由は、文面から価格と購入と広告を落としたことで
消えている。** 代わりに残る約束は「最初から完全オフライン」であり、これは
I18N_POLICY.md の高リスクキー 5 番(無料・オフライン・paywall 不在の保証)
そのものなので、2 キーを `highRiskKeys.ts` に登録して**リリース前の門の対象に

リリース前に読む。**

## 実装上の約束

- ゲームロジック(`games/*/game/`)は Pure TypeScript のまま。React / DOM /
  Capacitor / 広告 / 課金 / ストレージに依存させない。Web 版のために
  巨大なプラグイン基盤や過剰な抽象化を作らない。
- web と native の違いは**実行時ガード**で表現する。ビルドを不必要に分岐させない
  (公開ソースと配信物が対応していることが、この製品の証明手段そのもの)。
  例外は **Web 広告・計測・サイトクロームの 3 つ**だけで、いずれも
  `--mode web` のビルド時ゲートに置く。その分離は
  `.github/scripts/check-dist-ads-separation.sh` が**ビルド成果物**で機械検証する
  (native 側に不在・web 側に存在。ビルドが要るので grep だけの
  `check-principles.sh` とは別スクリプトになっており、CI の verify ジョブが呼ぶ)。
  **URL ルーティングは 4 つ目の例外にしていない**(上の「URL(ゲーム別の入口)」)。
  外部の SDK もサイト側の資産も持ち込まず、native では 1 行も走らない実行時ガードで
  足りるものを、成果物の分離検査が要る側へ移す理由がないため。Android の
  ホーム画面ショートカット(issue #110)も同じ理由でビルドゲートではなく
  実行時ガード側に置く(`Capacitor.getPlatform() === 'android'`)。
- `index.html` は 1 枚のまま。Web 向けの meta / OGP / canonical はネイティブ側の
  WebView(Android WebView / iOS の WKWebView)が無視するので、分ける理由がない。
  **共有リンクのプレビューもこの 1 枚が持つ OGP をそのまま使う**(issue #86)。
  `?game=<id>` はクエリなので同じページであり、ゲームごとの OG 画像を出すには
  動的生成か 30 枚の静的ページが要る —— どちらも固定インフラ費と維持を増やす
  ので、作らない。ゲーム別の絵が要るなら、既にあるゲーム別ガイドを共有先に
  するかどうかを別途決める話になる。結果画面の共有が付ける画像カードは共有
  シートに渡す**ファイル**であり(`services/share/card.ts`)、リンクのプレビュー
  (OGP)ではない —— だからゲーム別 OG 画像を作る理由は増えていない。
