# Loop Puzzle — 正式ゲームルール

この文書は Simple Games の新作「Loop Puzzle」(No. 44)の唯一のルールソースである。
実装(`apps/simple-games/src/games/loop-puzzle/`)、Hint、テスト、Quick Rules は
すべてこの文書に従う。コードはここへ `§n` で言及する。挙動や数値を変えるときは、
同じコミットでこの文書を先に直す。

ブランド原則([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md))はこの文書より上位にある。
Undo と Hint は無制限・無料、広告視聴や課金で解放しない、ストリークで急かさない、
プレイ中に時計を見せない、時間制限を作らない。

ゲーム ID は `loop-puzzle`、i18n キーの接頭辞は `loopPuzzle`、保存キーの接頭辞は `lp.`、
カテゴリは `logic` である。**Web 版の先行公開(ベータ)チャンネル**(registry の
`channel: 'web-beta'`)で、アプリ(Android / iOS)には正式収録していない
([WEB_VERSION.md](WEB_VERSION.md)「先行公開(ベータ)」、計画は
[plans/2026-10-17-unblock-snake-loop-bridges-peg.md](plans/2026-10-17-unblock-snake-loop-bridges-peg.md))。
保存スキーマはまだ凍結していない(§12)。

数字を手がかりに格子の辺をつなぎ、1 本の閉じたループを作る論理パズルである。
**一般に Slitherlink と呼ばれる形式**を参考にしているが、Simple Games での正式名称は
Loop Puzzle であり、他社の商品名・問題・盤面画像・画面デザインは使わない
([BRAND.md](BRAND.md)「自社タイトルと比較対象の名前」)。盤面はすべてこのゲームの生成器が
端末上で作る(§8)。同じ点の格子を使う既存の 2 本との違いは §15 に書く。

## 1. 盤面

- W×H の**マス**と、その角にある (W+1)×(H+1) 個の**点**。隣り合う 2 点を結ぶ線分が
  **辺**で、横の辺が (H+1)×W 本、縦の辺が H×(W+1) 本、合計 2WH + W + H 本ある。
- 番号(`game/grid.ts`。保存形式(§12)もこの番号で書く):
  - マス (r, c) = r·W + c(r < H、c < W)
  - 点 (r, c) = r·(W+1) + c(r ≤ H、c ≤ W)
  - 横の辺 (r, c) = r·W + c — 点 (r, c) と点 (r, c+1) を結ぶ(r ≤ H、c < W)
  - 縦の辺 (r, c) = (H+1)·W + r·(W+1) + c — 点 (r, c) と点 (r+1, c) を結ぶ(r < H、c ≤ W)
  - マスの 4 辺は上・右・下・左の順。マスの**角**(同じ点で出会う、そのマスの 2 辺の組。
    T2 が読む — §7)は 4·マス + j(j = 0 左上、1 右上、2 右下、3 左下)。
- 難易度ごとの盤(`game/types.ts` の `PRESETS`):

| 難易度 | マス | 点  | 辺  |
| ------ | ---- | --- | --- |
| Easy   | 4×4  | 5×5 | 40  |
| Medium | 5×5  | 6×6 | 60  |
| Hard   | 6×6  | 7×7 | 84  |

**難易度はサイズだけでは決めない。**必要な技法の深さと手がかりの密度で決める(§7)。
Hard を 6×6 にしただけで易しくならないことは、全走査で測って固定している(§7、§16)。
7×7 以上は作らない — 360px 幅で 1 辺の当たり判定を指で外さない大きさに保つため(§4)。

**盤面に翻訳の要る文字は 1 つも載らない。**数字は ASCII の `0`〜`3`、線と × はインライン
SVG / CSS で描く。読み上げ名だけが i18n を通る(§14)。盤面は RTL でも左右反転しない。

## 2. 手がかり

- 各マスは**数字 0〜3** を持つか、**空白**である(`Clue = number | null`)。
- 数字は「そのマスを囲む 4 辺のうち、ループに含まれる辺の本数」。空白は何も指定しない。
- 4 は出さない。4 辺すべてがループになるのは、ループがそのマス 1 つを囲むときだけで、
  生成するループは 2 マス以上で穴のない領域の境界なので、どのマスの本数も 3 以下になる(§8)。
  保存の検証も `4` を拒否する(§12)。
- 盤面は生成後に変わらない。プレイヤーが書くのは辺の印(§4)だけである。

## 3. ルールと勝利

1. 隣り合う点を辺で結ぶ。斜めの線はない。
2. 線は**1 本の閉じたループ**でなければならない。**交差・分岐・複数のループは禁止。**
3. ループが通る点の**次数は必ず 2**、通らない点の**次数は 0**(次数 = その点に集まる線の数)。
   格子の点で交差するには次数 4 が要るので、規則 3 が交差と分岐を同時に禁じる。
4. 数字のマスは、ループに含まれる辺がちょうどその本数。
5. 線が 1 本もない盤はループではない(数字が 0 と空白だけでも、空の盤は解にならない)。

- **勝利**: 線(LINE)の辺が 1 本の単純閉路をなし(全点の次数が 0 か 2、線がすべて
  つながっている、1 本以上)、すべての数字を満たした時点(`engine.ts` の `isSolved`)。
  **判定は規則で行い、保存している解と照合しない。**出題は一意解なので(§8)規則を
  満たした線は必ず解と一致し、「きれいに見えるのに完成しない盤面」は作れない。
- **× (CROSS)は勝利判定に使わない。**× は「ここはループに含めない」というメモで、
  完成判定は LINE だけを評価する。× を 1 つも書かずに勝ってよく、× を書き忘れた辺が
  あっても勝ちは変わらない。
- 敗北は存在しない。ミス回数の制限も、ライフも、ゲームオーバーも、時間制限もない(§15)。
- 勝利への遷移は 1 回だけ起きる。勝った盤では印を書けず、Undo もできない
  (`session.ts` の `doCycle` / `doSet` / `doUndo` が `solved` を拒否する)。

## 4. 操作

- **辺をタップすると印が順に切り替わる: 未定(UNKNOWN)→ 線(LINE)→ ×(CROSS)→ 未定。**
  1 タップ = 1 手(Undo の単位 — §6)。マスや点そのものをタップする操作はない。
- **当たり判定は広く取る**(誤操作の防止)。仕組みは 1 つだけ: 盤は CSS grid で、点の
  トラック(細い。360px 幅で 10px、600px 以上で 12px)と、マス 1 つを **3 割 · 4 割 · 3 割**
  の 3 本に割ったトラックを交互に並べ、外周の点の外側にも 3 割のトラックを置く
  (`LoopPuzzleBoard.tsx` の `tracks`: `3fr 点 (3fr 4fr 3fr 点)×W 3fr`)。**辺は 1 本ずつ
  `<button>`** で、そのボタンの grid 上の領域が**そのまま当たり判定**である: 辺の全長
  (2 点の間 = マスの 3 本)× 点のトラックとその両側の 3 割のトラック(外周の辺は盤の外側の
  3 割の余白)。見た目の線は細いまま、ボタンの中の小さな要素が描く(§13)。疑似要素で
  広げる方式は採らなかった — 当たり判定と見た目のずれが無く、ボタンの矩形がそのまま判定に
  なる方が古い WebView でも確かだからである。考え方は Dots and Boxes §10 のトラックの
  当たり判定で、コードは共有しない。
  - **マスの中央(4 割四方)はどの辺にも当たらない。**数字の上やその近くをタップしても、
    4 辺のどれかを偶然切り替えない(対角線で 4 つに分ける方式は中央で 4 辺が接し、数字の
    近くのタップがどの辺になるか紙一重になるので採らない)。
  - **中央は「穴」ではなく、何もしない要素(`.lp-pad`)で埋める。**タッチ画面の Chromium
    (Android の Chrome / WebView)は、操作できる要素の無い所に落ちたタップを指の届く範囲で
    いちばん近いボタンへ寄せる(touch adjustment)。穴のままだと、マスの中央のタップが下の辺
    などに寄せられて切り替わる — 実ブラウザ(Chromium 141 のタッチ再現)で、穴のままでは
    中央のタップ 3 回がすべて下の辺を切り替え、パッドを置くと 3 回とも何も起きないことを
    確かめた(2026-10-17)。パッドはイベントを 1 つも受けないが、`:active` に依存する CSS 規則が
    1 つあることで「タッチに反応する要素」と判定され、そこに落ちたタップはパッドに留まる
    (規則を消すと寄せが戻ることも同じ計測で確かめた。`contrast.test.ts` が規則の存在を
    固定する)。これはブラウザの経験則に頼っており、古い WebView と iOS の Safari では
    実機で見ていない(§16「未確認のこと」)。
  - 点のすぐ近くの小さな四角(3 割 × 3 割)では、縦横 2 本の判定が重なり、DOM で後に
    並ぶボタンが取る(マスの上の角では縦の辺、下の角では横の辺)。点そのもの(点のトラックの
    小さな正方形)はどの要素にも属さず、タッチではいちばん近い辺に寄せられる。どちらも
    「どの辺もありうる位置」で、Undo とタップの循環で直せる。
  - 実測(Chromium 141、2026-10-17): 6×6 を 360 × 640 で表示すると、Web 版の広告の予約
    (画面下 116px)がある状態で盤は 319px 四方(高さで決まる)、マスのトラックは約 37.4px、
    辺 1 本の判定の厚みは約 32.5px(線の両側に約 11px ずつ + 点のトラック 10px)。予約の
    無い状態(アプリと同じ。予約の属性を外して計測)では盤は 352px、マス約 42.4px、厚み約 35.5px。
    **盤には下限がある**(§13「大きさ」): 高さが足りない画面でも、辺の判定の厚みは約 29px、
    数字は約 16.6px より小さくならない(6×6 で盤 281px。5×5 は 239px、4×4 は 197px)。どれも
    Dots and Boxes の 24px 以上を上回る。下限を入れる前は高さだけで縮み、横持ちの 640 × 360
    で盤が 39px(辺のボタンの幅 0px)になって操作できず、360 × 460 では厚み 10px だった
    (2026-10-17 のレビューの計測)。線の真上・線から 12px 上下のタップは同じ辺を
    切り替え、マスの中央とそこから 6px ずれた点のタップは何も切り替えない(リポジトリの外の
    計測スクリプトによる。テストでは grid の配置で固定する — `LoopPuzzleBoard.test.tsx`)。
  - 判定はボタン(とパッド)の矩形だけで決め、盤全体の座標計算(盤レベルの pointer
    ハンドラ)や `clip-path` による当たり判定には頼らない。タップは各ボタンの click で受ける。
- **ドラッグで連続して引く操作は作らない**(v1)。1 回の押下と離しが 1 タップで、
  指が動いてもなぞりにはならない。盤は pointer イベントを 1 つも聞かず、ボタンの click
  だけを受ける: OS が取り消したタッチ(`pointercancel`)は click にならないので、そのタップは
  何も書かない。押下の状態を持たないので、取り消しの後に残るものも無い
  (`src/test/pointerContractWiring.test.ts` の対象外 — pointer ハンドラが無い)。盤は
  `touch-action: manipulation` で、ダブルタップのズームがタップを奪わない(ピンチは効く)。
- **長押し・モード切替は作らない。**線と × の切り替えはタップの順序だけで行う
  (モードボタンを置かない — 迷いと手数を減らす)。
- **マウス**: 左クリックがタップと同じ。右ボタン・中ボタンは何もしない。
- **キーボード**(画面に無い機能をキーボード専用にしない): 辺はボタンで、盤全体が
  **1 つのタブ位置**(roving tabindex — 最後にフォーカスした辺が Tab で入る辺)。
  矢印キーで辺から辺へ移り、Enter / Space でタップと同じ切り替え。移動の規則: 辺を
  「横の辺の段」と「縦の辺の段」が交互に並ぶ表として見て、←/→ は同じ段の隣の辺、
  ↑/↓ は上 / 下の段へ — 横の辺からは左端の点を通る縦の辺へ、縦の辺からは右側の横の辺へ
  (↓ のあと ↑ で元の辺に戻る)。盤の端ではその場に留まる(`edgeInDirection`)。
  盤の外にフォーカスがあるとき(結果カードや ↻ の問いが閉じた後など)、最初の矢印キーは
  フォーカスを盤のタブ位置へ移すだけ(Tab で戻らなくてよい)。`L` で線、`X` で ×、`Delete` / `Backspace` で空を、フォーカスした辺へ直接書く(`doSet`。
  タップで届く状態への近道で、新しい機能ではない)。`Ctrl/Cmd+Z` で Undo、`H` で Hint。
  押しっぱなしのキーリピートでは動かさない(Enter の自動の再クリックも止める)。
  修飾キー付きのキーは盤のものではない。結果カードと確認ダイアログの間は効かない
  (`.game-content` が `inert`、キーの受け口も外す)。
- 状態遷移は純粋関数(`engine.ts` の `cycleEdge` / `setEdge`、`session.ts` の
  `doCycle` / `doSet`)。`doSet` は「その印を直接書く」入口で、キーボードの直接入力が
  使う場合のためにある。変化がなければ null を返し、履歴を積まない。

## 5. 表示と矛盾

- **矛盾表示は常時オン**(`engine.ts` の `findConflicts`)。規則から見て今すでに破れている
  ものだけを示し、**解とは照合しない**:
  - **数字の矛盾**: 線が数字より多い、または「線 + 未定の辺」が数字に届かない(× の
    書きすぎ)。
  - **点の矛盾**: 線が 3 本以上集まる点(分岐・交差)、線が 1 本だけでほかの辺がすべて ×
    の点(行き止まり。盤の外周の点は辺が少ないだけで、同じ読み方)。
  - **ループの矛盾**: 閉じたループがあり、それ以外にも線がある(複数のループ、または
    閉じたループの外の線)。その閉じたループの辺を示す。
  - 閉じたループが 1 本だけで他に線がないのに数字が合わないときは、合わない数字を示す
    (閉じたループには分岐か 2 本目を作らずに線を足せないので、今のままでは確定的に
    合わない)。
- **矛盾を推測で書き換えない。**表示するだけで、どの印も自動では消さない・直さない。
- **言葉でも 1 行で伝える**(UI の段で確定)。盤の下に高さの決まった 1 行(`role="status"`)を
  置き、いま破れている規則の種類を 1 つだけ言う。どれを言うかは固定の順:
  分岐(線が 3 本以上の点)→ 閉じたループの外の線 → 数字より多い線 → 行き止まり →
  数字に届かない(閉じたループが 1 本だけのときは「ループは閉じたが合わない数字がある」)
  (`ui/feedback.ts` の `conflictMessageKey`)。場所は盤の上の印が全部示し、この行は
  「何を探せばよいか」だけを言う。何も破れていなければ空。矛盾に音は付けない。
- **満たした数字は穏やかに示す**(`metClues`: 線がちょうど数字の本数のマス)。数字の色を
  控えめにし(`--ink-soft`)、字の太さも細くする(800 → 500。色に頼らない手がかり)程度で、
  動き・音は付けない。満たした数字が解と一致しているとは限らない
  (正しくないループの一部でも満たしうる)ので、「正解」の印には使わない。
- **「満たした」は「今、本数が合っている」の意味で、「そのマスは終わった」ではない(決定)。**
  したがって **0 は最初の画面から満たした表示**で、線が 1 本でも触れると満たした表示が消えて
  数字の矛盾(線が多すぎる)に変わる。0 だけを「4 辺すべて ×」で満たした扱いにする案は
  採らない: 数字ごとに意味が変わり、× を書かないと表示が変わらない(× はメモであって、
  書くことを求めない — §3)。`engine.test.ts` がこの決定を固定する。
- **色だけで状態を伝えない。**線は太い実線、× は小さな × 記号、未定は何も描かない
  (点の格子だけ)。矛盾は警告色に加えて形(数字の輪・点の輪・ループの破線の縁取り)を
  併用し、読み上げにも含める(§13)。

## 6. Undo と Hint

### Undo

- **無料・無制限。**1 手 = 1 タップ(または 1 回の `doSet`)。履歴は「変えた辺と、その前の
  印」の列でセッションに持つ。上限 `UNDO_HISTORY_LIMIT` = 5,000 手は無限に伸びないための
  蓋で、6×6 の 84 辺それぞれを 59 回ずつ叩いても届かない(超えた分は古い方から落ちる)。
- 履歴は**保存しない** — 再開時は空(§12)。Undo は Hint 回数を戻さない。
- タップ 2 回で同じ辺を元に戻せるが、それは Undo の代わりにならない(どの辺を何から
  変えたかをプレイヤーに覚えさせない)。

### Hint

無料・無制限・回数を数える(結果画面に出す)。**盤面には書き込まない**(示すだけ。
プレイヤーが自分でタップする)。

**Hint が読む盤**(`solver.ts` の `hintMarks`。2026-10-17 の最終段で決定): プレイヤーの印に、
**見えている事実からすでに決まっている ×** を足したもの。× はメモであって書くことを求めない
(§3)ので、Hint は × が書かれるのを待たない:

- 盤が「満たした」と示している数字(§5 — 0 は最初から、ほかの数字は線がそろった時点)の
  残りの辺。
- 線が 2 本集まった点のほかの辺(3 本目は分岐になる — §3)。
- **前の Hint が × と示した辺**(書かれていなくても。セッションの `hinted`)。

以前は印だけを読んでいたので、× を書かないプレイヤーには 0 の周りの同じ × が何度押しても
返り、線の Hint に進まなかった(レビューの再現: Medium で 22 回中 21 回が × の Hint、うち
19 回が同じ 0 の横の辺。Hint 回数もそのたびに増えた)。ここで足す × は、解と違う印が 1 つも
ないとき(下の手順 1 を通った後)にだけ読むので、どれも解の × である(満たした数字・2 本の
点の線は正しい線であり、前の Hint は証明済みか解そのもの)。`hinted` に解の × でない辺が
紛れても無視する。走査集合 1,330 盤面で、空の盤から Hint だけで解き切るまでの回数の平均は
Easy 37.6 → 21.4、Medium 56.9 → 35.4、Hard 79.0 → 52.7、デイリー 57.3 → 35.5 回、そのうちの
× の Hint は Hard で 47.1 → 20.8 回になった(開発機の計測。× を 1 つも書かずに線の Hint だけに
従っても回数は同じで、同じ × が 2 度示されることは 0 回)。

**数え方**(`session.ts` の `askHint`): 前の Hint のあと印が何も変わっていないときに押した
Hint は、同じ Hint をもう一度示すだけで**数えない**(線の Hint・誤りの Hint はプレイヤーの手を
待つ)。× の Hint のあとに押せば、その × を読んだうえでの次の Hint になり、新しい 1 回として
数える。`hinted` と「直前の Hint」は保存しない(§12)— 再開後の最初の 1 回は、前に示した
× をもう一度示しうる。

順に(`solver.ts` の `findHint`):

1. **解と違う印**があれば、それを示す(「この辺は違う」)。先に LINE(解では線でない辺の
   線)、無ければ × (解では線の辺の ×)。一意解の出題なので誤りは定義できる。
2. なければ、技法ソルバー(§7)が**Hint が読む盤(上)から証明できる次の 1 辺**を示す:
   その辺と、線か × か、根拠の場所(数字のマス・点・閉じかけの鎖・仮定)。T1 → T2 → T3 の
   順に探し、同じ段の中では線を × より先に示す(線はループを進め、× はメモである)。
   **どの段の Hint も、Hint が読む盤 — 画面に見えている印と、そこから見て決まっている × と、
   前の Hint が示した × — だけを根拠にする**(エンジンが自分で書いた印に寄りかかった結論は
   出さない):
   以下の「見えている印」は、この Hint が読む盤のことである。
   - **T1** は、見えている印から 1 つの規則で 1 か所で読める辺に限る(`singleSteps`)。
   - **T2** は**印を 1 つも書かずに回す**(`findStep` の dry run): 見えている印から角の事実
     (§7)を覚え、その事実が決める辺をすべて記録し、盤には書かない。その中から線を先に
     選ぶ。根拠の場所は結論を出した数字のマスか点で、角の事実が隣のマスや点から伝わって
     くることはある(それも見えている印から読める)。T2 を不動点まで書きながら回して後から
     出た結論は、エンジンが自分で書いた × に寄りかかることが多く、画面からは根拠を追えない
     (書きながら回していた版では、Hint の歩みで T2 の Hint の約 3 分の 1 がそう
     だった — 2026-10-17 のレビューと `test-helpers.ts` の物差しによる再計測)ので出さない。
     記録が空なら、見えている印はすでに T1 + T2 の不動点である(書きながら回したとき最初に
     決まる辺は、必ずこの記録に入る)。`solver.test.ts` が、ソルバーとは別に書いた「印を書か
     ない T2」(`test-helpers.ts` の `cornerConclusions`)の結論にすべての T2 の Hint が
     含まれることを、同梱盤面と生成盤面の Hint の歩みで確かめる。
   - **T3** は、見えている印(と、そこから T2 が覚えた角の事実)の上で 1 辺を仮定し、矛盾
     から決める。
     技法名は UI に出さない。
3. 技法が何も言えないときだけ、**検証済みの解の 1 辺**(まだ未定の辺のうち、線を先に)を
   示す。出荷した盤面では起きない — 技法は単調で(知っている印が増えても決まる辺は減ら
   ない)、空の盤から全辺を決められる盤なら、解と矛盾しない印からも必ず次の 1 辺を証明
   できる。テストで確かめたのは、空の盤から Hint に従う歩み(同梱 12 面、走査集合の 133 面、
   T2 の物差しの 24 面、× を書かない歩みの 24 面)と、同梱 12 面 + 生成 12 面の上で解の印から
   無作為に選んだ部分集合(各 20 通り、どれも矛盾表示なし)であって、解と矛盾しない印の
   すべてではない(§16)。

**画面での示し方**(UI の段で確定): Hint の辺は**破線の枠**と淡い地で囲み(形で示す。
キーボードのフォーカスの実線の輪とは形が違う — §13)、根拠の数字は破線の輪、根拠の点は
破線の輪で示す。何を示したかは盤の下の 1 行(§5 と同じ場所)が文で言う
— 「印の線はループに含まれません」「丸で囲んだ数字から、印の辺は線になります」「印の辺に
線を引くと、矛盾が起きます」「印の辺はループの一部です」など、種類(誤り / 技法の根拠の場所 /
仮定 / 解の 1 辺)と、その辺が線か × かが分かる文(`ui/feedback.ts` の `hintMessageKey`)。
読み上げでは、その文のあとに Hint の辺の名前(「Horizontal edge, row 1, column 3, empty」
など、辺のボタンと同じ全文)が続き(画面には出さない)、盤の 1 つのタブ位置が Hint の辺へ
移る(§13)。
技法名(T1 / T2 / T3)は言わない。Hint の印と文は**次の 1 手(タップ・Undo・新しい盤面)まで**
残り、時間では消えない(読むのに急かされない)。文は盤の上に重ねない — 盤の下端の辺を
示したとき、文がその辺を隠さないように。Hint の間は矛盾の文を出さない(盤の上の矛盾の印は
残る)。何も言えないとき(勝った盤など)は「今は出せるヒントがありません」。

Hint の解は生成時に計数探索が「ちょうど 1 つ」と証明したもの(§8)で、再開時も再証明して
から使う(§12)。当てずっぽうの答えを Hint として出すことはない。仕事量の上限(§8)に
達したら、その段は「見つからなかった」として次の段へ進む。

## 7. 技法とティア

技法はすべて**健全**(正しい盤面から、どの解とも矛盾しない結論しか出さない)で、1 つの
伝播エンジン(`solver.ts`)に実装する。

- **T1 — 数える。**
  - 数字のマスで、線が数字と同じ本数 → 残りの辺は ×。線 + 未定 = 数字 → 未定はすべて線。
  - 点で、線 2 本 → 残りは ×。線 1 本・未定 1 本 → その辺は線。線 0 本・未定 1 本 → ×。
    線 3 本以上・行き止まり → 矛盾。
  - **ループの規則**: 1 本の鎖の両端を結ぶ未定の辺は、閉じると鎖がループになる。盤に
    その鎖以外の線があるなら ×。鎖がすべての線で、閉じてもどれかの数字を満たさないなら ×。
  - 閉じたループがすべての線を含むなら、残りの未定はすべて ×。
- **T2 — 角。**各マスの各角(同じ点で出会う 2 辺)について「少なくとも 1 本は線」
  「多くとも 1 本が線」の 2 つの事実を覚え、3 つの読み方で使う:
  - マス: 4 辺は対角の 2 つの角に分かれ、その本数の和が数字になる(例: 3 なら各角に
    少なくとも 1 本、1 なら各角に多くとも 1 本)。
  - 点: 点の次数は 0 か 2 なので、角の本数と、その点の残りの辺の本数の和は 0 か 2。
    残りの辺は、内側の点では対角のマスの角、外周では 1 辺、盤の角では無い。
  - 角の本数の幅が 1 つに決まれば、未定の辺を決める。
    「盤の角の 3」「盤の角の 1」「3 に入ってくる線」などの定番の型がこの族に入る。
- **T3 — 仮定(深さ 1)。**未定の辺を 1 本ずつ線と仮定し(次に × と仮定し)、T1 + T2 を
  不動点まで回す。矛盾したら、その辺は反対の印に決まる。仮定は入れ子にしない。
  T3 が決めた辺の数を `trials` と呼び、Hard の推論の深さの目安にする。

**技法だけで全辺が決まった盤は、解が 1 つしかない**(健全な推論が全辺を決めたので)。
技法の実装は 1 つだけで、生成時の等級判定(§8)、Hint(§6)、テスト(§16)が共有する。

### ティア(必要な技法 + 手がかりの密度)

## 8. 生成と Seed

すべての盤面は seed から決定的に作る(`generator.ts` の `generatePuzzle(seed, difficulty)`)。
問題データのダウンロードはしない。同梱するのは、この生成器が作った検証済みの予備盤面だけ
(手順 6)。

1. **領域を育てる。**seed で選んだ 1 マスから始め、領域に隣接するマスを 1 つずつ足す。
   足すマスは、領域に接する辺の数で重み付けして選ぶ(1 辺: 6、2 辺: 2、3 辺: 1 —
   `GROWTH_WEIGHTS`。ループが塊にならず曲がりくねるように)。**穴ができるマスは足さない**
   (領域の外側が盤の外とつながったままか毎回確かめる)。目標の大きさは盤のマス数の
   40〜60%(seed で決める)。領域はつながっていて穴がないので、**その境界は必ず 1 本の
   単純閉路**になる(探索せずにループが手に入る)。
2. **数字を数える。**全マスに、境界(ループ)の辺の本数を書く。領域は 2 マス以上で穴が
   ないので、どのマスも 3 以下。全数字の盤がティアの技法で解けなければ、この候補は捨てる。
3. **削る。**マスを seed 順に並べ、数字を 1 つずつ空白にして、**ティアの技法でまだ解ける
   ときだけ**空白のままにする。Easy / Medium は目標の数(9 / 12)に達したら止める。
   Hard はまず T1 + T2 で解ける限り削り、続けて T3 で解ける限り削る(T3 の判定の前に
   計数探索で一意性を見る。外した数字で解が 2 つになる場合が大半で、それは数十ノードで
   分かる。1 回の判定は `THINNING_NODE_LIMIT` = 400 ノードまで — 超えたら「一意と
   証明できない」として数字を残す)。上限は 1,500 から 400 に下げた(2026-10-17): 一意と
   証明できた判定が 400〜1,500 ノードを要することはほとんどなく(レビューの実測で 3,000 盤面
   中 約 6,500 回のうち 23 回)、上限まで回って数字を残す判定が Hard の最も重い盤面の仕事量の
   大半だった。同じ 20,000 seed で、1,500 → 400 は仕事量の最悪を 961,139 → 390,725、p99 を
   235,755 → 183,516 にし、手がかりの数の平均(13.20 → 13.21)と `trials` の中央値(4)は
   変えなかった。走査集合で変わった盤面は Hard の 3 面(g78・g95・g99)だけで、golden・
   同梱盤面・デイリー(Medium は上限を使わない)は変わらない。
   最初の数手はまとめて外して 1 回だけ判定する(6×6 なら 8 個ずつ。駄目ならその束から
   1 つずつ判定し直し、以後は 1 つずつ)。**判定が単調なら、結果は 1 つずつ試した場合と
   完全に同じ** — 数字が減って解きやすく・一意になることはないので、束ごと通るならその
   途中もすべて通る(`generator.test.ts` が単調な判定で任意の束の大きさの一致を確かめる)。
   T1 / T2 の判定は単調である。**T3 の判定は単調とは証明できない**: 結論は単調でも、計数
   探索のノード上限と仮定の仕事量上限のどちらかが、数字の多い盤で尽きて少ない盤で尽きない
   ことがありうる。そこで実際の判定で測る: 実 seed の候補で、既定の束と束 1(1 つずつ)の
   結果が一致する(`generator.test.ts` が各ティア 24 seed で固定。開発機の計測では Easy /
   Medium 各 1,000・Hard 2,000 の候補で全部一致)。一致は実測であって証明ではない。
4. **一意性を証明する。**計数探索(`countSolutions`: 各ノードで T1 + T2 を回し、未定の辺を
   線 / × に分岐。鎖の端があればそこ、なければ必要数の最も多い数字の辺)で解を 2 つまで
   数え、**ちょうど 1 つで、それが手順 1 のループである**ときだけ通す。上限は
   `COUNT_NODE_LIMIT` = 5,000 ノード。上限に達した探索は `complete: false` を返し、
   **一意とは扱わない**(候補を捨てる)。不完全な探索で一意解を宣言しない。
5. **等級を付ける。**T1、T1 + T2、T1 + T2 + T3 の順に解き、最初に解けた段が等級。
   ティアの条件(§7 の表: 解ける技法・必要とする技法・手がかりの上限)を満たせば出荷。
6. 満たさなければ **seed を派生させて作り直す**(`<seed>#2`, `#3`, …)。上限は 2 つで、
   先に尽きた方で止める: 派生 seed `ATTEMPT_LIMIT` = 24 回と、1 回の生成の仕事量
   `GENERATION_WORK_LIMIT` = 400,000。止まったら、**同梱の予備盤面**(`bundled.ts`、ティア
   ごとに 4 面。seed のハッシュで 1 つ選ぶ)を `fallback` 付きで出す。予備盤面はこの生成器が
   記載の seed から作ったもので、`bundled.test.ts` が毎回「その seed から同じ盤面ができる」
   「計数探索と独立オラクルの両方で解が 1 つ」「ティアの等級」を再証明する。仕事量の予算は
   生成の中のすべてのソルバー呼び出しに「残り」として渡す(各呼び出しは自分の上限と残りの
   小さい方で止まり、止まったら「解けない / 一意と証明できない」扱い)ので、**予算で途中まで
   しか調べなかった盤面は出荷されない**。
   予備盤面は出すときにも数字を読み直し、計数探索で解を導き直し、等級を付け直す(同梱する
   のは数字だけで、解は持たない。最大 3,448 仕事量)。この再証明が失敗したら
   (`bundledPuzzle`)**例外を投げる** — これは「見つからなかった」の正直な返答ではなく、
   `bundled.test.ts` が毎回の全面の再証明で起きないことを固定している前提の表明である。
   起きた場合、そのタップでは新しい盤面が始まらない(画面はそのまま)。

不変条件:

- 同じ seed なら、必ず同じ盤面になる(仕事量の値まで同じ。`compatibility.test.ts` の
  golden で固定する)。
- 出題は一意解を持ち、その解は生成に使ったループである(手順 4。ティアの技法が全辺を
  決めることでも二重に保証される)。
- 出題はそのティアの技法で解け、Medium / Hard は下の段の技法では解けない(手順 5)。
- 手順 6 の予備盤面の発生は監視値で、全走査で 0 件である。大きな標本(§7 の ②)では
  Easy / Medium / デイリーが 0 件、Hard は 35,000 seed 中 1 件(予算を超えた seed — 下の表)。
- 予算の内側で決まる盤面は、予算があってもなくても同じ(仕事量の値まで同じ。
  `generator.test.ts`、開発機の計測で Hard 20,000 seed の全部)。

### 仕事量と上限

仕事量 `solverWork` は「書いた印 + 調べた点・マス + 覚えた角の事実 + 探索ノード + 仮定 +
領域を育てる幅優先探索の訪問」の合計で、同じ seed ならどのマシンでも同じ数になる。
**門は壁時計ではなく仕事量**([SUDOKU_RULES.md](SUDOKU_RULES.md) §7 /
[BOX_REGIONS_RULES.md](BOX_REGIONS_RULES.md) §8 と同じ理由)。

| 上限                    | 値           | 対象                                                    | 上限に達したら                                 |
| ----------------------- | ------------ | ------------------------------------------------------- | ---------------------------------------------- |
| `GENERATION_WORK_LIMIT` | 400,000      | `generatePuzzle` 1 回の全体(派生 seed すべての合計)     | 同梱の予備盤面(`fallback`)                     |
| `ATTEMPT_LIMIT`         | 24 回        | 1 盤面の派生 seed                                       | 同梱の予備盤面(`fallback`)                     |
| `THINNING_NODE_LIMIT`   | 400 ノード   | Hard の削りの一意性判定 1 回                            | その数字を残す(一意と扱わない)                 |
| `COUNT_NODE_LIMIT`      | 5,000 ノード | 出荷前の一意性の証明、再開時の再証明(§12)               | 候補を捨てる / 保存を読み捨てる                |
| `TECHNIQUE_WORK_LIMIT`  | 100,000      | 技法ソルバー 1 回(Hint の T3 を含む)                    | `'limit'` = 解けなかった扱い / Hint は次の段へ |
| 領域を育てる            | 構成上有界   | 1 マス足すごとに最大マス数の候補 × BFS(6×6 で 36³ 以下) | —                                              |

**1 回の生成の仕事量の上限**は、`GENERATION_WORK_LIMIT` + 予算を確かめる粒度 1 つ分 +
予備盤面の確認である。予算は派生 seed ごと・削りの判定ごと・探索ノードごと・仮定ごとに
確かめるので、超過は最大でも「領域を 1 回育てる(構成上 36³ = 46,656 以下、実測は数百)+
伝播 1 回分(数千)」、予備盤面の確認は最大 3,448(`bundled.test.ts` が 4,000 未満に固定)。
実測の超過は合計で最大 4,500(不可能なティアで全部外させた Hard 200 seed:

## 9. モードとデイリー

- **Free Play(難易度モード)**: Easy / Medium / Hard を選んで遊ぶ。seed は
  `loop-puzzle-<difficulty>-<token>`(token = 時刻 + 乱数、`session.ts` の
  `newSeedToken(now, random)`。**時刻と乱数は状態の層が渡す**(`Date.now()` /
  `Math.random`)— `game/` の中では時計も乱数も読まない)。同じ seed なら同じ盤面になる。
  クリア画面の第一ボタンは同じ盤面での再挑戦、第二が「新しい盤面」。プレイ中のヘッダの ↻ も
  同じ 2 択(`RestartDialog`)。レベル 1〜100 は作らない。
- **「同じ盤面で再挑戦」は盤面を作り直さない**(`restartSession`): セッションが持っている
  数字と検証済みの解をそのまま使い、印・履歴・経過時間・Hint 回数を 0 に戻すだけ。探索は
  1 つも走らない(以前は seed から生成し直していて、Hard の重い seed では新しい盤面と同じ
  だけ掛かった)。中断から復帰した局でも、遊んでいた盤面そのものが戻る — 生成器が変わった後
  でも seed から作り直した別の盤面にはならない(§12)。デイリーも同じ。
- **デイリー**: 1 日 1 問。seed は `loop-puzzle-daily-<YYYY-MM-DD>`(**端末のローカル日付
  のみ**。サーバー時刻もネットワークも使わない)。**毎日 Medium 固定**(曜日で当たり外れを
  作らない)。デイリーの ↻ は再挑戦だけ。
- **デイリーは今日の 1 問だけ。**過去の日付には遡れず、一覧も入口も持たない。日付が過ぎた
  中断中のデイリーは次に読み込むとき(起動・ゲームを開く)にレコードごと捨て、ホームの
  デイリーはつねに今日の問題へ向く。遊んでいる最中の盤面は日付が変わっても取り上げない。
  達成した日の記録は残す([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md)「デイリーは今日の 1 問」)。
- **ストリークは数えない・表示しない。**
- 中断は Free Play 用・デイリー用の **2 スロットを独立して保持**する(§12)。
- 最後に選んだ難易度は `lp.prefs` に残る(初期値 Easy)。初回の Quick Rules の直後に始まる
  盤面もこの難易度。

## 10. 統計

- **プレイ中に時計を表示しない。**経過時間は内部で記録し、結果画面と統計でのみ見せる。
  時計で急かさない(既存のパズルと同じ扱い)。
- 難易度別に: プレイ回数 / クリア数 / 合計プレイ時間 / 最短時間。デイリーは Medium の
  集計に入り、さらに達成日ごとの最短時間(`dailyTimes`)を持つ(達成日数はその件数)。
  **累計プレイ時間**は 3 難易度の合計プレイ時間の和として表示する(別の値を保存しない)。
  Box Regions §10 と同形。Bridges はデイリーを別の枠に分けるので、3 本でそろえる規則は
  **製品オーナーの確認待ち**(計画 `plans/2026-10-17-unblock-snake-loop-bridges-peg.md`
  「オーナーの判断に残した点」)。
- **スコアは作らない。**結果カードは、自己ベストを更新したときは「Your fastest yet.」と
  前の記録との差(`BestDelta`)を、更新しなかったときは今の最短時間と、それとの差
  (`BestDelta`、+0:18 のように)を静かに示す(Box Regions のカードと同じ)。初めてのクリアは
  「Your fastest yet.」だけで、比べる記録が無いので差は出さない(同じ時間なら差も出さない)。
  比べる相手は自分の記録だけ。
- **途中で盤面を替えても、それまでの時間は数える。**プレイ中の ↻(同じ盤面で再挑戦 /
  新しい盤面)は、置き換わる盤面の未計上の秒を先に合計プレイ時間へ入れてから新しい盤面の
  時計を 0 から始める(`GameContext.tsx` の `bookReplacedBoard`)。以前はここで秒を落とし、
  30 秒遊んで ↻ → 5 秒で離れると合計は 5 秒だった(2026-10-17 のレビュー)。解いた盤面は
  解いた時点で計上済みなので、結果カードからの再挑戦では何も足さない。
- Hint の回数は結果カードに事実として出す(コストにしない)。

## 12. 中断と再開(保存)

保存キーは `storage/keys.ts`(import ゼロの葉)が宣言する **5 つ**で、他のキーには触れない。
キーの葉の並び(= `src/app/gameKeys.test.ts` の `RELEASED_KEYS` の並び)は
`game` → `dailyGame` → `stats` → `flags` → `prefs`:

| 葉          | キー           | 中身                                                    |
| ----------- | -------------- | ------------------------------------------------------- |
| `game`      | `lp.saveGame`  | Free Play の中断(1 局)                                  |
| `dailyGame` | `lp.saveDaily` | デイリーの中断(1 局)                                    |
| `stats`     | `lp.stats`     | 統計(§10)                                               |
| `flags`     | `lp.flags`     | `tutorialCompleted`(初回 Quick Rules を終えたか)        |
| `prefs`     | `lp.prefs`     | 最後に選んだ難易度だけ(遊び方を変える設定は 1 つもない) |

(`gameKeys.test.ts` の `loop-puzzle` の行は
`['lp.saveGame', 'lp.saveDaily', 'lp.stats', 'lp.flags', 'lp.prefs']`。`storage/prefs.test.ts` が
キーの葉の並びをこれに固定する。)

### 中断レコード(`lp.saveGame` / `lp.saveDaily`、v1)

**最小のレコード**: 盤面を決めるもの(数字とその digest)と、プレイヤーが書いたもの(印)だけを
持つ。**解は保存しない** — 読み込み時に計数探索で再導出し、その再導出が「規則どおり解が
ちょうど 1 つの盤面か」の検証を兼ねる(`game/serialize.ts` の `decodeBoard`)。**これは出自の
確認ではない**: 数字が seed の盤面と同じかどうかは見ない(見ないのは意図どおりで、数字を
レコードに持つのは生成器が変わっても中断中の局を失わないためである)。プリセットの大きさで
解がちょうど 1 つの数字列なら、seed と違う盤面(デイリーなら `dailySeed(date)` と違う盤面)も
受け入れる。数字列が壊れて**別の 1 解の盤面になった**場合を落とすのは digest である。

| フィールド       | 型・形                                                 | 検証(どれかに外れたら読み捨て)                                                                                                                   |
| ---------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `schemaVersion`  | `1`                                                    | 1 以外                                                                                                                                           |
| `mode`           | `'difficulty' \| 'daily'`                              | 未知の値。**キーが期待するモードと違う**(`gameSlotSchema(key, expectedMode)`)                                                                    |
| `seed`           | 文字列                                                 | 空・文字列でない・長すぎる                                                                                                                       |
| `difficulty`     | `'easy' \| 'medium' \| 'hard'`                         | 未知の値。`daily` なのに `medium` でない                                                                                                         |
| `dailyDate`      | `YYYY-MM-DD` または `null`                             | 形式違い・実在しない日(`daily.ts` の `isLocalDateString`)。`daily` で null、`difficulty` で値あり。**今日でないデイリー**(読み込みで捨てる — §9) |
| `width`/`height` | 整数                                                   | 難易度のプリセットと違う                                                                                                                         |
| `clues`          | 1 マス 1 文字(`0`〜`3`、空白は `.`)、行優先            | 長さ違い・未知の文字・`4`                                                                                                                        |
| `cluesDigest`    | `lp1:` + 8 桁の 16 進(`serialize.ts` の `cluesDigest`) | 形式違い。**`clues` から計算し直した値と違う**(スキーマ。`decodeBoard` ももう一度)                                                               |
| `marks`          | 1 辺 1 文字(`.` 未定、`L` 線、`X` ×)、§1 の番号順      | 長さ違い・未知の文字                                                                                                                             |
| `hintCount`      | 整数 0〜1e6                                            | 範囲外(`doHintUse` は `HINT_COUNT_MAX` = 1e6 で止まるので、遊んで範囲外にはならない)                                                             |
| `elapsedSeconds` | 整数 0〜1e9                                            | 範囲外(`withElapsedSeconds` は有限でない値を無視し、`ELAPSED_SECONDS_MAX` = 1e9 で止まる)                                                        |
| `savedAt`        | 整数(ms)                                               | 範囲外                                                                                                                                           |

さらに盤面として(探索でないものはスキーマと `decodeBoard` の両方、探索は `decodeBoard` だけ —
下の「検証の置き場所」):

- `cluesDigest` が `clues` の digest と違う → 読み捨て(探索の前に、ハッシュ 1 回で)。
  数字列の 1 文字が変わっても解が 1 つのままの盤面になることは珍しくなく(レビューの計測で
  Hard の保存 150 件の 1 文字の変化 21,600 通りのうち 4,522 通り = 21%)、探索だけでは別の
  盤面として読み込んでしまう。digest は破損の検出であって改ざん対策ではない(保存は
  プレイヤー自身のもの)。
- `clues` が**ちょうど 1 つのループ**を持つことを `COUNT_NODE_LIMIT` 以内の計数探索で証明
  できない(解なし・複数解・上限到達)→ 読み捨て。生成時に同じ関数・同じ上限で証明した
  盤面なので、本物の保存はここで落ちない(生成時の証明に仕事量の予算が付いても同じ:
  予算の内側で完了した探索は、予算なしでも同じ道を通って完了する)。**これだけが探索で、
  `decodeBoard` だけが行う。**
- `marks` がすでに勝っている(§3。`isSolved` は印と数字だけで決まり、解を要らない)→ 読み捨て
  (終局済みは履歴であり、再開しない)。
- `marks` はどの組み合わせもタップで作れるので、規則を破っている印(§5 の矛盾)は正当な
  途中経過として受け入れる。

**Undo 履歴とミス回数は持たない**(履歴は最大のデータで誰も困らない — §6。ミスという
概念がない — §3)。勝敗の状態も持たない(印から再判定する — `restoreSession`)。Hint が
示した × の記録(`hinted`)と直前の Hint(`lastHint`)も持たない(§6)。

- **fail-closed**: 読み捨てたら既定値に倒し、プレイヤーはゲームのホームに着く。**黙って
  新しい盤面を始めない。**破損した保存がほかのゲームやシェルを止めることはない。
  バリデータは例外を投げない。
- **どのスロットのレコードかを決めるのはキーである**(`src/test/savedGameSlots.test.ts` が
  `dailyGame` の葉・`expectedMode`・`parsed.mode === expectedMode`・`storage/slots.test.ts`
  の存在を強制する)。
- **スロットを置き換える前に確認する**(中断中と違う難易度を選んだとき)。
- 背景へ回るとき、盤面の保存と未計上秒の計上を**同じ同期処理で**行う。ブラウザの戻るや別のゲームへのショートカット(ゲームが聞かない扉)でゲームがアンマウントされるときも、プロバイダが同じ同期処理を走らせる(`useOnUnmount(syncActiveGame)`、[GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「アンマウントで計上する」、門は `src/test/unmountBookingWiring.test.ts`。main との合流で入れた — 2026-10-18)。
- **検証の層を分ける**: 上の表のフィールドの検証と、盤面の検証のうち探索でないもの(digest・
  印の文字・すでに勝っているか)は `SchemaDef`(`storage/schemas.ts`)が行い、探索はしない。
  計数探索(`decodeBoard` の 1 回。本物の Hard の保存で最悪 20,653 仕事量・数 ms。上限まで回る
  数字列は最悪約 26 万・開発機で 20〜50ms だが、digest まで合わせて作った数字列でなければ探索まで
  届かない — §16)は、ゲームがスロットを実際に読み込むとき(`storage/gamePersistence.ts`)に
  1 回だけ走る。プレイヤーがゲームを開く(コレクションのタイル・ショートカット・Web の URL)
  ときであり、バックアップの検証やシェルの起動では探索は走らない。
- **検証の置き場所**(Web 先行公開の 4 本 — Snake / Loop Puzzle / Bridges / Peg Solitaire — に
  共通の規則。各ルール文書の保存の節が同じことを書く):
  - **仕事量が盤の大きさで決まる検査は、盤面の検査も含めてすべてスキーマの `validate` に置く。**
    Snake の層ごとの歩みのように探索の形をしたものも、盤で仕事量が決まるならここに入る。
    バックアップの書き出しと復元は、レコードを持ち主の `validate` だけに通す
    ([architecture/backup.md](architecture/backup.md)「検証は各レコードの持ち主が行う」)ので、
    digest の合わない盤面や終局した盤面は書き出しに入らず、それを含むファイルの復元は
    「壊れている」(`backupFileDamaged`)として全体を拒否し、何も書かない。どれも盤の大きさで
    仕事量が決まり(ハッシュ 1 回と印の 1 走査)、`validate` 1 回(Hard)は開発機で中央値 0.02 ms・
    `--jitless` で 0.03 ms 程度(2026-10-17)。`validate` は例外を投げず、通らなければ null を返す
    (backup.md の契約)。
  - **スキーマの外に残すのは、仕事量を盤ではなくノード数の上限が抑えるソルバーの探索だけ**
    (この計数探索と、Bridges の一意性の再証明)。
  - **読み捨てた記録はストレージから消さない。** 既存の全ゲーム(共有の `loadRecord`、Box
    Regions / Crown Grid などの読み込み)と同じ扱いで、そのスロットに次に書くとき(対局の保存・
    完成で消す)に置き換わる。消さないのは、スキーマが読めない記録は新しい版が書いたものかも
    しれないから(backup.md は「新しすぎる」と「壊れている」を分ける)。プレイヤーはホームに
    着き、そのスロットで新しい盤面を始めれば置き換わるので行き止まりにはならない。読み込みで
    記録ごと消すのは、今日でないデイリーだけである(§9)。
  - **残る穴**: 探索だけが拒否する記録 — digest も印も通るのに、数字にループがちょうど 1 つと
    証明できないもの — は、消されないので、次のバックアップにも入り、復元も通り
    (「復元しました」)、開くとホームに着く。digest まで合わせて作った記録か、版をまたいで
    探索の上限やソルバーが変わった場合にしか生まれない(破損は digest が落とす)。消す・
    スキーマで探索する、のどちらも採らなかった(前者は既存の全ゲームの扱いと違う新しい
    振る舞いになり、後者は探索をバックアップの検証に持ち込む)。`storage/slots.test.ts` が、
    スキーマの拒否・書き出しから外れること・探索だけが拒否する記録が残って次の保存で
    置き換わることを確かめる。
- **これは [GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「CPU 探索」の文字どおりの規則(探索は
  明示的な操作 = 新しい盤面・Hint のタップのときだけ)からの例外である**と明記しておく。
  ゲームを開くタップの続きとして、スロットごとに 1 回、`COUNT_NODE_LIMIT` の上限の内側で
  走り、ポーリングも先読みもしない。解を保存して読み込み時に規則の確認(1 本のループで
  全数字を満たす)だけにする案(Box Regions の形)もあるが、その場合は「数字に解がちょうど
  1 つ」という検証が「保存された解が 1 つの解である」に弱まる(digest まで合わせて作った
  数字列なら複数解の盤面を受け入れ、Hint が別解の正しい線を誤りと言いうる)ので採らなかった。
  共有文書の側にこの例外を書くかどうかは文書の持ち主が決める(最終報告の
  sharedChangesNeeded)。

### `lp.stats`(v1)

`{ schemaVersion: 1, easy, medium, hard, dailyTimes }`。難易度ごとに
`{ played, solved, totalPlaySeconds, bestSeconds | null }`(整数、`bestSeconds` は null 可)。
`dailyTimes` は `YYYY-MM-DD → 秒` の疎な表で、**壊れた 1 件だけを落とし**、ほかの日の記録を
道連れにしない(最大 2,000 件)。難易度の 3 つのどれかが壊れていればレコードごと既定値。

### `lp.flags`(v1)・`lp.prefs`(v1)

`lp.flags` = `{ schemaVersion: 1, tutorialCompleted: boolean }`。
`lp.prefs` = `{ schemaVersion: 1, difficulty }`(初期値 `easy`。フィールドが無い古い形は
既定値として読む。未知の難易度は既定値)。

### ベータ中のスキーマ

先行公開中は、スキーマ変更で保存がリセットされることを許容する。黙って消さない — ホームの
`WebBetaNotice` が en / ja で先に告げる([WEB_VERSION.md](WEB_VERSION.md)「保存データ」)。
正式収録でスキーマを凍結し、以後は移行だけで変える(公開ビルドの payload で
`storage/releasedRecords.test.ts` を作る)。保存は盤面(数字)を自分で持つので、生成器が
変わっても中断中の局は失われない(デイリーの盤面は変わる — `compatibility.test.ts`)。

## 15. 意図的な差分

### 関連する既存ゲームとの違い

**Number Path**([NUMBER_PATH_RULES.md](NUMBER_PATH_RULES.md))も線を引く論理パズルだが、
線を引く場所も、線の形も、手がかりの意味も違う:

| 観点        | Number Path                                  | Loop Puzzle                                           |
| ----------- | -------------------------------------------- | ----------------------------------------------------- |
| 線が通る所  | **マスの中心**からマスへ(マスを訪れる)       | **点と点の間の辺**(マスの縁を通る)                    |
| 線の形      | 1 から K で終わる**開いた**道                | 始点も終点もない**閉じた**ループ                      |
| 覆う範囲    | **全マスをちょうど 1 回**通る                | 全部の点は通らない(使わない点は次数 0)                |
| 手がかり    | 数字は**通る順番**、太い辺は**壁**           | 数字は**そのマスの 4 辺のうちループの本数**、順番なし |
| 操作        | なぞる(ドラッグ)/ タップで伸ばす・切り詰める | 辺を 1 本ずつタップ(線 → × → 空)。ドラッグなし        |
| 違反の表示  | 入れないマスには入れないので違反がない       | 常時の矛盾表示(§5)                                    |
| × のメモ    | ない                                         | ある(勝利判定には使わない)                            |
| Hint の根拠 | 解の次の 1 マス                              | 誤った印 → 技法の次の 1 辺 → 解の 1 辺(§6)            |

**Dots and Boxes**([DOTS_AND_BOXES_RULES.md](DOTS_AND_BOXES_RULES.md))は同じ点の格子と
「辺をタップする」操作を使うが、別の遊びである:

| 観点         | Dots and Boxes                                                   | Loop Puzzle                                                          |
| ------------ | ---------------------------------------------------------------- | -------------------------------------------------------------------- |
| 遊びの形     | **CPU との対戦**(手番がある)                                     | **ひとりで解く**論理パズル(手番なし)                                 |
| 目的         | 4 辺目を引いて**箱を取り**、多く取った方が勝ち                   | 数字を満たす**1 本の閉じたループ**を作る                             |
| 辺の扱い     | 引いた辺は Undo 以外では消せない。最後には**全部の辺**が引かれる | 線 / × / 空を何度でも切り替える。使わない辺がある                    |
| 線の制約     | なし(分岐も複数の環もできる)                                     | 次数 0 か 2、1 本のループ(§3)                                        |
| 数字         | 箱の持ち主の印(数字はない)                                       | マスの数字 0〜3 が辺の本数を言う                                     |
| 解           | ない(局面の良し悪し)                                             | 一意解(§8)                                                           |
| 共有するもの | —                                                                | 当たり判定をトラックいっぱいに取る**考え方**のみ。コードは共有しない |

### ブランド原則により合わせないもの

- ミス回数制限・ライフ制・ゲームオーバー・時間制限(しない。§3)
- プレイ中のタイマー表示、ストリーク、オンラインランキング、スコア(しない。§10)
- Hint / Undo を広告視聴やコインの報酬にすること(しない。常に無料・無制限 — §6)
- 1 日 1 問だけの供給(しない。難易度を選べばいつでも新しい盤面 — §9)
- 過去のデイリーへの遡り(しない。§9)

### 設計判断として合わせないもの

- **他社の名称・問題・盤面画像・画面デザイン。**一般に Slitherlink と呼ばれる形式の規則
  (点の格子・0〜3 の数字・1 本のループ)だけを使い、名前はアプリ内でもストアでも製品名と
  して書かない。問題はすべてこのゲームの生成器が作る(§8)。
- **数字 4 と、7×7 以上の盤**(§1、§2)。
- **ドラッグで連続して引く操作・長押し・線 / × のモード切替**(§4)。タップの循環 1 つで全部の
  状態に届く。
- **自動の ×**(線 2 本の点の残りを自動で × にする等)。× はプレイヤーのメモであり、推論を
  肩代わりしない。Hint が示すのは 1 辺だけ(§6)。Hint はそうした辺を「決まっている」ものと
  して読む(× を書かないプレイヤーに × を求め続けないため — §6)が、盤には書かない。
- **推測が必要な盤面・複数解の盤面**(出さない。§7、§8)。
- **Reset / Clear ボタン**(作らない。「同じ盤面で再挑戦」が同じ結果を与える — §9)。
- **Club House への登録**(しない。結果の形がベータ中にまだ動きうる。registry に `challenge` を
  持たない)。
