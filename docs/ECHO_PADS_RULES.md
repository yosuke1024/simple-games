## 1. 規則

- パッドは **4 枚(2 × 2)か 6 枚(2 行 × 3 列)**。パッドは 1 枚ごとに別の**印(形)**と**位置**を持ち、
  色は補助にすぎない(§11)。
- run を始めると、seed(§3)から**目標長の長さの列を 1 本**作る。列の各項はパッドの番号(読み順で 0 から)。
  列は run の間変わらない。
- **ラウンド k では列の先頭 k 個**を使う。run はラウンド 3(長さ 3)から始まる。
  1. プレイヤーが ▶ を押すと、先頭 k 個が順に 1 枚ずつ光って鳴る(§4)。
  2. プレイヤーは同じ順番にパッドを k 回押す(§5)。
  3. k 個とも合えば、k が 1 増えて次のラウンドへ。**次のラウンドの再生は自動では始まらない**(▶ を待つ)。
  4. 目標長のラウンドを返し切れば**クリア**。
- **1 つでも違えば run はそこで終わる**(§5)。警告音・赤い明滅・振動は出さない。再挑戦は同じレベルの
  **新しい seed の列**(seed の attempt が進む — §3・§9)。新しい seed は新しい列の約束ではない: 規則を満たす
  列が少ない短いレベルでは、直前と同じ列がまた出ることがある(§9 に割合)。
- ラウンド k の列はラウンド k + 1 の列の先頭である(同じ 1 本の列の前のほう — `game/session.test.ts`)。
- **入力に制限時間は無い。**押す前に考える時間も、押す間隔も、端末は区切らない。
- 時間・得点・星は無い。結果は「どこまで返したか」と「聞き直した回数」と「聞いた Pace」の事実だけ(§9)。
- 状態は `game/session.ts` の `status` で表す: `idle`(ラウンドの最初の ▶ を待つ)→ `playing-back`(再生中)→
  `awaiting-input`(入力を待つ)→ `cleared` か `failed`。`failed` の後の聞き直しは `reviewing`(§6)。
  どの遷移も純関数で、許されない操作は `null` を返して何も変えない(§5・§6・§16)。

## 2. レベルの梯子

**4 パッド / 6 パッドの 2 段 × 目標長 4〜14 = 22 レベル**(計画の決定事項どおり)。

| レベル | パッド         | 目標長 | ラウンド数(長さ 3 から目標長まで) |
| ------ | -------------- | ------ | --------------------------------- |
| 1〜11  | 4(2 × 2)       | 4〜14  | 2〜12                             |
| 12〜22 | 6(2 行 × 3 列) | 4〜14  | 2〜12                             |

- 段の中ではレベル番号の順に目標長が 1 ずつ伸びる(レベル 1 = 4 パッド・目標長 4、レベル 11 = 4 パッド・
  目標長 14、レベル 12 = 6 パッド・目標長 4、レベル 22 = 6 パッド・目標長 14)。
- **2 段とも最初から開いている**(レベル 1 と 12)。段の中は順に解放する: レベル n をクリアすると、同じ段の
  n + 1 が開く。**解放済みのレベルはいつでも選び直せる**(列は挑戦ごとに変わる — §3)。
- 段を上がると「パッドの枚数」だけが変わり、目標長は 4 からやり直す(サイズと枚数を同時に上げない —
  Number Recall §7 と同じ考え方)。
- **9 パッドは作らない**(計画。Number Recall の 3 × 3 と同じ帯になる)。
- 記録はレベルごとの「クリアしたか」だけ(§9)。最短時間・聞き直しの最少は記録しない。

## 3. 列の生成

**seed**: レベルは `echo-level-<n>-r<attempt>`、デイリーは `echo-daily-<YYYY-MM-DD>-r<attempt>`
(attempt は 0 から。§9 の `ep.progress` が次の値を持つ)。乱数は `game/rng.ts` の `createRng`(xmur3 +
mulberry32 — 収録の各ゲームが自分の写しを持つ)。端末時刻から乱数を引かない。同じ seed は常に同じ列を返す
(`game/compatibility.test.ts` が固定する)。

計画は seed を `echo-<段>-<目標長>-r<attempt>` としていたが、**レベル番号 n だけで段と目標長が決まる**(§2)
ので、Number Recall の `recall-level-<n>-r<attempt>`(§7・§8)と同じ形にした(この段の指示どおり)。

**列の作り方**(`generateSequence(seed, padCount, length)`):

1. 候補を 1 本、先頭から 1 項ずつ引く。各項は、次の**局所の 2 規則**に触れるパッドを除いた中から一様に選ぶ
   (除かれるのは多くて 1 枚 — 下)。
   - **同じパッドの 3 連続を作らない。**直前の 2 項が同じパッドなら、そのパッドを除く。2 連続は許す
     (同じパッドが続けて 2 回光るのはこの形式の中身で、消灯 120ms 以上がそれを見分けさせる — §4)。
   - **輪のなぞりを 3 つ続けない。**パッドを外周の輪(下)に並べたとき、直前の 2 項が輪の隣どうしで一方向に
     進んでいるなら、同じ向きのその次のパッドを除く。2 × 2 と 2 行 × 3 列では**全部のパッドが外周にある**
     ので、輪をなぞる順送りは「覚える」ではなく「なぞる」で返せてしまう。
   - 2 規則の除く相手は同時に立たない(3 連続は直前 2 項が同じとき、なぞりは直前 2 項が隣どうし — つまり
     違うとき)ので、各項の候補は `padCount` か `padCount − 1` 枚で、**引き直しは起きない**。
2. 候補全体に**偏りの上限**をかける: どのパッドの出現回数も、公平な取り分(`length / padCount`)の
   **2 倍の切り上げ** `ceil(2 × length / padCount)` 以下(`biasCap`)。4 パッドは長さ 4 で 2・長さ 14 で 7、
   6 パッドは長さ 4 で 2・デイリーの長さ 10 で 4・長さ 14 で 5。
3. 上限を満たせば採る。満たさなければ次の候補を引く。**候補は最大 24 本(`GEN_DRAW_LIMIT`、初期値)**で、
   24 本目でも満たさなければ **24 本目を採る**(フォールバック。局所の 2 規則は満たしている)。仕事量は
   乱数の呼び出し 24 × 14 = 336 回で必ず止まる(算術)。

**外周の輪**(時計回り、パッドの番号は読み順):

| パッド | 読み順の配置      | 輪の順(時計回り)          |
| ------ | ----------------- | ------------------------- |
| 4      | `0 1` / `2 3`     | 0 → 1 → 3 → 2 → 0         |
| 6      | `0 1 2` / `3 4 5` | 0 → 1 → 2 → 5 → 4 → 3 → 0 |

**局所の 2 規則は不変条件、偏りの上限は通過率。**局所の 2 規則は作り方で必ず成り立つので、全レベル・全
デイリーの列で不変条件としてテストする。偏りの上限は通過率として測り、フォールバックの数を数える(§16・§17)。

**計画との差**: 計画は 3 つのフィルタ(3 連続・偏り・単調な並び)を候補全体にかけ、最大 24 回の再抽選で通す
形だった。局所の 2 規則まで候補全体の棄却にすると、算術では 4 パッド・長さ 14 で 1 本が通る確率は約 9%
(3 連続なし (15/16)¹² ≈ 0.46 × なぞりなし (7/8)¹² ≈ 0.20)で、24 本でもおよそ 1 割がフォールバックに
落ちる(0.91²⁴ ≈ 0.10)。局所の規則は 1 項ごとに除いて引けば棄却が要らないので、そうした。偏りは列全体の
性質なので、計画どおり棄却と通過率で扱う。

**Number Recall §6 / Schulte Table §6 と逆の結論である理由**: 両者は「配置に制約を課さない」(引き直しが配置を
偏らせる)。Echo Pads は列が**時間軸**に並ぶ。3 連続は「同じものを 3 回」と**数える**ことで、輪のなぞりは
指で**なぞる**ことで、それぞれ記憶を使わずに返せる。空間に散らばった配置にはこの抜け道が無い。偏りの上限は
引き直しを伴うが、上限はゆるく(取り分の 2 倍を越える出現だけを拒む)、通過率は §17 に書く(Phase 2 のテストで
実測: 最初の候補で通る列が 4 パッド 95.47%、6 パッド 86.71%、デイリー 94.06%、フォールバック 0)。

**上限の形はコードの段で 1 度替えた**: 最初は「取り分の切り上げ + 1」(`ceil(length / padCount) + 1`)で
書いたが、同じ歩き(§17)で最初の候補が通る列が 4 パッド 72.49%・6 パッド 71.13%・デイリー 65.66% で、
最初の候補が拒まれる割合は 4 パッドの長さ 8(レベル 5)で 40.80%、6 パッドの長さ 12(レベル 20)で 64.80%
だった(取り分 2 の長さで、1 枚が 4 回出るだけで拒む)。これは「1 枚に寄った列」を避けるのではなく列を
均すことになるので、取り分の 2 倍に替えた。(Phase 2 のテストで実測: `game/quality.test.ts` が旧い上限を
`cap` に与えて同じ歩きをし、数を固定する。旧い上限は規則ではなく、この段落の数のためだけに歩く。コードの
段の報告で書いた「長さ 8 の 4 パッドで 3 割」はこの歩きで再現せず、40.80% が正しい。)

**短い先頭の偏り**: フィルタは列全体にかけるので、ラウンド 3〜5 の先頭(列の最初の 3〜5 項)は上限の
外にある。先頭が何種類のパッドを使っているかを別に測る(§17)。局所の 2 規則は先頭にも効く(先頭 3 項が
3 連続やなぞりになることは無い)。

探索は持たない。

## 4. 再生 — 端末が進める唯一の例外(判断 2)

### 例外とその条件

収録のほかのゲームは、**プレイヤーが操作していない間に盤面を動かさない**(覚える時間を端末が区切らない —
[MEMORY_MATCH_RULES.md](MEMORY_MATCH_RULES.md) §3「見るのをやめるのは常にプレイヤーの操作である」、
[NUMBER_RECALL_RULES.md](NUMBER_RECALL_RULES.md) §3「端末が記憶時間を区切ることはしない」)。Echo Pads の
提示は**時間軸の列**で、1 枚ずつ光って消えることがそのまま問いなので、端末が再生を進めることを避けられない。
製品オーナーは 2026-10-19 にこれを**例外として認めた**(判断 2)。条件は 4 つ:

1. **再生は ▶ のタップでだけ始まる。**ラウンドが進んでも、画面を開いても、復元しても、自動では始めない。
2. **再生中はいつでも Stop できる。**▶ と Stop は同じ位置の 1 つのボタン。再生中はパッドを押せない。
3. **聞き直しは無料・無制限。**許すのは「そのラウンドの最初のタップの前」と「失敗の後」だけ(§6)。
4. **Pace は Calm / Normal / Quick**(下の表)。**列が長くなっても速くしない。**

**理由**: 見終わってから返す記憶では、**見る回数をプレイヤーが決められる**。1 回の再生は端末が進めるが、
それが足りなければ、もう一度 ▶ を押せばよい — 押すまで端末は何もしない。Number Recall が「眺める時間」を
プレイヤーに渡すのと同じものを、時間軸の提示では「聞き直す回数」と「速さ(Pace)」で渡す。だから「急かさない」
([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md))は保たれる。

**「もう 1 回だけ見る」との違い**: Number Recall §10 は「もう 1 回だけ見る」を、後から売り物にできる形
(回数の上限が売る口になる)として退けている。Echo Pads の聞き直しは**回数の上限も、売る口も、減る残数も
無い**(無料・無制限・広告や課金に結び付けない — 計画「共通要件」)ので、その形にならない。聞き直しの回数は
記録にもしない(§9 — 少ない聞き直しを記録にすれば、無料の聞き直しを使わせない圧になる。Schulte §9 と同じ理由)。

**入力の途中で聞き直せない理由**: 入力を始めた後に聞き直せれば、1 つ押すたびに聞き直して答えを写せる。
それは記憶ではなく書き写しである。だから聞き直しは「最初のタップの前」までで、入力を始めたら失敗するか
返し切るまで ▶ は出ない。この条件は**離れて戻っても緩めない**(§8、判断 8)。

### Pace(`ep.prefs`。初期値)

| Pace       | 点灯 `litMs` | 消灯 `gapMs` | 周期 `periodMs` | 明滅の頻度(算術) |
| ---------- | ------------ | ------------ | --------------- | ---------------- |
| Calm       | 700          | 300          | 1000            | 毎秒 1.0 回      |
| **Normal** | 450          | 200          | 650             | 毎秒 約 1.54 回  |
| Quick      | 280          | 140          | 420             | 毎秒 約 2.38 回  |

- **既定は Normal。**
- **下限(定数。テストで全 Pace × 全長さについて固定する)**: 周期 400ms 以上(`MIN_PERIOD_MS`)、消灯 120ms
  以上(`MIN_GAP_MS`)、同時に光るのは 1 枚。周期 400ms は 1 秒に 2.5 回の明滅で、WCAG 2.3.1(1 秒に 3 回を
  越える閃光の禁止)の 3 回を下回る。消灯 120ms は、同じパッドが 2 回続けて光るとき(§3 で許す 2 連続)に
  「2 回」と見分けるための暗い間である(見分けられるかは**未検証(実機)**)。
- **最初の点灯の前に 600ms の間**(`LEAD_IN_MS`、初期値)を置く。▶ を押した指が離れ、目がパッドへ戻る間で、
  AudioContext の再開(§12)の待ちも兼ねる。iOS 実機での音の遅れは測っていない(**未検証(実機)**)。
- **列が長くなっても速くしない**: 周期は Pace だけで決まり、ラウンド・目標長・レベルで変わらない。
- **Pace を替えられるのは再生していない間だけ**(`playing-back` と `reviewing` の間は替えられない)。
  **Pace で記録を分けない**: 結果には、その run で聞いた Pace を事実として並べる(§9)。
- 3 段の値は初期値で、聞き分け・見分けは実機で確かめていない。

### 時刻表(`game/timetable.ts`)

再生は `game/` の純関数 `buildTimetable(pads, pace)` が作る**時刻表**をなぞるだけである。

- 項 i(0 から)の点灯は `LEAD_IN_MS + i × periodMs`、消灯はその `litMs` 後。
- 再生の長さは最後の消灯の時刻: `LEAD_IN_MS + (k − 1) × periodMs + litMs`(算術。Normal・k = 14 で 9,500ms)。
- `playbackEvents(timetable)` は「点灯・消灯・終わり」の出来事を時刻順に並べた列を返す。UI は
  **`setTimeout` 1 本の鎖**で次の出来事まで待つだけで、同時に 2 本のタイマーを持たない。各音は点灯の出来事の
  ときにタイマーから鳴らし、**音声の時計に先の音を積まない**(Stop・アンマウントの後に何も鳴らない — §12)。
- **再生は次で止まり、戻っても再開しない**: Stop、バックグラウンド(`visibilitychange` の hidden・native の
  pause)、`blur`(Snake §6 と同じ)、Back、ダイアログが開いたとき、アンマウント。止まると、
  ラウンドの再生なら `awaiting-input`、失敗後の聞き直しなら `failed` に戻る(`endPlayback`)。止まった再生も
  「聞いた 1 回」に数える(§6)。リスナーは effect の中で張り、module レベルに置かない(GAME_LIFECYCLE.md)。
- **実装(Phase 3)**: 鎖は `state/GameContext.tsx` の `runPlayback` で、タイマーは常に 1 本(`playbackTimerRef`)。
  各出来事の待ちは**▶ の時刻からの差**(`performance.now()`)で計り、前の出来事からの差を積まない(遅れた
  タイマーが後の点灯をすべて後ろへずらさないように)。止める道はすべて `haltPlayback` を通る(Stop・
  `visibilitychange` の hidden と native の pause — `syncActiveGame` 経由 —・`blur`・Back・新しい run・
  アンマウント)。止めると鎖の印(`playbackTokenRef`)を進めるので、すでに積まれたコールバックは何もしない。
  ゲーム画面にはダイアログが無い(ヘッダの ↻ を置かない — §11)ので、「ダイアログが開いたとき」は画面の
  上では起きない(置換の確認はホームとレベル一覧にあり、そこでは再生していない)。

## 5. 入力と失敗

- **パッドを押せるのは `awaiting-input` の間だけ**(`idle` — まだそのラウンドを一度も再生していない —
  と再生中と終局後は、押しても何も起こさない。失敗にもしない)。`idle` で押せないのは、まだ聞いていない
  ラウンドの答えを当てずっぽうで押す形を作らないため。
- 押したパッドは列の次の項と 1 つずつ比べる(`press`)。
  - 合えば入力が 1 つ進む。k 個そろえば、目標長なら `cleared`、そうでなければ k + 1 のラウンドの `idle`。
  - **違えば run はそこで終わる**(`failed`)。失敗の事実(ラウンド k・何番目の項か・押したパッド・押すべき
    だったパッド)を持つ。
- 失敗の後は、**押すべきだったパッドを印で示す**(Number Recall §4 の開示と同じ形)。**この開示に時間制限を
  置かない**。失敗したラウンドの列は何度でも聞き直せる(§6)。見終わったらプレイヤーが再挑戦か退出を選ぶ。
- **警告音・赤い明滅・振動を出さない。**`sounds.invalid()` / `sounds.gameOver()` も使わない。誤りは叱らない
  (Schulte §14-5)。
- 押した瞬間に光らせる(押したパッドの点灯は入力の確認であり、問いではない)。押したパッドの音も鳴らす
  (§12)。
- **間違いの回数は結果に出さない**: 判断 2 で run は最初の間違いで終わるので、1 回の run の間違いは常に 0 か
  1 で、`cleared` か `failed` と同じ情報になる(計画の未決事項の推奨)。統計は失敗した run の数を持つ(§9)。
- 計画の仕様にあった「入力を先頭に戻す」は判断 2 より前の案の名残なので作らない(推奨どおり判断 2 を正とする)。
- **Undo・次を光らせる Hint・ライフ・復活・コンティニューは作らない**(タップは記憶の主張そのもの、
  次の 1 枚は答えそのもの — Number Recall §10)。助けは聞き直し・Pace・即時の再挑戦で、すべて無料・無制限。

## 6. 聞き直し

- **▶ を押せるのは**: `idle`(そのラウンドの最初の再生)、`awaiting-input` で**そのラウンドの入力を始めて
  いない**とき(聞き直し)、`failed`(失敗したラウンドの聞き直し)。それ以外(再生中・入力を始めた後・
  `cleared`)では ▶ は無い(`play` は `null`)。
- 「入力を始めた」はラウンドの最初のタップで立ち、次のラウンドへ進むか run が終わるまで降りない
  (`inputStarted`)。入力の途中で離れて戻った run は、この印を立てたまま復元する(§8)。
- **聞き直しの回数の数え方**(結果の事実。記録にはしない):
  - 数えるのは、**ラウンドの入力を始める前の、そのラウンドで 2 回目以降の ▶**。各ラウンドの最初の ▶ は
    数えない(聞かなければ返せない)。
  - Stop やバックグラウンドで途中で止まった再生も「聞いた 1 回」で、その後の ▶ は数える(何回 ▶ を押したか
    という事実であって、聞き終えたかではない)。
  - **失敗の後の再生は数えない**(run はもう終わっていて、答え合わせである)。
  - 離れて戻った run は、そのラウンドで何回 ▶ を押したか(`roundPlays`)を保存から持ち越すので、戻ってからの
    ▶ は 2 回目以降として数える(§8)。

## 7. デイリー

- **6 パッド・目標長 10 の、今日の 1 問**(端末のローカル日付)。seed は `echo-daily-<YYYY-MM-DD>-r<attempt>`
  (Number Recall §9 と同じ形)。曜日で難易度を変えない。
- 失敗した後の再挑戦は、同じ日の**新しい seed の列**(attempt が進む。同じ列を避けはしない — §9)。計画の仕様は `echo-daily-<日付>` で
  attempt を持たなかったが、判断 2 は失敗後に新しい列を求めるので attempt を足した(推奨どおり)。
- **記録は最初の完了だけ**: その日の最初のクリアで、その日付を達成日として記録する。同じ日にもう一度遊んで
  クリアしても記録は変わらない。クリアした後も、その日のデイリーは新しい seed の列で遊べる(記録には触れない)。
- **過去の日付は遊べない**(一覧も入口も持たない — PRODUCT_PRINCIPLES.md「デイリーは今日の 1 問」)。日付が
  過ぎた中断中のデイリーは、次に読み込むときにレコードごと捨てる(§9)。遊んでいる最中の run は日付が
  変わっても取り上げない。
- **ストリークは数えない・表示しない。**

## 8. 中断と復元(判断 8 — (B))

Number Recall §12 は途中保存を持たない(短期記憶は戻らないので、再開しても「見たはずの配置を思い出せない
盤面」を配るだけ)。**Echo Pads はこの理由が成り立たないので保存する**: 列はいつでも ▶ でもう一度聞ける
(入力を始める前なら)ので、戻ったときに覚えていなくてよい。

- run は**ラウンドの境目**と「入力を始めたか」を保存し、**列は seed から作り直す**(列そのものは書かない)。
- **入力を始める前に離れた run**: 復元は「ラウンド k の最初のタップの前」に立ち、▶ で聞き直せる
  (そのラウンドで一度でも ▶ を押していれば `awaiting-input`、まだなら `idle`)。
- **入力の途中で離れた run**(判断 8 の (B)、2026-10-20): 中断レコードに「入力を始めた」を持ち、復元した
  ラウンドは **▶ を出さずに入力から — 先頭から押し直して — 続ける**。**押した位置は保存しない**(短期記憶を
  前提にしない — Number Recall §12)。判断 2 の条件(聞き直しは入力の前と失敗の後だけ)は、離れても緩めない。
  - 採らなかった案: (A) 戻れば聞き直せることを受け入れる(条件が緩み、離れて戻ることが聞き直しの抜け道に
    なる)。(C) 途中で離れたラウンドを失敗として扱う(離れただけで run が終わる)。
- 再生中に離れた run は、再生を止めた状態(`awaiting-input`、入力前)として扱う。復元した run の再生は
  始めない(▶ を待つ)。ショートカットで中断中の run を直接開いても再生は始めない(`shortcutResumeWiring`)。
- **失敗とクリアは、同じ操作の中で中断のスロットを消す**(再読み込みで失敗を取り消せない)。
- `game/` は復元を `restoreSession` で行い、規則から生まれえない組み合わせを `null` で拒む(§9 の
  fail-closed の `game/` の側)。

`ep.stats` / `ep.flags` / `ep.prefs` の 6 つ(推奨どおり)。中断は **2 スロット規則**(`dailyGame:
'ep.saveDaily'`、`gameSlotSchema(key, expectedMode)`、`storage/slots.test.ts` —
`src/test/savedGameSlots.test.ts`)。計画の仕様は `ep.saveGame` だけを挙げていたが、計画の共通要件と

**キーを増やす段**: 計画の決定事項は「ルール文書の保存の節と同じコミット」だが、キーはスキーマと同じ

`docs/architecture/storage-keys.md` の `ep.*` の行は Phase 4 の統合(2026-10-22)で 6 つのキーに合わせて

### 中断レコード(`ep.saveGame` / `ep.saveDaily`、schemaVersion 1)

| 項目             | 型                    | 意味                                                 |
| ---------------- | --------------------- | ---------------------------------------------------- |
| `schemaVersion`  | `1`                   |                                                      |
| `mode`           | `'level' \| 'daily'`  | スロットのモードと一致しなければ拒む(`expectedMode`) |
| `level`          | 1〜22 / `null`        | レベルの run の番号(デイリーは `null`)               |
| `dailyDate`      | `YYYY-MM-DD` / `null` | デイリーの日付(レベルは `null`)                      |
| `attempt`        | 0 以上の整数          | seed の attempt                                      |
| `round`          | 3〜目標長             | いまのラウンド k                                     |
| `inputStarted`   | 真偽                  | そのラウンドの入力を始めたか(§8 の (B))              |
| `roundPlays`     | 0 以上の整数          | そのラウンドで ▶ を押した回数(§6 の数え方)           |
| `replays`        | 0 以上の整数          | その run の聞き直しの回数(§6)                        |
| `pacesHeard`     | Pace の列(重複なし)   | その run で再生に使った Pace(結果の事実)             |
| `elapsedSeconds` | 0 以上の数            | その run のプレイ秒(統計の総プレイ秒へ)              |

- 書くのは、run を始めたとき・▶ を押したとき・再生が終わった / 止まったとき・ラウンドの最初のタップ・
  ラウンドが進んだとき・バックグラウンドと退出とアンマウントのとき(経過秒)。ラウンドの途中のタップでは
  書かない(押した位置を持たない)。クリアと失敗は、その操作の中でスロットを消す(`clearSavedGame`)。
- **検査の置き場所(Phase 3)**: 形と規則は `storage/schemas.ts` のスロットのスキーマ自身が
  `restoreSession` で見る(`gameSlotSchema(key, expectedMode)` — 2 スロット規則)。ほかのレコードが要る検査
  (未解放のレベル、`ep.progress` がまだ渡していない attempt、日付)は `storage/gamePersistence.ts` の
  `loadSavedGames` が見る。日付の過ぎたデイリーは形より先に日付を読み、レコードごと消す(Tangram §8 と同じ)。
  それ以外で読み捨てた記録はストレージから消さない(次にそのスロットで始めた run が上書きする)。
- **fail-closed**(読み捨てて、黙って別の run を始めない): 型の違い、`level` の範囲外、`mode` と `level` /
  `dailyDate` の組の不整合、`round` が 3〜目標長の外、`attempt` が整数でない・負、`inputStarted` なのに
  `roundPlays` が 0、`replays` が `roundPlays − 1` 未満、**ラウンド 3 で `replays` が
  `max(0, roundPlays − 1)` でない**(前のラウンドが無いので、聞き直しはそのラウンドの分だけ)、`pacesHeard`
  の重複・知らない Pace、ラウンド 3 を過ぎた・そのラウンドを再生した後の空の `pacesHeard`、**ラウンド 3 で
  `pacesHeard` が `roundPlays` より多い**(1 回の再生は 1 つの Pace)、`elapsedSeconds` が負・有限でない、
  未解放のレベル(`ep.progress` で開いていない)、スロットとモードの不一致、
  **日付の過ぎたデイリー**、`ep.progress` の次の attempt 以上の `attempt`(まだ始めていない列)。

### `ep.progress`(schemaVersion 1)

- `cleared`: レベルごとの「クリアしたか」(22 個)。**fail-closed**(Phase 3): 長さが 22 でない・型の違い・
  負の attempt・ありえない日付に加えて、**閉じたレベルのクリア**(段の前のレベルをクリアしていない)と
  **一度も始めていないレベルのクリア**(`nextAttempt` が 0)を拒み、既定値に戻す。
- `nextAttempt`: レベルごとの次の attempt(22 個、0 以上の整数)。
- `daily`: 今日のデイリーの `{ date, nextAttempt }`(日付が今日でなければ 0 から)。

**attempt を保存する — Number Recall §8 との差**: Number Recall §8 は attempt を保存せず、開き直すと r0 に
戻る。Echo Pads では**失敗したラウンドの列を何度でも聞ける**(§6)ので、開き直すたびに同じ r0 に戻れば、
固定の列を先頭から少しずつ覚えていけてしまう(Web なら再読み込み 1 回)。だから**次の attempt をレベルごとと
今日のデイリーの分だけ `ep.progress` に持つ**(推奨どおり)。

**attempt は run を始めたときに消費する**(`beginLevelRun` / `beginDailyRun` が今の値を返し、保存する値を
+1 する)。失敗の後の再挑戦は次の attempt になり(`game/progress.test.ts`)、クリアの後・中断中の run を
別の run で置き換えた後も、**同じ seed は二度と出ない**。

**同じ列は出うる — 約束するのは seed まで**: 列は seed から引くだけで、前の attempt の列を避けない。規則
(§3)を満たす列が少ない短いレベルでは、別の seed が同じ列を引く。Phase 2 のテストで実測(全レベル ×
attempt 0〜499、`game/quality.test.ts` が出力し固定する。§17 に表):

- 直前の attempt と**列全体が同じ**: 10,978 組のうち **5 組**(レベル 1 の r129 = r130・r255 = r256・
  r388 = r389・r449 = r450、レベル 2 の r256 = r257 — `game/sequence.test.ts` がこの 5 組だけであることを
  固定する)。デイリーは 365 日 × r0〜r2 の 730 組で 0。
- 直前の attempt と**ラウンド 3 の列(先頭 3 項)が同じ**: 4 パッド 5,489 組のうち 120 組(2.19%)、6 パッド
  5,489 組のうち 23 組(0.42%)、デイリー 730 組のうち 5 組(0.68%)。レベル別の最多はレベル 8 の 15 組
  (499 組のうち)。失敗の後はそのラウンドを何度でも聞ける(§6)ので、ラウンド 3 で失敗した直後の再挑戦が
  同じ先頭 3 項から始まることが、この割合で起きる。
- 500 本のうちそれより前の attempt のどれかと同じ列: レベル 1 で 358 本(異なる列は 142 本)、レベル 2 で
  166 本、レベル 12 で 113 本。目標長が長いほど減り、4 パッドの目標長 11 以上・6 パッドの目標長 8 以上では 0。

避ける形(前の attempt の列を引き直しで避ける)はこの段では採らない: 前の attempt の列が引き直しで決まるなら、
それはさらに前の attempt の列によって決まるので、1 本の列を作るのに attempt の数だけ遡ることになり、§3 の
仕事量の上限(24 本)が保てない。遡らずに避ける別の作り方(先頭 3 項を attempt から決めるなど)は列の固定
(`compatibility.test.ts`)を替えることになり、試していない。
**直前と同じ列を避けるか — オーナーの確認待ち**(§18)。

### `ep.stats`(schemaVersion 1)

- 行は **4 パッド / 6 パッド / デイリー** の 3 つ。各行に `played`(始めた run)/ `cleared` / `failed` /
  `seconds`(総プレイ秒)。デイリーを 6 パッドの行に混ぜず別の行にする(Tangram §7 と同じ形 — 暫定、
  オーナーの確認待ち)。
- `dailyDates`: デイリーを最初にクリアした日付の列(§7。ストリークは数えない)。読めない日付・重複は
  その項だけ捨てる(Tangram §8 と同じ — 1 日分の破損で全部の日を失わない)。行は `cleared + failed ≤ played`

## 12. 音(Phase 3)

- 音は `services/sound.ts` だけ。WebAudio の合成音で、**音声ファイルは足さない**。Phase 3 で `sound.ts` に
  **追加だけ**をした(既存の関数・音・`LADDER`・`IDLE_SUSPEND_MS` は変えていない。`sound.test.ts` は手を入れず
  そのまま通る): `padToneFrequency(pad)`・`padTone(pad, durationMs)`・`PAD_TONE_COUNT`(6)・`primeSound()`。
- 割り当て(初期値): パッド p は、基音 330Hz(`PAD_TONE_BASE`、初期値)から既存の五音階 `LADDER` の p 段目。
  4 パッドは 0〜3 段(0・2・4・7 半音)、6 パッドは 0〜5 段(0・2・4・7・9・12 半音 — 0 段と 5 段が同じ音名の
  オクターブ)。6 音とも違う高さで、上がっていくことは `ui/padSound.test.ts` が確かめる。聞き分けは
  **未検証(実機)**。音量は既存の音と同じ既定値(0.035)、包絡も同じ形。
- 再生の音は点灯の出来事のときにタイマーから鳴らし、長さは点灯の長さ(`litMs`)。押したパッドの音は
  220ms。**音声の時計に先の音を積まない**ので、Stop・バックグラウンド・アンマウントの後に**新しく始まる音は
  無い**(`EchoPadsRoot.leak.test.tsx` が偽の AudioContext で数える)。ただし止めた瞬間に鳴っている 1 音は、
  自分の包絡で減衰して消える(最長で Calm の 700ms)。**警告音は鳴らさない**(`invalid` / `gameOver` を
  使わない)。
- **音を消しても遊べる**(印と位置と点灯で足りる)。iOS の消音スイッチで WebAudio が鳴らない可能性は未確認。
- **AudioContext の解錠**: `primeSound()` は音を鳴らさずに context を作り / resume し、アイドルの suspend の
  タイマーを張り直す。設定で音が切られていれば何もしない(context も作らない — `padSound.test.ts`)。
  ゲームは **▶ のタップのハンドラの中で同期で毎回**呼ぶ(聞き直しも失敗後の再生も同じ道)。最初の点灯の
  前の 600ms(§4)がその待ちを兼ねる。iOS 実機での遅れは測っていない(**未検証(実機)**)。
- シェルはゲームを離れるたびに `releaseSound()` を呼ぶ(app/App.tsx)。ゲーム側は何も足していない。

3 本」(Schulte Table / Number Recall / Quick Math)と書いているが、この文書はその 1〜5 を自分にも適用すると

2. **効能を謳わない**: アプリ内・ストアの文言に記憶力・脳・認知機能の主張を書かない。
3. **スコアを発明しない**: 指標は到達した長さと聞き直しの回数(事実)だけ。
