# Kakuro — 正式ゲームルール

この文書は Simple Games 収録タイトル「Kakuro」の唯一のルールソースである。
実装(`apps/simple-games/src/games/kakuro/game/`)、Hint、テスト、Quick Rules は
すべてこの文書に従う。数値を変える場合はここを先に直す。

ブランド原則([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md))はこの文書より上位にある。
Hint / Undo は無制限・無料、広告視聴で解放しない、ストリークで急かさない、
プレイ中に時計を見せない。

ゲーム ID は `kakuro`、i18n キーの接頭辞は `kakuro`、保存キーの接頭辞は `kk.` である。
名称は国際的な一般名の「Kakuro」を使う(§14)。

**この文書の数字は、3 つの出どころのどれかである。毎回どれかを書く。**

- **構成で決まる数** — 盤面のサイズ、run の長さの上限、技法の本数。実装
  (`types.ts` / `solver.ts`)の定数がそのまま正本で、この文書とコードは同じ数を持つ。
- **計算で出る数** — §7 の分割表。1〜9 の組み合わせを数えただけのもので、実装を待つ
  性質のものではない。
- **実測でしか決まらない数** — 生成の仕事量、派生シードの回数、帯の密度、技法ごとの
  要求実績。まだ入っていない。表のマスには **未測定** と書いてある。

**測る前に数字を置かない。**「だいたいこのくらい」を先に書くと、実装がその数に合わせに
行くか、誰も直さないまま文書だけが嘘になる([FUTOSHIKI_RULES.md](FUTOSHIKI_RULES.md)
冒頭と同じ規律)。生成器とレベル帯はまだ書かれていないので、§8 と §9 の表は空である。
**空であることは、この文書の欠陥ではなく現在地である。**

## 1. 盤面

- W×H のマス。各マスは **白マス**(`1`〜`9` を 1 つ入れる)か **手がかりマス**の
  どちらかである。中間の状態はない。
- **手がかりマスは合計を 2 つまで持つ。**右向きの合計は**そのマスの右に続く白マスの
  並び**の合計、下向きの合計は**そのマスの下に続く白マスの並び**の合計である。両方
  持つマスは対角線で 2 つに割り、右上に右向き、左下に下向きを置く。片方だけのマスも、
  どちらも持たないマス(ただの塞ぎ)もある。
- この「白マスの並び」を **run** と呼ぶ。**run の長さは 2〜9 マス**
  (`MIN_RUN` / `MAX_RUN`)。
- **すべての白マスは、ちょうど 1 つの横 run と、ちょうど 1 つの縦 run に属する。**
- **白マス全体は連結している**(上下左右でつながる)。
- **上端の行と左端の列に白マスは置けない。**すべての run はその手前に合計を書く手がかり
  マスを要求するので、そこに始まる run は数字の置き場所がない。
- 各白マスはメモ(候補数字 1〜9 の任意の組)を持てる。
- 出題は常に一意解を持つ(§7)。

**初期数字は 1 つもない。**Sudoku・Futoshiki・Takuzu はどれも固定の数字を配って盤面を
始めるが、Kakuro が配るのは手がかりだけである。**手がかりが出題のすべてであり、白マスは
すべてプレイヤーのものである。**この不在は §11 で効く — 「手がかりマスに数字が入っている」
が破損の判定になり、それと紛れる 2 つ目の固定数字が存在しない。

**長さ 1 の run は作らない。**白マス 1 つだけの run は、手がかりの数字がそのまま答えに
なる。それは解くマスではなく、印字された数字である。**長さ 10 以上は作れない** — run 内
で数字は重複しないので(§3)、1〜9 を使い切ったところで並びは終わる。合法な埋め方が 1 つも
存在しないので、そういうレイアウトは盤面ですらない。

**白マスが島に分かれる盤面は作らない。**分断された島は、盤面の見た目を 1 つに保ったまま
**別のパズルを 2 つ**出すことになる。交差(§7 技法 2)は島をまたがないので、片方をどこまで
解いてももう片方には 1 つも伝わらない。しかも 4 マス程度の島はそれ自体でほぼ必ず多解になる。

サイズは 3 種類(**寸法は手がかりマスを含む全体**で、3 つとも正方である):

| サイズ | 寸法  | 白マスになりうる内側 | run の最大長 | 用途                            |
| ------ | ----- | -------------------- | ------------ | ------------------------------- |
| 小     | 6×6   | 5×5 = 25             | 5            | 導入帯(レベル 1〜20)            |
| 中     | 8×8   | 7×7 = 49             | 7            | 標準帯(レベル 21〜65・デイリー) |
| 大     | 10×10 | 9×9 = 81             | 9            | 上位帯(レベル 66〜100)          |

**上限が 10 なのは恣意ではない。**上端行と左端列が必ず手がかりマスなので、内側は
(n−1)×(n−1) であり、10 幅なら内側はちょうど 9 — `MAX_RUN` と一致する。**11 幅の盤面は、
合法に埋められない行を許してしまう。**

**下限が 6 なのは逆の理由である。**5×5 の内側は 4×4 で、すべての run が 2 マス以上という
制約の下では選べるレイアウトがほとんど残らない。盤面同士が重なり合い、レベルが別のパズル
であることをやめる。

**盤面に翻訳の要る文字は 1 つも載らない。**白マスの数字も手がかりの合計も ASCII の数字
だけで書き、記号は対角線 1 本だけである
([I18N_POLICY.md](I18N_POLICY.md)「盤面の数字は全言語で ASCII の 0-9 固定」)。言語を
変えても盤面表記は変わらない。

**盤面は RTL でも左右反転しない。**これは Futoshiki と同じく他のタイトルより強い要求で
ある — 反転すれば「右へ合計」の指す先が逆になり、盤面がそのまま嘘になる。ホームのタイルに
使うグリフ `∑`(U+2211)はクロームであって盤面の一部ではない。

## 2. 勝利

- **勝利**: すべての白マスが埋まり、すべての run が §3 の 2 規則を満たした時点 —
  run 内に同じ数字がなく、run の合計が手がかりと一致する。
- 敗北は存在しない。ミス回数の制限も、ライフも、ゲームオーバーもない(§14)。

判定は「埋まっている」かつ「§5 の違反が 1 つも出ていない」で行い、解と照合しない。
**表示と判定は同じ 1 つの読み(`findViolations`)から出る** — 判定を別に書けば、
「きれいに見えるのに完成しない盤面」がいつか作れてしまう。埋まった run について
「重複がない」かつ「合計が一致する」は §3 そのものなので、2 つの読みは必ず一致する。

出題は一意解を持つので(§7)、規則を満たす完成形はそもそも 1 つしかない — 解と照合しても
同じ結論になる。

## 3. ルール(2 つ)

**規則 1 — 1 つの run の中で、同じ数字は 2 度使えない。**

**規則 2 — 1 つの run の数字の合計が、その run の手がかりと一致する。**

この 2 つで全部である。行全体・列全体についての規則はなく、ボックスもない。

**「同じ行に同じ数字が 2 つ」は違反ではない。**手がかりマスで区切られた別々の run に
入っているなら合法である。この 1 点が Sudoku との最大の違いで、§4 でパッドの残数表示を
作らない理由でもある。

### 小さな例

この文書では右向きの合計を `→`、下向きの合計を `↓` と書く(盤面では対角分割で描く。
矢印は説明のための記法であって、画面には出ない)。

|     | ↓12 | ↓3  |
| --- | --- | --- |
| →11 | a   | b   |
| →4  | c   | d   |

- 横 run は `a b`(合計 11)と `c d`(合計 4)。縦 run は `a c`(合計 12)と
  `b d`(合計 3)。
- **2 マスで合計 4 は `{1,3}` しかない。2 マスで合計 3 は `{1,2}` しかない**
  (§7 技法 1)。
- `d` はその両方に属するので、候補は `{1,3} ∩ {1,2} = {1}` — **`d` は 1** に確定する
  (§7 技法 2)。
- 残りは順に落ちる: `c` = 3、`b` = 2、`a` = 9。`a + b` = 11 で横 run も合う。

**初期数字を 1 つも配らずに、4 マスすべてが推測なしで決まった。**これが §7 が全盤面に
ついて保証する解き方である。

## 4. 操作

1. 白マスを選ぶ
2. 数字パッドで 1〜9 を入れる / 消す
3. メモモードのとき、数字パッドはメモの追加・削除になる

**選ぶと、そのマスの属する横 run と縦 run が、両方の手がかりマスごと強調される。**
Kakuro の手がかりはマスの外にあり、しかも 2 方向から来る。「今どの 2 つの合計に効いて
いるか」を目で追わせるのは盤面の読み方であって、パズルの中身ではない。

規則:

- **手がかりマスは選べない。**数字を置く先ではないので、選択も押下の見た目も持たない
  (§13)。
- 数字を入れると、そのマスのメモは消える。
- 数字を入れると、**同じ横 run と同じ縦 run のメモから同じ数字を自動で消す**(手作業の
  消し込みを省く。ルールを変える支援ではない)。消す先は 2 本で、**行や列ではなく
  run である** — 手がかりマスの向こう側は別の run なので、消さない。
- **数字の入っているマスにはメモを置けない。**表示と食い違うメモを持たせない。
- 数字を消すと、そのマスは空に戻る(そのマスのメモも一緒に消える)。**自動で消えた
  同じ run のメモは復元しない** — 戻すのは Undo の仕事である(§5)。
- **間違った数字も置ける。**このレイヤーは手を止めない。誤答は数えるだけで、警告色に
  するかどうかは設定である(§5)。

### パッドに残数表示は作らない

パッドは 1〜9 の 9 キーだけを持ち、**キーに残り個数を出さない。無効化もしない。**

**Sudoku と Futoshiki が残数を出せるのは、そこに不変量があるからである。**Sudoku の解は
各数字をちょうど 9 回、Futoshiki の解は各数字をちょうど N 回含む(各行に 1 つずつ)。
だから「9 − 盤上の個数」「N − 盤上の個数」は盤面の見た目ではなく**解についての事実**で、
最初から最後まで意味が変わらない([FUTOSHIKI_RULES.md](FUTOSHIKI_RULES.md) §4)。

**Kakuro にこの不変量は存在しない。**ある数字が盤面に何回現れるかは、レイアウト(run の
並び)と解の中身で決まり、規則からは何も決まらない。同じ行に同じ数字が 2 つ並ぶことすら
合法である(§3)。引く先の定数がないので、数えても意味のある数にならない。数えられない
ものにカウンタを付ければ、プレイヤーはそれを不変量だと読む。**同じ部品を全タイトルに
並べることが原則ではない**([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md))。

**「選択中のマスに入れられない数字を灰色にする」も作らない。**それは §7 の技法 1・2 を
プレイヤーの代わりに実行することであり、このパズルの中身そのものである。中身を先に消す
支援は作らない(Futoshiki が不等号ごしのメモ自動消去を作らないのと同じ理由)。次の一手が
要るときは Hint がある(§6)。

## 5. ミスと支援

- **ミス上限はない。ゲームオーバーもない。**3 ミスで失格のような仕様は採らない。
- **違反表示は常時オン**で、**3 つの形だけ**を出す:
  - **run 内の重複** — 1 つの run に同じ数字が 2 個以上あるとき、その数字のマス(規則 1)。
    ほかに何が起きていようと、これは必ず誤りである。
  - **埋まりかけの run の合計超過** — まだ空マスが残っているのに、書かれた数字の合計が
    既に手がかりを超えているとき、その run(規則 2)。**埋まりきる前に出す** — 残りの
    どのマスも 1 以上を足すので、超えた時点でその run はもう完成できない。
  - **埋まった run の合計不一致** — すべて埋まったのに合計が手がかりと違うとき、その run。
- 違反したマスと**違反した run の両方**を返す。手がかりマス自身も一緒に色が変わる —
  破れているのは run であって、マスだけではない。
- **これはルール違反の指摘であって、答え合わせではない。**規則を破っていない数字は、
  それが解と違っていても違反表示には出ない。

**「もう手がかりに届かない」は表示しない。**合計超過の裏返し —「残りの空マスに何を入れても
手がかりに足りない」— は、確かに同じくらい死んでいる。§7 のソルバーは実際にその推論を使う。
それでも違反として出さないのは、**まだ何も間違って書いていないマスに警告色を付けることに
なる**からである。それは「ここでルールを破った」とは別の約束である。§5 は規則違反のところに
線を引き、**推論は Hint に置く**。この線がないと、違反表示は少しずつソルバーになる。

### ミスの即時表示

- **ミスの即時表示**(一意解と異なる数字を警告色にする)は設定トグル。**既定はオン。**
  オフのときも違反表示は出る。
- ミスの定義: 一意解の値と異なる数字を空マスに入れたとき、ミス 1 回。同じマスに続けて
  別の誤答を入れれば、その都度 1 回。
- ミス回数は保存レコードに持ち(§11)、クリア画面で見せる。プレイ中にカウンタを常時表示
  しない。統計には積まない(§10)。

このトグルは `kk.prefs.highlightMistakes` に入り、**ゲーム自身がシェルの設定画面へ
差し込む**(`app/registry.ts` の `loadSettingsSection`)。**Sudoku・Futoshiki に次いで
3 例目**である。ゲームの選択肢はゲームと一緒に置き、シェルは場所を貸すだけにする —
そうしないとシェルが全タイトルの設定を知ることになる。

設定画面はホームからのみ到達し、そのときどのゲームも mount されていない。だから
**マウント時に 1 回読むだけで足りる**(実行中の盤面と競合しえない)。

### Undo

- **無制限**(実装上の上限は Sudoku / Futoshiki / Number Match と同じ 2000 手)。
- 対象は「数字の配置」「数字の消去」「メモの変更」。
- **Undo はミス回数を戻さない**(誤答した事実は消えない)。Hint 使用回数も戻さない。
- **保存された中断ゲームに Undo 履歴は含めない**(§11。Sudoku / Futoshiki と同じ)。

**Undo を作るのは、この操作が非自明に不可逆だからである。**数字を 1 つ入れると、そのマス
のメモが消え、同じ横 run・縦 run のメモからも自動で消える(§4)。1 タップで消えた候補を
手で復元することはできない。Takuzu が Undo を作らないのは正反対の理由で、あちらはタップ
1 種類ですべての状態が一巡するのでもともと可逆である
([TAKUZU_RULES.md](TAKUZU_RULES.md) §8)。

## 6. Hint

**無制限・無料。**プレイヤーの盤面に §7 の技法を当て、**次の 1 手を示す。**

Hint が示すのは 2 つの形のどちらかである:

- **確定するマス** — 技法 3・4 が数字を決めたマスと、その根拠の run。
- **候補が減る一手** — 技法 1・2・5・6 が候補を落とした run と、落ちた数字。

**候補が減るだけの一手も Hint に出す。**「合計 16 の 2 マスなので、7 と 9 しか入らない」は
Kakuro という推論そのものであり、**確定したマスしか示さない Hint は、教える価値のある部分を
まるごと飛ばす**([SUDOKU_RULES.md](SUDOKU_RULES.md) §5 /
[FUTOSHIKI_RULES.md](FUTOSHIKI_RULES.md) §6 と同じ扱い)。

- **数字は入れない。**プレイヤーが自分で入れる。
- **根拠の run を一緒に示す。**1 本の run で決まったならその run と手がかりを、交差で決まった
  なら**両方の run と両方の手がかり**を強調する。「なぜそこが確定するのか」を示すのが
  Hint であって、答えを埋めるのは Hint ではない。
- 短い一文を添える。**技法名(固定分割、naked pair など)は UI に出さない。**平易な
  言い換えのみ(例:「合計 16 の 2 マスなので、7 と 9 しか入らない」「この並びに残った
  数字は 3 だけ」)。理由は文章量を最小化する UI 原則
  ([I18N_POLICY.md](I18N_POLICY.md))と、多言語での用語統一コストを避けるため。技法名は
  内部表現・テスト・Landing Page の解説にのみ使う。
- **盤面が既に規則を破っているときは、先にその違反を示す。**これは好みの問題ですらない —
  run が数字を重ねたり合計を超えたりした時点で、技法が出発点にする候補集合が矛盾しており、
  提示できる推論が 1 つも存在しない。違反こそが、そのとき言える唯一のことである
  (Nonogram §7 の矛盾優先と同じ形)。
- **解と直接照合して「ここが間違い」と教える形は Hint では採らない** — それは §7 の論理
  ではなく答え合わせだからである。その用途はミスの即時表示(§5)が別に担っており、そちらは
  設定で切れる。
- 出題は §8 の生成条件により必ず技法だけで解けるので、**手つかずの盤面で Hint が空を返す
  ことはない。**空になるのは、完成した盤面か、プレイヤーの「規則は破っていないが解とは違う」
  数字がどこかのマスの候補を消し尽くしたときである。そのときは「今わかる手が見つかりません」
  を表示し、盤面は変えない。
- 使用回数は記録し、クリア画面で見せる。

## 7. 「推測なし」の保証と技法

**これがこのタイトルの中心的な設計判断である。**

出題は必ず、**次の 6 つの技法だけで最後まで解ける**。各白マスは候補集合(9 ビットのマスク)
を持ち、削れなくなるまで以下を繰り返す(不動点反復)。**安い技法から順に読み、上の段が何も
言わなくなってから次の段に降りる** — 人が解く順序であり、仕事量が小さく収まる理由でもある。

### すべては 1 つの表の上に載っている

run は「1〜9 から重複なく k 個選んで合計 S」である。だから run の中身は必ず `{1..9}` の
部分集合で、**部分集合はゲーム全体で 512 個しかない。**盤面のサイズによらず — 数字はどの
サイズでも 1〜9 だからである(§3)。この 512 個を (長さ, 合計) で 1 度だけ仕分けると、
「合計 16 の 2 マスに何が入るか」が配列 1 回の読みになる。以下の技法はすべて、この表引きと
マスク演算の組み合わせである。**初期数字が 1 つもない盤面でも §8 の仕事量が払えるのは、
これが理由である。**

### 技法 1 — 固定分割(fixed-partition)

長さ L・合計 S の (長さ, 合計) の組が、**1 通りの数字集合しか許さない**とき、その run の
空マスはすべてその集合に限られる(既に書かれた数字を除く)。`16(2) = {7,9}`、
`6(3) = {1,2,3}`、`45(9) = {1..9}` がその形である。

**この「1 通りしかない」は数えられる。**長さ 2〜9 で成立する (長さ, 合計) の組は全部で
**120 通り**あり、そのうち**組が 1 つに決まるのは 34 通り**である(1〜9 の組み合わせを
数えた結果であって、実測ではない):

| run の長さ | 成立する合計 | うち一意 | 一意な合計     |
| ---------- | ------------ | -------- | -------------- |
| 2          | 15           | 4        | 3・4・16・17   |
| 3          | 19           | 4        | 6・7・23・24   |
| 4          | 21           | 4        | 10・11・29・30 |
| 5          | 21           | 4        | 15・16・34・35 |
| 6          | 19           | 4        | 21・22・38・39 |
| 7          | 15           | 4        | 28・29・41・42 |
| 8          | 9            | 9        | 36〜44(すべて) |
| 9          | 1            | 1        | 45(1〜9 全部)  |
| **合計**   | **120**      | **34**   |                |

**長さ 8 と 9 を除けば、一意な分割はいつも「その長さで作れる最小の 2 つの合計と、最大の
2 つの合計」である。**それ以外の合計は必ず 2 通り以上ある。だから固定分割が一撃で効くのは
**両端の run** であり、真ん中の合計に対しては何も言わない。

盤面のサイズは、この表のどこまでを使えるかを決める(§1 の run 最大長より):

| サイズ | 使える (長さ, 合計) | うち一意 |
| ------ | ------------------- | -------- |
| 小     | 76                  | 16       |
| 中     | 110                 | 24       |
| 大     | 120                 | 34       |

**大サイズだけが長さ 8・9 の 10 通りを持つ。**ただし長さ 9 の run は 10 幅の盤面で 1 行を
丸ごと使うので、実際にレイアウトへ現れる頻度は生成が決める(**未測定**)。表にある一意な
分割の数は、盤面に出る回数ではない。

**技法 2 はこの技法を含んでいる**(分割が 1 通りなら和集合も 1 通りである)。それでも
別の段として先に置くのは、①候補集合を 1 度も走査せず表引き 1 回で済む最も安い段であり、
②**Hint が最も言いたい文がこれ**だからである。「この 2 マスは合計 16 だから 7 と 9」は、
交差の結果生き残った数字を並べるより、はるかによく教える。

### 技法 2 — 交差(intersection)

**すべての白マスは 1 つの横 run と 1 つの縦 run に属する**(§1)。だからそのマスの候補は、
横 run が許す数字と縦 run が許す数字の**共通部分**である。両側の「許す数字」は分割表から
直接読む。§3 の例で `d` が 1 に決まったのがこれである。

**最も多く働くのはこの技法であり、初期数字ゼロで Kakuro が成立するのもこれによる。**
片方の手がかりだけでは大して絞れないが、2 つ重ねると 1 つに落ちることが多い。

**この技法があるから、Kakuro は行や列ではなく run で読む。**手がかりマスの向こう側は
別の run であり、候補の伝播はそこで止まる。

### 技法 3 — naked single / 技法 4 — hidden single

- **naked single** — あるマスの候補が 1 つだけになったら、それを書く。
- **hidden single** — ある run で、ある数字が入れる空マスが 1 つだけなら、そこに書く。

**hidden single は Sudoku からそのまま写せない。**Sudoku のユニットは 1〜9 を必ず 1 つずつ
含むので、「その数字が入れるマスが 1 つ」だけで確定する。Kakuro の run が含むのは 1〜9 の
うち長さぶんだけで、**どの数字が現れるかは手がかりが決める**。だから hidden single は
2 段になる:

1. 「この run に**必ず**現れる数字」を出す — 生き残った分割すべての**共通部分**である。
2. その数字が入れる空マスが run 内に 1 つなら、そこに書く。

1 を飛ばして「入れるマスが 1 つだから確定」とすると、**その run に現れない数字を置く。**
これは健全性が破れる形の間違いであり、破れれば §7 の保証ごと崩れる。実装とテストは
この 2 段を明示的に分けて持つ。

### 技法 5 — naked pair / 技法 6 — 残り和(sum-tightening)

- **naked pair** — 同じ run の 2 マスが同じ 2 候補しか持たないなら、その 2 数はその 2 マスの
  ものなので、同じ run の他のマスの候補から外せる。規則 1 だけで言えることで、合計は使わない。
- **残り和** — 技法 2 と同じ分割の読みを、**マスが受け付けない分割を先に捨ててから**行う。
  「この run はあと 2 マスで 11 — 2+9 / 3+8 / 4+7 / 5+6 のどれか。でも左のマスは 2 か 3 しか
  取れないので 4+7 と 5+6 は消え、右のマスは 8 か 9」。この後半が技法 2 との差であり、
  分割ごとに run の候補を走査するぶん高いので、梯子の一番下に置く。

**分割を捨てる条件は「必要条件」だけで判定する** — その分割のどれかの数字に行き場がない、
またはどれかの空マスがその分割から何も取れない。十分条件(完全マッチング)は求めない。
だからこの段は**消し足りない**ことはあっても**消しすぎない**。ソルバーが誤ってよい向きは
こちらしかない。

### 候補の初期値は規則 1 だけで作る

候補集合を作る段では、**同じ run に同じ数字を置かないという規則 1 しか適用しない。**
手がかりが言うことはすべて上の 6 技法に任せる。**合計の推論を黙って候補に畳み込むと、
Kakuro の推論のほぼ全部が「プレイヤーには一度も説明されない部分」になる。**Hint が示せる
一手として残すために、安い推論をわざと後段に置いてある。

不動点反復には安全弁として 2000 ラウンドの上限があるが、81 マスの盤面はこれよりはるかに
少ない回数で止まる。

### ティアは作らない

**全レベルがこの 6 技法すべてを許容し、難易度はサイズとレイアウトの密度が担う**(§9)。
実装にも難易度の型は存在しない。

[FUTOSHIKI_RULES.md](FUTOSHIKI_RULES.md) §7 と同じ判断である。あちらは当初 3 ティアを
計画し、**出荷する 160 面が実際にどの技法を要求するかを数えて棄却した** — pair 系を必要と
したのは 160 面中 1 面で、「中身のない名前を 3 つ並べれば、プレイヤーにとっては嘘と区別が
つかない」ためである。同じ棄却が Sudoku §6 でも起きている(subset 系が必要になるのが約
20 面に 1 面)。

**この計画の当初案は技法 5・6 を「上位帯」に置いていた。採らない。**ティアが誠実に名乗れる
のは「許容する技法の集合」であって(Sudoku §6)、Kakuro が出荷するどの盤面もこの 6 つを
すべて許容する。どのレベルでも同じ集合を指す名前は、後ろに何もない札である。ティアを足す
条件は**実測が要求したとき** — ある技法の要求実績にはっきりした分かれ目があり、それが
プレイヤーの体験と対応しているときだけである。そのとき帯の端点を全部測り直し、golden を
全部取り直す。

`guarantee.test.ts` は出荷する全盤面について、技法ごとの要求実績を数えて出す:

| 技法            | 要求した盤面(全 100 レベル + デイリー帯) |
| --------------- | ---------------------------------------- |
| 1 固定分割      | 未測定                                   |
| 2 交差          | 未測定                                   |
| 3 naked single  | 未測定                                   |
| 4 hidden single | 未測定                                   |
| 5 naked pair    | 未測定                                   |
| 6 残り和        | 未測定                                   |

**この表が埋まっても、既定はティアを作らないままである。**

### 健全性から一意性が出る

**6 技法とも健全である。**どれも「合法な完成形すべてが一致する値」しか書かず、どの候補も
「どの完成形も使わない数字」しか落とさない。したがってこの技法だけで埋め切れる盤面は
**解が 1 つだけ**であり、推測なしで必ず完成できる。**一意性は健全性から出るので、解の個数を
別に数える必要はない**([TAKUZU_RULES.md](TAKUZU_RULES.md) §5 /
[FUTOSHIKI_RULES.md](FUTOSHIKI_RULES.md) §7 と同じ構造)。Sudoku が一意解を別途検査するのは、
あちらの掘削が技法での可解性と一意性を別の門として持っているからである。

理由: 推測で数字を置かされるパズルは、プレイヤーの論理を裏切る。Sudoku・Minesweeper・
Nonogram・Takuzu・Futoshiki で推測を排したのと同じ理由で、ここでも排する。

**技法の実装は 1 つだけ持ち、3 人の利用者が共有する** — 生成時の検査(§8)、Hint(§6)、
`guarantee.test.ts`。約束と検査と助けを別々に実装すると、静かに食い違う
(Sudoku §8 のグレーダーと同じ理由)。

## 8. 盤面生成と Seed

すべての盤面は seed から決定的に作る。問題データの同梱もダウンロードもしない。

1. **レイアウトを作る。**上端の行と左端の列は手がかりマスにする(§1)。残りのマスを seed
   由来のシャッフル順に手がかりマスへ変え、§1 の制約 — run の長さが 2〜9・長さ 1 の run を
   作らない・白マスが連結 — を破る変更は巻き戻す。帯の目標密度(§9)に達したら止める。
2. **充填する。**白マスをランダム化バックトラッキング(候補順を seed でシャッフル)で
   埋める。枝刈りは規則 1(同じ run に同じ数字を置かない)と、run が埋まりきったときの
   規則 2 で行う。
3. **手がかりを算出する。**各 run の合計を解から読む。**手がかりは選択肢ではない** —
   解が決めるので、生成の時点で手がかりと解が矛盾することはありえない。実装でも、手がかりを
   作る場所は `buildRuns` の 1 か所だけである。§11 が「手がかりが解と合わない」を破棄の理由に
   挙げていないのは、**その状態を表現できるデータをどこにも持っていない**からである。
4. **§7 のソルバーで検査する。**空の盤面から始めて技法だけで全白マスが確定すれば、その盤面は
   推測不要かつ一意解である(§7 末尾)。確定しきらなければこの候補は捨てる。
5. 通らなければ **seed を派生させて作り直す**(`<seed>#2`, `#3`, …)。上限つき。
   **派生では手順 1 からやり直す** — レイアウトを固定して充填だけ振り直すと、同じレイアウト
   に対する試行が偏り、失敗が相関する(Futoshiki §8 手順 4 と同じ論法)。
6. 上限に達したら、**その時点までに手順 4 を通った候補のうち、最も帯の目標に近いもの**を
   出題する。1 つも通っていなければ、**推測の要る盤面を黙って返さず、生成は失敗として
   投げる。**Takuzu の生成器が「何も返さない」より「大きく失敗する」を選んだのと同じ理由で、
   保証の破れは静かに出荷されるより赤で止まったほうがよい。この失敗は
   `guarantee.test.ts` が全レベルを走査して出荷前に捕まえる。

不変条件:

- 同じ seed なら、必ず同じ盤面になる(golden テストで固定する)。
- 出題は §7 の技法だけで解ける(推測不要・解は一意)。
- 手がかりは必ず解と整合する(手順 3 より構成上)。
- **帯の目標密度は目標であって約束ではない。**手順 6 の盤面は、一意解であることも推測が
  要らないことも変わらないが、帯が求めたより易しい。**出荷してよい唯一の失敗の形**なので
  これを選んである。発生率は監視する(**未測定**)。

### 予算は仕事量で門にする

これは**端末の予算**であって、開発機やテストランナーの予算ではない。だから門は壁時計では
なく**仕事量**で測る。同じ seed なら、どのマシンでも常に同じ数になる。

理由ごと [SUDOKU_RULES.md](SUDOKU_RULES.md) §7 に詳しい — 並列テストで壁時計は最大 41 倍
ぶれ、最も余裕のある Easy ですら 50ms の予算に対して 107.2ms を記録した。
**稀に落ちる門は、通らない門と同じくらい悪い。**壁時計は計測して出力するだけで、判定には
使わない。

数えるのは **`solverWork` — 技法が見た run とマスの本数**である。1 回の読みは「技法が
1 つの run または 1 つのマスを見た」ことを指す。生成は手順 4 のフル解答の積み上げであり、
フル解答は run とマスの掃きの積み上げなので、生成コストはこの 1 つの数に比例する。
実行時には誰もこの数を読まない — 読みごとに整数を 1 つ足すだけのコストで、門が
「観測できるだけ」ではなく「主張できる」ものになる。

### 実測

`guarantee.test.ts` が走査するのと同じ集合(全 100 レベル + デイリー帯)。仕事量の列は
seed が同じなら常に同じ数になるので、この列だけが門になる。

| サイズ        | n      | solverWork p50 | 最悪   | 壁時計 p50 |
| ------------- | ------ | -------------- | ------ | ---------- |
| 小 6×6        | 20     | 未測定         | 未測定 | 未測定     |
| 中 8×8        | 45     | 未測定         | 未測定 | 未測定     |
| 大 10×10      | 35     | 未測定         | 未測定 | 未測定     |
| デイリー(8×8) | 未測定 | 未測定         | 未測定 | 未測定     |

門(`guarantee.test.ts` が全 100 レベルとデイリー帯を走査して固定する):

- 1 盤面あたりの `solverWork` の上限: **未測定**。実測の最悪に対して 1.75〜2 倍の余裕を取り、
  **サイズごとには分けない** — これは端末の約束ではなく**退行の門**だからである。捕まえたいのは
  「技法が安い順の打ち切りをやめた」「検査が確定済みの run を読み直し始めた」「分割表が
  読みごとに作り直されるようになった」であって、そのどれもサイズを問わず数字に出る。
- 派生シードの上限: **未測定**。実装上の上限より十分手前に門を置き、手順 6 に落ちるより先に
  警告が出るようにする。
- **手順 6 の発生は 0 件が目標**(実測は**未測定**)。
- 壁時計は計測して出力するだけで、判定には使わない。

端末の予算は 1 盤面 100ms 未満。超えた場合の対処順序: ①レイアウト制約の調整(run 長分布を
短い側へ寄せると充填も検査も安くなる) ②派生シードの上限を下げる ③(最後の手段)ビルド時
生成したパズルパックの同梱 — Sudoku §7 と同順。**③を採ったらこの文書に書く**(採るまでは
§14 のとおり「作らないもの」である)。

**低スペック実機での 1 盤面あたりの生成時間も未測定である。**3 本の中で技術リスクが最も
高いのはここなので、[RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md) §2 で必ず確認する。

## 9. レベル(1〜100)とデイリー

**レベル**: level 番号だけからサイズ・レイアウトの密度・seed を決定的に導出する。
コンテンツパイプラインもダウンロードもなし。誰が遊んでも同じレベルは同じ盤面。

| レベル帯 | サイズ | 白マスの割合 | 白マスの個数 |
| -------- | ------ | ------------ | ------------ |
| 1〜20    | 6×6    | 未測定       | 未測定       |
| 21〜65   | 8×8    | 未測定       | 未測定       |
| 66〜100  | 10×10  | 未測定       | 未測定       |

**ティアの列はない。**難易度はサイズと密度という 2 つの数だけが担う(理由は §7)。

- **難しくなる向きは「白マスが増える」である。**手がかりマスを減らすと run が長くなり、
  固定分割(§7 技法 1)が両端の合計から遠ざかって効かなくなり、交差の相手も遠くなる。
  だから帯の内側では白マスの割合が**上がる**。
- **端点は実測から引く。**サイズごとに、技法が許す範囲でどこまで白マスを増やせるかを
  走査し(seed を複数本ずつ)、**各帯の終点をその「届く密度」の中央値に置く**。最も深く
  届いた seed に合わせないのは、そこを狙うと多くの seed が届かず、派生 seed を食いつぶした
  末に**帯が要求したより易しい盤面**を出荷することになるためである(§8 の手順 6)。
  **この走査はまだ行っていない** — 上の表が 未測定 なのはそのためである。
- **帯の内側では密度が線形に上がり**、隣り合うレベルが跳ねない(Nonogram の充填率と同じ形)。
- **帯の変わり目で密度が下がるのは意図的である。**同じ密度でも盤面が大きいほど難しい —
  run が長くなり、1 つの推論が届く距離が伸びる。密度をそのまま持ち越すと、帯の 1 レベル目が
  壁になる([TAKUZU_RULES.md](TAKUZU_RULES.md) §7 /
  [FUTOSHIKI_RULES.md](FUTOSHIKI_RULES.md) §9 と同じ形)。
- seed は `kakuro-level-<n>`。

**レベル数は 100 で、999 には引き伸ばさない。**999 にすると 1 レベルあたりの変化が白マス
1 個を割り、同じ盤面が seed 違いで何百も並ぶだけになる(Sudoku §9 / Nonogram §6 の圧縮判断
を、最初から採る)。レベルは順番に解放し、解放済みはいつでも選び直せる(seed が同じなので
同じ盤面)。

**デイリー**: 1 日 1 問。seed は `kakuro-daily-<YYYY-MM-DD>`(端末のローカル日付のみ。
サーバー時刻もネットワークも使わない)。

- **毎日 8×8・密度固定**(密度の値は **未測定**)。曜日でサイズや密度を変えると
  「当たり日 / 外れ日」という圧を生むため採らない(Sudoku §10)。8×8 はレベル 21〜65 の
  45 レベルを費やす形で、そこまで歩いたプレイヤーが見慣れている。
- **過去 30 日は無条件に開いている**(`DAILY_BACKLOG_LIMIT = 30`)。前の日を解かないと次が
  開かない、という連鎖解錠は付けない — Sudoku だけが持つ形であり、貯まった過去日を宿題に
  しないため新しいタイトルには採らない(Nonogram / Takuzu / Futoshiki と同じ)。
- 達成した日は記録する。**ストリークは数えない・表示しない。**

中断はレベル用・デイリー用の **2 スロットを独立して保持**する(§11)。別のレベルを始めると、
レベル用スロットは置き換わる(確認を出す)。

## 10. 時間と統計

- **プレイ中に時計を表示しない**(ブランド原則)。経過時間は内部で記録し、結果画面と統計で
  のみ見せる。
- 統計: **サイズ別のクリア数、サイズ別の最短時間、合計プレイ時間、デイリー達成日数。**
  サイズのキーは寸法から作る(`size6` / `size8` / `size10` — Nonogram / Takuzu / Futoshiki の
  sizeKey 方式)。帯の呼び名(小・中・大)ではなく寸法を使うのは、呼び名は翻訳の対象になり、
  寸法はならないためである。
- **難易度別には集計しない。**そもそもティアがない(§7)し、プレイヤーが選ぶのはレベル番号
  なので、それ以外の軸の表は「自分では選べない軸の表」になる。
- ミス回数と Hint 回数はクリア画面で見せるが、統計には積まない(§5・§6)。
- **スコアは作らない。**ランキングもストリークも作らない。自己ベストの更新は、更新したときだけ
  静かに示す。

## 11. 中断と再開

- レベル用とデイリー用の**2 スロットを独立して保持する**。レベルを中断してデイリーを遊んでも、
  どちらも失われない。
- 保存するのは モード / seed / レベル番号または日付 / **レイアウト**(マス種の列) /
  **解** / プレイヤーの数字 / メモ / ミス回数 / Hint 回数 / 経過秒数 / 保存時刻。
  **Undo 履歴は保存しない**(§5)。
- **初期数字のフィールドはない。**このゲームは数字を 1 つも配らない(§1)。だから
  「プレイヤーの数字が初期数字を上書きしている」という破損は概念ごと存在せず、代わりに
  「プレイヤーの数字が手がかりマスに乗っている」が同じ位置の検査になる。

### 手がかりは保存しない

**手がかりはレコードに入れず、レイアウトと解から読み直す。**理由は 1 つで、
**保存しなければドリフトできない**からである。手がかりは run の合計にすぎず、レイアウトと解が
揃っていれば足し算 1 回で戻る。両方を持てば、片方だけが壊れた・片方だけが古いレコードが
表現できてしまい、それを検出するコードを書く義務が生まれる。
**表現できない状態は、検証しなくてよい。**

この判断はデータ型の段から効いている — レイアウトの型はマスの種類しか持たず、手がかりを
入れる場所がない。手がかりを作る場所はゲーム全体で `buildRuns` の 1 か所だけである。

Nonogram が同じ判断をしている — あちらのレコードは解答盤面とプレイヤーの印だけを持ち、
行・列の手がかりは保存しない。Takuzu も同じ形で、デイリー達成日はレベル別・日付別ベストの
疎マップから導出し、カレンダー専用のレコードを持たない
([TAKUZU_RULES.md](TAKUZU_RULES.md) §11)。**導出できるものは導出する。**

### fail-closed の検証

**検証は fail-closed。**プレイから生まれえないレコードは読み捨ててホームへ戻す:

- **レイアウトが §1 の制約を破っている** — 長さ 1 または 10 以上の run がある / 上端行・
  左端列に白マスがある / 白マスが連結でない / 白マスが 1 つもない / どちらかの run を持たない
  白マスがある
- **解が §3 の規則 1 を破っている** — どこかの run に同じ数字が 2 つある。**規則 2 は検証
  しない** — 手がかりはこの解から作るので、規則 2 は定義上必ず成り立つ。**これは、手がかりを
  保存しないという判断が消してくれた検証である。**
- **プレイヤーの数字が手がかりマスに入っている**(手がかりマスは選べない — §4)、または
  メモが手がかりマスに乗っている
- **白マスなのに解が空**、または手がかりマスなのに解に数字がある
- レイアウト / 解 / プレイヤーの数字 / メモの**長さが寸法と合わない**、寸法が 6 / 8 / 10 の
  いずれでもない、または正方でない
- 解またはプレイヤーの数字に **1〜9 と空以外**が入っている、メモに 1〜9 の範囲外のビットが
  立っている

- **どちらのスロットのレコードかを決めるのはキーである。**両スロットは同じ形のレコードを
  持つので、レベル用のキーに入っている `mode: 'daily'` のレコードは「デイリーだった」のでは
  なく壊れている。復元せず既定値へ落とす([ARCHITECTURE.md](ARCHITECTURE.md))。この規則は
  `src/test/savedGameSlots.test.ts` が二重スロットのゲームを走査して自動強制する。
- **スロットを置き換える前に確認する。**中断中のレベルを置いて別のレベルを始めれば前の盤面は
  消える。デイリーも同じで、中断中の日と**違う日**を選んだときは確認を出す(同じ日を選ぶのは
  再開であって、何も置き換えない)。盤面と書き込みが黙って消えることを、このゲームでは作らない。
- 背景へ回るとき、盤面の保存と未計上秒の計上を**同じ同期処理で**行う。OS は別のイベントなしに
  アプリを終了できるため、盤面だけを保存すると前回の同期以降の秒数が永久に失われる。
- 保存キーは `kk.saveGame` / `kk.saveDaily` / `kk.stats` / `kk.progress` / `kk.flags` /
  `kk.prefs` の **6 つ**。`kk.stats` はサイズ別の記録、`kk.progress` は解放済みレベルと
  レベル別・日付別のベスト(デイリー達成日はこの疎マップから導出し、カレンダー専用のレコードは
  持たない)、`kk.flags` はチュートリアル完了。**`kk.prefs` があるのは、盤面をまたいで覚える
  設定が 1 つあるからである** — ミスの即時表示のトグル(§5)。Takuzu が 5 キーなのは覚えるものが
  ないからで、**キーの数は揃えるものではなく、そのゲームが覚えるものの数である**
  ([FUTOSHIKI_RULES.md](FUTOSHIKI_RULES.md) §11)。
- 保存の失敗でゲームを止めない。バリデータは例外を投げない。

## 12. Quick Rules(アプリ内チュートリアル)

3 ステップ以内・各ステップ原則 1 文・図中心([I18N_POLICY.md](I18N_POLICY.md))。

1. 数字は 1〜9。タテヨコひと続きの合計を、手がかりの数に合わせる。
2. 同じひと続きの中で、同じ数字は 2 度使えない。
3. 2 マスで 16 なら 7 と 9 — 組み合わせで絞れる(詰まったら Hint)。

詳細ルール・攻略・FAQ はアプリに入れず、ゲーム別 Landing Page
(`https://pixapps.ai/simple-games/games/kakuro/<locale>/`)へ分離する。チュートリアルの
「詳しく見る」から開く。オフラインでは静かに何もしない(ゲームは止めない)。

## 13. 演出とアクセシビリティ

- **手がかりマスは装飾ではなくテキストである。**対角分割を図形として描いて `aria-hidden` に
  すると、この盤面は「空の格子」になる。Futoshiki は不等号を落としてもボックスのない Sudoku が
  残るが、**Kakuro は手がかりを落とすと何も残らない** — 初期数字が 1 つもなく、出題そのものが
  手がかりだからである(§1)。読み上げは **言葉で**行う:「右へ合計 16、下へ合計 7」。記号の
  名前(「シグマ」「斜線」)では、どちらの向きの合計なのかが伝わらない。
- **各白マスはボタンで、位置と状態(空 / 数字)を読み上げ、続けて属する 2 つの run の手がかりを
  読む**(「3 行 5 列、空。右へ合計 16 の 2 マス、下へ合計 7 の 3 マス」)。冗長に見えるが、
  Kakuro では手がかりがマスの外にある — これを省くと、読み上げだけで遊ぶ人はマスごとに
  手がかりマスへ移動して戻る操作を繰り返すことになる。**移動の回数は、読み上げの文字数より
  高くつく。**
- **手がかりマスは押せない**(数字を置く先ではない — §4)。押下の見た目(枠・影)を持たない。
  押せそうに見えて押せないものを盤面に置かない。**ただし読み上げからは消さない** — テキストと
  して読める形で置く。
- 違反表示は色だけに頼らない。警告色に枠を併用する。違反したマスと一緒に**その run の手がかり**
  も示す(§5)。選択マスの 2 本の run のハイライトも同様で、色だけに意味を持たせない。
- プレイヤーの数字とメモは、色ではなく**字の大きさ**で分ける。初期数字が存在しないので、
  Sudoku / Futoshiki の「字の太さで初期数字を分ける」に当たるものはこのゲームにはない(§1)。
- Reduced Motion が有効なら、数字が変わる演出は即時にする。
- **手がかりマスの 2 数字が 320px で読めるかは、まだ測っていない。**1 マスの対角分割に 2 桁が
  2 つ載る — このコレクションで最も文字密度の高い盤面である。実装 PR の冒頭に静的モックの門
  (320 / 360 / 420px × ライト / ダーク)を置く。通らなければ大サイズを 9×9 に落とし、
  **`Size` 型とこの文書を一緒に直す**(§1)。実機では
  [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md) §2 で確認する。

## 14. 意図的な差分

ブランド原則により合わせないもの:

- ミス上限・ライフ制・ゲームオーバー(しない。ミスは数えるが、その数が何かを止めることはない
  — §5)
- プレイ中のタイマー表示、連続日数ストリークとその表示(しない — §9・§10)
- オンラインランキング、スコア(作らない — §10)
- Hint / Undo を広告視聴やコインの報酬にすること(しない。常に無料・無制限 — §5・§6)

設計判断として合わせないもの:

- **パッドの残数表示。**引く先の定数が存在しない(§4)。数えられないものにカウンタを付けない。
- **選択マスに入れられない数字をパッド上で灰色にすること。**技法の肩代わりである(§4)。
- **「もう手がかりに届かない」の違反表示。**まだ何も間違って書いていないマスに警告色が付く
  (§5)。推論は Hint に置く。
- **難易度ティア。**どのレベルも同じ 6 技法を許容するので、名前の後ろに何もない(§7)。
- **0 を含む変種・run 内の重複を許す変種。**どちらも規則 1 と分割表を無効にし、§7 の 6 技法が
  丸ごと成立しなくなる。v1 は 1 規則セットだけを扱う(Connect Four / Checkers の前例)。
- **サイズは 6×6 / 8×8 / 10×10 の 3 種のみ。**上限と下限には構成上の理由がある(§1)。
  11 幅以上は合法に埋められない行を許し、5×5 以下はレイアウトが選べない。
- **技法名の UI 表示。**平易な言い換えのみ(§6)。
- **推測が必要な盤面・複数解の盤面。**出さない(§7)。
- **問題データの同梱・配信。**すべて端末上で生成する(§8)。パック同梱は性能予算が破れたときの
  最後の手段としてのみ検討し、採ったらこの文書に書く — 対処順序は Sudoku §7 と同じで、
  ①レイアウト制約 ②派生シード上限 ③パック同梱の順である。
- **「カックロ」を併記に使うこと。**日本語の「カックロ」はニコリの商標である。README の併記は
  **クロスサム**を使う — Sudoku の併記を「数独」ではなく「ナンプレ」にしたのと同じ構図であり、
  Othello を使わず Reversi と呼んだのと同じ物差しである
  ([REVERSI_RULES.md](REVERSI_RULES.md))。タイトルの `Kakuro` は新聞各紙が使う国際的な一般名
  として、全言語で同一表記のまま使う。

合わせたもの:

- 1〜9 の標準ルール(run 内重複禁止 + 合計一致)、対角分割の手がかりマス、初期数字を配らない
  出題、一意解、常時の違反表示、メモとその自動消去、選択マスの run ハイライト。
