# 計画: Public Club House — 原則の改定から出荷までの段取り

作成 2026-09-30。`simple-games-club#1` の判断を受けた段取りで、

正典は [../PRODUCT_PRINCIPLES.md](../PRODUCT_PRINCIPLES.md)「Club House」と

## 0. 何が変わったか

2026-09-09 に Shared(自前サーバだけ)として設計した層を、Public / Private の 2 デプロイを
持つ **Club House** に広げた。製品オーナーの判断は 2 つだけである。

|                              | 2026-09-09                     | 2026-09-30                                             |
| ---------------------------- | ------------------------------ | ------------------------------------------------------ |
| PixApps がサーバを運用するか | しない                         | **Public を 1 デプロイだけ。固定費が限りなくゼロなら** |
| 順位表                       | 作らない(順位の数字を付けない) | **作る。同じ盤面・同じモードの中だけ**                 |

**変えていないもの**は他の全部である。Core は 1 語も変わらない。全ゲームはオフラインで
完結し、アカウントは無く、Core の画面に順位は出ず、Core が受け取る入口は 3 つのまま。
熱心さの順位(XP・ストリーク・シーズン・順位報酬)は Public でも作らない。

## 1. なぜ Public を先にやるか

2026-09-09 の計画は Private から始めていた。順序を入れ替える理由は 3 つある。

- **建てないと価値がわからない。** 自分でサーバを建てる判断を、体験する前に求めていた。
  これが旧計画の最大の弱点で、`simple-games-club#1` はここを突いている。
- **Public は一人で検証できる。** Private は 2 人以上いないと何も確かめられない。
- **クライアントの大半は共通。** `src/club/`、`sg.club`、結果の送信、Challenge の契約は
  両デプロイで同じものを使う。Public を先に作っても Private の作業は無駄にならない。

## 3. 設計として未決のもの

A の時点で決めていないことを明示する。**B と C で決めて club.md へ追記する。**

- **デイリーを順位表の軸にするか。** 全ゲームのデイリーは日付から seed を導くので、
  世界中で同じ 1 盤面になる。Public の順位表はこれを使えば新しいモードを足さずに済む。
  ただし「終わった 1 局から Challenge を作る」(club.md §6-3)とは作られ方が違い、
  誰も作らないのにカレンダーで存在する挑戦、という新しい種類になる。
- **開かれた参加の意味。** Private は招待 token で入る。Public は誰でも入れるが、
  member token は要る。最初の 1 回をどう配るか(その場で発行するのか、端末が自分で
  作るのか)は未決。
- **Cloudflare 上の SQLite 相当。** Durable Objects のストレージで §5 の契約を満たせるか、
  1 つの state object に全世界の書き込みが集まる形を避けられるか。
- **表示名の安全策の範囲。** 14 言語を一人で見る前提でどこまでが現実的か。

## 4. 前提が崩れたときに何をするか

**Public を出さない、または畳む。** そのとき残るものを先に決めておく。

- Core は 1 つも変わらない。全ゲームはそのまま動く。
- Private Club House は成立し続ける。契約も実装も Public とは独立している。
- 公開文面には Public を 1 語も書いていないので、撤回する約束が無い
  (BRAND.md「出荷するまで書かない」)。

この 3 つが成り立つ形でしか Public を作らない、というのがこの計画の安全弁である。
