# Android の文字サイズとプレイ画面(2026-10-30 計測、正式収録 65 本)

盤の大きさを画面の高さから決めるゲームは、上部バーや操作バーの高さを「文字 100% で測った px の定数」として
引いている。アプリ(Android)は WebView の文字の倍率(`WebSettings.setTextZoom`)を決めていないので、端末の
「フォントサイズ」の設定で文字が大きくなると、盤がバナー枠の下や上部バーの上へはみ出すのではないか。この疑いを、
正式収録の 65 本すべてで測った記録。

関係する正本は [ADS_POLICY.md](../ADS_POLICY.md)「バナー広告の仕様」(ゲーム盤・操作ボタンに重ねない)、
[ARCHITECTURE.md](../ARCHITECTURE.md)「広告と課金」(盤の高さから枠の最悪値 90px を引く規則。どちらの文書も、
高さの見積もりが文字 100% の px で決まっていることは書いていない)、[I18N_POLICY.md](../I18N_POLICY.md)
「レイアウト耐性チェックリスト」(OS のフォントサイズ拡大(font scaling)で崩れない)、
[PRODUCT_PRINCIPLES.md](../PRODUCT_PRINCIPLES.md)「何を削り、何を削らないか」(アクセシビリティは削らない)。

この文書は計測の記録と、選べる案の整理である。「推奨」は書き手の意見で、オーナーの判断を縛らない。決まった方針は
正本に書き、この文書は記録のまま残す。

**2026-10-31 決定: A(上限つきの形で、上限 100%)。** 方針は [PRODUCT_PRINCIPLES.md](../PRODUCT_PRINCIPLES.md)
「Android の文字の倍率」に書いた。下の本文は決定前の記録のまま。上限つきの debug ビルドは同じ日にエミュレータで
確かめた(Sudoku・FreeCell・Number Match の 360×640 と、起動中のフォントサイズの変更。結果は
[RELEASE_CHECKLIST.md](../RELEASE_CHECKLIST.md) の 2026-10-31 の節)。「確かめていないこと」の先頭の項目は、この
範囲では古い。

## 要点

- Android の WebView は、端末のフォントサイズの倍率どおりに文字だけを大きくする。画面の大きさは変わらない。
- 100% では、バナー枠のある状態で 65 本とも重ならない。130% では 14 本が崩れ(5 本は軽微)、200% では 360×640 で
  19 本が崩れ、うち 16 本はバナー枠の下や上部バーの上へ出る(2026-10-31 に「19 本が枠の下や上部バーの上へ出る」から
  直した。残る 3 本は隣へのはみ出し)。崩れは画面が低いほど大きい。
- アプリは最初から倍率を決めていないので、公開済みの版にも同じ仕組みがある(1.7.0 で生じたものではない。公開済みの
  版そのものは測っていない)。
- 文字サイズと関係なく 100% でも起きる問題が見つかった(広告を削除したアプリで操作バーが下端のジェスチャー領域に
  入る、など)。「計測で見えた別件」。

## 方法

- 端末: Android 17 のエミュレータ(Pixel 7 の AVD、WebView 148.0.7778.120)、日本語。411×914(端末のまま。
  上 52px・下 24px の safe area。下 24px はジェスチャーナビゲーションの値)と、`wm size 1080x1920` +
  `wm density 480` の 360×640。
- アプリ: エミュレータに入っていた debug APK(2026-10-30 14:00 のインストール、sha256 `bc4ca653…`)。PR #297
  (1.7.0 の候補)のブランチのビルドで、0ade02e2(13 本の盤の大きさを枠の最悪値で固定)を含み、2026-10-30 の
  eb272811・db195775・35fe2ba6・4b4dc0bd(Water Sort・`svh`・Bubble Pop)を含まない。この文書を書いたツリー
  (4b4dc0bd)とゲームの CSS を比べると、37 本が同じ、Hanoi Towers はクラス名の接頭辞だけ、12 本は `svh` の
  書き方だけ、13 本は 0ade02e2 の上限の有無が違う。Bubble Pop(APK は `--bu-chrome` 156px で、上部バーに残り
  発数の文がある)と Water Sort(列の間の数え方)も違う。
- 文字の倍率: 端末の `font_scale` を 1.0 / 1.3 / 2.0 に設定した。AOSP の設定の段(0.85・1.0・1.15・1.3・1.5・
  1.8・2.0。Android 13 以前は 1.3 まで)のうちの 3 つ。段は AOSP のソースで読んだもので、Samsung などメーカーごとの
  段は確かめていない。倍率を変えるたびにアプリを止めて起動し直した。
- 計り方は [2026-10-29 のバナー枠の計測](2026-10-29-app-banner-strip-audit.md) と同じ。DevTools で DOM を読み、
  65 本・182 モード(「誰かと遊ぶ」は除く)のプレイ画面で、枠 64px / 90px のときの次の 3 つを数えた。
  - **枠の下**: 盤・ボタン・文字が、画面下端のバナー枠の上端より下にある量。
  - **上部バーの上**: 上部バーの下端より上へ出た量。
  - **隣へのはみ出し**: 盤の領域や操作バーなど、隣り合う領域の外へ中身が出た量。
  加えて、広告を削除した状態(ルートの `data-sg-app-banner` を外して枠を消す。広告削除時に `BannerSlot` がすること
  と同じ)、上部バーの高さ、遊ぶ領域の中のスクロール量、画面の外に出た要素を数え、各モードの画面を 64px の枠で撮った。
- 言語: `id-ID` と `de-DE` を 2.0 で、重なりやすい 20 本だけ。
- 確かめ:
  - 各パスの悪かった行を中心に 18 行を選び(`de` の 411×914 のパスの行は含まない)、アプリを起動し直して測り直した。
    すべての値が 0px の差で一致した。
  - 表の数字は、計測とは別に書いたスクリプトで生データから計算し直して一致を確かめた。
  - 130% の写真は、65 本すべてで 100% と並べて見比べようとした(各ゲームのモード 0 を 2 サイズで、360×640 では
    最後のモードも)。見比べは 6 体のエージェントが分担し、Sudoku・Sudoku 6×6・Number Match・FreeCell・
    Gin Rummy・Nested Tic-Tac-Toe はもう一度写真を見て確かめた。人は全件を見ていない。前の状態が残った写真の
    ため、7 組(Gem Swap の両サイズと、Light Grid・Maze Escape・Peg Solitaire・Solitaire・Spider Solitaire の
    411×914)は判定できなかった。
- 計測の途中でエミュレータが 1 回落ちた。他の作業でホストの負荷が約 150 になり、エミュレータ自身のハング検出が
  qemu を止めた。100% の 411×914 は、後半の 31 本を起動し直した後に測った。
- 終わってから倍率・画面の大きさ・言語を元に戻し、APK が変わっていないことを確かめて、エミュレータを終了した。
  計測のたびに「進行中のゲームを置き換えますか?」に「はじめる」と答えたので、エミュレータのアプリに保存されていた
  途中の盤は新しい盤に置き換わった(元の盤は取っておいていない)。

## 結果

### 文字は端末の倍率どおりに大きくなり、画面の大きさは変わらない

16px の文字列の幅は 330.34 / 429.39 / 660.68px(×1.29984 / ×2.00000)。ルートの font-size は 16 / 20.8 / 32px
(`getComputedStyle` が返す値は倍率込み)。画面の幅と高さ、dpr、`100svh`、safe area、メディアクエリは 3 つの倍率で
同じだった。大きくなるのは字と行の高さ(px で書いた `line-height` も)で、px・em・rem で書いた箱の長さは変わらない
(ルートが 32px でも 10rem の箱は 160px のまま)。`ch`・`ex`・`lh` で書いた長さは倍率どおりに伸びる。
`text-size-adjust` は効かない。

仕組み: Android の WebView は、アプリが `setTextZoom` を呼ばない限り、文字の倍率を端末の `fontScale` × 100 に
する(Chromium の `AwSettings`。コードの履歴では 2014 年からの動作で、下限の Chromium 88 も同じはずだが、動かして
確かめたのは WebView 148 だけ)。アプリも Capacitor 8.4.3 もそのプラグインも呼んでいない。CSS で止める方法はない
(新しい `<meta name="text-scale">` は WebView 146 以降だけで、試していない)。iOS の WKWebView は、px で書いた
文字を端末の「さらに大きな文字」で大きくしない(WebKit bug 187013)ので、iOS 版は今も 100% のはず(端末では見て
いない)。

### 倍率ごとの重なり(DOM で測ったもの)

「枠の下」「上部バーの上」「隣へのはみ出し」のどれかが 0 より大きかったゲーム。数字は枠 64px / 90px のときの px で、
そのゲームの全モードのうち最大(モードで大きく違うことがある)。

| | 411×914 | 360×640 |
|---|---|---|
| 100% | なし(65 本・182 モード) | なし |
| 130% | Bubble Pop(枠の下 0/5) | Bubble Pop(枠の下 0/5)、Yacht(枠の下 0/1) |
| 200% | 5 本: Bubble Pop(枠の下 33/59)、Sudoku(はみ出し 12/25)、Memory Match・Water Sort(上部バーの上 0/4)、Overtake(上部バーの上 11/11) | 19 本(下の表) |

Overtake は 130% でも上部バーの上に 3/3px と出るが、画面読み上げ用の見えない文字を数えた誤検出なので、130% の欄には
入れていない。200% の 11/11px にも同じ文字が含まれ、見える文字が上部バーへ出ているのは 6〜8px である(200% の欄には
残した)。Sudoku の「はみ出し」は盤の外枠が切っているマスの目安で、見えない行の数とは一致しない(411×914 の 200% の
写真では 9 行中 6 行しか見えない)。

はず(触って確かめてはいない)。

200% では写真でさらに 10 本ほど崩れる。たとえば 411×914 でも、Sudoku は 9 行中 6 行、Number Match は 9 列中 6 列しか
見えない(Number Match の盤は横にスクロールできるはずだが、触って確かめてはいない)。

### 原因

- **上部バーの文が折れる。** 上部バーは 48px のボタン + 上下 8px で 64px。200% で状態の文が 2 行になると 106px、
  3 行で 151px になる。Gin Rummy は 196px、Sky Fighter は 185px、Bubble Pop は 173px(インドネシア語では 245px)。
- **盤の大きさが 100% で測った px の見積もりで決まる。** `--mm-chrome`・`--bu-chrome`・`--bp-chrome`・`--ws-chrome`
  などは文字が大きくなっても変わらないので、伸びた文字の行のぶん、中央に置いた盤が上部バーの上と枠の下の両方へ出る。
- **盤の中の字が、行や列を押し広げる。** Sudoku の行の高さは中の字で決まる(`grid-template-rows` がない)ので、
  正方形の外枠の中で下の行が隠れる。Number Match のマスは正方形なので、字の行の高さ(字の大きさ × 1.5 + 2px)が
  そのまま列の最小の幅になる。
- **字の入る場所の大きさが固定されている。** FreeCell の重なった札の見える帯(札の幅の約 36%。411×914 で約 17px、
  360×640 で約 14.5px)、Kakuro の 2 つの数字のマス、Yacht の役名の幅(360 幅で約 90px)、Nested Tic-Tac-Toe の
  手番の文(高さ 36px に 2 行ちょうど)。
- **言語で変わる。** `id`・`de` の 200% は、411×914 では日本語とほぼ同じ(Bubble Pop と、`id` の Water Sort の
  フリープレイだけ悪い)。360×640 では Unblock Puzzle が上部バーの上 72/85px(`de`)など悪くなる一方、Memory Match の
  むずかしいのように日本語より良いものもある。いちばん長い言語がいちばん悪いとは限らない。

## 選べる案(オーナーの判断待ち)

コードの上では、A と C は同じ形(`setTextZoom(min(fontScale × 100, 上限))`)で、上限の値が違うだけ。

**A. 上限を 100% にする(文字の倍率を固定する)**

- 得るもの: 文字の経路は 100% に戻るはずで、どの設定でも 100% の表示になる見込み(固定したビルドでは測っていない)。
  100% は、バナー枠のある状態で 65 本・182 モード・2 サイズとも重なり 0(日本語。広告を削除した状態は「別件」)。
  フォントサイズを変えるとアクティビティが作り直される(計測で確認)ので、`onCreate` で最初のレイアウトより前に
  設定すれば毎回効くはず(未確認)。新しく作るゲームも、文字の倍率ごとに測らなくてよくなる。戻すのは 1 行で、
  保存データには触れない。
- 失うもの: Android の端末のフォントサイズが、アプリのどの文字にも効かなくなる。盤やマスの大きさは変わらないが、
  盤の中の数字や状態の文は、文字を大きくしていた人にはそのぶん小さくなる(411×914・130% の Sudoku は今は崩れて
  いない)。ルール・設定・ダイアログなど、文字を読む画面にも効かなくなる。それらの画面が 130%・200% で崩れるかは
  測っていない。文字を大きくしている人の割合は、アプリが計測しないので分からない(オランダの調査では 2 割以上)。
- 残るもの: 「表示サイズ」の設定(画面全体が大きくなり、CSS の画面幅が狭くなる)は効き続ける。確かめたのは
  `wm density 480` で 360×640 にした 1 通りだけで、重ならなかった。もっと狭い幅は測っていない(RELEASE_CHECKLIST は
  320px も検証幅にしている)。
- 手間: コードは `MainActivity` の 1 か所。ほかに Android の新しいビルドと端末での確認、正本の書き換え、固定が
  黙って外れないための CI の門が要る。`@capacitor/text-zoom` でも固定できるが、設定は JS が動き出してからになり
  (最初の描画は端末の倍率になりうる)、Android と iOS の両方に依存が 1 つ増える。

**B. 各ゲームを文字の大きさに耐えるようにする**(バナー枠の最悪値 90px は引いたまま、上部バーや操作バーの実際の
高さを測って盤を決める。上部バーを 1 行に保つ。マスや帯の大きさを字に合わせて決める、など)

- 得るもの: 端末の設定がそのまま効く。長い翻訳やもっと狭い画面にも強くなる。
- 失うもの・手間: 130% までなら上の 14 本、200% まで言うなら 360×640 だけで 19 本と写真でさらに 10 本ほど、
  スクロールが増える 27 本を直し、倍率 × 2 サイズ × 14 言語で測り直す(130% の言語別は測っていない)。rem・em の
  長さは倍率で伸びないので、`ch`・`lh` や中身で決まる大きさ、または実測を使うことになる。今の計測の道具は縦の重なり
  しか見ないので、盤の中で切れたマス・横のはみ出し・「…」を見る検査を先に足さないと、直ったことを確かめられない。
  直すたびにそのゲームのルール文書を同じコミットで直す。上部バーは共有の枠なので、そこを直すとまとめて減るかも
  しれない(試していない)。200% の小さい画面では、盤を小さくするか遊ぶ領域をスクロールさせるしかない画面がある。

**C. 上限を 100% より上にする**

- 上限 115% なら、少なくとも Sudoku(盤を最悪値で固定した 0ade02e2 の形で 105% から)、Yacht の役名(日本語の
  6 文字の名前で 105% 前後から、英語の「Four of a Kind」は 101% から)、Nested Tic-Tac-Toe の手番の文(115% 前後から)
  を先に直す見込み。Sudoku と Nested Tic-Tac-Toe はデスクトップの Chromium で CSS を拡大して模した値、Yacht は CSS の
  寸法からの計算で、どれも端末では測っていない。115% は測っていない。
- 上限 130% なら、上の 14 本を直す。150・180・200% を選んだ人も 130% になる。AOSP(Pixel)では Android 13 以前の
  最大が 130%(Samsung など他社の端末は確かめていない)。

**D. 画面の種類で分ける**(プレイ画面は上限、ホーム・設定・ルール・ダイアログは端末どおり)

- `@capacitor/text-zoom` で、画面を移るたびに倍率を切り替える。文字を読む画面では設定が効く。画面を移るたびに
  字の大きさが変わって見える。評価していない。評価するには、ホーム・設定・ルール・ダイアログが 130%・200% で
  崩れないか、画面を移るたびの再レイアウトのコスト(低スペック端末)、どこまでを「プレイ画面」とするか(ゲームの
  ホーム・結果・プレイ中に開くダイアログ)を測って決める。

**E. 今のまま(記録だけ残す)**

- 手間はない。文字を大きくした人ほど崩れた盤を見る状態と、200% でバナーが操作ボタンに重なる状態が続く。

**推奨: A(上限つきの形で書き、上限は当面 100%)。** ただし固定したビルドを確かめるまでは推奨にとどめる。

1. この計測(1.7.0 候補のビルド)では、文字を大きくした人ほど崩れた盤を見ている。130% の小さい画面では Sudoku の
   下の行が隠れ、200% ではバナーが操作ボタンや盤に重なる。盤や操作に重なるバナーは ADS_POLICY が禁じる形
   (「ゲーム盤・操作ボタンに重ねない」)で、AdMob ヘルプの「Discouraged banner implementations」
   (support.google.com/admob/answer/6275345)も、アプリの内容の上に浮かんだり重なったりするバナーをポリシーに
   反するものとし、広告の配信を止めることがあるとしている(2026-10-31 に確認)。
2. 崩れがないと測れているのは 100% だけ。100% より上の上限は、Sudoku・Yacht などを直すまで、崩れると分かっている
   表示を出すことになる。
3. 上限つきの形で書いておけば、直したゲームと検査が揃ったところで上限を 115%、130% と 1 行で上げられる(C への
   道筋)。
4. 「アクセシビリティは削らない」とは正面からぶつかる。I18N_POLICY は「壊れたレイアウトを出さない」を言語数より
   優先して RTL を後回しにしたが、あれは「まだ無いものを加えない」判断で、A は「今は効いているものを止める」判断
   なので重さが違う。どちらを優先するかはオーナーが決める。A を採るなら、PRODUCT_PRINCIPLES に「Android の獲得計測
   (Meta)— 期限つきの例外」と同じ形で、境界(Android アプリの WebView の文字の倍率だけ。iOS・Web・表示サイズ・
   TalkBack は変えない)と外す条件(Sudoku・Yacht・Nested Tic-Tac-Toe を直し、盤の中の切れ・横のはみ出し・「…」を
   見る検査を足して、115% を 2 サイズで測る)を書く。

A でも C でも、出す前に次を確かめる: 固定したビルドをエミュレータの 130%・200% で起動し、起動中にフォントサイズを
変えても 100% のままであること。プレイ画面以外(設定・ルール・ダイアログ・結果)を 130%・200% で測ること(D が要るかは
これで決まる)。

### 決まったら書く場所

- PRODUCT_PRINCIPLES: 例外として(A・C の場合)。境界と外す条件。
- I18N_POLICY のチェックリスト「OS のフォントサイズ拡大(font scaling)で崩れない」: 消さずに、Android アプリでの
  扱い(固定または上限)を注記する。Web 版と iOS では引き続き確かめる項目のまま。
- ARCHITECTURE「広告と課金」: 盤の高さの見積もりが文字 100% の px であること(とその前提が守られる理由)。
- RELEASE_CHECKLIST の large text の確認項目(端末での確認)。
- CI の門(`check-principles.sh` など): 固定や上限が、Capacitor の更新やリファクタで黙って消えないように。

決めてほしいこと: (1) A〜E のどれか。(2) 1.7.0 に入れるか、その次の版か(A〜D はネイティブの変更なので、測り終えた
1.7.0 の候補に後から足すこと自体が新しい確認を要する)。(3) 下の「別件」をどう扱うか。
(2026-10-31: (1) は A に決まった。(2)(3) は未定。)

## 計測で見えた別件(文字サイズと関係なく 100% で起きる)

どれもこの文書では直していない。

- **広告を削除したアプリで、操作バーが下端の safe area に入る。** `ui/styles.css` の `.game-screen .action-bar` は
  下の余白を 10px にして(2026-07-27 から)、下端の safe area はその下の `.banner-slot` の `margin-bottom` に任せて
  いる。`.screen` は下を空けない。広告を削除すると `BannerSlot` は何も描かないので、操作バーは画面の下端まで来る。
  100% で、182 モードのうち 148(411×914)・152(360×640)でボタンが下端のジェスチャー領域(24px)に入り、ほとんどは
  操作バーの `.action-btn` が 14px。3 ボタンのナビゲーションでは下端が 48px になり、ボタンの下側がナビゲーション
  バーの下に入って押せない可能性がある(推定。3 ボタンでも iOS のホームインジケータでも見ていない)。
- **Sudoku 6×6 で、手がかりのない行が潰れる。** 行の高さが中の字で決まるので、手がかりが 1 つもない行は、ほかの行の
  3 分の 1 ほどの高さになる(411×914 の「むずかしい」の写真で確認)。字を入れるとその行が伸びて盤が動くはず。
  Sudoku(9×9)も同じ作りで、手がかりのない行がある盤なら同じことが起きるはず(未確認)。
- **Kakuro と Futoshiki の盤の上端に届かない(360×640 のデイリー・フリープレイ)。** 盤が遊ぶ領域より高く、
  `align-items: center` のスクロールする箱の中で上下へ同じだけはみ出すので、上にはみ出したぶんにはスクロールでも
  届かない。写真では最上段が 4〜5 割隠れていた(CSS と写真から。触って確かめてはいない)。
- **360×640 で見えたもの。** Peg Solitaire の「残り 32 個」が操作バーの下に隠れる(写真で確認)。Minesweeper の
  最初のヒントの文が途中で切れる。Ludo のダイスの欄が最初の画面に入らず、スクロールが要る。
- **Water Sort(入っていた APK)。** 広告を削除した 360×640 で、デイリーとフリープレイの棚が 3 段に折れ、上部バーに
  82px 重なった。原因は列の間を 10px で数える幅の式(実際は 12px)で、eb272811 が直している
  (WATER_SORT_RULES.md。PR #297 にはまだ入っていない)。
- **Bubble Pop(入っていた APK)。** 広告を削除した 360×640 で、発射台が画面の外にあって届かなかった。35fe2ba6 が
  直すはず(エミュレータでは測っていない)。

## 確かめていないこと

  タブレット)、ほかの WebView(下限は Chromium 88)。
