### 範囲の決定(2026-11-14、オーナー判断)

**手元の iPhone 1 台と Android 1 台で検証し、それをもって Phase 1 とする。Android には SIM を入れて
携帯の回線を使い、iPhone は SIM なしで自宅の Wi-Fi につなぐ。**

- **主の組は N1(iPhone の自宅の Wi-Fi ↔ Android の携帯の回線)**(§6)。家庭のルーターの NAT と携帯会社の
  CGN を越える組で、離れた 2 人が遊ぶ場面に最も近い。Android は Wi-Fi を切って試す。
- 2 台を同じ Wi-Fi に載せただけでは、インターネット越しの接続の確認にならない。2 台の公開 IP が同じなので、
  相手の srflx 宛ての通信は自宅のルーターで折り返す(ヘアピン)だけで、家の外へ出ない(W1、別枠)。
- 補助として、片方の端末で VPN を使う組(W2)も置く。iPhone の側を「家の外」にできる唯一の組で、
  N1 と違う種類の NAT の例にもなる(任意)。
- 携帯の回線どうし・ほかの携帯会社・別の家の回線・同じ OS どうしの組は、**この Phase 1 では測らない**
  (§6 に「未実施(設備なし)」として残す)。携帯の CGN は会社ごとに挙動が違いうるので、N1 の結果は
  「1 社の携帯の回線と、1 つの家庭のルーター」の結果として扱う。その扱いは §7 に書く。

## 3. PoC アプリの機能

ゲームは載せない。画面は 1 枚で、役割(招待する側 / 招待を開く側)を選ぶ。

- **招待する側**: `RTCPeerConnection` を作り、DataChannel を開いて候補を集める。trickle はせず、
  打ち切りの秒数を設定で選ぶ。最小化した招待を作り、共有シートかコピーで渡す。返事を貼り付け欄に
  入れると接続する。
- **招待を開く側**: 招待を貼り付けると返事を作り、共有シートかコピーで返す。そのまま接続を待つ。
- **接続後**:
  - ping / echo で往復時間を測る。
  - 4096 bytes の echo を両方向に 1 回ずつ送る(正典の 1 メッセージの上限)。
  - 背景の実験では、1 秒ごとに tick を送る。
  - 切れたら、同じ画面から新しい招待を作り直せる(E10)。
- **設定**(実験の切り替え):
  - 候補の絞り方: (a) srflx だけ(正典どおり)/ (b) srflx + グローバル IPv6 の host / (c) すべて
  - STUN あり / なし
  - 候補の収集の打ち切り秒数
  - 返事側で、招待の候補を当てるまでの遅れ(時間の窓を作るため)
- **記録と書き出し**: §4 のログを、洗浄してから端末内(IndexedDB)へ即座に追記する。試行ごとに JSON で
  書き出せる(共有シートかコピー)。書き出しは洗浄済みのものだけ。PoC は記録を自動で送信しない。
- Web では動かさない(`Capacitor.isNativePlatform()` で止める)。§5 の E0 の予行のためだけに、開発用に
  localhost のブラウザでも開けるようにする。Web 版には出さない。

### 招待と返事の最小の形

正典(nearby-multiplayer.md「招待と返事」)の形で作り、受け手が SDP を組み立て直す。

- **招待**: 形式の版・試行 ID・ice-ufrag・ice-pwd・DTLS の fingerprint・setup・候補・作成時刻(相対)。
- **返事**: 形式の版・試行 ID・ufrag・pwd・fingerprint・setup・候補。
- ufrag と pwd は省かない(ローカル SDP の書き換えに頼らない)。
- **運ばない欄は定数として仮定する**: mid・sctp-port・fingerprint のハッシュ名・BUNDLE。codec は招待を
  作るときに、自分の localDescription の値が仮定した定数と一致することを確かめる。違えば招待を作らず、
  その値を記録する。
- 候補はアドレスの種類(IPv4 / IPv6 / mDNS の UUID)を区別できる 2 進の形にし、base64url で包む。
- **テストで確かめる範囲**: CI の vitest は node 環境で、`RTCPeerConnection` が無い。CI で見るのは、
  Chromium と WebKit が実際に出す SDP を fixture にした形の検査(最小化して組み立て直すと一致すること)
  まで。`setRemoteDescription` が受理するかは、E0 と E1 と実機で確かめる。fixture のアドレスは文書用
  (192.0.2.0/24、2001:db8::/32)にする。
- PoC には、招待秘密の確認(正典で承認の代わりになるもの)も、アプリ層の暗号(`Channel`)も載せない。
  どちらも製品の層の仕事で、Phase 3 で既存のテストの形で確かめる。

## 4. 計測

1 試行 = 1 レコード。両端末がそれぞれ書き、試行 ID で突き合わせる。

### 試行の条件(毎回残す)

- 試行 ID、役割、端末と OS、userAgent(WebView の版)、設定値。
- ネットワークのラベル(テスターが付ける)。例: `home-wifi` / `cell-docomo` / `cell-au` / `public-wifi` /
  `vpn` / `tether`。
- **起動と接続の状態**:
  - 起動の方法(ホーム画面から / Xcode・devicectl から)
  - インスペクタ・デバッガの接続の有無
  - USB 接続と充電の有無

### イベントと時刻

各イベントに `Date.now()` と `performance.now()` の両方を付ける。記録するイベントは次のとおり。

- pc の生成、createOffer / createAnswer、setLocal / setRemoteDescription。
- 候補ごとの種類・プロトコル・アドレスの分類(下)・ポートが host と同じか・届いた時刻。
- 収集の状態と打ち切り。
- `icecandidateerror` のコード・errorText・URL・アドレスファミリー。
- ice / connection の状態の遷移、DataChannel の open / close、最初の往復時間。
- `@capacitor/app` の pause / resume / appStateChange、`visibilitychange`。
- 共有の開始と終了(Share プラグインが返す、選ばれたアプリ)、貼り付けの受理。
- 起動のたびの boot 記録。

**時計の扱い**: 端末が眠ると `performance.now()` は進まない(Android は CLOCK_MONOTONIC、iOS は
mach_absolute_time)。そこで次のように測る。

- 同じ端末の中の短い区間(数秒)は `performance.now()` で測る。
- 背景をまたぐ秒数は、前面にいる相手側の端末(錨)の時計で測る(E5)。
- `Date.now()` と `performance.now()` の差が変われば、端末が眠ったと判定する。
- 端末をまたぐ比較は、つながった試行の ping-pong(5 回)で推定したずれで補正する。

### getStats

- **間隔**: setLocal / setRemoteDescription から connected か failed になるまでは 1 秒ごと。open の後は
  5 秒ごと。加えて状態が変わるたびに取る。
- **失敗した試行の候補ペアを残す**: libwebrtc は応答の無いペアを約 15 秒で破棄し、getStats からも消える。
  そこで candidate-pair ごとの次の値の最大を、試行レコードへ畳み込んで残す。
  - state・nominated
  - requestsSent・requestsReceived・responsesReceived
- **選ばれたペア**: `transport.selectedCandidatePairId` から辿る(iOS 15 には `getSelectedCandidatePair` が
  無い)。アドレスは `address ?? ip` で読む(Chromium 88 での名前は `ip`)。iOS は host と prflx の
  address を空にする。

### 失敗の分類

イベントから機械的に決める。

| 分類 | 何が起きたか                                                                |
| ---- | --------------------------------------------------------------------------- |
| F1   | 自分の srflx を収集できなかった(`icecandidateerror` の有無も残す)           |
| F2   | 疎通確認を送ったが応答が無い。相手からの要求があったかで F2a / F2b に分ける |
| F3   | ICE は通ったが、DTLS・SCTP・DataChannel が開かない                          |
| F4   | 返事側が諦めた(failed)後に、招待側が返事を適用した                          |
| F5   | アプリの凍結・終了                                                          |
| F0   | 操作や設定の誤り。準備中の失敗として、失敗率に数えない                      |

### 選ばれたペアから NAT を読む(条件つき)

- **読んでよい試行**: 同じアドレスファミリーの srflx を収集できていて、作成から適用までの待ちが 0 の
  試行(E2)だけ。
- **読み方**: ローカル側が srflx なら、相手宛てのマッピングと STUN 宛てのマッピングが同じ。prflx なら、
  宛先ごとに別のマッピングの見込み。host なら NAT なし。
- **待ちのある試行では読まない**: マッピングの作り直しでも prflx になるため。
  - Android では、prflx のポートが srflx のポートと同じかを真偽で残して、作り直しと区別する。
  - iOS では prflx の address が空なので、待ちのある試行では NAT の種類を読まない。
- STUN の宛先は 1 つだけなので、それ以上の NAT の判定はアプリの中ではしない。

### 同じネットワークでの試行の検出

- 実行中に、相手の srflx と自分の srflx で、公開アドレスが同じか(IPv4 はアドレス、IPv6 は prefix)を
  真偽で計算する。
- 同じなら W1(§6)として、成功率の母数から外す。Android の Wi-Fi を切り忘れた N1 の試行や、VPN を入れ忘れた W2 の試行もこれで見つかる。
- 生の値は残さないので、この真偽を試行の時点で計算しておく。

### IP の扱い

公開リポジトリと #280 に結果を載せるため、次のように扱う。

- **洗浄**: IndexedDB に書く前に、洗浄の関数を通す。
  - 消す欄: `address` / `ip` / `port` / `relatedAddress` / `relatedPort` / `usernameFragment` / `url`、
    SDP の本文、ufrag / pwd / fingerprint。
  - 代わりに入れるもの: 下の分類と、「host と srflx が同じか」「ポートが同じか」の真偽。
  - 洗浄の単体テストを `remote:check` に入れる。
- **アドレスの分類**: private / 共有アドレス空間(100.64/10)/ CLAT(192.0.0.0/29)/ public /
  IPv6 global / ULA / link-local / mDNS。
  - CGN があるかは、この分類だけでは決めない。テスターのラベルと、Android の「host と srflx が違う」から
    判定する(100.64/10 は VPN も使い、国内のセルラーには 10/8 の CGN もある)。
  - iOS は host が mDNS 名なので、CGN の判定をしない。
- **生の値**: 端末の画面上のデバッグ表示に限り、書き出しには含めない。

## 5. 実験

前の実験で前提が崩れたら、次へ進む前に計画を直す。順番は §9 の段取りに従う。
共通の規律: **背景が絡む試行(E3 の背景の腕・E4・E5・E5b・E10・E11)では、Xcode や devicectl で起動した
プロセスを止め、ホーム画面から起動し、インスペクタを外す。** デバッガは iOS のアプリの停止を妨げる
(Apple DTS)。インスペクタの接続が停止に影響するかは資料が無いので、外して測る。

- **E0 デスクトップでの予行**: Mac 1 台の Chrome と Safari で、localhost の同じページを開く。最小化した
  招待と返事を、絞り方 (c) で手で往復させる。
  - 確かめること: Chromium と WebKit の間で SDP を組み立て直せること、ログの値が
    `chrome://webrtc-internals` と合うこと、収集の打ち切りの分布。
  - パケットキャプチャで、Chrome の Cloudflare 宛ての STUN のキープアライブが収集の開始から約 2 分で
    止まるかを確かめる(E3 の仮説の前提)。
  - 2 台目の PC を別のネットワークに置けるなら、絞り方 (a) でも試す(任意)。
  - ここでは分からないこと: Android WebView の候補の形、下限の版、アプリの lifecycle、携帯の CGN。
- **E1 下限の版**: iOS 15 のシミュレータと、古い WebView のエミュレータで行う。どちらも入れられるかは
  §9 で確かめる。
  - 必要な API があるか。
  - 同じページの中の 2 つの `RTCPeerConnection` で、「最小化 → 組み立て直し → setRemoteDescription →
    DataChannel が open」まで通るか(iceServers なし、絞り方 (c))。
  - ネットワークの結果は取らない(ホストの網を通るため)。実機の古い端末が借りられれば、E2 の 1 セルを足す。
- **予備確認(N1)**: 大きな行列の前に、手動の交換そのものを否定しうる点を安く確かめる。
  - E4 を 1 つのメッセンジャーで両方向に各 2 回。
  - E5 を 30 秒と 90 秒で、両 OS に各 2 回。
  - 結果が悪ければ、ここで計画を直す。
- **E2 接続の行列**(系統 A: 機械の中継):
  - 2 台を Mac に USB でつなぐ。Android は chrome://inspect の DevTools、iOS は Web Inspector か
    ios_webkit_debug_proxy(#171 の手順)で、招待と返事を機械で渡す。
  - USB の接続だけなら、端末の通信は Mac を通らない。Wi-Fi を切った Android の通信は携帯の回線を通る
    (Android の USB テザリングとアクセスポイントは切っておく)。VPN を入れた端末の通信は VPN を通る。
    ただし、Mac のインターネット共有と、端末の Wi-Fi の自動接続(別の SSID へ移ること)は切っておく(§9)。
  - **この中継はテストの道具であり、製品のシグナリングではない。**
  - 行はネットワークの組(N1・W2・W1、§6)、列は向き(Android が招待 / iOS が招待)。W2 ではどちらの端末を
    VPN 側にするかも振る。
    絞り方は (a)。
  - 接続後に 4096 bytes の echo を両方向に送る。
  - iOS は、絞り方 (c) と W1(同じ LAN)を含む条件で、ローカルネットワークの許可ダイアログが出るかと、
    設定のローカルネットワーク一覧にアプリが載るかを記録する。
  - Android は、ビルドした APK の権限を `aapt2 dump permissions` で記録する。
  - W1(同じ Wi-Fi)が失敗しても、ルーターがヘアピンに対応していないだけの可能性がある。W1 の結果は
    成功率の母数に混ぜない(同じ LAN の相手は近隣対戦を使う、が正典の扱い)。
- **E3 時間の窓**(N1 に限る):
  - **1 つ目の窓**: 招待を作ってから返事を適用するまで、0 / 30 / 60 / 120 / 150 / 180 / 240 / 300 秒待つ。
  - **2 つ目の窓**: 返事側が招待を適用してから、招待側が返事を適用するまで、0 / 5 / 10 / 15 / 20 / 30 /
    60 秒待つ。返事側が failed になった後に、招待側の疎通確認で戻るかも記録する。
  - **腕**:
    - 両方が前面のまま待つ(系統 A)。
    - 待つ間、招待側が背景にいる(人の手)。
    - 返事側が返事を作った直後に背景へ入り、招待側が返事を適用してから N 秒後(N = 0 / 10 / 30 / 60)に
      前面へ戻る(人の手)。現実に最も起きやすい場面である。
  - **凍結の検出**: 待つ間、両端末は 1 秒ごとにメモリ上で自分の時刻を刻む。`Date.now()` の間隔が飛んでいれば
    凍結したとみなし、凍結した試行としなかった試行を分けて集計する。
  - **仮説**(ソースの読解で、未計測):
    - libwebrtc は STUN へ 10 秒ごとにキープアライブを送り、前面で待つ間はマッピングを保つ。
    - ただし network cost の高いポートでは、収集の開始から 2 分で止まる。Android WebView は(メディアの
      許可が無いと)any アドレスのポートで集めるので、Wi-Fi でも 2 分で止まる見込み。iOS はセルラーなら
      2 分になりうる。VPN のインターフェースのコストがどう分類されるかは未確認で、W2 ではそれも記録する。
    - 止まった後は、NAT のタイムアウト(中央値でセルラー 65 秒・それ以外 35 秒と報告されている)で失効しうる。
      N1 で効くのは自宅のルーターと、Android の携帯会社の CGN のタイムアウトである(1 社の値で、ほかの会社の値は
      分からない)。Android がセルラーのとき、キープアライブの 2 分の打ち切りが掛かる見込みが高い。
    - そこで、前面で 120 秒を超えて待った試行の失敗は、凍結による失敗とは別に集計する。
- **E4 共有シートとメッセンジャーの往復**(系統 B: 人の手):
  - 実際のメッセンジャーで、向きごと・アプリごとに招待と返事を渡す。iPhone には SIM が無いので、
    電話番号に縛られず 2 台で同じアカウントを使えるもの(メール・Slack・Discord など)から選ぶ(§9)。LINE は 1 つのアカウントを
    2 台のスマートフォンで同時に使えず、iPhone の「メッセージ」は Android との間で iMessage にならない。
    共有シートの往復の挙動はアプリによって違いうるので、使ったアプリの名前を残し、ほかのアプリでの挙動は
    未確認として扱う。
  - 記録すること:
    - 共有シートを開いてから戻るまでの秒数
    - 戻ったときの pc・ICE・DataChannel の状態
    - iOS の共有拡張の間に、アプリが背景へ入るか
- **E5 背景での生存**:
  - **錨**: 測る側の端末は前面に置き、自動ロックを切る。被験側も自動ロックを切る。画面オフは別の入り方として
    扱う。
  - **入り方を変数にする**: ホームへ戻る / メッセンジャーへ移る / メッセンジャーからさらに別のアプリへ移る /
    画面オフ。iOS ではホームと画面ロックを分ける。Android は、直前に使ったアプリのまま 60 秒の猶予がある
    かどうかで、凍結までの時間が約 10 秒か約 70 秒に分かれる見込み(AOSP のソースから導いた値で、未計測)。
  - **背景に置く秒数**: 5 / 10 / 20 / 30 / 45 / 60 / 90 / 120 秒。
  - **被験側**: 背景に入れる前に「試行開始」を IndexedDB に確定させる。visibilitychange の時点で
    DataChannel に「背景へ」を送る。戻ったら、resume の時刻・自分の状態・3 秒以内に往復できたかを記録する。
  - **錨**: 最後に tick を受けた時刻、「背景へ」を受けた時刻、disconnected / failed の時刻を、自分の時計で
    記録する。
  - Android を USB につないでいる試行では、`adb logcat` の freezer の行と `dumpsys activity` の
    「Apps frozen」を補助の証拠として残す。本人の申告とは区別する。
- **E5b 終了と回線の切り替え**:
  - 被験側をスワイプで終了し、錨が切断に気づくまでの秒数と、E10 でつなぎ直せるかを測る。
  - 対局中にネットワークを変える。Android は Wi-Fi とセルラーを行き来させる(Wi-Fi を入れる・切る)。
    iPhone は Wi-Fi を切って入れ直す。ICE の状態と、戻るかを測る。
- **E6 IPv6 の経路**:
  - 絞り方 (a)(b)(c) を同じセルで比べる。絞る前に集まった全候補の「種類 × ファミリー」と、host と srflx の
    アドレスが同じかを必ず残す。
  - 見込みは 2 通りある(どちらもソースの読解で、未計測)。
    - Android でグローバル IPv6 を持つとき、IPv6 の srflx が捨てられる。
    - any アドレスに bind するので捨てられず、host と同じグローバル IPv6 が srflx として載る。
  - どちらになるかで、正典の「srflx だけ」で IPv6 の経路が残るかが決まる(§8)。
  - IPv6 のアドレスが一時アドレスか安定アドレスかを判別できるかも記録する。
- **E7 STUN なしの対照**: 絞り方 (c)(すべての候補)と `iceServers: []` で行う(絞り方 (a) だと候補が
  0 個になり、必ず失敗して何も確かめないため)。生の値は書き出しから除く(§4)。
  - 別ネットワーク間ではつながらない見込み。
  - 例外になりうるのは、どちらか一方が相手に届く生のアドレス(Android のグローバル IPv6 の host)を出し、
    その受信が塞がれていない組。Android ↔ iOS も含む。ICE は片側の候補だけでも、受け手が届いた検査から
    peer-reflexive 候補を学んで成立しうる。
  - 成功したら、選ばれたペアの種類(host / prflx)で経路を確かめる。
- **E8 大きさ**:
  - 試行ごとに、最小化した JSON の bytes・base64url の長さ・候補の数を残す。
  - **製品の大きさも見積もる**: 製品の欄をダミーで埋めた招待の長さを算出する。gameId・label・
    募集名(上限の長さの日本語)・protocol・席・期限・招待秘密(実際の長さのランダムな bytes)を入れ、
    リンクの前置き(`https://pixapps.ai/simple-games/invite/#`、パスは未定)を足したリンク全体の長さを出す。
  - QR の版は表から求める。byte モード・誤り訂正 M で、v10 は 213 字まで、v11 は 251 字まで。
- **E9 人の手間**: E4 の試行で、交換の開始から DataChannel が開くまでの総秒数、アプリを行き来した回数、
  つまずいた点を記録する。ふだん使っている人(家族など)にも試してもらえれば、1 回ずつ足す。
- **E10 つなぎ直し**: E5・E5b で切れた後に、招待する側が新しい招待を作り、1 往復でつなぎ直せるかと、
  その秒数を記録する。継続鍵の確認は載せない。
- **E11 ふつうの使用**: 15〜20 分のセッションを何本か行う。着信・通知・別のアプリの短い利用など、
  ふつうに起きることは止めない。1 セッションあたりの切断の回数、どちらの側(招待した側 / 開いた側)が
  切れたか、E10 でつなぎ直せたかを数える。

## 6. 端末とネットワークの台帳

使う実機は、A2(Pixel 9 Pro / Android 17)と I2(iPhone 11 / iOS 26)の 2 台だけ(範囲の決定)。
Android は SIM で携帯の回線に、iPhone は自宅の Wi-Fi につなぐ。測らない組も台帳に「未実施(設備なし)」として
残し、測った組の結果で埋めない。

| ID  | 組み合わせ                                             | 扱い                     | 何を試すか                                                                                                          |
| --- | ------------------------------------------------------ | ------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| N1  | iPhone: 自宅の Wi-Fi ↔ Android: 携帯の回線(Wi-Fi オフ) | 主                       | 家庭のルーターと携帯の CGN。離れた 2 人で最も多い組と見込まれる。携帯会社の名前と IPv6 の有無を残す                 |
| W2  | 自宅の Wi-Fi ↔ 自宅の Wi-Fi + VPN(片方の端末)          | 補助(任意)               | 家庭のルーターと VPN の出口の NAT。iPhone を「家の外」にできる唯一の組。どちらを VPN 側にするかも振る               |
| W1  | 同じ Wi-Fi(2 台とも VPN なし)                          | 別枠                     | 公開 IP が同じでヘアピン頼み。STUN の収集の確認にはなるが、インターネット越しの確認ではない。成功率の母数に混ぜない |
| W3  | 公衆 Wi-Fi ↔ 自宅の Wi-Fi / 携帯の回線                 | 任意                     | 外出先で iPhone を公衆 Wi-Fi に載せられるときだけ。硬い NAT・UDP の制限の例                                         |
| N2  | 別の家どうしの Wi-Fi(同じ ISP / 違う ISP)              | 未実施(設備なし)         | 家庭のルーターどうし                                                                                                |
| N3  | 携帯の回線 ↔ 携帯の回線                                | 未実施(設備なし)         | 携帯の CGN どうし                                                                                                   |
| N1' | ほかの携帯会社での N1                                  | 未実施(設備なし)         | CGN は会社ごとに挙動が違いうる                                                                                      |
| N4  | IPv6 シングルスタックの携帯の回線                      | Android の携帯会社しだい | NAT64 / 464XLAT。Android の host 候補に 192.0.0.x(CLAT)があれば該当する                                             |
| S1  | Android ↔ Android                                      | 未実施(設備なし)         | Issue の「同じ OS 同士」。E7 の例外の確認にも要る                                                                   |

- 向きは Android が招待 / iOS が招待の両方。
- **VPN を使うとき(W2)**: 両 OS で無料で使える Cloudflare WARP(1.1.1.1 アプリ)を第一候補にする。VPN の出口の
  NAT の性質は事業者ごとに違い、直接の接続を通さない形なら W2 は失敗し続けうる。VPN の名前と、そのときの
  選ばれた候補の種類を残す。STUN の問い合わせも VPN を通るので、STUN の事業者(Cloudflare)が見る IP は
  VPN の出口になる。

## 7. 試行回数と判定

- **回数**: 各セルはまず 5 回。全勝か全敗なら止める(Wilson の 95% 区間で、5 回全勝の下限は 57%、
  10 回全勝なら 72%)。結果が割れたセルだけ 20 回まで増やし、経過時間などの条件で説明できるかを見る。
- **独立ではない**: 同じ組み合わせの試行は独立ではない。NAT の挙動は回線ごとにほぼ決まっているので、
  1 セルを増やしても精度が上がるのは「その 1 組」だけで、利用者全体の成功率は分からない。報告では
  セルごとの k/n と区間を並べ、全体の率を 1 つの数にまとめない。
- **数えないもの**: 準備中の失敗(分類 F0)は失敗率に数えない。失敗した試行も消さずに残す。
- **Phase 2 の判断の基準は、実験の前にオーナーが決める**(結果を見てから基準を動かさないため)。
  基準は最終の試行数で定める。案:
  - 延ばさなかったセルは 5/5 なら可。
  - 延ばしたセルは、k/20 の区間の下限が X% 以上なら可。失敗が経過時間などの条件で説明でき、製品の
    案内でその条件を避けられる場合も可。
  - N1 の Android ↔ iOS が両方向(どちらが招待しても)で可で、E9 の交換が 2 分以内に終わるなら、
    手動の交換で Go。W2 は補助の証拠として並べる。
  - 届かなければシグナリングの比較(B1 / B2)へ。ほとんどつながらなければ見送り。
  - 再接続の頻度(E11)と E10 の成功率を基準に入れるかも、オーナーが決める。
- **測れない組が残ることの扱い**(範囲の決定による):
  - Phase 2 で Go を出すときも、「Phase 1 が確かめたのは、1 つの家庭のルーター ↔ 1 社の携帯の回線(N1)と、
    補助の VPN の組だけで、ほかの携帯会社・携帯の回線どうし・別の家どうしの成功率は分からない」と
    判断の記録に書く。
  - 製品の画面には、つながらないことがある前提の案内(近ければ近隣対戦を勧める)を最初から置く
    (正典の境界 7 のとおり)。
  - 携帯の回線での実際の挙動は、Phase 3 の配布前の確認(内部テスト・TestFlight で協力してくれる人の
    手での報告)で補う。アプリから接続の結果を送る仕組みは作らない(正典の「計測しない」の約束のまま)。

## 8. 正典に跳ね返りうる点

Phase 1 の結果によっては、Phase 0 で書いた正典を直す。直すかどうかはオーナーが決める。

- **IPv6 の経路**(E6): 「srflx だけ運ぶ」で IPv6 の経路が消える場合、グローバル IPv6 の host 候補を
  載せるかが未決の問いになる。正典の nearby-multiplayer.md は、Android の host 候補の IPv6 を
  「LAN 内アドレス」に数えて落としている。載せるなら、PRODUCT_PRINCIPLES「遠隔対戦」9 の解釈と
  nearby-multiplayer.md の両方を改める判断が要る。
- **時間の窓**(E3): 正典の「つながる見込みと、開始の時間の窓」を実測で書き直す。失効の主な原因が
  キープアライブの 2 分の打ち切りか、背景での凍結か、返事側が諦めることかで、効く手当て(招待の期限・
  「返事を送ったらすぐアプリへ戻る」案内・シグナリング)が変わる。
- **背景**(E5): 今は未計測の秒数を、入り方ごとの実測値に置き換える。
- **携帯の回線**: 正典の「つながる見込み」は、1 社の携帯の回線と 1 つの家庭のルーターの組(N1)の実測で
  補う。正典には測った範囲(携帯会社の名前・IPv6 の有無)を書き、携帯の回線どうしやほかの会社は
  見込みのまま残す。

## 9. 段取り

1. **設備の確認**(オーナー)。
   - Android の SIM: 携帯会社とデータ通信の契約。試験の通信は STUN と小さなメッセージだけで、使う量は
     ごくわずかの見込み(E5・E11 の長いセッションでも数 MB 以下)。IPv6 の有無は試験のときに候補から記録する。
   - VPN(W2 をするときだけ): 片方の端末に入れる VPN(第一候補は Cloudflare WARP)。
   - メッセンジャー: iPhone は SIM なしなので、2 台で同じアカウントを使えるもの(メール・Slack・Discord など)。
   - 下限の版(任意): iOS 15 のシミュレータのランタイムをこの Mac の Xcode に入れられるか。Play ストアの無い
     古い Android のシステムイメージ(WebView が更新されないもの)と、その WebView の版。入れられなければ
     E1 は未実施として残す。
   - `com.pixapps.remotepoc` の iOS の署名(前回はオーナーの操作が要った)。
   - 試験の間は、Mac のインターネット共有、Android の USB テザリングとアクセスポイント、端末の Wi-Fi の
     自動接続(別の SSID へ移ること)を切る。N1 では Android の Wi-Fi を切る。
2. **判断の基準を決める**(オーナー)。§7 の案を採るか直す。
3. **PoC アプリを作る**: `prototypes/remote/`、prepare・check・isolation、最小の招待の codec とテスト、
   洗浄の関数とテスト、ログと書き出し。CI に 2 ステップを足す。PR は Phase 0 の #329 と分ける。
4. E0(デスクトップ)と E1(下限の版)。
5. 端末に入れる(Android は debug APK、iOS は PoC 専用の署名。前回の手順は Nearby PoC の README)。
6. 予備確認(N1 で E4 と E5 を少し)。悪ければ計画を直す。
7. E2・E6・E7(系統 A)と、E3 の前面の腕。
8. E3 の背景の腕、E4・E5・E5b・E9・E10・E11(人の手)。外出先で公衆 Wi-Fi を使えれば W3 を足す。
9. 結果をこの文書の記録の節にまとめ、#280 に要約を書き、Phase 2 の判断に渡す。

## 10. 範囲外

- 製品のコード(`src/nearby/remote/`)、`Session` / `Channel` / `Delivery` への接続、招待秘密の確認、
  継続鍵の確認(すべて Phase 3)。
- 配布サイズ(製品の chunk・Web 成果物・native の増分)。製品へ入れる Phase 3 の門
  (nearby-multiplayer.md「実装時に足すもの」)で測る。PoC は自分の JS の大きさを参考値として残すだけ。
- App Links / Universal Links での受け渡し(§2)。
- QR の読みやすさ。遠隔の 2 人は離れていて、製品はカメラの権限を持たない。製品で QR を出すかは
  Phase 3 で決める。
- targetSdk 37 での `ACCESS_LOCAL_NETWORK` の挙動。PoC は targetSdk 36 でビルドする。
- シグナリングサーバー・TURN(Phase 2 の判断と別の issue)。
- ゲームを載せた対局(Phase 3 の代表 4 本で確かめる)。
- 電池・発熱の計測(遠隔は前面で遊ぶ前提で、背景処理を持たないため。必要なら Phase 3 で)。

## 記録の規律

前回の Nearby PoC の規律を引き継ぐ。

- **試行ごとに残すもの**: 日付(UTC)・基準の commit・app ID・APK の SHA-256・読み込んだ asset 名・端末・
  OS・WebView の版・ネットワークのラベル・起動と接続の状態(§4)・設定・結果。ADB などで読んだ値と、
  本人の申告を区別する。
- **書かないもの**: 個人名・端末のシリアル / UDID・Wi-Fi 名・Team ID・証明書 ID・**生の IP / ポート /
  ufrag / pwd / fingerprint**。洗浄済みの書き出しは、gitignore した `build/measurements/` に置く。
- **読み替えない**: 単発の値を分布として扱わない。シミュレータとエミュレータの結果を実機の結果に数えない。
  コードと自動テストの成功を、実機での成功と読み替えない。
