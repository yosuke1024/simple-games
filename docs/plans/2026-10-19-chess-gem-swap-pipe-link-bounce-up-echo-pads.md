## 共通要件(5 本とも)

前例(42〜46)の「共通要件」をそのまま引き継ぐ。違いと追加だけを書く。

- **オフラインで完結**し、ログイン・サーバー・外部 API を使わない。全機能無料。Undo・Hint・
  聞き直し・Wide を広告や課金に結び付けない。タイムリミット・ストリーク・通知・ログイン
  ボーナス・コンティニュー・ライフを作らない([PRODUCT_PRINCIPLES.md](../PRODUCT_PRINCIPLES.md))。
- **ゲームロジックは Pure TypeScript**(`game/` は React・DOM・storage を import しない)。
  Android / iOS / Web で同じルール。乱数はシード付き PRNG で決定的(`createRng`)。
- **探索・生成・物理に仕事量の上限。**Chess の CPU はノード上限で止まり、完了済みの深さの最善を
  返す。Pipe Link の生成と一意性の検証はノード上限で止まり、上限で自前の生成器で作って検証した
  同梱盤面へフォールバックする。Gem Swap の初期盤面は試行回数の上限で同梱盤面へ。Bounce Up の
  物理は固定ステップと持ち越しの上限。探索は明示的な操作(新しい盤面・CPU の手番・Hint の
  タップ)のときだけ同期で走り、先読み・ポーリングをしない
  ([GAME_LIFECYCLE.md](../GAME_LIFECYCLE.md)「CPU 探索」)。性能の門は仕事量で、壁時計は出力するだけ。
- **時間で進むもの**(Bounce Up のフレームループ、Echo Pads の再生、Gem Swap の連鎖の再生)は、
  バックグラウンド(visibilitychange / native pause)と Back で止まり、**復帰しても勝手に
  再開しない**。アンマウントで timer / RAF / listener / observer / AudioContext の作業を
  すべて解放し、各ゲームに `*.leak.test.tsx` を足す。
- **保存は fail-closed。**規則から生まれえない状態・終局済みの状態・破損データは読み捨て、
  黙って新しい対局を始めない。他ゲームのキーに触れない。デイリーを持つゲーム(Pipe Link・
  Echo Pads)は 2 スロット規則(`dailyGame` キー・`expectedMode`・`slots.test.ts`。
  `src/test/savedGameSlots.test.ts`)。
- **シェル統合**: registry に `channel: 'web-beta'`・`loadStorageSchemas`。`storage/keys.ts` は
  import ゼロの葉。ホームと Quick Rules に `WebBetaNotice`(スキャフォールドが置き、
  `src/test/webBetaNoticeWiring.test.ts` が外させない)。結果カードは `ShareAction`。
  ヘッダの ↻ は、結果カードと同じ再挑戦を出すゲームなら `RestartDialog`(`tryAgain` の ↻ —
  `src/test/restartDialogWiring.test.ts`)。Chess は盤面の CPU 対局 4 本と同じく ↻ = 新しい対局の確認
  (`newGame` + `ConfirmDialog`)、Bounce Up はアーケードの慣例どおり確認なしの即時リトライ(どちらも同じ門が
  許す形)。Back ボタンの唯一の持ち主は GameContext。退出の同期は
  `useOnUnmount(syncActiveGame)` を 1 回(`src/test/unmountBookingWiring.test.ts`)。
  ダイアログの Escape は Cancel(`useDialogDismiss`)— 自分で Escape を受けるゲームは、
  ダイアログが開いている間は答えない。
- **Quick Rules は最大 3 ステップ・図中心・1 文ずつ**(各ゲームの節の文案は仮。ルール文書で
  確定する)。初回の Quick Rules を終えたら、そのまま 1 タップで遊べる。Learn More は出ない。
- **UI**: 1 ゲーム 1 アクセント(ライト / ダーク)。360×640 でスクロールなしに盤面と主要操作が
  収まり、タブレット・PC では幅を使う。Web では下の広告の予約(116px)込みで考える。タッチ・
  マウス・キーボードで遊べ、操作対象は位置と状態を読み上げる。色だけで状態を伝えない
  (Gem Swap の宝石・Bounce Up の足場・Echo Pads のパッドは形でも区別する)。Reduced Motion を
  尊重。音は `services/sound.ts` だけ(WebAudio の合成音 — Echo Pads のパッドの音もここに足し、
  音声ファイルは足さない)。新しい画像・音声・動画アセットは足さない(盤面と駒は CSS /
  インライン SVG。Chess の駒は自作の SVG)。盤面に翻訳の要る文字を置かない。
- **i18n**: 14 言語。新しいキーは各ゲームの `i18n/*.ts`(キー接頭辞は上の表)。`en` が原文。
  `ja` と他 12 言語は **AI が書いたものであり、ネイティブ / 作者はまだ読んでいない**(ルール文書の

  ⑦ 主要操作の UI ⑧ Undo / Hint の正当性 ⑨ 複数シードでの品質 ⑩ 他ゲームとデータが衝突しない)。

## 47. Chess(`chess`)

CPU と指す標準のチェス(8×8。駒の動き・キャスリング・アンパッサン・昇格は FIDE のとおり)。対局相手は
CPU だけで、対人戦・時計・レーティングは作らない([PRODUCT_PRINCIPLES.md](../PRODUCT_PRINCIPLES.md)
「初期リリースで実装しないもの」)。骨格は盤面の CPU 対局 4 本(Reversi / Checkers / Connect Four /
Gomoku — [GAME_LIFECYCLE.md](../GAME_LIFECYCLE.md)「CPU 探索」の実例)から引き継ぐ。1 本のタイマーで指す
CPU・Undo・合法手の点・難易度別の統計・途中保存はそのままで、違うところだけをここで決める。名称は一般名の
「Chess」。2026-08-08 に見送った理由(Web 検索は chess.com / lichess が固定していて取れない・対局エンジンの
工数が最大 — [2026-08-08-mahjong-bubble-ludo.md](2026-08-08-mahjong-bubble-ludo.md))は今も変わっていない。
採る根拠は検索流入ではなく、遊びの語彙である。**工数が 5 本で最大なので、別フェーズ・別 PR で進める**
(この節の末尾「フェーズ(判断 4)」)。

- **規則**: 自分のキングが取られる形になる手(ピンされた駒の手、王手の放置)は非合法。勝敗はチェックメイトだけで
  決まる。**引き分けは自動で成立する** — ステイルメイト・駒不足・三回同形・50 手規則。FIDE では三回同形と
  50 手は申請制(自動になるのは 5 回同形と 75 手)だが、申請の操作を作らない代わりに早いほうを自動にする
  (ルール文書の「意図的な差分」に書く)。50 手規則は**双方 50 手 = 100 プライ**で数える(Checkers の
  `DRAW_QUIET_PLIES` は 50 プライで、数え方が違う)。100 プライ目の手で詰んだ場合は詰みを優先する。同形とは、
  手番・キャスリング権・アンパッサンの可否まで同じ局面のこと。駒不足は K 対 K / K+B 対 K / K+N 対 K /
  同色ビショップだけ、の 4 形に限る(FIDE の「デッドポジション」全体ではない — これも差分として書く)。
- **モード**: 難易度 Easy / Normal / Hard(最初から全部選べる)と、先後(白 = 先手 / 黒 = 後手、既定は白)。
  デイリー・時計・レーティング・ストリークは無い。先後は `ch.prefs` に置き、**次の対局から**適用する。
  進行中の対局には触らない(Reversi §1)。ボタンには「白(先手)」「黒(後手)」と書く(同 — 色と先後の対応を
  知っている前提に立たない)。難易度もホームで選び、次の対局から適用する。ただし盤面 4 本は難易度を prefs に
  持たない。ホームの難易度ボタンがそのまま対局を始め、進行中の対局があれば先に確認する形である。
  `ch.prefs` に難易度を入れるかは、ルール文書で決める。
- **操作**: タップ 2 回(自分の駒 → 行き先の点)。別の自分の駒をタップすれば選び直し、同じ駒か点の無いマスを
  タップすれば選択を外す。合法手の無い駒(ピンされた駒、王手を受けられない駒)は選べない。点も、叱る通知も、
  音も出さない(Checkers §6「無効な操作を叱らない」)。キャスリングはキングの行き先(2 マス先)の点、
  アンパッサンは行き先の点で示す(取れる行き先の印は形を変える)。昇格は 4 択のピッカー(クイーンが先頭で
  フォーカス)。開いている間は盤を `inert` にし、Escape や取り消しでは着手しない(`useDialogDismiss`)。
  マスはボタンで、Tab / Enter / Space で操作する。Undo は Ctrl/Cmd+Z(`useGameKeys`。Checkers と同じ)。
  盤は常に自分が手前(黒なら 180° 回す)。ドラッグは v1 では作らない(足すなら
  `src/test/pointerContractWiring.test.ts` の配線が要る)。
- **CPU**: 探索はプレイヤーの着手を起点にだけ、`CPU_DELAY_MS`(450ms)の 1 本のタイマーの中で同期に走る
  (Worker も先読みも無い。盤面 4 本と同じ)。盤面の生成は無い(初期局面は標準の 1 つ)。探索は反復深化 α–β +
  静止探索(取る手のみ、深さ上限 6〜8。王手を受けている局面の扱いは未決 — 下)で、手の順序は MVV-LVA。根で詰みとステイルメイトを判定し、深さ 1 で
  1 手詰めを必ず見る。**探索は引き分けも終局として読む** — 局面の履歴と 50 手のカウンタを探索へ渡す
  (Checkers §4 が `quietPlies` で直した、CPU の読む木と実際のルールのずれと同じ問題)。
  難易度ごとの読み:
  - Easy = 1 手読み + seed の揺らぎ。
  - Normal = 固定深さ 2〜3。
  - Hard = 反復深化 + ノード上限(**仮 20,000**)。上限に達したら完了済みの深さの最善を返す(深さ 1 は
    必ず完了する)。

  ノード上限は静止探索のノードも数える。Normal も同じ上限の内側で走る。上限値は vitest の仕事量の計測
  (`game/cpu.bench.test.ts` — Checkers / Gomoku の形。判定するのは決定的なノード数で、壁時計は出力だけ)と、
  スロットル下の最悪値で決め、実測をルール文書に書く。同点は `createRng(`${seed}:cpu:${moveCount}`)` で
  決める。seed は対局ごとに 1 つで、同点と Easy の揺らぎにだけ使う。Zobrist 鍵は 32bit の 2 語にし、BigInt を
  使わない(BigInt のリテラルは、ビルドの target である es2018 へ下げられない。`vite.config.ts`)。ルールとしての
  同形の判定は、鍵の一致のあとに局面そのものを比べる(鍵の衝突で誤って引き分けにしない。探索の中は鍵だけでよい)。
  **ルールは `game/engine.ts` の 1 セットだけ**で、探索用の速いコピーを持たない。盤は作り直さずに make / unmake
  する(Reversi §5)。終盤データベースと定石集は積まない(issue #26)。

- **助け**: Undo は無制限・無料で、CPU の応手と自分の 1 手をまとめて戻す(自分の直前の決定点へ。Reversi §6 /
  Checkers §5)。後手で始めた対局の CPU の初手は、自分の決定点が無いので戻らない。戻して同じ手を指せば、
  CPU は同じ手を返す。合法手の点は規則の可視化であって、最善手の提案ではない(Reversi §7)。**作らない**:
  Hint・評価バー・棋譜解析・「取られる」警告・投了・引き分けの提案。盤面はすべて見えているので、次の一手を
  教えれば CPU がプレイヤーの側でも指すことになる(Connect Four §6 と同じ判断)。投了の代わりは新しい対局で、
  負けには数えない。
- **保存と統計**: `ch.saveGame`(1 スロット)/ `ch.stats` / `ch.flags` / `ch.prefs`。デイリーが無いので
  2 スロット規則はかからない。途中保存する(ターン制 — GAME_2048_RULES §10 と同じ理由)。
  - 中身は**着手リスト**(`e2e4` / `e7e8q` の ASCII)と、先後・難易度・seed・経過秒。手番は保存せず、手数から
    導出する。
  - 読み込みでは、同じ engine で初期局面から再生する。非合法手・終局後の手・手数上限の超過・形の合わない記号の
    どれかがあれば保存を読み捨て、ホームへ戻る(fail-closed。黙って新しい対局を始めない)。
  - 着手リストが局面の履歴そのものなので、保存を挟んでも三回同形の判定を失わない。Checkers §11 は「局面の履歴を
    保存形式に持ち込む」ことを理由に三回同形を見送ったが、ここではそれが要件になる。
  - CPU の手番で離れた対局は、再開の 450ms 後に CPU が指す(ショートカットからも同じ — GAME_LIFECYCLE.md の
    例外)。スロットが 1 つなので、ショートカットは中断中の対局へ直接入る(`entry` と
    `storage/gamePersistence.ts`。`src/test/shortcutResumeWiring.test.ts`)。
  - 統計は難易度別の `played`(開始で数える)/ `wins` / `losses` / `draws` と、全体の `totalPlaySeconds`
    (bookedRef、`useOnUnmount(syncActiveGame)`)。放棄は負けに数えない(Reversi §8 / Checkers §7)。

- 再開後の Undo。盤面 4 本は Undo の履歴を保存しない(再開した対局はその局面から始まる)。Chess の保存は着手リストなので、再開後も追加の保存なしで Undo できる。推奨: 再開後も Undo できるようにし(「Undo は無制限」をそのまま守る)、盤面 4 本との意図的な違いとしてルール文書に書く。

## 48. Gem Swap(`gem-swap`)

8×8 の盤で隣り合う 2 つの宝石を入れ替え、同じ種類を縦か横に 3 つ以上並べて消す一人用のパズル
(一般に Match-3 と呼ばれる形式)。1 ラウンドは成立した入れ替え 30 回で、消した個数がそのまま得点に
なる。2048・Block Puzzle と同じく「自分の記録を伸ばす一人パズル・助けは Undo・デイリーなし」の側に
置く。同じ「3 つそろえて消す」語彙を持つ Bubble Pop(撃って吸着させる・天井が降りる・アーケードの棚)
とは、操作・形・色・文言を分ける。F2P の Match-3 が積み上げる仕掛け(特殊宝石・コンボ倍率・ブースター・
ライフ・追加手数・レベルマップ・称賛の掛け声)は持たない。

- **規則**: 盤は 8×8 固定。宝石の種類は 5(Easy)/ 6(Normal、既定)で、1 種類 = 1 つの形 + 1 つの色。
  上下左右に隣り合う 2 つを入れ替えた結果、どこかに同じ種類の縦か横の 3 連以上ができたときだけ成立する
  (同じ種類どうしの入れ替えは成立しない)。成立した並びは同時にすべて消える(L・T 字の交点は 1 個と
  数える)。上の宝石が落ち、空いたマスは列ごとの補充で埋まる。落ちてまたそろえば続けて消え、盤が
  静まるまでを 1 手とする。**得点 = その手で消えた個数の合計**(4 連・5 連・連鎖にも倍率や特殊宝石は
  無い)。成立しない入れ替えは何も変えず、回数にも数えない。ラウンドが終わるのは、成立した入れ替えが
  30 回に達したときか、盤が静まった時点で成立する入れ替えが 1 つも無い(手詰まり)とき。シャッフルは
  しない。7 色は v1 に入れない(手詰まり率を測ってから判断する)。
- **モード**: Free Play のみ(ステージ・デイリー・時間制はない。デイリーを持たないのは 2048 /
  Block Puzzle の §13 と同じ判断)。色数は `gs.prefs` に覚え、選ぶことを強制しない(Snake の速度と
  同じ形)。変えた色数は次のラウンドから効き、進行中のラウンドは自分の色数のまま続く。
- **操作**: タップで 1 つ選び、隣をタップすると入れ替わる(マウス・支援技術も同じ道)。隣でない宝石を
  タップしたら選び直しになる。宝石から隣へのスワイプでも入れ替えられる。判定は 2048 §3 の形(1 本の
  指を `pointerId` で記録し、離した時点で測り、`pointercancel` で捨てる)で、スワイプの後に残る click は
  使用済みにする(`src/test/pointerContractWiring.test.ts`)。キーボードは、矢印で焦点を動かし、
  Enter / Space で選び、選択中の矢印でその方向と入れ替え、Escape で選択を外す(ダイアログが開いている
  間は答えない)。**不成立は叱らない**: 宝石は動かず、`invalid` も含めて音は鳴らず、選択はそのまま残る
  (2048 §3・MEMORY_MATCH_RULES §3)。副操作が無いので、右クリックの契約は持たない。再生中のタップは
  最終盤面を確定するだけで、次の選択には使わない。
- **生成と解決**: 初期盤面は行優先で、左 2 つ・上 2 つと 3 連にならない種類だけから一様に選んで
  **組み立てる**。これで「最初からそろっている並び」が無いことを保証する(できあがりを検査するのでは
  なく組み立て方で保証する — Bubble Pop §6 と同じ考え方。除かれる種類は高々 2 つなので、候補は必ず
  残る)。そのうえで、成立する入れ替え(隣接対 112 組)が 1 つ以上あるかを確かめ、無ければ引き直す
  (最大 64 試行。超えたら色数ごとの同梱盤面 — 同じ生成器で作り、テストで「並び無し・成立手あり」を
  確かめたもの)。補充は列ごとの決定的なテープで、列 `c` の `k` 個目は
  ``createRng(`${seed}:${c}:${k}`)``(初期盤面の試行の鍵とは名前空間を分ける)。補充は盤面を見ない —
  そろう色を選んで助けることも、詰ませることもしない(Block Puzzle §6 と同じ)。1 手の解決は
  **純関数を 1 回呼ぶだけ**で、全工程(入れ替え → 消去 → 落下 → 補充 → 連鎖の各段)と最終盤面・得点・
  テープ位置を返す。UI はそれを再生するだけ(Bubble Pop §2 の `placeAndResolve` と同じ形)。探索は
  持たない。連鎖の段数には上限を置き、実測した分布とともに RULES に書く。
- **助け(Undo)**: 無料・無制限。成立した 1 手を丸ごと戻す(盤面・得点・残り回数・列ごとの補充位置)。
  ラウンドは 30 手なので履歴は最大 30 で、2048 / Block Puzzle の 2000 手の上限は要らない。
  **Undo は振り直しではない**(2048 §6・Block Puzzle §7): 戻して同じ入れ替えをすれば、同じ宝石が
  落ちる。列のテープは手に依らないので、戻せば各列に次に落ちる宝石が見える。**Undo が先読みを兼ねる**
  ことを RULES に正直に書く(2048 の新しいタイルは空きマスの並びで置き場所が変わるが、ここの補充は
  変わらないので、先読みはより正確になる)。同じ先読みを理由に Undo を作らなかった Ludo §6 と結論が
  逆になる理由も添える(あちらは相手のいる対局で未来の出目が漏れる。こちらは一人で自分の記録と比べる
  だけ)。ラウンドが終わった後は Undo を出さない(推奨。2048 は終局で結果カードが盤を覆い、Undo の
  キーも止まる。Block Puzzle の `canUndoNow` はプレイ中だけ)。**作らない**: 最善手の Hint・成立手の
  一覧(放置すると光る形も)・消える数の予告・シャッフル・追加手数・ハンマー等の道具・ライフ。Hint を
  作らない理由は 2048 §8 と同じ(盤面は全部見えている)。予告を作らない理由は Bubble Pop §8 と同じ
  (着弾までは示すが、何が消えるかは示さない — 読むことが遊びの中身)。Block Puzzle §4 が消えるライン
  を先に見せるのは、それが見えている盤面の事実だからだ。ここの連鎖は、まだ見えていない補充に依る。
- **保存と統計**: キーは `gs.saveGame` / `gs.stats` / `gs.flags` / `gs.prefs`(スキャフォールドには
  stats / flags しか無いので、`storage/keys.ts` に足す)。保存スロットは 1 つなので、ショートカットは
  中断中のラウンドへ直接入る(`entry`。`gs.save…` と `storage/gamePersistence.ts` を足すときに一緒に
  宣言する — `src/test/shortcutResumeWiring.test.ts`、スキャフォールドの `GemSwapRoot` のコメント)。
  中断レコードは seed・色数・成立した入れ替えの列(最大 30)・経過秒とし、**同じ解決関数で再生して**
  fail-closed で読む(隣でない・不成立・31 手目・手詰まりの後の手・知らない色数を拒否)ことを推奨する
  (Ludo §10.1 の「入力だけ」、Chess の着手リスト再生と同じ形。導出できる盤面まで保存すると、食い違い
  うる 2 つ目の真実になる。再生なら Undo 履歴も戻る)。保存するのは、成立した手ごと・退出・バック
  グラウンドへ回ったとき。統計は `played`(始めたラウンド数)・色数別の自己ベスト・`totalPlaySeconds`
  だけ。自己ベストはラウンドの終わり(30 手か手詰まり)でだけ更新し、途中で新しい盤面へ移ったラウンドは
  `played` にだけ残る。累計の消した数・最長の連鎖・Undo の回数・ストリークは持たない。退出の同期は
  `useOnUnmount(syncActiveGame)`。
- **UX**: 残り回数は数字ではなく **30 区切りの細いバー**で見せる(数字のカウントダウンは「あと何回」
  という圧になる — Bubble Pop §3・§13 の点の列と同じ判断)。数は読み上げだけ。得点は常時表示する
  (2048 §7 と同じく「いま何をしたかの結果」)。時計・称賛の言葉・紙吹雪・画面揺れ・連鎖の段数の表示は
  出さない。再生は 1 段 150〜180ms、1 手あたり約 1 秒まで。段が多い手ではこの 2 つが両立しないので、約 1 秒を
  優先して段の間隔を 150ms より詰める(仕様の数からの意図的な差分。下限と詰め方は下の未決事項)。再生中に
  タップすると最終盤面になる。Reduced Motion では再生せず、最終盤面をそのまま描く。バックグラウンドへ
  回ったときと Back では、最終盤面を確定してからタイマーを止める(状態は解決の時点で確定しているので、
  止めても失うものは無い)。最後の手から結果カードまで約 1 秒置く(`useResultReveal`)。結果カードには
  得点・色数・終わった理由 1 行(30 手 / 手詰まり)・自分の記録との差(`BestDelta`)・`ShareAction` を
  置き、↻ は `RestartDialog`。宝石は 5〜6 種の**宝石のカットのシルエット**をインライン SVG のパスで描く
  (フォントのグリフは使わない)。形が主で、色は補助。Bubble Pop の ● ▲ ■ ◆ ✦ ☾ と同じ形は使わない
  (円・三角・正方形・菱形・星・三日月を外し、六角・八角・しずく・舟形などから選ぶ — 確定は RULES)。
  宝石の色はゲームの中身として `gem-swap.css` のトークンに置き(Bubble Pop §12 の `--bu-c-*` と同じ
  例外)、選択の輪に使うアクセントの色相族は避ける(同 §12)。読み上げは位置と形の名前で、色の名前に
  しない。手の後には「n 個消えた・残り m 回」を読み上げる。8×8 は 360 幅で 1 マス約 40px で、Web の
  広告予約 116px を含めても盤・バー・Undo が収まる見込み(Phase 3 で実測)。効果音は
  `services/sound.ts` の既存の音だけを使い、**連鎖の段ごとに高くしない**(推奨 — 段ごとに上がる音は、
  連鎖への報酬の合図になる)。
- **Quick Rules(仮)**: ① 隣り合う 2 つの宝石を入れ替えて、同じ形を 3 つ以上並べる。② そろうと消えて
  上から補充され、落ちてまたそろえば続けて消える。③ 成立した入れ替え 30 回で 1 ラウンド、消した数が
  得点になる。(「無料」などの約束の語は入れない。)
- **テスト**: 3 連の検出(縦横・4 連・5 連・L / T の交点を 1 個)/ 入れ替えの成立(隣接だけ・同じ種類
  どうしは不可・不成立は盤も回数も変えない)/ 落下と補充(列ごとのテープ・決定性)/ 連鎖と得点 /
  30 手と手詰まりでの終わり(手詰まりは作った盤面で確かめる)/ 生成(どの seed でも並び無し・成立手
  あり、64 試行の上限と同梱盤面への切り替え、同梱盤面そのものの検証)/ Undo(解決の逆になっていること・
  戻して同じ手で同じ結果)/ golden(seed `gem-swap-golden` の初期盤面と短い手順 — 2048 / Block Puzzle
  の `compatibility.test.ts` と同じ)/ 再生による復元と破損した保存の拒否 / 再生中のアンマウントと
  バックグラウンド(`*.leak.test.tsx`)/ Reduced Motion / タップ・スワイプ・`pointercancel`・
  キーボード。**品質の実測(⑨)**: 簡単な自動プレイ(成立手から一様に選ぶものと、その場で最も多く
  消すものの 2 通り)を 5 色・6 色 × 多数の seed で回し、30 手より前に手詰まりで終わる率・連鎖の段数の
  分布(最大を含む)・得点の分布・同梱盤面への切り替え率を、回した数とともに RULES に書く。
- **文書**: GEM_SWAP_RULES.md の「意図的な差分」に、F2P の Match-3 に期待されるものとの差(特殊宝石・
  コンボ倍率・ブースター・ライフ / エナジー・追加手数・シャッフル・レベルマップ・放置すると光る手・
  称賛の掛け声・時間制のモード)を並べる。Bejeweled / Candy Crush の名前は、その中の比較の小節(出典と
  確認日つき — BRAND.md「自社タイトルと比較対象の名前」)にだけ書く。Bubble Pop・2048・Block Puzzle との
  ルールの違いも同じ節に書く。i18n 節には来歴を書く(`en` が原文、`ja` と 12 言語は AI が書いたもので
  未読)。`src/i18n/unreadCatalogs.test.ts` の `UNREAD_JA_GAME_IDS` の `gem-swap` は Phase 1 で足した
  (共有ファイルなので、Phase 1 で 4 本まとめて。Chess は ②)。
- **リスク**: Bubble Pop と見た目も語彙も近い(形・色・文言を別物にする。棚は別だが、検索・お気に入り・
  最近遊んだの行では並びうる)。F2P の Match-3 を期待する人には物足りなく見える(削ったものは意図として
  RULES に書き、謝らない)。Undo と決定的なテープのため、自己ベストは読む力だけでなく、試し続ける根気も
  測ってしまう(2048 と同じ性質 — 正直に書く)。6 色の手詰まり率はまだ測っていない。早い手詰まりが
  多ければ、既定の色数をオーナーの判断に戻す(シャッフルでは救わない)。Hint が無いので、成立手を
  見つけられない人の出口は ↻ と Home だけになる(Phase 4 の試遊で見る)。連鎖の再生は、入力の競合や
  タイマーの取り残しが起きやすい場所である。題「Gem Swap」の同名作品と商標は調べていない。

**未決事項(Phase 2 でルール文書に決める。推奨つき)**:

## 49. Pipe Link(`pipe-link`)

格子のタイルを回してパイプをつなぎ、水源からすべてのタイルへ水を通す論理パズル(一般に
パイプを回してつなぐ形式と呼ばれるもの。MIT ライセンスのパズル集の Net が同じ形式。正式名称は
Pipe Link)。時間とともに流れ出す水の前に部品を置いていく Pipe Mania とは別の遊びである。
論理の棚の 16 本目(registry の `category: 'logic'` は Pipe Link を含めて 16)で、推論の型が
Bridges・Loop Puzzle と重なる — それを隠さず、ルール文書で比べる(下の「文書」)。

- **規則**: W×H の全マスにタイルが 1 枚ずつある。型は管を出す方向の数で端(1)・直線(2)・
  エルボ(直角の 2)・T(3)の 4 種で、十字(4)は無い。隣り合う 2 枚が互いに管を向けているとき
  だけつながる。盤の端は閉じていて、外へ向いた管は行き止まり(折り返しは作らない — 仕様に明記が
  無いので未決事項に挙げた)。水源は 1 マスに固定され、そこからつながりをたどって届くタイルが
  点灯する。**全タイルが点灯したらクリア。**型の多重集合は全域木から作るので管の口の総数は
  2(n−1) で、n 枚が全部つながる配置はちょうど n−1 本のつながりの木になる(行き止まりも閉路も
  残らない)。だから勝利判定は保存した解と比べず、点灯だけで決まる。
- **モード**: Easy 5×5 / Medium 7×7 / Hard 8×8 の Free Play と Daily(Medium 固定・今日の 1 問だけ。
  seed は前例と同じ形の `pipe-link-<difficulty>-<token>` / `pipe-link-daily-<YYYY-MM-DD>`、token は
  状態の層が渡す — Loop Puzzle §9)。9×9 は v1 に無い: Bridges の実測で 360×640(Web の広告予約
  込み)の 9×9 は 1 マス 34.0px と、Box Regions / Shape Regions の 1 マスの下限 `clamp(34px, …)` に
  張り付く。Pipe Link はタイルそのものが的で、Bridges の島(直径 1.3 マスの円)のように的を
  広げられない。ヘッダの ↻ は `RestartDialog` で「Restart(同じ盤面を初期の向きへ。作り直さず
  探索も走らない)」と「New Board」、Daily は Restart だけ。最後の難易度は `pn.prefs`(初期値
  Easy)。ストリーク・過去のデイリー・レベル番号・星の評価は作らない。
- **操作**: タップ(左クリック)で 90° 時計回り。反時計回りはマウスの右クリックと Shift+Enter で、
  タッチには無い。右ボタンは既存の契約どおり — 盤全体(隙間も)でブラウザのメニューを出さない、
  タッチとペン先の長押しが出す `contextmenu` は無視する(Pipe Link では長押しに意味が無い)、
  macOS の Ctrl+クリックは反時計回り 1 回で、後に続く click を `detail > 0` の印で飲む
  (キーボードの Enter は飲まない)— ここまでは Minesweeper §3・Nonogram §3 と同じ。ペンの
  バレルボタンは右ボタン(ホバー中は `button` 2、先を着ける前から押していれば `buttons` 3)—
  これは Nonogram §3 だけが持つ形で、それに合わせる。右ドラッグは作らない。押下で覚えたものは
  `pointercancel` で解く(`src/test/pointerContractWiring.test.ts`)。キーボードは盤が 1 つの
  タブ位置(roving tabindex)で、矢印で移り、Enter / Space で時計回り、Shift+Enter で反時計回り
  (ボタンの既定の click と重ならないよう keydown で受ける)、Ctrl/Cmd+Z で Undo、H で Hint
  (Loop Puzzle §4 と同じ割り当て)。キーリピートでは回さない。選択の状態が無いので Escape は
  受けない。
- **生成**: seed から決定的。① 次数 3 以下・十字無しの全域木を作り、始点を水源にする(木から
  各マスの型と正しい向き — 解 — が決まる)。② 一意性: DFS で解を 2 つまで数え、ちょうど 1 の
  盤だけを採る(解は「各タイルがつながる方向の集合」で数える — 直線の 180° は同じ解。上限に
  届いた数え上げは一意とも複数とも言わない)。③ 等級: 技法ソルバー — L1 噛み合わせ(盤の端と、
  決まった隣との管の有無を両側でそろえる)/ L2 閉路と孤立の排除(閉路を作る向き、水源へ届かない
  閉じた集まりを作る向きを捨てる)/ L3 仮定 1 回(入れ子にしない)— を型だけの盤から回す。
  Easy = L1 だけで全部決まる、Medium = L2 が要る、Hard = L3 が要る(Medium に L3 の要る盤を
  入れるかは未決事項)。④ 出題: 解から型ごとに別の向きへ崩し、完成済みの盤と、解と同じ向きの
  タイルが 60% を超える盤は捨てる(「別の向き」の読み方は未決事項 — 全タイルを解と違う向きに
  すると直線の答えが初期配置から漏れる)。⑤ 仕事量は Bridges §6 と同じく 1 盤面に予算 1 本
  (全試行で 1 つの上限。各呼び出しは残りの予算で走る)、数え上げのノード上限は 5,000〜20,000 の
  間で実測から決める。上限に届いたら各ティア 24 面の同梱盤面へ(この生成器が記録した seed から
  作ったもので、テストが別実装で一意性と等級を確かめ直す)。探索が走るのは New Board・デイリーを
  開く・Hint のタップだけで、**読み込み時の再証明はしない**(下の「保存と統計」)。
- **助け**: Undo は無料・無制限(履歴はセッションだけで保存しない。Hint 回数は戻さない)。
  理由は 2 つ — タッチに反時計回りが無く、1 段戻すのにエルボ・T・端は 3 タップ(直線は 1 タップ)
  かかる。隣のタイルを誤って回しても警告は出ない。Bridges §9 の「循環は 1 段戻れない」と同じ形。
  Hint も無料・無制限で、盤面には書き込まない: 技法ソルバーが証明できるタイルを 1 枚、点線の輪と
  正しい向きの薄い図で示し、盤の下の 1 行で何を示したかを言う(技法名は出さない)。技法で言えない
  ときだけ保存した解の 1 枚。これは Loop Puzzle §6 の「技法 → 解」の順で、§6 の第 1 段(解と違う印を
  先に示す)は持たない — 未完成の盤ではほとんどのタイルが解と違い、それを示すのは作らないと決めた
  答え合わせになる。印は次の 1 手まで残り、時間では消えない。回数は結果カードに事実として出し、
  盤が変わっていない Hint の押し直しは数えない(Loop Puzzle §6)。作らない: 自動回転・答え合わせ
  ボタン・タイルロック・Hint 回数制限。
- **保存と統計**: `pn.saveGame` / `pn.saveDaily`(キーの葉 `game` / `dailyGame`。2 スロット規則 —
  `gameSlotSchema(key, expectedMode)`・`storage/slots.test.ts`)/ `pn.stats` / `pn.flags` / `pn.prefs`。
  中断レコードは seed・難易度・日付・**解・初期の向き・今の向き**・Hint 回数・経過秒(初期の向きは
  Restart のため、解は Hint の最後の段のため。Undo 履歴は持たない)。検証はすべてスキーマの
  `validate` の中で、盤の大きさに比例する仕事で終える(解が次数 3 以下・十字無しの全域木で外へ管を
  出さない、今と初期の向きが解の型の回転、水源が盤内、未クリア、プリセットの大きさ、カウンタの
  範囲、キーとモード。今日でないデイリーは記録ごと捨てる)。通らなければゲームのホームへ — 黙って
  新しい盤面を始めない。**一意性は探索で証明し直さない**: 勝利判定は点灯で決まり、技法の Hint は
  解を読まないので、手で作った複数解のレコードで食い違いうるのは最後の段の「解の 1 枚」だけ。
  Bridges / Loop Puzzle の「開くときの再証明」(GAME_LIFECYCLE.md「CPU 探索」の暫定の例外。
  オーナーの確認待ち)には乗らない。統計は難易度別のプレイ回数・クリア数・合計秒・最短秒と、
  デイリーの達成日 → その日の最短秒(日付の集合。連続は数えない)。プレイ中は時計も回した回数も
  出さず、記録は経過秒だけ(回した回数は 3 タップか右クリックか Undo かで変わり、比べられない)。
  デイリーを Medium に数えるかは、前例 3 本でそろっていない規則(オーナーの確認待ち)に従う。
- **UX**: タイルは 1 枚 1 `<button>` で、行・列・型・今つながっている方向・点灯・水源・Hint の印を
  読み上げる(盤は `role="group"`)。点灯は色だけで伝えず形でも分け(例: 中空の管と満ちた管)、
  水源も形で示す。盤に翻訳の要る文字を置かない。回転は状態がタップで即座に変わり、演出は見た目
  だけで連打を待たせない(表示角は累積で持ち、270° → 0° で逆回りさせない)。Reduced Motion では
  回転も点灯も演出なし。音は既存の `sounds.select` / `undo` / `clear` だけ。盤の高さは `svh` で
  測り、横持ちでつぶれない下限を置く(Loop Puzzle §13・Bridges §13 の教訓)。アクセントは点灯した
  管が着る見込み(全点灯で盤のほぼ全面 — アクセント選定の手順 4 に渡す)。
- **テスト**: 共通の 10 種に加えて — 点灯の到達、回転の周期(直線 2・ほか 4)と反時計回り =
  時計回りの逆、全点灯 ⇔ 全域木 / 生成の不変条件(次数・十字・端・連結・非巡回)と seed の golden /
  崩し(完成済み無し・60% 以下)/ ティア(Easy は L1 で解ける・Medium は L1 だけでは解けない・Hard は
  L1〜L2 だけでは解けない)/ 数え上げの 1 解・2 解・解なし・ノード上限 / 小さな予算で同梱盤面へ
  落ちること・同梱 72 面の再確認 / **全数**: 3×3・3×4 の次数 3 以下の全域木をすべて列挙し、
  全回転の総当たりと数え上げ・技法の結論を照合 / 別実装の DFS で 1,000 seed を照合 / 空の盤から
  Hint だけで解き切れ、示す向きが常に解と一致 / Undo / 保存の往復と破損の拒否 / 右クリック・長押しの
  `contextmenu`・ペンのバレル・Ctrl+クリック・`pointercancel`・Shift+Enter / アンマウントと ↻ の
  計上が 1 回だけ。実際に確かめた範囲(全数 / 標本の数)をルール文書に書き、提案時の試作の一意率
  などは再現するまで「検証済み」と書かない。
- **文書**: `docs/PIPE_LINK_RULES.md`(Phase 1 はスタブと決定事項)を Phase 2 でコードより先に書く。
  外の製品(Net・Pipe Mania)との対応 — 何を同じにし何を変えたかを出典と確認日つきで — は
  BRAND.md の言う「比較対象との対応」の節(仕様の §14)、Bridges / Loop Puzzle / Number Path との
  比較表(盤に書くもの・手がかり・解の形・操作・Hint の根拠)は仕様の §15。比較表では推論が
  重なることを正直に書く — 閉路と孤立の排除は Loop Puzzle T1 の「ループの規則」と Bridges T3 の
  「閉じたグループの回避」、仮定 1 回は Loop Puzzle T3・Bridges T4 と同じ型。i18n 節に来歴
  (`en` が原文、`ja` と 12 言語は AI が書いて未読)。共有ファイルは Phase 4 で: GAME_LIFECYCLE.md
  「CPU 探索」に Pipe Link の形(探索はタップのときだけ、読み込みでは走らない)。
  `src/i18n/unreadCatalogs.test.ts` の `UNREAD_JA_GAME_IDS` の `pipe-link` は Phase 1 で足した。
- **リスク**: ① 論理の棚の 16 本目で、推論が Bridges / Loop Puzzle と重なる(違いは「書くのは

  緩める前にルール文書を先に直す)。⑤ グリフ `┣` は罫線素片で、全角の CJK フォントへ落ちる端末では
  中心がずれうる(registry のコメント。予備 `⊢`)。⑥ 題「Pipe Link」と同名の作品の確認はまだ
  (Unblock Puzzle と同じく正式収録の前に)。

**未決事項(Phase 2 でルール文書に決める。推奨つき)**:

- 崩し方「型ごとに別の向きへ崩す」の読み方。全タイルを解と違う向きにする読み方だと、直線(取りうる向きが 2 つ)は初期の向きの反対が答えだと分かり、端・エルボ・T も候補が 1 つ消える(初期配置から答えが漏れる)。推奨: 各タイルを型の取りうる向き(直線 2・ほか 4)から seed で一様に選び、解と同じ向きのままのタイルも許す。そのうえで完成済み(全点灯)と、解と同じ向きのタイルが 60% を超える盤を捨てる。60% は初期値として扱い、崩した盤の分布を測ってルール文書に書く。
- 「Medium = L2 以上」の範囲。推奨: Medium は L2 が要り L3 は要らない盤(L1〜L2 で全部決まる)、Hard は L3 が要る盤として、帯を重ねない(Bridges の Medium が T4 を使わないのと同じ考え方)。8×8 で L3 の要る盤の通過率が低く同梱盤面へ落ちる率が上がるなら、予算や帯を緩める前にルール文書を先に直す。
- Hint が読む盤と順序。仕様の「Loop Puzzle §6 と同じ順」は、節は正しい(LOOP_PUZZLE_RULES.md §6 = Undo と Hint)が、同じ順が成り立つのは第 2 段(技法)→ 第 3 段(解の 1 つ)だけ。§6 の第 1 段(解と違う印を先に示す)には対応物が無い。またタイルの向きはプレイヤーの主張ではない(タイルロックが無い)ので、Loop Puzzle のように見えている印を前提として読めない。推奨: 技法は型だけの盤から回し、その推論の順(L1 → L2 → L3)で最初に出てくる「今の向きが解と違うタイル」を示す。出荷する盤面では解の段に落ちないことを、空の盤から Hint だけで解き切るテストで確かめる。
- 盤の端の折り返し(wrap)。仕様に明記が無い。推奨: v1 は折り返さない。閉じた端は L1 の足場で、Easy を L1 だけで解ける盤にするのに要る。§14 相当の節で、外の同じ形式との差分として書く。
- 水源のタイル: 回るか、どこに置くか。推奨: 水源は形の印が付いた普通のタイルで、ほかと同じく回す(固定すると 1 枚だけ規則が違うことになる)。位置は seed で中央寄りのマスから選び、全域木の根にする。Phase 2 で生成の分布を見て決め、ルール文書に書く。
- デイリーの統計の数え方は前例 3 本でそろっていない(Unblock Puzzle と Loop Puzzle は Medium に数え、Bridges は別の枠。オーナーの確認待ち)。推奨: オーナーが 1 つの規則を決めるまで、Pipe Link は Bridges と同じ別の枠にする。分けた数は後で足せるが、混ぜた数は後から分けられない。どちらの規則でも、正式収録でスキーマを凍結する前にそろえる。
- 結果カードの第一ボタンと統計・結果の文言も前例でそろっていない(オーナーの確認待ち)。推奨: 決まるまでは論理の棚の隣人 Loop Puzzle / Bridges と同じく「同じ盤面で再挑戦」(Pipe Link では初期の向きへの Restart)を第一、New Board を第二にし、文言は Bridges に合わせる。4 つ目の形を作らない。
- 右クリック契約の参照の確認。「Minesweeper / Nonogram の右クリック契約」のうち、ペンのバレル(`button` 2 / `buttons` 3)は NONOGRAM_RULES.md §3 だけが持つ形。同じ節が「バレルボタンは Nonogram だけが持つ」と明記しており、Minesweeper は pen の contextmenu を無視してバレルを持たない(MinesBoard.tsx)。推奨: ルール文書では、単発の右クリック・長押しの contextmenu の無視・盤全体のメニュー抑止は両方に、バレルは Nonogram §3 に帰して書く。右ドラッグ(Nonogram の #130)は持たない。
- 節番号「§14 / §15」の確認。BRAND.md の言う §14「比較対象との対応」は練習セット(Crown Grid / Number Path 等。§14 が意図的な差分)の構成。前例の Loop Puzzle / Bridges は §14 が i18n、§15 が意図的な差分で、外の製品と既存ゲームの比較を両方そこに置いている。推奨: 計画とルール文書は番号ではなく節の名前で指す。構成は Loop Puzzle / Bridges に合わせ、「意図的な差分」の下に「比較対象との対応(出典と確認日)」と「関連する既存ゲームとの違い(比較表)」を置く。
- 題の確認。「Pipe Link」と同名・近い名のアプリや作品があるかは、このタスクでは調べていない(ネットワーク不可)。推奨: UNBLOCK_PUZZLE_RULES.md 冒頭の「題の確認」と同じ形で、比較した製品と理由をルール文書に書き、正式収録とストア掲載の前にオーナーが判断する。
- タッチの長押しの後の click の扱い。長押しには意味が無いが、離した後にブラウザが click を出すかどうかは環境で違いうるので、長押しが「時計回り 1 回」になったりならなかったりする。推奨: Minesweeper の長押しと同じしきい値で印を付け、長押しの後の click では回さない(「長押しは何もしない」で一貫させる)。Android の Chrome と iOS の Safari の実機で確かめてからルール文書に書く。
- 9×9 を外す根拠の数値の確認。仕様の「360 幅で 34px 未満」は見込みの値。実測は Bridges §13 の「360×640 の 9×9 は 1 マス 34.0px」だけで、これは幅ではなく、広告の予約 116px を引いた高さで決まった値で、下限 34px を割ってはいない(張り付いている)。推奨: v1 で 9×9 を出さない判断は変えない(タイルそのものが的で広げられない)。ルール文書には根拠を「下限に張り付く」と書き、Phase 3 で 8×8 の実際の 1 マス(360×640・640×360・320 幅)を測って書く。

## 50. Bounce Up(`bounce-up`)

足場に乗るたびに自動で跳ね、左右に動いて上の足場へ登っていく縦長 1 画面のアーケード。入力は
左右の移動だけで、ジャンプのボタンは無い。記録は登った最大の高さ。提案時の仮名は Cloud Climb
(改名の理由は冒頭のオーナー判断 3)。アーケードの棚の 6 本目で、Bunny Hop・Snake に続く 3 本目の
エンドレス記録型である。重力・初速・最高水平速度の値と踏破の数字は、提案時の使い捨て試作で出たもの。
ルール文書には初期値として書き、実装で再現して実機で決めるまで「検証済み」と書かない。

- **規則**: 論理盤面は 360×640(Sky Fighter §1 と同じ大きさ)。主人公は、落ちている間に足場の上面を
  横切ったときだけ乗って自動で跳ねる。下からはすり抜ける。左右の端は反対の端へつながる。カメラは
  主人公が登ったときだけ上へ進み、下がらない。画面の下端より下へ落ちたら `over`。**画面は自動では
  上へ流れない**ので、同じ足場で跳ね続ければ落ちない。急かす仕組みは持たない
  (PRODUCT_PRINCIPLES.md「タイマープレッシャーを既定にしない」)。難しさを決めるのは、高さとともに
  伸びる足場の間隔と種類だけで、速さは変えない。スコア = 到達した最大の高さ(点への換算はルール文書で
  決める)。はねる足場は v1 では作らない。
- **モードと状態**: Endless のみ。デイリーは作らない(Bunny Hop §13 と同じ理由。生成は seed で決まる
  ので後から足せる)。設定は足場の幅 Normal / Wide(1.5 倍)の 1 つだけ。選んだ幅は `bo.prefs` に残り、
  次のランから効く。既定は Normal で、選ばなくても始められる(Snake §7)。記録は幅ごとに分ける。
  状態は `ready`(最初の入力まで世界は止まる — Bunny Hop §2)→ `running` ⇄ `paused` → `over`。
  バックグラウンド(`visibilitychange` の hidden・native の pause)と Back で `paused` になり、
  **復帰してもタップまで再開しない**(Snake §6 と同じ)。Bunny Hop は画面が見えると走りを再開する
  (`BunnyBoard.tsx` の visibilitychange)ので、ここは意図的な差分になる。止めるときは、押しっぱなしの
  入力(キー・◀ ▶・ドラッグ)を捨てる。途中保存は無いので、画面を離れればランは終わる(Back の
  正確な扱いは Phase 2 で決める)。
- **操作**:
  - 相対ドラッグ(Sky Fighter §3 の形を左右だけにしたもの): 指の移動量を、盤面上の見た目で 1:1 に
    目標の x へ写す。体は最高水平速度で目標を追う。目標と体の差には上限を置き、指を止めた後も体が
    流れ続けることを防ぐ。盤のどこから触れてもよい(指が主人公を隠さない)。折り返しをまたぐときの
    目標の扱いはルール文書で決める。
  - ← → / A D は押している間だけ動く。タッチ端末では、盤の下の左右に ◀ ▶ を重ねる(押している
    間だけ動く、名前付きのボタン)。「タッチ端末」を見分ける前例はリポジトリに無いので、Phase 3 で決める。
  - ドラッグと ◀ ▶ は、`onPointerUp` を聞く要素で `onPointerCancel` も聞き、記録に `pointerId` を
    持たせる(ARCHITECTURE.md「指を取り上げられたときの契約」「押下の記録は誰のものか」)。
    `onPointerMove` と `setPointerCapture` を使うので、`pointerContractWiring.test.ts` の除外
    (Bunny Hop)には当たらない。
- **物理**: Pure TS の `step(state, input)` で、固定ステップは 1/120 秒。1 フレームに持ち越すステップには
  上限を置く(背景から戻った直後に大量のステップを回さないため)。重力 1800 px/s²・初速 760 px/s・
  最高水平速度 600 px/s は**初期値**で、実機の手触りで決める。この値での頂点は v²/2g で約 160px になる
  (計算であって実測ではない)。乗ったかどうかは、前のステップと今のステップの足の位置から、上面を
  横切ったかで判定する(速く落ちてもすり抜けない)。同じ seed と同じ入力列からは同じランになる。
- **生成**: 足場 i は (seed, i) だけで決まる(Bunny Hop §5 の `${seed}:obstacle:${連番}` と同じ形)。
  段差は step(i) で、y はその前置和のキャッシュから読み、x は整数にする。座標を積み上げないので、
  高く登っても位置がずれない(Bunny Hop §1 と同じ考え)。各段に固体の「安全鎖」の足場を 1 枚置く。
  動く足場(300 以降)と消える足場(600 以降)は鎖の外にだけ置く。動く足場は三角波で動かす。区分線形
  なので、実装によって近似が違いうる `Math.sin` を使わずに golden を固定できる。鎖の水平距離は高さと
  ともに連続に伸ばす(例 110 → 170px)が、必要な水平速度が最高速の 7 割を超えない範囲にとどめる。
  不変条件は「段差 ≤ 頂点の高さの 82%」と「鎖の水平距離 ≤ 上限」。seed はランごとに新しくする
  (Bunny Hop と同じ。`game/` は時計も `Math.random` も読まない)。生成は作り直しを持たない構成法にして、
  1 枚あたりの仕事量を定数に抑える(Snake §8 と同じ形 — 上限を超えて回る経路を作らない)。足場の種類は
  色だけでなく形でも見分けられるようにする。足場を雲に見せる見た目は残してよい。
- **助け**: Undo と Hint は作らない。遊びの中身がリアルタイムの反射で、盤面に隠れた情報も無いから
  (Bunny Hop §8・Snake §9 と同じ理由)。代わりの無料・無制限の助けは、**即時リトライ**(確認も待ち時間も
  広告も無い)と **Wide**。コンティニュー・復活・パワーアップ・ジェットパックは作らない。
- **保存と統計**: キーは `bo.stats` / `bo.flags` / `bo.prefs`。スキャフォールドの 2 つに `bo.prefs` を
  足し、自分の `gameKeys.test.ts` の 1 行も直す。**ランの途中保存は作らない**(Bunny Hop §10 と同じ)。
  そのため `saveGame` も `storage/gamePersistence.ts` も無く、Root は `entry` を受け取らない
  (ショートカットはゲームのホームへ。`src/test/shortcutResumeWiring.test.ts`)。デイリーが無いので
  2 スロット規則は関係しない。`bo.stats` の中身は次のとおり。
  - `played`: `ready` → `running` で 1 回数える(Snake §10)
  - 幅ごとの最高
  - 累計
  - `totalPlaySeconds`: `running` の間だけ数える

  **途中で離れたランの到達高も、最高と累計に入れる。**Bunny Hop(§10)も Sky Fighter(§10「離れた場合、
  そのランは破棄される」)も離れたランの点を捨てるので、ここはアーケードのどの前例とも違う意図的な差分になる
  (近いのは Sky Fighter §9 の「失敗したランの得点も立つ」だが、あれは終わったランの話で、離れたランではない)。バックグラウンドでも、
  そこまでの秒と到達高を書く(OS がそのまま終わらせても失わないため)。到達高も秒と同じ bookedRef 方式で、
  差分だけを足して二重に数えない。終局・↻・退出・バックグラウンド・アンマウントは、同じ 1 本の計上を呼ぶ
  (GAME_LIFECYCLE.md「計上の経路を増やさない」)。門は `unmountBookingWiring.test.ts`。計上の置き場所は、
  アーケード 4 本の形(盤面の cleanup の `flushSeconds()`)か、スキャフォールドの
  `useOnUnmount(syncActiveGame)` のどちらか 1 つにする。毎フレームは書かない。

- **画面と寸法**: 使える高さから ResizeObserver で幅を導き(9:16)、盤を縮める。広い画面では高さに
  合わせる(上限はルール文書で決める)。Sky Fighter の `.sf-canvas`(`width: min(100%, 360px);
max-height: 100%`)は流用しない。幅を決めたまま高さだけを縮めるので、縦につぶれる。下限は、360×640 で
  Web の広告予約 116px を込みにしても、主人公の上に足場が 2 段以上見えること。計算上、ヘッダ 64 と
  予約 116 を引いた盤は高さ 460px 以下・幅約 259px 以下になる(余白と safe area を引く前)。実測の表は
  Snake §13「寸法」の形でルール文書に書く。
- **UX**:
  - 描画は Canvas + RAF(アーケード 4 本と同じ)。RAF は `running` の間だけ回す。`ready` / `paused` /
    `over` / バックグラウンドではループを止め、1 回描くだけにする。
  - スコアと自己ベストは、canvas とは別に読み上げ用の値も置く。結果と記録の見せ方は、Bunny Hop
    (コース上の数字と旗)とは別の形にする。
  - `over` の後は、止まった盤を約 1 秒見せてから結果カードを出す(`ui/useResultReveal.ts`。Reduced Motion
    では即時)。結果カードの中身は、到達高・その幅の自己ベストとの差(`BestDelta`)・`ShareAction`
    (`outcome="played"`)・即時リトライ・ホーム。
  - 称賛語は出さない(PRODUCT_PRINCIPLES.md「手応えは、盤面に既に見えている事実をもう一度言う形に
    限る」)。スキャフォールドの `bounceUpResultTitle` の "Nice work" は置き換える(どのスキャフォールドも同じ — 共通要件)。
  - 上部バーの ↻ は即時リトライにする。`tryAgain` のラベルも `RestartDialog` も使わない(Bunny Hop の
    `bunnyRunAgain` と同じ。`restartDialogWiring.test.ts` がアーケードに許している形)。共通要件に書いた
    アーケードの形で、ルール文書の意図的な差分の節にも書く。
  - Reduced Motion では、遊びに関係しない動き(背景の雲・着地のつぶれ・消える足場のフェード)だけを
    止める。カメラ・跳ね・動く足場は止めない(Bunny Hop §12)。
  - 音は `services/sound.ts` の既存の合成音だけを使い、鳴らす場所はルール文書で決める。盤面には
    翻訳の要る文字を置かない。
- **i18n**: キーの接頭辞は `bounceUp*`。`en` が原文で、`ja` と他 12 言語は AI が書いたもの。作者も
  ネイティブもまだ読んでいない(ルール文書の i18n 節に書く)。高リスク文言は足さない。
  `src/i18n/unreadCatalogs.test.ts` の `UNREAD_JA_GAME_IDS` の `bounce-up` は Phase 1 で足した。
- **テスト**: 共通の 10 種のうち ⑧ は無い(Undo / Hint を作らないため)。足すものは次のとおり。
  - 物理の単体: 頂点の高さ・落ちているときだけ乗る・下からすり抜ける・折り返し・持ち越しの上限
  - 状態遷移: バックグラウンドと Back で `paused` になる・復帰しても止まったまま・押しっぱなしの入力を
    捨てる
  - 生成の決定性と golden: `game/compatibility.test.ts` が、golden seed の足場列と、固定した入力列の結果を
    固定する
  - 不変条件の性質テスト: 多数の seed × 段で確かめる
  - 自動操縦(最高速の 3/4)で 200 seed × 2000 段を踏破する: 仕事量(ステップ数)を出力し、重ければ
    遅いテストに分ける。提案時の試作で出た踏破の数字は、ここで再現するまで検証済みと書かない
  - 計上: N 秒遊ぶ → アンマウント → N 増える → 再マウントしても増えない。離れたランの到達高が最高に
    入り、バックグラウンドの後に終局しても累計が二重にならない
  - 破損した stats・prefs を拒否する
  - `BounceUpRoot.leak.test.tsx`: Canvas スタブでループを回し、RAF・リスナー・ResizeObserver・DEV シーム
    `__boFrame` が消えることを確かめる。手でフレームを回すテストは `stubAnimationFrames()` を使う
  - ドラッグと ◀ ▶: `pointercancel`・2 本目の指・残るクリック、キー操作
  - `gameKeys.test.ts`
- **文書**: `docs/BOUNCE_UP_RULES.md` を Phase 2 でコードより先に起こす。
  - 意図的な差分の節に、既存 3 本との違いを書く。Bunny Hop とは、復帰で再開しない・離れたランも記録
    する・左右の相対ドラッグ。Snake とは、途中保存をしない(空中の実時間の状態は、マス目の離散状態の
    ようには正直に戻せない)。Sky Fighter とは、左右だけで射撃が無い。
  - 比較の節(BRAND.md が言う「§14 比較対象との対応」に当たる節)に、このジャンルの代表作
    (Doodle Jump)と何を同じにし、何を変えたかを、出典と確認日つきで書く。
  - `store/listing.md` の使用禁止表現に `Doodle Jump` を足す。共有ファイルなので Phase 4 で足す(Phase 1 では
    足していない)。Bounce Up の名前は正式収録まで書かない。
  - Phase 4 で、GAME_LIFECYCLE.md の「Web 先行公開の 5 本の形」の一覧に、Bounce Up のループ(RAF は
    `running` の間だけ)を並べる。
- **リスク**:
  - 3 本目のエンドレス記録型なので、結果と記録の見せ方を Bunny Hop と同じにしない。

  - 横向きの電話(Web だけ)では、予約の 116px を引くと盤が極端に小さくなる。最小の高さと、それを
    下回ったときの扱いを実測し、ルール文書に書く(Snake §13 の 568×320 と同じ書き方)。
  - 横ドラッグが、ブラウザや OS の画面端スワイプ(戻る)と重なる恐れがある(未確認)。盤の左右に余白を
    残し、どこからでもドラッグを始められる形にして和らげる。
  - 「Bounce Up」という名前の商標と同名の作品は、まだ調べていない。

**未決事項(Phase 2 でルール文書に決める。推奨つき)**:

- Back の扱い: 仕様は「Back で paused」と言うが、途中保存が無いので、離れればランは終わる。推奨は次の 3 つ。(1) ゲーム内の ← と Web のブラウザの戻る(アンマウント)は、到達高を計上してからランを終え、確認なしでゲームのホームへ戻す(Sky Fighter §10・Bunny Hop と同じ)。(2) 正式収録後のハードウェア Back(唯一の持ち主は GameContext)は、running 中の 1 回目では paused にするだけにし、paused から押したらホームへ。横ドラッグが端からのスワイプの「戻る」と重なりうるので、1 回の誤操作でランを失わないようにする。(3) Web ベータで効くのは (1) だけ、とルール文書に書く。
- ウィンドウがフォーカスを失った(blur)ときも止めるか: 推奨は止める(Snake §6 と同じ。PC のキーボードの人が別のウィンドウへ移り、戻ったら落ちていた、を起こさない)。アーケード 4 本(Bunny Hop など)は止めないので、意図的な差分としてルール文書に書く。
- 明示的な Pause の操作: 仕様には paused の状態はあるが、止めるボタンが無い。推奨は、上部バーに ❚❚ を置くこと(Snake §6 と同じく無料・無制限・確認なし)。再開は盤のタップか Resume か Space。ボタンにフォーカスがあるときは、ボタン自身のキー操作に任せる(Bunny Hop §3)。
- 高さの点への換算・「累計」の中身・記録の見せ方: 推奨は次のとおり。点 = 論理 px を一定の係数で割った整数とし、単位の語(m など)を付けない(訳が要り、実寸でもないため。係数は Phase 2 で決める)。累計 = 各ランの到達高の和とする。スコアは上部バーに DOM で出す。自己ベストは、ラン開始時点の最高の高さに、盤を横切る細い線として描く。これで Bunny Hop のコース上の数字・旗とは形が分かれる。
- 動く足場の「300 以降」と消える足場の「600 以降」の単位、および消え方: 推奨は単位を段の番号 i にすること(生成が (seed, i) の純関数のまま決まる)。消え方は「1 回跳ねたら消える」とし、時間では消さない。時間で消えるものは急かす仕組みになるため(Snake §15 が時間で消える食べ物を退けたのと同じ理由)。
- 安全鎖の水平距離に折り返しを含めるか: 推奨は、折り返しを使わない直接の距離で上限(例 170px)を守ること。折り返しを知らない人も必ず登れ、折り返しは近道としてだけ効く。ドラッグの目標は折り返さない連続の座標で持ち、描画と当たり判定のときだけ幅の剰余を取る。
- 音: 推奨は、着地ごとには鳴らさないこと(およそ 1 秒に 1 回の一定の拍が鳴り続けるため)。鳴らすのは over の gameOver だけにし、必要なら消える足場で select を鳴らす。services/sound.ts には新しい音を足さない。
- ◀ ▶ を出す条件: リポジトリに「タッチ端末」の判定の前例が無い。推奨は CSS の @media (any-pointer: coarse) で出すこと(JS で判定しない)。キーボード付きの iPad と、タッチ付きの PC で実際に見て確かめる。
- 名前「Bounce Up」の確認: 改名の理由は同名作の存在だったが、新しい名前はまだ調べていない。推奨は、Phase 4 の前に Bubble Pop と同じ程度の軽い商標・同名作の調査をすること(BUBBLE_POP_RULES.md 冒頭、2026-08-13)。結果は日付つきでルール文書の冒頭に記録する。

## 51. Echo Pads(`echo-pads`)

光って鳴るパッドの順番を覚え、同じ順番にタップして返す記憶ドリル(一般に Simon と呼ばれる形式。
製品名はルール文書の比較の節にだけ書く)。drills の棚で最も近い Number Recall とは、提示が時間軸に
並ぶ・同じパッドが何度も出る・音がある、の 3 点で分かれる。収録で唯一**端末が再生を進める**
タイトルで、オーナー判断 2 の条件の中でだけ認めた例外である。

- **規則**: パッドは 4 枚(2×2)か 6 枚(2×3)。run ごとに seed から目標長の固定の列を 1 本作り、
  ラウンド k ではその先頭 k 個を再生する。長さ 3 から始め、正しく返すたびに k が 1 増え、目標長を
  返し切ればクリア。入力に制限時間は無い。1 つでも違えば run はそこで終わる(警告音・赤い明滅・
  振動は出さない。`sounds.invalid()` / `sounds.gameOver()` も使わない)。失敗の後は押すべきだった
  パッドを形の印で示す案(Number Recall §4 の開示と同じ形)。再挑戦は同じレベルの**新しい列**
  (seed の attempt を +1。Number Recall §4・§8 と同形 — 同じ列なら記憶ではなく直前に聞いた答えの
  再生になる)。
- **再生(判断 2 の例外)**: ▶ のタップでだけ始まり、ラウンドが進んでも自動では始めない。再生中は
  いつでも Stop でき、その間パッドは押せない。聞き直しは無料・無制限で、許すのは「そのラウンドの
  最初のタップの前」と「失敗の後」(失敗したラウンドの列を何度でも。開示に時間制限を置かない —
  Number Recall §4)だけ。Pace は Calm / Normal / Quick(`ep.prefs`。再生していない間に替える)で、
  **列が長くなっても速くしない**。周期 400ms 以上(Quick でも。明滅は 1 秒に 2.5 回まで —
  WCAG 2.3.1 の 3 回を下回る)・消灯 120ms 以上・同時に光るのは 1 枚、を定数にしてテストで固定する。
  ルール文書に例外と理由(見終わってから返す記憶は、見る回数をプレイヤーが決められるので
  「急かさない」を保つ)を、Memory Match §3 / Number Recall §3 の「覚える時間を端末が区切らない」
  との関係とともに書く。Number Recall §10 は「もう 1 回だけ見る」を、後から売り物にできる形として退けている。
  聞き直しは無料・無制限で、回数の上限も売る口も無いのでその形にならないことも、同じ節に書く。
- **モード**: Levels — 4 パッド / 6 パッドの 2 段 × 目標長 4〜14 の 22 レベル。2 段とも最初から開き、
  段の中は順に解放(解放済みはいつでも選び直せる)。9 パッドは Number Recall の 3×3 と同じ帯に
  なるので作らない。Daily — 6 パッド・目標長 10・今日の 1 問(過去日なし・ストリークなし)。
- **操作**: パッドは位置と印を読み上げる `<button>`。▶ と Stop は同じ位置の 1 つのボタン。
  キーボードは数字キー(読み順)でパッド、Space / Enter で ▶ / Stop(案。ダイアログが開いている間は
  Escape に答えない)。押した瞬間に光らせるために `onPointerDown` を使うなら pointercancel を配線し、
  自分のテストを置く(`pointerContractWiring.test.ts`)。副操作が無いので右クリック契約は持たない。
- **生成**: seed は `echo-<段>-<目標長>-r<attempt>`、デイリーは `echo-daily-<YYYY-MM-DD>`(失敗後の
  attempt の付け方は未決)。品質フィルタ(同じパッドの 3 連続なし・偏りの上限・単調な並びの回避)を
  最大 24 回の再抽選で通し、通らなければ最後の候補を採る — 仕事量は必ず有限で、フィルタは不変条件
  ではなく通過率として測る。Number Recall §6 / Schulte §6 の「配置に制約を課さない」と逆の結論
  なので、理由(時間軸の列では 3 連続や順送りが記憶ではなく数えやなぞりになる)をルール文書に書く。
  フィルタは列全体にかけるので、短い先頭(k = 3〜5)の偏りは別に測る。探索は持たない。再生の
  時刻表(列と Pace → 各パッドの点灯・消灯の時刻)は `game/` の純関数にし、UI はそれを
  `setTimeout` 1 本の鎖でなぞるだけにする。
- **助け**: 聞き直し・Pace・即時の再挑戦(すべて無料・無制限)。作らない: Undo(タップは記憶の主張
  そのもの — Number Recall §10)・次を光らせる Hint(答えそのもの)・ライフ・復活。
- **保存と統計**: `ep.saveGame` / `ep.saveDaily`(2 スロット規則)/ `ep.progress` / `ep.stats` /
  `ep.flags` / `ep.prefs`。run はラウンドの境目で(段・目標長・attempt・k・デイリーの日付・経過秒)
  と「入力を始めたか」を書き、列は seed から作り直す。入力を始める前に離れた run の復元は「ラウンド k の
  最初のタップの前」に立ち、▶ で聞き直せる — Number Recall §12 が途中保存を持たない理由(短期記憶は
  戻らない)はここでは成り立たないので保存する。この差をルール文書に書く。**入力の途中で離れた run は、
  復元で ▶ を出さずに入力から(先頭から押し直して)続ける**(判断 8 の (B)。聞き直しの条件を離れても守る)。
  押した位置は書かない。失敗は同じ操作の中で
  スロットを消す(再読み込みで失敗を取り消せない)。fail-closed: 段・目標長・k(3〜目標長)・attempt の
  範囲外、未解放のレベル、スロットとモードの不一致(`expectedMode`)、日付の過ぎたデイリー。記録は
  「クリアしたレベル」とデイリーの達成日(最初の完了で確定)だけ。聞き直しの回数は結果の
  事実としてだけ出す(少ない聞き直しを記録にすれば、無料の聞き直しを使わせない圧になる — Schulte §9 と
  同じ理由)。仕様は間違いの回数も同じ扱いにしているが、判断 2 で 1 回の run の間違いは常に 0 か 1 になるので、
  結果に出すかは未決(下の未決事項)。統計は段別の played / cleared / 総プレイ秒(案)。中断中の run がちょうど 1 つなら
  ショートカットで直接開くが、開いても再生は始めない(`entry`・`shortcutResumeWiring.test.ts`)。
  プレイ時計は `playClockSeed.test.ts`、退出の同期は `useOnUnmount(syncActiveGame)` を 1 回。
- **UX**: 360×640(Web は広告の予約 116px 込み)で 2×3 のパッド・▶ / Stop・長さ(k / 目標長)が
  スクロールなしに収まる。パッドは形(1 枚ごとに別の印)と位置で見分け、色はアクセントの濃淡などの
  補助にとどめる。赤緑青黄の 4 象限・扇形は使わない。点灯も形の変化で示し、Reduced Motion では
  フェードだけを消す(点灯は情報なので残す)。再生はバックグラウンド(visibilitychange の hidden・
  native の pause)・`blur`(Snake §6 と同じ)・Back・ダイアログで止まり、戻っても再開しない。
  リスナーは effect の中で張り、module レベルに置かない(GAME_LIFECYCLE.md)。音は Phase 3 で
  `services/sound.ts` にパッド 1 枚 1 音を既存の五音階(`LADDER`)から足し、既存の音は変えない
  (6 枚では同じ音名のオクターブが 1 組入るので、聞き分けを確かめる)。各音は点灯の瞬間にタイマーから
  鳴らし、音声の時計に先の音を積まない(Stop・アンマウントの後に何も鳴らない)。音を消しても遊べる。
  ヘッダの ↻ は置かない案(Number Recall と同じ。置くなら `RestartDialog` は retry だけ)。結果は
  `useResultReveal` で一拍置き、`ShareAction` を載せる。
- **テスト**: 前例の 10 種に加えて、時刻表の定数(周期・消灯・同時 1 枚)を全 Pace × 全長さで、
  ラウンド k の列がラウンド k+1 の先頭であること、再生中のタップと入力中の ▶ を受けないこと、
  失敗 → attempt +1 の新しい列、フィルタの通過率と最後の候補に落ちた数(22 レベル × attempt の幅と
  1 年分のデイリー。数はルール文書の「検証の範囲」へ)、入力前に離れた run の復元が最初のタップの前に
  立つこと、入力中に離れた run の復元が ▶ を出さずに入力に立つこと(判断 8)、失敗でスロットが消えること。`ui/EchoPadsRoot.leak.test.tsx` で、再生中のアンマウント・Stop・hidden の後に
  timer / listener が残らないことと、偽の AudioContext(`sound.test.ts` の形)で Stop の後に鳴る音が
  無いことを見る。`sound.test.ts` は既存の音の周波数が変わらないことを保つ。
- **文書**: `docs/ECHO_PADS_RULES.md` を Phase 2 でコードより先に書く。判断 2 の例外と理由、
  Number Recall / Memory Match / Schulte Table との違いの表、ジャンル原則(Schulte §14)の 1〜5 を
  引き継ぐこと — §14-5 の「点滅を作らない」は急かす演出のことで、提示そのものの点灯とは別だと
  明記する。意図的な差分の節の「比較対象との対応」に、Simon(Hasbro)と何を変えたか(4 色の扇形・
  ブザー・自動の加速を持たない)を確認日つきで書く(BRAND.md「自社タイトルと比較対象の名前」)。
  i18n 節に `en` が原文、`ja` と 12 言語は AI が書き未読と書く。GAME_LIFECYCLE.md の「Web 先行公開」の
  列挙への追記は Phase 4。
- **リスク**: Number Recall との近さ(違いの 3 点をルール文書の表で示す)。Simon の見た目・音・加速を
  複製しない。効能の主張(「記憶力が上がる」等)は `check-principles.sh` §7 が英日だけで落とし、
  12 言語は見ない。iOS 実機での音の遅れは未確認で、消音スイッチで WebAudio が鳴らない可能性も
  未確認 — 音なしでも遊べることが前提。`sound.ts` は 30 秒のアイドルとバックグラウンドで suspend
  するので、AudioContext の生成・resume は最初の ▶ だけでなく ▶ のたびに同期で行う必要があるが、
  いまはそのための公開の口が無い(未決)。再生の各点灯を aria-live で読むと数百 ms の周期に
  収まらない恐れがある(Phase 3 で読み上げ機能を使って決める)。

**未決事項(Phase 2 でルール文書に決める。推奨つき)**:

- Number Recall の参照: 仕様の「Number Recall §4 と同形」は半分だけ正しい。§4 が言うのは「同じレベルの新しい配置で再挑戦する」ことだけである。attempt を含む seed(`recall-level-<n>-r<attempt>`)とその理由は §7・§8 にあり、デイリーの形(`recall-daily-<date>-r<attempt>`)は §9 にある。推奨: 「§4・§8」と書く(この節ではそう書いた)。
- デイリーの再挑戦の seed: 仕様は `echo-daily-<日付>` としている。しかし判断 2 は、失敗の後に新しい列を出すことを求めている。推奨: `echo-daily-<YYYY-MM-DD>-r<attempt>` にする(Number Recall §9 と同じ形)。記録は最初の完了だけで確定する。
- デイリーの保存スロット: 仕様が挙げているのは `ep.saveGame` だけである。計画の共通要件と `docs/architecture/storage-keys.md` は、デイリーを持つゲームの中断を 2 スロットにする(`src/test/savedGameSlots.test.ts` は keys.ts に `dailyGame` を持つゲームを検査するだけで、足すことは強制しない)。推奨: `dailyGame: 'ep.saveDaily'` を足し、`expectedMode` と `storage/slots.test.ts` を用意する。キーは `ep.saveGame` / `ep.saveDaily` / `ep.progress` / `ep.stats` / `ep.flags` / `ep.prefs` になる。
- 「間違い回数」と「入力を先頭に戻す」: 判断 2 では、run は最初の間違いで終わる。そのため 1 回の run の間違いは常に 0 か 1 になる。仕様にある「入力を先頭に戻す」は、判断より前の案の名残に見える。推奨: 判断 2 を正とする。結果には到達した長さと聞き直しの回数を出し、間違い回数は出さない(統計は失敗した run の数で足りる)。聞き直しの数え方もルール文書で決める(例: そのラウンドの 2 回目以降の ▶ だけを数え、失敗後の再生は数えない)。
- attempt の保存: Number Recall §8 は attempt を保存しないので、開き直すと r0 に戻る。Echo Pads では、失敗したラウンドの列を何度でも聞ける。そのため Web なら再読み込み 1 回で同じ r0 に戻り、固定の列を先頭から少しずつ覚えられてしまう。推奨: レベルごとの次の attempt(と今日のデイリーの分)を `ep.progress` に持ち、Number Recall §8 との差としてルール文書に書く。代案は Number Recall と同じく受け入れ、その旨を記録すること。
- Pace の値と記録: 仕様にあるのは 3 段の名前だけである。推奨: 値は Phase 2 で決める(Quick でも周期 400ms・消灯 120ms の下限を守る)。既定は Normal。Pace で記録を分けず、結果に事実として出すだけにする。Pace を替えられるのは再生していない間だけとする。
- AudioContext の解錠: `services/sound.ts` の `getContext()` は公開されておらず、音を鳴らさずに生成・resume する手段が無い。さらにこの context は 30 秒のアイドル(`IDLE_SUSPEND_MS`)と visibilitychange の hidden で suspend される。そのため「最初の ▶ のタップ内で」だけでは足りない。推奨: Phase 3 で `sound.ts` に公開関数を 1 つだけ足す(例 `primeSound()`。`setSoundEnabled(false)` を尊重する)。▶ と聞き直しのハンドラの中で、毎回同期で呼ぶ。最初の点灯の前には短い間を置き、iOS 実機で遅れを測る。
- ジャンル原則の範囲: Schulte §14 は「脳トレドリル 3 本」(Schulte Table / Number Recall / Quick Math)を対象としており、§14-5 は点滅を禁じている。`check-principles.sh` §7 のコメントも 3 本になっている。推奨: Echo Pads のルール文書で §14 の 1〜5 を自分にも適用すると宣言し、提示のための点灯は急かす点滅ではないと区別を明記する。Schulte §14 の範囲の書き方を直すかは Phase 4 で決める(他のゲームの文書なので Phase 2 では触らない)。
- ヘッダの ↻: 推奨: Number Recall と同じく置かない。再挑戦は、失敗後のパネルと結果カードにある。置くなら `RestartDialog` は retry(新しい列 = attempt +1)だけにし、`newBoard` は渡さない(`restartDialogWiring.test.ts` のレベルの梯子の形)。
- Quick Rules の文案: 仕様の文案は「1) パッドが光って鳴る順番を見て覚える。2) 覚えたら、同じ順番にパッドをタップする。3) 成功するたびに順番が 1 つ長くなる — 時間制限はない。」である。1 行目は ▶ にも聞き直しにも触れていない。このため、例外の条件がチュートリアルに出てこない。推奨: 1 行目を「▶ を押すとパッドが光って鳴る。その順番を覚える(何度でも聞き直せる)」にする。3 行目の「時間制限はない」は残す。
- 名前の確認: Bounce Up は、語の衝突と同名作品を理由に改名した。「Echo Pads」については、同じ確認をした記録が無い(「Echo」は他社の機器名でもある)。推奨: 正式収録の前に、同名作品の確認を記録する。ベータの Phase 2 は止めない。

**フォールバック。**同梱の Nunito サブセット(`@fontsource/nunito` 5.3.0 の latin-700 と latin-800 の woff、230 コードポイント)の cmap を読んだ。`♞ ♜ ❖ ◆ ┣ ⊢ ◠ ⇡ ♪ ♫` はどれも入っていない。既存の記号グリフと同じく `--font-display` の `ui-rounded, system-ui, sans-serif` へ落ちる。この環境で実際に描いたフォントは CDP `CSS.getPlatformFontsForNode` で次のとおり。

- Inter ExtraBold: `❖`(Minesweeper の `◆` も同じ)
- Liberation Sans: `♪ ♫ ♬`

**絵文字の危険。**ローカルに `emoji-data.txt` は無かった(ファイルシステムを探して見つからず)。代わりに Node 22.22 の V8 の Unicode プロパティ(Unicode 16.0、ICU 77.1)で判定した。

- `♞ ♜ ♪ ♫ ♬`: `Emoji` も `Emoji_Presentation` も無い。`Extended_Pictographic` だけを持つ(出荷済みの `♛ ⚅ ⚄ ♡ ♢` と同じ扱い)。U+FE0F を付けても RGI 絵文字にならない。
- `❖ ◆ ◠ ┣ ⊢ ⇡`: 3 つとも無い。
- 対照として測った `♟`: `Emoji=true`、`+FE0F` で RGI 絵文字になる。iOS で絵文字になる理由と合う。`♠ ♣ ♥` も同じ性質。

Unicode データの上では、5 本と予備のどれも絵文字として出る性質を持たない。ただし、Apple Color Emoji や Android の絵文字フォントがこれらの字形を持っていて、フォールバックで使われる可能性は実機で見ていない(未確認)。

**インク。**タイルを撮り、測ったのは次の量だ。

- タイル面積に対する「背景からの輝度差 ÷ 計算済みの文字色と背景色の輝度差」の和(%)
- 縁の 12% の帯は除く
- 色相に関係なく輝度差で測った。新しい 5 本はまだアクセントが無く、シリーズ既定の青(ライト文字 `rgb(63,91,143)`/背景 `rgb(226,232,243)`)で描かれている。最終のアクセントでは値が多少動く。
- この方法で Loop Puzzle の `⬚` は 2.62〜2.73%(16〜17 番目)と出て、前例の 2.62〜2.86% を再現した。

**隣人。**新しい 5 本はどの幅でも棚の最後なので、右と下には何も来ない。左と上は次のとおり(括弧は斜め)。

- **Chess `♞`**(盤ゲームの棚)
  - 2 列: 左 Dots and Boxes `⊡`、上 Dominoes `⊟`(Mancala `⊚`)
  - 3 列: 上 `⊚`(`⊟`)
  - 4 列: 左 `⊡`、上 Yacht `⚄`(Gomoku `⁙`、`⊚`)
  - 5 列: 左 `⊡`、上 `⁙`(Connect Four `⁘`)

  紛らわしい形は無い。同じチェスの駒の Crown Grid `♛` は論理の棚にあり、並ぶのはお気に入り・最近・検索の行だけ。そこでも馬の頭と王冠で分かれる(比較画像で確認)。

- **Gem Swap `❖`**(パズルの棚)
  - 2 列: 上 Unblock Puzzle `⇥`(Peg Solitaire `⁜`)
  - 3 列: 左 `⁜`、上 Sliding Puzzle `⇄`(Water Sort `≋`)
  - 4 列: 上 `≋`(`⇄`)
  - 5 列: 左 `⁜`、上 Number Match `10`(Block Puzzle `▣`、`≋`)

  `◆` の Minesweeper は論理の棚で、棚の中では隣に来ない。並ぶのはお気に入り・最近・検索の行だけ。そこでは、4 つの小さな菱形と塗りつぶした菱形 1 つとして、54px でも 40px の行でも分かれた。最も近いのは 3 列と 5 列で左に来る `⁜`(4 方向へ伸びる十字)。点と線の十字と、塗った菱形 4 枚で分かれると判断した。Gin Rummy の `♢`(輪郭だけの菱形)はカードの棚。

- **Pipe Link `┣`**(論理の棚)
  - 2 列: 左 Bridges `⊶`、上 Loop Puzzle `⬚`(Box Regions `▭`)
  - 3 列: 上 `▭`(`⬚`)
  - 4 列: 左 `⊶`、上 Sudoku 6×6 `6`(Binary Balance `⊜`)
  - 5 列: 上 `⊜`(`6`)

  罫線・枠の印(`▭ ⬚ ▙`)は輪郭の四角か塗った塊で、太い T 字とは分かれる。`┣` は罫線素片なので行の高さいっぱいの縦棒になり(2x で 18×51px)、他より背が高く左寄りに見える。CJK フォントへ落ちる端末(ja 等)では全角の罫線として描かれ、横の棒がタイルの中心から外れる恐れがある(未確認)。

- **Bounce Up `◠`**(アーケードの棚)
  - 2 列: 左 Snake `∿`、**上 Bunny Hop `⌃`**(Sky Fighter `▲`)
  - 3 列: 左 `∿`、上 `▲`(Brick Breaker `≡`)
  - 4 列: 左 `∿`、上 `≡`(Bubble Pop `○`、`▲`)
  - 5 列: **上 `○`**(`≡`)

  電話の既定の 2 列で、跳ぶゲーム同士の `⌃` と `◠` が上下に重なる。同じくらいの太さと幅の「細い上向きの山」で、角と丸の差しか無い(比較画像 `cmp-arcs-*`)。5 列で真上に来る `○` は、`◠` の下を足した形になる。`⇡` は縦の点線の軸と矢じりで、`⌃`・`○`・`▲` のどれとも形が分かれる。

- **Echo Pads `♪`**(ドリルの棚)
  - 2 列: 上 Number Recall `?`(Memory Match `⧉`)
  - 3 列: 左 `⧉`、上 Schulte Table `⌖`(Quick Math `÷`、`?`)
  - 4 列: 上 `÷`(`⌖`)
  - 5 列: 左 `⧉`

  音符に似た印は棚にも全体にも無い。`♫` でも同じ。

**採ったもの。**勧めのとおりにした — Chess・Gem Swap・Pipe Link はそのまま、Echo Pads は仕様の予備 `♫` へ、Bounce Up は `⇡` へ(オーナーの条件とは別の理由なので暫定とし、2026-10-20 の判断 7 で確定)。勧めの理由:

- **Chess**: `♞` のまま。
- **Gem Swap**: `❖` のまま。
- **Pipe Link**: `┣` のまま。
- **Bounce Up**: `⇡` へ替える。仕様の切り替え条件(「薄ければ」)には当たらない。理由は 2 列での `⌃` との見分け。オーナーの書いた条件とは別の理由なので、そう明記して判断を仰いだ(判断 7 で承認)。
- **Echo Pads**: `♫` へ替える。`♪` は 51 本で最も薄く、`◌` を外したときと同じ水準。`♫` で下から 3 本の外へ出るが、`÷` との差は 0.07〜0.24 ポイントしかない。仕様外の候補として `♬`(U+266C、被覆 17、Emoji 無し・Extended_Pictographic のみ)がある。既定のフォールバックで 1.48%(6 番目)、DejaVu Sans で 2.95% で、より安全側。
