# アプリのバナー枠の計測(2026-10-29、正式収録 65 本)

v1.7.0 で Web 先行公開の 20 本を収録したとき、画面の高さから盤を決める 4 本がアプリのバナー枠に潜っていた
([RELEASE_CHECKLIST.md](../RELEASE_CHECKLIST.md)「2026-10-29: 1.7.0」)。それより前に収録したゲームは測って
いなかったので、正式収録の 65 本すべてを同じ方法で測り、重なっていたものを直した記録。方針の正本は
[ADS_POLICY.md](../ADS_POLICY.md)「バナー広告の仕様」(盤・操作ボタンに重ねない、スロットはスクロールする
領域の外)と [ARCHITECTURE.md](../ARCHITECTURE.md)「広告と課金」(`data-sg-app-banner` /
`--sg-app-banner-reserve`)。この文書は計測の記録で、方針ではない。

## 方法

- このブランチの debug APK(1.7.0 の上)を Android 17 エミュレータ(Pixel 7、日本語)に入れ、各ゲームを
  ホーム画面ショートカットと同じ Intent(`?game=<id>`)で開き、ホームのモードのボタン(`.home-actions .btn-big`)を
  1 つずつ押してプレイ画面を開いた(確認ダイアログは「はじめる」、Quick Rules は最後まで進める)。「誰かと遊ぶ」は
  2 台が要るので除いた。65 本で 182 のモード。
- 2 サイズ: 既定の 411×914(ノッチ 52px、下端 24px)と、`wm size 1080x1920` + `wm density 480` の 360×640
  (ノッチ 37px、下端 24px)。終わったら `wm size reset` / `wm density reset`。
- 枠は 64px(既定)と 90px(スマホのアンカー型アダプティブバナーの最大)。エミュレータは広告を描かないので、
  90px は `.banner-slot` の高さを手で変えた(実際の広告と同じく resize は起こさない)。
- WebView の DOM を DevTools(CDP)で読み、次を数えた。
  1. **枠の下**: 盤・ボタン・文字・枠線や背景のある要素で、画面の下端 − 下端の safe area − 枠の高さより下にあるもの
     (祖先の overflow で切られた部分は除く)。
  2. **上部バーの上**: 上部バー(`.game-topbar`)の下端より上へ出た、上部バー以外の要素。
  3. **隣へのはみ出し**: `.game-content` の子(上部バー・盤の領域・操作バー…)の箱から外へ出た中身。自分で
     スクロールする領域は除く(中身はその中で届く)。
  4. 参考: 遊ぶ領域の中でスクロールする量(枠の上で届くが、最初は画面に見えていない)。
- Web 版は、触ったゲームの画面を、公開中のビルド(pixapps-landing `dcb9a887`)・変更前のビルド・変更後のビルドで
  ヘッドレス Chromium(外部への通信は遮断)に開き、360×640 / 390×844 / 412×915 × 広告予約あり / なしで
  要素ごとの箱を突き合わせた。

## 直したもの

どれも各ゲームの CSS(と GameScreen の `<BannerSlot />` の位置)だけで、`:root[data-sg-app-banner]` の下にだけ効く。
Web 版と、広告を削除したアプリには何も変わらない。詳細は各ルール文書の 2026-10-29 の項。

| ゲーム | 原因 | 直し方 |
|---|---|---|
| Bubble Pop | 盤(320×672)を幅いっぱいで描くと高さが入らない | 幅を残りの高さ × 0.476 でも抑える(`--bu-chrome` 156px) |
| Water Sort | 1 本の高さの上限が画面の割合(68%)で、ノッチ・操作バー・枠を見ない。幅の式が列間を 10px で数え、3 段に折れる | 列間を 12px で数え、高さを残りの高さ ÷ 段数でも抑える(`--ws-chrome` 165px) |
| Memory Match | 高さの見積もりが 64px の枠のまま、ノッチを数えない | 見積もりを 78px + ノッチ + 90px + 下端に(`--mm-chrome`) |
| Yacht | 行の高さが固定(42px) | 6 行が残りの高さを分け合う(36〜42px)、680px 以下は詰めた間隔 |
| Light Grid | `BannerSlot` がスクロールする `.game-content` の中 | `.screen` の最後の子へ(盤は縮めない — 90px のとき最大 29px スクロール) |
| Hanoi Towers / Invaders / Maze Escape / Paddle Rally | 同上(測った 2 サイズでは重なっていない) | 同上 |
| Block Puzzle | 高さの見積もりが 64px の枠のまま、ノッチを数えない | 実測の 257px + ノッチ + 90px + 下端に(`--bp-chrome`) |
| Unblock Puzzle | `--ub-chrome` が 64px の枠で数えていた | 90px で数える(326px、横長の広い段は 146px) |
| Reversi / Gomoku / Dots and Boxes | 盤の上限が画面の高さの割合(52% / 58%) | 盤の幅を残りの高さでも抑える(186 / 202 / 186px) |

## 修正後

- 65 本・182 モード・2 サイズ・枠 64px / 90px のすべてで、枠の下・上部バーの上・隣へのはみ出しが 0px。
- Web 版: 触った 21 画面 × 3 サイズ × 広告予約あり / なしの 126 通りで、変更前のビルドと箱が同じ(違いは乱数の盤の
  アイコンと文字幅、Unblock Puzzle のブロック数だけ)。公開版との違いも同じ種類だけ。
- `pnpm verify:changed --base e73b047e`(このブランチの変更だけ): eslint・typecheck・スコープしたテスト
  `Test Files 328 passed | 1 skipped (329)`、`Tests 6013 passed | 1 skipped (6014)`。

## 確かめていないこと

- 実際の広告(高さ、読み込みのタイミング)。90px は手で伸ばした枠。
- 実機、iOS、ほかの画面サイズ(とくに 360×640 と 411×914 の間の高さ、横向き、タブレット)、他の言語の長い文。
- 各ゲームの途中の局面(手札が増えた、行が増えた後など)。測ったのは各モードを開いた直後(または再開した局)。
- Nearby の画面。
- エミュレータの Light Grid のスクリーンショットで、盤の上の帯(列番号)がページの色で塗りつぶされて見える
  (変更前から。DOM のヒットテストでは盤が最前面なので描画の残像と見ているが、実機では見ていない)。

## 残ったこと(この変更の外)

- **Web 版の重なり**: 公開版の Bubble Pop は 360×640 で盤の下半分とトレイが、390×844 でもトレイが 116px の広告予約の
  下にある。Water Sort は 360 / 390 幅でデイリーの棚が 3 段(621 / 829px)に折れ、戻す・ヒントが画面の外に出る。
  アプリ側だけ直したので、Web 版は別の変更で直す。
- **盤が動くこと**: ADS_POLICY は「盤面は決して動かない」と書くが、枠が 64px より伸びると、411×914 では 65 本のうち
  45 本が 13px(中央寄せ)、8 本が 26px(下寄せ)、1 本が 7px 上へ動く(動かないのは 11 本)。大きさは変わらない。
  枠はゲーム画面に入るたびに 64px から作り直され、プラグインは `resumeBanner` のたびに高さを知らせるので、広告が 64px
  より高い端末では入るたびに動く。文の方を直すか、枠を最初から最悪値で取る・前回の高さを覚えるなどで動かなくするかは
  製品オーナーの判断待ち。
- 参考の「遊ぶ領域の中のスクロール」が大きいもの(360×640、90px): Mahjong Solitaire のデイリー 445px、Ludo 161px、
  Minesweeper の むずかしい 157px、Hearts 135px — どれも各ゲームがもともとスクロールする領域として作っているもので、
  枠には重ならない。
