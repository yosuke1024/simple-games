# Mahjong Solitaire / Bubble Pop / Ludo — 検索の頭を取る 3 本の実装計画 (2026-08-08)

コレクションを 30 本にする最後の 3 枠。選定基準は**検索流入**である。進行中の 5 本
(Kakuro / Futoshiki / Takuzu = ロングテールのロジック棚、Hearts / Gin Rummy =
定番カード)がロングテールと中堅を埋めるのに対し、この 3 本は**まだ取っていない
頭キーワード**を 3 つの棚に 1 本ずつ足す: Mahjong Solitaire はパズル棚に
(「mahjong」は月間 67 万件 — Semrush のボードゲーム統計でチェスに次ぐ規模)、
Bubble Pop はアーケード棚に(ジャンル専業ポータルが成立する規模のカジュアル
キーワード)、Ludo はボード棚に(世界合計より配分が特殊で、既にロケールを持つ
hi / id / th / vi / tr の市場で最大級)。

3 本とも生成・対局は端末内で完結し、コンテンツサーバーも外部素材も要らない
([CONTRIBUTING.md](../../CONTRIBUTING.md) の収録条件)。ルールはパブリック
ドメイン(名前の商標は下の「名前」節で個別に扱う — 1 本は名前を変えて収録する)。

検討の経緯: **Chess は見送った。**検索量は月 150 万件で全ボードゲーム中最大だが、
web 検索は chess.com / lichess が固定した壁で実流入が見込めず、まともな対局エンジンの
工数も全候補で最大 — 量ではなく「取れる量」で落ちる。**Word Search 系も見送り**
(14 ロケール分の辞書供給が `machine` 来歴と正面衝突する — 脳トレ計画「単語・
クイズ系への拡張」と同じ理由で棚ごと不可)。**Snake** は Google 検索結果の内蔵
Snake がクリックを吸うため保留のまま(2026-08-06 計画の記録どおり)。**Spades**
は Hearts 計画の検討の経緯で既に見送り(意思疎通できない CPU 相棒)。**Jigsaw**
は写真素材が収録条件に抵触。**Backgammon / Dominoes / Pyramid Solitaire** は
成立するが今回の 3 枠では頭キーワードに負ける — 30 本以後の候補として
フォローアップに申し送る。テトリス型・Yahtzee・UNO は権利で既決
(Checkers 計画の物差し)。

**この文書は着手前の実装計画である。**実装は未着手。仕様の正本は実装時に
`docs/MAHJONG_SOLITAIRE_RULES.md` / `docs/BUBBLE_POP_RULES.md` /
`docs/LUDO_RULES.md` として起こし、以後はそちらが勝つ。進行中の 2 ブランチ
(ロジック 3 本・カード 2 本)とは独立で、どの順に main へ入っても成立する —
収録本数の文言はマージ時点の実数に合わせる(Phase 5。現行 22 本 + 5 本 +

## 前提(調査済み)

3 本は正本がそれぞれ違う。共通して踏襲するのは: `rng.ts`(xmur3 + mulberry32 +
Fisher–Yates)は**ゲームごとにコピーが正** / シード決定的生成 + golden を最初の
コミットから(「直すのは実装であってテストではない」の契約文込み)/ 時計はプレイ中に
出さない / スコアという数を発明しない / プレイ時間は bookedRef 方式の逐次計上
(可視時のみ。Root テストに背景化パターンを複製)/ 保存のデコードは fail-closed
(プレイから生まれえない状態は破棄してホームへ戻る)/ 効果音は既存の合成音のみ・
粒子と画面揺れなし・Reduced Motion で演出全停止 / オンライン対戦なし。

- **Mahjong Solitaire の正本は Sudoku / Nonogram**(100 レベル + デイリー +
  DOM 盤面・RAF なし)。手詰まり検知と「同じ配置 / 新しい配置」の 2 択提示は
  FreeCell §2、Hint の存在理由(伏せ牌 = 隠れた情報がある)は Klondike / Spider の
  側。デイリーは過去 30 日無条件開放(Nonogram / ドリルの実装を正とする)。
- **Bubble Pop の正本は Brick Breaker**(純 TS 固定タイムステップの engine +
  Canvas 2D + rAF、DPR 上限 2・shadowBlur / filter 不使用、visibilitychange で
  ループ完全停止、`setPointerCapture` は try/catch、canvas の色は `data-game` の
  アクセントトークンを computed style から読む)。RAF ループを持つので
  `*.leak.test.tsx` が要る(ドリル 3 本が不要だったのと逆側)。

## ゲーム仕様の要点(ルール文書の骨子)

### Mahjong Solitaire

- **盤面(§1)**: レイアウト = 牌座標のリスト(x, y は半格子単位、z は段)。
  **縦持ち前提でレイアウトを起こす** — クラシックのタートルは横長 15 列で
  320px には入らないため、90° 回した**縦タートル(幅 8〜9 列 × 縦長)**を看板
  レイアウトにする。幅は最大 9 列(Spider の 10 列より広い牌が取れる)。
  牌は標準 144 枚セット: 数牌 3 種 × 9 × 4 + 風 4 種 × 4 + 三元 3 種 × 4 +
  花 4 + 季 4。**偶数の不変量は「一致の単位」ごとに立てる**(牌面ごとではない)—
  通常牌 34 面はそれぞれ 4 枚だが、**花 4 面と季 4 面は各 1 枚ずつしかなく、
  牌面ごとの偶数を課すと標準セットが常に不正になる**。花はどの花とも、季はどの季とも
  一致する(§2 のグループ一致)ので、不変量は「花グループ 4 枚 = 偶数」「季グループ
  4 枚 = 偶数」で満たされる。小さいレベルは部分セット(通常牌は面ごとに 4 枚か
  2 枚、ボーナス牌はグループごとに 0 / 2 / 4 枚 — どちらも偶数)。
- **一手の解決(§2)**: 取れる牌(自由牌)= 上に牌が載っておらず、左右いずれかが
  空いている牌。同種 2 枚(花同士・季同士は**グループ一致**)を選択 → 2 枚目で
  取る(カードの「選択 → 行き先」と同じ二段。無効タップは叱らない — 選択が
  移るだけ)。全部取れば勝ち。
- **生成と可解性(§5 — この収録の柱)**: **逆順ペア構成**。レイアウトを満杯とみなし
  「自由牌 2 枚を選んで外す」シミュレーションを最後まで走らせ、その外し順の
  k 番目のペアに一致する牌面を割り当てる — 外し順をそのまま再生すれば必ず勝てる
  ので、**全レベル・全デイリーが構成として可解**(Minesweeper の推測不要・
  Water Sort のソルバー証明と並ぶ誠実列。ランダムに配って不可解を混ぜる他社との
  差別化そのもの)。プレイヤーの選択で詰みには到達しうる — それがこのゲームの
  中身である。難易度レバーは牌数・段数・同種 4 枚の重なり方。
  **「不成立なら派生シードで作り直す」(Nonogram §5)はここでは使えない。**
  Nonogram の打ち切りが成立するのは、最後の候補もパズルとして成立しているからで
  ある。こちらは外し順の作成に失敗すると**牌面を割り当てる土台そのものが無い** —
  返せるものが何もなく、「全レベル・全デイリーが常に開けて可解」という約束と
  正面から矛盾する。上限つきリトライは、失敗が構造的ではなく稀であることを黙って
  仮定している。
  **そこで保証をレイアウト側へ移す。**外し順が存在するかはシードではなく**座標
  データの性質**である。レイアウトは 10 個前後の**作られたデータ**なので、
  **各レイアウトが完全に剥がせること(peelable)をバックトラック付きの探索で
  1 度だけ確かめ、テストで固定する**(貪欲でほぼ通り、バックトラックは取り残しの
  安全網)。剥がせないレイアウトはレイアウトの側の不備として**落とす** — 実行時に
  出さない。こうすると実行時は常に完全な外し順を持てて、シードが選ぶのは
  **どの有効な順序か**と**どの牌面割り当てか**だけになる。生成の失敗という状態が
  存在しなくなるので、リトライは正しさの仕組みではなくなる(Minesweeper の
  推測なし保証・Water Sort のソルバー証明と同じく、**保証は構成側に置く**)。
  **ただし「存在する」と「毎回すぐ見つかる」は別である。**レイアウトの 1 度きりの
  検査が示すのは**証人が 1 本あること**だけで、レベルを開くたびに走るシード付きの
  探索の仕事量は縛らない。剥がせるレイアウトでも、貪欲な出だしが残りを詰ませる枝を
  持つなら、その枝を先に並べるシードは完全な順序に辿り着くまでに**指数的な数の
  部分集合**を掘りうる。そこで 2 つ足す:
  ① **各レイアウトは検証済みの証人順序をデータとして持つ**(オフラインで求めて
  同梱する)。② 実行時のシード付き探索には**決定的なノード上限**を課し、
  超えたら**証人順序へ落ちる**。上限を超えても必ず盤面が返るので、生成失敗は
  やはり存在しない。**門は壁時計ではなく仕事量で立てる**(Sudoku §7 と同じ規律 —
  並列テストで壁時計は最大 41 倍ぶれる)。テストは全レイアウト × 広いシード掃引で
  **最悪ノード数**と**証人へ落ちた頻度**を測り、上限そのものを固定する。
  property テストは生成域全体で可解列の存在・グループ牌・偶数不変量を固定する。
- **手詰まり(§7)**: 自由牌に一致ペアがなくなったら静かな通知を出し、**Undo と
  同じ配置への再挑戦をどちらも無料・無制限**で提示。
  **「新しい配置」は提示しない**(Phase 2 実装時の解消、2026-08-08)。当初案は
  FreeCell §2 の 2 択(再挑戦 / 新しい配札)を同文で引いていたが、FreeCell の
  フリー対局は配札の同一性を seed トークンとして**保存する**ゲームであり、
  こちらはレベル番号と日付が盤面を一意に決めるゲームである。「レベル 12 の
  新しい配置」を作れば、「誰が遊んでも同じレベルは同じ盤面」(シリーズのレベル
  契約)と、§10 の「レイアウトと seed は同一性から導出する(2 つ目の真実を
  作らない)」の両方と正面衝突する — デイリーはなおさらで、その日の盤面である
  ことが同一性そのものである。同じ文書の 3 箇所が既に反対側を向いていた以上、
  引き写しの側を落とす。詰みからの出口は Undo と再挑戦が全部担う。
  **リシャッフルは作らない** — 「詰みの解消」は他社アプリ最大の課金・広告ポイント
  であり、ここでは Undo と再挑戦が無料でその全部を担う(§13 に記録)。
- **助け(§8)**: **Undo 無制限**(スナップショット。取った牌の下が見えた後に戻せる
  のは Klondike がめくりを戻せるのと同じ側)+ **Hint(取れる一致ペアを 1 組
  示す)** — 伏せ牌・埋まった牌という隠れた情報があるので Hint を持つ
  (Klondike / Spider の理屈)。勝ち筋の提示はしない。
- **牌面(§12 と i18n)**: インライン SVG 42 種。筒子・索子は手続き描画、萬子・風・
  三元の漢字は**パスデータとして埋め込む**(システム CJK フォントに依存しない —
  床の端末にフォントがなければ豆腐になるため)。数牌にはアラビア数字の隅
  インデックス、風には E / S / W / N(西洋牌の慣習)— カード 3 本が全ロケールで
  J / Q / K / A を牌面に載せている前例に連なる。牌面は両テーマとも紙
  (カードと同じ例外。CSS ヘッダに理由文)。a11y は牌種を読み上げる
  (「萬子の 3・取れます」— 牌種名 ~15 キーは訳す)。実在メーカーの牌面は
  模倣しない(自作 SVG)。
- **進行**: L1–100(牌数 24 → 144、段数 1 → 5)。デイリーは**縦タートル 144 枚
  固定**(難易度・サイズ固定の原則 — 当たり日 / 外れ日を作らない)。過去 30 日
  無条件開放。ストリークなし。
- **統計(§9)**: クリア数・ベスト時間・合計プレイ時間・デイリー達成日 —
  Nonogram の統計の実物に形を合わせる(実装時)。時計はプレイ中に出さない。
  **レビュー依頼**: レベルクリアとデイリー完了で `recordGameCompleted()` を呼ぶ
  (手詰まりからの再挑戦では呼ばない)。REVIEW_PROMPT_POLICY の閾値は
  「合計 5 勝・**全ゲーム横断**」の共有カウンタなので、呼ばないゲームはそのぶん
  他ゲームに負担を回すことになる。1 面が数分なので、ドリル 3 本が入れた L11 の
  ゲートは要らない(Sudoku / Nonogram と同じ)。
- **storage(§10)**: `mj.progress` / `mj.saveGame` / `mj.saveDaily` / `mj.stats` /
  `mj.flags`(5 キー・prefs なし)。スロットの正体はキーが決める
  (`savedGameSlots` の自動強制に乗る)。
  **保存は牌面を持たず、同一性と除去の順序だけを持つ。**
  **2 スロットは同じ形を共有する**(v1):
  `schemaVersion` / `mode`(`'level' | 'daily'`)/ `level: number | null` /
  `dailyDate: string | null` / **除去したペアの列**(座標対の並び)/
  `hintCount` / `elapsedSeconds` / `savedAt`。Nonogram の `PersistedGame` と
  同型である。
  **スロットごとに形を変えてはいけない。**`src/test/savedGameSlots.test.ts` は
  `dailyGame` を持つ全ゲームを走査して、`storage/schemas.ts` に `expectedMode` と
  `parsed.mode === expectedMode` があること、`storage/slots.test.ts` が存在する
  ことを要求する。門の理由はコメントが書いている — 「2 スロットのゲームは両方で
  同じレコード形を保ち、どちらのモードかを言うのは**キー**である」。以前は
  レコード自身の `mode` を答えにしていたため、**free スロットに入った daily
  レコードが素直に読み込まれ**、再開すると別のゲームか空画面が出た。
  したがって `mode` は**保存し、キーと突き合わせて食い違えば破棄する**
  (`gameSlotSchema(key, expectedMode)`)。
  **同一性も必ず保存する** — キーが分けるのはモードだけで、「どのレベルを解錠・
  記録するか」「過去 30 日のどの日か」はキーからは出ない(Nonogram の
  `level` / `dailyDate` と同じ理由)。レイアウトと seed は**同一性から導出する**
  (`mj-level-<n>` / `mj-daily-<YYYY-MM-DD>` は正準)ので保存しない —
  保存すると食い違いうる 2 つ目の真実になる。
  **`hintCount` を持つ**のは、このゲームが Hint を持つからである(§8)。
  中断して再開したときにヒント数が 0 に戻ると、リザルトが嘘をつく
  (Nonogram と Spider Solitaire がどちらも `hintCount` を保存して結果に出す)。
  牌面は復元時に **(レイアウト, seed) から作り直して**得る。合法な操作は牌を
  **取り除く**だけで、動かしも貼り替えもしないからである。この形にすると、
  壊れた保存が表現しうる誤りが**型の上から消える**: 占有座標どうしで牌面を
  入れ替える(牌面を持っていない)、在庫超過(牌面は生成が配ったものだけ)、
  同一性と盤面の食い違い(同一性が唯一の真実)。
  **除去は集合ではなく順序で持つ。**ビットマスク(残り集合)だけだと、
  一致の単位ごとの偶数を満たしながら**プレイからは生まれえない幾何**が通る —
  たとえば上に牌が載ったままの下の牌を 1 組外した保存は、枚数もパリティも
  正しいのに、その除去は当時できなかった。順序を持てば検証は**探索ではなく
  O(n) の再生**になる: 満杯から順に適用し、各ペアが**その時点で自由牌かつ
  一致していたか**を確かめるだけでよい。1 つでも成り立たなければ破棄する。
  これで fail-closed が近似ではなく**そのとおり**になる(前の版は「ペアで
  取られた形か」までしか見ておらず、そこは正直に書いてあったが、幾何が壊れた
  盤面が自由牌の計算に入りうる穴だった)。
  描画に使う残り集合は順序から導く。**ネガティブな保存テスト**: 座標対が
  レイアウト外 / 同じ座標が 2 度出る / 当時自由でなかった除去 / 一致しない
  ペア / 存在しないレベル番号・日付 / **モードがキーと食い違うレコード**
  (`storage/slots.test.ts`)。
  **盤面の golden は保存形式を守らない。**`compatibility.test.ts` は生成の
  決定性を固定するもので、座標対の符号化・フィールド名・直列化を変えても緑のまま
  通る — つまり既存の保存が読めなくなっても気付かない。RELEASE_CHECKLIST が
  そのとおり書いている(「golden テストだけでは足りない — これは生成の決定性を
  守るもので、保存データが生き残ることは検証しない」)。**除去列を持つ v1 の
  永続化ラウンドトリップ・フィクスチャをレベルとデイリーの両方に作る**
  (実際の保存済みペイロードを読み込む形。空でない除去列を含める)。
  以後の変更はこのテストに対する移行だけにする。
- **i18n**: 45 キー前後(牌種ラベル込み)。高リスクキーなし。
- **サイズ**: SVG 牌セット込みで gzip 30KB 以下を見込む — シリーズ最大の
  「コードで描く絵」であり、サイズ門が正直な歯止め(実測して §12 に書く)。

### Bubble Pop

- **盤面(§1)**: 六角オフセット格子の泡 + 下端の砲台。1 発ずつ: ドラッグで狙い、
  離して発射。撃った泡は壁で反射し、格子の最寄り空きセルに吸着する。
- **一手の解決(§2)**: 同色 3 個以上が接続したらポップ。天井から切り離された房は
  落下する(ポップより高得点な爽快点だが、**スコアという数は作らない** —
  指標は残レベルとクリアだけ)。
- **軌道ガイド(§8 — この収録の柱)**: **フル軌道と着弾セルを常時表示する。
  無料・無制限。**他社がコイン・広告視聴で解放する定番機能を、ルールの可視化と
  してそのまま全員に渡す(Checkers の合法手表示と同じ側 — 物理は決定的なので
  予告は嘘をつかない)。ガイドが示すのは**着弾位置だけ**: ポップするか・何が
  落ちるかは示さない(そこを読むのがこのゲームの中身)。Undo / Hint は作らない。
  **反射回数を固定しない** — ガイドは発射する泡と**同じシミュレーションを同じ
  コードで**走らせ、着弾セルに達するまで壁反射を何回でも辿る。浅い角度の一撃は
  天井や既存の泡に届く前に盤を何度も横切りうるので、「反射 1 回まで」の予告は
  そこで嘘になる — **この収録の柱が「予告は嘘をつかない」である以上、回数の上限は
  引けない**。狙いの角度は鉛直から一定内にクランプする(極端な水平撃ちを作らない
  ため。値は実装時に実測して §8 へ)が、クランプの内側でも複数回の反射は残るので、
  ガイドの完全性はクランプではなくシミュレーションの共有で担保する。
  **同じ計算を共有するだけでは足りない — 同じ入力も強制する。**着弾は角度だけで
  決まらず、占有セルの配置と現在の天井オフセットにも依存する。ガイドがドラッグ中に
  キャッシュした盤面を見て、発射が降下後の生きた盤面を見れば、共通の積分器を通しても
  結果はずれる。**ガイドは自前の盤面を持たない** — 予告と発射は 1 つの呼び出し元から
  同じ盤面参照を受け、別々の状態を渡せる口を作らない(Hearts の `CpuView`・Ludo の
  `LudoView` と同じ「型の上で渡せなくする」側)。
  **テストで固定する**: **生成した占有盤面 × 全天井オフセット × クランプ内の角度**を
  掃引して、**ガイドが予告した着弾セルと実際に発射した泡の着弾セルが一致すること**。
  角度は衝突とセル選択の境界付近を明示的に含める(1 つの固定盤面での角度掃引だけでは、
  入力のズレを取り逃す)。これが「嘘をつかない」を主張ではなく機械検証にする
  (golden と同じ側)。
- **圧の形(§3)**: N ショットごとに天井が 1 段降りる(N はレベルで 8 → 5)。
  残りショットは**点の列**で見せる — 数字のカウントダウンにしない。泡が下端の
  点線を越えたらそのレベルは失敗、同じ盤面(同シード)へ即時無料リトライ
  (Brick Breaker と同文)。**時間の圧はゼロ** — 発射までいくらでも考えられる。
  せり下がり(実時間)より手数駆動のこちらの方が「急かさない」に素直に適合する。
- **次弾**: 現弾 + 次弾のプレビューと入れ替え(無料・無制限)。
- **色(§12)**: 4 → 6 色 + **各色の泡に内側マーク**(形で読み分ける — 色に頼らない。
  Checkers のキングが形で示される前例)。泡のパレットはゲーム内容(canvas)で、
  タイトルアクセントはクローム側。**ただし順序はアクセントが先** — 軌道ガイドが
  アクセント色で泡の上に引かれるため、パレットはアクセントの色相家族を空けて選ぶ。
  アクセントがオックスブラッドに決まったので(Phase 1 の結果)、**v1 の泡は赤系を
  持たない**(青・緑・黄・紫・橙・シアンで 6 色は足りる)。
- **生成**: シード決定的。配給される色は盤面の残色に依存する(seed + ショット履歴の
  決定的関数)— golden はスクリプト射撃で固定。レベルは 100(行数 5 → 9・色数・
  降下 N・配置の癖)。**カーブが 100 まで飽和しないことをテストで固定**し、自動
  プレイ実走で膠着を探す(Brick Breaker が 96 秒の垂直往復を実測で見つけた教訓)。
- **デイリーなし(v1)**: 生成はシード決定的なので後から足せる(§13。BB / SF と
  同じ判断)。**途中保存もなし**: 発射間は静止だが、挑戦は 1〜3 分で終わり、
  即時無料リトライが助けの形 — アーケード棚の一貫性を優先(§13 に BB の
  「復元した瞬間に死ぬ保存」とは別の理由として書き分ける)。
- **storage**: `bu.progress` / `bu.stats` / `bu.flags`(3 キー。BB 同型)。
- **統計**: 挑戦数・クリア数・playSeconds。
  **レビュー依頼**: レベルクリアで `recordGameCompleted()` を呼ぶ(失敗と
  リトライでは呼ばない)。1 レベルが 1〜3 分なので、Bunny Hop が入れた
  score ≥ 100 のような下限は要らない(Brick Breaker と同じ側)。
- **i18n**: 20 キー前後。高リスクキーなし。

### Ludo

- **盤面(§1)**: 15 × 15 グリッドの DOM(周回 52 マス + 各色ホーム列 6 +
  ヤード 4 × 4 + 中央ゴール)。Canvas なし。下 = あなた、以下時計回りに
  `CPU 1 / 2 / 3`(Hearts の席次と同文)。**4 席固定**(2 人・3 人モードは
  作らない — §13)。3 席とも選択中の難易度。
- **規則(§2 — 標準コアに絞る)**: 6 で出走(出走マスへ)・6 でもう 1 投・連続
  3 回の 6 はその手番を無効に。着地マスに敵のコマがいれば、**そのマスの敵コマを
  すべて**相手ヤードへ返す。セーフマス 8(各色の出走マス 4 + 星 4)では捕獲されない。
  **自分のコマが乗っているマスにも着地できる。重なりは何の効果も持たない** —
  通行止めにもならず、守りにもならない。**ここを黙って済ませられない**:
  ブロッケードを採らない以上、「**単独の**敵コマだけ捕獲する」と書くと重なりが
  **守り**になり、ブロッケードの半分を裏口から入れることになる。逆に重なりを
  **禁じる**なら、それは移動制限であって §2 に書かねばならない。どちらでもなく
  沈黙すると、**合法な着手から生まれた保存が §10 の検証に弾かれる**(その節)。
  変種の選択なので、実装時の文献確認(本項末尾)はこの 1 行を第一の対象にする。
  ホーム列は
  自分の色だけが入り、**ちょうどの目**で上がり(超過する目ではそのコマは動け
  ない)。出目に合法手がなければ自動パス(Reversi のパス通知と同型の静かな表示)。
  **その出目が 6 だった場合でも、もう 1 投は同じ席に与える** — 自動パスが消費する
  のは**着手**であって追加の投擲ではない。ここを書いていないと「6 でもう 1 投」と
  「合法手ゼロで自動パス」が同じ出目で衝突し、手番が誰に渡るか決まらない。この
  選び方を採るのは遊びの理屈からである(6 が稼ぐのは投擲であって着手ではない。
  「連続 3 回の 6 で手番無効」も、着手の有無に関わらず 6 が連なることを前提に
  している)。重なりの規則と並ぶ、実装時の文献確認の対象である。
  **この規則は保存の設計から独立している** — §10 は合法な進行の**再生**で復元を
  検証するので、再生は各時点の合法手を知っており、どちらの規則でもそのまま従う。
  前の版は手番の境界が出目の値だけで決まることに §10 が依存していて、覆った場合の
  退避先を書く必要があったが、その依存は消えた。**保存の都合で遊びの規則を決めない**が、
  依存そのものを断てるならそのほうがよい。
  **先手は規則で固定する: いつでもあなた(下の席)が最初に振る。**seed から選ばない。
  §10 の手番席はここを起点に数えるので、**「どこかで決まっているはず」では足りない** —
  書いていないと復元側が起点を持てず、解釈次第で別の席から再開する。固定なので
  保存もしない。
  **規則からは対局の長さに有限の上限が出ない** — 捕獲されたコマはヤードへ戻り、
  引き分けも最大手数もないので、合法な対局はいくらでも長くなりうる。だから
  **上限を置くならそれは規則でなければならない**: 投擲数が上限に達したらその対局は
  **無勝負で終わる**(勝ちでも負けでもない。§9 の統計は played にだけ数える)。
  **保存の検証の側に上限を置いてはいけない** — それは合法なプレイから生まれた
  長い対局を「壊れた保存」として捨てることであり、fail-closed の向きが逆になる
  (第 11 巡で「ありえない状態を捨てるのであって、ありうる状態を捨てるのではない」と
  自分で書いた線を、その次の巡で跨いでいた)。上限の数は**典型的な長さから引かない**
  — 15〜30 分は典型であって最大ではない。自己対局を広いシードで走らせて**投擲数の
  分布を実測し**、観測された最大より十分上に置き、測定値ごとルール文書に書く。
  4 コマ全部上がった席の勝ち — **1 位が出た時点で終局**(2 位以降は数えない —
  §13)。捕獲でもう 1 投・ブロッケード(2 枚壁)・最大取り義務は**採らない** —
  いずれも変種であり、対 CPU では膠着と長考の製造機になる(§13 に理由を書く)。
  **ただしこの規則一式は「v1 の候補」であって、検索者の期待に合うことの証明ではない。**
  この 3 本の選定理由は検索流入なので、遊びが「思っていた Ludo と違う」なら前提の
  ほうが崩れる。**「いずれも変種だから採らない」という説明だけでは、期待との一致は
  示せない** — 捕獲でもう 1 投なし / ブロッケードなし / 最大取り義務なし / 自席の
  重なりは合法だが無効果 / 敵のスタックは一括捕獲 / 6 で合法手がなくても追加投擲 /
  4 席固定 は、UI の省略ではなく**プレイ感に直接効く変種選択**である。
  `docs/LUDO_RULES.md` を書く**前に**、一次資料か、対象ロケール(hi / id / th /
  vi / tr)ごとの有力な実装で確認し、出典をルール文書に載せる(Gin Rummy の
  配り手と同じ手順)。**覆ったら §2 を書き換えてから実装に入る。**
- **ダイスの公正(§4 — この収録の柱)**: 出目は
  `createRng(`${seed}:dice:${rollIndex}`)` — **一様・シード決定的・席で偏らない**。
  一様性は生成域のプロパティテストで固定し、golden が出目列そのものを固定する。
  CPU の決定関数は**公開盤面と今の出目だけ**を受ける型(`LudoView` — Hearts の
  `CpuView` 契約の同型)で、未来の出目も乱数器も**型の上で渡せない**。ルール文書に
  「ダイスの出どころ」「CPU が見ているもの」の章を置く。Ludo はジャンルとして
  「ダイスが操作されている」という不信が最も深い場所であり、シード決定・一様・
  ソース公開・型契約・テストの列がそのまま差別化になる。**文言は事実だけを書く**:
  他社名も「不正」「rigged」の語もアプリ内・ストア文言に出さない
  (check-principles の禁止表現と整合)。
- **CPU(§4)**: **探索なし** — すべて合法手数に対する O(n) の算術であることを
  ルール文書に明記する(ボード 4 本の「探索がどこで走るか」の列に加わる)。
  easy = 合法手からシード乱択 / normal = 貪欲重み表(捕獲 > 上がり > 出走 >
  セーフ入り > 前進)/ hard = normal + 1 手先の被捕獲リスクを重みに算入。
  **リスクが 0 になるのは「規則上そこでは捕獲が起こりえない」領域である**
  (まずこれを見る)。**マスを 1 つずつ特例にするのではなく、領域の性質として
  書く** — 該当するのは **① セーフマス 8 ② 自分のホーム列 ③ 上がり済み**の
  3 つで、いずれも敵のコマが到達できない(ホーム列に入れるのは自分の色だけ =
  §2)。**この分岐がないと、脅威のある安全な移動先が脅威のない普通のマスより
  危険に見え、hard が客観的に安全な手を避ける** — 見積りの誤差ではなく分類の
  誤りである。判定は O(1) で、探索なしの設計を一切崩さない。
  **②を落とすと実際に誤る**: ホーム列の入口寄りのセルへ入る手は、後方 1–6 マスを
  辿ると共有トラック上の敵コマに届くので、**敵が絶対に入れないマスに正のリスクが
  付く**。①だけを特例として書いた版がこれを取りこぼした — **規則ではなくマスの
  一覧で考えたから**であり、同じ誤りを 2 度やらないために、ここは領域の一覧では
  なく「捕獲が規則上起こりえないこと」を判定の根拠として書く。
  上の 3 領域以外では**リスクを席ごとに出して掛け合わせる**: 席 i について、
  移動先の後方 1–6 マスにその席のコマがいる**相異なる出目の数** kᵢ(コマ数では
  ない — 同じ席の 2 コマが同じ距離にいても、必要な目は 1 つ)を数え、
  `1 − Π(1 − kᵢ / 6)` とする。
  **「後方 6 マスの敵コマ数 ÷ 6」は誤り** — 3 席は独立に振るので確率は足し算に
  ならず(各席 1 コマずつ 2 席なら 2/6 ではなく `1 − (5/6)² = 11/36`)、脅威が
  増えると 1 を超えて重み表を壊す。
  **この数は「1 投ぶんの見積り」であり、確率でも上界でもない。**6 でもう 1 投が
  あるので**実際より低く出る**(後方 1 マスのコマとヤードのコマを持つ席は、1 で
  即捕獲するほかに「6 で出走 → 1」の筋があり、`1/6` ではなく少なくとも
  `1/6 + (1/6)(1/6) = 7/36`)。逆に、その目が出ても席は別の手を選びうるので
  **高くも出る**。
  **真の手番ぶんの値は求めない** — 連鎖する 6 を織り込むには「その席が 6 で何を
  動かすか」を読む必要があり、それは探索である。このゲームの CPU は探索を持たない
  ことを売りにしている(本項の冒頭)。**その代わり、この数が移動先の順序を保つとは
  主張しない** — 連鎖する 6 の膨らみは席ごとに不均一(ヤードにコマがある席ほど
  連鎖の余地が大きい)で、順序を入れ替えうる。これは貪欲な重み表の**入力の 1 つ**で
  あって最善手の保証ではなく、**hard は「より強い経験則」であって解ではない**
  (Reversi §12「最強の CPU を作らない」の側)。**ルール文書 §4 はこの数を
  「確率」と呼ばず、順序の保証も謳わない** — 何であって何でないかをそのまま書く
  (ダイスの公正を謳う章の隣で、CPU 側の数字だけ盛るわけにいかない)。
  **タイブレークは `createRng(`${seed}:cpu:${rollIndex}`)`** — `turnIndex` では
  ない。CPU の判断は必ず 1 回の出目に対して起きるので rollIndex は判断ごとに
  一意である。**鍵は復元後も同じ値が出るものでなければならない**(§10 の契約①②)—
  保存するか再生で作り直すかは Phase 4 の選択だが、どちらにせよ鍵がその性質を
  持つことは動かない。`turnIndex` を鍵にすると、
  自動パスと連鎖する 6 で 2 つのカウンタがずれ、**盤面と手番席からは捨てた履歴を
  復元できない** — kill → 復元をまたぐと、同点の CPU 判断が中断なしのプレイと
  違う手を選びうる。**決定性を柱に置くゲームで、保存に現れない数を鍵にしては
  いけない**(Mahjong で seed を「食い違いうる 2 つ目の真実」として持たせなかった
  のと同じ規律の裏返し — あちらは真実を減らし、こちらは鍵を保存済みの数へ寄せる)。
  連鎖する 6 の 2 回の判断が別々の値を引く点でも、rollIndex のほうが素直である。
  手番の再生は CPU 3 席分が連続する —
  各席 `CPU_DELAY_MS` で、1 巡の体感(450ms × 3 + 出目表示)は実装時に実機で
  確かめ、長ければ CPU 間隔だけ詰める(値はルール文書 §4 へ)。
- **Undo なし(§8)**: Undo は置かない。Hearts と同じく、**不可逆な情報開示のあとに
  選び直させてしまう**からである。**ただし Hearts と「同型」ではない** — Hearts で
  漏れるのは**他家の選択という非公開情報**、Ludo で先読みされるのは **seed により
  確定した未来の出目**であり、漏れる情報の持ち主も性質も違う。結論は同じ、理由の
  構造は類似、漏れるものは別物、と書き分ける(前の版は「同型」と断定していて、
  そこまでは言えない)。出目を維持したまま戻せば先読みになり、振り直せば Undo が
  リロールになって決定性の原則と両立しない — どちらへ倒しても成立しない。
  助けは**動かせるコマの常時表示**(出目で動かせるコマだけが選べる — Checkers の
  捕獲義務の可視化と同文)。
- **席の色(§12)**: 4 人色(赤・緑・黄・青)は**ゲーム内容**であり、テーマや
  アクセントから独立(カードの赤黒と同じ例外 — ludo.css のヘッダに理由文)。
  コマには席の**形マーク**を重ね、色に頼らない。あなたの席色は固定
  (アクセントと紛れない側を実装時に確定)。ダイスの回転演出は 220ms 上限、
  Reduced Motion では出目を即時表示。
- **中断と再開(§10 — 計画は契約と制約まで。形式は正本と実装 PR で確定する)**:
  1 スロット・fail-closed。**この節はレコードの形を凍結しない** — 本文書は着手前の
  計画であり、仕様の正本は `docs/LUDO_RULES.md` である(冒頭)。第 11〜15 巡の
  レビューで得られたのは「今の形式が正しい」ことではなく、**形式が変わっても残る
  要求**のほうだった。散文だけで状態機械を完成させようとすると、隣接する遷移との
  整合を機械的に確かめられない — 実際、第 15 巡では**同じコミットの中で散文と
  テスト一覧が矛盾**した。だから確定は、型とテストを同時に置ける Phase 4 で行う。
  **外部契約(ここは弱めない)**:
  ① 中断・再開後も、**同じ seed と同じプレイヤー入力からは同じ対局状態へ戻る**。
  ② 復元後も **RNG と CPU 判断の決定性が保たれる**(同点の判断を含む)。
  ③ **合法な対局から到達できない進捗を受理しない**。
  ④ Web 先行公開の時点から**スキーマ凍結**の対象になる(RELEASE_CHECKLIST §0)。
  ⑤ **実際の v1 ペイロードを読む永続化互換性テストを置く** — kill → 復元テストも
  対局 golden も現行コードでレコードを作り直すので、これらでは代替できない。
  **設計制約(実装がどの形式を採っても守る)**:
  ・到達可能性は**スナップショットへの局所検査で済ませず、合法な進行の再生で確かめる**
  (Mahjong の除去列と同じ形)。
  ・**導出できる値は原則として保存しない**。保存するなら正準値と照合する。
  ・**レコードを信じる前に復元の仕事量を有界化する**(門は壁時計ではなく仕事量)。
  ・**合法な対局を「長い」というだけで破棄しない** — 上限を課すなら §2 の規則側に置く。
  ・CPU の演出中など**複数のランタイム状態が同じレコードになる場合は、復元先を正準化する**。
  ・形式・生成・CPU 決定関数の変更が、**既存の v1 ペイロードを黙って読み替えない**。
  **実装候補(確定ではない)**: プレイヤーの入力履歴を再生し、CPU 側の中間進捗は
  保存せず、**次にプレイヤーの手番が始まるところ**へ正準化する方式。第 15 巡までの
  検討ではこれが筋の通る候補だが、**v1 契約として凍結はしない**。
  **Phase 4 で決めること**: イベント列 / チェックポイント / 併用のどれか・プレイヤー
  入力だけを保存するか CPU 境界も持つか・自動パスを明示イベントにするか別の正準
  カウンタで表すか・正準化を保存時に行うか復元時に行うか・再生の仕事量上限と対局
  上限の具体値・v1 のフィールド名と型と encoding・スキーマ decoder と再生 validator の
  責務分担。**受け入れ条件(下の Phase 4 テスト)を満たさない実装は通さない** —
  緩めるのは制約ではなく、未検証の具体案への過剰な確約のほうである。
- **統計(§9)**: 難易度別 played / wins / losses + totalPlaySeconds。
  **`played` は `wins + losses` より大きくなりうる** — 差は §2 の上限に達して
  無勝負で終わった対局である(引き分けという結果は作らないが、**結果が出ない
  終わり方はある**。数えないと played が嘘になる)。マッチは典型 15〜30 分 —
  勝利時のみ `recordGameCompleted()`(無勝負では呼ばない。Hearts と同文)。
- **storage**: `ld.saveGame` / `ld.stats` / `ld.flags` / `ld.prefs`(4 キー。
  prefs は難易度)。
- **i18n**: 30 キー前後。高リスクキーなし。

### Phase 2 — Mahjong Solitaire 本実装(大)

- 最初に**縦タートルの静的モック実測**(320 / 360 / 420px × ライト / ダーク):
  牌の判読(隅インデックス)・段の立体感・タップ精度。9 列で不成立なら列数を
  落とした看板レイアウトを測り直してから進む(サイズ変更は本文書の更新を要する)。
- `game/`: types(座標・牌種・グループ一致述語・`isValidBoard`)、rng(コピー)、
  layouts(座標データ 10 前後 + レベル表 + **peelable 検査**)、
  generator(逆順ペア構成。**リトライではなくバックトラックで外し順を必ず完成
  させる** — §5)、freeState(自由牌計算)、session(選択 → 除去・スナップショット
  Undo・手詰まり検知)、serialize、daily、index。
- **`isValidBoard` は偶数だけでは足りない。**一致の単位ごとの偶数(§1)は
  「取り切れる形か」しか見ておらず、**そのレベルの牌在庫から生まれえない盤面を
  通してしまう** — 同じ花が 2 枚あって別の花が無い、通常牌が 6 枚ある、といった
  状態が全部偶数を満たす。検査は 2 段にする: ① **牌面ごとの枚数がそのレベルの
  在庫を超えない**(標準セットなら通常牌は 4 枚まで、花と季は各 1 枚まで)
  ② **一致の単位ごとに「在庫 − 残り」が偶数**(通常牌は牌面ごと、花と季は
  グループごと)。①がないと fail-closed の保存契約が嘘になる(壊れた保存も
  手で書いた保存も通る)。
  **さらに、牌面の多重集合を検査するだけでは幾何が守れない。**座標の重複・
  レイアウト外の座標・占有座標どうしの牌面入れ替えは、枚数もパリティも一切
  動かさないのに合法なプレイからは生まれない(プレイは取り除くだけで、動かしも
  貼り替えもしない)。そして壊れた幾何は自由牌の計算にそのまま入る。
  **保存形式でこれを表現不能にする** — 保存は同一性と除去の順序だけを持ち、
  牌面は (レイアウト, seed) から作り直す(§10)。座標と牌面の結び付き・在庫・
  同一性との整合は、検査ではなく**表現の性質**として満たされる。
  **残りは順序の再生で見る**: 満杯から順に適用し、各ペアがその時点で自由牌かつ
