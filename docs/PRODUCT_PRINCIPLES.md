# Simple Games — プロダクト原則

Simple Games の全収録タイトルは以下を守る。これはブランドプロミスであり、
個別ゲームの都合で破ってはならない。

## コンセプト

**Honest by design. Simple games, built in the open.**
「無料ゲームを、誠実に。シンプルなゲームを、オープンに。
私たちの説明を信じる必要はありません。ソースコードを公開しています。」

コンセプト語: シンプル / 完全オフライン / 低消費電力 / 広告は控えめ / 急かさない /
サブスクなし / 機能課金なし / ログインなし / ソースコード公開

設計思想: **Built by subtraction.** 足すのではなく、削る。ユーザーへの体験価値としては
**Less between you and the game.**(下の「引き算の原則」)

## 引き算の原則(Built by subtraction)

Honest by design が「何を約束するか」なら、Built by subtraction は「何を足し、何を
足さないかをどう決めるか」である。2 つは別々のスローガンではなく 1 つの話で、削った
結果が下の「必須原則」になり、その約束を公開ソースで検証できる(issue #123)。

一般的な無料ゲームアプリは機能を足すことで競争する。Simple Games は、**ユーザーと
ゲームのあいだにある不要なものを削る**ことで差別化する。これは UI の簡素さだけの話では
なく、プロダクト・技術・収益モデルを貫く 1 本の判断軸である。

> We remove what gets between you and the game.
> あなたとゲームのあいだにあるものを、削る。

**目指すのは「少ない機能」ではなく「少ない負担」である。** 機能の数を減らすこと自体が
目的なら Hint も Undo も削れてしまうが、それはプレイヤーの負担を増やす。物差しは
「その機能はユーザーの操作・判断・通信・待ち時間・中断を減らすか、増やすか」であって、
機能の多寡ではない。

### 判断原則

> 新しい機能は、それによって増える複雑さと手数に見合う価値を示さなければならない。
> エンゲージメント機能を足すより、ユーザーの操作・判断・通信・待ち時間を減らすことを
> 優先する。

> Every new feature must justify the friction it adds. Prefer removing steps over
> adding engagement mechanics.

### 何を削り、何を削らないか

| 削るもの                            | 削らないもの                                             |
| ----------------------------------- | -------------------------------------------------------- |
| 不要なタップ・モード切替・探索      | ゲームそのもの                                           |
| ゲームを中断する広告                | 必要なゲーム機能                                         |
| サブスクリプション                  | Hint / Undo など、負担を減らす助け(形はゲームごとに違う) |
| 機能課金・広告視聴による機能解放    | ローカル保存                                             |
| アカウント登録                      | タッチ / マウス / キーボードで自然に遊ぶための入力経路   |
| 通知・ストリーク・人工的な緊急性    | アクセシビリティ                                         |
| オンライン依存                      | オフライン品質                                           |
| 不要なバックエンド / サーバーサイド | 低スペック端末での快適さ                                 |
| 大きなアプリサイズ・重いアセット    |                                                          |
| 不要な運用 / 固定インフラコスト     |                                                          |

削る軸は 6 つある:

1. **操作を削る** — 遊び始めるまで・遊んでいる最中の不要なタップ・モード切替・
   中断を減らす(Zero Friction、issue #107)。お気に入りとゲーム名検索、Android の
   Pinned Shortcut と iOS の Quick Actions、進行中の局がちょうど 1 つならその盤面へ
   直接復帰、Solitaire 系のドラッグ移動、Minesweeper / Nonogram の右クリックと
   キーボード([ARCHITECTURE.md](ARCHITECTURE.md)「コレクションホーム」)。
2. **中断を削る** — Interstitial / Rewarded / App Open を持たず、盤面に重ならない
   小さなバナー 1 枠だけ([ADS_POLICY.md](ADS_POLICY.md))。レビューのお願いも
   ゲームからコレクションへ戻った瞬間にしか出さず、答えたら二度と聞かない
   ([REVIEW_PROMPT_POLICY.md](REVIEW_PROMPT_POLICY.md))。
3. **判断と義務を削る** — サブスクリプションなし、Hint / Undo を課金しない、
   アカウント不要、ストリークなし、通知なし、期間限定イベントなし。
4. **ネットワーク依存を削る** — ゲームロジックは端末内で完結し、初回起動から
   オフラインで動く。ゲームデータをサーバーへ送らない
   ([OFFLINE_POLICY.md](OFFLINE_POLICY.md))。
5. **アプリサイズを削る** — 盤面は端末内で生成し、重いアセットもコンテンツ配信も
   持たない。低速回線でも導入しやすく、モバイルデータを消費せず、ストレージの少ない
   端末にも入り、インストールから遊び始めるまでが短い。技術的な小ささではなく、
   設計判断として伝える。
6. **サーバーと固定コストを削る** — 下の「維持費の原則」。

**サーバーと固定コストを削るのは、開発者の都合ではなくユーザー価値である。**
API サーバー・クラウド DB・認証基盤を持たないことで、障害点が減り、オフライン動作が
成立し、継続的な固定費が発生しない。固定費が無いから、それを回収するための
サブスクリプションや強い収益化をユーザーに要求しなくて済む。Web 版も静的配信だけで
動く([WEB_VERSION.md](WEB_VERSION.md))。「オフライン・全ゲーム機能が無料・軽量」の
約束はこの構造の上に立っており、対外的に説明するときもこの順で言う — インフラの話では
なく、ユーザーが受け取るものの話として。

### 公開文面への反映の規則

- **「すでにそうなっている」だけを根拠にする。** LP・ストア掲載文・README に書くのは
  実装済み・検証済みの事実だけで、「これから作る」機能や未検証の性能を書かない。
  Zero Friction の各施策(お気に入り・検索・ショートカット・直接復帰・入力経路)は、
  実装が終わってから初めて公開文面に載せた。
- **数値は公開時点の実測値だけ。** アプリの配布サイズを「約 x MB」と書くときは、
  Play Console / App Store Connect が示す**その時点の**配布サイズを確認してから書き、
  未確認の数値を固定コピーにしない。リポジトリの `size-baseline.json` はバンドルの
  Gate であってストアの配布サイズではない。数字を書かずに「軽い」とだけ言うほうが、
  古い数字を残すより誠実である。
- **Honest by design と矛盾させない。** 削ったと言うものは実際に不在であること
  (機械判定できる範囲は `.github/scripts/check-principles.sh` が見る)。残したと言う
  ものは実際に無料・無制限であること。禁止表現は [BRAND.md](BRAND.md)「表現ルール」の
  まま。

## 必須原則

**適用範囲**: 以下は **Android アプリ**(ストアで配る製品)の約束である。同じソースから
配信するブラウザ版は役割が違い、広告・課金・オフライン・計測・収録タイミングの範囲に
ついて別の約束を持つ([WEB_VERSION.md](WEB_VERSION.md))。**版をまたいで必ず成立する**のは、課金ロックなし /
サブスクなし / **広告視聴や課金による機能解放なし** / アカウント登録なし / ストリークなし /
ゲームデータはローカル / ソースコード公開。**版によって異なる**のは、広告フォーマット
(アプリ = バナー 1 枠のみ / Web = 複数形式)、広告削除の買い切り(アプリのみ)、
オフラインの範囲(アプリ = 初回起動から / Web = 初回アクセスの読み込み後)、
計測(アプリ = Analytics なし。ただし Android に限り、EEA/UK/CH 等の同意が要る地域を
除く新規インストールについて、利用者の操作なしにインストールを 1 回だけ Meta に
知らせる獲得計測がある — 下の「Android の獲得計測(Meta)」/
Web = サイト共通のページ解析 — [WEB_VERSION.md](WEB_VERSION.md)「計測」、読み方と限界は
[GROWTH_MEASUREMENT.md](GROWTH_MEASUREMENT.md))、
収録タイミング(アプリ = 検証済みの正式収録のみ / Web = 新作の先行公開あり —
[WEB_VERSION.md](WEB_VERSION.md)「先行公開」)。
どちらの版でも、その版で成立しない約束を掲げない。

**Core と Club House**(2026-09-09 の issue #176、2026-09-30 の
issue `simple-games-club#1`): この文書の約束はすべて **Core** — Club House を使って
いない状態のアプリと Web 版、つまり誰もが受け取るもの — の約束である。
Club House(issue #161 / #164)は本人が明示的に参加したときだけ現れる任意の層で、
Core の約束の**例外ではなく Core の外**に置く。デプロイは PixApps が運用する
**Public Club House** と、利用者が建てる **Private Club House** の 2 つ。Club House を
一度も触らないプレイヤーにとって、この文書の約束は 1 語も変わらない。境界は本文書
末尾の「Club House」節が定める。

英語(ストア・対外表現の基準):

- No paywalls
- No subscriptions
- Banner ads only
- Optional one-time ad removal
- All games playable offline
- No account required
- No streaks or artificial urgency
- Local-first game data
- Low battery consumption
- Public source code

日本語:

- ゲーム機能の課金ロックなし
- サブスクリプションなし
- 広告はバナーのみ
- 広告削除は任意の買い切り
- 全ゲームをオフラインで利用可能
- アカウント登録なし
- ストリークや人工的な緊急性なし
- ゲームデータはローカルファースト
- 低消費電力
- ソースコード公開

補足:

- 全ゲーム機能は**初回起動から**オフラインで利用できる。広告を見なくても
  ゲームを最後まで遊べる(そのゲームが持つ Hint / Undo を含む)。広告取得を
  待つ必要がなく、広告取得失敗でゲームが停止しない。
- **助けは無料・無制限。ただし機能一覧を全ゲームで揃えない。** 各タイトルには
  「そのゲームの中身を空にしない形の助け」を用意する。原則は「Undo / Hint を
  広告視聴や課金の報酬にしない」ことであって、全タイトルに同じ 2 つのボタンを
  並べることではない。Minesweeper は **Undo を作らない**(推測なしで解けることを
  保証している以上、地雷を開くのは常にプレイヤーの判断であり、取り消せるなら
  賭けが残らない。代わりに同じ盤面への即時・無料の再挑戦を出す)。
  Sliding Puzzle は **Hint を作らない**(盤面は完全に見えており、隠れている情報が
  ないため、次の一手を教えることはパズルそのものを肩代わりしてしまう)。
  各タイトルの結論と理由はそのゲームのルール文書に書く。
- ゲームデータは端末内に保存。クラウド同期なし。**Core の画面に順位は出ない。**
- API サーバーなし / アプリ用データベースなし / コンテンツ配信サーバーなし。
  (どちらも Core の約束。Club House に参加した端末が、本人の選んだデプロイへ挑戦の
  結果だけを送るのはこの外側にあり、条件は「Club House」節 — 送るのは結果画面が
  表示した事実だけで、進行・盤面・統計・設定は送らない。順位表もその層にあり、
  Core の画面には現れない。)
- 継続的なゲームイベント運営なし。ログインボーナス・期間限定イベント・
  エナジー/待ち時間タイマーを作らない。タイマープレッシャーを既定にしない。
- ソースコード公開は開発者向け機能ではなく、ユーザーがこれらの約束を
  検証できる仕組みである(BRAND.md)。

## 広告と課金

- 広告は **Anchored Adaptive Banner のみ**。オンライン時のみ表示し、
  オフライン時は広告リクエスト自体を行わない。
- Rewarded / Interstitial / Rewarded Interstitial / App Open / Native 広告は
  初期リリースに限らず**今後も採用しない**。盤面に重なる広告・進行を止める広告・
  広告視聴による機能解放も同様に禁止(ADS_POLICY.md)。
- アプリ内課金は「広告削除の買い切り(Remove Ads & Support Simple Games、
  基準価格 USD 3.99、一度だけ、購入復元あり)」の **1 商品のみ**。
  ゲーム機能は無料ユーザーと完全に同一。課金専用のゲーム・機能を作らない。
- 「Lifetime Access」という表現は使わない(無期限なのは広告削除権であって、
  アプリのサービス存続期間ではない)。

## 維持費の原則

**ゲームのために**以下の有料インフラを使用しない。

独自 API サーバー / アプリ用クラウド DB / ユーザー認証基盤 / クラウドセーブ /
オンラインランキング / マッチングサーバー / Push 通知配信サーバー / 独自分析サーバー /
AI API / CMS / 定期実行ジョブ / 有料問題生成 API / 有料ゲームバックエンド

既存の Google Play・Apple Developer・GitHub・AdMob を除き、
追加の固定インフラ費を発生させない。無料枠超過時に自動課金される構成に依存しない。

**ゲームは PixApps のサーバーを 1 つも必要としない。** 全ゲームの生成・保存・デイリー・
言語・テーマは端末内で完結し、PixApps 側が止まってもアプリと Web 版は何も変わらず
動く。上の一覧が守っているのはこの事実であり、**利用者が受け取る保証はここにある**。

**例外は Public Club House の 1 デプロイだけである**(2026-09-30、issue
`simple-games-club#1`)。2026-09-09 の「PixApps はサーバーを運用しない」は、この 1 台に
限って撤回した。そこには順位表があり、API があり、固定費がある — ただし**限りなく
ゼロに近いことが条件**で、無料枠を超えたら機能を削るかデプロイを畳む。利用者への
課金・サブスク・広告の強化で埋めない。条件と畳み方は「Club House」節「費用の上限」。
Private Club House のサーバは従来どおり利用者のもので、建てる・払う・消すのは持ち主。
ホスティング事業者のテンプレートは配布物であって運用ではない。

## 低消費電力の原則

通信と計算を最小にする。これは電池のためであると同時に、透明性のためでもある。

- プレイ中の定期ポーリングなし。バックグラウンド処理なし。常時接続なし
- オフライン時は広告取得のリトライを止める(リトライループを作らない)
- 画面外のゲームを描画しない(アンマウントする)
- 不要なアニメーションを避ける。タイマーは低頻度にする
- ゲームロジックは Pure TypeScript(重いランタイム・ネイティブ呼び出しに依存しない)
- 保存はイベント駆動で、頻度を常識的に保つ
- ローエンド Android 端末で快適に動作すること

## 初回体験の原則

初回起動時に求めてはならないもの:

ログイン / メールアドレス / ニックネーム / プロフィール / 通知許可 / 課金 /
購入ダイアログ / サブスクリプション / レビュー投稿 / 不要なアンケート

説明(How to Play)は 3 ステップ以内。説明後すぐゲームを開始する。
広告同意が法的に必要な場合でも、ゲーム初期化と切り離し、同意処理の失敗で
ゲームを停止させない。

## UI / UX の原則

- シンプル・静か・読みやすい・操作が予測可能
- ゲーム盤を最優先。不要な情報・演出を表示しない
- ユーザーを急かさない。ストリーク表示・連続日数カウンタを持たない
  (デイリーの「達成日カレンダー」は記録であり、これは持ってよい)
- 広告・課金への言及は謝罪調・強制調にしない。購入を繰り返し促さない
- Reduced Motion 有効時は不要なアニメーションを停止する
- **手応えは、盤面に既に見えている事実をもう一度言う形に限る**(2026-09-03)。
  効果音は「揃った・消した・できた大きさ」に応じて高くなるだけで、速くも大きくもならない。
  結果カードは完成した盤面を一拍見せてから出し、比べる相手は自分の記録だけ
  (`+0:18` / `−0:05`)。称号・実績ギャラリー・ストリーク・タイマー・通知・全ゲーム横断の
  経験値など、「まだ手に入れていないもの」を見せて呼び戻す仕掛けは作らない。
  記録(達成日、自己ベスト、レベル別のクリア)は持ってよいが、未達成の一覧は持たない

### デイリーは今日の 1 問

デイリーチャレンジは、端末のローカル日付で決まる **今日の 1 問** である(2026-10-02 に
過去日への遡りを廃止)。遡れるなら、それはデイリーではなくもう 1 つの出題モードになる。

- 過去の日付には遡れない。「過去のデイリー」の一覧も入口も持たない。
- 日付が過ぎた中断中のデイリーは捨てる。次に読み込むとき(起動・ゲームを開く)に、保存された
  デイリーの日付が今日と違えば復元せず、レコードを削除する。ホームの「デイリーチャレンジ」は
  つねに今日の問題へ向き、「続きから」と扱うのは今日の日付の盤面だけ。
- 遊んでいる最中の盤面は日付が変わっても取り上げない。終えればその日の達成として記録する。
- 急かさない。残り時間・期限・「あと n 時間」は出さない。盤面は黙って翌日の問題に替わるだけで、
  逃した日を数えもしない(ストリークを持たない原則と同じ)。
- 達成日の記録(カレンダー)は残す。未達成の日の一覧は持たない。
- 実装: 各ゲームの `storage/gamePersistence.ts` の `loadSavedGames(kv, today)` が別の日のデイリーを
  読み捨て、Home は `sessions.daily.dailyDate === today` のときだけ再開を出す。横断変更は
  `apps/simple-games/scripts/codemods/2026-10-02-daily-today-only.mjs`。

### 多言語と説明の原則

- 初回起動時に言語選択画面を出さない(端末の優先言語から解決し、即プレイ可能にする)
- 言語の切り替えでゲームの進行・保存データをリセットしない・壊さない
- アプリ内の文章は最小限に保つ。チュートリアルは 3 ステップ以内・図中心
- 詳細ルール・FAQ・攻略はアプリ内に持たず、ゲーム別 Landing Page へ分離する
- オフラインで外部リンク(Learn More 等)が開けなくてもゲームを止めない

## エンジニアリングの原則

- ゲームロジックは UI / 広告 / Capacitor に依存しない Pure TypeScript
- 依存方向は `apps → packages` のみ。循環依存禁止
- `games/A/` から `games/B/` への import 禁止。シェルはゲーム内部に踏み込まない
- ゲームごとに保存領域を分離する。一方のデータ破損が他方へ波及しない
- 一度しか使われていないコードを共通化しない(重複が確認されてから抽出)
- 巨大な共通ゲームフレームワークを作らない
- アプリへのゲームの正式収録・更新はアプリのリリースとして一体で行う。Web 版への
  先行公開はこれに先行してよい([WEB_VERSION.md](WEB_VERSION.md)「先行公開」)。
  ただしゲームの追加・更新が既存ゲームの挙動・保存データを変えてはならない
- ストア公開は明示的な手動実行またはタグを必要とする
- 実施していない検証を成功扱いにしない

## 初期リリースで実装しないもの

対人戦 / オンラインランキング / フレンド / チャット / シーズン / 期間限定イベント /
ログインボーナス / 課金アイテム / ガチャ / バトルパス / ユーザープロフィール /
クラウド同期 / ソーシャルログイン / AI 機能 / オンライン問題配信 / Coming Soon 表示 /
Push 通知 / ローカル通知 / ストリーク表示 / Analytics / Remote Config /
Rewarded 広告 / Interstitial 広告 / App Open 広告 / Native 広告

このうち各種広告フォーマット・ストリーク・ログインボーナス・期間限定イベント・
Push/ローカル通知・Coming Soon 表示は「初期リリースで見送る」のではなく、
**採用しない**。Analytics も**アプリでは採用しない**。
Web 版のページ解析は「適用範囲」のとおり別の約束であり、
[WEB_VERSION.md](WEB_VERSION.md)「計測」が定める。Android の獲得計測(Meta)は
Analytics ではなく、下の「Android の獲得計測(Meta)」が定める期限つきの例外である
(プレイの記録・送信は、それによっても 1 つも増えない)。

この一覧と「採用しない」は Core のものである。**「オンラインランキング」だけは
2026-09-30 に扱いが変わった** — Core の画面には今も無いが、Club House の層では
同じ盤面・同じモードでの**成績の**順位を作る(「Club House」節「順位表」)。
Club House の中で何を持てて何を持てないかも同節が定める — そこでもリアルタイムの
対人戦・マッチング・フレンドグラフ・リアルタイムチャット・ソーシャルログイン・
クラウド同期・Push / ローカル通知・ストリーク・**熱心さの順位**は持たない。

**共有報酬 / 招待ボーナス / 紹介コードも採用しない**(issue #86)。結果画面には
任意の共有があるが、押しても押さなくてもゲーム・進行・広告表示・解放される
ものは一切変わらず、催促も再要求もしない。共有は「気に入ったゲームを本人の
意思で渡す」ためのものであって、こちらが対価を出して買う行動ではない
([ARCHITECTURE.md](ARCHITECTURE.md)「レイヤー規則」)。Club House の招待・参加・Host 化にも
報酬を出さない(「Club House」節「紹介」)。

共有文と共有画像には、そのプレイの結果(結果画面が表示した時間・スコア・ミス・
ヒント回数など)を載せる(2026-09-03 に「数値を載せない」規則を撤回)。載せるのは
本人がボタンを押したときだけ・結果画面が表示した事実だけ・履歴は載せない・
勝っていない結果を勝ったと言わせない。ランキング・ストリーク・成績の保存や送信は
これによっても増えない。

## Android の獲得計測(Meta)— 期限つきの例外

2026-09-27 決定(issue #204、オーナー合意)。2026-09-29、オーナーの判断で同意方式を
やめ、対象地域では自動送信に変更した(許可した人だけでは大半のインストールが Meta に
届かず、Meta の学習が進まなかったため)。運用・送信内容・手作業・撤去手順の正本は
[META_ANDROID_ACQUISITION.md](META_ANDROID_ACQUISITION.md)。

**これは「アプリには Analytics を入れない」からの明示的な変更である。** 獲得のためだから
既存の方針と同じ、とは扱わない。Web に着地する Meta 広告はすでに出しているが、Android
アプリを直接インストールさせる広告(Meta → Google Play)は、インストールの信号が
アプリから Meta に届かないと計測も最適化もできない。そのためだけに、Android 版へ
Meta の App Events SDK(`facebook-core`)を入れる。

境界 —— これを越える変更は、この節を先に改める:

1. **Android だけ。** iOS・Web には SDK・通信を足さない。
2. **送るのはインストールの 1 件だけ。** 「このアプリがインストールされた」という Meta の
   標準の報告を、インストールごとに 1 回。ゲーム・プレイ時間・盤面・スコア・勝敗・
   レベル・Hint / Undo・保存データ・購入 / 復元・広告収益・セッション・画面・操作は
   送らない。利用者の連絡先・位置情報を渡さない。リターゲティング用のイベントを送らない。
   **広告 ID(Android Advertising ID)はこの 1 件の報告に限り送る** —— 2026-09-29 より前は
   送っていなかったが、対象地域での自動送信への変更にあわせて有効にした。SDK が
   合わせて付ける情報(端末情報・Facebook アプリの計測用 ID など)は
   META_ANDROID_ACQUISITION.md §4 が一覧を持つ。
3. **同意は求めない。地域で送る/送らないを分ける。** EU・EEA(アイスランド/
   リヒテンシュタイン/ノルウェー)・英国・スイスとその関連地域では送らない(SIM・
   ネットワーク・端末の地域設定のいずれかが該当する、またはどれも分からなければ
   送らない)。それ以外の地域では、新規インストールに対して利用者への質問・確認画面
   なしに自動で送る。アプリ内の同意ダイアログと Settings の切り替えは廃止した。
4. **新規インストールだけを報告する。** 既存インストールの更新(例: v1.2.2 → v1.3.x)は
   `firstInstallTime` が変わらないため、インストールとしては報告しない。受理されるまで
   起動のたびに上限回数まで再試行し、再試行は 7 日の期限に縛られない。受理された端末は
   二度と送らない。
5. **既定は「無い」。** 明示的に有効化したリリースビルドにだけ SDK が入り、それ以外の
   ビルド(debug を含む)には存在しない。これは CI がビルドされた APK で示す。
6. **期限つき。** 目標は Android 版の累計 1,000+ installs で、到達時に獲得広告の停止と
   SDK の撤去を判断する。恒久的な行動分析基盤にしない。延長するなら理由と次の見直し
   条件を明記する。停止のためにサーバーや Remote Config を作らない。
7. **開示が先、送信が後。** 公開プライバシーポリシーとデータ セーフティを実装と一致させて
   から有効化する。「ゲームデータを送らない」と「SDK 由来の獲得情報(広告 ID を含む)は
   対象地域で自動的に送る」を区別して書き、包括的な「トラッキングなし」や「許可した
   場合だけ送る」という、対象地域では実態と矛盾する表現を残さない。
8. **Audience Network(アプリ内広告)ではない。** 広告はバナー 1 枠のまま、広告削除の
   買い切りも変えない。
9. **アプリ内に opt-out はない。** 利用者の手段は、Android の設定で広告 ID を
   リセット/削除する、Meta 自身の設定を使う、アンインストールする、の 3 つ。送った 1 件を
   アプリから取り消す手段は無い。同意が要る地域と判定した端末(SIM・ネットワーク・地域
   設定のどれかが該当、またはどれも不明。一度判定したら記録して以後も送らない)では何も
   送らない —— 位置情報を使わない推定であり、判定の限界は runbook §6。

機械で示すこと: 追跡系の依存は release 限定・フラグ付きの `facebook-core` 1 行だけ
(`check-principles.sh` §3b)、SDK に触れるのはネイティブの 1 ディレクトリだけ(同 §8 a)で、
任意のイベント・購入・セッション・利用者データを送る API を呼ばない(同 §8 b)、manifest で
SDK の自動動作を止めている(同 §8 c)、JS から呼び出す口(`@PluginMethod`)自体が無い
(同 §8 d)、APK の権限・初期化 provider・
SDK の有無(`check-android-artifact.sh`)。

## Club House(Public / Private)— Core の外にある任意の層

2026-09-09 に Shared(自前サーバだけ)として定めた層を、2026-09-30 に **Club House** へ
改める(issue `simple-games-club#1`、Epic #175)。変えた判断は 2 つだけである。

1. **PixApps が 1 デプロイだけ運用する。** 2026-09-09 の「PixApps はサーバーを 1 台も
   運用しない」を撤回し、**Public Club House** という公式デプロイ 1 つに限って認める。
   撤回の理由は下の「費用の上限」に書く条件が付いているからで、条件が崩れたら畳む。
2. **成績の順位表を作る。** 同 9 月の「ランキングの縮め方」(順位の数字を付けない)を
   撤回し、**ゲーム × モードごとの成績の順位**を作る(2026-10-02 に「同じ盤面でだけ」の
   条件をデイリーに限った)。熱心さの順位は引き続き作らない。線の引き方は下の「順位表」に書く。

**変えていない判断**はこれ以外の全部である。とくに Core の約束は 1 語も変わらない
(下の「定義」)。製品設計の正典は [architecture/club.md](architecture/club.md)、
順序と段取りは [plans/2026-09-30-public-club-house.md](plans/2026-09-30-public-club-house.md)。

### 定義

- **Core** — Club House を使っていない状態のアプリと Web 版。全ゲーム・コレクション・
  設定・バックアップ・結果の共有・バナー 1 枠・買い切り 1 商品。**本文書の他の全節は
  Core の約束**であり、Club House があっても 1 語も変えない。変えずに済む形にしか
  Club House を作らない。
- **Club House** — 同じ seed の挑戦をそれぞれの端末で遊んで、**結果だけ**を持ち寄る
  任意の層。**Solo by default. Social by choice.** デプロイは 2 つある。
  - **Public Club House** — PixApps が運用する 1 台。誰でも入れる。表示名だけで、
    アカウントは作らない。
  - **Private Club House** — 利用者(または招待してくれた知人)が自分で建てた 1 台。
    招待リンクでだけ入れる。建てる・払う・消すのは持ち主。
    2026-09-09 まで Private Game Club と呼んでいたものである。
- **実装側の語は変えない。** ディレクトリは `apps/simple-games/src/club/` のまま、
  CI ガードと import 境界の規則名も変えない。`Shared` は過去の文書に残る旧称で、
  新しい文面では使わない。
- Club House は Core の約束の**例外ではなく、Core の外**である。次の 4 つは Core に
  ついて真のままで、Club House はそのどれも Core について偽にしない。
  - **全ゲームがオフラインで最後まで遊べる。** 盤面の生成も保存も端末内。
  - **アカウント登録なし。** Public でも表示名だけで、PixApps に登録するものは無い。
  - **ゲームは PixApps のサーバーを 1 つも必要としない。** Public Club House が
    止まっても、消えても、全 30 ゲームは何も変わらず動く。これが「PixApps は
    サーバーを運用しない」の置き換えであり、**利用者が受け取る保証はここにある**。
  - **Core の画面に順位は出ない。** 順位を見るのは Club House の画面へ行った人だけ。

### Core が Club House から受け取る変更は次の 3 つまで

1. 設定 > Advanced の入口 1 つ(参加する / 自分の Club House を作る)。
2. 参加済みの端末に限り、コレクションホームの入口 1 つと、挑戦が自然に成立する
   ゲームの結果画面の操作 1 つ(#164。全ゲームへ機械的に足さない)。
3. 参加していない端末では、コレクションホームの静かな入口(Play together)1 つまで
   (#164)。

それ以外の Core の画面 — 初回起動・チュートリアル・盤面・結果画面の主要操作・広告・
購入 — に Club House は現れない。バッジ・モーダル・通知・Coming Soon で知らせない
(「初期リリースで実装しないもの」の Coming Soon 禁止はここにも効く)。**Public が
できても、この 3 つは増えない。**

### 2 つのデプロイ — 同じ体験、違う持ち主

- **Public を上位版にしない。** Public にあって Private に無い**ゲーム体験**を作らない。
  挑戦・結果・順位・記録は同じものが両方にある。差があってよいのは持ち主・入り方・
  宣伝枠・LP への露出だけで、これは運用の差であって機能の差ではない。
  逆に Private を不便にして Public へ誘導することもしない。
- **Public を課金の入口にしない。** Public 限定の有料機能・サブスク・Club House の
  SaaS 事業は作らない。
- **「同じ」とは API 契約のことである**(2026-09-30)。Public は Cloudflare、Private は
  Node + SQLite で、**実装は 2 つあってよい**。同一性はコードの共有ではなく、
  [architecture/club.md](architecture/club.md) §5 の契約と、両実装が通す同じ契約テストが
  示す。どちらかにしか無いエンドポイントを作らない。

### 両方のデプロイが守ること

- **通信は、参加した端末が、本人の操作の直後にだけ行う。** 参加していなければ
  0 リクエスト。ポーリング・バックグラウンド同期・常時接続・Push を持たない
  (「低消費電力の原則」はそのまま)。サーバの障害はゲームを止めず、Club House 1 つの
  障害を他の Club House や Core へ波及させない。
- **送るのは結果画面が表示した事実だけ。** 結果の共有(issue #86)と同じ線 — 結果画面に
  出た時間・スコア・ミス・ヒント回数と、そこでの表示名。進行・中断中の盤面・統計・
  自己ベストの履歴・お気に入り・設定・バックアップ・購入状態は送らない。送信は
  **本人が押したときだけ**で、参加しているだけでは何も上がらない。
- **アカウントを作らない。** password / email / OAuth / 電話番号なし。表示名と端末ごとの
  member token だけ。表示名の重複は許す — 自分の行は `You` で示す。接続情報
  (member token)はバックアップに入れない(`sg.iap` と同じ理由。
  [architecture/backup.md](architecture/backup.md))。
- **利用者が書ける公開物は表示名だけにする。** コメント・自由投稿・DM・フォロー /
  フレンド・いいね / リアクション・公開プロフィール・ソーシャルグラフは作らない。
  表示名には長さと文字種の制約を置き、通報と削除の手段を持つ。汎用のモデレーション
  基盤は作らない。
- **ゲーム機能を Club House の後ろに置かない。** 入っても入らなくても、全ゲーム・
  全機能・Hint / Undo は同じ。Club House 専用の盤面・モード・難易度を作らない
  (共有するのは seed だけ)。参加・招待・Host 化を、Core の何かの対価にしない。
- **急かさない。** 締切の強制・ストリーク・ログインボーナス・Push / ローカル通知・
  「まだ手に入れていないもの」を見せて呼び戻す仕掛けは Club House でも作らない。
- **お金に関わる文言は高リスクキーと同じ扱い。** hosting に費用がかかること・切断は
  サーバ削除ではないこと・削除は利用者が事業者側で行うことは、購入・削除の文言と
  同じ「誤訳が約束の反故になる文言」であり、機械翻訳で配らない
  ([I18N_POLICY.md](I18N_POLICY.md))。

### Public Club House だけの規則

- **広告ネットワークを入れない。** 置いてよいのは PixApps 自社アプリの静かな枠
  (`More from PixApps` 相当)1 つだけ。第三者広告ネットワーク・インタースティシャル・
  リワード広告・広告で解放される機能は無い。順位や結果の行に広告を混ぜない。参加・
  送信・閲覧を広告のために待たせない。**Private は広告ゼロ**で、この枠は Public の
  デプロイ層にだけ存在しゲームの成果物には入らない([ADS_POLICY.md](ADS_POLICY.md))。
- **公開されることを、参加の前に言う。** 表示名と送った結果が Public Club House と
  pixapps.ai の公開ページに出ることを、参加画面で開示する。**開示が先、送信が後**
  ([WEB_VERSION.md](WEB_VERSION.md)「計測」と同じ順序)。
- **LP へ出すのは読み取り専用の抜粋だけ。** Simple Games の公開ページが読むのは
  キャッシュ付きの公開ビューで、2 つ目の順位表データベースを持たない。ページには
  抜粋だけを出し、Club House の UI を複製しない。リアルタイム更新は要らない。
- **自分の Club House を建てる導線を必ず置く。** Public は入口であって終点ではない。
  技術用語ではなく利用者の言葉で、何が違うのか・誰に向くのか・誰が管理して誰が
  払うのか・どう招待するのか・どう復旧するのかを説明する。Docker やデータベースの
  理解を、判断の前提にしない。

### 順位表 — 成績の順位は作る、熱心さの順位は作らない

2026-09-30 の改定。撤回したのは「順位の数字・ポイント・称号を付けない」であって、
**その理由まで撤回したのではない**。残す線は「盤面の事実か、通った時間の長さか」である。
2026-10-02 に製品オーナーが「同じ盤面でだけ並べる」をデイリーに限った — ランダムな配札・
配置はゲームの一部で、何度も遊んで自己ベストを更新するのが競い方だから。

**作る(成績の順位)**

- **ゲーム × モードの中で、各メンバーの自己ベスト 1 行を並べ、番号を付ける。** 盤面は
  違ってよい。モードはゲームごとに決める(難易度・ティア・設定。[architecture/club.md](architecture/club.md)
  §6-1)。表の 1 行は自己ベストで、送った回数は表に出ない。
- **同じ盤面で競うのはデイリー。** 日付から seed を導くゲームのデイリーは世界中で同じ 1 つの
  盤面になり、その日の挑戦の中で順位が付く。デイリーの結果は上の表には入れない(同じ盤面で
  比べたものと、違う盤面で比べたものを混ぜない)。順位のためにサーバ側の盤面生成を作らない。
- 比較軸はゲームごとに [architecture/club.md](architecture/club.md) §6-1 が定める。時間と手数は
  小さいほど上、スコアは大きいほど上(低いほど良い点数のゲームは低いほど上)。同値は先に
  出した人が上。
- 勝ち負けしか無いゲーム(対 CPU のボードゲーム)には表を作らない — 勝った回数は熱心さの
  数だから。

**作らない(熱心さの順位)**

- XP / 利用量で上がるレベル / 「最も活発なプレイヤー」/ ログインストリーク /
  シーズン / 順位に対する報酬 / 期間限定の順位報酬。
- **積み上げない。** 通算・回数・ラダー・累積ポイントを持たない。表の 1 行は自己ベストで、
  Club House が持てる横断の値はそれだけである(ゲーム・モードの 1 位が**記録**)。
- **プレイ中と結果画面には出さない。** 順位を見るのは Club House の画面へ行った人だけで、
  Core の画面は参加の有無で変わらない。結果画面の `Send to Club` が返すのは「送った」の
  1 行で、順位の数字ではない。

### 費用の上限 — これが崩れたら Public は出さない

Public Club House を認めたのは、**固定費が限りなくゼロに近いという条件の下**である
(2026-09-30、製品オーナー判断)。「維持費の原則」の趣旨 — 固定費が無いから、それを
回収するためのサブスクや強い収益化をユーザーへ要求しなくて済む — はここでも守る。

- **無料枠に収まる構成から始める。** Cloudflare の Workers / Durable Objects を第一候補と
  し、常時起動のアプリサーバと managed database を既定にしない。
- **無料枠を超えたら、機能を削るかデプロイを畳む。** 利用者への課金・サブスク・広告の
  強化で埋めない。Public が消えても Core は 1 つも変わらず、Private だけで Club House は
  成立し続ける。
- **費用の driver を公開前に文書化し、上限・レート制限・濫用対策を最初から入れる。**
  無料枠の事故的な超過が起きうる形で公開しない。
- **実測する前に金額を書かない。** 「実施していない検証を成功扱いにしない」はここにも
  効く。Private 側のホスティング費についても同じ。

### 紹介

Simple Games 自身は、招待・参加・Host 化のどれにも報酬を出さず、数えず、表示しない。
Private Club House の持ち主が置ける**事業者側の referral リンク**を、「自分の Club House を
作る」を選んだ人向けの説明画面で 1 回運ぶまで。主となる CTA は「別の group が
Club House を持つのを助ける」であって、稼ぐことではない。事業者の制度が無くても同じ
UX が成立すること、併用可否や実コストが未確認のまま公開文面で謳わないことは変わらない。
紹介の順位表・紹介ストリーク・勧誘目標・PixApps 独自の報酬通貨や payout は作らない。

### 公開文面

- **出荷するまで 1 語も書かない**([BRAND.md](BRAND.md)「表現ルール」)。README・
  ストア掲載文・LP・GitHub metadata・プライバシーページに Club House を足すのは、
  実装を出荷した版から。
- 出荷後も **Core の約束は Core の主語で言う**。「The games never go online」
  「アカウント登録なし」は Core について真のままで、Club House を説明する文は
  デプロイの持ち主(PixApps か、あなたか、招待してくれた人)を主語にする。
  Club House について「オフライン」「サーバーなし」を言わない。
- **順位表を leaderboard と呼んでよい**(2026-09-30)。ただし Core の画面と
  ストア文面では引き続き使わない — Core に順位は無いからである。
- 出荷時にプライバシーページへ Club House の節を足す。何を、どのデプロイへ送り、
  誰の管理下に置かれ、どこに公開されるのかを書く。Public については、表示名と結果が
  公開ページに出ることを明示する。

### 機械で示すこと

「参加していない限り一切通信しない」を、文書ではなく CI で示す。2 つのデプロイが
できても**この 4 つは変わらない** — 通信するのは端末側の 1 ディレクトリだけだからである。

1. **ソース** — 通信 API(fetch / XMLHttpRequest / WebSocket / sendBeacon /
   EventSource)を書けるのは `apps/simple-games/src/club/` だけ。
   `.github/scripts/check-principles.sh` §1 は Core を例外なく赤にし、この 1 ディレクトリを
   パスで除外する(除外が他のパスを飲み込んでいないことを自己検査する)。位置情報は
   Club House でも禁止のまま。サーバ実装はこのリポジトリの `apps/*/src` /
   `packages/*/src` に置かない(別リポジトリ)ので、例外はこの 1 つに保てる。
2. **到達経路** — `club/` の外から `club/` への import は、`src/app/` からの動的
   `import()` だけ(入口は 1 か所に保つ)。静的 import は 1 本も許さず、ゲーム・`ui/`・
   `services/`・`storage/`・`i18n/`・`backup/` は `club/` を知らない
   (`src/test/importBoundaries.test.ts`)。`club/` がゲームへ触るのは registry 経由だけ。
3. **成果物** — `club/` を `game-<id>` と同じくビルドで独立したチャンクに分け、
   エントリの静的 import グラフから届かないことを `scripts/bundle-size.mjs` の
   初期グラフ検査で見る。成果物の `fetch(` の grep は**使わない** — native ビルドは
   Vite の modulepreload polyfill、`@capacitor/core`(CapacitorHttp)、
   `@capacitor/filesystem` がもともと `fetch(` を含む(2026-09-09 の dist で確認)。
   証明はトークンの不在ではなく、到達経路の不在で行う。
4. **実行時** — 動的 import を呼ぶのは、保存された接続がある場合、招待リンクを開いた
   操作のあと、そして本人が設定 > Advanced の入口かホームの `Play together` を押した
   操作のあと、の 3 つだけ。どれも無ければ呼ばれないこと、ホームを描いただけでは
   呼ばれないことをユニットテストで固定する。**Public があっても既定の接続先は
   持たない** — 端末は本人が参加するまで、どのデプロイの住所も知らない。

1 と 2 は 2026-09-09 の決定と同じ PR で入れてある(ディレクトリはまだ無く、除外と規則は
宣言だけ — どちらも自己検査を持つ)。3 と 4 は `club/` が生まれる PR の受け入れ条件。
