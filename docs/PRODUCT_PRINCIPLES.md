# Simple Games — プロダクト原則

Simple Games の全収録タイトルは以下を守る。これはブランドプロミスであり、
個別ゲームの都合で破ってはならない。

## コンセプト

**Honest by design. Simple games, built in the open.**
「無料ゲームを、誠実に。シンプルなゲームを、オープンに。
私たちの説明を信じる必要はありません。ソースコードを公開しています。」

コンセプト語: シンプル / 完全オフライン / 低消費電力 / 広告は控えめ / 急かさない /
サブスクなし / 機能課金なし / ログインなし / ソースコード公開

設計思想: **Built by subtraction.** 足すのではなく、削る。ユーザーへの体験価値としては
**Less between you and the game.**(下の「引き算の原則」)

## 引き算の原則(Built by subtraction)

Honest by design が「何を約束するか」なら、Built by subtraction は「何を足し、何を
足さないかをどう決めるか」である。2 つは別々のスローガンではなく 1 つの話で、削った
結果が下の「必須原則」になり、その約束を公開ソースで検証できる(issue #123)。

一般的な無料ゲームアプリは機能を足すことで競争する。Simple Games は、**ユーザーと
ゲームのあいだにある不要なものを削る**ことで差別化する。これは UI の簡素さだけの話では
なく、プロダクト・技術・収益モデルを貫く 1 本の判断軸である。

> We remove what gets between you and the game.
> あなたとゲームのあいだにあるものを、削る。

**目指すのは「少ない機能」ではなく「少ない負担」である。** 機能の数を減らすこと自体が
目的なら Hint も Undo も削れてしまうが、それはプレイヤーの負担を増やす。物差しは
「その機能はユーザーの操作・判断・通信・待ち時間・中断を減らすか、増やすか」であって、
機能の多寡ではない。

### 判断原則

> 新しい機能は、それによって増える複雑さと手数に見合う価値を示さなければならない。
> エンゲージメント機能を足すより、ユーザーの操作・判断・通信・待ち時間を減らすことを
> 優先する。

> Every new feature must justify the friction it adds. Prefer removing steps over
> adding engagement mechanics.

### 何を削り、何を削らないか

| 削るもの                            | 削らないもの                                             |
| ----------------------------------- | -------------------------------------------------------- |
| 不要なタップ・モード切替・探索      | ゲームそのもの                                           |
| ゲームを中断する広告                | 必要なゲーム機能                                         |
| サブスクリプション                  | Hint / Undo など、負担を減らす助け(形はゲームごとに違う) |
| 機能課金・広告視聴による機能解放    | ローカル保存                                             |
| アカウント登録                      | タッチ / マウス / キーボードで自然に遊ぶための入力経路   |
| 通知・ストリーク・人工的な緊急性    | アクセシビリティ                                         |
| オンライン依存                      | オフライン品質                                           |
| 不要なバックエンド / サーバーサイド | 低スペック端末での快適さ                                 |
| 大きなアプリサイズ・重いアセット    |                                                          |
| 不要な運用 / 固定インフラコスト     |                                                          |

アクセシビリティには例外が 1 つある: Android アプリでは、端末のフォントサイズを大きくしても
文字は 100% より大きくならない(下の「Android の文字の倍率」、2026-10-31)。

削る軸は 6 つある:

1. **操作を削る** — 遊び始めるまで・遊んでいる最中の不要なタップ・モード切替・
   中断を減らす(Zero Friction、issue #107)。お気に入りとゲーム名検索、Android の
   Pinned Shortcut と iOS の Quick Actions、進行中の局がちょうど 1 つならその盤面へ
   直接復帰、Solitaire 系のドラッグ移動、Minesweeper / Nonogram の右クリックと
   キーボード([ARCHITECTURE.md](ARCHITECTURE.md)「コレクションホーム」)。
2. **中断を削る** — Interstitial / Rewarded / App Open を持たず、盤面に重ならない
   小さなバナー 1 枠だけ([ADS_POLICY.md](ADS_POLICY.md))。レビューのお願いも
   ゲームからコレクションへ戻った瞬間にしか出さず、答えたら二度と聞かない
   ([REVIEW_PROMPT_POLICY.md](REVIEW_PROMPT_POLICY.md))。
3. **判断と義務を削る** — サブスクリプションなし、Hint / Undo を課金しない、
   アカウント不要、ストリークなし、通知なし、期間限定イベントなし。
4. **ネットワーク依存を削る** — ゲームロジックは端末内で完結し、初回起動から
   オフラインで動く。ゲームデータをサーバーへ送らない
   ([OFFLINE_POLICY.md](OFFLINE_POLICY.md))。
5. **アプリサイズを削る** — 盤面は端末内で生成し、重いアセットもコンテンツ配信も
   持たない。低速回線でも導入しやすく、モバイルデータを消費せず、ストレージの少ない
   端末にも入り、インストールから遊び始めるまでが短い。技術的な小ささではなく、
   設計判断として伝える。
6. **サーバーと固定コストを削る** — 下の「維持費の原則」。

**サーバーと固定コストを削るのは、開発者の都合ではなくユーザー価値である。**
API サーバー・クラウド DB・認証基盤を持たないことで、障害点が減り、オフライン動作が
成立し、継続的な固定費が発生しない。固定費が無いから、それを回収するための
サブスクリプションや強い収益化をユーザーに要求しなくて済む。Web 版も静的配信だけで
動く([WEB_VERSION.md](WEB_VERSION.md))。「オフライン・全ゲーム機能が無料・軽量」の
約束はこの構造の上に立っており、対外的に説明するときもこの順で言う — インフラの話では
なく、ユーザーが受け取るものの話として。

### 公開文面への反映の規則

- **「すでにそうなっている」だけを根拠にする。** LP・ストア掲載文・README に書くのは
  実装済み・検証済みの事実だけで、「これから作る」機能や未検証の性能を書かない。
  Zero Friction の各施策(お気に入り・検索・ショートカット・直接復帰・入力経路)は、
  実装が終わってから初めて公開文面に載せた。
- **数値は公開時点の実測値だけ。** アプリの配布サイズを「約 x MB」と書くときは、
  Play Console / App Store Connect が示す**その時点の**配布サイズを確認してから書き、
  未確認の数値を固定コピーにしない。リポジトリの `size-baseline.json` はバンドルの
  Gate であってストアの配布サイズではない。数字を書かずに「軽い」とだけ言うほうが、
  古い数字を残すより誠実である。
- **Honest by design と矛盾させない。** 削ったと言うものは実際に不在であること
  (機械判定できる範囲は `.github/scripts/check-principles.sh` が見る)。残したと言う
  ものは実際に無料・無制限であること。禁止表現は [BRAND.md](BRAND.md)「表現ルール」の
  まま。

## 必須原則

**適用範囲**: 以下は **Android アプリ**(ストアで配る製品)の約束である。同じソースから
配信するブラウザ版は役割が違い、広告・課金・オフライン・計測・収録タイミングの範囲に
ついて別の約束を持つ([WEB_VERSION.md](WEB_VERSION.md))。**版をまたいで必ず成立する**のは、課金ロックなし /
サブスクなし / **広告視聴や課金による機能解放なし** / アカウント登録なし / ストリークなし /
ゲームデータはローカル / ソースコード公開。**版によって異なる**のは、広告フォーマット
(アプリ = バナー 1 枠のみ / Web = 複数形式)、広告削除の買い切り(アプリのみ)、
オフラインの範囲(アプリ = 初回起動から / Web = 初回アクセスの読み込み後)、
計測(アプリ = Analytics なし。ただし Android に限り、EEA/UK/CH 等の同意が要る地域を
除く新規インストールについて、利用者の操作なしにインストールを 1 回だけ Meta に
知らせる獲得計測がある — 下の「Android の獲得計測(Meta)」/
Web = サイト共通のページ解析 — [WEB_VERSION.md](WEB_VERSION.md)「計測」、読み方と限界は
[GROWTH_MEASUREMENT.md](GROWTH_MEASUREMENT.md))、
収録タイミング(アプリ = 検証済みの正式収録のみ / Web = 新作の先行公開あり —
[WEB_VERSION.md](WEB_VERSION.md)「先行公開」)。
どちらの版でも、その版で成立しない約束を掲げない。

**Core と Club House**(2026-09-09 の issue #176、2026-09-30 の
issue `simple-games-club#1`): この文書の約束はすべて **Core** — Club House を使って
いない状態のアプリと Web 版、つまり誰もが受け取るもの — の約束である。
Club House(issue #161 / #164)は本人が明示的に参加したときだけ現れる任意の層で、
Core の約束の**例外ではなく Core の外**に置く。公式 **Public Club House**、利用者が建てる
**Self-hosted Club House** に、2026-10-23 のオーナー判断で PixApps が提供する
**Managed Club House** を加える。Managed はオーナーのホスティング契約で運用する。Club House を
一度も触らないプレイヤーにとって、この文書の約束は 1 語も変わらない。境界は本文書
末尾の「Club House」節が定める。

**Nearby Play**(2026-10-25、issue #268)は、下の同名節で許容する **Core の任意の
近隣端末間対戦**であり、Club House の層ではない。隔離 PoC を経て製品へ導入した。
入口は対応ゲームのトップの「誰かと遊ぶ」で、接続機能は Android / iOS に提供する。
本人が開始した集まりの接続を画面から独立して保持し、アプリ切替や一時切断からの継続を許容する。
採用した設計、出荷済みの版、実機で確認した範囲は区別する。

英語(ストア・対外表現の基準):

- No paywalls
- No subscriptions
- Banner ads only
- Optional one-time ad removal
- All games playable offline
- No account required
- No streaks or artificial urgency
- Local-first game data
- Low battery consumption
- Public source code

日本語:

- ゲーム機能の課金ロックなし
- サブスクリプションなし
- 広告はバナーのみ
- 広告削除は任意の買い切り
- 全ゲームをオフラインで利用可能
- アカウント登録なし
- ストリークや人工的な緊急性なし
- ゲームデータはローカルファースト
- 低消費電力
- ソースコード公開

補足:

- 全ゲーム機能は**初回起動から**オフラインで利用できる。広告を見なくても
  ゲームを最後まで遊べる(そのゲームが持つ Hint / Undo を含む)。広告取得を
  待つ必要がなく、広告取得失敗でゲームが停止しない。
- **助けは無料・無制限。ただし機能一覧を全ゲームで揃えない。** 各タイトルには
  「そのゲームの中身を空にしない形の助け」を用意する。原則は「Undo / Hint を
  広告視聴や課金の報酬にしない」ことであって、全タイトルに同じ 2 つのボタンを
  並べることではない。Minesweeper は **Undo を作らない**(推測なしで解けることを
  保証している以上、地雷を開くのは常にプレイヤーの判断であり、取り消せるなら
  賭けが残らない。代わりに同じ盤面への即時・無料の再挑戦を出す)。
  Sliding Puzzle は **Hint を作らない**(盤面は完全に見えており、隠れている情報が
  ないため、次の一手を教えることはパズルそのものを肩代わりしてしまう)。
  各タイトルの結論と理由はそのゲームのルール文書に書く。
- ゲームデータは端末内に保存。クラウド同期なし。**Core の画面に順位は出ない。**
  ゲーム内のペース車に対する着順はゲームの結果で、プレイヤー間の順位ではない(Hearts の清算画面と同じ —
  HEARTS_RULES.md §3.2・§3.3)。
  Nearby の参加者間で示す一局の点数・勝敗もその局の結果であり、局をまたぐ順位表は作らない。
  Nearby で相手へ渡す進行はそのセッションに必要なものだけで、保存・クラウド同期とは分ける(下)。
- API サーバーなし / アプリ用データベースなし / コンテンツ配信サーバーなし。
  (どちらも Core の約束。Club House に参加した端末が、本人の選んだデプロイへ、参加している
  間に遊び終えた結果だけを送るのはこの外側にあり、条件は「Club House」節 — 参加の前に
  開示し、送るのは結果画面が表示した事実だけで、進行・盤面・統計・設定は送らない。順位表もその層にあり、
  Core の画面には現れない。)
- 継続的なゲームイベント運営なし。ログインボーナス・期間限定イベント・
  エナジー/待ち時間タイマーを作らない。タイマープレッシャーを既定にしない。
- ソースコード公開は開発者向け機能ではなく、ユーザーがこれらの約束を
  検証できる仕組みである(BRAND.md)。

## 広告と課金

- 広告は **Anchored Adaptive Banner のみ**。オンライン時のみ表示し、
  オフライン時は広告リクエスト自体を行わない。
- Rewarded / Interstitial / Rewarded Interstitial / App Open / Native 広告は
  初期リリースに限らず**今後も採用しない**。盤面に重なる広告・進行を止める広告・
  広告視聴による機能解放も同様に禁止(ADS_POLICY.md)。
- アプリ内課金は「広告削除の買い切り(Remove Ads & Support Simple Games、
  基準価格 USD 3.99、一度だけ、購入復元あり)」の **1 商品のみ**。
  ゲーム機能は無料ユーザーと完全に同一。課金専用のゲーム・機能を作らない。
- 「Lifetime Access」という表現は使わない(無期限なのは広告削除権であって、
  アプリのサービス存続期間ではない)。

### PixApps の自社アプリの一覧は広告ではない

2026-10-29(issue #276)のオーナー判断で、Core のコレクションホームの**最後尾**に、同じ開発者の
別アプリ(PixMeal / PixWork)を並べる小さな一覧「PixApps のほかのアプリ(More from PixApps)」を
置く。目的は「Simple Games を作った人が他に何を作っているか」を、知りたい人が自分で見つけられる
ことで、送客の数を増やすことではない。**全ゲームの後でしか出会わないこと・見つけにくいことを
受け入れる。** 位置を上げる・目立たせる・押された数を測る変更は、この判断の外にある。

この一覧は**広告ではない**ので、「Banner ads only / 広告はバナーのみ」は真のまま。
そう言えるのは次の条件をすべて満たしているからで、どれか 1 つでも崩す変更は、広告の枠を
1 つ増やす変更として扱う。

- **自社の別アプリだけ。** 第三者のアプリ・広告ネットワーク・アフィリエイトは載せない。
  載せるアプリを足すのはこの節を改める判断であり、文言の追加ではない。
- **広告リクエストも計測も無い。** SDK・リモート設定・表示や押下の記録・UTM 等の
  追跡パラメータを持たない。リンク先はストアの掲載ページ(Android の Google Play /
  iOS の App Store。Web 版は端末から選び、判定できない PC は pixapps.ai の各アプリのページ)。
- **報酬・解放・特典と結びつけない。** 押しても何も解放されず、押さなくても何も失わない。
- **押した時だけ外へ出る。** 起動時・表示時の通信は 0 件。オフラインでは一覧ごと出さない
  ([OFFLINE_POLICY.md](OFFLINE_POLICY.md))。
- **ゲームと混ぜない。** ゲームの一覧・カテゴリ・収録数・検索・お気に入り・最近遊んだ・
  統計には入れない。位置と見た目の規則は
  [architecture/collection-home.md](architecture/collection-home.md)「PixApps のほかのアプリ」。
- **Simple Games の約束をそのアプリに貸さない。** 載せるアプリには、サブスク・アカウント・
  XP やバッジ・AI 機能など、Simple Games が作らないものがある。一覧には「別のアプリで、
  料金や機能はアプリごとに異なる」と必ず書き、説明はそのアプリ自身の公開ページの文言に限る
  ([BRAND.md](BRAND.md)「PixApps のほかのアプリの書き方」)。
- **煽らない。** アイコン画像・アニメーション・バッジ・ポップアップ・初回表示・通知・
  「今すぐ」「無料」の類を持たない。広告との区別は [ADS_POLICY.md](ADS_POLICY.md)
  「自社アプリの一覧は広告ではない」。

## 維持費の原則

**ゲームのために**以下の有料インフラを使用しない。

独自 API サーバー / アプリ用クラウド DB / ユーザー認証基盤 / クラウドセーブ /
オンラインランキング / マッチングサーバー / Push 通知配信サーバー / 独自分析サーバー /
AI API / CMS / 定期実行ジョブ / 有料問題生成 API / 有料ゲームバックエンド

既存の Google Play・Apple Developer・GitHub・AdMob を除き、
追加の固定インフラ費を発生させない。無料枠超過時に自動課金される構成に依存しない。

**ゲームは PixApps のサーバーを 1 つも必要としない。** 全ゲームの生成・保存・デイリー・
言語・テーマは端末内で完結し、PixApps 側が止まってもアプリと Web 版は何も変わらず
動く。上の一覧が守っているのはこの事実であり、**利用者が受け取る保証はここにある**。

**例外は Public Club House の 1 デプロイだけである**(2026-09-30、issue
`simple-games-club#1`)。2026-09-09 の「PixApps はサーバーを運用しない」は、この 1 台に
限って撤回した。そこには順位表があり、API があり、固定費がある — ただし**限りなく
ゼロに近いことが条件**で、無料枠を超えたら機能を削るかデプロイを畳む。利用者への
課金・サブスク・広告の強化で埋めない。条件と畳み方は「Club House」節「費用の上限」。
Private Club House のサーバは従来どおり利用者のもので、建てる・払う・消すのは持ち主。
ホスティング事業者のテンプレートは配布物であって運用ではない。

## 低消費電力の原則

通信と計算を最小にする。これは電池のためであると同時に、透明性のためでもある。

- 通常のゲームに定期ポーリング・バックグラウンド処理・常時接続を持たない。
  Nearby は本人が明示的に開始した集まりに限り、ゲームトップへ戻った間とアプリ切替中の
  接続維持、前面での同じ相手への再接続を許容する(下)。退出・解散で終了し、未利用時は無線を開始しない。
- オフライン時は広告取得のリトライを止める(リトライループを作らない)
- 画面外のゲームを描画しない(アンマウントする)
- 不要なアニメーションを避ける。タイマーは低頻度にする
- ゲームロジックは Pure TypeScript(重いランタイム・ネイティブ呼び出しに依存しない)
- 保存はイベント駆動で、頻度を常識的に保つ
- ローエンド Android 端末で快適に動作すること

## 初回体験の原則

初回起動時に求めてはならないもの:

ログイン / メールアドレス / ニックネーム / プロフィール / 通知許可 / 課金 /
購入ダイアログ / サブスクリプション / レビュー投稿 / 不要なアンケート

説明(How to Play)は 3 ステップ以内。説明後すぐゲームを開始する。
広告同意が法的に必要な場合でも、ゲーム初期化と切り離し、同意処理の失敗で
ゲームを停止させない。

## UI / UX の原則

- シンプル・静か・読みやすい・操作が予測可能
- ゲーム盤を最優先。不要な情報・演出を表示しない
- ユーザーを急かさない。ストリーク表示・連続日数カウンタを持たない
  (デイリーの「達成日カレンダー」は記録であり、これは持ってよい)
- 広告・課金への言及は謝罪調・強制調にしない。購入を繰り返し促さない
- Reduced Motion 有効時は不要なアニメーションを停止する
- **手応えは、盤面に既に見えている事実をもう一度言う形に限る**(2026-09-03)。
  効果音は「揃った・消した・できた大きさ」に応じて高くなるだけで、速くも大きくもならない。
  結果カードは完成した盤面を一拍見せてから出し、比べる相手は自分の記録だけ
  (`+0:18` / `−0:05`)。称号・実績ギャラリー・ストリーク・タイマー・通知・全ゲーム横断の
  経験値など、「まだ手に入れていないもの」を見せて呼び戻す仕掛けは作らない。
  記録(達成日、自己ベスト、レベル別のクリア)は持ってよいが、未達成の一覧は持たない

### デイリーは今日の 1 問

デイリーチャレンジは、端末のローカル日付で決まる **今日の 1 問** である(2026-10-02 に
過去日への遡りを廃止)。遡れるなら、それはデイリーではなくもう 1 つの出題モードになる。

- 過去の日付には遡れない。「過去のデイリー」の一覧も入口も持たない。
- 日付が過ぎた中断中のデイリーは捨てる。次に読み込むとき(起動・ゲームを開く)に、保存された
  デイリーの日付が今日と違えば復元せず、レコードを削除する。ホームの「デイリーチャレンジ」は
  つねに今日の問題へ向き、「続きから」と扱うのは今日の日付の盤面だけ。
- 遊んでいる最中の盤面は日付が変わっても取り上げない。終えればその日の達成として記録する。
- 急かさない。残り時間・期限・「あと n 時間」は出さない。盤面は黙って翌日の問題に替わるだけで、
  逃した日を数えもしない(ストリークを持たない原則と同じ)。
- 達成日の記録(カレンダー)は残す。未達成の日の一覧は持たない。
- 実装: 各ゲームの `storage/gamePersistence.ts` の `loadSavedGames(kv, today)` が別の日のデイリーを
  読み捨て、Home は `sessions.daily.dailyDate === today` のときだけ再開を出す。横断変更は
  `apps/simple-games/scripts/codemods/2026-10-02-daily-today-only.mjs`。

### 多言語と説明の原則

- 初回起動時に言語選択画面を出さない(端末の優先言語から解決し、即プレイ可能にする)
- 言語の切り替えでゲームの進行・保存データをリセットしない・壊さない
- アプリ内の文章は最小限に保つ。チュートリアルは 3 ステップ以内・図中心
- 詳細ルール・FAQ・攻略はアプリ内に持たず、ゲーム別 Landing Page へ分離する
- オフラインで外部リンク(Learn More 等)が開けなくてもゲームを止めない

## エンジニアリングの原則

- ゲームロジックは UI / 広告 / Capacitor に依存しない Pure TypeScript
- 依存方向は `apps → packages` のみ。循環依存禁止
- `games/A/` から `games/B/` への import 禁止。シェルはゲーム内部に踏み込まない
- ゲームごとに保存領域を分離する。一方のデータ破損が他方へ波及しない
- 一度しか使われていないコードを共通化しない(重複が確認されてから抽出)
- 巨大な共通ゲームフレームワークを作らない
- アプリへのゲームの正式収録・更新はアプリのリリースとして一体で行う。Web 版への
  先行公開はこれに先行してよい([WEB_VERSION.md](WEB_VERSION.md)「先行公開」)。
  ただしゲームの追加・更新が既存ゲームの挙動・保存データを変えてはならない
- ストア公開は明示的な手動実行またはタグを必要とする
- 実施していない検証を成功扱いにしない

## 初期リリースで実装しないもの

対人戦(Nearby の採用判断は下記) / オンラインランキング / フレンド / チャット / シーズン / 期間限定イベント /
ログインボーナス / 課金アイテム / ガチャ / バトルパス / ユーザープロフィール /
クラウド同期 / ソーシャルログイン / AI 機能 / オンライン問題配信 / Coming Soon 表示 /
Push 通知 / ローカル通知 / ストリーク表示 / Analytics / Remote Config /
Rewarded 広告 / Interstitial 広告 / App Open 広告 / Native 広告

このうち各種広告フォーマット・ストリーク・ログインボーナス・期間限定イベント・
Push/ローカル通知・Coming Soon 表示は「初期リリースで見送る」のではなく、
**採用しない**。Analytics も**アプリでは採用しない**。
Nearby の利用中に Android が必要とする接続維持の状態通知だけは、下記の限定した例外である。
Web 版のページ解析は「適用範囲」のとおり別の約束であり、
[WEB_VERSION.md](WEB_VERSION.md)「計測」が定める。Android の獲得計測(Meta)は
Analytics ではなく、下の「Android の獲得計測(Meta)」が定める期限つきの例外である
(プレイの記録・送信は、それによっても 1 つも増えない)。

この一覧と「採用しない」は Core のものである。**「オンラインランキング」は
2026-09-30 に扱いが変わった** — Core の画面には今も無いが、Club House の層では
ゲーム × モードごとの自己ベスト(デイリーだけは同じ盤面)の**成績の**順位を作る(「Club House」節「順位表」)。
Club House の中で何を持てて何を持てないかも同節が定める — そこでもリアルタイムの
対人戦・マッチング・フレンドグラフ・リアルタイムチャット・ソーシャルログイン・
クラウド同期・Push / ローカル通知・ストリーク・**熱心さの順位**は持たない。

**「対人戦・チャット」は 2026-10-25 に範囲を改定した。** 近隣端末間のオフライン対戦だけを
Core の任意モードとして許容する(次節)。インターネット経由の遠隔対戦は禁止のまま。

**共有報酬 / 招待ボーナス / 紹介コードも採用しない**(issue #86)。結果画面には
任意の共有があるが、押しても押さなくてもゲーム・進行・広告表示・解放される
ものは一切変わらず、催促も再要求もしない。共有は「気に入ったゲームを本人の
意思で渡す」ためのものであって、こちらが対価を出して買う行動ではない
([ARCHITECTURE.md](ARCHITECTURE.md)「レイヤー規則」)。Club House では、2026-10-23 に
採用した Managed オーナーの在籍メンバー数による広告非表示だけを別に定める
(「Managed Club House」)。結果共有や招待リンクを送る行為自体への報酬は作らない。

共有文と共有画像には、そのプレイの結果(結果画面が表示した時間・スコア・ミス・
ヒント回数など)を載せる(2026-09-03 に「数値を載せない」規則を撤回)。載せるのは
本人がボタンを押したときだけ・結果画面が表示した事実だけ・履歴は載せない・
勝っていない結果を勝ったと言わせない。ランキング・ストリーク・成績の保存や送信は
これによっても増えない。

## Nearby Play — 近くの人との対戦・チャット

2026-10-25 のオーナー判断で、隔離 PoC に続く製品実装を採用し、1.5.1 の実機フィードバック後に
ゲームを起点とする導線へ改定した。**対応ゲームのトップから「誰かと遊ぶ」。**
近くの相手と Bluetooth／同一 Wi-Fi で遊ぶ機能であることを短く補足する。
Club House は記録・ランキング、Nearby Play はその場限りの近隣対戦である。

- Android / iOS の任意機能。対象は **2人・1対1ターン制の13本・任意の短いテキストチャット**に、
  2026-10-26のオーナー指示で追加する **4席のLudo・人間とCPUの混成対局**。
  募集の入口は対応ゲームのトップに置く。コレクションには参加専用の「近くの対戦相手を探す」を加え、
  Club House直下に、Club Houseと同程度の控えめなテキスト行として配置する。
  Bluetooth／同一Wi-Fiを明示選択して全対応ゲームの募集名・ゲーム名・人数を一覧表示する。
  一覧で選ぶと、そのゲームの参加・host承認・双方Readyへ進む。
  探索画面下部の「対戦サポートゲーム」から全14本の通常トップを開ける。移動前に探索を止める。
  Club House からも開始しない。対応は Yacht / Reversi / Connect Four / Gomoku / Checkers / Gin Rummy / Mancala / Dominoes / Dots and Boxes / Chess / Nested Tic-Tac-Toe / Scopa / Nim / Ludo。それ以外のゲームに未実装のボタンを置かない。
  ゲーム選択済み → 募集／参加 → host承認 → 双方Ready → 既存と共通のゲーム画面へ進む。
  初回に同じゲームを改めて提案する操作は求めない。内部protocolの提案・確認処理は維持できる。
- **席数はゲームごとに固定し、席とその操作担当を分ける。** 既存13本は2席、Ludoは4席。
  今回の混成対局はLudoに限る。hostは残り3席の人間／CPUを開始前・対局中に切り替えられる。
  人間からCPUへ替えても、その席の駒・手番・出目を引き継ぐ。CPUから人間へ戻すときは接続中の
  本人へ操作を戻す。勝手な振り直しや盤面の初期化はしない。
  操作担当を変更した後に旧担当の入力が届いても適用しない。host本人は対局の管理者として残る。
  **3席以上の対戦はすべて、離席・退出・復帰・参加の受付について共通の約束に従う**
  （正本は [architecture/nearby-multiplayer.md](architecture/nearby-multiplayer.md)。現在使うのはLudoだけ）。
  ゲストの明示的な退出は即座にその席をCPUにし、その人はその対局へ戻れない。
  通信が切れただけの離席では席を本人のものとして残し、全員が待つ。CPUへ替えるかはhostが手動で決め、
  システムは自動で替えない。戻るときにhostの承認は要らない。hostが離席しても全員が待ち、
  集まりを終えるのはhostの明示的な退出だけで、host移譲はしない。
  参加は対局と対局の間だけ受け付け、対局中の部屋は探索一覧に出さない。
  Ludoのチャットは今回の対象外。対局履歴は既存のNearby専用保存に分けて追加し、
  ソロの保存・統計・Clubへ混ぜない。4台の実機検証は別途必要で、対応機種の保証にはしない。
- Web のコレクションには無効な「近くの対戦相手を探す」、対応14本のトップには無効な「誰かと遊ぶ」ボタンと「アプリ専用の機能です」を表示する。
  英語は “Play with someone” / “Available in the app only.”。接続画面への遷移は無く、
  Web に Nearby の実行コード・探索・権限要求・接続・履歴読取を追加しない。
  ソロ / CPU 戦は従来どおり遊べる。未対応ゲームにはこの案内を置かない。
- **ゲームが主、チャットは任意の補助。** 既存13本では募集時にhostが有無を選び、初期値はOFF。
  設定は双方へ適用し、終了まで固定する。参加者にも対局開始前に有無を示す。OFFでは会話ボタンを
  出さず、送受信も認めない。ONの会話は本人がボタンから開き、ゲームと同格のタブにしない。
  受信しても自動表示しない。終局後は結果と再戦を主にし、同じ接続で双方Readyを
  確認して再戦する。集まりのゲームは開始時に固定し、別ゲームへ移るときは集まりを終了して作り直す。
- 募集名と個人の表示名を分ける。募集名はゲーム名＋短い番号を初期値として編集でき、募集中は
  募集名とゲームを近くの探索者に公開する。開始前にこの範囲を説明する。
  個人の表示名は接続後の対局・チャットに使い、募集名・OSの端末名で代用しない。
  個人の表示名・OSの端末名・install ID・履歴は探索情報に含めない。名前は本人認証ではない。
  一覧の探索だけを閉じれば無線を止め、参加後の対戦はホームへ戻っても保持する。
- 「仲間と／近くの人を募集」の2択は置かず、すべての参加にhost承認を必須とする。定員はゲームごとの席数を上限とする。
  参加申請は個人の表示名だけで、自由コメントは設けない。公開される発見用番号は認証情報でも本人確認でもない。
- インターネット・ログイン・対戦サーバー・Club 加入は不要。Bluetooth を既定にし、
  同一 Wi-Fi の LAN を明示的な代替とする。自動切替、遠隔対戦、友達グラフ、DM、画像、
  再訪通知は追加しない。Android の利用中の接続維持通知だけを許容する。Web での近隣対戦は非対応。
  通常のソロ / CPU 戦は影響を受けない。
- 通信は本人が始めた集まりだけ。利用時だけ OS 権限を求める。接続の寿命は画面から分離し、
  ゲームトップへ戻るだけでは切らない。同じ「誰かと遊ぶ」の入口から進行中の対戦へ戻れる。
  会話を閉じる操作やアプリ切替でも明示的に切断しない。
  既存13本では一時切断・受信確認待ちの期限超過は対局を終了せず、盤面と未確認操作を保持して待機する。
  同じ相手を確認して再接続し、重複操作を適用せず続行する。明示的な退出・解散は終了。
  OS による実行停止を無制限に回避する約束はしない。現実装の継続状態・鍵はメモリ内であり、
  プロセス終了・強制終了・端末再起動からの対局復元は未対応。履歴を開いても再接続しない。
  3席以上の集まり（現在はLudo）でも、切断中は席と盤面を保持して全員が待つ。hostがCPUへ切り替えれば
  継続できる。離席した人は前面で同じhostを見つけ直し、最初の承認時の継続鍵による確認でhostの承認なしに
  同じ席へ戻る。リンクが切れている間に押した退出は相手に届かない。
- **チャットと対局履歴は各参加端末にだけ保存する。** 自分が送受信したメッセージ、
  募集名、参加者の表示名、ゲーム・日時・結果を保持し、退出では消さない。履歴閲覧は通信しない。
  自分の履歴を削除しても相手のコピーは消えない。サーバー、Club、通常のバックアップ、
  OS のクラウドバックアップへ送らない。明示終了した途中の対局は中断として残す。
- 不適切な内容には端末内の限定的な表現チェックを行い、完全な検出は約束しない。
  募集一覧の非表示はその探索の間だけ。接続後と対応する履歴からのブロックは、受信した相手の
  アプリ識別子をこの端末に保存して行う。古い履歴に識別子が無い場合はブロック操作を出さない。
  通報は本人が対象と理由を選び、全文を確認して同意した後にメール下書きまたはコピーを用意する。
  アプリは自動送信せず、全履歴や識別子を添付しない。本人が外部のメールアプリで送信した内容は
  サポートへ届くため、「履歴を端末だけに保存する」通常動作とは区別して説明する。
- 自分の表示名を同じ端末で次回も使えるよう保存し、開始前に変更できる。別端末への設定同期はしない。
  保存先はNearby専用データで、通常バックアップ・OSバックアップ・Clubには含めない。
  履歴1件の削除では保存した表示名を保ち、Nearby全削除・設定のローカルデータ削除では一緒に消す。
- 各ゲームの盤面・手札・操作は既存 CPU 戦と同じ画面部品を使う。相手が人間でも
  別ゲームの操作体験にしない。既存 CPU 戦の統計・自己ベスト・保存・ランキングには混ぜない。
  一方的なUndoは設けない。Gin Rummy / Dominoes / Scopa の非公開手札・山札・乱数seedは相手へ送らない。
  host が確定するモデルで、
  改造 host の不正防止は保証しない。端末内ブロックはアプリの識別子に対するもので、
  再インストールや改造を越える本人認証ではない。
- テキストは上限・受信確認を持つ。受信確認は既読を意味しない。保存失敗や容量上限を
  隠さず、保存済みの古い履歴を無断で消さない。退出とチャット非表示を用意する。
- 製品コードは `src/nearby/` と各 OS の製品所有 native source に置く。PoC から import
  しない。第三者通信 SDK を追加しない。配布・実機・プライバシー・UGC 運用の検証と
  ストア公開は実装と別であり、未確認項目を成功扱いしない。

今回の導線と接続保持は採用方針であり、修正版の実機検証済みを意味しない。
技術・画面遷移の契約は [architecture/nearby-multiplayer.md](architecture/nearby-multiplayer.md)。
過去の製品体験の検討は [plans/2026-10-25-club-nearby-ux.md](plans/2026-10-25-club-nearby-ux.md) に保持する。
PoC の実測は [作業記録](plans/2026-10-25-nearby-multiplayer-poc.md) に保持する。

## Android の獲得計測(Meta)— 期限つきの例外

2026-09-27 決定(issue #204、オーナー合意)。2026-09-29、オーナーの判断で同意方式を
やめ、対象地域では自動送信に変更した(許可した人だけでは大半のインストールが Meta に
届かず、Meta の学習が進まなかったため)。運用・送信内容・手作業・撤去手順の正本は
[META_ANDROID_ACQUISITION.md](META_ANDROID_ACQUISITION.md)。

**これは「アプリには Analytics を入れない」からの明示的な変更である。** 獲得のためだから
既存の方針と同じ、とは扱わない。Web に着地する Meta 広告はすでに出しているが、Android
アプリを直接インストールさせる広告(Meta → Google Play)は、インストールの信号が
アプリから Meta に届かないと計測も最適化もできない。そのためだけに、Android 版へ
Meta の App Events SDK(`facebook-core`)を入れる。

境界 —— これを越える変更は、この節を先に改める:

1. **Android だけ。** iOS・Web には SDK・通信を足さない。
2. **送るのはインストールの 1 件だけ。** 「このアプリがインストールされた」という Meta の
   標準の報告を、インストールごとに 1 回。ゲーム・プレイ時間・盤面・スコア・勝敗・
   レベル・Hint / Undo・保存データ・購入 / 復元・広告収益・セッション・画面・操作は
   送らない。利用者の連絡先・位置情報を渡さない。リターゲティング用のイベントを送らない。
   **広告 ID(Android Advertising ID)はこの 1 件の報告に限り送る** —— 2026-09-29 より前は
   送っていなかったが、対象地域での自動送信への変更にあわせて有効にした。SDK が
   合わせて付ける情報(端末情報・Facebook アプリの計測用 ID など)は
   META_ANDROID_ACQUISITION.md §4 が一覧を持つ。
3. **同意は求めない。地域で送る/送らないを分ける。** EU・EEA(アイスランド/
   リヒテンシュタイン/ノルウェー)・英国・スイスとその関連地域では送らない(SIM・
   ネットワーク・端末の地域設定のいずれかが該当する、またはどれも分からなければ
   送らない)。それ以外の地域では、新規インストールに対して利用者への質問・確認画面
   なしに自動で送る。アプリ内の同意ダイアログと Settings の切り替えは廃止した。
4. **新規インストールだけを報告する。** 既存インストールの更新(例: v1.2.2 → v1.3.x)は
   `firstInstallTime` が変わらないため、インストールとしては報告しない。受理されるまで
   起動のたびに上限回数まで再試行し、再試行は 7 日の期限に縛られない。受理された端末は
   二度と送らない。
5. **既定は「無い」。** 明示的に有効化したリリースビルドにだけ SDK が入り、それ以外の
   ビルド(debug を含む)には存在しない。これは CI がビルドされた APK で示す。
6. **期限つき。** 目標は Android 版の累計 1,000+ installs で、到達時に獲得広告の停止と
   SDK の撤去を判断する。恒久的な行動分析基盤にしない。延長するなら理由と次の見直し
   条件を明記する。停止のためにサーバーや Remote Config を作らない。
7. **開示が先、送信が後。** 公開プライバシーポリシーとデータ セーフティを実装と一致させて
   から有効化する。「ゲームデータを送らない」と「SDK 由来の獲得情報(広告 ID を含む)は
   対象地域で自動的に送る」を区別して書き、包括的な「トラッキングなし」や「許可した
   場合だけ送る」という、対象地域では実態と矛盾する表現を残さない。
8. **Audience Network(アプリ内広告)ではない。** 広告はバナー 1 枠のまま、広告削除の
   買い切りも変えない。
9. **アプリ内に opt-out はない。** 利用者の手段は、Android の設定で広告 ID を
   リセット/削除する、Meta 自身の設定を使う、アンインストールする、の 3 つ。送った 1 件を
   アプリから取り消す手段は無い。同意が要る地域と判定した端末(SIM・ネットワーク・地域
   設定のどれかが該当、またはどれも不明。一度判定したら記録して以後も送らない)では何も
   送らない —— 位置情報を使わない推定であり、判定の限界は runbook §6。

機械で示すこと: 追跡系の依存は release 限定・フラグ付きの `facebook-core` 1 行だけ
(`check-principles.sh` §3b)、SDK に触れるのはネイティブの 1 ディレクトリだけ(同 §8 a)で、
任意のイベント・購入・セッション・利用者データを送る API を呼ばない(同 §8 b)、manifest で
SDK の自動動作を止めている(同 §8 c)、JS から呼び出す口(`@PluginMethod`)自体が無い
(同 §8 d)、APK の権限・初期化 provider・
SDK の有無(`check-android-artifact.sh`)。

## Android の文字の倍率 — 上げる条件つきの例外

2026-10-31 決定(オーナー判断)。計測と、選べた案の記録は
[plans/2026-10-30-android-os-text-size.md](plans/2026-10-30-android-os-text-size.md)。

**これは「アクセシビリティは削らない」(上の「何を削り、何を削らないか」)からの明示的な
変更である。** Android の WebView は、アプリが倍率を決めない限り、端末の「フォントサイズ」の
倍率どおりに文字だけを大きくする(画面の大きさは変わらない)。盤の大きさを画面の高さから
決めるゲームは、上部バーや操作バーの高さを文字 100% で測った px として引いている。
2026-10-30 の計測(正式収録の 65 本、Android 17 のエミュレータ)では、130% で 14 本が崩れ
(5 本は軽微)、200% では 360×640 で 19 本が崩れて、うち 16 本はバナーの枠の下や上部バーの
上へ出た。崩れないと測れているのは 100% だけで、盤や操作にバナーが重なる形は [ADS_POLICY.md](ADS_POLICY.md) が
禁じ、AdMob も広告の配信を止めることがある。各ゲームを直し終えるまで、文字のほうを止める。

境界 —— これを越える変更は、この節を先に改める:

1. **Android アプリの WebView の文字の倍率だけ。** `MainActivity` が
   `setTextZoom(min(端末の倍率 × 100, 100))` を当てる。端末のフォントサイズを 100% より
   大きくしても、アプリの文字は 100% の大きさのまま。小さくする設定はそのまま効く。
2. **ほかは変えない。** iOS(WKWebView は「さらに大きな文字」で px の文字を大きくしない。
   WebKit の挙動で、端末では確かめていない)、Web 版(ブラウザの文字の設定に従う。測って
   いない)、Android の「表示サイズ」(画面全体が大きくなる)、TalkBack や拡大表示などの
   支援技術。
3. **倍率を決めるのは 1 か所。** `MainActivity` のほかに、JS から倍率を変える経路
   (`@capacitor/text-zoom` など)を作らない。

上げる条件 —— 上限は、その倍率で崩れないことを測ってから上げる。測るのはプレイ画面だけでなく、
設定・ルール・ダイアログ・結果などの画面も含み、言語による差(計測の記録の「原因」)も見る。
日付の期限は置いていない:

- **115%**: Sudoku・Yacht・Nested Tic-Tac-Toe を直す(計測の記録で 115% までに崩れる見込みの
  3 本)。盤の中で切れたマス・横のはみ出し・「…」を見る検査を計測に足し、115% を 2 サイズ
  (360×640・411×914)で測る。
- **130%**: 130% で崩れた 14 本を直し、同じ検査で 130% を 2 サイズで測る。
- **上限を外す**: 200% まで同じように測れたとき。

上げるときは `MainActivity` の `TEXT_ZOOM_CAP_PERCENT`、`check-principles.sh` §9、この節を
同じ PR で変え、100% と書いたほかの文書(ARCHITECTURE・architecture/platforms.md・I18N_POLICY・
RELEASE_CHECKLIST)も直す。

機械で示すこと: `MainActivity` の形 —— 上限の定数が 1 つで値が 100、端末の倍率との小さい方を
取った次の行で `setTextZoom` に渡すこと(呼び出しはその 1 か所)、`onCreate` の中で
`super.onCreate` の後に当てること —— と、アプリのネイティブのコードと依存の宣言に、ほかに倍率を
決める経路が無いこと(`check-principles.sh` §9)。依存するライブラリの中身と、実行時に効くことは
機械では示さない。端末で上限が効くことは、人が [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md) §4 で
確かめる。

## Club House — Core の外にある任意の層

2026-09-09 に Shared(自前サーバだけ)として定めた層を、2026-09-30 に **Club House** へ
改めた(issue `simple-games-club#1`、Epic #175)。その時点で変えた判断は次の 2 つである。

1. **PixApps が 1 デプロイだけ運用する。** 2026-09-09 の「PixApps はサーバーを 1 台も
   運用しない」を撤回し、**Public Club House** という公式デプロイ 1 つに限って認める。
   撤回の理由は下の「費用の上限」に書く条件が付いているからで、条件が崩れたら畳む。
2. **成績の順位表を作る。** 同 9 月の「ランキングの縮め方」(順位の数字を付けない)を
   撤回し、**ゲーム × モードごとの成績の順位**を作る(2026-10-02 に「同じ盤面でだけ」の
   条件をデイリーに限った)。熱心さの順位は引き続き作らない。線の引き方は下の「順位表」に書く。

**2026-10-23 の追加判断**は下の「Managed Club House」に定める。とくに Core の約束は変わらない
(下の「定義」)。製品設計の正典は [architecture/club.md](architecture/club.md)、
順序と段取りは [plans/2026-09-30-public-club-house.md](plans/2026-09-30-public-club-house.md)。

### 定義

- **Core** — Club House を使っていない状態のアプリと Web 版。全ゲーム・コレクション・
  設定・バックアップ・結果の共有・バナー 1 枠・買い切り 1 商品。**本文書の他の全節は
  Core の約束**であり、Club House があっても 1 語も変えない。変えずに済む形にしか
  Club House を作らない。
- **Club House** — それぞれの端末で遊んで、**結果だけ**を持ち寄る(デイリーは全員が同じ盤面、それ以外は自己ベストの比べ合い)
  任意の層。**Solo by default. Social by choice.** 運用の形は 3 つある。
  - **Public Club House** — PixApps が運用する 1 台。誰でも入れる。表示名だけで、
    アカウントは作らない。
  - **Self-hosted Club House** — 利用者(または招待してくれた知人)が自分で建てた 1 台。
    招待リンクでだけ入れる。建てる・払う・消すのは持ち主。
    2026-09-09 まで Private Game Club と呼んでいたものである。
    (v1.4.0 は Public だけを出す。招待リンクでの参加は**隠す** — Private は次の版で、予告
    (Coming Soon)も置かない。[architecture/club.md](architecture/club.md) §7-3。)
  - **Managed Club House** — PixApps がクラブごとの保存領域を提供する。オーナーだけが
    ホスティング契約を持ち、通常メンバーの参加とゲームは無料。公開範囲と承認の設定は
    運用形態から切り離す。[architecture/managed-clubs.md](architecture/managed-clubs.md) が契約である。
- **実装側の語は変えない。** ディレクトリは `apps/simple-games/src/club/` のまま、
  CI ガードと import 境界の規則名も変えない。`Shared` は過去の文書に残る旧称で、
  新しい文面では使わない。
- Club House は Core の約束の**例外ではなく、Core の外**である。次の 4 つは Core に
  ついて真のままで、Club House はそのどれも Core について偽にしない。
  - **全ゲームがオフラインで最後まで遊べる。** 盤面の生成も保存も端末内。
  - **アカウント登録なし。** Public でも表示名だけで、PixApps に登録するものは無い。
  - **ゲームは PixApps のサーバーを 1 つも必要としない。** Public Club House が
    止まっても、消えても、すべてのゲームは何も変わらず動く。これが「PixApps は
    サーバーを運用しない」の置き換えであり、**利用者が受け取る保証はここにある**。
  - **Core の画面に順位は出ない。** 順位を見るのは Club House の画面へ行った人だけ。

### Managed Club House — 2026-10-23 のオーナー判断

Railway 等へのデプロイをクラブ作成の前提にせず、PixApps が Cloudflare 上でクラブを
提供する。これは従来の「Club House の SaaS 事業は作らない」を明示的に改めた判断である。
オーナーが場を作り、参加者と対象ゲームを管理し、預かった記録をまとめるための契約とする。

- **Trial は無料・期限なしで 1 クラブ 5 メンバー、最大 1 クラブ**。自分で開始できる。
  **Basic は 1 クラブ 50 メンバー、最大 3 クラブ**。オーナーも人数に含む。
  Trial から Basic へは同じクラブ・メンバー・記録を保って移行する。
  将来の Plus は 100 メンバー × 5 クラブ、MAX は人数上限なし × 100 クラブ。
  Plus / MAX は未提供の定義で、現時点の API は契約の付与を拒否する。価格は未定。
- **公開 / 非公開**と**承認が必要 / 不要**は独立する。非公開は招待キーが必要で、
  通常の招待キーは承認を飛ばさない。公開は名前・人数・対象ゲーム等を発見できる意味であり、
  記録を未参加者へ公開する意味ではない。公開かつ承認不要なら誰でも参加して記録を読める。
- オーナーが対象ゲームを選ぶ。選択外の新しい結果は端末から送らず、サーバーも受け取らない。
  設定変更だけで過去の記録を消さず、本人による削除は続けられる。Core では全ゲームが使える。
- **オーナーの記録帳**は、管理するクラブの現在の成績をまとめる。人数は現在有効な
  クラブ内メンバーの単位で数え、自己ベストの分布は 1 人 1 件とする。別クラブの同名の人を
  同一人物と推測しない。保持上限で消えた結果から総プレイ回数・成功率・過去の推移を作らない。
- **記録アルバム**はオーナーが発行し、そのクラブのメンバーが読む。現在の保持記録への
  参照を固定した記録集であり、全期間の完全な履歴ではない。本人の削除、メンバーの無効化、
  保持上限による削除を回避する裏のコピーを残さない。通常の記録閲覧は一般メンバーにも開く。
- **所有クラブの在籍メンバーが合計 50 名以上なら、オーナーの広告を非表示にする。**
  承認済みで現在有効なメンバーを、オーナー本人も含めてクラブごとに合算する。
  申請中・無効化済みの人は含めず、クラブをまたいで同一人物とは推測しない。
  特典はホスティングが有効で条件を満たす間のもの。永久の購入済み状態にはしない。
  契約キーを接続した端末のアプリ・Web ゲームに適用し、通常メンバー全員の特典にはしない。
  オーナー画面だけに現在の人数と有効状態を表示する。ゲーム機能・結果共有は条件にしない。
  起動時は最後に確認した期限内の端末キャッシュを使い、確認通信はオーナー画面の
  読み込み・更新で行う。既存の広告削除 IAP と資格・保存先を分ける([ADS_POLICY.md](ADS_POLICY.md))。
- 通常メンバーの資格と、**オーナーの契約キー**を分ける。キーは端末に保存しても
  バックアップには入れず、運用者の資格付与キーをクライアントへ入れない。オーナーが
  自分で有料の契約期間・枠を増やせる API を作らない。無料 Trial は本人が開始する。
  1 人であることの認証は追加せず、枠は契約キーごとのもの。メール・パスワード・追跡用 ID は追加しない。
- 初回の実装は**本人が無料 Trial を開始し、運用者が有効期限つきの Basic 枠を付与・
  移行する段階**である。決済・価格・
  自動更新・ストアでの販売は未実装。契約期限後も既存記録の閲覧と本人の削除は可能で、
  新クラブ・新メンバー・新記録の受け付けを止める。自動削除や課金開始を暗黙に行わない。
- Managed の費用はオーナー向けサービスの収支として検証し、公式 Public の無料運営費の
  規則と分ける。MAX は保持量・集計・同時利用の実測と設計を終えるまで有効化しない。
- 入口は `MANAGED_CLUBS_ENABLED` を true にしたビルドだけに出す。新しい公開範囲・
  送信同意・資格・削除文言の翻訳確認と運用設定を済ませるまで公開しない。

### Core の導線に加える変更は次の 3 つまで

1. 設定 > Advanced の入口 1 つ(参加する / 自分の Club House を作る)。
2. 参加済みの端末に限り、コレクションホームの入口 1 つ(参加中の Club の行と、その下の
   「新しい Club House に参加」の 1 行。2026-10-24 にオーナー判断で 2 行目を足した —
   別の Club への参加が 2 画面奥にあり、辿り着けなかったため)と、挑戦が自然に成立する
   ゲームの結果画面の状態表示 1 行(#164。全ゲームへ機械的に足さない)。2026-10-02 に
   「操作 1 つ(`Send to Club` のボタン)」から読み替えた — 結果は参加中に自動で送られ、
   結果画面は押すものを持たず、何が起きたかを 1 行で言うだけ。
3. 参加していない端末では、コレクションホームの静かな入口(Play together)1 つまで
   (#164)。

それ以外の Core の画面 — 初回起動・チュートリアル・盤面・結果画面の主要操作・広告・
購入 — に Club House の勧誘は現れない。上記のオーナー特典による広告非表示は、既存の
広告判定に端末内の資格を加えるだけで、入口や購入済み表示を追加しない。
バッジ・モーダル・通知・Coming Soon で知らせない
(「初期リリースで実装しないもの」の Coming Soon 禁止はここにも効く)。**Public が
できても、この 3 つは増えない。**

### 2 つのデプロイ — 同じ体験、違う持ち主

- **Public を上位版にしない。** Public にあって Private に無い**ゲーム体験**を作らない。
  挑戦・結果・順位・記録は同じものが両方にある。差があってよいのは持ち主・入り方・
  宣伝枠・LP への露出だけで、これは運用の差であって機能の差ではない。
  逆に Private を不便にして Public へ誘導することもしない。
- **公式 Public のメンバーを課金必須にしない。** 自分の Managed Club を作る任意の
  オーナー契約は上の規則に従う。既存ゲームや一般メンバーの記録閲覧を有料にしない。
- **「同じ」とは API 契約のことである**(2026-09-30)。Public は Cloudflare、Private は
  Node + SQLite で、**実装は 2 つあってよい**。同一性はコードの共有ではなく、
  [architecture/club.md](architecture/club.md) §5 の契約と、両実装が通す同じ契約テストが
  示す。どちらかにしか無いエンドポイントを作らない。

### すべての運用形態が守ること

- **通信は、本人の Club 操作の直後にだけ行う。** Club を操作しない未参加の端末は
  0 リクエスト。ここでいう行為は、Club の画面を開く・参加する・Managed の一覧や
  オーナー画面を開く・Trial を開始する・**参加中のゲームを 1 局遊び終えて
  結果が現れる**こと。ポーリング・バックグラウンド同期・常時接続・Push を持たない
  (「低消費電力の原則」はそのまま)。ネットワークに届かなかった結果は端末のキューに残り、
  次の結果を送るときと Club の画面を開いたときにだけ再送する — **起動時・タイマー・
  接続の回復では送らない**。サーバの障害はゲームを止めず、Club House 1 つの
  障害を他の Club House や Core へ波及させない。
- **送るのは結果画面が表示した事実だけ。** 結果の共有(issue #86)と同じ線 — 結果画面に
  出た時間・スコア・ミス・ヒント回数と、そこでの表示名。進行・中断中の盤面・統計・
  自己ベストの履歴・お気に入り・設定・バックアップ・購入状態は送らない。**参加する前に
  遊んだ局は決して送らない。** 参加している間は、遊び終えた結果が参加している
  すべての Club へ**自動で**送られる(2026-10-02 の改定。以前は「送信は本人が押した
  ときだけ」としていた — 押さずに次の盤面へ進んだ良い記録が失われるのを、製品オーナーが
  望まなかった)。**同意の場所は結果ごとのボタンから参加の画面へ移る**: 次の
  「公開されることを、参加の前に言う」のとおり、参加の前に言う。切断すれば以後は
  送られない。対応するゲームの結果だけが対象。Minesweeper で地雷を踏んだ局、Number Match の
  行き止まり、Dominoes で勝てなかった局は送らない。点数を競うゲーム(2048 や、対 CPU の Reversi・
  Hearts など)は、ゲームオーバーや負けの局でもその点数を送る(club.md §14 判断 30)。
- **自分の記録は、本人が自分で、1 件ずつ消せる。名前も自分で直せる**(2026-10-02)。自分の記録の**横の削除
  ボタン**(ランキングの自分の行、デイリーの自分の結果)から、いつでも、確認のあとにその 1 件だけが消える
  (メンバーのまま残る。ランキングの行は次の局でまた入る。**デイリーの結果を消すと、その日の挑戦から抜ける**
  ことになり、その挑戦へはもう結果を送れない — 「最初に完了した結果が数える」は変わらない)。表示名は
  Club の Settings で変えられる。どちらも持ち主の手を借りない(持ち主も自分のものはできる)。
  **全部の記録を一度に消すボタンは作らない。** **参加(入る・切断する)と記録の削除は別のもの**で、
  切断しただけでは記録は消えない — 消したい人は切断の前に消す。公開の説明(プライバシーページ)もそう言う。
- **通常メンバーにアカウントを要求しない。** password / email / OAuth / 電話番号なし。
  表示名と端末ごとの member token だけ。Managed オーナーの契約キーは上の規則で分ける。
  表示名の重複は許す — 自分の行は `You` で示す。接続情報
  (member token)はバックアップに入れない(`sg.iap` と同じ理由。
  [architecture/backup.md](architecture/backup.md))。
  **端末を識別する値は作らない**(device id・指紋・広告 ID を Club House に使わない)。同じ端末で同じ Club に
  入り直すと**同じメンバーに戻る**(2026-10-02)のは、切断した Club の member token を端末が持っている間だけ
  — それ以上でも以下でもない。アンインストール・`Reset Local Data`・別の端末は**別の人**として入り直すことに
  なり、サーバはそれを「同じ人」と推測しない。別の人として入り直した前の行は、前の名前のまま残る —
  残したくない人は、**入り直す前に自分の記録を 1 件ずつ消す**。
- **公開物は表示名とクラブを識別する情報に限定する。** Managed の発見一覧にはクラブ名・
  人数・対象ゲーム・承認要否を載せる。アルバムの題はメンバー内に限る。コメント・自由投稿・DM・フォロー /
  フレンド・いいね / リアクション・公開プロフィール・ソーシャルグラフは作らない。
  表示名には長さと文字種の制約を置き、通報と削除の手段を持つ。汎用のモデレーション
  基盤は作らない。
- **ゲーム機能を Club House の後ろに置かない。** 入っても入らなくても、全ゲーム・
  全機能・Hint / Undo は同じ。Club House 専用の盤面・モード・難易度を作らない
  (共有するのは seed だけ)。2026-10-23 に明示した Managed オーナーの広告非表示を
  除き、参加・招待・Host 化を Core の特典の条件にしない。ゲーム機能は一切条件にしない。
- **急かさない。** 締切の強制・ストリーク・ログインボーナス・Push / ローカル通知・
  「まだ手に入れていないもの」を見せて呼び戻す仕掛けは Club House でも作らない。
  オーナー本人が開く画面には、50 名の広告非表示条件と現在の在籍数を静かに表示してよい。
- **お金に関わる文言は高リスクキーと同じ扱い。** hosting に費用がかかること・切断は
  サーバ削除ではないこと・削除は利用者が事業者側で行うことは、購入・削除の文言と
  同じ「誤訳が約束の反故になる文言」であり、機械翻訳で配らない
  ([I18N_POLICY.md](I18N_POLICY.md))。

### Public Club House だけの規則

- **広告ネットワークを入れない。** Club House の画面に置いてよいのは PixApps 自社アプリの静かな枠
  (`More from PixApps` 相当)1 つだけ。第三者広告ネットワーク・インタースティシャル・
  リワード広告・広告で解放される機能は無い。順位や結果の行に広告を混ぜない。参加・
  送信・閲覧を広告のために待たせない。**Private は広告ゼロ**で、Club House の画面のこの枠は
  Public のデプロイ層にだけ置き、Private の Club House の画面には置かない。
  **Core のコレクションホーム末尾の一覧はこの枠とは別物**で、Club House の層ではなく Core の
  一部としてどのビルドにも同じく出る(2026-10-29、issue #276。上の「PixApps の自社アプリの一覧は
  広告ではない」)。広告ではないので、Private のデプロイが Web 版を配っていても「広告ゼロ」は
  真のまま([ADS_POLICY.md](ADS_POLICY.md)「自社アプリの一覧は広告ではない」)。
- **参加の前に、参加中は遊び終えた結果が自動で送られることを言う。** 参加の画面で、
  Public でも Private でも、参加の全経路(Public・貼った招待リンク・招待 URL)に開示する。
  加えて Public では、表示名と送った結果が Public Club House と pixapps.ai の公開ページに
  出ることを開示する。**開示が先、送信が後**([WEB_VERSION.md](WEB_VERSION.md)「計測」と
  同じ順序)。結果ごとのボタンで同意を取り直さないので、この開示が同意のすべてである —
  文言は高リスクキーとして門を通す([I18N_POLICY.md](I18N_POLICY.md))。
  自動送信が無かった版で参加した接続は、この開示を見ていない。その接続は、持ち主が Club の画面で
  同じ開示を受け入れるまで何も送らない。
  (デイリーは最初に完了した結果が確定する。この点は参加の画面ではまだ言っていない —
  [architecture/club.md](architecture/club.md) §14 末尾の「未決」。言うなら新しい高リスクの文言になる。)
- **LP へ出すのは読み取り専用の抜粋だけ。** Simple Games の公開ページが読むのは
  公開ビューで、2 つ目の順位表データベースを持たない。2026-10-23 の公開範囲設定からは
  古い公開情報を残さないため `no-store` とし、その読み取り費用を別途検証する。ページには
  抜粋だけを出し、Club House の UI を複製しない。リアルタイム更新は要らない。
- **自分の Club House を建てる導線を必ず置く。** Public は入口であって終点ではない。
  技術用語ではなく利用者の言葉で、何が違うのか・誰に向くのか・誰が管理して誰が
  払うのか・どう招待するのか・どう復旧するのかを説明する。Docker やデータベースの
  理解を、判断の前提にしない。

### 順位表 — 成績の順位は作る、熱心さの順位は作らない

2026-09-30 の改定。撤回したのは「順位の数字・ポイント・称号を付けない」であって、
**その理由まで撤回したのではない**。残す線は「盤面の事実か、通った時間の長さか」である。
2026-10-02 に製品オーナーが「同じ盤面でだけ並べる」をデイリーに限った — ランダムな配札・
配置はゲームの一部で、何度も遊んで自己ベストを更新するのが競い方だから。
2026-10-10 に製品オーナーが「表の 1 行は自己ベスト」を撤回し、**結果ごとに 1 行**にした — 最高記録
以外の局も記録に残したいから。同時に、表の中の 1〜3 位の印と、自分の 1 つ上との差を出すことを認めた
([plans/2026-10-10-club-ranking-rows.md](plans/2026-10-10-club-ranking-rows.md))。

**作る(成績の順位)**

- **ゲーム × モードの中で、遊び終えた結果を 1 件 1 行で並べ、番号を付ける**(2026-10-10。それまでは
  各メンバーの自己ベスト 1 行だった)。盤面は違ってよい。モードはゲームごとに決める(難易度・ティア・設定。
  [architecture/club.md](architecture/club.md) §6-1)。同じ人が何度も並ぶ。1 人が 1 つの表に持てる行数には
  上限があり、超えた分はその人の最も悪い行から落ちる(同 §16-1)。回数の合計や集計は、表にも別の場所にも
  出さない。
- **表の中の印と、1 つ上との差は出してよい**(2026-10-10)。1〜3 位の行に色分け・メダルの印を付け、
  自分の最良の行には 1 つ上の値との差を添える。印はその表の中のもので、持ち越す称号・実績ではない。
  差は静かな 1 行で、期限・通知・後ろとの差を伴わない。
- 名前を押すと、その人が入っている表の一覧(表ごとの順位と最良の値)が見える(2026-10-22)。それ以外 — 通算・局数・
  最終プレイ・自由文 — は載せず、プロフィールにはしない。
- **同じ盤面で競うのはデイリー。** 日付から seed を導くゲームのデイリーは世界中で同じ 1 つの
  盤面になり、その日の挑戦の中で順位が付く。全員同じ盤面のデイリー(2026-10-02 時点で 21 本)の
  結果は上の表には入れない(同じ盤面で比べたものと、違う盤面で比べたものを混ぜない)。
  **例外(リードの設計注記。オーナーの確認はまだ無い)**: Minesweeper(初手で地雷が変わる)と
  Number Recall(やり直すたびに配置が変わる)のデイリーは全員同じ盤面ではないので、ゲームの通常の
  局としてその難易度の表へ入る([architecture/club.md](architecture/club.md) §14 末尾)。
  順位のためにサーバ側の盤面生成を作らない。
- 比較軸はゲームごとに [architecture/club.md](architecture/club.md) §6-1 が定める。時間と手数は
  小さいほど上、スコアは大きいほど上(低いほど良い点数のゲームは低いほど上)。同値は先に
  出した人が上。
- 勝ち負けしか無いゲーム(対 CPU のボードゲーム)には表を作らない — 勝った回数は熱心さの
  数だから。

**作らない(熱心さの順位)**

- XP / 利用量で上がるレベル / 「最も活発なプレイヤー」/ ログインストリーク /
  シーズン / 順位に対する報酬 / 期間限定の順位報酬。
- **積み上げない。** 通算・回数・ラダー・累積ポイントを持たない。表の 1 行は 1 つの結果で、
  表をまたいで足し合わせた値を Club House は持たない(ゲーム・モードの 1 位が**記録**)。
- **プレイ中と結果画面には出さない。** 順位を見るのは Club House の画面へ行った人だけで、
  Core の画面は参加の有無で変わらない(参加済みの端末の結果画面が持つのは、送れたかを言う
  状態 1 行だけ)。その行が返すのは「送った」で、順位の数字ではない。

### 公式 Public の費用の上限 — Managed の収支とは分ける

Public Club House を認めたのは、**固定費が限りなくゼロに近いという条件の下**である
(2026-09-30、製品オーナー判断)。「維持費の原則」の趣旨 — 固定費が無いから、それを
回収するためのサブスクや強い収益化をユーザーへ要求しなくて済む — はここでも守る。

- **無料枠に収まる構成から始める。** Cloudflare の Workers / Durable Objects を第一候補と
  し、常時起動のアプリサーバと managed database を既定にしない。
- **無料枠を超えたら、機能を削るかデプロイを畳む。** 利用者への課金・サブスク・広告の
  強化で埋めない。Public が消えても Core は 1 つも変わらず、Private だけで Club House は
  成立し続ける。
- **費用の driver を公開前に文書化し、上限・レート制限・濫用対策を最初から入れる。**
  無料枠の事故的な超過が起きうる形で公開しない。
- **自動送信で読み書きの量の driver が変わった(2026-10-02)。** 以前は「ボタンを押した数」だった
  サーバへの書き込みが、「参加している Club の数 × 遊び終えた局の数」になる。1 日 10 万リクエストの
  天井と 1 メンバー 1 分 60 リクエストの上限が、Public のデプロイでなお足りるかは、v1.4.0 を出す前に
  再確認する([RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md) 5.17 の前提、
  [architecture/club.md](architecture/club.md) §15-3)。
- **実測する前に金額を書かない。** 「実施していない検証を成功扱いにしない」はここにも
  効く。Private 側のホスティング費についても同じ。

### 紹介

Simple Games 自身が扱う特典は、上記の Managed オーナーの在籍メンバー数による
広告非表示に限る。招待の送信数や紹介の成果を数える報酬・順位は作らない。
Private Club House の持ち主が置ける**事業者側の referral リンク**を、「自分の Club House を
作る」を選んだ人向けの説明画面で 1 回運ぶまで。主となる CTA は「別の group が
Club House を持つのを助ける」であって、稼ぐことではない。事業者の制度が無くても同じ
UX が成立すること、併用可否や実コストが未確認のまま公開文面で謳わないことは変わらない。
紹介の順位表・紹介ストリーク・勧誘目標・PixApps 独自の報酬通貨や payout は作らない。

### 公開文面

- **出荷するまで 1 語も書かない**([BRAND.md](BRAND.md)「表現ルール」)。README・
  ストア掲載文・LP・GitHub metadata・プライバシーページに Club House を足すのは、
  実装を出荷した版から。
- 出荷後も **Core の約束は Core の主語で言う**。「The games never go online」
  「アカウント登録なし」は Core について真のままで、Club House を説明する文は
  デプロイの持ち主(PixApps か、あなたか、招待してくれた人)を主語にする。
  Club House について「オフライン」「サーバーなし」を言わない。
- **順位表を leaderboard と呼んでよい**(2026-09-30)。ただし Core の画面と
  ストア文面では引き続き使わない — Core に順位は無いからである。
- 出荷時にプライバシーページへ Club House の節を足す。何を、どのデプロイへ送り、
  誰の管理下に置かれ、どこに公開されるのかを書く。Public については、表示名と結果が
  公開ページに出ることを明示する。**参加している間は遊び終えた結果が自動で送られる**こと
  (ボタンで選ぶものとして書かない)、参加の前の局は送られないこと、送れなかった結果は端末に
  残って後で送られることを書く。Club House の公開文面は、結果の送信を「結果ごとの任意」と
  説明しない。送られるのは対応するゲームだけである(「すべてのゲーム」と書かない)。

### 機械で示すこと

「Club を操作せず、参加していない端末では Club の通信をしない」を、文書ではなく CI で示す。2 つのデプロイが
できても**この 4 つは変わらない** — 通信するのは端末側の 1 ディレクトリだけだからである。

1. **ソース** — 通信 API(fetch / XMLHttpRequest / WebSocket / sendBeacon /
   EventSource)を製品の TypeScript ソースに書けるのは `apps/simple-games/src/club/` だけ。
   `.github/scripts/check-principles.sh` §1 は Core を例外なく赤にし、この 1 ディレクトリを
   パスで除外する(除外が他のパスを飲み込んでいないことを自己検査する)。位置情報は
   Club House でも禁止のまま。サーバ実装はこのリポジトリの `apps/*/src` /
   `packages/*/src` に置かない(別リポジトリ)ので、例外はこの 1 つに保てる。
   Nearby PoC は製品ソースの外に隔離し、この除外を広げない。製品から PoC への import と
   Web / 製品成果物への混入を禁止する。製品Nearbyは別所有の `src/nearby/` とnative実装を使い、
   ゲームtopからの明示開始・画面から独立した接続保持・明示終了を専用の境界検査で扱う。
2. **到達経路** — `club/` の外から `club/` への import は、`src/app/` からの動的
   `import()` だけ(入口は 1 か所に保つ)。静的 import は 1 本も許さず、ゲーム・`ui/`・
   `services/`・`storage/`・`i18n/`・`backup/` は `club/` を知らない
   (`src/test/importBoundaries.test.ts`)。`club/` がゲームへ触るのは registry 経由だけ。
3. **成果物** — `club/` を `game-<id>` と同じくビルドで独立したチャンクに分け、
   エントリの静的 import グラフから届かないことを `scripts/bundle-size.mjs` の
   初期グラフ検査で見る。成果物の `fetch(` の grep は**使わない** — native ビルドは
   Vite の modulepreload polyfill、`@capacitor/core`(CapacitorHttp)、
   `@capacitor/filesystem` がもともと `fetch(` を含む(2026-09-09 の dist で確認)。
   証明はトークンの不在ではなく、到達経路の不在で行う。
4. **実行時** — 動的 import を呼ぶのは、保存された接続がある場合、招待リンクを開いた
   操作のあと、そして本人が設定 > Advanced の入口かホームの `Play together` を押した
   操作のあと、の 3 つだけ。どれも無ければ呼ばれないこと、ホームを描いただけでは
   呼ばれないことをユニットテストで固定する。**Public があっても既定の接続はしない** —
   アプリが名前で知っている住所は Public の 1 つだけ(`club/public.ts`)で、それは
   `club/` のチャンクの中にしか無く、チャンクは上の操作のあとにしか読まれない。読まれても、
   本人が参加(`Join`)を押すまで、どのデプロイにもリクエストは出ない(2026-10-02、実装に
   合わせて改訂 — 以前の「どのデプロイの住所も知らない」は、Public の住所をアプリが持つ
   club.md §15-1 と食い違っていた)。

1 と 2 は 2026-09-09 の決定と同じ PR で入れてある(ディレクトリはまだ無く、除外と規則は
宣言だけ — どちらも自己検査を持つ)。3 と 4 は `club/` が生まれる PR の受け入れ条件。
