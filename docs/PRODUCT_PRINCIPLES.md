# Simple Games — プロダクト原則

Simple Games の全収録タイトルは以下を守る。これはブランドプロミスであり、
個別ゲームの都合で破ってはならない。

## コンセプト

**Honest by design. Simple games, built in the open.**
「無料ゲームを、誠実に。シンプルなゲームを、オープンに。
私たちの説明を信じる必要はありません。ソースコードを公開しています。」

コンセプト語: シンプル / 完全オフライン / 低消費電力 / 広告は控えめ / 急かさない /
サブスクなし / 機能課金なし / ログインなし / ソースコード公開

設計思想: **Built by subtraction.** 足すのではなく、削る。ユーザーへの体験価値としては
**Less between you and the game.**(下の「引き算の原則」)

## 引き算の原則(Built by subtraction)

Honest by design が「何を約束するか」なら、Built by subtraction は「何を足し、何を
足さないかをどう決めるか」である。2 つは別々のスローガンではなく 1 つの話で、削った
結果が下の「必須原則」になり、その約束を公開ソースで検証できる(issue #123)。

一般的な無料ゲームアプリは機能を足すことで競争する。Simple Games は、**ユーザーと
ゲームのあいだにある不要なものを削る**ことで差別化する。これは UI の簡素さだけの話では
なく、プロダクト・技術・収益モデルを貫く 1 本の判断軸である。

> We remove what gets between you and the game.
> あなたとゲームのあいだにあるものを、削る。

**目指すのは「少ない機能」ではなく「少ない負担」である。** 機能の数を減らすこと自体が
目的なら Hint も Undo も削れてしまうが、それはプレイヤーの負担を増やす。物差しは
「その機能はユーザーの操作・判断・通信・待ち時間・中断を減らすか、増やすか」であって、
機能の多寡ではない。

### 判断原則

> 新しい機能は、それによって増える複雑さと手数に見合う価値を示さなければならない。
> エンゲージメント機能を足すより、ユーザーの操作・判断・通信・待ち時間を減らすことを
> 優先する。

> Every new feature must justify the friction it adds. Prefer removing steps over
> adding engagement mechanics.

### 何を削り、何を削らないか

| 削るもの                            | 削らないもの                                             |
| ----------------------------------- | -------------------------------------------------------- |
| 不要なタップ・モード切替・探索      | ゲームそのもの                                           |
| ゲームを中断する広告                | 必要なゲーム機能                                         |
| サブスクリプション                  | Hint / Undo など、負担を減らす助け(形はゲームごとに違う) |
| 機能課金・広告視聴による機能解放    | ローカル保存                                             |
| アカウント登録                      | タッチ / マウス / キーボードで自然に遊ぶための入力経路   |
| 通知・ストリーク・人工的な緊急性    | アクセシビリティ                                         |
| オンライン依存                      | オフライン品質                                           |
| 不要なバックエンド / サーバーサイド | 低スペック端末での快適さ                                 |
| 大きなアプリサイズ・重いアセット    |                                                          |
| 不要な運用 / 固定インフラコスト     |                                                          |

削る軸は 6 つある:

1. **操作を削る** — 遊び始めるまで・遊んでいる最中の不要なタップ・モード切替・
   中断を減らす(Zero Friction、issue #107)。お気に入りとゲーム名検索、Android の
   Pinned Shortcut と iOS の Quick Actions、進行中の局がちょうど 1 つならその盤面へ
   直接復帰、Solitaire 系のドラッグ移動、Minesweeper / Nonogram の右クリックと
   キーボード([ARCHITECTURE.md](ARCHITECTURE.md)「コレクションホーム」)。
2. **中断を削る** — Interstitial / Rewarded / App Open を持たず、盤面に重ならない
   小さなバナー 1 枠だけ([ADS_POLICY.md](ADS_POLICY.md))。レビューのお願いも
   ゲームからコレクションへ戻った瞬間にしか出さず、答えたら二度と聞かない
   ([REVIEW_PROMPT_POLICY.md](REVIEW_PROMPT_POLICY.md))。
3. **判断と義務を削る** — サブスクリプションなし、Hint / Undo を課金しない、
   アカウント不要、ストリークなし、通知なし、期間限定イベントなし。
4. **ネットワーク依存を削る** — ゲームロジックは端末内で完結し、初回起動から
   オフラインで動く。ゲームデータをサーバーへ送らない
   ([OFFLINE_POLICY.md](OFFLINE_POLICY.md))。
5. **アプリサイズを削る** — 盤面は端末内で生成し、重いアセットもコンテンツ配信も
   持たない。低速回線でも導入しやすく、モバイルデータを消費せず、ストレージの少ない
   端末にも入り、インストールから遊び始めるまでが短い。技術的な小ささではなく、
   設計判断として伝える。
6. **サーバーと固定コストを削る** — 下の「維持費の原則」。

**サーバーと固定コストを削るのは、開発者の都合ではなくユーザー価値である。**
API サーバー・クラウド DB・認証基盤を持たないことで、障害点が減り、オフライン動作が
成立し、継続的な固定費が発生しない。固定費が無いから、それを回収するための
サブスクリプションや強い収益化をユーザーに要求しなくて済む。Web 版も静的配信だけで
動く([WEB_VERSION.md](WEB_VERSION.md))。「オフライン・全ゲーム機能が無料・軽量」の
約束はこの構造の上に立っており、対外的に説明するときもこの順で言う — インフラの話では
なく、ユーザーが受け取るものの話として。

### 公開文面への反映の規則

- **「すでにそうなっている」だけを根拠にする。** LP・ストア掲載文・README に書くのは
  実装済み・検証済みの事実だけで、「これから作る」機能や未検証の性能を書かない。
  Zero Friction の各施策(お気に入り・検索・ショートカット・直接復帰・入力経路)は、
  実装が終わってから初めて公開文面に載せた。
- **数値は公開時点の実測値だけ。** アプリの配布サイズを「約 x MB」と書くときは、
  Play Console / App Store Connect が示す**その時点の**配布サイズを確認してから書き、
  未確認の数値を固定コピーにしない。リポジトリの `size-baseline.json` はバンドルの
  Gate であってストアの配布サイズではない。数字を書かずに「軽い」とだけ言うほうが、
  古い数字を残すより誠実である。
- **Honest by design と矛盾させない。** 削ったと言うものは実際に不在であること
  (機械判定できる範囲は `.github/scripts/check-principles.sh` が見る)。残したと言う
  ものは実際に無料・無制限であること。禁止表現は [BRAND.md](BRAND.md)「表現ルール」の
  まま。

## 必須原則

**適用範囲**: 以下は **Android アプリ**(ストアで配る製品)の約束である。同じソースから
配信するブラウザ版は役割が違い、広告・課金・オフライン・計測・収録タイミングの範囲に
ついて別の約束を持つ([WEB_VERSION.md](WEB_VERSION.md))。**版をまたいで必ず成立する**のは、課金ロックなし /
サブスクなし / **広告視聴や課金による機能解放なし** / アカウント登録なし / ストリークなし /
ゲームデータはローカル / ソースコード公開。**版によって異なる**のは、広告フォーマット
(アプリ = バナー 1 枠のみ / Web = 複数形式)、広告削除の買い切り(アプリのみ)、
オフラインの範囲(アプリ = 初回起動から / Web = 初回アクセスの読み込み後)、
計測(アプリ = Analytics なし / Web = サイト共通のページ解析 —
[WEB_VERSION.md](WEB_VERSION.md)「計測」、読み方と限界は
[GROWTH_MEASUREMENT.md](GROWTH_MEASUREMENT.md))、
収録タイミング(アプリ = 検証済みの正式収録のみ / Web = 新作の先行公開あり —
[WEB_VERSION.md](WEB_VERSION.md)「先行公開」)。
どちらの版でも、その版で成立しない約束を掲げない。

**Core と Shared**(2026-09-09、issue #176): この文書の約束はすべて **Core** —
Shared を有効化していない状態のアプリと Web 版、つまり誰もが受け取るもの — の
約束である。Shared(Private Game Club、issue #161)は利用者が自分で建てたサーバへ
明示的に接続したときだけ現れる任意の層で、Core の約束の**例外ではなく Core の外**に
置く。Shared を一度も触らないプレイヤーにとって、この文書の約束は 1 語も変わらない。
Shared の側が守る境界は本文書末尾の「Shared」節が定める。

英語(ストア・対外表現の基準):

- No paywalls
- No subscriptions
- Banner ads only
- Optional one-time ad removal
- All games playable offline
- No account required
- No streaks or artificial urgency
- Local-first game data
- Low battery consumption
- Public source code

日本語:

- ゲーム機能の課金ロックなし
- サブスクリプションなし
- 広告はバナーのみ
- 広告削除は任意の買い切り
- 全ゲームをオフラインで利用可能
- アカウント登録なし
- ストリークや人工的な緊急性なし
- ゲームデータはローカルファースト
- 低消費電力
- ソースコード公開

補足:

- 全ゲーム機能は**初回起動から**オフラインで利用できる。広告を見なくても
  ゲームを最後まで遊べる(そのゲームが持つ Hint / Undo を含む)。広告取得を
  待つ必要がなく、広告取得失敗でゲームが停止しない。
- **助けは無料・無制限。ただし機能一覧を全ゲームで揃えない。** 各タイトルには
  「そのゲームの中身を空にしない形の助け」を用意する。原則は「Undo / Hint を
  広告視聴や課金の報酬にしない」ことであって、全タイトルに同じ 2 つのボタンを
  並べることではない。Minesweeper は **Undo を作らない**(推測なしで解けることを
  保証している以上、地雷を開くのは常にプレイヤーの判断であり、取り消せるなら
  賭けが残らない。代わりに同じ盤面への即時・無料の再挑戦を出す)。
  Sliding Puzzle は **Hint を作らない**(盤面は完全に見えており、隠れている情報が
  ないため、次の一手を教えることはパズルそのものを肩代わりしてしまう)。
  各タイトルの結論と理由はそのゲームのルール文書に書く。
- ゲームデータは端末内に保存。クラウド同期なし。オンラインランキングなし。
- API サーバーなし / アプリ用データベースなし / コンテンツ配信サーバーなし。
  (どちらも Core の約束。Shared を有効化した端末が、本人の選んだサーバへ挑戦の結果
  だけを送るのはこの外側にあり、条件は「Shared」節 — 送るのは結果画面が表示した事実
  だけで、進行・盤面・統計・設定は送らない。)
- 継続的なゲームイベント運営なし。ログインボーナス・期間限定イベント・
  エナジー/待ち時間タイマーを作らない。タイマープレッシャーを既定にしない。
- ソースコード公開は開発者向け機能ではなく、ユーザーがこれらの約束を
  検証できる仕組みである(BRAND.md)。

## 広告と課金

- 広告は **Anchored Adaptive Banner のみ**。オンライン時のみ表示し、
  オフライン時は広告リクエスト自体を行わない。
- Rewarded / Interstitial / Rewarded Interstitial / App Open / Native 広告は
  初期リリースに限らず**今後も採用しない**。盤面に重なる広告・進行を止める広告・
  広告視聴による機能解放も同様に禁止(ADS_POLICY.md)。
- アプリ内課金は「広告削除の買い切り(Remove Ads & Support Simple Games、
  基準価格 USD 3.99、一度だけ、購入復元あり)」の **1 商品のみ**。
  ゲーム機能は無料ユーザーと完全に同一。課金専用のゲーム・機能を作らない。
- 「Lifetime Access」という表現は使わない(無期限なのは広告削除権であって、
  アプリのサービス存続期間ではない)。

## 維持費の原則

以下の有料インフラを使用しない。

独自 API サーバー / アプリ用クラウド DB / ユーザー認証基盤 / クラウドセーブ /
オンラインランキング / マッチングサーバー / Push 通知配信サーバー / 独自分析サーバー /
AI API / CMS / 定期実行ジョブ / 有料問題生成 API / 有料ゲームバックエンド

既存の Google Play・Apple Developer・GitHub・AdMob を除き、
追加の固定インフラ費を発生させない。無料枠超過時に自動課金される構成に依存しない。
PixApps はサーバーを運用しない。

Shared(Private Game Club)のサーバも同じである — 建てる・払う・消すのは利用者で、
PixApps は 1 台も持たず、中央 hub・中継・登録簿・公式インスタンスも作らない
(「Shared」節)。ホスティング事業者のテンプレートは配布物であって運用ではない。

## 低消費電力の原則

通信と計算を最小にする。これは電池のためであると同時に、透明性のためでもある。

- プレイ中の定期ポーリングなし。バックグラウンド処理なし。常時接続なし
- オフライン時は広告取得のリトライを止める(リトライループを作らない)
- 画面外のゲームを描画しない(アンマウントする)
- 不要なアニメーションを避ける。タイマーは低頻度にする
- ゲームロジックは Pure TypeScript(重いランタイム・ネイティブ呼び出しに依存しない)
- 保存はイベント駆動で、頻度を常識的に保つ
- ローエンド Android 端末で快適に動作すること

## 初回体験の原則

初回起動時に求めてはならないもの:

ログイン / メールアドレス / ニックネーム / プロフィール / 通知許可 / 課金 /
購入ダイアログ / サブスクリプション / レビュー投稿 / 不要なアンケート

説明(How to Play)は 3 ステップ以内。説明後すぐゲームを開始する。
広告同意が法的に必要な場合でも、ゲーム初期化と切り離し、同意処理の失敗で
ゲームを停止させない。

## UI / UX の原則

- シンプル・静か・読みやすい・操作が予測可能
- ゲーム盤を最優先。不要な情報・演出を表示しない
- ユーザーを急かさない。ストリーク表示・連続日数カウンタを持たない
  (デイリーの「達成日カレンダー」は記録であり、これは持ってよい)
- 広告・課金への言及は謝罪調・強制調にしない。購入を繰り返し促さない
- Reduced Motion 有効時は不要なアニメーションを停止する
- **手応えは、盤面に既に見えている事実をもう一度言う形に限る**(2026-09-03)。
  効果音は「揃った・消した・できた大きさ」に応じて高くなるだけで、速くも大きくもならない。
  結果カードは完成した盤面を一拍見せてから出し、比べる相手は自分の記録だけ
  (`+0:18` / `−0:05`)。称号・実績ギャラリー・ストリーク・タイマー・通知・全ゲーム横断の
  経験値など、「まだ手に入れていないもの」を見せて呼び戻す仕掛けは作らない。
  記録(達成日、自己ベスト、レベル別のクリア)は持ってよいが、未達成の一覧は持たない

### 多言語と説明の原則

- 初回起動時に言語選択画面を出さない(端末の優先言語から解決し、即プレイ可能にする)
- 言語の切り替えでゲームの進行・保存データをリセットしない・壊さない
- アプリ内の文章は最小限に保つ。チュートリアルは 3 ステップ以内・図中心
- 詳細ルール・FAQ・攻略はアプリ内に持たず、ゲーム別 Landing Page へ分離する
- オフラインで外部リンク(Learn More 等)が開けなくてもゲームを止めない

## エンジニアリングの原則

- ゲームロジックは UI / 広告 / Capacitor に依存しない Pure TypeScript
- 依存方向は `apps → packages` のみ。循環依存禁止
- `games/A/` から `games/B/` への import 禁止。シェルはゲーム内部に踏み込まない
- ゲームごとに保存領域を分離する。一方のデータ破損が他方へ波及しない
- 一度しか使われていないコードを共通化しない(重複が確認されてから抽出)
- 巨大な共通ゲームフレームワークを作らない
- アプリへのゲームの正式収録・更新はアプリのリリースとして一体で行う。Web 版への
  先行公開はこれに先行してよい([WEB_VERSION.md](WEB_VERSION.md)「先行公開」)。
  ただしゲームの追加・更新が既存ゲームの挙動・保存データを変えてはならない
- ストア公開は明示的な手動実行またはタグを必要とする
- 実施していない検証を成功扱いにしない

## 初期リリースで実装しないもの

対人戦 / オンラインランキング / フレンド / チャット / シーズン / 期間限定イベント /
ログインボーナス / 課金アイテム / ガチャ / バトルパス / ユーザープロフィール /
クラウド同期 / ソーシャルログイン / AI 機能 / オンライン問題配信 / Coming Soon 表示 /
Push 通知 / ローカル通知 / ストリーク表示 / Analytics / Remote Config /
Rewarded 広告 / Interstitial 広告 / App Open 広告 / Native 広告

このうち各種広告フォーマット・ストリーク・ログインボーナス・期間限定イベント・
Push/ローカル通知・オンラインランキング・Coming Soon 表示は「初期リリースで
見送る」のではなく、**採用しない**。Analytics も**アプリでは採用しない**。
Web 版のページ解析は「適用範囲」のとおり別の約束であり、
[WEB_VERSION.md](WEB_VERSION.md)「計測」が定める。

この一覧と「採用しない」は Core のものである。Shared(Private Game Club)の Club の
中で何を持てて何を持てないかは「Shared」節が定める — そこでもリアルタイムの対人戦・
マッチング・グローバルランキング・フレンドグラフ・公開グループ・リアルタイムチャット・
ソーシャルログイン・クラウド同期・Push / ローカル通知・ストリークは持たない。

**共有報酬 / 招待ボーナス / 紹介コードも採用しない**(issue #86)。結果画面には
任意の共有があるが、押しても押さなくてもゲーム・進行・広告表示・解放される
ものは一切変わらず、催促も再要求もしない。共有は「気に入ったゲームを本人の
意思で渡す」ためのものであって、こちらが対価を出して買う行動ではない
([ARCHITECTURE.md](ARCHITECTURE.md)「レイヤー規則」)。Shared の招待・参加・Host 化にも
報酬を出さない(「Shared」節「紹介」)。

共有文と共有画像には、そのプレイの結果(結果画面が表示した時間・スコア・ミス・
ヒント回数など)を載せる(2026-09-03 に「数値を載せない」規則を撤回)。載せるのは
本人がボタンを押したときだけ・結果画面が表示した事実だけ・履歴は載せない・
勝っていない結果を勝ったと言わせない。ランキング・ストリーク・成績の保存や送信は
これによっても増えない。

## Shared(Private Game Club)— Core の外にある任意の層

2026-09-09 決定(issue #176、Epic #175)。製品設計は issue #161(Shared Server /
Private Game Club)と #164(発見の導線)が持ち、**実装はまだ無い**。この節は機能の

この節 → #161 の設計 → #164 で、Friction first([PROJECT_CONTEXT.md](PROJECT_CONTEXT.md)

### 定義

- **Core** — Shared を有効化していない状態のアプリと Web 版。全ゲーム・コレクション・
  設定・バックアップ・結果の共有・バナー 1 枠・買い切り 1 商品。**本文書の他の全節は
  Core の約束**であり、Shared があっても 1 語も変えない。変えずに済む形にしか Shared を
  作らない。
- **Shared** — 利用者(または招待してくれた知人)が**自分で建てた 1 台のサーバ**に、
  知っている人同士の小さな Club を持ち、同じ seed の挑戦をそれぞれの端末で遊んで、
  結果だけを持ち寄る任意の層。製品名は Private Game Club。入口は設定の奥(Advanced)と
  招待リンクだけ。**Solo by default. Social by choice.**
- Shared は Core の約束の**例外ではなく、Core の外**である。「オフライン」「アカウント
  登録なし」「API サーバーなし」「オンラインランキングなし」「PixApps はサーバーを
  運用しない」は Core について真のままで、Shared はそのどれも Core について偽にしない。

### Core が Shared から受け取る変更は次の 3 つまで

1. 設定 > Advanced の入口 1 つ(接続する / 自分の Club を作る)。
2. 接続済みの端末に限り、コレクションホームの入口 1 つと、挑戦が自然に成立する
   ゲームの結果画面の操作 1 つ(#164。全ゲームへ機械的に足さない)。
3. 接続していない端末では、コレクションホームの静かな入口(Play together)1 つまで
   (#164)。

それ以外の Core の画面 — 初回起動・チュートリアル・盤面・結果画面の主要操作・広告・
購入 — に Shared は現れない。バッジ・モーダル・通知・Coming Soon で知らせない
(「初期リリースで実装しないもの」の Coming Soon 禁止はここにも効く)。

### Shared 自身が守ること

Core の約束の写しではなく、Shared の側の約束である。

- **PixApps はサーバーを 1 台も運用しない。** 中央 hub・中継・登録簿・公式インスタンス・
  identity service を作らない。建てる・払う・消すのは利用者。ホスティング事業者の
  テンプレートは配布物であって運用ではなく、そこからの kickback / referral は副次収益 —
  それを増やすためにサーバの消費を増やさない(#161)。
- **通信は、有効化した端末が、本人の選んだサーバへ、本人の操作の直後にだけ行う。**
  有効化していなければ 0 リクエスト。ポーリング・バックグラウンド同期・常時接続・Push を
  持たない(「低消費電力の原則」はそのまま)。サーバの障害はゲームを止めず、Club 1 つの
  障害を他の Club や Core へ波及させない。
- **送るのは結果画面が表示した事実だけ。** 結果の共有(issue #86)と同じ線 — 結果画面に
  出た時間・スコア・ミス・ヒント回数と、その Club での nickname。進行・中断中の盤面・
  統計・自己ベストの履歴・お気に入り・設定・バックアップ・購入状態は送らない(#161
  「Core とのデータ境界」)。通常プレイの結果は本人が選んだときだけ、選んだ Club へ。
- **アカウントを作らない。** password / email / OAuth / 電話番号なし。Club ごとの
  nickname と端末ごとの member token だけで、PixApps に登録するものは無い。接続情報
  (member token)はバックアップに入れない — `sg.iap` と同じ理由で、ファイルはコピー
  できるので入れた時点で「コピーできる鍵」になる(docs/architecture/backup.md)。
- **ゲーム機能を Shared の後ろに置かない。** Club に入っても入らなくても、全ゲーム・
  全機能・Hint / Undo は同じ。Shared 専用の盤面・モード・難易度を作らない(共有するのは
  seed だけ)。Club への参加・招待・Host 化を、Core の何かの対価にしない。
- **急かさない。** 締切の強制・ストリーク・ログインボーナス・Push / ローカル通知・
  「まだ手に入れていないもの」を見せて呼び戻す仕掛けは Shared でも作らない
  (「UI / UX の原則」の手応えの境界はここにも効く)。
- **お金に関わる文言は高リスクキーと同じ扱い。** hosting に費用がかかること・切断は
  サーバ削除ではないこと・削除は利用者が事業者側で行うことは、購入・削除の文言と
  同じ「誤訳が約束の反故になる文言」であり、機械翻訳で配らない
  ([I18N_POLICY.md](I18N_POLICY.md))。

### ランキングの縮め方 — 「オンラインランキングなし」は維持する

Core の約束はそのままで、Shared でも**グローバル / 公開 / 知らない人との順位**は作らない。
Club の中で許すのは**結果の比較**であって、順位表ではない。語を変えるだけでは足りず、
形の制約が本体である:

- 1 つの挑戦に参加した Club 員の結果を、その挑戦の比較軸(時間・手数など)の順に
  **並べる**ことはできる。**順位の数字・ポイント・称号は付けない。**
- 挑戦をまたいで**積み上げない**。Club 員ごとの通算・シーズン・ラダー・累積ポイントを
  持たない。Club が持てる「記録」は、自己ベストと同じ意味の **Club 記録**(そのゲーム・
  モードの Club 内ベストとその持ち主)までで、これは記録であってランキングではない
  (「UI / UX の原則」— 記録は持ってよいが、未達成の一覧は持たない)。
- プレイ中と結果画面には**出さない**。比較は Shared の画面へ行った人だけが見る
  (#161「順位を常時プレイ画面へ出さない」)。
- 語も変える。UI と公開文面で Shared の比較を leaderboard / ranking /「ランキング」と
  呼ばない(Results /「結果」)。「No online leaderboard」のスクリーンショットの隣に
  「Leaderboard」の画面が並ぶ状態を作らないため。

### 紹介 — 「共有報酬 / 招待ボーナス / 紹介コードは採用しない」も維持する

Simple Games 自身は、招待・参加・Host 化のどれにも報酬を出さず、数えず、表示しない。
#161 が検討するホスティング事業者の referral は、**Host が自分の意思で置く事業者側の
リンク**を、「自分の Club を作る」を選んだ人向けの hosting の説明画面で 1 回運ぶまで。
Core の画面と Club 員向けの画面に金銭の文言を出さない。事業者の制度が無くても同じ UX が
成立すること、併用可否や実コストが未確認のまま公開文面で謳わないことは #161 の条件のまま。

### 公開文面

- **出荷するまで 1 語も書かない**([BRAND.md](BRAND.md)「表現ルール」)。README・
  ストア掲載文・LP・GitHub metadata・プライバシーページに Shared を足すのは、実装を
  出荷した版から。
- 出荷後も **Core の約束は Core の主語で言う**。「The games never go online」
  「アカウント登録なし」は Core について真のままで、Shared を説明する文はサーバの
  持ち主(あなた、または招待してくれた人)を主語にする。Shared について「オフライン」
  「サーバーなし」「アカウント不要」を言わない。
- 出荷時にプライバシーページ(pixapps.ai/simple-games/privacy)へ Shared の節を足す。
  「PixApps が運用する仕組みを通じて端末外へ出ることはない」は真のままで、利用者が
  選んだサーバへ何を送り、それが Club の持ち主の管理下にあることを書く。
  **開示が先、送信が後**([WEB_VERSION.md](WEB_VERSION.md)「計測」と同じ順序)。

### 機械で示すこと

「Shared を有効化していない限り一切通信しない」を、文書ではなく CI で示す。

1. **ソース** — 通信 API(fetch / XMLHttpRequest / WebSocket / sendBeacon /
   EventSource)を書けるのは `apps/simple-games/src/club/` だけ。
   `.github/scripts/check-principles.sh` §1 は Core を例外なく赤にし、この 1 ディレクトリを
   パスで除外する(除外が他のパスを飲み込んでいないことを自己検査する)。位置情報は
   Shared でも禁止のまま。サーバ実装はこのリポジトリの `apps/*/src` / `packages/*/src` に
   置かない(別リポジトリ)ので、例外はこの 1 つに保てる。
2. **到達経路** — `club/` の外から `club/` への import は、`src/app/` からの動的
   `import()` だけ(入口は 1 か所に保つ)。静的 import は 1 本も許さず、ゲーム・`ui/`・
   `services/`・`storage/`・`i18n/`・`backup/` は `club/` を知らない
   (`src/test/importBoundaries.test.ts`)。`club/` がゲームへ触るのは registry 経由だけ
   ([ARCHITECTURE.md](ARCHITECTURE.md)「アプリ内レイヤー」)。
3. **成果物** — #161 の最初の PR で、`club/` を `game-<id>` と同じくビルドで独立した
   チャンクに分け、エントリの静的 import グラフから届かないことを
   `scripts/bundle-size.mjs` の初期グラフ検査で見る。成果物の `fetch(` の grep は
   **使わない** — native ビルドは Vite の modulepreload polyfill、`@capacitor/core`
   (CapacitorHttp)、`@capacitor/filesystem` がもともと `fetch(` を含む(2026-09-09 の
   dist で確認)。証明はトークンの不在ではなく、到達経路の不在で行う。
4. **実行時** — 動的 import を呼ぶのは、保存された接続がある場合と招待リンクを開いた
   操作のあとだけ。どちらも無ければ呼ばれないことをユニットテストで固定する(#161)。

1 と 2 は本決定と同じ PR で入れてある(ディレクトリはまだ無く、除外と規則は宣言だけ —
どちらも自己検査を持つ)。3 と 4 は `club/` が生まれる PR の受け入れ条件。
