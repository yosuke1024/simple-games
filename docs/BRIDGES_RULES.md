# Bridges — 正式ゲームルール

この文書は Simple Games 収録タイトル「Bridges」の唯一のルールソースである。
実装(`apps/simple-games/src/games/bridges/`)、Hint、テスト、Quick Rules は
すべてこの文書に従う。コードはここへ `§n` で言及する。数値を変える場合はここを先に直す。

ブランド原則([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md))はこの文書より上位にある。
Undo と Hint は回数の制限なし・無料、広告視聴で解放しない、ストリークで急かさない、
プレイ中に時計を見せない。

ゲーム ID は `bridges`、i18n キーの接頭辞は `bridges`、保存キーの接頭辞は `bg.`、
カテゴリは `logic`、No. 45。**Web 先行公開(ベータ)のタイトル**であり、アプリには
まだ収録していない(registry の `channel: 'web-beta'`。[WEB_VERSION.md](WEB_VERSION.md)
「先行公開(ベータ)」、計画は
[plans/2026-10-17-unblock-snake-loop-bridges-peg.md](plans/2026-10-17-unblock-snake-loop-bridges-peg.md))。

数字の島を橋でつなぎ、すべての島を 1 つのネットワークにする論理パズルである。
**一般に Hashiwokakero(「橋をかけろ」)と呼ばれる形式**を、Simple Games の名前と
表現で作る。アプリ内・ストア・i18n の名前は **Bridges だけ**で、他社の商品名
(Hashi / Hashiwokakero を製品名として、等)は使わない
([BRAND.md](BRAND.md)「自社タイトルと比較対象の名前」)。他社の問題・盤面画像・
画面デザイン・データは複製しない — 盤面はすべてこのゲームの生成器が作る(§6)。

**この文書の状態(2026-10-17)。**§1〜§14 は実装とテストに一致している — ルール・生成・
保存レコードの形は `game/`(Phase 2)、操作・表示・保存キー・統計・Quick Rules・文言・
アクセシビリティは `storage/` `state/` `ui/` `i18n/`(Phase 3)、12 言語の訳と 360×640 の
レイアウト確認(§14)、2 人の独立レビューの指摘への対応(Hint の場所の読み上げ・結果カードの
誤操作防止・`svh` の高さ・Undo の読み上げ・テストの追加 — 各節)。未了は 2 つ: 訳を人が読むこと
(ja は作者、他の 12 言語はネイティブも逆翻訳もまだ — §14)と、実機での確認(§16)。

## 1. 盤面

- W×H のマス。いくつかのマスが **島**で、島には **数字 1〜8** が書かれている。
  ほかのマスは水。
- **2 つの島が上下左右に隣り合うことはない**(斜めは可)。橋は少なくとも 1 マスの水の
  上を渡る — 長さ 0 の橋は描けず、読めないからである。
- 島は 2 つ以上。どの島も、その数字をまかなえるだけの相手が見えている
  (数字 ≤ 見えている相手の数 × 2)。
- 盤面は生成後に変わらない。プレイヤーが書くのは**橋**(§2)だけである。

難易度プリセット(スマートフォンの画面で島のタップ目標を大きく取れる範囲で選んだ。Hard の
目標は 360×640 で直径約 40px — iOS の 44pt・Android の 48dp の目安より小さく、**実機の指で
十分かはまだ確かめていない**(§16)。足りなければ、Hard を 9×9 にする(360×640 で約 44px)か、
盤面の高さの取り分から引く予約(§13 の 320px)を減らす — どちらも先にこの文書を直す):

| 難易度 | 盤面  | 島の数 |
| ------ | ----- | ------ |
| Easy   | 7×7   | 8〜12  |
| Medium | 9×9   | 14〜20 |
| Hard   | 10×10 | 20〜28 |

11×11 以上は作らない。360px 幅の端末では 10×10 の 1 マスが約 31〜32px になる(幅と、
盤面以外の画面の部品を除いた高さの小さいほうで決まる — §13)。島は上下左右に隣り合わない
ので、島のタップ目標はマスより大きく取れる(§13: 直径 1.3 マスの円 — 360×640 で約 40px、
高さに余裕のある 360px 幅の端末で約 42px。斜めの島どうしの中心は √2 ≈ 1.41 マス離れて
いるので、円は重ならない)。11×11 では 1 マスが 30px を切り、この余裕が無くなる。
**難易度はサイズだけでは決めない** — ティアは「数えるだけでは進めなくなる回数」と、
そのとき要る推論の中身で定義する(§7)。

**盤面に翻訳の要る文字は 1 つも載らない。**数字は ASCII の `1`〜`8`、橋は線、
状態は形(輪・塗り)で描く([I18N_POLICY.md](I18N_POLICY.md))。読み上げ名だけが
i18n を通る。盤面は RTL でも左右反転しない。

## 2. ルール

1. **各島につながる橋の本数は、その島の数字と等しい。**
2. **橋は水平か垂直にまっすぐ引く。**島 A から橋を引ける相手は、上下左右それぞれの
   方向で **最初に見える島**だけである。**島を飛び越えた接続はできない** — 間に島が
   あれば、その島が「最初に見える島」になる。
3. **同じ 2 島の間の橋は最大 2 本。**
4. **橋は他の橋を横切れない。**(島を横切ることは 2 の定義で起こりえない。)
5. **橋を介して、すべての島が 1 つのグループにつながっていなければならない。**
6. **ネットワークの中のループは禁止しない。**橋をたどって元の島へ戻れる形があっても
   ルール違反ではない(出題の答えにループが含まれることもある — §6 手順 2)。

用語(`engine.ts`):

- **辺**(edge)= 互いに見えている 2 島の組。橋はつねにどれかの辺の上にあり、辺ごとに
  0 / 1 / 2 本を持つ。辺の並び順は「島を index 順に、各島について右の辺 → 下の辺」で
  固定する(保存形式の一部 — §10)。
- 2 つの辺が **交差する** = 一方が横に通る水のマスを、他方が縦に通る。交差する 2 辺の
  両方に橋があることはない(規則 4)。

この読みは `engine.ts` の `buildGraph` が 1 か所で持ち、勝利判定(§3)・操作(§4)・
表示(§5)・ソルバー(§6)・生成器の答えの検証・保存の fail-closed 検証(§10)が
すべて同じものを読む。「見え方」を 2 通りに読むコードは無い。

## 3. 勝利と終了

- **勝利**: 交差が無く、すべての島で橋の本数が数字と等しく、全島が 1 つのグループに
  つながった時点(`isSolved`)。判定は**規則で**行い、保存している答えと照合しない
  (出題は一意解なので一致する — §6)。
- **見た目は完成でも未完成の形**がちょうど 1 つある: すべての数字を満たしたが、島が
  2 つ以上のグループに分かれている状態。このときは「すべての島を 1 つにつなぐ」ことを
  静かに示す(§5)。
- 敗北は存在しない。ミス回数の制限も、ライフも、ゲームオーバーもない(§15)。
- 勝利した盤面は、それ以上の操作(橋・Undo・Hint)を受け付けない。勝利への遷移は
  1 度だけ起こるので、完了の記録(§11)はその瞬間に 1 度だけ付く。

## 4. 操作

**島を 1 つ選び、つなぎたい島をタップする。**

- **島をタップ**すると選択になる(選択中の島をもう一度タップすると選択を外す)。
  選択中の島から**つなげる相手**(§2 で見えていて、交差する橋に塞がれていない島)を
  見やすく示す(§5、`candidatesOf`)。
- **選択中に相手の島をタップ**すると、その 2 島の間の橋が
  **0 本 → 1 本 → 2 本 → 0 本**と 1 段進む(`cycleBridge`)。選択は元の島に残るので、
  同じ相手をもう一度タップすれば次の段へ進む。相手でない島をタップすると、選択が
  その島へ移る。水をタップすると選択を外す。
- **塞がれた辺**(交差する辺に橋がある)には橋を引けない。候補として示さない。塞がれた辺の
  向こうの島は §2 で見えていても「相手」ではないので、選択中にタップすると**橋は変わらず、
  相手でない島と同じく選択がその島へ移る**(エラー音も警告文も出さない。その島から始めたい
  ときに、選択を外す 1 タップが要らない)。塞いでいる橋を外せば、また引ける。
- **数字を超える橋は拒まない。**0 → 1 → 2 → 0 の循環をどの辺でも同じにするため、
  島が数字を超えることは許し、その島を「超過」として示す(§5)。超過はルール違反の
  表示であり、答え合わせではない。
- **橋の細い線そのものを唯一の操作対象にしない。**操作対象は島(大きな円 — §13)で、
  橋の線や水のマスをタップして橋を変える操作は作らない(1 マスに縦横 2 本の辺が
  通りうるので、どちらの辺かが曖昧になる)。
- **ドラッグ**(島から別の島へ指を滑らせて離す)は「選んでタップ」と同じ 1 手である
  (`ui/components/BridgesBoard.tsx`)。押した島の円(§13)を出た時点でドラッグになり、
  離した点が**相手**の島の円の中ならその 2 島の間が 1 段進み、押した島が選択として残る。
  相手でない島や水の上で離せば何も起きない。ドラッグの間は、押した島の相手(点線の輪と
  候補線)と、指の下の相手(太い輪)を示す。ドラッグの後に来るクリックは消費し、押した島を
  タップしたことにしない。`pointercancel`(通知シェード・着信など)はドラッグを丸ごと
  取り消す(解放ではない)。押し始めは主ボタンだけ。島のボタンは `touch-action: none` で、
  島の上から始めたスワイプは画面を流さない(水から始めたスワイプは流れる)。タップだけで
  全状態に届くので、ドラッグは近道でしかない。
- **キーボード**(`ui/tapLogic.ts` の `islandToward`、`useGameKeys`): 矢印キーで島から島へ
  フォーカスを移す — その方向に見えている島(§2 の相手。交差する橋で塞がれていても)へ、
  無ければその側で最も近い島へ(進む距離 + 横のずれ × 2 が最小。同点は横のずれが小さい
  ほう、次に盤面の順)。どの島からもどの島へも届く。盤面でタブ順に入る島は 1 つだけ
  (roving tabindex)なので、Tab 1 回で盤面を出られる。Enter / Space が「タップ」で、
  押しっぱなしの Enter は橋を増やし続けない(リピートの keydown を止める)。Escape は
  選択を外す(水のタップと同じ)。フォーカスが盤面の外にあるときの矢印キーは、フォーカスを
  盤面へ入れる。`Ctrl/Cmd+Z` = Undo、`H` = Hint(どちらもキーリピートでは動かさない)。
  結果カードと確認ダイアログの間はどのキーも効かない(盤面は `inert`)。画面に無い機能を
  キーボード専用にしない。
- **結果カードは盤面への入力を拾わない**(`ui/components/BridgesResultOverlay.tsx`)。最後の
  橋は同じ相手をもう一度タップして架けることが多く、Enter でも架けられる。Reduced Motion では
  カードがその瞬間に出て「同じ盤面で再挑戦」にフォーカスが移るので、続けて来た 2 回目の
  タップ・Enter がカードのボタンを押してしまう(レビューで、素早い 2 回目のタップで 6 回中
  2 回、押しっぱなしの Enter で — Reduced Motion で 700ms、ふつうの動きで 1.6 秒押したとき —
  結果が消えてプレイ回数が 1 増えた)。そこでカードは、現れてから **400ms(`RESULT_ARM_MS`)は
  クリック・タップを受け付けず**、**キーリピートの keydown はいつでも受け付けない**。待ち時間の演出はなく、再描画もしない(タイマー 1 つ、
  カードと一緒に解放)。
- 長押し・モード切替・自動補完(「確定した橋を自動で引く」)は作らない(§15)。

## 5. 表示

- 島は丸の中の ASCII 数字。状態は**色だけでなく形でも**示す(`islandStates`):
  - **不足**(open): 縁取りだけ。
  - **ちょうど**(complete): 塗りつぶし。
  - **超過**(over): 警告色(`--warn`)の二重の輪。
- 選択中の島は太い輪。つなげる相手の島には点線の輪と、選択中の島からその島へ向かう
  点線の**候補線**を出す(色だけに頼らない)。既に橋のある相手には候補線を重ねず、輪だけ。
  塞がれた辺には何も出さない。
- 橋は 1 本なら 1 本線、2 本なら平行な 2 本線。
- 盤面の下に 2 行ぶんの欄を常に取ってある(出ても盤面が跳ねない)。出すのは Hint の言葉
  (§9)か、全島の数字を満たしたのに 2 グループ以上に分かれているときの「すべての数字を
  満たしたが、島が n グループに分かれている。1 つにつなぐ」の 1 文(`boardFacts` の
  `allNumbersMet` と `groups`)だけ。欄は `role="status"` で読み上げられる。
- Hint の印(§9): 示した 2 島の間に太く淡い帯、2 島の背後にタップ目標の大きさの淡い円。
  理由の島(1 つの島で確かめられる一手のとき)には、その円に沿った点線の輪。答えより多い
  辺は、帯と円を警告色(`--warn`)で。**印は読み上げにも出す**: 示した 2 島の読み上げ名の
  末尾に「ヒントで強調」(理由の島は「ヒントで強調、点線の輪」— `bridgesIslandHinted` /
  `bridgesIslandHintRing`)を足し、選択中・相手の表示はその後ろに続く。盤面の下の欄には、
  見えない 1 文で場所を足す(「強調した島: n 行 m 列と p 行 q 列。点線の輪: r 行 s 列。」—
  `bridgesHintWhere` / `bridgesHintWhereRing`)。欄は `role="status"` なので、Hint の言葉と
  一緒に読み上げられる。
- 橋を変えるたびに、読み上げにだけ「n 行 m 列と p 行 q 列の間: 橋 k 本」を知らせる
  (`aria-live="polite"`。画面には出さない)。**Undo も同じ文で、戻した後の本数を知らせる**
  (どの変化も聞こえ、Undo の後に同じ手を打ち直しても同じ文の繰り返しにならない)。手の前後の
  本数は、手を適用したセッション(`GameContext` の ref)から読む — 1 つのタスクに 2 手が
  入っても、2 手目は 1 手目の結果と比べて音と読み上げを決める。
- **これはルールの表示であって答え合わせではない。**規則を破っていない橋は、それが
  答えと違っていても何も言われない(答えと比べるのは Hint だけ — §9)。

## 6. 生成・一意性・技法

すべての盤面は seed から決定的に作る。ダウンロードはしない。生成が上限に達したときだけ、
このゲームの生成器が作って同梱した盤面へフォールバックする(手順 6)。
(`generator.ts` の `generatePuzzle(seed, difficulty)`。)

1. **ネットワークを育てる**(`growNetwork`)。空の盤面のランダムなマスに島を 1 つ置き、
   「置いた島を 1 つ選ぶ → 上下左右の 1 方向を選ぶ → その方向の水の上を 2 マス以上
   進んだ、**上下左右に島の無い**水のマスに新しい島を置き、その間に橋を 1 本か 2 本
   (2 本の割合はティアの `doubleShare`)架ける」を繰り返す。進む途中に島か橋があれば
   そこで止まる — **橋は橋を横切らず、島を飛び越えない**ことが構成で守られる。目標の島数
   (ティアの範囲から seed で 1 つ)に届くか、成長の試行が `GROW_STEP_LIMIT`(600)回に
   達したら止める。ティアの最少島数に届かなければ、この候補は捨てる。
2. **ループを閉じる。**できあがった盤面で、互いに見えていて間が全部水の 2 島
   (=まだ橋の無い辺で、架けても何も横切らない)を seed 順に見て、ティアの `loopShare`
   の割合で橋を 1 本か 2 本足す。答えにループができうる(§2 規則 6)。
3. **数字を決める。**各島の数字 = 育てたネットワークでの橋の本数(`numbersFrom`)。
   このネットワークがそのまま答えなので、**解の無い盤面は構成上出ない**。答えが §3 の
   勝利条件を満たすことを `isSolved` で確かめる。
4. **等級と一意性**(`gradeLayout` と `countSolutions`)。技法ソルバー(下)を空の盤面から
   回し、全辺が決まるか、何回「数えるだけでは進めなくなったか」(`stalls`)を得る。
   技法で決まった盤面には、さらに解の個数を 2 まで数え、**ちょうど 1 つ**であることを
   探索で証明する。
5. **ティアに合えば出荷**(`meetsTier`: 一意・技法で決まる・Hard 以外は T4 不要・
   `stalls` がティアの帯に入る・島数が範囲内。Hard はさらに `rounds` が 2 以上で、
   数える + 対の規則では決まらないこと — §7)。合わなければ **seed を派生させて**
   作り直す(`<seed>#2`, `#3`, …)。
6. **`ATTEMPT_LIMIT`(80)回で合わなければ、または 1 盤面の仕事量が
   `GENERATION_WORK_LIMIT`(150,000)に達したら、同梱盤面へフォールバックする**
   (`bundledPuzzle`)。`game/bundled.ts` にティアごと 4 面、**このゲームの生成器
   (`buildCandidate`)が、記録した seed から 1 回目の試行で作った盤面**を持ち、seed の
   ハッシュで 1 面を選ぶ(同じ seed なら同じ盤面)。`fallback` 印が付く。同梱盤面は
   ほかの製品や書籍から写したものではない。`guarantee.test.ts` が各面を seed から
   作り直して 1 文字単位の一致を確かめ、一意性(2 通りの方法)とティアを検証する。
   生成器を変えて一致しなくなったら、同梱盤面を作り直す(それは決定であり、コミット
   メッセージに書く)。

**既知の性質: 盤面の端の行・列が空のことがある。**成長(手順 1)は端に届くことを求めないので、
島が 1 つも無い端の行・列が残る盤面がある(固定の大きさの枠の中で、島の範囲が枠より小さく、
少し片寄って見える)。実測(開発時、2026-10-17。走査の固定 seed `g1`〜`g200`): 端に空の行・列が
1 本以上ある盤面は Easy 151 / 200(最大 4 本、島の範囲の面積は平均で枠の 85%)、Medium
116 / 200(最大 2 本、92%)、Hard 66 / 200(最大 2 本、96%)。別の seed `r0`〜`r299` では
Easy 208 / 300・Medium 154 / 300・Hard 88 / 300(レビューの測定と一致)。ルール上の問題は
無く、タップ目標の大きさは枠で決まる(§13 の数字を下回らない)。**今は変えない**: 端に届く
ことを条件にすると、すべての盤面・golden・同梱盤面・§6〜§7 の実測が変わる。変えるなら
`meetsTier` に条件を足して同梱盤面と golden を作り直し、分布を測り直す(決定として記録する)。

不変条件:

- 同じ seed なら、必ず同じ盤面になる(`compatibility.test.ts` の golden で固定する)。
- 出題は一意解を持つ(手順 4 で証明する。証明できない盤面は出さない)。
- 出題はそのティアの帯(§7)に入る。手順 6 の同梱盤面も同じ帯に入る。
- 手順 6 の発生は監視値である(走査した全盤面で 0 件 — 下の実測)。

### 技法ソルバー(`solver.ts`)

各辺は「まだ取りうる本数」(0 / 1 / 2 の部分集合)を持つ。最初は 0 から
`min(2, 両端の数字)` まで。4 つの技法で狭める。**4 つとも健全**(どの解も使っている
本数を消さない)である。

- **T1 数える**(count): 島の数字と、その島の辺が「まだ取りうる最大の合計 / 既に確実な
  最小の合計」を比べる。ほかの辺で足りない分はこの辺が持たねばならず、ほかの辺が既に
  持つ分を超えてこの辺は持てない。(「4 方向が見えている 8 は全部 2 本」「相手が 1 つ
  しか見えない 1 は 1 本」などはここに入る。)
- **T2 交差**(crossing): 確実に橋がある辺と交差する辺は 0 本。
- **T3 つながり**(connect)— 全島が 1 グループになる、という規則 5 からの推論:
  1. 橋を持ちうる辺だけで全島がつながっていなければ、その盤面は解けない(矛盾)。
  2. そのネットワークを 2 つに切ってしまう唯一の辺(グラフの橋 — Tarjan の low-link)は、
     少なくとも 1 本の橋を持つ。
  3. **閉じたグループの回避**: 確実な橋でつながった島の集まりで、全員が数字ちょうどに
     なっているものは、もう外へ橋を出せない。それが全島でなければ矛盾であり、ある辺を
     ある本数にすると**そういうグループができてしまう**なら、その本数は取れない
     (「1 と 1 はつながない」「2 と 2 を 2 本でつながない」を、任意の大きさの
     グループへ一般化したもの)。
- **T4 仮定**(hypothesis、深さ 1): まだ決まっていない辺の 1 つの本数を仮に置き、
  T1〜T3 を不動点まで回す。矛盾したら、その本数を実際の盤面から除く。

**梯子として回す**(`runSolve`): T1〜T2 を不動点まで → それで止まったら T3 の推論を
**1 つだけ**適用して最初へ戻る → T3 も無ければ T4 の除外を **1 つだけ**適用して最初へ
戻る。T3 か T4 を使った回数が **`stalls`**(数えるだけでは進めなくなった回数)で、
ティアはこの数で帯を決める(§7)。安い技法で進める限り高い技法は使わないので、
`stalls` は「数えるだけでは手詰まりになり、つながりか仮定を考える必要があった回数」の
近似になる。技法の不動点は適用の順序によらないので、どの技法が要るか(等級)は 1 回の
実行で決まる。

`stalls` は推論を **1 つずつ**数えるので、同じ時点で見えている推論が 5 つあれば 5 と数える
(開始時に「1 と 1」の対が 5 組見えていて、それに気づけば後は数えるだけ、という盤面も
`stalls` 5 になる)。そこで、1 つずつ数えない尺度を 2 つ持ち、Hard の条件に使う(§7):

- **`rounds`**(`countRounds`): 同じ梯子を、T3 の段で**見えている推論を全部まとめて**
  適用して回す — 切断辺をすべて、続けてそれを反映した盤面で閉じたグループをすべて。
  T4 の除外は 1 回 = 1 ラウンド。数えるだけで止まった回数を「何度、手詰まりになったか」で
  数える。まとめるほど回数は減る方向なので、Hard の下限としては厳しい側の読み方である。
- **対の規則**(`settledByPairs`): 「1 と 1 はつながない」「2 と 2 を 2 本でつながない」は、
  T3 の閉じたグループの推論のうち **2 つの数字だけで決まる**もの(2 島とも確実な橋を
  まだ持たないときの場合)で、プレイヤーが最初に覚える規則である。最初からこの 2 つを
  盤面全体に適用したうえで T1〜T2 だけで全辺が決まるかを見る。決まらない盤面には、
  切断辺・3 島以上の閉じたグループ・仮定のどれかが少なくとも 1 回要る。

**技法で全辺が決まった盤面は一意解である**(技法が健全なので、残った唯一の割り当てが
唯一の解)。それでも生成器は手順 4 で解の個数を別に数える。

実装は 1 つだけ持ち、3 人の利用者が共有する — 生成時の等級(手順 4)、Hint(§9)、
`guarantee.test.ts`。

### 解の個数(`countSolutions`)

各ノードで T1〜T3 を不動点まで適用し(推論は 1 つずつではなく、見えているものを全部
まとめて — 切断辺をすべて、続けて閉じたグループをすべて)、まだ
決まっていない辺のうち取りうる本数が最も少ないものを選んで、本数ごとに枝分かれする。
全辺が決まった葉で勝利条件(`isSolved`)を確かめて数える。解を `limit`(既定 2)個
見つけたら止める。技法は健全なので刈り込みで解は失われず、**探索が最後まで走った
とき**の数は正確である。

- **ノード上限 `SEARCH_NODE_LIMIT`(500)**に達したら `complete: false` を返す。この
  ときの数は下限にすぎず、**一意とも解なしとも主張しない**(`isUnique` は false、
  生成器はその候補を捨て、保存の検証はそのレコードを捨てる)。生成と読み込みの検証は
  同じ上限を使うので、生成器が一意と証明した盤面は読み込みでも必ず証明できる。
  生成器の候補 約 6 万面で最大 28 ノード(レビューの独立検証では 9×9〜16×16 で育てた盤面
  約 17,600 面で最大 117 ノード)。
- 生成器から呼ぶときは、ノードに加えて**仕事量の上限**(1 盤面の残りの予算)も渡す。
  途中で尽きた伝播は「枝が矛盾した」ではなく `complete: false` として読む。
- 技法ソルバーにも **仕事量上限 `TECHNIQUE_WORK_LIMIT`(100,000)**がある。達したら
  `aborted` を返し、等級は `unsolved`(=出荷しない)、`countRounds` / `settledByPairs` は
  `null`(=どちらとも言わない。Hard の条件を満たさない)、Hint は「見つからない」(§9)。
  どの上限でも、推測を答えとして示すことは無い。

`solver.test.ts` が、一意解・2 解(3 の正方形)・解なし(唯一の 2 辺が交差)・
ノード上限・仕事量上限(技法ソルバー・数え上げ・`countRounds`・`settledByPairs`)の
各ケースを固定する。

### 予算は仕事量で門にする

門は壁時計ではなく**仕事量**で測る(`GeneratedPuzzle.work` = ソルバーの仕事量
`solverWork`(島の検査回数 + 探索ノード + 仮定の試行)+ 成長の試行回数。最少島数に届かずに
捨てた成長の試行も数える)。同じ seed ならどのマシンでも同じ数になる(理由は
[SUDOKU_RULES.md](SUDOKU_RULES.md) §7・[NUMBER_PATH_RULES.md](NUMBER_PATH_RULES.md) §6)。
探索は UI スレッドで同期に走らせる(Worker は使わない —
[GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「CPU 探索」)。

**探索が走るのは、プレイヤーの明示的な操作のときだけ**で、先読み・定期実行・常駐はしない:

| 操作                                                   | 走るもの                                                    | 上限                                                  |
| ------------------------------------------------------ | ----------------------------------------------------------- | ----------------------------------------------------- |
| 「新しい盤面」「デイリーを開く」(再挑戦は作り直さない) | 生成(手順 1〜6)                                             | `ATTEMPT_LIMIT` / `GENERATION_WORK_LIMIT` / 下の 3 つ |
| Hint をタップ                                          | 1 島での確認、無ければ技法ソルバー(最初の推論で止まる — §9) | `TECHNIQUE_WORK_LIMIT`                                |
| 中断中の盤面を読み込む(ゲームを開く)                   | `fromRecord` が解の個数を数え直す(§10)                      | `SEARCH_NODE_LIMIT`                                   |

読み込み時の数え直しは、生成の証明をそのまま信じず保存データを fail-closed で検証するための
意図した探索である。**`fromRecord` を呼ぶのは `storage/gamePersistence.ts` の
`loadSavedGames` だけ**で、それを呼ぶのはゲームのルート(`ui/BridgesRoot.tsx`)の読み込み
— プレイヤーがゲームを開いたとき(コレクションからでもショートカットからでも)— だけである。
ショートカットの再開判定(`soleSuspendedMode`)はその結果を読むだけで探索を足さず、アプリの
起動はゲームのチャンクを読み込まない。バックアップの書き出し・復元はスキーマの検証
(`storage/schemas.ts`)しか通らず、それは形と、探索なしで読める中身(盤面・答えの勝利条件・
置ける橋・解けていないこと)だけを見る — 探索は走らない(§10)。答えが唯一であることは、
次にゲームを開いたときに `fromRecord` が確かめる。

**上限**(どれも、達したら推測ではなく「見つからない」「証明できない」を返す):

| 上限                    | 値      | 何を                                                           | 達したとき                                                                                     |
| ----------------------- | ------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `ATTEMPT_LIMIT`         | 80      | 1 盤面の派生 seed の数                                         | 同梱盤面へ                                                                                     |
| `GENERATION_WORK_LIMIT` | 150,000 | 1 盤面の全試行の仕事量の合計                                   | 同梱盤面へ。各試行のソルバー呼び出しは残りの予算で走り、途中で尽きた呼び出しは不合格として読む |
| `TECHNIQUE_WORK_LIMIT`  | 100,000 | 技法ソルバー 1 回(等級・`countRounds`・`settledByPairs`・Hint) | 等級は `unsolved`、2 つの尺度は `null`、Hint は「見つからない」                                |
| `SEARCH_NODE_LIMIT`     | 500     | 解の個数の探索 1 回(生成と読み込みで同じ値)                    | `complete: false` — 一意とも解なしとも言わない                                                 |

超えない(各呼び出しが残りの予算で止まり、予算が尽きたら次の試行を始めない — `guarantee.test.ts`

約 0.5 µs(レビューが作った格子状の盤面)なので、天井は約 40〜75 ms。`TECHNIQUE_WORK_LIMIT`
は候補 1 つの技法ソルバー 1 回の実測の最悪(27,624)の約 3.6 倍、`GENERATION_WORK_LIMIT` は
1 盤面の実測の最悪(Hard 62,959)の約 2.4 倍で、どちらも実測した盤面を 1 つも変えない

## 7. 難易度(ティア)

ティアは **盤面サイズ・島の数・必要な推論**の 3 つで決める(`TIERS` と `PRESETS`)。
推論の軸は §6 の 3 つの尺度 — `stalls`(T1〜T2 だけでは進めなくなり、T3 か T4 が要った
回数。推論を 1 つずつ数える)、`rounds`(同じ時点で見えている推論をまとめて数えたときに
手詰まりになった回数)、対の規則で決まるか — である。帯の値は下の実測分布から決めた。

| ティア | 盤面  | 島の数 | 必要な推論                                                                                             | T4(仮定)                                                                                                | 2 本の橋の割合 | ループの割合 |
| ------ | ----- | ------ | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- | -------------- | ------------ |
| Easy   | 7×7   | 8〜12  | `stalls` **0** — 数える(T1〜T2)だけで全部決まる                                                        | 使わない                                                                                                | 0.5            | 0.1          |
| Medium | 9×9   | 14〜20 | `stalls` **1〜3** — つながり・孤立回避(T3)が要る                                                       | 使わない                                                                                                | 0.2            | 0.05         |
| Hard   | 10×10 | 20〜28 | `stalls` **4 以上**、かつ `rounds` **2 以上**、かつ**数える + 対の規則では決まらない**(3 つとも満たす) | 使ってよい(T4 の除外 1 回は `stalls` 1 回・`rounds` 1 回。T4 が要っても 3 つを満たさない盤面は出さない) | 0.1            | 0.05         |

「2 本の橋の割合」「ループの割合」は分類ではなく、帯に入る盤面が出やすいように成長を
傾けるつまみである(2 本の橋が多いと数字が大きくなり、大きな数字は数えるだけで決まり
やすい。ループは解の候補を増やし、一意でない盤面を増やす)。分類は上の尺度と T4 の可否だけで
行う。

**Hard に `rounds` と対の規則を足した理由**(レビューの指摘、2026-10-17): `stalls` だけで
帯を分けていたとき、開始時に「1 と 1」「2 と 2」の対が 4〜5 組見えていて、それに気づけば後は
数えるだけ、という盤面が `stalls` 4〜5 で Hard に入っていた(レビューの測定で、当時の Hard の
約 13% が数える + 対の規則だけで解け、約 84% が `rounds` 3 以下 = Medium と同じ範囲だった)。今の Hard はどれも、
まとめて考えても 2 度以上手詰まりになり、対の規則より先の推論(切断辺・3 島以上の閉じた
グループ・仮定)が少なくとも 1 回要る。

| デイリー | 1: 349、2: 231、3: 150                                               | 1: 567、2: 154、3: 9             | 289 / 730        | connect 730                 | 14 / 16 / 20 |

走査の外(§6 の実測 2、20,000 面ずつ): Medium は `rounds` 1 が 79.9%・2 が 18.6%・3 が 1.5%、
対の規則で決まる盤面が 42.6%。Hard は `rounds` 2 が 58.4%・3 が 26.1%・4 が 10.0%・5 以上が
5.5%、対の規則で決まる盤面は 0、T4 が要る盤面が 15.0%。

島の数字の分布(§6 の候補のうちティアに合った盤面の全島。Easy 615 面 / Medium 311 面 /
Hard 196 面): Easy は 1: 18%・2: 29%・3: 24%・4: 18%・5: 7%・6: 3%・7〜8: 1% 未満、
Medium は 1: 31%・2: 35%・3: 22%・4: 9%・5: 3%・6〜7: 1% 未満、Hard は 1: 34%・2: 37%・
3: 22%・4: 7%・5: 2%・6〜7: 0.2% 未満。Hard ほど小さな数字が多い — 小さな数字は相手の
選び方が多く、数えるだけでは決まらない。

**Hard は Medium より難しく、Medium は Easy より難しい**ことを、走査した全盤面でテストが
固定する:

- Easy は全面が T1〜T2 だけで解け、Medium と Hard は全面が T1〜T2 だけでは解けない。
- Hard の `stalls` の最小(4)は Medium の最大(3)より大きい。ただしこれは 1 つずつ数えた
  **推論の個数**の差であり、同時に見えている推論も別々に数えた結果である。
- そこで 1 つずつ数えない尺度でも固定する: Hard は全面が `rounds` 2 以上で、対の規則で
  決まる盤面は 0。Medium は `rounds` 1 が過半(164 / 200)で、対の規則で決まる盤面が
  90 / 200 ある。`rounds` の中央値は Hard 2 > Medium 1。
- 島の数の中央値は Hard > Medium > Easy。T4 が要る盤面は Hard にだけある(200 面中 26 面)。

**帯が「推論の種類で」重ならない、とは言わない。**Medium にも、対の規則より先の推論が要る
盤面(走査で 110 / 200)や `rounds` が 2〜3 の盤面(36 / 200)がある。Hard が保証するのは、
「推論が 4 つ以上・まとめても 2 度以上手詰まり・対の規則より先の推論が要る」の 3 つが**同時に**
成り立つことで、Medium の盤面はどれも 1 つ目(`stalls` ≤ 3)で外れる。これは**ソルバーの
尺度での**難しさであり、人がどう感じるかを測ったものではない(§16)。

## 8. モードとデイリー

- **難易度モード**(Free Play): Easy / Medium / Hard を選んで遊ぶ。seed は
  `bridges-<difficulty>-<token>`(token = 起動時刻 + 乱数、Box Regions と同じ
  `newSeedToken`)。同じ seed なら同じ盤面。レベル 1〜100 は作らない。クリア画面の
  第一ボタンは同じ盤面での再挑戦、第二が「新しい盤面」。プレイ中のヘッダの ↻ も同じ
  2 択(再挑戦 / 新しい盤面)を出す(`RestartDialog`)。デイリーは再挑戦だけ。
- **再挑戦**(`restartSession`)は画面の盤面そのものを、橋なし・Hint 0・時計 0 で
  作り直す(seed から作り直さないので、同梱盤面へ落ちた盤面でも同じ盤面が戻る)。
- **デイリー**: 1 日 1 問。seed は `bridges-daily-<YYYY-MM-DD>`(端末のローカル日付のみ。
  サーバー時刻もネットワークも使わない)。**毎日 Medium 固定**(曜日で当たり外れを
  作らない — Sudoku §10)。
- **デイリーは今日の 1 問だけ。**過去の日付には遡れず、一覧も入口も持たない。日付が
  今日でない中断中のデイリー(過ぎたものも、時計を戻した端末や時差のある端末のバックアップで
  先の日付になったものも)は次にゲームを開いたとき(コレクションからでもショートカットからでも)に
  レコードごと捨て、ホームの「デイリーチャレンジ」はつねに今日の問題へ向く。遊んでいる最中の盤面は
  日付が変わっても取り上げない。達成した日の記録は残す
  (`docs/PRODUCT_PRINCIPLES.md`「デイリーは今日の 1 問」)。
- **ストリークは数えない・表示しない。**
- 中断は難易度モード用・デイリー用の **2 スロットを独立して保持**する(§10)。
- 最後に選んだ難易度は `bg.prefs` に残る(初期値 Easy)。初回の Quick Rules の直後に
  始まる盤面もこの難易度。ただし難易度モードの中断中の盤面があれば(`bg.flags` だけが失われて
  Quick Rules がもう一度出た場合)、新しい盤面で置き換えず、その盤面を難易度にかかわらず再開する
  (§10「黙って新しい対局を始めない」)。

## 9. Undo と Hint

### Undo

- **無料・回数の制限なし。**1 手 = 1 回のタップ(ある辺の本数を 1 段進めた)。
- 履歴はセッションに持ち、**直近 500 手まで**保持する(`UNDO_HISTORY_LIMIT` — 実際の対局で
  届く数ではなく、無限に伸びないための蓋。501 手目を打つと最も古い 1 手が履歴から落ちる)。
  **保存しない** — 再開時は空(§10)。Undo は Hint 回数を戻さない。勝利した盤面では
  使えない(§3)。
- **Undo を作る理由**: 0 → 1 → 2 → 0 の循環は 1 段戻れない(2 本を 1 本にするには 0 を
  回る)。橋を外して交差の塞ぎが解けた別の辺に、もう橋を引いているかもしれない。
  手で戻すのは作業であり、ゲームの思考ではない。

### Hint

無料・回数の制限なし・使った回数を数える(結果画面に事実として出す。コストにはしない)。
**盤面には書き込まない。**順に(`findHint`):

1. **現在の盤面が答えと矛盾していないかを確かめる。**答えより多い橋を持つ辺が 1 つでも
   あれば、その辺を示す(「この 2 島の間の橋が多すぎる」)。出題は一意解なので、
   答えを超えた辺がある盤面は**決して完成できず**、どの辺も答え以下の盤面は**必ず
   完成できる** — これは探索なしで正確な「矛盾の判定」である。
2. 矛盾が無ければ、**盤面から証明できる橋を 1 つ**示す: 「この 2 島の間には少なくとも
   n 本」。答えを読み上げているのではなく、盤面から証明できる一手である。
   1. **まず、1 つの島で確かめられる一手を探す**(`evidentRise`)。島を盤面の順(左上から)に
      見て、その島の数字と、ほかの各辺が最大で持てる本数 — 引いた橋に塞がれた辺は 0、
      それ以外は 2・両端の島それぞれの「数字 − その辺以外に引いた橋」のうち最も小さいもの
      — を比べる。
      ほかの辺で足りない分は、この辺が持たねばならない。使うのは盤面に見えているもの
      (数字・引いた橋・交差)だけなので、**示した島を見ればそのまま理由がわかる**。この
      ときだけ、その島も示す。
   2. どの島でも確かめられないときは、技法ソルバー(§6)を**プレイヤーの盤面から**回す
      (引いた橋をその辺の下限として読み、引いた橋と交差する辺は 0 本)。梯子の順
      (T1〜T2 → T3 → T4)で**最初に下限が上がった推論で止め**、それを示す。理由は、別の
      推論(T3 の「この 2 つの 1 はつながない」、T4、ほかの島の数え)が下げた上限を経た
      連鎖で、1 つの島には見えない。だから**島は示さない**(`island: -1`)。
3. どちらも無いとき(=技法が仕事量上限までに何も示せなかったとき)は「今わかる手が
   見つかりません」と表示し、盤面は変えない。**推測を答えとして示さない。**

以前は 2 で梯子の最初の推論を示し、T1 の推論ならその数字の島を「理由」として示していた。
レビュー(2026-10-17)で、示した島の見えている状態だけでは本数が決まらない Hint が Medium で
約 10%・Hard で約 21% あるとわかり、上のように改めた。今は、走査盤面の Hint だけの経路で
島を示した Hint が 6,603、示さない Hint が 898(全 200 面ずつでは Easy 0%・Medium 9.6%・
Hard 24.2% が示さない)。

**最初の推論で止める**(以前は梯子を最後まで回して最初の 1 つだけを使っていた)。示す一手は
同じ(Medium と Hard の走査盤面 400 面の Hint の経路のすべての状態で、止めない場合と一致する
ことを開発時に確かめた)で、仕事量は盤面全体を解く量にならない: 空の盤面からの最初の Hint は
走査盤面で最大 79、Free Play 20,000 面ずつで Hard 最大 159(レビューの測定では、以前は盤面を
解くのと同じ量で、Hard 5,000 面で最大 12,970)。

出荷した盤面では 2 が必ず見つかる: 盤面は技法で全辺が決まり、プレイヤーの盤面が答え
以下なら、そこから始めた技法の不動点は空の盤面から始めたものより弱くならない(技法は
単調)ので、答えより少ない辺のどこかで必ず「少なくとも n 本」が出る。単調性は証明ではなく
議論なので、`guarantee.test.ts` が次を固定して、壊れたら落ちるようにしている:

- 走査盤面の 3 面に 1 面(444 面)で、空の盤面から Hint の示す本数だけを引き続ければ完成する。
- 各ティア 30 面 × 答え以下のシード付き途中盤面 10 通り(計 900 通り)で、Hint が常に一手を
  示し、答えを超えず、引いた本数より多くを求める。同じ途中盤面から 1 つの島で確かめられる
  一手を全部引いた盤面(155 通りが完成せずに残る)では、技法が一手を見つけ、島を示さない。
  そこから 1 本多い盤面では「多すぎる」を示す。
- **島を示した Hint はすべて、その島の見えている状態だけで本数が決まる**(solver.ts を
  使わない独立の確認で)。

技法名は UI に出さない。

**表示**(`ui/screens/GameScreen.tsx`): Hint の言葉は盤面の下の欄(§5)に出し、印(§5)と
一緒に次の 1 手(橋の変更・Undo)まで残る。トーストにはしない — 盤面に重なると、示した
2 島そのものを隠しうる(試作で実際に隠れた)。Hint を出すと選択は外れる(選択の点線の輪と
Hint の点線の輪を見分けさせない)。選択は手ではないので、選んでも言葉は消えない。
スクリーンリーダーには、印の付いた島の読み上げ名と、欄の見えない 1 文で場所を伝える(§5)。
英語の例: 「Highlighted: row 1, column 7 and row 1, column 9. Dotted ring: row 1, column 9.」

| 場合                                  | 言葉(en。ja は §14)                                                                  |
| ------------------------------------- | ------------------------------------------------------------------------------------ |
| 答えより多い辺(1)                     | Too many bridges between the highlighted islands.                                    |
| 1 つの島で確かめられる・少なくとも 1  | Count the island in the dotted ring: the highlighted pair needs at least one bridge. |
| 1 つの島で確かめられる・2 本          | Count the island in the dotted ring: the highlighted pair needs two bridges.         |
| 島を示さない(2b)・少なくとも 1 / 2 本 | The highlighted pair needs at least one bridge. / … needs two bridges.               |
| 見つからない(3)                       | No certain step found from here.                                                     |

## 10. 中断と再開(保存)

保存キーは次の **5 つ**(すべて `bg.` 接頭辞。import ゼロの葉 `storage/keys.ts` が宣言し、
registry の `storageKeys` はその `Object.values` — `src/app/gameKeys.test.ts` の
`RELEASED_KEYS` はこの順で `bg.saveGame` / `bg.saveDaily` / `bg.stats` / `bg.flags` /
`bg.prefs` と固定している)。どれも `schemaVersion: 1`。

| キー           | 中身                                                             |
| -------------- | ---------------------------------------------------------------- |
| `bg.saveGame`  | 難易度モードの中断中の盤面(1 スロット)                           |
| `bg.saveDaily` | デイリーの中断中の盤面(1 スロット。キーの葉の名前は `dailyGame`) |
| `bg.stats`     | 統計(§11)                                                        |
| `bg.flags`     | チュートリアル完了                                               |
| `bg.prefs`     | 最後に選んだ難易度だけ(盤面の遊び方を変える設定は 1 つもない)    |

**中断中の盤面のレコード**(v1。`game/session.ts` の `SessionRecord` に、保存層が
`schemaVersion` と `savedAt` を足す):

| フィールド       | 型・形                                                            |
| ---------------- | ----------------------------------------------------------------- |
| `mode`           | `'difficulty'` / `'daily'`                                        |
| `seed`           | 1〜200 文字                                                       |
| `difficulty`     | `'easy'` / `'medium'` / `'hard'`                                  |
| `dailyDate`      | デイリーは `YYYY-MM-DD`、難易度モードは `null`                    |
| `width` `height` | 難易度のプリセットと一致                                          |
| `board`          | 1 マス 1 文字の行優先: `.` = 水、`1`〜`8` = 島(10×10 で 100 文字) |
| `solution`       | 答え。辺ごとに 1 桁の `0`〜`2`、§2 の辺の順                       |
| `bridges`        | プレイヤーの橋。同じ形                                            |
| `hintCount`      | 0〜10⁹ の整数                                                     |
| `elapsedSeconds` | 0〜10⁹ の整数                                                     |
| `schemaVersion`  | `1`(保存層)                                                       |
| `savedAt`        | 保存した時刻(ms、0〜10¹⁵ の整数。保存層。読むだけで使わない)      |

辺の順は盤面だけから決まる(§2)ので、`solution` / `bridges` の桁の意味は `board` が
与える。**Undo 履歴は持たない**(§9)。ミス回数も持たない(概念がない)。盤面と答えを
そのまま持つので、生成器が版で変わっても中断中の盤面は生き残る。手の列ではなく橋の
状態を持つのは、どの橋の状態(0〜2・交差なし)もタップの列で作れる — 超過も許す(§4)
ので — からで、手の列を再生しても同じ集合にしか届かない。

- **どのスロットのレコードかを決めるのはキーである**(`gameSlotSchema(key, expectedMode)`、
  `parsed.mode === expectedMode`。`src/test/savedGameSlots.test.ts` と
  `storage/slots.test.ts` が強制する)。難易度用のキーに入っている `mode: 'daily'` の
  レコードは「デイリーだった」のではなく壊れている。
- **スロットを置き換える前に確認する**(中断中と違う難易度を選んだとき)。
- **検証は 2 段の fail-closed**。どちらかが `null` を返したレコードは読み捨て、プレイヤーは
  ゲームのホームに着く — **黙って新しい対局を始めない**。
  1. **形と中身のうち、ソルバーの探索でないものすべて**(`storage/schemas.ts` の `gameSlotSchema`。
     バックアップの書き出し・復元もこれだけを通す — ソルバーの探索は走らない):
     - 形: JSON として読めない・`schemaVersion` が 1 でない・`mode` / `difficulty` が未知・
       `seed` が空 / 200 文字超 / 文字列でない・日付と `mode` が合わない・デイリーが medium で
       ない・幅と高さがプリセットと違う・`board` の長さが幅 × 高さでない / `.` と `1`〜`8` 以外の
       文字・`solution` / `bridges` が `0`〜`2` 以外の文字 / 長さが互いに違う / マス数の 2 倍を
       超える・カウンタが範囲外・キーとモードが合わない。
     - 中身(`fromRecord` と同じ `decodeBoards` と `isSolved` で読む): `board` が組み立たない
       (上下左右に隣り合う島、島が 1 つ以下、見えている相手で数字をまかなえない島)・島の数が
       ティアの範囲外・`solution` が §3 の勝利条件を満たさない(本数違い・交差・2 グループ以上・
       辺の数と長さが違う)・`bridges` が盤面に置けない(交差する 2 辺の両方に橋。数字を超えた
       島はプレイで生まれる — §4 — ので通す)・**既に解けている**(完成した盤面は履歴であり、
       再開しない)。
  2. **一意性の再証明**(`fromRecord`、ゲームを開いたときだけ — §6)。1 のすべてをもう一度
     確かめたうえで、**答えが唯一でなければ**捨てる: 読み込み時に `countSolutions` で解を 2 まで
     数え直し、ちょうど 1 つと最後まで証明できなければ捨てる(Hint が別の解を指すことを
     起こさない)。これは §6 の探索の一つで、ゲームを開くときにだけ走る。ノード上限は
     生成と同じ `SEARCH_NODE_LIMIT`(500)なので、生成器が一意と証明した盤面は読み込みでも
     必ず証明できる(数え上げは走査した出荷盤面で最大 5 ノード、生成器の候補 約 6 万面で
     最大 28 ノード)。上限に届く作為的な盤面は捨てる(`session.test.ts`)。
  - デイリーの日付が**今日の日付でない**(過去も未来も)ものは、保存層が読み込みで記録ごと
    捨てる(§8。Box Regions と同じ `dailyDate !== today`)。`fromRecord` 自体は形の正しい日付
    ならどれも通す — 今日を知っているのは保存層である
- **検証の置き場所**(Web 先行公開の 4 本 — Snake / Loop Puzzle / Bridges / Peg Solitaire — に
  共通の規則。各ルール文書の保存の節が同じことを書く):
  - **仕事量が盤の大きさで決まる検査は、中身の検査も含めてすべてスキーマの `validate` に置く**
    (上の 1。Snake の層ごとの歩みのように探索の形をしたものも、盤で仕事量が決まるならここ)。
    バックアップの書き出しと復元は、レコードを持ち主の `validate` だけに通す
    ([architecture/backup.md](architecture/backup.md)「検証は各レコードの持ち主が行う」)ので、
    プレイから生まれえない盤面は書き出しに入らず、それを含むファイルの復元は「壊れている」
    (`backupFileDamaged`)として全体を拒否し、何も書かない。どれも盤の大きさ(最大 10 × 10)で
    仕事量が決まり、`validate` 1 回(Hard)は開発機で中央値 0.04〜0.07 ms・`--jitless` で
    0.14 ms 程度(2026-10-17)。`validate` は例外を投げず、通らなければ null を返す(backup.md の契約)。
  - **スキーマの外に残すのは、仕事量を盤ではなくノード数の上限が抑えるソルバーの探索だけ**
    (上の 2 の `countSolutions`。Loop Puzzle の計数探索も同じ扱い)。ゲームがスロットを読み込む
    ときにだけ走り、バックアップの検証では走らせない([GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)
    「CPU 探索」)。
  - **読み捨てた記録はストレージから消さない。** 既存の全ゲーム(共有の `loadRecord`、Box
    Regions / Crown Grid などの読み込み)と同じ扱いで、そのスロットに次に書くとき(対局の保存・
    完成で消す)に置き換わる。消さないのは、スキーマが読めない記録は新しい版が書いたものかも
    しれないから(backup.md は「新しすぎる」と「壊れている」を分ける)。プレイヤーはホームに
    着き、そのスロットで新しい盤面を始めれば置き換わるので行き止まりにはならない。読み込みで
    記録ごと消すのは、今日でないデイリーだけである。
  - **残る穴**: 2 だけが拒否する記録 — 盤面も答えも 1 を通るのに、答えが唯一と証明できない
    もの — は、消されないので、次のバックアップにも入り、復元も通り(「復元しました」)、
    開くとホームに着く。手で作った記録か、版をまたいで探索の上限やソルバーが変わった場合に
    しか生まれない(1 字の破損は、ほぼ必ず 1 の勝利条件か盤面の検査で落ちる)。消す・
    スキーマで探索する、のどちらも採らなかった(前者は既存の全ゲームの扱いと違う新しい
    振る舞いになり、後者は探索をバックアップの検証に持ち込む)。`storage/slots.test.ts` が、
    1 の拒否・書き出しから外れること・2 だけが拒否する記録が残って次の保存で置き換わることを
    確かめる。
- 背景へ回るとき、盤面の保存と未計上秒の計上を**同じ同期処理で**行う(既存ゲームと同じ)。
- 保存の失敗でゲームを止めない。バリデータは例外を投げない。このゲームの保存が壊れても
  シェルや他のゲームは止まらない。他のゲームのキーには触れない。
- **ベータ中はスキーマを変えうる。**変えるときは黙って消さず、ホームの `WebBetaNotice` が
  先に告げる([WEB_VERSION.md](WEB_VERSION.md)「保存データ」)。正式収録でスキーマを
  凍結し、公開ビルドの payload で `storage/releasedRecords.test.ts` を作る。

## 11. 統計と時計

- **プレイ中に時計を表示しない。**経過時間は内部で記録し、結果画面と統計でのみ見せる。
  セッションは時計を読まない(`withElapsedSeconds` で持ち主から受け取り、減る方向の値は
  無視する)。
- `bg.stats`(v1、`state/statsLogic.ts`):
  - `easy` / `medium` / `hard`(難易度モードだけ): プレイ回数(新しい盤面と再挑戦。再開は
    数えない)/ クリア数 / 合計プレイ時間 / 最短時間(未クリアは `null`)。
  - `daily`: プレイ回数 / 合計プレイ時間。**デイリーは `medium` に混ぜない**(同じ Medium の
    盤面でも、毎日 1 問の記録と好きなだけ遊ぶ記録は別のもの)。Unblock Puzzle と Loop Puzzle は
    デイリーを Medium の行に数えるので、3 本でそろえる規則は**製品オーナーの確認待ち**
    (計画 `plans/2026-10-17-unblock-snake-loop-bridges-peg.md`「オーナーの判断に残した点」)。
  - `dailyTimes`: 達成した日 → その日の最短時間。日付の**集合**であり、連続は数えない。
    読めない 1 日は捨て、ほかの日は残す(2,000 日まで)。
  - **累計プレイ時間**は 4 つの合計プレイ時間の和で、別に保存しない(食い違いようがない)。
  - 統計画面: 難易度ごとの 4 項目、デイリーのプレイ回数・達成日数・合計プレイ時間、
    「すべてのモード」の合計プレイ時間。ストリークも順位も無い。
- 時計は 1 秒ごとに ref を進めるだけで再描画しない。盤面の画面が見えていない間
  (`visibilityState` が `visible` でない)は進まない。背景へ回る・ホームへ戻る・コレクション
  へ戻るときに、盤面の保存と未計上の秒の計上を同じ同期処理で行い(§10)、同じ秒を二度
  数えない。戻ってきたときに勝手に進むものは何も無い(時計は見えている間だけ、橋は
  プレイヤーの手でだけ動く)。
- **スコアは作らない。**自己ベストの更新は、更新したときだけ静かに示す(`BestDelta`)。

## 13. 演出とアクセシビリティ

- **アクセント 1 色**(鉄紺 — ライト `#323b5d` / ダーク `#7d83b0`、`src/ui/styles.css` に
  登録済み)。ゲームの CSS(`ui/bridges.css`、クラスは `bg-` 接頭辞)は `var(--accent)`
  等の共通トークンだけを使い、`styles.css` は変えない。アクセントの置き場所は**橋の線**
  (盤面でいちばん多いインク)、選択の輪、ちょうどの島の塗り。ライト / ダークの両方。
- **島の描き方**: 直径 0.84 マスの円に ASCII の数字(`--font-display`、0.46 マス)。
  不足 = 縁取りだけ(`--ink`)、ちょうど = アクセントで塗りつぶし(数字は `--accent-ink`)、
  超過 = 警告色の**二重の輪**(`--warn` の縁 + 内側にもう 1 本、地は `--warn-soft`)。選択 =
  1.1 マスの太い輪(3px、アクセント)、相手 = 同じ大きさの点線の輪、ドラッグの的 = 太い輪。
  キーボードのフォーカス = タップ目標の円の内側の輪(`--ink-soft`)— 選択の輪と別の形。
- **島のタップ目標**: 直径 1.3 マスの円のボタン(角丸で当たり判定も円)。島は上下左右に
  隣り合わず、斜めの島の中心は √2 マス離れているので、円は重ならない。
- **大きさ**: 1 マス = min(幅の取り分, 高さの取り分) を 28〜72px に収める。幅の取り分は
  (画面幅 − 26px) ÷ (列 + 0.4)、高さの取り分は (画面高 − 320px − 下端のセーフエリア) ÷
  (行 + 0.4)。320px は上のバー・Undo / Hint の列・盤面の下の 2 行・余白・Web 版の広告の予約
  (116px)の実測の和。下端のセーフエリア(ホームインジケーターの帯)は、Web 版の広告の予約が
  116px の上に足すもの(`src/ui/styles.css`)なので、ここでも引く。
- **画面高は `svh`(小さいビューポート)で測る**。モバイルのブラウザの `100vh` はツールバーを
  隠したときの高さなので、`vh` で決めるとツールバーが出ている間は盤面が大きすぎ、Undo / Hint が
  広告の下にずれてページがスクロールする(レビューの模擬: 412×660 の表示で `100vh` = 716 のとき
  Undo / Hint の列が 502〜579px、広告の上端 544px)。`svh` を知らない WebView(Chromium 108
  より前 — 最低線の Chromium 88 を含む)では `vh` のまま。選び分けは `@supports (height: 100svh)`
  で行う — `--bg-cell` はカスタムプロパティで、構文解析の時点ではどんな値も受け付けるので、
  `vh` の行の後に `svh` の行を重ねる書き方では、`svh` を知らない環境でも上書きされ、それを使う
  大きさがすべて無効になる(`ui/bridges.css` のコメント)。
- 実測(Chromium 1194、Playwright、2026-10-17。`svh` の式が選ばれていることを計算値で確認。
  自動の模擬では `svh` = `vh` = 表示の高さなので、ツールバーの出入りそのものは再現していない):
  360×640 の Hard 10×10 は 1 マス 30.8px・タップ目標 40px で、盤面・下の欄・Undo / Hint が
  スクロールなしに収まる(盤面 78〜400px・Undo / Hint の列 447〜524px、広告の上端 540px)。
  360×640 の Medium 9×9 は 34.0px(目標 44px)、Easy 7×7 は 43.2px(目標 56px)— どれも高さの
  取り分で決まる。360×660 の Hard は幅の取り分が勝って 32.1px(目標 42px)、412×660 の Hard は
  高さで 32.7px(Undo / Hint の列 467〜544px、広告の上端 560px — レビューが `svh` の振る舞いとして
  測った位置と同じ)。1280×800 の Medium は高さで 51.1px(目標 66px)。768×1024 の Hard は高さで
  67.7px、Easy / Medium は上限の 72px。どの測定でも Hint の後の下の欄は 2 行で、ページも盤面の
  欄もスクロールしない。盤面のサイズ・配置は言語によって変わらない。
- 各島はボタンで、**数字・行・列・今の橋の本数・状態(不足 / ちょうど / 超過)・選択中か・
  つなげる相手か(とその 2 島の間の本数)**を読み上げる(`bridgesIsland*`)。盤面は
  `role="group"` で「盤面、W × H、島 n 個」。状態は色だけでなく形でも示す(§5)。
- 各島の読み上げ名には、Hint の印が付いているときはそのこと(§5)も入る。
- 盤面が解けた一拍と結果カードまでの間は既存ゲームと同じ(`useResultReveal`)。カードは
  現れてから 400ms はクリック・タップを受け付けず、キーリピートは受け付けない(§4)。
  解けた瞬間に盤面全体へ 1 回だけ淡い塗りが重なる(0.9 秒)。**Reduced Motion**(OS の設定とアプリの
  設定のどちらでも)では塗りは出ず、島の色の切り替えも即時、結果カードも即時。連続再描画を

- 効果音は既存の `services/sound.ts` だけ: 橋を足す = `select`、0 本に戻す・Undo = `undo`、

## 15. 意図的な差分

ブランド原則により合わせないもの:

- ミス回数制限・ライフ制・ゲームオーバー(しない。§3)
- プレイ中のタイマー表示、ストリーク、オンラインランキング、スコア(しない)
- Hint / Undo を広告視聴やコインの報酬にすること(しない。常に無料・無制限 — §9)
- 1 日 1 問だけの供給(しない。難易度を選べばいつでも新しい盤面 — §8)
- レベル 1〜100(段階が存在しないので作らない)

設計判断として合わせないもの:

- **他社の名称・問題・画面。**形式は一般に Hashiwokakero と呼ばれるものと同じだが、
  名前は Bridges だけ、盤面はこのゲームの生成器のもの、見た目はこのゲームのもの。
- **数字を超える橋を拒むこと**(しない。§4 — 循環を全辺で同じにし、超過は表示で知らせる)。
- **橋の線・水のタップで橋を変えること**(作らない。§4)。
- **自動補完**(「確定した橋を自動で引く」— 作らない。推論はプレイヤーのもの)。
- **推測が必要な盤面・複数解の盤面**(出さない。§6)。
- **11×11 以上**(§1)。

関連する既存ゲームとの違い(混同しないため):

- **Number Path**: 1 本の道が**マス**を全部通る(番号順の一筆書き)。Bridges の橋は
  **島と島の間の水**を渡り、島は何本の橋とも結べ、全マスを覆う必要はない。
- **Loop Puzzle**(同じ先行公開の 5 本の 1 つ): 格子の**辺**に 1 本の閉じたループを引き、
  交差・分岐・複数ループは禁止。Bridges はループを禁止せず、分岐(1 つの島から最大
  4 方向)がふつうで、2 本の橋がある。
- **Dots and Boxes**: 2 人対戦で、点と点の間の線を取り合って箱を作る。Bridges は 1 人の
  論理パズルで、線(橋)の本数を数字が決める。
- **Box Regions / Shape Regions**: 盤面を領域に切り分ける。Bridges は切り分けず、つなぐ。

保存・コード・ルールはどのゲームとも共有しない(`games/A` は `games/B` を import しない —
`importBoundaries.test.ts`。乱数の `rng.ts` は Box Regions からの写し)。
