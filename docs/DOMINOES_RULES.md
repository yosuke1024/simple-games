# Dominoes — 正式ゲームルール

このドキュメントが Dominoes の仕様の正本である。実装
(`apps/simple-games/src/games/dominoes/`)、テスト、Quick Rules はここに従う。
コードはここへ `§n` で言及する。挙動を変えるときは、同じコミットでこの文書を直す。
着手前の計画は
[docs/plans/2026-09-27-yacht-mancala-dominoes-hit-and-blow-dots-and-boxes.md](plans/2026-09-27-yacht-mancala-dominoes-hit-and-blow-dots-and-boxes.md)
にあるが、実装後はこの文書が勝つ。

ブランド原則([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md))はこの文書より上位にある。

ゲーム ID は `dominoes`、i18n キーの接頭辞は `dominoes`、保存キーの接頭辞は `dm.` である。
タイトルは全言語で `Dominoes`(固有名詞は訳さない — [I18N_POLICY.md](I18N_POLICY.md))。
現在は **Web 版の先行公開(ベータ)**で、アプリには収録していない(registry の
`channel: 'web-beta'`、[WEB_VERSION.md](WEB_VERSION.md)「先行公開(ベータ)」)。

**採ったルールの出典**: 標準的な 2 人制のドロー・ドミノ(ダブル 6 の 28 枚、7 枚配り、
山から引く、出し切った側が相手の残りの目を得る)。採らなかった変種は §12 に列挙する。

## 1. 用具と配札

- **ダブル 6 の 28 枚**。牌は 2 つの目 `[a, b]` で持ち、**小さい目を先に**正規化する
  (`game/types.ts`)。[3, 5] はあって [5, 3] はない — だから「28 枚が 1 回ずつ」を
  同一性で確かめられる。牌が向きを持つのは列に置かれたときだけで、列は牌の横に
  置いた向き(`Placed` の `left` / `right`)を持つ。
- 全 28 枚は固定の順序 `ALL_TILES`([0,0], [0,1] … [0,6], [1,1] … [6,6])で作る。
  配札はこの並びをシャッフルするので、**この順序は過去に配ったすべての盤の一部**で
  ある(`game/compatibility.test.ts` が固定する)。
- 対局者は **2 人**。下があなた、上が CPU(`PLAYER = 1` / `CPU = 2`)。対局相手は
  CPU だけである — オンライン対戦もローカル対人戦も作らない。
- **配札はシード決定的**。`shuffled(ALL_TILES, createRng(seed))` の先頭 7 枚があなた、
  次の 7 枚が CPU、残り 14 枚が**山(ボーンヤード)**で、山は**先頭から**引く。
  手札は読みやすいよう配った時点で昇順に並べ、山はシャッフルされた順のまま持つ。
- シードは対局ごとに新しい(`dominoes-<時刻>-<乱数>`)。レベルも日付もないゲームなので
  毎回新しい配札になり、同時にシードが配札と CPU の同点処理(§5)を完全に決める。
- CPU の手札と山は**枚数だけ**見える(§6、§11)。

## 2. 開始

- **両手札のうち最大のダブル**を持つ側が、それを出して始める。ダブルが 1 枚も
  配られていなければ、**最も重い牌**(目の合計が最大。同じなら大きい目が大きい方)。
  別の 2 枚がこの比較で並ぶことはない — 合計も大きい目も同じなら同じ牌である。
- 開始牌は**対局を作った時点で自動的に列に置かれる**(`createSession`)。遊びは
  相手側の手番から始まり、手数(`moveCount`)は 1 から数える。
- **先攻は選べない**。規則が決めるので `prefs` は持たない(Connect Four §1 や
  Mancala と違う)。ホームには選ぶものがない。
- 画面の最初の 1 行が、誰が何で始めたかを言う(「CPU が 6–6 で始めました」)。

## 3. 一手の解決(置く・引く・パス)

手番は 1 つ以上の**動作**でできている。どの動作も手数を 1 つ進める。

- **置く**: 列の**どちらかの端**に、端の目と同じ目を持つ牌をつなぐ。向きは自動で、
  一致する目が端に接する(`placeTile`)。置いたら手番は相手へ移る。
  - 両端に置けて**端の目が違う**ときだけ、置く端を選ぶ。1 回目のタップで牌が
    持ち上がり、列の両端の印が「左端(3)に置く」「右端(5)に置く」のボタンになる。
    **同じ牌をもう一度タップすると取り消し**。
  - 両端の目が**同じ**ときは、どちらに置いても残る端が同じなので**選ばせず右端に置く**
    (`distinctEnds`)。CPU も同じ規則で右端だけを候補にする。
  - ダブルも列の中に 1 枚として置く。十字に置いて枝を増やす(スピナー)ことはしない
    — 列の端は常に 2 つである(§12)。
- **出せる牌があれば出さねばならない**。そのあいだ Draw は無効で、パスもできない。
- **引く**: 出せる牌がなく、山が残っていれば、山の**先頭の 1 枚**を引いて手札の末尾に
  加える。**1 タップで 1 枚**。手番はそのまま — 引いた牌が出せれば出し、出せなければ
  また引く。
- **パス**: 出せる牌がなく、**山も空**なら、パスして手番を相手へ渡す。Pass ボタンは
  この状況でだけ現れる。
- **連続パスの数**(`passes`)を数え、**どちらかが置いた時点で 0 に戻る**。
- 規則が許さない入力は、ボタンが無効になっていて何も起きない。音も鳴らさない。
- CPU は手番を **450ms ごとに 1 動作**(置く / 引く / パス)で進める(§5)。

## 4. 終了条件と得点

- **出し切り**: 最後の牌を置いた側の勝ち。**得点 = 相手の手札に残った目の合計**。
- **手詰まり**: 山が空のまま**両者が続けてパス**したら(`passes` が 2)終局。
  **残りの目の合計が少ない側の勝ち**で、得点は**その差**。同じなら**引き分け**
  (得点 0)。
  - 「どちらも置けない」を先読みして自動で終わらせず、パスを 1 回ずつ実際に踏む。
    パスは画面に見える出来事であり、あなたが置けないことを確かめてからボタンで
    渡す — ゲームが勝手に代わりに降参しない。
- **1 局 = 1 ゲーム**。100 点先取のマッチは作らない(§12)。
- 遷移は `status`(`'playing' | 'won' | 'lost' | 'draw'`、あなたから見た結果)で
  一度だけ起きる。終局の仕方(`ending`: `'out'` / `'blocked'`)、勝者の得点、両者の
  残りの目もセッションが持ち、結果カードがそのまま読む(§11)。

## 5. CPU

- **強さは 1 段階**。合法な(牌, 端)の組のうち、**「目の合計 + ダブルなら 3」が
  最大**のものを置く(`tileWeight`)。重い牌は手詰まりでも出し切られても失点になり、
  ダブルは合う端が 1 つの目しかないので後で最も置きにくい — 早く手放すのが定石の
  入口である。探索はしない。
- **同点**は `createRng(`${seed}:cpu:${moveCount}`)` でシャッフルしてから重さで
  安定ソートして決める。同じシードで同じ手順を踏めば、CPU は必ず同じ動作を返す
  (`game/compatibility.test.ts` が 2 シードで固定する)。
- 出せる牌が無ければ、山があれば 1 枚引き、山が空ならパスする(§3 と同じ規則)。
- **難易度は作らない**。弱い CPU を作るなら乱数で打たせるしかなく、それは易しい
  相手ではなく退屈な相手である。
- **1 本の timeout で 1 動作**(`CPU_DELAY_MS` = 450ms、`state/GameContext.tsx`)。
  引いた場合は山の枚数が 1 つ減り、状態行が「CPU が山から 1 枚引きました」と言い、
  CPU の手番のままなので同じ effect が次の 1 拍を張る。ループも待ち合わせも書かない
  ([GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「手番が連なるゲーム」— Hearts / Gin Rummy と
  同じ形)。アンマウント・画面遷移・新規対局は保留中のタイマーを外す。
- CPU の手番の途中で中断した対局は、再開すると CPU がそのまま続きを打つ(§9)。

## 6. CPU が見ているもの

このゲームは**不完全情報**である。「CPU はこちらの手札や山を覗いているのでは」という
疑いは議論では晴れないので、Gin Rummy と同じく**型で決着させている**
([GIN_RUMMY_RULES.md](GIN_RUMMY_RULES.md) §5)。

- `game/cpu.ts` が読むものはすべて **`CpuView`** として渡る。`CpuView` には
  **あなたの手札を置く場所も、山の並びを置く場所もない**。
- セッションから `CpuView` への橋は **`buildCpuView` ただ 1 つ**(`cpuViewOf` 経由)で、
  参照ではなく**コピー**を渡す。テストは、あなたの手札と山を混ぜて配り直しても
  ビューも CPU の動作も変わらないことを確かめる(`game/cpu.test.ts`)。
- `CpuView` が持つのはこれだけである:

  | フィールド          | 中身                                         |
  | ------------------- | -------------------------------------------- |
  | `hand`              | **CPU 自身の手札**                           |
  | `line`              | 場の列(両者に見えている)                     |
  | `boneyardCount`     | 山の**枚数だけ**。どの牌かも、並びも入らない |
  | `opponentTileCount` | あなたの手札の**枚数だけ**                   |

- **配札のシードは cpu.ts に渡らない**。同点処理用の乱数列(上の `${seed}:cpu:…`)が
  関数として 1 本だけ渡る — **鍵ではなく硬貨**である(`chooseCpuMove(view, rng)`)。
- 人間の熟練者なら「さっき 3 と 5 の端で引いたから、3 も 5 も持っていない」と覚えて
  おける。その推理は許される情報だが、この CPU は**使わない** — 1 段階の強さを
  負かせる相手に留めるための選択であって、見えないものを見ないための制約ではない。

## 7. 助けの形 — なし

- **Undo は作らない**。引いた牌は情報であり、引いたあとで戻せば山の先頭を覗いた
  ことになる。**戻せるのは手であって、知ってしまったことではない**
  (Gin Rummy §6 と同じ判断)。
- **Hint も作らない**。どの牌を手放すかがこのゲームの判断そのものである。
- 代わりに**規則を見えるようにする**: あなたの手番では出せる牌だけが押せる、
  Draw は引かねばならないときだけ有効、Pass はそれしか残っていないときだけ現れる、
  両端の目が数字で出ている、状態行がいま何をすべきかを 1 行で言う。
  どれも「どれを出すべきか」は言わない。
- 広告視聴や課金による助けは、もちろん作らない([ADS_POLICY.md](ADS_POLICY.md))。

## 8. スコアと統計

- 1 局の得点(§4)は結果カードで示すだけで、**積み上げない**(マッチがない)。
- 統計は全体で 1 組: `played`(開始した回数)・`wins`・`losses`・`draws`・
  `totalPlaySeconds`(`dm.stats` v1)。ストリークは数えないし表示しない。
- 対局を放棄して新しく始めた場合、負けには数えない(`played` には既に数えている)。
  記録されるのは実際に終局した対局だけ — 統計が脅しになってはならない。
- プレイ時間は逐次計上(bookedRef 方式、Connect Four §7 と同じ)。

## 9. 中断と再開

- **途中保存する**。1 動作ごとに保存し、開き直した対局は保存した瞬間と同じである
  — 同じ列、同じ手札、**同じ順の山**(次に引く牌も同じ)。
- 保存スロットは 1 つ(`dm.saveGame` v1):
  `seed` / `line`(置いた向きの `[left, right]` の列)/ `playerHand` / `cpuHand` /
  `boneyard`(引く順)/ `toMove` / `passes`(連続パス数)/ `moveCount` /
  `elapsedSeconds` / `savedAt`。手札と山の牌は小さい目を先に書く。
- **保存しないもの**: 結果(局面から導く)、開始牌(シードの配札からもう一度導く)、
  Undo 履歴(そもそも無い)。
- 壊れた保存・規則から生まれえない保存は**読み捨てて、ホームへ戻る**(勝手に新しい
  対局を始めない)。検証は fail-closed(`game/serialize.ts` の `decodePosition`):
  - 目が 0〜6 の外にある。手札か山の牌が大きい目を先に書いている。
  - **28 枚が過不足なく 1 回ずつ**現れない(列・両手札・山を通して)。
  - **列の隣接が一致しない**(`line[i].right !== line[i+1].left`)、または列が空。
  - 山が**そのシードの配札から先頭を引いた残り**と一致しない(枚数・牌・順序)。
    列に**そのシードの開始牌**が無い。— 再開するのは配られたとおりの対局である。
  - 連続パスが山の残っている状態で数えられている。
  - 手数が局面と合わない。手数 = 列の枚数(開始牌を含む)+ 引いた枚数 + パスの総数
    で、応答されたパスは必ず直後の 1 枚の配置で応答されているので、パスの総数は
    「いまの連続パス数」以上「それ + 開始後に置いた枚数」以下に収まる。手数は
    CPU の同点処理の半分(§5)なので、合わない保存は別の対局として再開してしまう。
  - 開始牌にまだ誰も応えていない(列が 1 枚)のに、手番が規則と合わない。
  - **終局済み**: どちらかの手札が空、または連続パスが 2(手詰まり)。
- ホーム画面ショートカットからの起動は、保存された対局があればホームを経ずに
  そのまま盤面を開く(issue #113。Quick Rules が未了なら Quick Rules が先)。

## 10. Quick Rules(アプリ内チュートリアル)

3 ステップ・図中心・各 1 文(初回起動時に表示し、終えるとそのまま最初の対局を配る。
以後はホームから):

1. 列のどちらかの端と同じ目の牌をつなぐ。
2. 置ける牌がなければ、置けるまで山から引く。山が空のときだけパス。
3. 最後の牌を出したら勝ち。相手に残った目の合計が得点。

ガイドを公開するまで「詳しく見る」は出さない(`src/ui/landing.ts`)。

## 11. 演出とアクセシビリティ

- **画面**は上から: 上部バー(戻る / CPU の手札の枚数と山の枚数 / 新しい対局)、
  場の列、状態行 1 行、あなたの手札、アクションバー(Draw、必要なときだけ Pass)、
  バナー。
- **列は `flex-wrap` で折り返す 1 行**で、横にスクロールしない。28 枚すべてが並んでも
  行が増えるだけで電話の幅に収まる(`ui/DominoesLine.test.tsx` がマークアップと
  スタイルシートの両方を固定する)。牌は横向きで 44×22px、**ダブルは縦向き**
  (22×44px)に描いて一目で区別する。幅 600px 以上では 1 段大きくする。
- 牌の各半分は **Ludo のサイコロと同じ 3×3 の点**。0 は無地。面は `--surface`、点は
  `--ink` で、テーマに従う。盤面に翻訳の要る文字は置かない — 目は点、端の目は ASCII
  数字である。
- 列の**両端に端の印**(開いている目の数字)。タップ対象の大きさ(`--tap-size`)を
  常に確保しているので、端を選ぶボタンに変わっても列は動かない。
- **あなたの手札**は縦向きの牌ボタンが折り返して並ぶ。あなたの手番では出せる牌だけが
  押せ、出せない牌は薄くなる。CPU の手番のあいだは全部押せないが**薄くしない**
  (出せないのではなく、手番ではないだけ)。端を選ぶ途中の牌は持ち上がり、枠が付き、
  `aria-pressed` で読み上げる。
- **直前に置かれた牌**(CPU の牌を含む)には輪を付ける — 目を離しても相手の手が
  見つかる。色ではなく形で示す。到着は 160ms の小さな収まりで、Reduced Motion
  (アプリ設定または OS)では出さない。
- **状態行は 1 行固定**(何も言わないときも高さを保つ): 開始牌、あなたの番、端を選ぶ、
  引かねばならない、パスするしかない、CPU が考えている、CPU が引いた、CPU がパスした。
- **読み上げ**: 列は「場の列:12 枚、左端 3、右端 5」、列の牌と手札の牌は「牌 3–5」、
  CPU と山は「CPU の手牌 7 枚」「山 残り 14 枚」、端のボタンは「左端(3)に置く」。
- **決着してから結果カードが出るまでに約 1 秒置く**(`ui/useResultReveal.ts`)。
  Reduced Motion では即時。結果カードは勝敗、終わり方、勝者の得点
  (「あなたの得点 17」/「CPU の得点 17」。引き分けには無い)、両者の残りの目、
  通算の勝敗を示す。共有(`ShareAction`)が送るのは得点の行 — 引き分けなら残りの目の
  行 — だけで、通算は送らない。
- 効果音は既存の合成音(`services/sound`)のみ: 置く(どちらの側でも)で `select`、
  引く・パスで `undo` の短い音、勝ちで `clear`、負け・引き分けで `gameOver`。設定に従う。
- **時計を出さない**。経過時間は統計にだけ残る。

## 12. 意図的な差分

市中のドミノアプリや変種を調べたうえで、意図的に合わせないものを記録する。

**ブランド原則により合わせないもの**

- 助け・牌のデザイン・強さを広告や課金に結び付けない。
- オンライン対戦・レーティング・ランキングはない。記録は端末の中だけにある(§8)。
- デイリーやストリークで毎日呼び戻さない。

**設計判断として合わせないもの**

- **1 局 = 1 ゲーム**。100 点(や 150 点)先取のマッチは作らない。1 局が短く、
  それ自体で完結する単位だからで、マッチは中断と再開の単位を長くするだけである。
- **Block / All Fives(Muggins)/ Mexican Train などの変種は作らない**。山から引く
  ドロー・ドミノ 1 つに絞る。All Fives の「端の合計が 5 の倍数で得点」は算術の
  別ゲームであり、Mexican Train は多人数の遊びである。
- **難易度の段階を作らない**(§5)。
- **Undo を作らない**(§7)。
- **牌のデザインを着せ替えない**。見た目の選択肢は遊びを変えない。
- **ダブルは列の中で縦向きに描く**。十字に置いて四方に枝を出すスピナーは採らない —
  列の端は常に 2 つで、画面は折り返す 1 行のまま読める。
- パスは自動にしない。手詰まりの判定も先読みしない(§4)。
- 先攻は選ばせない(§2)。規則が決めるものに設定を足さない。
