## 1. 盤と物理

### 盤

- 論理盤面は **360×640**(Sky Fighter §1 と同じ大きさ)。上から見た道路で、**上が前**。
- 横の座標 x は盤の左端 0 から右端 360。**路面は x ∈ [28, 332](幅 304)**、その外側の 12px ずつ
  (x ∈ [16, 28) と (332, 344])が**路肩**、さらに外は走れない(車体がはみ出さないよう車の中心を
  [33, 327] にクランプする)。路肩は Bump ではなく減速の帯である(§4)。
  - 計画の「Bump になるのは交通と路肩(外側 12px)だけ」と「路肩は … Bump に数えない」は同じ箇条の
    中で食い違うので、後者を採った(§18)。
- **車線**は路面 304 を等分する。3 / 4 / 5 車線(面で決まる、§7)で幅は 101.33 / 76 / 60.8px、
  車線 i(左から 0)の中心は `28 + 304 × (2i + 1) / (2L)`。車線は交通の置き場所を決めるだけで、
  **自車は車線に吸着しない**(横位置は連続)。交通車は車線の中心に置く(壁の行だけは §5 の幾何)。
  - **車線の境目は壁ではない**: 車の幅(34〜42)は車線の幅より小さく、辺が触れるだけは重ならない
    (§4)ので、車線の中心に 1 台ずつ置いても、隣り合う車の間を自車(34)が通れる。算術では、隣り合う
    車の間の空きは 3 車線で 59.3〜67.3px、4 車線で 34〜42px(34px ちょうども通れる)、5 車線で
    18.8〜26.8px(通れない)。3 車線では最も外の車と路肩の端(x = 16)の間も 41.7〜45.7px 空く。
    したがって「壁」は交通の置き方で作る(§5「壁の幾何」)。
- 縦は**コース座標 r**(スタートライン 0、ゴール U)。交通は全車が同じ速度 **vT = 200 px/s** で
  走るので、交通と一緒に動く座標で書けば**交通は静止している**。交通の位置は生成(§5)が決めた
  固定値で、毎ステップ積み上げない(Bunny Hop §1 と同じ考え)。
- 車の速度 **w はこの座標での速さ**(= 交通に対する速さ)で、**0〜420 px/s**。地面に対する速さは
  w + vT で、路面の破線(§11)はこの速さで流れる(算術では最大 620 px/s)。w ≥ 0 なので、交通が
  後ろから当たってくることは無い。
- 車の位置は**前端**の r と**中心**の x で持つ。自車は **34×58**(幅 × 長さ)。画面では前端を
  **y = 470** に固定し(盤の下 1/3)、世界のほうが流れる。前方に見えるのは 470 論理 px。
- 交通車は 3 車種(幅 × 長さ。長さは計画の初期値、幅はこの文書の初期値):

  | 車種  | 幅  | 長さ | 初出(§7) |
  | ----- | --- | ---- | -------- |
  | sedan | 34  | 58   | Lv1      |
  | van   | 38  | 70   | Lv11     |
  | truck | 42  | 104  | Lv21     |

  加えて**工事区間**: 外側の 1 車線(左端か右端)を長さ 500 だけ閉じる静止物(Lv31 から)。幅はその
  車線の幅いっぱい(初期値。路肩との間の空きは 12px で通れない)。当たりは交通車と同じ(§4)。

- ライバル 3 台も 34×58 で、自車と同じ物理で走る(§6)。

### 物理(`step(state, input)`)

`game/` の Pure TypeScript。React・DOM・時計・`Math.random` を読まない。

- **固定ステップ 1/120 秒**。UI は 1 フレームに最大 6 ステップ回す(Sky Fighter の盤面コンポーネント
  `SkyBoard.tsx` の `STEP_MS` / `MAX_STEPS_PER_FRAME` と同じ形。フレームの上限は UI の値で、
  ロジックが決めるのは刻みだけ)。
- **整数だけで計算する。**位置(x と r)は **1/120 px 単位の整数**(`SUB = 120`)、速度は px/s の整数。
  したがって 1 ステップの移動量は速度の数値そのもの(w px/s × 1/120 秒 = w/120 px = w 単位)。
  加速 360 px/s² は 1 ステップ +3、減速 720 px/s² は −6、横の追従 440 px/s は 1 ステップ最大
  440 単位。
- **数の規則**(V8 と JavaScriptCore で golden がずれないように):
  - `step`・生成・`planLane`・ボット・ライバル(`game/` のうち `input.ts` 以外)は**整数だけ**で計算し、
    `Math.sin` / `cos` / `pow` / `exp` / `sqrt` を使わない。割り算は**整数どうしの `Math.floor(a / b)`
    と `Math.ceil(a / b)` だけ**にする(整数 a, b で |a| < 2^52 なら結果は正確。負の数の floor は
    −∞ 方向)。この文書の `floor(a / b)` `ceil(a / b)` はすべてこの意味で、係数は ‰ などの整数で持つ
    (例: σ = 1100 ‰、`v_check = floor(9 × σ‰ × 420 / 10000)`)。
    ほかに素の `/` を使うのは、定数が割り切れることを保証している商(車線の幅 `304 × 120 / L`・車の半幅・
    三角数の `/ 2` など)だけで、それも `exactDiv(a, b)`(`game/arith.ts`)を通す。`exactDiv` は割り切れない
    ときに例外を投げるので、7 車線のような割り切れない定数を足すと最初の呼び出しで落ち、端数が状態へ静かに
    入ることは無い(Phase 2 のレビューで決めた)。
  - `game/input.ts`(指・キー・ボタンから `{ steerX, brake }` を作る写像、§3)だけは、CSS px の
    ポインタ座標・gain 1.2・盤の倍率という浮動小数を扱ってよい。ただし `step` へ渡す前に、`steerX` は
    `Math.round(x_px × 120)`(1/120 px 単位の整数)、`brake` は `Math.floor(… × 1000)`(0〜1000 の
    整数)にそろえる。物理が見るのは整数だけ。
  - この門は**閉じる側に倒す**(Phase 2 のレビューで決めた): 有限でない数は物理に届かない。レイアウト前の
    盤は倍率 0 で、指が動かなければ 0 / 0 = NaN になる — 倍率(0 以下・有限でない)か座標が使えない
    ドラッグは状態を変えず、ブレーキの源は有限でない引きを 0 と読み、`toStepInput` は有限でない目標を
    `null`(いまの目標を保つ)、有限でない `brake` を 0(全開)にする。`step` の側も、安全な整数でない
    `steerX` は `null` と同じに、安全な整数でない `brake` は 0 と読む(`game/input.test.ts`)。
  - 「浮動小数の割り算を使わない」ことを静的に見分ける検査は無い。確かめるのは、`Math.sin` などの不在の
    ソース検査と、状態・コース・ペース表のすべての数が整数であること、golden の一致(§16)。
- **入力**は 1 ステップに 1 つ: `{ steerX, brake }`。`steerX` は目標の横位置(1/120 px 単位の
  整数、または `null` = いまの目標を保つ)、`brake` は 0〜1000(‰。0 = 全開、1000 = 最大減速)。
  指・キー・ボタンからこの 2 つを作るのは入力の写像(§3)で、物理は入力の出所を知らない。
- 定数(すべて初期値。`game/constants.ts` に 1 か所だけ置く):

  | 名前                        | 値                    | 意味                                           |
  | --------------------------- | --------------------- | ---------------------------------------------- |
  | 全開の目標速度              | 420 px/s              | `brake` 0                                      |
  | 最大減速の目標速度          | 60 px/s               | `brake` 1000                                   |
  | 加速 / 減速                 | 360 / 720 px/s²       | 1 ステップ +3 / −6                             |
  | 横の追従                    | 440 px/s              | 目標の横位置へ、加速なしで最大この速さ         |
  | 路肩の頭打ち                | 231 px/s              | 全開の 55%                                     |
  | Bump の保持 / ロック / 点滅 | 60 / 36 / 96 ステップ | 0.5 / 0.3 / 0.8 秒(§4)                         |
  | ローリングスタートの速度    | 240 px/s              | §2                                             |
  | 交通の速度 vT               | 200 px/s              | 破線の流れと算術にだけ使う(コース座標では静止) |

**1 ステップの順序**(自車もライバルも同じ):

1. **操舵**: ロック中(§4)でなければ、目標の横位置を入力の `steerX` にする(`null` なら前の目標)。
   ロック中は入力を読まず、目標を動かさない。x は目標へ最大 440 単位動く。中心を [33, 327] px に
   クランプする。
2. **速度**: 保持中(§4)なら w = 0。そうでなければ目標速度 = `420 − floor(360 × brake / 1000)`。
   車体の一部でも路肩にあれば(左端 < 28 または右端 > 332)目標速度を 231 で頭打ちにする。w は
   目標へ +3 / −6 ずつ近づき、越えない。
3. **前進**: r += w(単位)。
4. **当たり**: 交通との重なりを解消し、必要なら Bump にする(§4)。
5. **タイマー**: 保持・ロック・点滅の残りを 1 ずつ減らす。
6. **ゴール**: 前端 r ≥ U になったステップでゴール(§2)。

- **タイマーの数え方**(Phase 2 で決めた): Bump が起きたステップではタイマーを減らさない。保持 60・
  ロック 36・点滅 96 は「Bump のステップの**後の** 60 / 36 / 96 ステップ」である(保持の間は w = 0、
  ロックの間は入力の `steerX` を読まない、点滅の間は新しい Bump を数えない)。ロックが 0 になった
  ステップを `lockReleased` として返す(§3 の基準の取り直しに使う)。
- **ロック中の目標**(Phase 2 で決めた): Bump のステップで、目標の横位置を**重なりを解消した後の x**
  にする。手順 1 の「ロック中は目標を動かさない」をそのまま読むと、車はロックの間も当たる前の目標へ
  動き続け、同じ交通へ横から押し付けられる。ロックは「横へ動かない」の意味に揃えた。

Bump の保持中を除けば w は 60 以上の目標速度へ向かう。したがって、交通の真後ろで操舵しないまま
当たり続ける場合(§4)を除けば、どのレースも有限の時間で終わる(算術では最長のコース 32,500 を
60 px/s で約 9 分)。

## 2. レースと着順

### 1 レース

- 1 レース = 長さ **U**(§7。16,000〜32,500 論理 px)のコースを、自分とライバル 3 台の 4 台で走る。
  算術では全開のまま走り切って 38〜77 秒。
- **スタートは 2 行の千鳥配置**(初期値。前端の r と中心の x):

  | 位置 | r   | x   | 車                   |
  | ---- | --- | --- | -------------------- |
  | 前列 | 0   | 104 | ライバル 3(最も遅い) |
  | 前列 | 0   | 208 | ライバル 2           |
  | 後列 | −90 | 152 | 自車                 |
  | 後列 | −90 | 256 | ライバル 1(最も速い) |

  車線の数によらず同じ配置。後ろから始めて前へ出る — 題のとおり、抜かなければ 1 位にならない。

- 交通(交通車と工事区間)は、コース上の [600, U − 400] の**内側だけ**に置く — スタートラインの先
  600 と、ゴールの手前 400 には、交通のどの部分も無い(§5)。

### 状態

状態は `ready` → `running` ⇄ `paused` → `finished`。**死は無い**(`over` という状態を持たない)。
どのレースも着順で終わる。

- **`ready`**: スタートの配置が全部見えていて、何も動かない(Bunny Hop §2 と同じ — 開いただけで
  1 回分を失わない)。盤の上には何も重ねない。状態は盤の外の 1 行(§11)に「タッチで出発」と出す。
- **`ready` → `running`**: 最初の入力で**全車がローリングスタート**する(全 4 台 w = 240 から。
  カウントダウンは無い)。入力は盤への押下(どの形でも)、Space / Enter(フォーカスがボタンに
  無いとき)、上部バーの ▶。◀ ▶ ▼ のボタンは `ready` では何もしない(誤って出発しない)。
  Drag の形で盤への押下から始めたときは、その指がそのまま操舵の指になる(§3)。Buttons の形では
  盤への押下は出発するだけで、操舵の指にはならない。
- **`running` → `paused`**: 上部バーの ❚❚、P / Esc、バックグラウンド、ウィンドウの blur(下)。
  止める時点で押しっぱなしの入力をすべて捨てる(指の記録・押しているキー・▼)。止めている間は
  ステップを進めず、ループも止める(§11)。回数・時間の制限も確認も無い。
- **`paused` → `running`**: **プレイヤーの操作だけ**で起きる — 盤への押下、Space / Enter、上部バーの
  ▶。Drag の形で盤への押下から再開したときは、その指が新しい操舵の指になり、基準をそこで取る。
  Buttons の形では、盤への押下は再開するだけ。
- **`running` → `finished`**: 自車の前端がゴールを越えたステップ。世界はそこで止まる(ライバルも
  それ以上進めない)。結果は約 1 秒後(§11)。`finished` の間、盤の操作キーは盤に届かない(§3)。
  止まったレースの中にいないライバルのゴールは、レースの外の『ライバルだけの走り』で得る(§6)。

### 着順

- 結果の**着順** = 1 + 自車より前のステップでゴールしたライバルの数。**同じステップは自分が前**。
- ライバル 3 台がすべてゴールしても、レースは自分がゴールするまで続く(4/4 は確定しているが、
  打ち切る理由が無い — 打ち切ればライバルのタイムで時間切れにすることになる)。猶予も打ち切りも無く、
  Bumps はゴールまで数える。計画の提案文「4 位が確定し、短い猶予の後に結果を出す」は採らない
  (§18)。
- 走っている間の着順(上部の `n/4`、§11)= 1 + 前端の r が自車より大きいライバルの数(ゴール済みの
  ライバルは前に数える。同じ r は自分が前)。
- **1 位でクリア**し、次の面が開く(§7)。2〜4 位はクリアではない。どちらも「終わり」であって失敗の
  演出は無い。

### 中断・バックグラウンド・Back

- **途中保存は作らない**(§9)。
- **バックグラウンド**(`visibilitychange` の hidden、native の pause)では、走っていれば `paused`
  にし、走った秒を計上する(§9)。**復帰しても再開しない** — 再開はタップか Space / Enter だけ
  (Snake §6 と同じ。Bunny Hop の盤面は画面が見えると再開するので、ここは意図的な差分 — §13)。
- **ウィンドウの blur**(PC で別のウィンドウへ移った・広告の枠を押した等)でも、走っていれば `paused`
  にする。focus が戻っても再開しない。止まっているレースには何もしない。アーケードの 4 本
  (Brick Breaker / Sky Fighter / Bubble Pop / Bunny Hop)は blur で止めないので、意図的な差分(§13)。
- **画面を離れればレースは終わる**(Sky Fighter §10 / Brick Breaker §10 と同じ)。出口は 2 つで、
  どちらも確認なし、走った秒は同じ 1 本の計上(§9)で数える。`played` はもう数えてある(§9)。
  開放の最前線は変わらない。
  - **ゲーム内の ←**: `goHome`(ゲームのホームへ)。Provider は残り、盤だけが外れる。`goHome` が
    計上の同期を呼んでからホームを出す。
  - **Web のブラウザの戻る**: シェルの履歴は `?game=overtake` の 1 項目なので(`app/webRoute.ts`)、
    `popstate` は**コレクションへ**戻り、Root ごとアンマウントされる(ゲームのホームには寄らない)。
    計上は Provider の `useOnUnmount(syncActiveGame)` が受け持つ。
- **ハードウェアの Back**(正式収録後の native。唯一の持ち主は GameContext): `running` 中の 1 回目は
  `paused` にするだけ、`paused` / `ready` / 結果の画面から押したらゲームのホームへ。横ドラッグが
  画面端からの戻るのスワイプと重なりうる(未確認、§16)ので、走っている最中の 1 回で盤を失わない
  ようにする。**Web ベータで効くのは上の「画面を離れれば」だけ**(ベータはアプリに出ない)。

### リトライと次の面

- **Retry**(上部バーの ↻ と結果カードの Retry。同じ関数): **確認なし・即時・無料・無制限**で、
  **同じ面・同じコース**の `ready` に戻す(交通もライバルも (seed, level) で決まるので、毎回同じ —
  §5)。走っていたなら走った秒を計上してから。↻ は `ready` の間は押せない(捨てるものが無い)。
- **Next**(1 位のときだけ、Lv100 を除く): 次の面の `ready`。
- **Levels**: 面の選択へ(§7)。

## 3. 操作(暫定 — Phase 0 未実施)

**この節は凍結していない。**計画は「操作の節は実機 2 台の Phase 0 を通してから書く」と決めていたが、
Phase 0 の実機の試行はまだ行っていない(2026-10-21)。ロジックと UI を待たせないために、Phase 0 の
**2 つの結果の両方**をここに書き、コードは両方を実装して、既定を **1 つの定数**
(`DRAG_MAPPING: 'A' | 'B'`、`game/constants.ts`)で切り替える。**暫定の既定はモード A**(計画の
既定)。Phase 0 が通らなければ定数を `'B'` にし、モード A のコードを消す(§18)。
**A が既定なのは registry が `channel: 'in-development'`(どのビルドにも出ない)の間だけ**: 計画は
2 軸 1 本指を「通ったら」既定にするので、Phase 0 の結果をこの節に記録するまで、registry を
`'web-beta'` にしない(統合の作業 — §18)。記録の前に `'web-beta'` へ上げるなら、`DRAG_MAPPING` を
`'B'` にして出す。

### 3 つの形

- **Drag**(既定。`ot.prefs` の `controls: 'drag'`): 盤のどこからでも 1 本指の相対ドラッグ。縦の
  扱いが Phase 0 で決まる 2 通り — **モード A**(2 軸 1 本指)と**モード B**(横ドラッグ + ▼ 長押し)。
  **プレイヤーが A と B を選ぶ設定は作らない**(計画: 通らなければ 2 軸式は選択肢にも残さない。
  通っても、選ばせるほど確かな形ではない)。
- **Buttons**(`controls: 'buttons'`): 画面下の **◀ ▶ ▼** を常設し、**ドラッグは無効**。名前の付いた
  ボタンなので支援技術からも押せる。**盤への押下は、`ready` からの出発と `paused` からの再開だけ**に
  使う(§2)。`running` 中の盤への押下・ドラッグ・第 2 指は**何も起こさない**(操舵の指も作らず、減速も
  しない — 手の置き場として盤に触れても車は動かない。減速は ▼ と ↓ / S だけ)。
- **キーボード**(どの形でも有効): 下の「キー」。

`ot.prefs` が覚えるのは Drag / Buttons の 2 値だけ(§9)。

### 横(Drag のモード A・B 共通)

- 押下(`pointerdown`)で、車の目標の横位置と指の位置を**基準**に取る。目標の横位置 =
  基準の車の x + (指の x − 基準の指の x) × **gain** ÷ 盤の倍率(CSS px → 論理 px)。つまり
  **画面の上で、車は指の gain 倍動く**。gain は **1.2**(試作の既定。1.0〜1.4 の範囲で Phase 0 で
  決める)。指が車を隠さないよう、盤のどこから触れてもよい(Sky Fighter §3 の相対式)。計算は
  `input.ts` の浮動小数で、物理へ渡す前に `steerX = Math.round(目標の x(論理 px) × 120)` の整数に
  する(§1)。
- 目標が走れる範囲の端を越えたら、基準をずらして端に貼り付ける(指を戻した瞬間に車が戻り始める —
  試作の `REANCHOR_AT_WALL`)。
- 車は物理の横の追従(440 px/s、§1)で目標へ動く。
- 指を離す(`pointerup`)と車はその位置に残り、減速は全開へ戻る。

### 縦 — モード A(2 軸 1 本指、暫定の既定)

- **速度は自動で全開。指を下へ引いた量に比例して減速し、上へ動かしても何も起きない片側式。**
  縦の基準からの下向きの距離 dy(CSS px)に対し
  `brake = Math.floor(clamp((dy − 不感帯) / (最大減速の距離 − 不感帯), 0, 1) × 1000)`(`input.ts` の
  浮動小数。結果は 0〜1000 の整数 — §1)。
  **不感帯 18 CSS px、最大減速の距離 90 CSS px**(CSS px の出発点。計画は論理 28 / 138px を倍率 0.65 で
  換算した値としたが、タッチ端末の倍率は算術では約 0.56 になる(§11)ので、倍率から導いた値とは
  扱わない — 親指の動かしやすさから Phase 0 が決める)。算術では dy = 54 で brake 500、dy ≥ 90 で 1000。
- **ラチェット式の基準**(試作で選んだ解釈。計画の「指が上へ動けばそこへ追従し、ゆっくり現在値へ
  戻る」を一意にしたもの):
  - 指が基準より**上**なら、基準は即座に指の位置へ移る。
  - 指が基準より**下**なら、基準は**戻り速度**(**20 CSS px/s**。試作の既定)で指の位置へ下がって
    いく。ゆっくりした親指のずれは基準が吸収して減速に積み上がらず、素早く引いた分は基準が追い
    つく前に効く(40〜60 秒の連続ドラッグで意図しない減速を積み重ねないための形)。
  - **帰結: 指で引いた減速は保持できず、戻り速度で全開へ戻る**(算術では 100 px 引くと 0.5 秒は
    最大減速のまま、約 4.1 秒で全開)。続けて減速するのは第 2 指か ▼。これでよいか(戻り速度 0 =
    基準は上へだけ動く、にするか)は**製品オーナーが Phase 0 の手触りで決める**(§18)。
- 写像は `game/input.ts` の純関数(経過時間を引数で受け取る)で、DOM を読まない。浮動小数を扱ってよい
  のはここだけ(§1)。

### 縦 — モード B(横ドラッグ + ▼ 長押し、Phase 0 が通らなかったときの既定)

- ドラッグの縦の成分は**完全に無視**する。減速は ▼ の長押し・第 2 指・↓ / S キーだけ。

### 最大減速

- **第 2 指**(Drag の形のみ。Buttons の形では盤への押下は何も起こさない — 上): 操舵の指とは別の
  `pointerId` が盤に押下している間は `brake = 1000`。操舵の指は奪わない(`pointerId` で別扱い)。
  第 2 指は離して置き直すまで操舵の指にならない。操舵の指が無いときの押下は、操舵の指になる。
- **▼ の長押し**: 押している間 `brake = 1000`。押した瞬間(`pointerdown`)から効き、しきい値の時間は
  無い。
- **↓ / S キー**: 押している間 `brake = 1000`。
- 複数が同時なら最大の値(1000)。

### ▼ を Drag の形でも出すか

**出す**(計画の推奨)。▼ は第 2 指の代替であり、名前付きのボタンは支援技術の経路でもある。
Drag の形では **CSS の `@media (any-pointer: coarse)`** のときだけ出し、JS で端末を判定しない(Bounce Up の
未決事項の推奨と同じ線。Bounce Up 側もまだ決めていない)。マウスとキーボードの環境では ↓ / S がある。
Buttons の形では ◀ ▶ ▼ を常に出す(プレイヤーが選んだ形なので、ポインタの種類で隠さない)。

### ◀ ▶(Buttons の形)

- 押している間、目標の横位置が 440 px/s で動く(車と同じ速さ)。離すと目標はそこで止まる。
  `pointercancel`・ボタンの外で離した指・`lostpointercapture` でも同じく止まる(下の「ポインタの契約」)。
- **速さは盤の時間で数える**(← → / A D も同じ): 走らせた 1 ステップごとに 440 / 120 px。壁時計の dt では
  ない — 遅い機械で 1 フレームのステップが上限の 6 に詰められても(§1)、目標だけが車の走った時間より先へ
  進んで、離した後も車が滑り続けることはない(Phase 3 のレビューで直した。`OvertakeRoot.test.tsx` の
  250 ms のフレーム)。

### キー

- **← → / A D** で操舵(押している間、目標の横位置が 440 px/s で動く)、**↓ / S** で最大減速、
  **Space / Enter** で出発・再開、**P / Esc** で一時停止。W A S D は印字ではなくキーの位置
  (`KeyboardEvent.code`)で読む(Snake §13)。押しっぱなしの repeat は出発・再開・一時停止の入力に
  しない。矢印と W A S D・Space は既定動作を止める(ページがスクロールしない)。
- **ボタンにフォーカスがあるときの Space / Enter はボタン自身に任せ**、二重に処理しない(Bunny Hop
  §3)。P / Esc はボタンの操作キーではないので、`finished` 以外では常にゲームが受ける(ゲーム画面に
  ダイアログは無い — §8 の ↻ は確認を出さない)。
- **`finished` では、キーのリスナーを外す** — ゴールのステップから、結果カードを出すまでの 900 ms の間
  (§11)も、結果カードが出ている間も。`useGameKeys` を使うなら、`enabled` 引数が状態 `finished` を読んで
  false になる(`modalIsolationWiring.test.ts` が、ダイアログの無い `useGameKeys` に求める形)。結果カード
  の上でキーに答えるのは、カードのボタン(Retry / Next / Levels / 共有)の自分の操作だけで、盤の操作キー
  (← → A D ↓ S Space Enter P Esc)は盤へ届かない。
- キーとドラッグを同時に使ったときは、後から動いたほうの目標が勝つ(キーで動いた後のドラッグは、
  次の `pointermove` で基準を取り直す)。

### ポインタの契約

[ARCHITECTURE.md](ARCHITECTURE.md)「指を取り上げられたときの契約」「押下の記録は誰のものか」のとおり。

- 盤は `pointerdown` / `pointermove` / `pointerup` / `pointercancel` を同じ要素で聞き、操舵の指に
  `setPointerCapture` を掛ける。記録はすべて `pointerId` を持ち、別の指の `pointerup` で操舵を
  終えない。盤は `touch-action: none`。マウスは左ボタンだけ(マウスに第 2 指は無い)。
- **`pointercancel`**: 操舵の指ならドラッグを終える(車はその位置に残り、減速は全開へ)。次の押下で
  基準を取り直す。第 2 指・▼ なら最大減速をやめる。◀ ▶ なら目標の移動をやめる(目標はそこで止まる)。
- **◀ ▶ ▼ のボタンは押下で `setPointerCapture` を掛け**、`pointerup`・`pointercancel`・
  `lostpointercapture` のどれでも押している状態を終える(指がボタンの外へ滑って離れても、押しっぱなしの
  ままにならない)。`paused`・`finished`・blur では、押している記録をすべて捨てる(§2)。
- **盤は `click` を聞かない**(出発・再開は押下で起きる)ので、ドラッグが残す click を使い切る必要は
  盤には無い。**◀ ▶ ▼ は押下で効く**ので、押下が残す click(`event.detail > 0`)は捨てる。キーボード
  や支援技術の起動(押下を伴わない `detail === 0` の click)は 1 回ぶんの操作にする: ◀ ▶ は目標を
  その面の 1 車線の幅だけ動かし、▼ は 0.5 秒(盤の時間、60 ステップ)の最大減速(初期値)。
- **押下の印の扱い**(ARCHITECTURE は「印は `detail > 0` のときだけ使う」とする。ここはそれを広げ、押下を
  聞いたボタンでは `detail === 0` の click も捨てる — タッチのタップの click を `detail === 0` で報告する
  エンジンがあるため。広げたぶんの穴を次の 2 つで塞ぐ — Phase 3 のレビューで直した):
  - **`pointercancel`、または `pointerup` の前に失った capture** は click を残さないので、印も取り消す。
    次のキーボード・支援技術の click(`detail === 0`)は、keydown が先に来なくても 1 回ぶんの操作になる。
    `pointerup` の後にブラウザが出す `lostpointercapture` は、押している状態がもう終わっているので印を
    残す(続く click を捨てる)。
  - **どのステップにも読まれなかった押下**(1 フレームの中で押して離した — 合成の、または支援技術の
    ダブルタップは `pointerdown`・`pointerup`・click を一度に出す)は何も動かしていないので、続く click
    (`detail` によらず)を捨てずに 1 回ぶんの操作にする。押下の後に 1 ステップでも走れば、その click は
    捨てる(人の指のタップは数フレームにまたがる)。
- `onPointerMove` と `setPointerCapture` を使うので、`pointerContractWiring.test.ts` の除外(Bunny Hop)
  には当たらない。

### Bump の後の操舵

Bump の操舵ロック(0.3 秒、§4)の間、入力の `steerX` は読まれない。**ロックが解けた最初のステップで、
操舵の指の基準を取り直す**(横は指のいまの位置といまの車の x、モード A の縦の基準も指のいまの位置)。
ロックの間に動いた指の量で車が跳ばないため。

### 採らなかった案

「上 = 加速・下 = 減速」の両方向(自動全開と冗長で、親指の弧が誤加速になる)、「指を離すと惰行」

射撃・ニトロのボタンは作らない — 入力は横の移動と「ゆるめる」の 2 つだけ。

## 4. 衝突(Bump)と路肩

- **Bump になるのは交通(交通車と工事区間)との接触だけ。**レーサー同士(自車とライバル、ライバル
  どうし)は**互いに当たらない** — 重なってもすり抜け、罰も押し合いも無い(§6)。路肩は Bump では
  ない(下)。
- **重なりの判定**: 車体の矩形(コース上の [r − 長さ, r] × [x − 幅/2, x + 幅/2])が交通の矩形と
  内部で重なる(辺が触れるだけは重ならない — 幅ちょうど 34 の空きは自車が通れる)。
- **重なりの解消**(毎ステップ、点滅中も必ず): 重なっている交通のうち**最初に見つかった 1 つ**(コース上の
  後端が最も前のもの)について、自車を動かす候補を **後ろ**(r を減らす)・**左**・**右**の 3 つ作る
  (**前へは決して動かさない** — 進行 r は増えない)。移動量の小さい順(同じなら 後ろ → 左 → 右)に試し、
  どの交通とも重ならず走れる範囲に収まる最初の候補を採る。どれも採れなければ後ろへ、いまの x で重なる
  すべての交通の後端より後ろまで下げる。
  繰り返しは 1 ステップ 8 回まで(仕事量の上限。§17)。
  計画の「最小移動ベクトル」は、前向きの移動を許すと進行 r が増えるので、前へ動かさない 3 方向に
  絞った(§18)。
  - **候補を作るのは最初に見つかった 1 台からだけ**(Phase 2 のレビューで決めた)。自車が 2 台に重なる
    場面(3・4 車線の壁は 1 車線に 2 台並ぶ)では、2 台目から作った左右の候補のほうが小さく空いていても
    試さず、1 台目の 3 つがどれも採れなければ後ろへ下げる。出荷のテストでは後ろへ下げる場面は 0 で
    (§16)、この違いが効く走りは観測していない。すべての重なりから候補を集めて小さい順に試す形は golden と
    `RIVAL_PACE` を動かしうるので、v1 はこの形で決めた。
  - **候補を採る条件が「どの交通とも重ならない」なので、1 回の候補の試しで必ず片付く**(採れば重なりは
    残らず、採れなければ後ろへ下げて終わる)。8 回の上限は届かない守りとして残した。計画と前の版の
    「上限に届く場面(9 回目が要る配置)をテストで手で組む」は、この規則の下では組めない — 代わりに、
    上限を 0 にして渡すと「後ろへ下げる」分岐だけが走ること、どの候補も採れない手組みの場面で後ろへ
    下げて r が増えないことをテストする(§16。Phase 2 で決めた)。
- **Bump**(点滅中でない自車が重なったとき): (a) 上のとおり重なりを解消、(b) **w = 0 にして
  0.5 秒(60 ステップ)保持**してから再加速、(c) **操舵を 0.3 秒(36 ステップ)ロック**(解除で
  指の基準を取り直す — §3)、(d) **0.8 秒(96 ステップ)点滅**。点滅は「当たらない状態」の表示で、
  Sky Fighter §4 の 1.2 秒・Bunny Hop §7 の 0.8 秒の無敵の点滅と同じ役割。**点滅中は新しい Bump は
  起きないが、位置の重なりは解消し続ける。**Bump は 1 エピソード(点滅が終わるまで)で 1 回だけ数える。
- **路肩**: 車体の一部でも路肩にある間だけ、目標速度が 231 px/s(全開の 55%)で頭打ちになる。
  Bump に数えず、点滅もロックも無い。
- **損の構造**: 「Bump 1 回の損」が「壁の前で減速する損」の**2 倍以上**であることをテストで
  固定する(§16。値は `step` で測る。測り方は、壁の組だけの合成コースで 1 つの出来事の損を測る)。
  **Phase 2 のテストで実測**: Lv11〜100 の全 90 面で、**その面で D_k が最も長い組**(各面 1 組 — §16)に
  ついて成り立ち、比の最小は **3.25(Lv92)**、最小の減速の
  損は最大でも **40 ステップ(0.333 秒)**、Bump の損は最小でも **129 ステップ(1.075 秒)**。
  算術では、全開から Bump して保持 0.5 秒 + 0 から 420 への再加速 1.17 秒で、全開のままに比べて約
  455 px、約 1.08 秒の損。計画の算術は「約 1.1 秒 対 約 0.5 秒」(選定時の最初の案は算術で 0.49 秒
  対 0.52 秒で、突っ込むほうが得だった — この構造をテストで固定するのはそのため)。
  - 減速の損が最も小さいのは、**必要な速度までの減速を 1 枚目の窓の中で済ませ、2 枚目の前の D_k の間
    だけその速度で走り、2 枚目の窓の中で再加速する**走りで、構造のテストはこの走りで測る(§16)。
    `planLane` も、間ごとの速度の上限の手前でだけ減速し、間を出たら戻す(§6「実装で決めた細部」)。ただし
    判断の遅れ・20 px/s の速度の格子・減速の余裕(5 ステップ)のぶん、ボット A の減速の損はこれより
    大きくなりうる(A の損は測っていない)。
  - 算術では(この走りの損。隙間を 1〜2 車線ずらす組): Lv11 の v_check = 283 px/s で約 0.12〜0.2 秒、
    Lv100 の 207 px/s で約 0.24〜0.32 秒(Bump の損の約 1/3〜1/9)。2 倍の門にはこの走りなら余裕がある。
    門が落ちる面が出たら、Bump の保持 0.5 秒か σ_gate の下限 0.55 を直す(§7。仕様の決定として扱う)。
- **ライフ・燃料・ニトロ・ピックアップ・ガレージ・コンティニューは作らない。**Bump は時間を失う
  だけで、レースは必ず続く。
- 交通の真後ろで操舵しないままでいると、点滅が終わるたびに当たり続ける(前へ進めない)。これは
  プレイヤーの選択で、時間で打ち切らない(§2。いつでも ↻ と一時停止がある)。

## 5. 交通の生成

### 決定性

- 交通は **(seed, level) から決定的**に生成する(`generateCourse`、`game/course.ts`)。seed は
  `TRAFFIC_SEED = 'overtake-v1'`(`game/constants.ts`)、乱数は
  ``createRng(`${TRAFFIC_SEED}:${level}`)``(xmur3 + mulberry32。`game/rng.ts`、他ゲームと同じものの写しで
  共有しない)。他ゲームの写しは [0, 1) の浮動小数を返すが、この写しは 32 ビットの整数を返し、範囲の整数を
  `floor(語 × n / 2^32)` で引く(§1 の数の規則。Phase 2 で決めた)。全プレイヤーが同じ面で同じコースを走り、**同じ面は毎回同じコース**(リトライは
  同一性 — Bubble Pop §7)。
- golden(`game/compatibility.test.ts`)が生成とライバルの走りを固定する(§16)。乱数・生成の順序・
  定数・幾何を変える改修は、事故ではなく決定でなければならない — 変えれば `RIVAL_PACE`(§6)も
  作り直しになる。

### 構成(探索は無く、必ず成功する)

コースは**行**の列でできている。行 k はコース上の位置 u_k(行の交通の**後端**)、行の**長さ** L_k
(行で最も長い車の長さ。58 / 70 / 104)、**正解の隙間**の車線 g_k を持つ。生成は**正解ルートを先に
彫ってから**残りを埋める構成法で、やり直しも探索も無い。

- **行の窓**: 自車の前端 r が (u_k, u_k + L_k + 58)(自車の長さ 58 を含む)にある間だけ、自車は行 k の
  交通と縦に重なりうる。行 k − 1 の窓の終わりから行 k の窓の始まりまでの距離を
  `D_k = u_k − (u_{k−1} + L_{k−1} + 58)` とする。窓の中の自車はその行の空いた区間の中にいなければ
  ならず、次の行の空きへ自由に動けるのは窓と窓の間(D_k)だけ — 窓の中でも、その区間の中なら動ける。
  (この節の距離の式は px で書く。実装は 1/120 px 単位の整数で、長さや 58 には 120 を掛ける — §1。)
- **壁の幾何**(ゲートの行): 壁は、隙間の車線 g 以外の各車線を、**3・4 車線は 1 車線に 2 台**(その車線の
  左端と右端にそれぞれ寄せる)、**5 車線は 1 台**(車線の中心)で塞ぐ。壁の車は 1 つの行で**車種を揃える**
  (長さが揃い、窓の中でも壁として振る舞う)。その結果、x ∈ [16, 344](路面と路肩)のうち交通に覆われない
  区間で**幅が 34 以上**(自車が入れる — §4)のものは**ちょうど 1 つ**で、それが**隙間の区間** G_k である。
  隣り合う交通の間と、交通と x = 16 / 344 の間の空きは、G_k のほかはどこも 34 未満(算術では、車線の中の
  空きが 3 車線で最大 33.3(sedan 2 台)・4 車線で最大 8、5 車線の隣り合う車の間が最大 26.8・路肩側が最大
  25.4)。車線の中心に 1 台ずつ置くだけでは 3・4 車線で壁にならない(§1)ので、この幾何が壁の定義である。
  - G_k は、3・4 車線の内側の車線なら車線の幅いっぱい、外側の車線なら路肩まで含む([16, 車線の右端] か
    [車線の左端, 344])。5 車線は隣の車どうしの間(外側は路肩まで)。
  - **隙間の帯** B_k は、G_k に自車が収まる**中心**の範囲([G_k の左 + 17, G_k の右 − 17])を、全開で走れる
    中心の範囲 R(420)(下)に切ったもの。算術では帯の幅は 3 車線で 67.3、4 車線で 42、5 車線で 53.6(sedan
    の隣)〜45.6(truck の隣)(5 車線の外側の車線は路肩の側が R で切れて 40.2〜36.2)。
  - 壁でない行(**普通の行**)でも、隙間の車線の中心は必ず空いた区間の中に入る(車線の幅 ≥ 60.8 は、隣の
    車線の車の半幅 + 17 = 最大 38 より大きい)。

1. **彫る**: 行ごとに、位置・種類・隙間・並びを決める(乱数を引く順序は `generateCourse` の中で固定する)。
   - 行 1 は u_1 = 600 + (乱数で 0〜120)、隙間の車線は乱数。以降は、前の行の隙間から −2〜+2 車線(面の
     語彙と重み — §7)で決める。**S 字**(連続する 2 行の隙間を左右に振る = 隙間の動きが逆向きの 2 行)と
     **工事**(外側の 1 車線を長さ 500 閉じる。閉じている間の行は隙間をその車線に置かない)は、隙間の
     決め方なので、この段で決める。
   - 行 1・2 は『ゆるめると楽な組』(下)。
   - 必須減速の組(Lv11 から)は、j 本目(j = 0..n_gate − 1)の目標位置を
     `T_j = 600 + (U − 1000 − GATE_TAIL) × (2j + 1) / (2 × n_gate)`(`GATE_TAIL = 700` — 組が置き切れる
     余裕。初期値)とし、**行 k を普通の間隔(σ(ℓ)、下)で置いたときの位置が T_j 以上になる最初の行 k(k ≥ 3)**
     を j 本目の組の 1 枚目にする。2 枚目は行 k + 1 で、σ_gate(ℓ) の間隔で置く。1 枚目の位置は普通の
     間隔で決まるので、行の種類が位置を決め、位置が種類を決める循環は無い。工事の閉鎖の間には組を置かず、
     閉鎖が終わった後の最初の行を使う。
   - 行を足すのは `u_k + L_k ≤ U − 400` が成り立つ間だけ(行の交通のどの部分もゴールの手前 400 に入らない)。
     工事は `開始 + 500 ≤ U − 400`、スタート側は `u_k ≥ 600`(工事は `開始 ≥ 600`)。組の 2 枚目まで入らない
     組は置かない(足りない本数は、下の n_gate のテストが落とす)。
2. **行の間隔**: 行 k は `u_k = u_{k−1} + Δ_k`、`Δ_k = (L_{k−1} + 58) × 120 + D_k` に置く(1/120 px 単位。
   行 1 は上のとおりで、Δ も D も σ も無い)。
   `D_k = ceil(420 × m_k × σ‰ / (440 × 1000))`(D_k と m_k は 1/120 px 単位の整数、σ‰ は整数 — §1)。
   括弧の前半は「前の行を抜け切るまで」(自車の長さ 58 を足す)、D_k は「全開 420 で D_k だけ進む間に、横
   440 px/s で動ける距離 `D_k × 440 / 420`」が m_k の σ 倍になる長さ。
   - **普通の行**: m_k = |g_k − g_{k−1}| × 車線の幅(車線中心の差。同じ車線なら 1 車線の幅)、
     σ = σ(ℓ)(2.2 → 1.25。§7)。隙間の車線の中心は前後の隙間の区間の中にあるので、帯どうしの距離は
     m_k を超えない。したがって **σ ≥ 1 なら全開で通れる**(十分条件)。σ < 1 でも通れないとは限らない
     (動く距離が帯の間の距離で済み、前の行が壁でなければ出発点もほぼ道幅の全体になる)。
   - **壁の組の 2 枚目**(下): m_k = 1 枚目の帯 B_{k−1} から 2 枚目の帯 B_k までの距離(帯が重なれば 0。
     算術では 3・4 車線で隣の車線へ 34px・2 車線先へ 135.3px(3 車線)/ 110px(4 車線)、5 車線は 2 車線先
     だけ(下)で 68〜76px)。1 枚目の窓の中では
     B_{k−1} の外へ、2 枚目の窓の中では B_k の外へ出られないので、**帯から帯へ m_k を D_k の間に動ききる**
     ことが必要になる。全開 420 の**連続の**到達量 `D_k × 440 / 420` は σ × m_k 以上、σ × m_k + 0.009px 未満
     (切り上げは 1/120 px 単位)。
   - **ステップの刻み**(Phase 2 のレビューで直した — 前の版は動きを連続とみなし、σ < 1 なら通れないとして
     いた): 実際の `step` は横へ動いてから前へ進み、交通との重なりは各ステップの終わりでだけ見る。1 枚目の
     窓の中で最後にステップが終わる位置から、2 枚目の窓の中で最初にステップが終わる位置までは、全開なら
     最大 **N = floor(D_k / 420) + 2** ステップ(D_k は 1/120 px 単位。窓の終わりの側と始まりの側でそれぞれ
     最大 1 ステップの端数)あり、その間に横へ N × 440 単位動ける — 連続の到達量より最大 2 × 440 単位
     (約 7.33px)多い。したがって全開で通れないための十分条件は **m_k > N × 440 単位**(おおよそ
     (1 − σ_gate) × m_k > 7.34px)で、σ < 1 だけでは足りない。出荷する組の 2 枚目は m_k ≥ 34px(3・4 車線)・
     68px(5 車線は 2 車線ずらし)、σ_gate ≤ 0.75 なので (1 − σ_gate) × m_k ≥ 8.5px で、この条件が成り立つ。
     **Phase 2 のテストで実測**(`game/course.test.ts`): 組の 2 枚目 1,493 行すべてで m_k > N × 440 が成り立ち、
     余裕 m_k − N × 440 は最小 4.67px(連続の余裕 m_k − D_k × 440 / 420 は最小 8.50px)。同じ 1,493 行を
     `step`(全開、1 枚目の帯の 2 枚目に近い端から 2 枚目の帯の近い端へ操舵、開始の位相 8 通り — 最悪の位相を
     含む)で走らせると、11,944 走すべてが 2 枚目の交通に重なった。この主張は壁の組の 2 枚目にだけ立つ。
3. **行の種類**:
   - **普通の行**: 上のとおり。テンプレートで埋める(下)。
   - **ゆるめると楽な組**(毎面): **1 行目と 2 行目を壁**にし(隙間をずらす — 壁の組のずらし方は下)、2 行目を
     σ = 1.10 にする。2 行目は『Δ を計算する最初の行』(1 行目は u_1 を乱数で置くので Δ も σ も無く、自車は x = 152 から
     690px 以上の助走で帯に着く)。2 行目は全開でも通れるが、必要な動きに対する余裕は 1 割だけで、減速すれば
     楽に通れる(Quick Rules 2 を最初の面で体験させる)。
   - **壁の組のずらし方**(Phase 2 で決めた): 3・4 車線は ±1 車線(重み 3)か ±2 車線(重み 1)、**5 車線は
     ±2 車線だけ**。5 車線で 1 車線だけずらすと、2 つの帯の間は 7.2〜15.2px しかなく(上の算術)、目で読める
     動きにならず、**ステップの刻みの 7.33px(上)より小さいか同程度なので、必須減速の行が全開で通れてしまう**
     (sedan の隙間 2 → 3、m = 7.2px、σ_gate 0.75: 連続の掃引は通れないとするが、`step` は重ならずに通る —
     `game/course.test.ts` の手組みで確かめる)うえ、ライバルとボットの 30 Hz の判断の遅れ(§6)が動き自体より
     大きく効く — 1 車線の版では、
     Lv51〜100 の多くの面で Rusher(減速しないボット)のタイムが較正の目標 T_1 を下回った(Phase 2 の開発中の
     試行では最大 3.4%、Lv82。いまのテストはこの版を走らせないので再現しない)。
   - **必須減速の組**(Lv11 から): 連続する 2 つの壁で、1 枚目は普通の間隔、2 枚目は隙間を上のとおりずらし
     σ = σ_gate(ℓ)(0.75 → 0.55)で置く。2 枚目 = **必須減速の行**で、上のとおり**全開では幾何的に通れない**。
     組の数は `n_gate(ℓ) = ceil(s‰(ℓ) × U(ℓ) / (420 × 500)) + 1` 以上(s(ℓ) は §6 のスラックの ‰、分母の
     500 は係数 0.5 の ‰。計画の式 `ceil(s × T / 0.6) + 1` の T = U / 420 秒)。
     - **係数は計画の 0.6 から 0.5 に下げた**(Phase 2 で決めた — 下の「構造の門」が許す初期値の調整)。0.6 でも
       Rusher の門は Lv21〜100 で成り立ったが、最速のライバルとの差は最小で 0.6%(Lv79)しかなく(Phase 2 の
       開発中の試行。0.6 の版はいまのテストでは走らない)、生成・`planLane`・較正のどれを触っても崩れうる幅
       だった。0.5 では最小 1.6%(Lv96、Phase 2 のテストで実測)。組は Lv11〜100 で 11〜24 組になる(0.6 では
       算術で 10〜20 組)。
     - 計画の式の T は「T_1(最速ライバルのタイム)」と読めるが、T_1 は生成したコースで較正して決まる
       (§6)ので、生成が T_1 を使うと循環する。**T は較正の前に決まる全開の理論時間 U(ℓ) / 420 とした**
       (§18)。T_1 ≥ (1 + s) × U / 420 なので、本数はこの読み方のほうが少なくなりうる。足りるかは Rusher の
       門(§6)が決める — 門が落ちたら本数(0.6)を直す。
     - **構造の門**: 全開で通れない行の本数(下)と Rusher の門(§6)の 2 つが「減速が必須」を構造として
       固定する。**どちらかを外す・弱める変更は、本数の調整ではなく仕様の変更として扱う**(計画のリスク欄。
       §13)。直してよいのは本数の係数(0.6)などの初期値で、門を弱めて通すことはしない。
4. **埋める**: 壁でない各行を、隙間の車線(とその帯)を空けたまま、テンプレートで埋める — **単発**(1 台)/
   **2 台**(隣り合う 2 車線)/ **トラック**(truck を 1 台含む)/ **工事**(1 で閉じた外側の車線)。交通車は
   車線の中心に置く。S 字は隙間の振り方(1)で、埋めるテンプレートではない。壁は上の幾何どおり(車種を
   揃える)。テンプレートの重みと初出は §7、表は `game/levels.ts` に 1 か所だけ置く。
   - 実装では 1 と 4 を 1 本の乱数の列で行ごとに続けて行う(行の長さ L_k は並びで決まり、次の行の位置に
     要るので、並びは彫る段で決まる — 1 の「並びを決める」)。乱数を引く順序は `generateCourse` の中で
     固定してあり、golden が固定する(§16)。
   - **工事は 1 つの行**(Phase 2 で決めた): 工事の行の交通は閉鎖 1 つだけで、その行の長さ L_k = 500。
     次の行は閉鎖の窓の後に置くので、**閉鎖の間にほかの行は無い**(1 の「閉じている間の行は隙間をその車線に
     置かない」は空に成り立つ)。工事の行の隙間は閉じない車線にある。閉鎖の間に行を重ねる形は、掃引の区間
     (§5「確かめる」)が行の窓と重なって複雑になるわりに得るものが少ないので v1 では作らない。
   - **トラック**の行は truck 1 台と、半分の確率でほかの空いた車線の sedan か van 1 台。
5. **確かめる**(`verifyRoute(course, v)`): 一定の速度 v で走り切れる横の経路があるかを、行ごとの掃引で
   判定する(連続の x・車幅・行の窓。`planLane` も同じ掃引を使う — §6)。整数の演算(§1)で、集合は区間の和:
   - **自車の中心の範囲 R(v)**: v > 231 なら [45, 315](車体のどこも路肩に出ない — 路肩では目標速度が
     231 で頭打ちになり、一定の v を保てない)、v ≤ 231 なら [33, 327]。
   - **行 k の空き F_k**: R(v) から、行 k の交通 o(中心 x_o・幅 w_o)ごとの開区間
     (x_o − w_o / 2 − 17, x_o + w_o / 2 + 17) を除いたもの(辺が触れるだけは重ならない)。
   - **窓の前**: A_k = (S_{k−1} を ±floor(440 × D_k / v) 広げたもの) ∩ F_k。S_0 は R(v) の全体(助走が
     690px 以上あり、横の全幅に届く)。**窓の中**: S_k = (A_k を ±floor(440 × (L_k + 58) / v) 広げたもの)
     ∩ (A_k が入っている F_k の連続した区間)。どれかの A_k が空なら通れない。
   - **出荷する全面で**(v は一定):
     - Lv1〜10 は v = 420(全開)で通れる。
     - Lv11 以降は `v_check = floor(9 × σ_gate‰(ℓ) × 420 / 10000)`(必須減速の行を 1 割の余裕で通れる
       一定速度。壁の組の 2 枚目の到達量は m_k の約 1.11 倍になる)で通れる。Lv1〜10 の v_check は 420。
     - 通れなければ、その面の交通を「**ルートのみ**」(壁の車だけを残し、普通の行のテンプレートの車を
       すべて捨てる — 普通の行は空になり、壁は隙間の帯だけを通す構造のまま)に落として出す — 不公平な
       盤を出さない。落とした数を `fallbackCount` として返し、**出荷 100 面で `fallbackCount === 0` を
       テストで assert する**。ルートのみでも通れないのは生成の誤りで、出荷せずテストが落ちる。

- **全開で通れない行**の定義(テストが数えるもの): 行 k で、v_check の掃引が求めた S_{k−1} を R(420) に
  切ったものから出発して、v = 420 で行 k の A_k を求めると空になる行。Lv11 以降、**この行の集合が必須減速の
  行の集合とちょうど一致する**ことと、その数が n_gate(ℓ) 以上であることをテストで固定する(普通の行・
  ゆるめると楽な組・組の 1 枚目はすべて全開で通れる)。この掃引は連続の動きなので、組の 2 枚目が全開で通れ
  ないことは、上の「ステップの刻み」の条件と `step` の走りでも別に確かめる。
- **仕事量**: 生成は行の数に比例する 1 本道で、行は 1 面 `GEN_ROW_LIMIT = 200` 行まで(初期値。超えたら
  そこで止めて「ルートのみ」に落とし、`fallbackCount` に数える — 正直に返す)。`verifyRoute` は
  行 × 区間(1 行の区間は車線数 + 1 以下)。
- **Phase 2 のテストで実測**(`game/course.test.ts`): 出荷 100 面すべてが §5 の速度で `verifyRoute` を通り、
  **`fallbackCount` は 100 面とも 0**。行の数は最大 **137**(上限 200)。全開で通れない行の集合は 100 面とも
  組の 2 枚目の集合と一致し、その数は Lv11〜100 で **11〜24**(各面の n_gate とちょうど同じ)。壁の行
  **3,186 行**すべてで、幅 34 以上の空きはちょうど 1 つで G_k と一致(3 / 4 / 5 車線 × 3 車種 × 全隙間の
  手組みでも同じ)。帯の幅は上の算術(67.33 / 42 / 53.6〜45.6、外側 40.2〜36.2)を再現した。すべての交通が
  [600, U − 400] の内側、すべての数が整数。ゆるめると楽な組は 100 面とも全開で通れ、到達量は m 以上
  1.10 m + 0.009px 未満。壁の組 1,593 組(ゆるめると楽な組 100・必須減速の組 1,493)のずらしは 3・4 車線で
  ±1 か ±2、5 車線で ±2 ちょうど。必須減速の組の j 本目の 1 枚目は、普通の位置が T_j 以上になる最初の行
  (k ≥ 3)。u_1 は 100 面で 601〜717px(600〜720 の内側)。S 字の振り戻し(4 回に 1 回、1 車線が重み 3・
  2 車線が重み 1、Lv11 から)は乱数を手で与えた引き方と 40,000 回の頻度で確かめた。

## 6. ライバルとペース

### ライバルの走り

- 3 台は**参照ボットと同じ純関数のプランナー `planLane`**(`game/planner.ts`)で走る — ライバルを
  書くことが、そのまま CI での検証になる。
- `planLane(course, 車の状態, 上限速度)` → `{ steerX, brake }`。前方 480 px の視界窓の各行(行の窓は §5)
  について、通れる横区間を DP でつなぎ、**横移動が最小の経路**を選ぶ。速度の候補 v は、上限速度から
  20 px/s 刻みで下げていく。候補ごとに、視界窓を `verifyRoute`(§5)と同じ掃引 — 同じ R(v)・窓の前後の
  広げ方 — で通れるかを見るが、**視界窓の全体を v で走るのではない**: 間ごとの速度の上限(下の「実装で
  決めた細部」)が v より低い間だけ、その上限で通る。採るのは、通れて、しかもその間の手前で上限まで
  減速し切れる最初の候補。v > 231 の候補は路肩に出ない経路だけを使う。
  判断は 30 Hz(4 ステップに 1 回)、間のステップは前の判断を保つ。
- **実装で決めた細部**(Phase 2 で決めた。どれも「同じ掃引」を、判断を 4 ステップ保つ車で正しく使うため):
  - **判断の遅れ**: 判断を 4 ステップ保つので、窓が終わって横へ動けるようになってから次の判断まで最大
    3 ステップ動けない。掃引は、窓の後の間(制約がゆるむ所)の横の到達量からこの 3 ステップ分
    (`DECISION_LAG`、3 × 440 単位)を引く。`verifyRoute` は遅れを引かない(コースの性質の判定なので)。
  - **間の速度の上限**: 組の 2 枚目の前の間のように、動く距離が決まっている間ごとに「遅れを引いても
    動き切れる最も速い一定速度」(前の行の空きから次の行の空きまでの距離で決まる)を求めておき、その間を
    その速度以下で通る。候補の速度は、その間の手前で上限まで減速し切れる(減速の距離 + **5 ステップ分**の
    余裕 — 判断を保つ 4 ステップ + 1 ステップ、`(DECISION_INTERVAL + 1) × 速さ`)ときだけ採る。これで
    「視界窓の全体を一定の速度」ではなく、**必要な間の手前でだけ減速し、間を出たら戻す**走りになる(§4 の
    「最小の減速」に近い。視界窓の全体を一定にすると、組が見えた瞬間から 480 px を
    遅く走り、減速の損が Bump の損に近づいた — Phase 2 の開発中の試行)。減速中の区間は、その区間に入る
    ときの速さ(−6 / ステップの減速で計算)で到達量を数える。
  - **操舵**: 前向きの掃引(届く位置)と後ろ向きの掃引(視界の終わりまで通れる位置)の共通部分を各区間の
    境目で求め、車がいる位置を含まない最初の境目で、車に最も近い点を目指す(最小の横移動を、なるべく早く
    始める)。目指す点はいまの区間の終わりの集合へ写す。ただし、いまの区間が判断を保つ間に終わる窓なら、
    次の区間の終わりへ写す。最後に、判断を保つ 4 ステップを物理どおりに先読みし、交通に入る手前で止まる
    ように目標を詰める。
  - **通れる候補が無いとき**: 60 px/s(brake 1000)で、次の行の空きの最も近い点を目指す(`feasible: false`
    を返す)。**Phase 2 のテストで実測**: 出荷 100 面のボット A(100 走、計 169,727 判断)でも、『ライバルだけの
    走り』(300 走、計 613,026 判断)でも一度も起きない(どちらも 0 を assert する)。
  - **仕事量の上限**(Phase 2 のレビューで決めた): 構造の上限(§17)とは別に、候補を試す前ごとに仕事量を
    `PLAN_WORK_LIMIT = 4,000`(区間の操作。初期値)と比べ、届いていればそこで止めて、上と同じ 60 px/s の
    判断を `feasible: false`・`capped: true` で返す(GAME_LIFECYCLE.md「CPU 探索」の「ノードの上限で止め、
    正直に返す」と同じ形)。構造の上限 3,458 より大きく、実測の最大(ボット A 93・ライバル 79)から遠いので、
    出荷の面では届かない守りである。届いたときの返し方は上限を小さく渡すテストで確かめる。
- **ライバルはプレイヤーに一切依存しない。**ライバルの入力は (course, 自分の状態, 自分の上限速度)
  だけから決まり、自車の位置・速度・着順・Bump・その面の挑戦回数のどれも読まない(関数の引数に
  無い)。ライバルどうしも互いを読まない。したがってライバル 3 台の軌跡は (seed, level) だけで
  決まり、毎回同じ。
  - 計画は「レーサー同士の接触は罰なし」に加えて「ライバルが横へ譲って解消」「自分の車線変更が
    届く範囲にいる間はその車線へ変えない」と書いていた。譲る・割り込まない動きはプレイヤーの
    位置に依存し、「ペースはプレイヤーの状態に依存しない(ラバーバンドなし)」を構造としては
    保てない(譲ったライバルのタイムが変わりうる)。**依存しないほうを採り、レーサー同士は
    すり抜けにした**(§4、§18 — 計画からの逸脱、暫定)。重なったときの描き方は §11。
- **ライバルだけの走り**(`game/rivals.ts` の `simulateRivals(course, level)`): 自車を入れず、自車の
  ゴールでも止めず、3 台がそれぞれ自分のゴールに着くまで(または `MAX_RACE_STEPS`)走らせ、毎ステップの
  状態と各台のゴールのステップを返す。ライバルは自車に依存しない(上)ので、どのレースのライバルの軌跡
  も、そのレースが止まるまでの分はこの走りの先頭と一致する。レースは自車のゴール(§2)やボットの打ち切り
  (下)で止まり、ライバル 3 台が揃ってゴールするとは限らない。そこで**ライバルのゴールのステップを得る・
  固定する・比べるのは、すべてこの走りで行う**(§16 の golden とラバーバンドなしのテスト、ペースの較正)。
- ライバルは交通に当たらない(全 100 面 × 3 台で Bump 0 をテストで固定する)。物理は自車と同じ
  `step` で、当たれば同じ Bump になる — 当たらないのは `planLane` の性質であって特別扱いではない。
  **Phase 2 のテストで実測**: 300 走すべてで Bump 0。判断は 300 走で計 613,026 回、1 回の仕事量の最大は 79。
- **ループの中で `planLane` を走らせる**(GAME_LIFECYCLE.md「CPU 探索」の例外): ライバル 3 台の判断
  (30 Hz)は RAF の中で `step` と一緒に走る。「探索は明示的な操作のときだけ、ポーリングも先読みも
  しない」の例外で、理由と仕事量の上限は次のとおり。(1) `planLane` は木の探索ではなく有界の DP で、
  1 回の仕事量は構造で決まり(視界窓の行 × 速度の候補 19 × 区間、§17)、そのうえ `PLAN_WORK_LIMIT` で
  止まって正直に返す(上)。(2) 1 フレームの 6 ステップに
  入る判断は 1 台あたり最大 2 回、3 台で最大 6 回。(3) ライバルの判断はプレイヤーの操作への応答ではなく
  世界の進行で、`running` の間だけ走り、停止・バックグラウンド・アンマウントで止まる(§11)。(4) ライバルは
  自車に依存しないので、`ready` → `running` で 3 台の軌跡を一度に計算して再生する形にしても結果は同じ
  だが、その 1 回で最長の面は 3 台ぶんの `planLane` が約 8,000 回(算術: 各台 約 85〜95 秒 × 30 Hz)
  最初のタッチに載り、低スペック機で最初の入力が固まる — 採らない。GAME_LIFECYCLE.md は「この原則への例外を
  決めるのは製品オーナー」とするので、**この例外は製品オーナーの確認待ち**(暫定。§18)。確認が得られたら、
  統合が GAME_LIFECYCLE.md「CPU 探索」に 1 行足す(共有文書なので、この作業は触れない)。

### ペース(`RIVAL_PACE`、ラバーバンドなし)

- ライバル i(1 = 最も速い)の**上限速度**は、凍結表 **`RIVAL_PACE[level − 1] = [c_1, c_2, c_3]`**
  (px/s の整数、`game/rivalPace.ts`)を平均とし、コース位置に対する**整数の三角波(±6%)**で揺れる:
  - 周期 P = 4,000 px、位相 φ_i = (i − 1) × 1,333 px(初期値)。r_px = `Math.floor(r / 120)`(r は
    1/120 px 単位。スタートの r = −90 px は負なので、負の数も −∞ 方向に切り捨てる)、
    **q = ((r_px + φ_i) % P + P) % P**(JavaScript の `%` は負の数に負を返すので、非負の剰余にする。
    r_px + φ_i < 0 でも q は 0〜P − 1)、t = |2q − P|(0〜P)、
    `上限_i(r) = min(420, c_i + floor(c_i × 6 × (2t − P) / (100 × P)))`(floor は −∞ 方向)。
  - 整数の演算だけで、`Math.sin` を使わない。上限は **`c_i − ceil(6 × c_i / 100)` 以上、
    `c_i + floor(6 × c_i / 100)` 以下**(さらに 60〜420 で切る)。floor が −∞ 方向なので、6 × c_i / 100 が
    整数でないとき、**下側は 0.94 × c_i を 1 px/s 未満だけ下回る**(凍結した表の平均で最大 0.98 px/s。例:
    c = 335 の谷は 314 で、0.94 × 335 = 314.9)。上側は 1.06 × c_i を超えない。この整数の範囲と、谷と山で
    範囲の端に届くことを、r = −90 px を含めてテストで固定する(§16)。
  - **下限 60**(Phase 2 で決めた): 上限は 60 px/s を下回らない(ブレーキで出せる最も遅い目標速度が 60 なので、
    それより低い上限は守れない)。c_i = 60 のときだけ効き、表に 60 の値は無い。
- **ペースはプレイヤーの位置・順位・連敗に依存しない**(ラバーバンドなし)。上限速度は (level, i, r_i)
  だけの関数で、上の「プレイヤーに一切依存しない」と合わせてテストで固定する(§16)。
- **目標のタイム**: 最速のライバルのゴール T_1(ステップ)、2 台目 T_1 × 1.04、3 台目 T_1 × 1.09
  (初期値)。T_1 は**較正**で決める:
  - **較正のボット B_ref**: 下の B の族の中級(反応 250 ms・横ノイズ ±6 px・視界 0.9 秒、ノイズの
    seed は `overtake-calibrate`)。ライバルを走らせない単独走(ライバルは幽霊)で、自車の位置から
    ゴールまでのステップ S_B(ℓ) を測る。
  - **T_1 は何から測った値か**(Phase 2 のレビューで書き足した): B_ref は 250 ms の遅れを持つが、自分の
    待っている入力と動かない交通から、遅れの後の自分の位置を正確に予測して計画する(下「遅れとの付き合い
    方」)ので、遅れはほとんど損にならない。**Phase 2 のテストで実測**(`game/bots.test.ts`): 100 面で
    S_B はボット A(遅れ 0 の完全な走り)より**最大 2.21% 遅いだけ**(Lv74。最小は −0.13% で、A より速い面も
    ある)。したがって T_1 = ceil(S_B × (1 + s)) は「250 ms の人の走り」に対する余裕ではなく、**ほぼ完全な
    走りに対する余裕**で、Lv81〜100 では最速のライバルのゴールは A より **8.2%(Lv89)〜11.7%** 遅いだけ
    (この範囲の s(ℓ) は 8.0〜11.3% — 算術)。人がその面で 1 位になるには、反応 0 の完全な走りから 8〜12%
    以内でゴールしなければならない。それが人にとってどれだけ難しいかは測っていない(§16「確かめないこと」)。B_ref に不完全な予測を
    入れれば T_1 は上がるが、表の作り直しと Rusher の門(最速のライバルとの差は最小 1.6%)の見直しが要る —
    v1 では変えない(§18「1 位でクリア」の材料)。
  - T_1(ℓ) = ceil(S_B(ℓ) × (1000 + s‰(ℓ)) / 1000)。T_2・T_3 は T_1 × 1040 / 1000・× 1090 / 1000 を最も
    近い整数に丸める(`floor((T_1 × 1040 + 500) / 1000)`。Phase 2 で決めた)。**スラック s(ℓ)** は 0.25 から下限 0.08 へ下がる
    10 面ごとののこぎり波(§7 の表。新しい語彙が入るブロックの頭は +0.04 緩める)。
  - 各ライバルの c_i は、そのライバルのスタート位置から `planLane` で(ライバルだけの走りとして)走らせた
    ゴールのステップが目標(T_1・T_1 × 1.04・T_1 × 1.09)に最も近くなる整数にする。**探索は全探索**:
    c = 60..420 の 361 値をすべて走らせ、目標との差が最小のものを採る。**同点は大きい c**。ゴールの
    ステップは c に対して単調とは限らない(`planLane` が選ぶ速度の格子が c で動く)ので、二分法は前提に
    しない — 近道を使うなら、全探索と同じ表を返すことを数面で確かめる。全 100 面 × 3 台で単独走が約
    108,000 回(算術)になるので、較正は開発時にだけ走らせる(CI の対象外、下)。
    - **近道**(Phase 2 で決めた): 二分法で「目標に間に合う最も遅い c」を探し、その ±8 を走らせ、走らせた
      すべての c のうち目標に最も近いもの(同点は大きい c)を採る。`OT_REGEN_PACE=1` の走りで、Lv1・50・100
      の 3 台すべてで全探索と同じ c を返した(Phase 2 のテストで実測)。ふだんのテストも Lv1 の 1 台目で
      近道と全探索の一致を確かめる(近道 20 走、全探索 361 走)。表全体の再生成は単独走 **6,249 回**(B_ref の
      100 回を含む)で、開発機で約 56〜58 秒(`OT_REGEN_PACE=1` の走りが出力。2026-10-21 の再実行で 6,249 回・
      55.8 秒、表は一致)。3 台を探した後に
      **c_2 = min(c_2, c_1)、c_3 = min(c_3, c_2)** で順序をそろえる(そろえた後のタイム比は下のテストが見る)。
- **表は凍結する。**較正は開発時にだけ走らせ、結果の表をソースに書いて固定する。実行時は表を読む
  だけで、プレイ中に較正しない。表の作り直しは golden の更新と同じく**意図した決定**として扱い、
  差分をコミットに残す。
  - 較正の置き場所: 計画の推奨は `apps/simple-games/scripts/` だが、この作業が触れられるのは
    `src/games/overtake/` だけなので、**較正の関数は `game/calibrate.ts`(純関数)に置き、表の
    書き出しは環境変数で有効にするテスト(`OT_REGEN_PACE=1` を付けて `game/rivalPace.test.ts` を
    走らせると新しい表を出力する)にする**(暫定 — §18。統合で `scripts/` へ移してもよい)。ふだんの
    テストは表の形・順序・ハッシュと、表で走らせた結果を確かめる。**再生成は CI に入れない**(通常の
    `pnpm test` では走らない)。表・較正の定数・生成・`planLane` のどれかを変える変更のときだけ
    `OT_REGEN_PACE=1` で走らせ、出力が新しい表と一致することを確かめて、その差分と一緒にコミットする。
- **クリアの実体は最速ライバル 1 台のタイム**である。2 台目・3 台目は着順の 2〜4 を分けるだけで、
  1 位かどうかには効かない(§13 にそう書く)。
- **Phase 2 のテストで実測**(凍結した表で『ライバルだけの走り』): 100 面とも T_1 < T_2 < T_3、T_2 / T_1 は
  **1.0373〜1.0424**、T_3 / T_1 は **1.0870〜1.0924**(どちらも ±1% の内側)。最も遅いのは Lv100 の 3 台目で
  11,859 ステップ(98.8 秒)。表の c_1 は 293〜383、c_2 は 280〜364、c_3 は 264〜345 px/s
  (`game/rivalPace.test.ts` が表から出力)。

### 参照ボット(テストと較正だけ。アプリでは走らない)

ボットは `game/bots.ts` に置き、UI からは import しない。すべて (seed, level, ボットのパラメータ) で
決定的で、判断は 30 Hz、**着順が確定した時点で打ち切る**(自分がゴールした、または最速のライバルが
先にゴールして 1 位の可能性が無くなった)。打ち切らずに 1 レースが
`MAX_RACE_STEPS = 72,000`(600 秒ぶん。初期値)に届いたら「未完」として返す(仕事量の上限。§17)。
打ち切ったレースにはライバル 3 台のゴールが揃わないので、ライバルのゴールのステップは『ライバルだけの
走り』から取る(上)。

| ボット  | 操舵                                            | 速度                     | 門(§16)                                                                      |
| ------- | ----------------------------------------------- | ------------------------ | ---------------------------------------------------------------------------- |
| A(完全) | `planLane`、遅延 0                              | `planLane`(上限 420)     | 全 100 面で Bump 0 の 1 位                                                   |
| B(族)   | `planLane` を反応の遅延・横ノイズ・視界を付けて | `planLane`(上限 420)     | スキルラダー(下。飽和した煙テスト)                                           |
| Rusher  | `planLane`                                      | 常に全開(brake 0)        | **Lv21〜100 で 1 位になれない**                                              |
| Crawler | `planLane`                                      | 常に最大減速(brake 1000) | 全 100 面で 1 位になれない(煙テスト)                                         |
| Idler   | 操舵しない(スタートの x のまま)                 | 常に全開                 | 全 100 面で 1 位になれない(煙テスト。ライバルを幽霊にした単独走では「未完」) |

- **B の族**(初期値): 上級 = 反応 150 ms・横ノイズ ±6 px・視界 0.9 秒、中級 = 250 ms・±6 px・0.9 秒
  (= B_ref)、新人 = 400 ms・±12 px・0.7 秒。
  - **反応の遅れ**はステップで持つ(120 Hz で 18 / 30 / 48 ステップ)。判断は 4 ステップごと(ステップ番号が
    4 の倍数のとき)に作り、**ステップ t に物理へ渡す入力は、t − 遅れ 以前で最も新しい判断**とする(最初の
    判断が効くまでは `{ steerX: null, brake: 0 }`)。遅れが 4 の倍数でない 18・30 も同じ規則で決まる
    (4.5 / 7.5 判断ぶんの遅れ)。テストは 3 段それぞれで、遅れの前の入力がすべて `{ steerX: null, brake: 0 }`
    であることと、入力が変わるのは t − 遅れ が判断のステップ(4 の倍数)のときだけであることを確かめる。
  - **ノイズ**は判断ごとに、目標の横位置へ一様な整数(±6 px または ±12 px を 1/120 px 単位にした範囲)を
    足す。seed はノイズの seed(B_ref は `overtake-calibrate`、ラダーのテストは 20 本)から決定的に引く。
  - **視界**は `planLane` の窓を、**全開の速度 420 で秒数ぶんに進む距離**(0.9 秒 = 378 px、0.7 秒 =
    294 px)に縮める。自車のいまの速さにはよらない(Bump の保持中に窓が 0 に縮み、S_B と T_1 を水増し
    しないため)。
  - **遅れとの付き合い方**(Phase 2 で決めた): 判断は、それが効くとき(遅れの後)の自分の位置から計画する。
    ボットは自分の待っている入力を知っており、交通は動かないので、この予測は正確である(実際の車より
    遅れの分だけ先の状態を 1 ステップずつ進めて持つ。**Phase 2 のテストで実測**: 4 面 × 3 段の 1,500 ステップ
    で、予測した状態と遅れの後の実際の状態 17,616 組が完全に一致)。この正確さのせいで B の族は A にほぼ
    等しい(上「T_1 は何から測った値か」)。視界はいまの位置から測るので、**遅れの分だけ先が
    見えなくなる**(中級で 0.9 秒の視界から約 105 px、新人で 0.7 秒から約 168 px)。遅れをそのまま(いまの
    位置から計画して遅れて効かせる)にすると、組の 2 枚目の前の間(約 24 px)で動き出しが必ず間に合わず、
    B_ref が組のたびに当たって S_B と T_1 が膨らみ、Rusher が最速のライバルに勝つ(Phase 2 の開発中の試行。
    いまの速さと目標を保つと仮定する粗い予測でも同じで、B_ref は 1 走で 40 回前後当たった)。
  - **ノイズの入れ方**(Phase 2 で決めた): ノイズは目指す点に足し、その後で「視界の終わりまで通れる位置」へ
    写す(§6 の操舵)。写した後に足すと、壁の帯の端に寄せた車を ±6 px 押し出して組のたびに当たり(中級で
    1 走 9〜16 回 — Phase 2 の開発中の試行)、上と同じ理由で Rusher の門が崩れた。
- **スキルラダーの門**: ノイズの seed を 20 本変えて各面を走らせ、10 面のブロックごとの勝率(1 位の
  割合)が上級 ≥ 中級 ≥ 新人であること、**新人が Lv1〜10 で 90% 以上**(200 走中 180 以上)勝つこと
  (しきい値は初期値)。
  - **Phase 2 のテストで実測**: 10 ブロックすべてで、上級・中級・新人とも **200 走中 200 勝**。門は
    成り立つが、**ラダーは技量の差を何も分けていない**(同点の単調)。上の遅れの付き合い方とノイズの入れ方で
    B の族が A にほぼ等しくなり、しかもスラック(8〜27%)が大きいため。人の難しさについては何も言わない
    (§16「確かめないこと」)。差の出るボットの族(視界をさらに縮める・予測を不完全にする)を作るなら、
    B_ref を変えずに族の下側だけを弱くする(B_ref を弱くすると T_1 が上がり Rusher の門が崩れる)。
    v1 では作らない(§18)。**この門は飽和しており、技量への感度の証拠にはならない** — テストの名前も
    「smoke」とし、ボットの配線が壊れていないことの煙テストとして扱う(§16)。
- 門の外では勝ってもよい — Rusher は Lv1〜20(境界は初期値)。Lv11〜20 には必須減速の行があるが、
  Rusher の門は Lv21 から(計画のとおり)。
- **Phase 2 のテストで実測**(`game/bots.test.ts`。ライバルのゴールは『ライバルだけの走り』から):
  - **A**: 100 面すべてで Bump 0 の 1 位。最速のライバルへの差は最小でも **7.6%(Lv89)**。
  - **Rusher**: **Lv21〜100 のどの面でも 1 位になれない**(打ち切らずに走らせてゴールまで測り、最速の
    ライバルより最小でも **1.6% 遅い**(Lv96))。Lv11〜20 でも 1 位になれず、Lv1〜10 では 10 面とも 1 位
    (門の外。組が無いので減速しなくてよい)。
  - **Crawler と Idler**: 100 面すべてで 1 位になれない。Idler は通常のレースでは最速のライバルのゴールで
    打ち切られ(`decided`)、ライバルを幽霊にした Lv1 の単独走では `MAX_RACE_STEPS`(72,000)に届いて
    `unfinished` を返す(その間の Bump 740 回)。
- **Crawler と Idler の門は、この文書の数では必ず成り立つ**(算術)。Crawler は目標速度の床 60 px/s で走り、
  Lv1 でも 16,000 / 60 = 約 267 秒かかる(最速のライバルの T_1 は 1.25 × 38.1 秒以上 = 約 48 秒以上)。
  Idler は x = 152(自車の幅 34 で [135, 169])から動かず、車線 1 の交通車(3 車線で [163, 197]、4 車線で
  [125, 159]、5 車線で車線 1 と 2)と重なるので、点滅が終わるたびに当たり続ける(§4)。計画の境界(Crawler
  Lv5、Idler Lv10)は低い面なら勝てるかもしれないという見込みだったが、この規則の数では低い面でも
  勝てない — **境界は Lv1 に下げ、この 2 つの門は『ボットのつなぎが壊れていない』ことの煙テストとして残す**
  (勝ちを返さない。Idler は通常のレースでは最速のライバルのゴールで打ち切られ、ライバルを幽霊にした単独走
  では `MAX_RACE_STEPS` に届いて「未完」を返す)。意味のある境界を引きたければ、
  ボットを「混んだ所でだけ最大減速する」「当たりそうなときだけ避ける」へ作り直す必要があるが、v1 では
  作らない(§18)。

## 7. レベル

- **100 面のはしご、10 ブロック。**新しいルールは足さず、描かれる語彙(車種・並び・車線の数)だけが
  増える。**1 位でクリア**し、次の面が開く。**既クリアはいつでも再走**でき、**開放の最前線は
  戻らない**。Lv100 をクリアすると最前線は 101 に進み、「全部クリアした」を意味する(Brick Breaker §7・
  Bubble Pop と同じ持ち方)。ホームの Levels チップは `n/100`(n = min(最前線 − 1, 100))。ホームの
  Play とレベル選択は `min(最前線, 100)` を指し続ける(§11)。
  レベル番号は 1..100 にクランプし、外挿しない。
- **10 の倍数は決勝**: コースが 1.25 倍(`floor(U × 5 / 4)`)になるだけ。ペースの形・ルール・画面の
  印は変えない(計画の「1 台が後半に伸びる追い込み型」は v1 では作らない — §18)。
- **難易度選択・Free Run・タイムアタック・デイリーは作らない。**
- レバー(すべて初期値。`game/levels.ts` に 1 か所だけ置く。k = ((ℓ − 1) mod 10) + 1 はブロックの中の
  番号、整数は ‰ や px):

  | レバー                           | 式                                                                                |
  | -------------------------------- | --------------------------------------------------------------------------------- |
  | 車線の数 L(ℓ)                    | Lv1〜20: 3、Lv21〜50: 4、Lv51〜100: 5(10 面のブロックの境界でだけ変える)          |
  | コース長の基準 U₀(ℓ)             | `16000 + floor(10000 × (ℓ − 1) / 99)`(16,000 → 26,000、狭義単調で飽和しない)      |
  | コース長 U(ℓ)                    | 10 の倍数は `floor(U₀ × 5 / 4)`、ほかは U₀                                        |
  | 普通の行の σ(ℓ)                  | `2200 − floor(950 × (ℓ − 1) / 99)` ‰(2.2 → 1.25)                                  |
  | ゆるめると楽な組(2 枚目)の σ     | 1100 ‰(全面)                                                                      |
  | 必須減速の組(2 枚目)の σ_gate(ℓ) | Lv11〜: `750 − floor(200 × (ℓ − 11) / 89)` ‰(0.75 → 0.55)。Lv1〜10 は無し         |
  | スラック s(ℓ)                    | `max(80, 250 − floor(170 × (ℓ − 1) / 99) − floor(20 × (k − 1) / 9) + 頭の緩め)` ‰ |
  | 頭の緩め                         | 新しい語彙が入るブロックの頭(Lv11・21・31・51)だけ +40 ‰                          |
  | 必須減速の組の数 n_gate(ℓ)       | Lv11〜: `ceil(s‰ × U(ℓ) / (420 × 500)) + 1` 以上(§5。係数は 0.5)                  |

- **語彙の初出**: Lv1 sedan・単発・2 台・壁(ゆるめると楽な組として)/ Lv11 van・S 字・必須減速の組 /
  Lv21 truck・トラックのテンプレート・4 車線 / Lv31 工事 / Lv51 5 車線。壁の車種は、その面で使える車種の
  うち 1 つ(1 つの壁の中では揃える — §5)。
- **重み**(初期値。Phase 2 で決めた — 前の版は「§7 に置く」と書いたまま置いていなかった。すべて整数で、
  `game/levels.ts` と `game/course.ts` に置く):
  - 普通の行のテンプレート: 単発 5 / 2 台 3 / トラック 2(Lv21〜)/ 工事 1(Lv31〜)。2 台は隙間を挟まない
    隣り合う 2 車線が無いとき(3 車線で隙間が真ん中)は引かない。工事は外側の車線が隙間でないときだけ。
  - 単発・2 台・トラックの添え車の車種: Lv1〜10 は sedan、Lv11〜 は sedan / van を等しく。壁の車種は
    Lv1〜10 sedan、Lv11〜20 sedan / van、Lv21〜 sedan / van / truck を等しく。
  - 普通の行の隙間のずらし: −2 / −1 / 0 / +1 / +2 車線を 1 / 3 / 2 / 3 / 1(車線の外へ出るものは除く)。
    **S 字**(Lv11〜): 前の行で隙間が動いていれば、4 回に 1 回、逆向きに 1 車線(重み 3)か 2 車線(重み 1)。
  - 壁の組のずらし: §5(3・4 車線は ±1 を 3・±2 を 1、5 車線は ±2 だけ)。
- 上の式の値(`game/levels.test.ts` が式から再現する。全開の理論時間だけは算術。頭の緩めは、Lv11・21・31・51
  でちょうど +40 ‰(Lv31 は 239 ‰)、ほかのブロックの頭(Lv1・41・61・71・81・91)には無いことも確かめる):

  | ℓ   | L   | U      | 全開の理論時間 | σ    | σ_gate(必要な速度) | v_check | s     | n_gate |

  | 1   | 3   | 16,000 | 38.1 秒        | 2.20 | —                  | 420     | 0.250 | —      |

  | 50  | 4   | 26,186 | 62.3 秒        | 1.73 | 0.663(278 px/s)    | 250     | 0.146 | 20     |

  n_gate は Lv11〜100 で 11〜24 組(係数 0.5。0.6 では 10〜20 組)。スラックが大きい前半ほど組が多いのは
  式の帰結で、体験として多すぎれば、Rusher の門を保ったまま係数を直す(0.5 へ下げた理由は §5)。

- **Phase 2 のテストで実測**(ボット A の 1 走、ステップ = 1/120 秒): Lv1 は 4,621(38.5 秒)、Lv11 は
  5,682(47.4 秒)、Lv51 は 6,909(57.6 秒)、Lv100 は 10,063(83.9 秒)。最速のライバルは Lv1 5,785・

## 8. 助けの形(Undo / Hint を作らない)

- **Undo は作らない**: リアルタイムの盤に「一手戻す」は存在しない。
- **Hint・レーシングラインは作らない**: 盤面は全部見えていて隠れた情報が無く、ルートを示すと遊びを
  代行する(Brick Breaker §8・Bunny Hop §8・Snake §9 と同じ理由)。
- 代わりの無料・無制限の助けは 2 つ:
  - **即時・同一コースの再走**(↻ と結果カードの Retry、§2)。交通が (seed, level) で決定的なので、
    覚えた難所がそのまま効く(Brick Breaker §8)。**↻ は確認なしの即時リトライ**(アーケードの形。
    失うのは数十秒のそのレースだけ)— `tryAgain` のラベルは使うが `RestartDialog` も
    `ConfirmDialog` も置かない(`restartDialogWiring.test.ts` がアーケードに許している形。Sky Fighter /
    Brick Breaker / Bubble Pop / Bunny Hop の `GameScreen.tsx` にダイアログは無い)。
  - **操作の助け**: Buttons の形・↓ / S キー・▼(§3)。
- **一時停止は無料・無制限・確認なし**(§2)。
- **時間の整理**: ライバルのペースは実質「隠れた目標タイム」だが、画面には車として現れ、数字の
  カウントダウンも点滅も無い。開始は最初のタッチまで待ち、一時停止は自由で、時間で打ち切らない。
  Brick Breaker §6(時計を出さず、盤面そのものが残り時間)と同じ整理で、人工的な緊急性ではない
  (§13。「タイマープレッシャーを既定にしない」との関係も §13)。
- コンティニュー・復活・追加ライフは作らない。広告視聴や課金に結び付けない。

## 9. 保存と統計

- **保存キーは 4 つ**: `ot.progress` / `ot.stats` / `ot.flags` / `ot.prefs`(この順で
  `storage/keys.ts` に宣言する)。Phase 3 で `progress` と `prefs` を `storage/keys.ts`・
  `storage/schemas.ts`・`gameKeys.test.ts` の自分の行に同じコミットで足した(Phase 2 の文書だけの段階で
  足さなかった逸脱は、これで解消した — §18)。他ゲームのキーには触れない。
- **途中保存は作らない**(Sky Fighter §10 / Brick Breaker §10 と同じ理由 — リアルタイムの復元は
  正直な再開にならない)。そのため `saveGame` も `storage/gamePersistence.ts` も無く、Root は `entry` を
  受け取らない(`src/test/shortcutResumeWiring.test.ts`)。ホーム画面ショートカットはゲームのホームへ
  開く。デイリーが無いので 2 スロット規則(`src/test/savedGameSlots.test.ts`)は関係しない。
- 保存する値の純関数(開放の最前線の進め方・Play の面・`n/100`・`played` と秒の計上・壊れた値を受け入れない
  読み取り・結果の事実)は `game/progress.ts` にある(Phase 2)。`storage/schemas.ts` の 4 つのスキーマは
  欄の検査をこの関数(`decodeHighestUnlocked`・`decodeStats`・`decodeControls`)に任せ、`state/statsLogic.ts`
  はこの関数を記録の形に載せるだけにした(ロジックと保存が「正しい値」で食い違わないため。Phase 3)。
  - `decodeStats` は 2 つの数(`played`・`totalPlaySeconds`)だけを読み、`schemaVersion` を見ず、余分な
    キーも無視する。**Phase 3 の `ot.stats` のスキーマは `schemaVersion === 1` を自分で確かめてから呼ぶ**
    (版の違う記録・版の無い記録は既定値に倒す)。
  - `advanceProgress` は、開放されていない面(と 1..100 の整数でない番号)の 1 位を無視する — UI から誤った
    面の番号が来ても最前線を飛ばさない(Phase 2 のレビューで決めた。`game/progress.test.ts`)。
- 壊れた記録・型の合わない記録は**受け入れない**: どのスキーマも、合わなければレコードごと既定値に
  倒す(共有の `loadRecord` の扱い。バリデータは例外を投げない)。保存の失敗はゲームを止めない。

| キー          | 形(v1)                                                          | 既定                 |
| ------------- | --------------------------------------------------------------- | -------------------- |
| `ot.progress` | `{ schemaVersion: 1, highestUnlocked }` — 整数 1..101           | `highestUnlocked: 1` |
| `ot.stats`    | `{ schemaVersion: 1, played, totalPlaySeconds }` — 0 以上の整数 | すべて 0             |
| `ot.flags`    | `{ schemaVersion: 1, tutorialCompleted }` — 真偽                | `false`              |
| `ot.prefs`    | `{ schemaVersion: 1, controls }` — `'drag'` か `'buttons'`      | `controls: 'drag'`   |

- `ot.stats` はスキャフォールドの v1(`played` だけ)に `totalPlaySeconds` を足す。この版は
  どのビルドにも出ていない(`channel: 'in-development'`)ので保存データが存在せず、版は 1 のまま
  変える。`totalPlaySeconds` の無い記録は既定値に倒れる。
- **面ごとの着順・タイム・Bumps は保存しない。**比べる記録を持たない(`BestDelta` を使わない、§11)。
- `ot.progress`: 1 位のゴールで `highestUnlocked = max(highestUnlocked, ℓ + 1)`(上限 101)。結果の
  画面が出る前、ゴールのステップで書く。
- **レビュー依頼**: 1 位のゴールのときだけ `recordGameCompleted()` を呼ぶ(`ot.progress` を書くのと同じ
  ステップ。Bubble Pop §10・Brick Breaker・Sky Fighter と同じ形)。2〜4 位と、離脱では呼ばない。

### 統計

- **`played`**: レースが動き出したとき(`ready` → `running`)に 1 回数える。Retry・Next の後の
  レースも、動き出せば 1 回と数える(Bubble Pop §10「リトライ・次のレベルの開始も 1 回と数える」)。
  一時停止からの再開は数え直さない。画面を離れて終わったレースも数えてある。
- **`totalPlaySeconds`**: `running` の間だけ数える(`ready`・`paused`・結果の画面は数えない)。
  計上は逐次(bookedRef 方式)で、**ゴール・↻・退出・バックグラウンド・blur・一時停止・アンマウントは
  同じ 1 本の計上を呼ぶ**([GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「計上の経路を増やさない」)。
  計上の置き場所は、スキャフォールドが `state/GameContext.tsx` に置いている
  **`useOnUnmount(syncActiveGame)` の 1 本**にする(盤面の cleanup の `flushSeconds()` は持たない —
  門は `src/test/unmountBookingWiring.test.ts`)。
  - **プレイ時計は GameContext が持つ**: 走り始めた時刻(`runningSinceRef`)・それまでに走った秒
    (`elapsedRef`)・計上済みの秒(`bookedRef`)は Provider の ref。**レースの状態(`ready` / `running` /
    `paused` / `finished`)も Provider が持ち**、状態を変えるのは `commit` の 1 か所だけで、時計は
    `commit` が `running` に入るときに動かし、出るときに止める(Snake の GameContext と同じ形。Phase 3 で
    決めた — 前の版の「盤面が `startClock()` / `stopClock()` を呼ぶ」は採らなかった。止める理由
    (❚❚・バックグラウンド・blur・Back・ゴール)の多くは盤の外で起き、盤に時計の口を渡すと同じ遷移を
    2 か所で見ることになるため)。盤面(`ui/components/OvertakeStage.tsx`)は状態を受け取って従う
    だけで、秒を数えず、計上もしない。ref が盤面にあると、アンマウントで親(Provider)の cleanup が
    盤面の cleanup より先に走ったとき、`syncActiveGame` は走っている秒を読めない。現在時刻は `state/` が
    `Date.now()` で読む(`game/` は時計を読まない)。
  - **`syncActiveGame`** は、時計が走っていれば `elapsed = elapsedRef + (now − runningSince)` を求め、
    `bookedRef` との差を `totalPlaySeconds` に足して `bookedRef` を進める(冪等)。ゴール・↻・←(`goHome`)・
    バックグラウンド・blur・一時停止・アンマウント(ブラウザの戻る — §2)は、すべてこの関数を呼ぶ。
- **統計の画面**: `played` と総プレイ時間だけ。クリア数は `ot.progress` から `n/100` で出す。
  Brick Breaker / Bubble Pop の `cleared` は足さない(既クリアの再走を数える理由が無い)。
  ストリークは持たない。**レースの経過時間はどこにも出さない**(統計の総プレイ時間は別物)。

3 ステップ・図中心・各 1 文(初回はゲームを開いたときに表示し、以後はホームから)。文案(ja)。en の

## 11. 画面・寸法・演出とアクセシビリティ

### ホーム

- **Play**(主ボタン)は、開放の最前線の面の `ready` を開く。最前線が 101(全クリア)になっても、
  **Play とレベル選択は Lv100 を指し続ける**(`min(最前線, 100)` — Brick Breaker §7 と同じ)。Levels
  チップは `n/100`(§7)。Quick Rules と統計へのボタンは共有の枠。
- **操作の形(Drag / Buttons)の選択はホームに置く**: 共有の `segmented`(2 択のボタン列。`role="group"`
  とラベル、選ばれている側に `aria-pressed` — Snake の速度の選択と同じ形)で、ラベルは「操作 / Controls」と
  「Drag / Buttons」(`en`。他の言語は §12)。**選ばなくても始められる**(既定は Drag)。選ぶと
  `ot.prefs` に残り、次の `ready` から効く(走っている最中には変えられない — 選択はホームにしか無い)。
  タップの的は 48px 以上。

### 画面の構成(上から)

- **上部バー**: ← ホームへ / 面の表示(`Lv n`)/ **❚❚ と ▶**(1 つのボタン。`running` で ❚❚ =
  一時停止、`paused` と `ready` で ▶ = 再開・出発)/ **↻**(Retry。`ready` では押せない)。
  ❚❚ を上部バーに置くのは Overtake の選択(Snake の Pause は十字の中央)。
- **着順の行**: 小さな静的なインク色の **`n/4`** と、**進行バー**(自分とライバル 3 台の目盛り)、
  状態の短い文(`ready` で「タッチで出発」、`paused` で「❚❚ 一時停止中」)。この行は 1 行で、
  状態が変わっても高さが変わらない(盤が動かない)。
- **盤**(canvas)。盤の上にはカード・帯・幕を重ねない(`ready` でも `paused` でも — Snake §13 と
  同じ理由。結果カードはゴールの後)。
- **ボタンの行**: Drag の形では ▼(`any-pointer: coarse` のときだけ)、Buttons の形では ◀ ▼ ▶。
  タップの的は 48px 以上。

### 着順と進行バー

- `n/4` は変化しても**色・点滅・トースト・音を付けない**。進行バーも同じで、目盛りは r / U の位置に
  静かに動くだけ(Brick Breaker §6 に倣い、目標を画面から隠さない)。自分の目盛りはインクの塗り、
  ライバルはアクセントの輪郭に ASCII の数字 1〜3。色だけに頼らない。
- **数字が隠れない並べ方**(Phase 3 のレビューで直した): 行の 28px を 2 段に分け、ライバルの輪(16px)は
  上の段(0〜16)、線と自分の点(10px)は下の段(16〜26)に置く — 自分の点は輪に重ならない。4 台は同じ
  位置から出て、ペースの差は 1 割に満たない(§6)ので、輪はほとんどの間ひと塊になる。輪どうしは
  `ui/progressMarks.ts` の `spreadMarks` で、互いに輪 1 つぶん(16px)以上離し、コースの順(同じ位置なら
  数字の順)を保ち、線の上から出さず、塊の望む位置の平均を中心に等間隔に並べる(動かす量は塊が要る
  ぶんだけ)。線の幅は ResizeObserver で測る(測る前と jsdom では 360 幅の 166px)。ヘッドレスの Chromium
  (360×640)で、`ready` の 3 つの輪が 16px 間隔で数字が読め、点は下の段にあることを見た。並べた位置は
  目安で、実際の進行の比は r / U(輪が塊のときは数 px ずれる)。
- **レースの経過時間は、プレイ中・結果・統計のどこにも出さない。**

### 結果

- ゴールから約 1 秒置いて結果カードを出す(`ui/useResultReveal.ts`、900 ms。止まった盤を見る時間で、
  その間に押せるものは無く、盤の操作キーも届かない(§3)。Reduced Motion では即時)。
- カードは**大きな着順 `n/4`** と **Bumps n** だけ。追い抜き回数は往復で水増しできるので採らない。
  Lead / Behind も時間差の代用なので出さない。`BestDelta` は使わない(比べる記録が無い)。
- 見出しは事実だけ(例: 1 位なら「Lv 12 をクリア」、ほかは「Lv 12 — 3/4」。`en` は「Level {n} cleared」・
  「Level {n} — {place}」、`ja` は「レベル {n} クリア」・「レベル {n} — {place}」— §12)。
  称賛語(Nice work / Great / すごい)は出さない — スキャフォールドの `overtakeResultTitle` の
  "Nice work" は置き換える。「負け」「失敗」とも言わない。
- ボタン: **1 位なら Next が第一**(Lv100 では出さない)、次に Retry・Levels。**2〜4 位なら Retry が
  第一**、次に Levels(計画の推奨 — Brick Breaker / Bubble Pop の結果カードの形に合わせる。42〜46 で
  分かれた「結果カードの第一ボタン」はオーナーの選択待ちなので暫定 — §18)。↻ と Retry は同じ関数。
- 共有は `ShareAction`。details は `Level n · Place n/4 · Bumps n`。**`outcome` が `completed` になるのは
  1 位のときだけ**、それ以外は `played`(`ShareOutcome` はこの 2 値)。ラベルは「Place / 着順」で、
  Rank / Ranking / leaderboard は使わない([BRAND.md](BRAND.md)「表現ルール」)。

### 寸法

- canvas の CSS 幅は **min(100%, 360px, 使える高さ × 0.5625)**、高さは幅 × 16/9。使える高さ =
  画面の高さ − 上部バー − 着順の行 − 余白 − ボタンの行 − Web の広告予約 116px(`ui/styles.css` の
  `:root[data-sg-web-ads]`。ネイティブはバナー + safe area)。`svh` を使い、使えないエンジンには `vh`
  を先に宣言する。Sky Fighter の `.sf-canvas`(基本は幅から決めて縦につぶれる)は流用せず、最初から
  高さから導く。
- **各段の高さ**(`ui/overtake.css` の値。Phase 3 で共有の枠に合わせて直した。下の表でヘッドレスの Chromium の
  値と一致した — 上部バー 0〜64・着順の行 64〜92・盤の上端 104): 上部バー
  64(共有の `.game-topbar` の上下 8 + 48px の的)・着順の行 28・余白 24(`.ot-body` の上下 8 + 盤と
  ボタンの行の間 8)・ボタンの行 56(48px の的 + 余白)。CSS は「ほかの段」を `--ot-chrome` に持ち、
  ボタンの行が無いとき 116px、あるとき 172px(`.ot-buttons` か `@media (any-pointer: coarse)`)、Web の
  広告予約は `:root[data-sg-web-ads]` で `--ot-reserve` 116px。盤の幅は
  `min(100%, 360px, (100svh − --ot-chrome − --ot-reserve) × 0.5625)`(`svh` の前に `vh` を宣言)。
  ボタンの行は、Drag の形では `any-pointer: coarse` のときだけ(§3)、Buttons の形では常に出る。Snake の
  「ほかの段」254px(SNAKE_RULES §13「寸法」)と比べて、ここは 172px。
- 算術では Web 360×640(広告予約あり)で、使える高さ = 640 − 116 − 172 = 352 なので **約 198×352
  (倍率 0.55)** — ボタンの行が出るタッチ端末と Buttons の形。ボタンの行が無いとき(マウスなど)は
  640 − 116 − 116 = 408 で約 230×408(倍率 0.64)。倍率 0.55 でも自車 34×58 は約 19×32 CSS px、5 車線の
  1 車線は約 33 CSS px(算術。見分けられるかは実測の段階 — 未確認)。モード A の不感帯などの CSS px の値
  (§3)は、この倍率によらない。
- **ネイティブのバナーは引いていない**(Phase 3): `BannerSlot` の高さ(64px 以上)は `--ot-chrome` に入って
  いない。ゲームはアプリに出ない(ベータ)ので、正式収録のときに盤の高さの式へ足す(§16「確かめないこと」)。
- **受け入れ基準**: 360×640 の広告予約ありで、自車と前方 440 論理 px 以上が広告帯より上にすべて
  見える(canvas 全体が見えれば満たす — 自車の前端は y = 470)。スクロールなし・横スクロールなし。

  **ヘッドレス Chromium(Playwright、`isMobile`、DPR 2)**で測った — **実機ではない**(2026-10-21。Phase 3 の
  最初の版は「ブラウザが無い」と書いたが、誤りだった)。ゲームの Root だけを載せた開発用の頁で、Level 1 の

- **横向きの電話は受け入れる(遊べる形にはしない)**(Phase 3 のレビューで決めた): 盤は 9:16 の縦長で、
  高さから幅が決まる。640×360 では広告予約 116 と上部バー・着順の行を引くと、盤は 40.5×72 になり見えも
  操作もできないが、ページは崩れずスクロールも出ない。▼ の行を盤の横へ移しても(Snake §13 の横向きの形)
  取り戻すのは 56px で、盤は約 72×128 にしかならない — 縦長の盤である限り、横向きの電話で遊べる大きさには
  ならない。回転を促す案内も出さない(翻訳の要る文を 1 つ足し、盤の代わりに出す状態をもう 1 つ持つことになる
  — アプリは縦向き固定で、横向きは Web だけの形)。横向きで遊べるかは、正式収録の前に実機で見直す(§18)。
- **ホームの高さ**(同じ測定で見えたこと。この節の受け入れ基準の外): 360×640 の広告予約ありで、ホームは
  675px(英語)〜697px(日本語ほか)でスクロールする。Snake のホームも同じ頁で 770px、Brick Breaker は 640px。
  操作の形の選択の行(§11「ホーム」)が 1 行ぶん足している。直すかは統合で決める(§18)。

### 描画とループ

- **Canvas + RAF**(アーケード 4 本と同じ)。**RAF は `running` の間だけ回す。**`ready` / `paused` /
  `finished` / バックグラウンドではループを止め、状態が変わったときに 1 回描くだけにする。
- 1 フレームに最大 6 ステップ(§1)。ロジックの状態は盤面コンポーネントの ref に持つ。
- テーマ(`data-theme` / `data-game`)と OS のダークモードの変化で色を読み直して再描画する。
  `shadowBlur` / `ctx.filter` は使わない(低スペック床)。
- アンマウントで RAF・リスナー・ResizeObserver・DEV のシーム `__otFrame`(テストが手でフレームを回す
  ための口)と `__otState`(レースの状態を読む口。兄弟の `__sfState` / `__bbState` と同じ。Phase 3 で
  足した)をすべて解放する([GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)、`OvertakeRoot.leak.test.tsx`)。
  どちらも `import.meta.env.DEV` の中だけで、本番のビルドには入らない。

### 見た目(色だけに頼らない)

- アクセントは 1 色(登録済みの `overtake` の蘇芳、`var(--accent)`)。色はすべて共有のトークン
  (`--surface` `--line` `--ink` `--ink-soft` `--accent` `--accent-ink`)から取り、ゲームの CSS に色の値を
  書かない。
- **自車はインクの塗り**、**交通はアクセントの塗り**、**ライバルはアクセントの輪郭(中は面の色)に
  インクの数字 1〜3**。塗りと輪郭で区別する。工事区間はアクセントの斜線。路肩は細い線と
  `--ink-soft`。ゴールは路面を横切る市松の帯(インクと面の色)。
- 車の形は自作する(Bunny Hop §12 のように、形をソースに絵として書く)。角を落とした矩形と窓の
  切り欠きだけで、**比較対象(§14)の配色・車体シルエット・パトカー・燃料計を複製しない**。
- 重なり(自車とライバル、ライバルどうし — すり抜け、§4)は、**自車を最後に描くので自車は常に上に
  見える**。ライバルは中を面の色で塗る(上の「中は面の色」)ので**ライバルどうしは透けない**: 1 → 3 の
  順に描くので、重なると番号の大きい車が下の車を数字ごと隠す(3 が 1・2 を隠す)。Phase 3 の最初の版の
  「輪郭なので下の車が透けて見える」は描画と食い違っていた(レビューの指摘で文を直した。透かす塗りにはして
  いない — 輪郭だけにすると交通の塗りと重なったときに数字が読めない)。
- 盤の文字は ASCII の数字だけ(ライバルの 1〜3)。翻訳の要る文字は盤に置かない。

### 演出

- **路面の破線**: 車線の境目の破線はピッチ 210 論理 px 以上(長さ 70・間 140。初期値)、低い
  コントラスト(`--line`)。地面の速さ w + vT で流れる(算術では最大 620 px/s で 2.95 Hz の縞 —
  3 Hz 以下)。
- **点滅**(Bump の 0.8 秒): 不透明度 1 ↔ 0.35 を 0.25 秒ずつ(2 Hz 以下)。ステップ数から決める。
- 爆発・破片・画面揺れ・速度線・粒子は作らない。

### Reduced Motion

- **路面の破線は止めない** — 速度の唯一の連続信号で、コースの流れそのもの(Bunny Hop §12 /
  Snake §13 の線引き)。**点滅も止めない** — 当たらない状態という状態の表示(Bunny Hop §12)。
- 結果カードまでの約 1 秒は即時にする(既存ゲームと同じ)。ほかに止める演出は持たない(最初から
  作らない)。

### 音

既存の合成音(`services/sound.ts`)だけ。新しい音は足さない。設定に従う。

- **Bump**: `sounds.invalid()`(低い短音 1 つ。速くも大きくもならない)。
- **1 位のゴール**: `sounds.clear()`。
- **2〜4 位のゴール**: 鳴らさない(終わりであって失敗ではないので `gameOver` は使わない)。
- エンジン音・連続音・速度で上がるピッチ・追い抜きの音・クラクションは作らない。

### スクリーンリーダー

- 盤は `role="img"` で、面と状態を名前に持つ(例「Overtake, level 12: running」)。リアルタイムの盤を
  読み上げることはしない。canvas 自体は `aria-hidden`。
- **ライブリージョン(丁寧、`role="status"`)はゴール時の着順と Bumps だけ**を読み上げる(例
  「Place 1 of 4. Bumps 2.」)。走っている間の着順の変化は読まない。ライブリージョンは結果カードで
  盤が `inert` になっても聞こえる場所に置く。
- 着順の行の `n/4` は数字を `aria-hidden` にし、隣の見えない文(`visually-hidden`)が「Place 3 of 4」と
  言葉で持つ(役割の無い `span` の `aria-label` は ARIA 1.2 で名前を持てず、読み上げに無視されるため —
  Phase 3 のレビューで直した)。ライブリージョンにはしない(走っている間の着順は読み上げない)。
- ◀ ▶ ▼ と ❚❚ / ▶ は名前の付いたボタン。❚❚ / ▶ の印は共有のアイコンと同じ 1em(上部バーで 22px — ← と ↻ に
  そろう。ヘッドレスの Chromium で 3 つとも高さ 22px を測った)。❚❚ / ▶ は `aria-keyshortcuts` で同じことをするキーを名乗る
  (❚❚ のとき P、▶ のとき Space)。

## 13. 意図的な差分

**クリアの実体(正直に)**

- **クリアの実体は、最速ライバル 1 台のタイムより速くゴールすること**である(§6)。ライバルは
  プレイヤーに反応しない「ペースの違う車」で、その面の最速の 1 台のゴールのステップは (seed, level)
  だけで決まる凍結した値になる。2 台目・3 台目は着順の 2〜4 を分けるだけ。「3 台より先に」は
  「最速の 1 台より先に」と同じ意味である。
- **目標タイムの基準は、ほぼ完全な走り**: T_1 は B_ref(ボット A から 2.21% 以内 — 実測)の単独走に
  スラック s(ℓ) を足した値で、「反応 250 ms の人」に対する余裕ではない。Lv81〜100 では最速のライバルは
  ボット A(反応 0・完全な走り)より 8.2〜11.7% 遅いだけで、人はその幅の中でゴールしなければ 1 位になれない
  (§6「T_1 は何から測った値か」)。「1 位でクリア」の判断(§18)の材料。
- **時計を出さない整理**: ライバルのペースは実質「隠れた目標タイム」だが、画面には車として現れ、
  数字のカウントダウンも点滅も無い。開始は最初のタッチまで待ち、一時停止は自由で、時間で打ち切らない
  (ライバルが全員ゴールしても自分のゴールまで走る — §2)。Brick Breaker §6 の整理と同じで、人工的な
  緊急性(ストリーク・エナジー・期間限定)とは別物である。**「時計を出さない」は見せ方であって構造
  ではない** — 構造としては目標タイムがある。ストア文面で「時間制限なし」と言うときは「時計も打ち切りも
  無い」の意味に限る。
- **「タイマープレッシャーを既定にしない」との関係**([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md)
  「継続的なゲームイベント運営なし」の箇条)。上の時計の整理は「人工的な緊急性」への答えで、この原則には
  別の答えが要る: Overtake の唯一のモードは、凍結した目標タイム(最速のライバル)との競走で、構造としては
  時間の圧力がある。それでも許容するのは、(1) 製品オーナーがこの設計(ペースの違う車との競走・クリアは
  1 位)を承認した(2026-10-20、計画)、(2) 時計もカウントダウンも出さず、時間で打ち切らず、一時停止は
  無料・無制限で、開始は最初のタッチまで待つ(§2・§8)、(3) ストリーク・エナジー・期間限定・待ち時間は
  無く、リトライは即時・無料(§8)から。圧力を下げる案(「2 位以内でクリア」)は判断待ちとして残してある
  (§18)。
- **減速を必須にする 2 つの門は構造**: 「全開で通れない行の本数」(§5)と「Rusher が Lv21 以降で 1 位に
  なれない」(§6)は、唯一の新しい動詞(減速)を任意にしないための構造で、**どちらかを外す・弱める変更は
  仕様の変更として扱う**(門が落ちたときに直してよいのは本数の係数 0.6 などの初期値だけ)。これが無いと
  「銃の無い Sky Fighter」に潰れる(計画)。
- **ラバーバンドなし**: ライバルの速さはプレイヤーの位置・順位・連敗に依存しない(§6)。負け続けても
  ライバルは遅くならず、勝ち続けても速くならない。

**既存の収録ゲームとの違い**

- **Sky Fighter**(縦スクロール・相対ドラッグ・100 面のはしごが共通): 射撃・ライフ・強化・ボスが無く、
  結果は着順。差別化の本体は**減速が本物の判断になる壁の組**(Lv11 から全開では通れない 2 枚目 — §5)と
  **ライバルとの着順**に置く。
- **Brick Breaker / Bubble Pop**(同じ 100 面のはしご): 「クリア」を決めるのが盤を崩し切ることではなく
  ライバルのペース。失敗の終わり方が無く、どのレースも着順で終わる。結果と記録の見せ方(着順と
  Bumps)を「クリア / 失敗」と同じにしない。
- **Bunny Hop / Snake**: 面があり、エンドレスではない。スコアも自己ベストも無い。
- **Bounce Up**: 離れたランの記録(高さの記録)を持たない。
- **復帰で再開しない**(§2)。Bunny Hop の盤面は画面が見えると再開するが、こちらはタップまで止まった
  まま(Snake §6 と同じ)。
- **blur で止まる**(§2)。アーケードの 4 本は止めない。PC で別のウィンドウへ移ったキーボードの人が、
  戻ったらぶつかっていた、を起こさないため(Snake §15 と同じ理由)。
- **↻ は確認なしの即時リトライ**(§8)。失うのは数十秒のそのレースだけ。
- **`BestDelta` を持たない**(§11)。比べる記録が無い。
- **レーサー同士はすり抜ける**(§4・§6)。接触の罰も押し合いも無い — ライバルをプレイヤーから
  完全に独立させるため。

- 燃料・ニトロ・ピックアップ・パトカー・射撃・ギア・ガレージ・車の強化・コイン・コンティニューは

- **デイリーなし・難易度選択なし・Free Run なし・タイムアタックなし**(§7)。生成は seed 決定的なので、
  必要になれば後から足せる。
- **途中保存なし**(§9)。
- スコア・オンラインランキングは無い(維持費の原則)。
