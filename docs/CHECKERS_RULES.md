# Checkers — 正式ゲームルール

このドキュメントが Checkers の仕様の正本である。実装(`apps/simple-games/src/games/checkers/`)、
テスト、Quick Rules はここに従う。コードはここへ `§n` で言及する。挙動を変えるときは、
同じコミットでこの文書を直す。

ブランド原則([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md))はこの文書より上位にある。

ゲーム ID は `checkers`、i18n キーの接頭辞は `checkers`、保存キーの接頭辞は `ck.` である。
規則は**英式(アメリカン・チェッカー / English draughts)**を採る。名称は一般名の
「Checkers」を使う(英連邦圏の「Draughts」はストアのキーワードに置く)。

## 1. 盤面と対局者

- 8×8 の 64 マス(`game/types.ts`。行優先の配列、行 0 が最上段)。使うのは**暗色マスの
  32 だけ**で、明色マスには何も乗らない。右下が明色になる印刷盤の慣習に合わせ、
  暗色は「行 + 列が奇数」である(`isDarkSquare`)。
- 駒は 5 値で表す: 0 = 空、1 = プレイヤーの兵、2 = CPU の兵、3 = プレイヤーのキング、
  4 = CPU のキング。
- 初期配置は各 12 枚。CPU が行 0〜2、プレイヤーが行 5〜7 の暗色マス。**プレイヤーは
  常に画面の手前側**で、プレイヤーの兵は行 0 へ向かって進み、CPU の兵は行 7 へ向かう。
  これは絵の話であって先後の話ではない。
- **先攻・後攻はプレイヤーが選ぶ**(ホーム画面。既定は先攻)。選択は次の対局に適用される
  設定であり、**対局中のゲームには触らない** — 始めた側のまま終わる。保存キーは
  `ck.prefs`、セッションは開いた側を `first` として持つ。対局相手は CPU だけである —
  オンライン対戦もローカル対人戦も作らない([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md)
  「初期リリースで実装しないもの」)。
- 駒は色だけを描く。プレイヤーはタイトルのアクセント色(ウォルナット)、CPU はこの
  ゲームが持つ第 2 色(アイボリー。ゲームコンテンツの色。Connect Four のティールと同じ
  立場)。文字は置かない — 盤面は全言語で同じに読める([I18N_POLICY.md](I18N_POLICY.md))。
  **キングは色ではなく形で示す**(内側のリング。§10)。

## 2. 一手の解決

1. 兵は**斜め前**に 1 マス進む。キングは斜め 4 方向に 1 マス進む。**飛びキングは
   作らない**(それは国際式の規則。§11)。
2. 捕獲は、斜めに隣接する相手の駒を跳び越えて直後の空きマスへ着地する。兵は前方 2 方向、
   キングは 4 方向へ跳べる。
3. **捕獲できる手が盤面のどこかにあるとき、捕獲以外の手は非合法である**(強制捕獲)。
   合法手の生成器(`game/engine.ts` の `collectMoves`)は跳びがあれば跳びだけを返し、
   静かな手を作らない — 画面と CPU が「何が合法か」で食い違えない唯一の作り方である。
   **どの捕獲を選ぶかは自由**で、最大取り義務は課さない(それも国際式の規則。§11)。
4. 着地した駒がさらに跳べるときは、**同じ駒で続けて跳ぶ義務**がある。
5. 跳びの途中で最奥段に達したら**昇格し、その手番はそこで終わる**。新しいキングがさらに
   跳べても跳ばない。これは英式の規則であり、捕獲の連鎖が早く止まる唯一の場所である。

**1 手と 1 ステップは別物である。**手数(`moveCount`)が数えるのは**手**で、連続捕獲は
何ステップあっても 1 手である。手番の途中はセッションが `pendingJumpFrom`(跳び継続元の
セル)として持ち、画面はその駒に選択を固定して続く跳び先だけを合法にする。

## 3. 終了条件

- 駒がなくなった側の負け。
- **手番に合法手がない側の負け**(閉塞)。囲まれて動けないことは、取り尽くされることと
  同じ結末である。
- **引き分けは「捕獲も兵の移動もない手が 50 手続いたとき」**。動いているのがキングだけで、
  材料も昇格への距離も変わっていない局面であり、そこから先は繰り返ししかない。
  カウンタ `quietPlies` 1 個で表し、捕獲か兵の移動でゼロに戻る(`DRAW_QUIET_PLIES`)。
  **三回同形は実装しない** — 同じ結末をより単純な機構が与え、保存形式に局面の履歴を
  持ち込まずに済む(§11)。
- 遷移は `status`(`'playing' | 'won' | 'lost' | 'draw'`)で一度だけ起きる
  (`game/session.ts`)。終局の瞬間に両者の残り駒数を提示する。負けを叱る文言は書かない。

## 4. CPU

- 探索は**プレイヤーの着手を起点にのみ**走る。ポーリングも先読みもしない
  ([GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「CPU 探索」)。
- 難易度は 3 つ(`easy` / `normal` / `hard`):
  - **easy** — 合法手(**捕獲義務込み**)からシード決定的にランダムで選ぶ。初心者であって
    ズルではない。
  - **normal** — 3 手読みの α–β 探索。すぐの損得は見えるが、深い罠には掛かる。
  - **hard** — 反復深化 α–β(最大 8 手読み)。ノード上限 `HARD_NODE_LIMIT`(26,000)に
    達したら**完了済みの深さの最善で打つ**。深さ 1 は必ず完了するので、hard が normal より
    弱くなることはない。
- **探索は引き分け(§3)も終局として読む。**`quietPlies` は探索と根へ渡され、手が
  完了するたびに更新され、50 に達した枝は評価値 0(引き分け)で閉じる。渡さないと
  **CPU が読んでいるゲーム木と実際のルールがずれる** — 49 手目に静かなキング移動を
  打てば盤面上はその瞬間に引き分けなのに、探索はその先も続くものとして数える。
  駒得しているときに自分から引き分けへ歩いていく読みになるので、これは強さの調整では
  なく正しさの問題である(`DRAW_QUIET_PLIES` は `types.ts` に置く — セッションと
  探索の両方が要るため)。
- **連続捕獲は同一プライとして読む** — 手番も深さも消費しない。跳びの継続に 1 手ぶんの
  深さを課すと、局面が最も鋭いところで探索が浅くなる(Reversi がパスに深さを課さないのと
  同じ理屈)。地平線の先でも**捕獲が強制されている間は読み進める**(静止探索。
  `QUIESCENCE_PLIES` で上限)。
- 評価は駒の価値(兵 100 / キング 165)+ 兵の前進 + 自陣最奥段の守り + 端の列。
- 同点の候補はセッションのシードと手数から決定的に選ぶ:
  `createRng(`${seed}:cpu:${moveCount}`)`。同じシードで同じ手順を踏めば、CPU は必ず
  同じ手を返す。ゴールデンテスト(`game/compatibility.test.ts`)が固定する。
- **ノード上限は既存の CPU 対局 2 本を基準に決めた。**同じ環境で Reversi の hard が
  約 248ms、Connect Four の hard が約 301ms かかるのに対し、この上限での応答は約 136ms
  である。コレクションで**最も軽い hard**であることが、**出荷済みの CPU より重くない**と
  言える正直な言い方である。
- **探索は 450ms の「間」の中では走らない。**`CPU_DELAY_MS` は 1 本の timeout を張り、
  探索はその**中**で走る(`state/GameContext.tsx`。Reversi と Connect Four も同じ形)。
  つまり着手が現れるのは概ね **450ms + 探索時間**であって、450ms の内側ではない。
  上限を「間に収まるか」ではなく既存 2 本を基準に決めたのはこのためで、
  あの 2 本が「待ち時間全体の体感」の既に出荷された基準だからである。
  **ただしこの実測値を CI の判定に使わない。**`game/cpu.bench.test.ts` が見るのは
  「訪問ノード数が上限以内で、実行ごとに同じで、少なくとも 1 局面は上限を使い切る」
  という決定的な仕事量で、壁時計はログに出すだけである。共有ランナーの壁時計は
  ランナーを測っているにすぎず、生成コストのテストが既に
  「**壁時計は判定していない**」と決めている([RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md)、
  [SUDOKU_RULES.md](SUDOKU_RULES.md) §7)。実測値は機械で動くので、
  **出荷済みの CPU と同程度のコストで収まる範囲でいちばん強い CPU** がこの選択であって、
  そこからはみ出す強さは採らない(issue #26 非目標)。低スペック実機での体感は、
  このドキュメントではなく**実機確認(リリース Gate)で見る**。
- CPU の着手は約 450ms 置いてから現れる(`CPU_DELAY_MS`)。**連続捕獲は 1 跳びずつ**、
  跳びのあいだは短い 260ms(`CPU_STEP_MS`)で描く — 相手が考えている間ではなく、
  1 つの手がまだ進行中だからである。アンマウント・Undo・新規対局はこの予定を破棄する。

## 5. Undo

- **無制限・無料**。自分の直前の決定点まで戻す — CPU の応手と自分の一手がまとめて
  取り消される。
- **連続捕獲の途中で押しても、シーケンスが始まる前まで戻る。**強制された 2 跳び目は
  何かを決めた場所ではないので、そこを決定点として残さない。途中の駒だけ戻す中途半端は
  作らない。
- Undo は振り直しではない: 戻して同じ手を打てば、CPU も同じ手を返す(§4 の決定性)。
- 広告視聴や課金による Undo は作らない([ADS_POLICY.md](ADS_POLICY.md))。

## 6. 助けの形

- **動かせる駒と行き先は常に盤面に示す**(選択できる駒だけが押せて、行き先には小さな点)。
  チェッカーで初心者が最初に躓くのは強制捕獲であり、**跳べる駒だけが選べる**という形に
  すると、規則が説明ではなく操作として伝わる。これはルールの可視化であって最善手の提案では
  なく、Reversi の合法手表示や Minesweeper の旗と同じ側にある(REVERSI_RULES.md §7)。
- **無効な操作を叱らない。**取れる手があるときに他の駒を押しても、何も起きず音も鳴らない。
  拒否ではなく、そもそも提示していない。
- **Hint(最善手の提案)は作らない**: 盤面は完全に見えており、隠れた情報がない。
  次の一手を教える機能は CPU がプレイヤーの側でも打つことになる(REVERSI_RULES.md §7 /
  CONNECT_FOUR_RULES.md §6 と同じ判断)。
- 助けは Undo(§5)と合法手の表示だけ。どちらも無料で、初回起動から使える。

## 7. スコアと統計

- スコアという数はない。対局の結果は勝ち / 負け / 引き分けと残り駒数だけである。
- 統計は難易度ごとに `played`(開始した回数)・`wins`・`losses`・`draws`、全体で
  `totalPlaySeconds`。ストリークは数えないし表示しない。
- 対局を放棄して新しく始めた場合、負けには数えない(`played` には既に数えている)。
  記録されるのは実際に終局した対局だけ — 統計が脅しになってはならない。
- プレイ時間は逐次計上(bookedRef 方式、2048 と同じ)。

## 8. 中断と再開

- **途中保存する。** 盤面はターン制で、保存して開き直した盤面は保存した瞬間と同じである
  (GAME_2048_RULES.md §10 と同じ理由)。
- 保存スロットは 1 つ(`ck.saveGame`)。盤面(64 文字、マスごとに `0`〜`4`)・**開いた側**
  (`first`)・難易度・シード・手数・`quietPlies`・`pendingJumpFrom`・経過秒を持つ
  (`game/serialize.ts`)。**手番は保存しない** — 交互が崩れないゲームなので、手数と
  `first` から導出できる(`sideToMove`)。
- **`pendingJumpFrom` を保存形式 v1 に最初から含める。**捕獲の連鎖は最後まで強制される
  ので、その途中で閉じたアプリは途中へ戻らなければならない。義務が保存を跨いで消えると、
  復元した盤面は別のゲームになる。
- **Undo 履歴は保存しない**。再開した対局はその局面から始まる。
- 壊れた保存は読み捨てて、ホームへ戻る(勝手に新しい対局を始めない)。検証は fail-closed:
  明色マスの駒・**昇格段に立ったままの兵**・駒種以外の文字・片側 12 枚超・どちらかが 0 枚・
  終局済み(手番側に合法手なし)・**`pendingJumpFrom` の駒がそこから跳べない**保存は破棄する。
  最後の 1 つは、放置すると誰にも解消できない義務の上に座り続ける盤面を復元してしまう。
  手数は CPU の抽選の半分(§4)なので、食い違う保存を受け入れると、保存した対局とは違う
  応手を返す盤面を再開させてしまう。
- CPU の手番の途中(連続捕獲の最中)で離れた場合も同じ形で保存され、再開時は
  `pendingJumpFrom` から**残りの跳びだけ**を決め直す。

## 9. Quick Rules(アプリ内チュートリアル)

3 ステップ・図中心・各 1 文(初回起動時に表示、以後はホームから):

1. 斜め前へ 1 マス。相手の駒は跳び越して取る — 取れるときは、取る手しか打てない。
2. 着地した場所からまた跳べるなら、同じ駒で続けて跳ぶ。
3. いちばん奥に着けばキング(斜め後ろへも動ける)。相手の駒を全部取るか、動けなくしたら勝ち。

詳細は Landing Page へ。ガイドを公開するまで「詳しく見る」は出さない
(`src/ui/landing.ts`)。オフラインでは何も起きない(ゲームは止めない)。

## 10. 演出とアクセシビリティ

- 駒は DOM 要素。移動と跳びは transform のスライド(1 マスあたり約 110ms、上限 220ms)で、
  **跳んだ距離に応じて時間が変わる**。取られた駒はその場を 1 度だけ光らせて消す。昇格は
  内側リングが 160ms でポップして現れる。要素は増やさない — 粒子も画面揺れもない。
- Reduced Motion(アプリ設定または OS)では移動・消滅・昇格のすべてを無効にし、駒は
  着地位置にすでにある状態で描かれる。
- **キングは形で示す**(内側のリング)。色だけに頼らない。
- 最後に動いた駒には小さな印を付ける(CPU の手を見失わないため)。印は相手側の色で描く —
  1 色では両方の駒の上で読めないため。
- 盤面は 64 個のボタン。各マスは「行・列: 空 / 自分の駒 / 自分のキング / CPU の駒 /
  CPU のキング / 選択中 / ここへ動かす」を読み上げる。押せるのは、動かせる駒と、
  選択中の駒の行き先だけである。
- ターン行は高さを固定し、手番・強制捕獲・跳びの継続のどれを言っても盤面が跳ねない。
- **時計を出さない**。経過時間は統計にだけ残る。
- 効果音は既存の合成音(`services/sound`)のみ: 着手で `select`、捕獲で `match`、
  勝ちで `clear`、負け・引き分けで `gameOver`。設定に従う。無効な操作では鳴らさない。

## 11. 意図的な差分

市中のチェッカー / ドラフツ系アプリを調べたうえで、意図的に合わせないものを記録する。

**ブランド原則により合わせないもの**

- **Undo・強さ解放を広告や課金に結び付けない**。難易度は最初から全部選べる。
- レーティング・ランキング・オンライン対戦はない。記録は端末の中だけにある(§7)。
- デイリーやストリークで毎日呼び戻さない。

**設計判断として合わせないもの**

- **国際式(10×10・飛びキング・最大取り義務)を採らない。**「Checkers」という名前で
  探す人の期待は英式であり、v1 では盤面規則を 1 つに絞る(CONNECT_FOUR_RULES.md
  「盤面サイズは 7×6 だけ」と同じ判断)。
- **強制捕獲を切る設定は作らない。**捕獲義務はチェッカーの戦術のほぼすべてであり、
  外した遊びは別のゲームである。躓きは設定ではなく提示の形で吸収する(§6)。
- **三回同形を数えない。**引き分けは `quietPlies` 1 個で判定する(§3)。局面の履歴を
  保存形式に持ち込む価値が、この判定の精度差に見合わない。
- **赤と黒という物理の慣習を継がない。**駒の色は役割の色であり(自分 = アクセント、
  相手 = このゲームの第 2 色)、先後は設定である(§1)。
- **最強 CPU を作らない**。hard は「よく考えるが読み切らない」上限付き探索であり、
  終盤データベースも定石集も積まない(§4、issue #26)。
- **棋譜・解析・形勢グラフを持たない**。対局が終わったら結果だけが残る。
