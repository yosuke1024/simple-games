## 1. 盤面

- **W×H のマス**の全マスにタイルが 1 枚ずつある。空きマスは無い。行と列は 0 始まりで数える(画面と
  読み上げでは 1 始まり)。マスの番号は行優先(`index = row × W + col`)。
- **タイルの型は 4 種**。管を出す方向(上・右・下・左)の集合で決まる:

  | 型(コードの名前) | 管の数 | 向き 0 の管 | 取りうる向き | 保存の 1 文字 |
  | ---------------- | ------ | ----------- | ------------ | ------------- |
  | 端(`end`)        | 1      | 上          | 4(0〜3)      | `e`           |
  | 直線(`straight`) | 2      | 上・下      | **2**(0〜1)  | `s`           |
  | エルボ(`elbow`)  | 2      | 上・右      | 4(0〜3)      | `l`           |
  | T(`tee`)         | 3      | 上・右・下  | 4(0〜3)      | `t`           |

  **十字(4 方向)は無い。**管を出さないタイル(0 方向)も無い。

- **向き k** は向き 0 を時計回りに 90° × k 回したもの。直線は 180° 回すと同じ管の集合になるので、向きは 2 つ
  だけを数える(向き 0 = 縦、向き 1 = 横)。ほかの型は 4 つの向きがすべて違う管の集合になる。だから
  **「向き」と「管の集合」は 1 対 1** で、解も保存もこの向きの番号で持つ(§4 の一意性は管の集合で数える —
  直線の 180° は同じ解)。
- **水源**は盤の 1 マスに固定され、そのマスのタイルに形の印(§10)が付く。**水源のタイルも普通のタイルで、
  ほかと同じく回せる**(§15 の決定)。水源は生成で中央寄りのマスから選ぶ(§4)。
- 盤の型・水源の位置は生成後に変わらない。プレイヤーが変えるのは**向き**だけである。
- **盤の端は閉じている**(折り返さない — §15 の決定)。盤の外へ向いた管は行き止まりのまま残る。

難易度プリセット(タイルそのものがタップの的で、Bridges の島のように的を広げられない):

| 難易度 | 盤  | タイル数 |
| ------ | --- | -------- |
| Easy   | 5×5 | 25       |
| Medium | 7×7 | 49       |
| Hard   | 8×8 | 64       |

**9×9 は v1 に無い。**根拠は「下限に張り付く」: [BRIDGES_RULES.md](BRIDGES_RULES.md) §13 の実測で 360×640(Web の
広告の予約 116px 込み)の 9×9 は 1 マス 34.0px で、これは幅ではなく高さの取り分で決まった値であり、Box Regions /
Shape Regions の 1 マスの下限 `clamp(34px, …)` に**張り付いている**(割ってはいない)。Pipe Link のタップの的は
タイル 1 枚の正方形そのもので、これより広げられない。同じ式(高さの取り分 =(画面高 − 320px)÷(行 + 0.4))で
算術では 8×8 は 1 マス約 38.1px。**Phase 3 の実測**(ヘッドレスの Chromium 1194 で測った — §14「Phase 3 の実測」。
テストではなく再現の手順だけを書く): 360×640 の 8×8 は Web の広告の予約込みで **1 マス 38.1px**(盤 322px、
Undo / Hint の下端 524px = 画面高 − 116px の内側、スクロールなし)で、算術の見込みと一致した。320×640 では 35.0px、
320×568 と 640×360(横持ち)では下限の 34px に張り付き、ページ(広告の予約あり)か盤の領域(なし)がスクロール
する。その後、1 マスと盤の余白を整数の px に切り下げた(§10。`round()` のあるブラウザーだけ)ので、同じ手順の
測り直しでは 360×640 の 8×8 は **1 マス 38px**(盤 320px)、320×640 は 35px(§14「継ぎ目の修正の後の測り直し」)。

**盤面に翻訳の要る文字は 1 つも載らない。**タイルは管の線、点灯・水源・Hint の印は形で描く
([I18N_POLICY.md](I18N_POLICY.md))。読み上げ名だけが i18n を通る。盤面は RTL でも左右反転しない。

## 2. 規則と勝利

1. 各タイルは、型の取りうる向きのどれか 1 つを向いている。
2. **上下左右に隣り合う 2 枚が、互いに相手へ管を向けているときだけ、その 2 枚はつながっている**(片方だけが
   向けている管は行き止まり)。盤の外へ向いた管は何ともつながらない。
3. 水源のタイルから、つながりをたどって届くタイルが**点灯**する(水源自身も点灯する)。
4. **全タイルが点灯し、行き止まりの管が 1 本も無く、つながりが閉路を作らないとき、盤は完成**(クリア)。

**用語と定義**(`game/board.ts`):

- **つながり**(connection)= 規則 2 で互いに管を向け合った隣の組。
- **行き止まり**(open end)= どのタイルとも組になっていない管の口(盤の外へ向いた口と、向け返されていない口)。
- **点灯集合**(`litSet`)= 水源から、つながりだけをたどる幅優先探索で届くタイル。
- **完成**(`isSolved`)= 点灯集合が全タイル **かつ** 行き止まりが 0 **かつ** つながりの数がちょうど
  `タイル数 − 1`(=つながりのグラフが全域木)。

**出題では「全タイル点灯」だけで完成が決まる。**出題の型の多重集合は全域木から作る(§4)ので、管の口の総数は
ちょうど `2 × (タイル数 − 1)` である。全タイルが点灯していれば、つながりのグラフは連結なので少なくとも
`タイル数 − 1` 本のつながりを持ち、1 本のつながりは口を 2 つ使うので、口はすべて使われ(行き止まり 0)、
つながりはちょうど `タイル数 − 1` 本で、連結でこの本数のグラフは木(閉路なし)である。だから**勝利判定は
保存した解と比べず、点灯で決まる**。`isSolved` が 3 つを全部確かめるのは、口の総数がこの値でない手作りの盤
(テスト)でも同じ関数で正しく答えるためで、口の総数が `2 × (タイル数 − 1)` の盤で「全点灯 ⇔ `isSolved`」が
成り立つことはテストが全数で確かめる(§13)。

- **完成の判定は水源の位置によらない**(全域木はどこから見ても全域木)。水源が意味を持つのは、遊んでいる途中に
  どのタイルが点灯して見えるか、だけである。
- 敗北は無い。ミス回数・ライフ・ゲームオーバー・時間切れは無い(§12)。
- 完成した盤面は、それ以上の操作(回転・Undo・Hint)を受け付けない。完成への遷移は 1 度だけ起こるので、
  完了の記録(§8)はその瞬間に 1 度だけ付く。

**回転**(`game/tiles.ts`):

- 時計回り `rotateCw`: 向き k → (k + 1) mod 周期。反時計回り `rotateCcw`: 向き k → (k + 周期 − 1) mod 周期。
  周期は直線 2・ほかの型 4。反時計回りは時計回りの逆(どの型・どの向きでも `rotateCcw(rotateCw(k)) = k`)。
- 管の集合で見ると、時計回り 1 回は上 → 右 → 下 → 左 → 上の写像で、直線の向き 1 を時計回りに回すと向き 0 の
  管の集合(上・下)に戻る。

## 3. 操作

**タイルをタップすると、そのタイルが 90° 時計回りに回る。**1 タップ = 1 手。回転は状態がタップで即座に変わり、
演出は見た目だけで、連打を待たせない(§10)。

- **反時計回り**はマウスの**右クリック**とキーボードの **Shift+Enter** だけで、**タッチには無い**(1 段戻すのは
  Undo — §6)。
- **右ボタンの契約**(既存の 2 本に合わせる):
  - 単発の右クリック = そのタイルを反時計回りに 1 回。**盤全体(タイルの間の隙間も)**でブラウザのメニューを
    出さない。タッチとペン先の長押しがブラウザに出させる `contextmenu` は**この操作ではない**ので無視する。
    ここまでは [MINESWEEPER_RULES.md](MINESWEEPER_RULES.md) §3 と [NONOGRAM_RULES.md](NONOGRAM_RULES.md) §3 の
    両方が持つ形である。
  - **ペンのバレルボタンは右ボタンとして扱う**(ホバー中に押せば `button` 2、先を着ける前から押していれば
    `buttons` の 2 のビット)。これは **Nonogram §3 だけが持つ形**(同じ節が「バレルボタンは Nonogram だけが
    持つ」と書き、Minesweeper はペンの `contextmenu` を無視してバレルを持たない)で、Pipe Link は Nonogram に
    合わせる。ペン先だけのタップは時計回りのまま。
  - macOS の Ctrl+クリックはブラウザが `contextmenu` として届けるので、反時計回り 1 回として扱い、後に続く
    `click` を `detail > 0` の印で飲む(キーボードの Enter が出す `click` は `detail` 0 なので飲まない)。
  - **右ドラッグは作らない**(Nonogram の #130 は持たない)。押下で覚えたもの(押したタイル・ボタン・長押しの
    タイマー)は `pointercancel` で解く([ARCHITECTURE.md](ARCHITECTURE.md)「指を取り上げられたときの契約」、
    `src/test/pointerContractWiring.test.ts`)。
- **長押しは何もしない。**タッチとペン先で同じタイルを Minesweeper と同じしきい値(`LONG_PRESS_MS` = 450ms —
  `games/minesweeper/ui/components/MinesBoard.tsx`。値は写し、コードは共有しない)以上押し続けたら印を付け、
  **離した後にブラウザが出す `click` では回さない**。長押しの後に `click` が来るかどうかは環境で違いうる
  ので、こう決めないと長押しが「時計回り 1 回」になったりならなかったりする。**Android の Chrome と iOS の
  Safari の実機では確かめていない**(§13 — 未検証(実機))。
- **キーボード**: 盤はタブ位置 1 つ(roving tabindex)。矢印キーでタイルからタイルへ移り(盤の端で止まり、
  折り返さない)、**Enter / Space で時計回り**、**Shift+Enter で反時計回り**(ボタンの既定の `click` と重ならない
  よう `keydown` で受け、既定の動作を止める)、`Ctrl/Cmd+Z` で Undo、`H` で Hint
  ([LOOP_PUZZLE_RULES.md](LOOP_PUZZLE_RULES.md) §4 と同じ割り当て)。**キーリピートでは回さない**(押しっぱなしの
  Enter はタイルを回し続けない。Undo・Hint も同じ)。選択の状態が無いので **Escape は受けない**(↻ の問いが
  開いている間の Escape は問いのキャンセル — [ARCHITECTURE.md](ARCHITECTURE.md)「Escape は Cancel」)。結果
  カードと確認ダイアログの間はどのキーも効かない(盤面は `inert`)。画面に無い機能をキーボード専用にしない
  (反時計回りは右クリックにもあり、どちらも Undo で代わりがきく)。
- **結果カードは盤面への入力を拾わない。**最後のタイルは連打の途中で完成することが多いので、Bridges §4 と同じく
  カードは現れてから 400ms(`RESULT_ARM_MS`、Bridges の値の写し — 初期値)クリック・タップを受け付けず、
  キーリピートの `keydown` はいつでも受け付けない。
- **作らない**: 自動回転・「答え合わせ」ボタン・タイルロック・ドラッグで回す操作・2 本指の回転・回転の
  モード切り替え(§12)。

**手の数え方**: 時計回り 1 回・反時計回り 1 回がそれぞれ 1 手(Undo の 1 段 — §6)。手数は**表示もせず記録も
しない**(§8 — 3 タップか右クリック 1 回か Undo かで同じ向きへの手数が変わり、比べられない)。

## 4. 生成と一意性

すべての盤面は seed から決定的に作る。ダウンロードはしない。生成が上限に届いたときだけ、このゲームの
生成器が作って同梱した盤面へフォールバックする(手順 6)。(`game/generator.ts` の `generatePuzzle(seed,
difficulty)` — 段 2 で実装。1 つの派生 seed の手順 1〜5 は `attemptCandidate`。確かめた範囲は §13。)

1. **全域木を育てる。**水源を盤の**中央寄りのマス**(中心から縦横 1 マス以内 — 奇数の盤は中央の 3×3 の 9 マス、
   偶数の盤は中央の 2×2 の 4 マス)から seed で一様に選び、木の根にする。根から始めて「木に入ったマスから
   木の外の隣へ伸びる辺」の中から、**木の側のマスの次数が 3 未満の辺**を seed で一様に選んで足す、を全マスが
   木に入るまで繰り返す(十字は構成で作られない)。途中で選べる辺が無くなったら(全部の候補の木の側の
   マスが次数 3)その木を捨てて派生 seed で作り直す(`grow` — 段 2 のテストで実測では、走査した候補と
   census の 3,000 本で一度も起きていない)。木から各マスの型と正しい向き — **解** — が決まる。
   1 マスの次数が 1・2・3 のどれかになるので、型は端・直線・エルボ・T のどれかになる。水源・成長・崩しの
   乱数は `createRng`(Bridges からの写し)で、木は `createRng(<派生 seed>)` の 1 本の列から、水源 → 辺の順に引く。
2. **等級**: 技法ソルバー(下)を**型だけの盤**(全タイルがどの向きも取りうる状態)から回し、全タイルの向きが
   決まるか、決まったなら要った最も高い技法の段(L1 / L2 / L3)を得る。
3. **一意性**: 解の個数を **2 まで**数える(`countSolutions`、下)。**最後まで走ってちょうど 1** の盤だけを
   採る。技法で全タイルが決まった盤は一意(技法は健全なので)だが、生成器は数え上げでも別に証明する
   (Bridges §6 と同じ二重の確かめ)。上限に届いた数え上げは一意とも複数とも言わない(`complete: false`)ので、
   その候補は捨てる。
4. **ティアに合えば採る**(§5 の帯: Easy = L1 だけで全部決まる、Medium = L2 が要り L3 は要らない、Hard =
   L2 か L3 が要り、L1 だけでは 16 枚以上が決まらない — 段 2 で直した帯。§5)。合わなければ seed を派生させて
   (`<seed>#2`, `#3`, …)手順 1 から作り直す。数え上げ(手順 3)は、等級がティアに合った候補だけに回す
   (技法で決まらない候補や帯の外の候補に数え上げの仕事を使わない)。
5. **崩す**(§15 の決定): 各タイルの初期の向きを、**型の取りうる向き(直線 2・ほか 4)から seed で一様に
   選ぶ**。解と同じ向きのままのタイルも許す(全タイルを解と違う向きにすると、直線は初期の向きの反対が
   答えだと分かり、ほかの型も候補が 1 つ消える — 初期配置から答えが漏れる)。そのうえで、**完成済み
   (全点灯)の崩し**と、**解と同じ向きのタイルが 60% を超える崩し**を捨てて、同じ盤の崩しだけを引き直す。
   崩しは木とは別の乱数の列 `createRng(<派生 seed>|scramble)` から引き、引き直しは同じ列の続きである。
   引き直しは **`SCRAMBLE_ATTEMPT_LIMIT` = 40 回まで**(**初期値**)で、40 回とも捨てたらその候補は外れ
   (`scramble`)として次の派生 seed へ進む。60% は**初期値**(計画の推奨)。算術では、各タイルが解と同じ向きの
   ままになる確率は直線 1/2・ほか 1/4 なので、期待値は直線の割合で決まり 25〜50% の間にある。**段 2 のテストで
   実測**(`guarantee.test.ts` の「scramble」行、走査した 1,265 盤): 解と同じ向きの割合は平均 27.6〜29.6%
   (算術の期待値 28.4〜28.6% — 直線は全タイルの 13.5〜14.5%)、最大 56.0%(Easy)。**捨てる規則は 1 度も
   働かなかった**(どの盤も 1 回目の崩しで採られた)— 60% は盤 25〜64 枚では分布の外にあり、守りとしてだけ
   置いてある(§14)。
6. **上限で同梱盤面へ。**派生 seed の数(`ATTEMPT_LIMIT`)か 1 盤面の仕事量(`GENERATION_WORK_LIMIT` — 下)が
   上限に届いたら、同梱盤面(`game/bundled.ts`、ティアごとに 24 面、計 72 面)から seed のハッシュ
   (`hashSeed(seed) mod 24`)で 1 面を選ぶ(同じ seed なら同じ面)。同梱盤面は**この生成器が記録した seed から
   作ったもの**(seed は `pipe-link-bundled-<難易度>-<k>` で、`k` = 1, 2, … のうち 1 回目の試行で採られたものを
   先頭から 24 個)で、ほかの製品や書籍から写していない。`bundled.test.ts` が seed から作り直して文字単位の一致を
   確かめ、数え上げと別実装の探索(`test-helpers.ts` の `independentCount`)で一意性を、技法ソルバーで等級を
   確かめ直し、崩しから Hint だけで解き切る。`fallback` 印が付く(デイリーも同じ)。生成器を変えて一致しなく
   なったら同梱盤面を作り直す(それは決定であり、コミットメッセージに書く)。

不変条件(段 2 のテストが固定する — §13):

- 同じ seed なら、必ず同じ盤面・同じ解・同じ水源・同じ初期の向き・同じ仕事量になる(`compatibility.test.ts`
  の golden 4 面と、走査の各組の先頭 20 面の作り直し)。
- 解は次数 1〜3・十字なし・盤の外へ管を出さない全域木で、水源は中央寄りのマス。
- 出題は一意解を持ち、そのティアの帯に入る。同梱盤面も同じ。
- 初期の向きは完成していず、解と同じ向きのタイルは 60% 以下。

### 技法ソルバー(`game/solver.ts`、段 1 で実装)

各タイルは「まだ取りうる向き」の集合(**ドメイン**)を持つ。型だけの盤では、どのタイルもその型の全部の向き
(直線 2・ほか 4)を持つ。隣り合う 2 マスの間の**辺**(と盤の端の辺)は、両側のドメインから「管が通る」
「通らない」「まだ分からない」のどれかに読める。技法は次の 3 段で、**3 つとも健全**(完成した配置
— §2 の `isSolved` — のどれかが使っている向きを消さない)である。

- **L1 — 噛み合わせ**(盤の端と、決まった隣との管の有無を両側でそろえる):
  - 盤の外へ管を向ける向きを捨てる。
  - 隣との辺について、片側のドメインのどの向きもその辺に管を出す(出さない)なら、もう片側からもその辺に管を
    出さない(出す)向きを捨てる。両側で「出せる」と「出さずに済む」が 1 つも重ならなければ矛盾。
  - ドメインが空になったら矛盾。変化が無くなるまで(不動点まで)繰り返す。
- **L2 — 閉路と孤立の排除**(1 枚の 1 つの向きを仮に置き、その 1 歩と、隣への 1 ホップだけを見る。それより先へは
  伝播しない): いま**確実に管が通る辺**でつながったタイルの集まりを**組**と呼び、組から出ている「まだ分からない
  辺」の端の数を組の**出口**と呼ぶ。タイル t の向き r を仮に置くと、t の「まだ分からない辺」の管の有無が決まる。
  **1 ホップ**: そうして辺が決まった隣 u は、その辺に合う向きだけに絞られ、絞った u のドメインで**確実になる**
  u のほかの辺も決まる(u の先のタイルは見ない)。こうして決まった辺だけを動かして:
  - **閉路**(`loop`): 新しく開く辺が、すでに同じ組(か、この仮置きで開く別の辺で同じ組にまとまったもの)の
    2 枚を結ぶなら、r は閉路を作る。捨てる(完成は木 — §2)。
  - **孤立**(`closed-group`): 仮置きで触れた組(開く辺でまとめた後)のどれかの出口が 0 になり、その組が
    全タイルでなければ、r はどこへも伸びられない閉じた集まりを作る。捨てる。t の側の組でも、r が閉じた辺の先の
    組でも同じ(**水源を含むかどうかによらない** — 全タイルが 1 つにつながらなければ完成しないので、全タイル
    でない閉じた集まりはどれも行き止まりである)。
  - 例: 向かい合いうる 2 枚の端。t(端)を隣の端 u へ向けると、u は t の方を向く向きだけに絞られ、u のほかの辺は
    閉じる — 2 枚の閉じた組になるので捨てる。1 ホップが無いと、u のほかの辺がまだ開きうるように見えて、これを
    捨てられない(`solver.test.ts` の 2×2 の端 4 枚)。
  - 1 ホップで隣のドメインが空になる仮置き(`interlock`)も捨てるが、L1 の不動点ではどの向きにも各辺の相手が
    いるので起きない。
  - L2 の除外はどれも「その仮置きから必ず起きること」だけで証明するので健全である。隣の隣へ広げた先は L3 の
    仕事である。
- **L3 — 仮定 1 回**(入れ子にしない): ドメインが 2 つ以上のタイル t の向き r を 1 つ仮に置き、L1 と L2 を不動点
  まで回す。矛盾したら r を実際の盤から捨てる。仮定の中でさらに仮定はしない。

**梯子として回す**(`solve`): L1 を不動点まで → 止まったら、L2 の 1 回の見渡しで見つかった除外を
**すべて**適用して最初へ戻る(どの除外も同じ盤から証明したものなので、まとめて適用しても健全)→ L2 も
何も無ければ、L3 の除外を**最初の 1 つだけ**適用して最初へ戻る → L3 も無ければ止まる。タイルは行優先、
向きは番号の昇順で見渡すので、結果は決定的である。安い段で進める限り高い段は使わない。

結果(`SolveResult`):

| フィールド      | 意味                                                                                                             |
| --------------- | ---------------------------------------------------------------------------------------------------------------- |
| `status`        | `solved`(全タイルのドメインが 1 つ)/ `stuck`(技法が止まった)/ `contradiction`(解が無い)/ `aborted`(仕事量の上限) |
| `level`         | 実際に何かを捨てた最も高い段(0〜3)。型だけの盤から始めて L1 だけで決まれば 1                                     |
| `domains`       | 終わったときのドメイン                                                                                           |
| `order`         | ドメインが 1 つになった順のタイルの番号(同じ時点で決まったものは行優先)— Hint の順(§6)                           |
| `stageOf`       | 各タイルが決まった時点の段(そのタイルが決まるまでに使った最も高い段。決まっていなければ 0)                       |
| `l2Rounds` `l3` | L2 の除外を適用した見渡しの回数 / L3 で捨てた向きの数                                                            |
| `work`          | 仕事量(下)                                                                                                       |

**技法で全タイルが決まった盤は一意解である**(健全な推論が残した唯一の配置が唯一の解)。ただし健全性は
「完成した配置を消さない」ことで、決まった配置が本当に完成しているかは `isSolved` で確かめる(段 1 の
テストは全数でこれを確かめる — §13)。

実装は 1 つだけで、生成時の等級(手順 2)、Hint(§6)、テストが共有する。

### 解の個数(`countSolutions`、段 1 で実装)

深さ優先の数え上げ。各ノードで L1 と L2 を不動点まで適用し(健全な刈り込み)、さらに盤全体で「確実に管が通る
辺が閉路を作る」「出口 0 で全タイルでない組がある」を矛盾として刈る。まだ決まっていないタイルのうちドメインが
最も小さいもの(同点は行優先で先のもの)を選び、向きの番号の昇順に枝分かれする。全タイルが決まった葉で
`isSolved` を確かめて数える。解を `limit`(既定 2)個見つけたら止める。

- 解は**管の集合**で数える。向きと管の集合は 1 対 1(§1)なので、向きの配列として数えればよい。
- **ノード上限 `SEARCH_NODE_LIMIT` = 5,000**(段 2 で決め直した。計画が「5,000〜20,000 の間で実測から決める」と
  した範囲の下端。**段 2 のテストで実測**では、数え上げが要ったノードは最大 7(`guarantee.test.ts` の census
  8×8。走査した出題では最大 5)で、どの値でも届かない。だから下端を採り、最悪の場合の仕事を小さくした。段 1 の
  初期値は 10,000)に届いたら `complete: false` を返す。このときの数は下限に
  すぎず、**一意とも解なしとも主張しない**(`isUnique` は `complete && count === 1` だけで真)。
- 生成器から呼ぶときは、ノードに加えて**仕事量の予算**(1 盤面の残りの予算)も渡せる。途中で尽きた伝播は
  「枝が矛盾した」ではなく `complete: false` として読む。
- 技法ソルバーにも**仕事量の上限 `TECHNIQUE_WORK_LIMIT` = 200,000**(段 2 で決め直した。段 1 の初期値は
  2,000,000)がある。**段 2 のテストで実測**では、1 回の技法ソルバーの仕事量は census の 3,000 本で最大 15,332
  (7×7 の技法で決まらない木 — L3 の仮定を全部試すので重い)、出荷する盤(Hint が解く盤)では最大 465(同梱 72 面)/
  399(走査の 160 面)。上限はその最悪の約 13 倍。届いたら `status: 'aborted'`(等級は付かない = 出荷しない。
  Hint は解の段へ — §6)。どの上限でも、推測を答えとして示すことは無い。

**仕事量の単位**(壁時計ではなく仕事量で門にする — [BRIDGES_RULES.md](BRIDGES_RULES.md) §6「予算は仕事量で
門にする」と同じ理由): L1 でタイルを 1 枚見直すごとに 1、L2 で 1 つの仮の向きを確かめるごとに 1(と、組と
出口を数え直すごとにタイル数)、L3 の 1 回の仮定ごとに 1 + その中の L1・L2 の仕事量、数え上げの 1 ノードごとに
1 + そのノードの伝播の仕事量。生成ではさらに、木に辺を 1 本足すごとにタイル数(候補の辺を探して盤を 1 回
見渡す)、崩しを 1 回引くごとにタイル数。同じ盤ならどのマシンでも同じ数になる。

### 仕事量と上限(探索が走るのは明示的な操作のときだけ)

探索は UI スレッドで同期に走る(Worker は使わない — [GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「CPU 探索」)。
先読み・定期実行・常駐はしない。

| 操作                                                    | 走るもの                                               | 上限                                                   |
| ------------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------ |
| 「New Board」「デイリーを開く」(Restart は作り直さない) | 生成(手順 1〜6)                                        | `ATTEMPT_LIMIT` 160・`GENERATION_WORK_LIMIT` 1,500,000 |
| Hint をタップ(その盤で最初の 1 回)                      | 型だけの盤からの技法ソルバー 1 回                      | `TECHNIQUE_WORK_LIMIT` 200,000                         |
| Hint をタップ(2 回目以降)                               | **走らない**(セッションが持つ 1 回目の結果を読む — 下) | —                                                      |
| 中断中の盤面を読み込む                                  | **走らない**(形と中身の検査だけ — §7)                  | —                                                      |

**読み込み時に一意性を探索で証明し直さない。**勝利判定は点灯で決まり(§2)、技法の Hint は解を読まない
(§6)ので、手で作った複数解のレコードで食い違いうるのは Hint の最後の段の「解の 1 枚」だけで、それは出荷した
盤では起きない。だから Bridges / Loop Puzzle の「開くときの再証明」([GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)
「CPU 探索」の暫定の例外。オーナーの確認待ち)には乗らない — Pipe Link の探索はタップのときだけ走る。
これは統合の作業で GAME_LIFECYCLE.md「CPU 探索」に書き足す(共有ファイル)。

Hint の技法ソルバーは型だけの盤から回すので、結果は盤ごとに一定である。**セッションは 1 盤面につき 1 回だけ
回して結果を持つ**(段 2 の決定。`PipeLinkSession.techniques` — 保存しない。Restart は同じ盤なので持ち越し、
読み込み直した盤では最初の Hint のタップでまた 1 回回す)。走るのは Hint のタップの中だけで、盤を開いただけでは
走らない。

**生成の上限**(段 2 で決めた。根拠の数は §14 の「段 2 のテストで実測」):

- **`ATTEMPT_LIMIT` = 160**(派生 seed の数)。最も通りにくい Hard の候補の通過率は走査で 11.7%(2,563 候補で
  300 面)。算術では、160 回続けて外れる確率は (1 − 0.117)¹⁶⁰ ≈ 2 × 10⁻⁹。走査の最大は 49 回(Hard)。
- **`GENERATION_WORK_LIMIT` = 1,500,000**(1 盤面の全試行の仕事量)。走査の最大 223,439(Hard、49 回の試行)の
  約 6.7 倍で、実際にはヒットか試行の上限が先に決める。仕事量の門は試行の偶然によらない最悪の天井として置く。
  各試行の技法ソルバー・数え上げ・崩しは残りの予算で走り(崩しは、1 回分の仕事(タイル数)が残りに収まらない
  ときは引かない)、途中で尽きた試行は外れ(`budget`)で、決して通過ではない。だから**出荷した試行の仕事量は
  その予算を越えない**。予算を見る前に最後まで走るのは成長だけなので、1 盤面の仕事量は、上限 + 最後の 1 回の
  成長(タイル数 × (タイル数 − 1)、8×8 で 4,032)を越えない(ソルバーと数え上げは 1 回の加算 — 最大でタイル数 —
  だけ越えうるが、それは成長が予算の内で終わった試行だけで起き、成長 1 回分より小さい)。`generator.test.ts` が、
  各ティアで出荷する 1 試行を成長の直前からその全仕事量まで 1 単位ずつの予算で切り、等級・数え上げ・崩しの
  どこで尽きても `budget` になり、全仕事量でだけ出荷することを確かめる。
- **`SCRAMBLE_ATTEMPT_LIMIT` = 40**(手順 5。**初期値** — 走査では 1 回目で必ず採られた)。

**計画のリスク ④ の扱い(段 2)。**段 1 の探索の見込みのとおり、8×8 で L3 が要る一意な盤は少なかった — **段 2 の
テストで実測**では census の 8×8 の 1,000 本で 7 本(0.7%)。L3 が要ることを Hard の条件にすると、候補 1 つあたりの
通過率は 1% 未満になり、算術では 1 面に平均約 140 回の試行が要り、上限 160 でも約 3 割((1 − 0.007)¹⁶⁰ ≈ 0.33)が
同梱盤面へ落ちる。**予算を
緩める前に**、段 2 の探索で成長の形を変える案を試した(下)が、L3 の率は上がらなかった。そこで**この文書の §5 の
Hard の帯を先に直し**(L2 か L3 が要り、L1 だけでは 16 枚以上が決まらない盤)、それから生成器を書いた。直した
帯での Hard の通過率が上の 11.7% である。

- **段 2 の探索では**(テストではなく、再現しない): 8×8 の木 400 本ずつで、§4 手順 1 の一様な成長のほか、
  「最後に足したマスから伸ばす」を確率 0.5 / 0.8 で優先する成長(長い通路になる)、次数 2 のマスから伸ばす辺の
  重みを 0.3 / 3 にする成長(T の数を減らす / 増やす)を比べた。L3 が要る一意な盤は 400 本中 0〜2 本で、どれも
  一様な成長(1 本)と変わらなかった。技法で決まらない盤の「決まらなかったマス」の周りで木の辺を入れ替える
  局所探索も試したが、L3 の盤 1 面あたり 160〜1,000 回の技法ソルバーを要し、一様な成長の再試行(約 140 回)より
  良くなかった(一様な成長の再試行は、census の 0.7% から算術で 1 面あたり約 140 本)。だから成長は §4 手順 1 の
  まま変えていない。

## 5. ティア

ティアは**盤の大きさと、型だけの盤から全部を決めるのに要る技法の段**、Hard ではさらに **L1 だけでは決まらない
タイルの数**で決める(`game/generator.ts` の `TIERS` と `meetsTier`):

| ティア | 盤  | 要る技法                                                                                            | 計画との対応                                                         |
| ------ | --- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Easy   | 5×5 | **L1 だけ**で全部決まる(`level` 1)                                                                  | 計画の「Easy = L1 だけで全部決まる」                                 |
| Medium | 7×7 | **L2 が要り、L3 は要らない**(`level` 2 で `solved`)                                                 | 推奨どおり、Medium に L3 の要る盤を入れない                          |
| Hard   | 8×8 | **L2 か L3 が要り**(`level` 2〜3 で `solved`)、**L1 だけでは 16 枚以上が決まらない**(`l1Open` ≥ 16) | 計画の「Hard = L3 が要る」から**段 2 で変えた**(下 — 計画のリスク ④) |
| Daily  | 7×7 | Medium と同じ                                                                                       | Medium 固定                                                          |

- **`l1Open`**(L1 だけでは決まらないタイルの数)= 型だけの盤から L1 を不動点まで回したとき、ドメインが 1 つに
  なっていないタイルの数(`SolveResult.stageOf` が 2 以上のタイルの数と同じ)。L1 で最初に止まった時点で、
  盤のどれだけが L2・L3 の推論の向こうにあるかを数える。16 は 8×8 の 64 枚の 4 分の 1(`HARD_MIN_L1_OPEN`、
  **初期値**)。
- **Hard を変えた理由**(§4「計画のリスク ④ の扱い」): L3 が要る一意な 8×8 の盤は census で 0.7% しかなく、
  「L3 が要る」を条件にすると Hard の約 3 割が同梱盤面へ落ちる(算術)。予算を緩める前にこの文書を直した。
  L3 が要る盤も Hard に入る(`l1Open` が 16 以上なら)。**段 2 のテストで実測**(`guarantee.test.ts` の
  「walk hard」行): 走査した Hard 300 面のうち L3 が要る盤は 12 面、`l1Open` は最小 16・中央値 22・最大 52。
  census の 8×8 で L3 が要る 7 本のうち 2 本は `l1Open` が 16 未満で、Hard に入らない。
- **帯の重なり**: 技法の段で見ると、Easy(L1)と Medium(L2)は重ならず、Medium は L3 の盤を入れない(推奨の
  とおり)。Hard は L2 の盤を含むので、段だけで見ると Medium と重なる — 違いは盤の大きさ(7×7 と 8×8)と
  `l1Open` の床である。Medium の `l1Open` は走査で最小 4・中央値 8・最大 33(Daily は最大 37)、Hard は中央値 22。
- 技法で全部決まらない盤(`stuck`)は、一意でも**出さない**(推測が要る盤は出さない — §12)。ただし**段 2 の
  テストで実測**では、census の 3,000 本で「一意なのに技法で決まらない」盤は 0 本だった(技法で決まらない盤は
  どれも 2 解以上)。
- `level` は「型だけの盤から始めて実際に何かを捨てた最も高い段」。L1 は盤の端がある限り必ず何かを捨てる
  (外へ向く向きがある)ので、どの盤も `level` は 1 以上になる。
- Bridges §7 と同じく、帯は**ソルバーの尺度**であり、人がどう感じるかを測ったものではない(§13)。L2 の見渡しの
  回数(`l2Rounds`)はティアの濃淡に使わない — L2 は 1 回の見渡しの除外をまとめて適用するので、段 2 の探索では
  技法で決まった L2 の盤のほとんど(8×8 の木 1,000 本のうち L2〜L3 で決まった 400 本中 378 本)が 1 回だった。
- **確かめたこと**(段 2 のテスト — §13): 走査した全盤面と同梱 72 面が、新しく回した技法ソルバーでそのティアの
  帯に入る(Easy は L1 で解け、Medium は L1 だけでは解けず L1〜L2 で解け、Hard は L1 だけでは 16 枚以上が残り
  L1〜L3 で解ける)。各ティアの通過率と fallback の率は §14。

## 6. Undo と Hint

### Undo

- **無料・回数の制限なし。**1 手 = 1 回の回転(時計回りでも反時計回りでも)。Undo はその回転を戻す。
- 履歴はセッションに持ち、**直近 5,000 手まで**(`UNDO_HISTORY_LIMIT`、初期値。Loop Puzzle §6 と同じ蓋の値。
  超えた分は古い方から落ちる)。1 手は「回したマスと、回す前の向き」(`game/session.ts` の `Move`)。**保存しない**
  — 再開時は空(§7)。Undo は Hint 回数を戻さない。完成した盤では使えない(§2)。`session.test.ts` が、両方向の
  回転を 1 段ずつ戻すこと・Hint 回数を戻さないこと・5,000 手で古い方から落ちることを確かめる。
- **Undo を作る理由**は 2 つ: タッチに反時計回りが無く、1 段戻すのにエルボ・T・端は 3 タップ(直線は
  1 タップ)かかる。隣のタイルを誤って回しても警告は出ない(答え合わせをしないので)— どのタイルを何回
  回したかをプレイヤーに覚えさせない。Bridges §9 の「循環は 1 段戻れない」と同じ形。

### Hint

無料・回数の制限なし・使った回数を数える(結果カードに事実として出す。コストにはしない)。**盤面には書き
込まない**(示すだけ。回すのはプレイヤー)。順に(`game/hint.ts` の `findHint`。セッションからは
`game/session.ts` の `askHint`):

1. **技法の段**: 技法ソルバーを**型だけの盤**から回し(§4。結果は盤ごとに一定)、その `order`(ドメインが 1 つに
   なった順 — L1 → L2 → L3 の推論の順)を先頭から見て、**今の向きが解の向きと違う最初のタイル**を示す。示すのは
   そのタイルと、**正しい向きの薄い図**。
2. **解の段**: 技法の段に候補が無い(=技法が全部を決められなかった盤で、決まらなかったタイルだけが解と違う)
   ときだけ、保存した解と今の向きが違うタイルを行優先で 1 枚示す。**出荷する盤面ではこの段に落ちない** — 出荷する
   盤は型だけの盤から技法で全タイルが決まる(§5)ので、未完成の盤には必ず `order` の中に解と違うタイルがある。
   **段 2 のテストで確かめた**: 崩した初期の向きから Hint だけで解き切れ、示すタイルは毎回いまの向きが解と違い、
   示す向きは毎回解と一致し、解の段に一度も落ちない — 同梱 72 面(`bundled.test.ts`、計 2,382 回の Hint)と、
   走査の各組の先頭 40 面ずつ計 160 面(`guarantee.test.ts`、5,304 回)。同じ 160 面に崩しの上からさらに無作為な
   回転を 30 回加えた盤からも同じ(5,378 回)。解の段は手で作った技法の結果(何も決めていない)を渡したときだけ
   出ることを `session.test.ts` が確かめる。
3. 完成した盤では Hint は出ない(§2)。

**Hint が読む盤**: 技法は型だけの盤から回すので、**プレイヤーの今の向きを前提に推論しない**。タイルロックが
無い(§3)ので、今の向きはプレイヤーの主張ではなく、Loop Puzzle §6 のように見えている印を前提として読めない
からである。示したタイルより前に `order` に並ぶタイルは、どれも今すでに解の向きを向いている(だから最初の
「違う」タイルなのである)— 示したタイルの向きを決める推論の足場は、盤の上に見えている。

**示さないもの**: Loop Puzzle §6 の第 1 段(解と違う印を先に示す)に当たる段は**持たない**。未完成の盤では
ほとんどのタイルが解と違い、それを並べて示すのは、作らないと決めた答え合わせになる。

**数え方**: 前の Hint のあと盤が変わっていない(回転も Undo もしていない)ときに押した Hint は、同じ印を
もう一度示すだけで**数えない**(Loop Puzzle §6)。セッションは最後の Hint を `lastHint` に持ち(保存しない)、
回転・Undo・Restart で空にする。Hint 回数は 10⁹ で止まる(保存の上限 — §7)。印(点線の輪と薄い図)と盤の下の 1 行は**次の 1 手(回転・
Undo・Restart・New Board)まで**残り、時間では消えない。1 行は何を示したかを言う — `pipeLinkHintNote`
「Turn the tile in the dotted ring until its pipes match the faint ones.」と、読み上げにだけ場所と向き
(`pipeLinkHintWhere`「Marked: row {row}, column {col}. Turn it to {pipes}.」)。**技法名(L1 / L2 / L3)は UI に
出さない。**解の段の Hint も**同じ見せ方・同じ文言**にした(Phase 3 の決定 — プレイヤーに求める操作が同じで、
出荷する盤では起きないので、文言を分けても手作りの盤でしか見えない。§15)。完成した盤では Hint のボタンは
押せない(`disabled`)。

**作らない**: 自動回転・答え合わせボタン・タイルロック・Hint の回数制限・Hint の広告解放(§12)。

## 7. 保存(中断と再開)

保存キーは次の **5 つ**(すべて `pn.` 接頭辞。import ゼロの葉 `storage/keys.ts` が宣言し、registry の
`storageKeys` はその `Object.values`。`src/app/gameKeys.test.ts` の自分の行は Phase 3 でこの 5 つに増やした)。
どれも `schemaVersion: 1`。

| キー           | 中身                                                                       |
| -------------- | -------------------------------------------------------------------------- |
| `pn.saveGame`  | 難易度モード(Free Play)の中断中の盤面(1 スロット。キーの葉 `game`)         |
| `pn.saveDaily` | デイリーの中断中の盤面(1 スロット。キーの葉 `dailyGame`)                   |
| `pn.stats`     | 統計(§8)                                                                   |
| `pn.flags`     | チュートリアル完了                                                         |
| `pn.prefs`     | 最後に選んだ難易度だけ(初期値 Easy。盤面の遊び方を変える設定は 1 つもない) |

**中断中の盤面のレコード**(v1。`game/session.ts` の `SessionRecord` — 段 2 で実装。`toRecord` が作り、
`fromRecord` が読む。保存層(Phase 3)が `schemaVersion` と `savedAt` を足す):

| フィールド       | 型・形                                                           |
| ---------------- | ---------------------------------------------------------------- |
| `mode`           | `'difficulty'` / `'daily'`                                       |
| `seed`           | 1〜200 文字                                                      |
| `difficulty`     | `'easy'` / `'medium'` / `'hard'`(デイリーは `'medium'`)          |
| `dailyDate`      | デイリーは `YYYY-MM-DD`、難易度モードは `null`                   |
| `width` `height` | 難易度のプリセットと一致                                         |
| `types`          | 1 マス 1 文字の行優先: `e` / `s` / `l` / `t`(§1。8×8 で 64 文字) |
| `source`         | 水源のマスの番号(0 〜 W×H − 1 の整数)                            |
| `solution`       | 解の向き。1 マス 1 桁(`0`〜`3`、直線は `0`〜`1`)                 |
| `initial`        | 初期の向き(Restart のため)。同じ形                               |
| `current`        | 今の向き。同じ形                                                 |
| `hintCount`      | 0〜10⁹ の整数                                                    |
| `elapsedSeconds` | 0〜10⁹ の整数                                                    |
| `schemaVersion`  | `1`(保存層)                                                      |
| `savedAt`        | 保存した時刻(ms、0〜10¹⁵ の整数。保存層。読むだけで使わない)     |

初期の向きは Restart のため、解は Hint の最後の段(§6)のために持つ。**Undo 履歴は持たない**(§6)。盤面と解を
そのまま持つので、生成器が版で変わっても中断中の盤面は生き残る。手の列ではなく向きを持つのは、どの向きの
組み合わせも回転の列で作れるからである。

- **どのスロットのレコードかを決めるのはキーである**(`gameSlotSchema(key, expectedMode)`、
  `parsed.mode === expectedMode`。`src/test/savedGameSlots.test.ts` と `storage/slots.test.ts` が強制する)。
- **スロットを置き換える前に確認する**(中断中と違う難易度を選んだとき)。
- **検証は 1 段の fail-closed で、すべてスキーマの `validate` の中**(盤の大きさに比例する仕事で終わる。
  バックアップの書き出し・復元もこれだけを通す — [architecture/backup.md](architecture/backup.md)「検証は各
  レコードの持ち主が行う」)。通らなければ `null` を返し、プレイヤーはゲームのホームに着く — **黙って新しい
  盤面を始めない**。`validate` は例外を投げない。
  - 形: JSON として読めない・`schemaVersion` が 1 でない・`mode` / `difficulty` が未知・`seed` が空 / 200 文字超
    / 文字列でない・日付と `mode` が合わない・デイリーが medium でない・幅と高さがプリセットと違う・`types` の
    長さが W×H でない / 未知の文字・`solution` / `initial` / `current` の長さが W×H でない / 型の周期の外の桁
    (直線に `2`・`3`)・`source` が盤の外・カウンタが範囲外か整数でない・キーとモードが合わない。
  - 中身(`fromRecord` → `game/serialize.ts` の `decodeParts` で読む。探索ではない): **解が、次数 3 以下・十字なし・盤の外へ管を出さない
    全域木**(=解の向きで `isSolved`)、`types` が解の各マスの管の数と形に一致(`types` は解の型の列そのもの —
    型と向きの組は §1 の表で読む)、`initial` と `current` が各マスの型の周期の中(=解の型の回転)、
    **`current` が完成していない**(完成した盤面は履歴であり、再開しない)。`initial` が完成していないこと・
    60% 以下であること(§4 手順 5)は**読み込みでは確かめない**(崩しの規則は生成の規則で、版で変わりうる。
    再開に要るのは初期の向きが回転で届く形であることだけ — `session.test.ts` が、1 枚だけ解と違う初期の向きの
    記録を読み込めることを確かめる)。
  - 保存層(Phase 3、`storage/schemas.ts` の `gameSlotSchema`)は、`schemaVersion` と `savedAt` を確かめ、
    デイリーの日付が**暦にある日**であること(`2026-02-30` を拒む — 共有の `asDateString` は綴りしか見ない)を足し、
    残りは同じ `fromRecord` で読む。読んだ結果から記録を作り直すので、記録が持っていた余分なフィールドは残らない。
    `storage/slots.test.ts` が、2 つのスロットの往復・他方のモードの記録の拒否・形と範囲の拒否(18 通り)・
    大きさ・型の列(十字 `+` を含む)・周期の外の桁・盤の外の水源・完成しない解・解のものでない型・完成済みの
    盤・60% を超える初期の向きの記録を読めること・今日でないデイリーの削除・バックアップの復元と書き出しが
    同じ拒否をすることを確かめる。
  - `session.test.ts` / `serialize.test.ts` が、往復(難易度とデイリー)と、上の拒否の 1 つ 1 つ(計 25 通り —
    未知のモード・空 / 長すぎる / 文字列でない seed・未知の難易度・日付とモードの食い違い・medium でないデイリー・
    形の悪い日付・幅と高さ・型の列の長さと未知の文字・水源が盤の外 / 整数でない・解が完成していない・解と型の
    食い違い・周期の外の桁・長さの違う向き・範囲外 / 整数でないカウンタ・完成済みの `current`)を確かめる。
  - **一意性は探索で証明し直さない**(§4 の「仕事量と上限」)。だからこのゲームには「スキーマは通るが開くと
    捨てる」記録(Bridges §10 の「残る穴」)が無い。
  - デイリーの日付が**今日の日付でない**(過去も未来も)ものは、保存層が読み込みで記録ごと捨てる(§8 の
    デイリー。Box Regions と同じ `dailyDate !== today`)。
- **読み捨てた記録はストレージから消さない**(既存の全ゲームと同じ。次にそのスロットに書くときに置き換わる。
  記録ごと消すのは今日でないデイリーだけ)。
- 背景へ回るとき、盤面の保存と未計上秒の計上を**同じ同期処理で**行う(既存ゲームと同じ)。保存の失敗で
  ゲームを止めない。他のゲームのキーには触れない。
- **ベータ中はスキーマを変えうる。**変えるときは黙って消さず、ホームの `WebBetaNotice` が先に告げる
  ([WEB_VERSION.md](WEB_VERSION.md)「保存データ」)。正式収録でスキーマを凍結する。

## 8. 統計と時計

- **プレイ中に時計も回した回数も表示しない。**経過時間は内部で記録し、結果カードと統計でだけ見せる。
  セッションは時計を読まない(持ち主から秒を受け取り、減る方向の値は無視する — Bridges §11)。時計は画面が
  見えている間だけ進む(`visibilityState` が `visible`)。
- **記録は経過秒だけ**。回した回数は記録しない(§3 の「手の数え方」— 比べられない)。
- `pn.stats`(v1):
  - `easy` / `medium` / `hard`(難易度モードだけ): プレイ回数(New Board と Restart。再開は数えない)/
    クリア数 / 合計秒 / 最短秒(未クリアは `null`)。
  - `daily`: プレイ回数 / 合計秒。**デイリーは `medium` に混ぜない**(Bridges §11 と同じ別の枠 — §15 の決定、
    **暫定 — オーナーの確認待ち**)。分けた数は後で足せるが、混ぜた数は後から分けられない。どちらの規則でも、
    正式収録でスキーマを凍結する前にそろえる。
  - `dailyTimes`: 達成した日 → その日の最短秒。日付の**集合**で、連続は数えない。読めない 1 日は捨て、ほかの
    日は残す(2,000 日まで)。
  - 累計プレイ時間は合計秒の和で、別に保存しない。
- **途中で盤面を替えても、それまでの時間は数える**(↻ の Restart / New Board は置き換わる盤の未計上の秒を先に
  入れてから、新しい盤の時計を 0 から始める — Bridges §11 / Loop Puzzle §10)。退出の同期は
  `useOnUnmount(syncActiveGame)` を 1 回([GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「アンマウントで計上する」)。
- **スコアは作らない。**自己ベストの更新は、更新したときだけ静かに示す(`BestDelta`)。順位・ストリーク・星・
  レベル番号は無い。

**モードとデイリー**(計画「モード」):

- **難易度モード**(Free Play): Easy / Medium / Hard。seed は `pipe-link-<difficulty>-<token>`(token は状態の層が
  渡す。Box Regions と同じ `newSeedToken` — Loop Puzzle §9)。同じ seed なら同じ盤面。
- **デイリー**: 1 日 1 問、毎日 Medium(曜日で当たり外れを作らない)。seed は `pipe-link-daily-<YYYY-MM-DD>`(端末の
  ローカル日付のみ。サーバー時刻もネットワークも使わない)。**今日の 1 問だけ** — 過去の日付には遡れず、一覧も
  入口も持たない。今日でない中断中のデイリーは次にゲームを開いたときにレコードごと捨てる。遊んでいる最中の
  盤面は日付が変わっても取り上げない(`docs/PRODUCT_PRINCIPLES.md`「デイリーは今日の 1 問」)。
- **Restart**(同じ盤面を初期の向きへ): 画面の盤面そのものを、初期の向き・Hint 0・時計 0・Undo 履歴なしで作り
  直す。**seed から作り直さず、探索も走らない**(同梱盤面へ落ちた盤でも同じ盤が戻る)。
- **ヘッダの ↻** は `RestartDialog`: 難易度モードは「Restart(同じ盤面を初期の向きへ)」と「New Board」の 2 択、
  デイリーは Restart だけ(`src/test/restartDialogWiring.test.ts` が形を決める)。
- **結果カード**の第一ボタンは**同じ盤面で再挑戦**(=初期の向きへの Restart)、第二が **New Board**(難易度
  モードだけ)。文言は Bridges に合わせる(§15 の決定、**暫定 — オーナーの確認待ち**。4 つ目の形を作らない)。
  結果カードは `ShareAction` を持ち、出すのは事実(盤の大きさ・経過秒・Hint の回数)だけで、称賛の語を使わない。
- 中断は難易度モード用・デイリー用の **2 スロットを独立して保持**する(§7)。最後に選んだ難易度は `pn.prefs`
  (初期値 Easy)。初回の Quick Rules の直後に始まる盤面もこの難易度。ただし難易度モードの中断中の盤面があれば
  (`pn.flags` だけが失われた場合)、新しい盤面で置き換えず、その盤面を再開する(Bridges §8)。

## 10. 演出とアクセシビリティ

- **アクセント 1 色**(琥珀 — ライト `#a5672c` / ダーク `#dba775`、Phase 1 で `src/ui/styles.css` に登録済み)。
  ゲームの CSS(`ui/pipe-link.css`、クラスは `pn-` 接頭辞)は `var(--accent)` 等の共通トークンだけを使う。
  アクセントの置き場所は**点灯した管**(完成で盤のほぼ全面 — 計画「Phase 1 の実施結果」)。光っていない管は
  `--ink-soft`。光った管は盤のタイル(カード地)の上に置き、アクセント色の文字を紙に直接置かない(ライトの
  紙の上で 4.03 — 計画「Phase 1 の実施結果」)。
- **点灯は色だけで伝えない**: 光っていない管は**中空の管**(輪郭だけ)、光った管は**満ちた管**(塗り)で描き、
  形でも分ける。水源は形の印(管の交点の上の、塗った丸と外側の輪の二重の印)で示す。
- **Hint の印**: 示したタイルに点線の輪と、正しい向きの薄い図(§6)。キーボードのフォーカスは実線の内側の輪で、
  Hint の点線の輪と形が違う。
- **描き方(Phase 3 の実装)**: タイル 1 枚 = `<button>` の中のインライン SVG(100 単位の正方形)。管は向き 0 で
  描き、SVG ごと CSS の `rotate()` で回す。各形を 2 回描く — 太い線の縁(`--pn-edge`)の上に線なしの芯
  (`--pn-core`)を重ね、重なった形を 1 本の管にする。光っていない管は縁 `--ink-soft`・芯 `--surface`(中空)、
  光った管は縁も芯も `--accent`(満ちた管)。腕は正方形の外まで伸ばし、管の口の縁が隣のタイルとの境に線を
  引かないようにした。ただしそれだけでは足りなかった: 1 マスが端数の px(式のままだと 360×640 の Easy で 59.3px、
  Hard で 38.1px)だと、タイルごとの SVG が端数の位置で切られ、隣どうしのにじみ(アンチエイリアス)が重なって
  管を横切る細い線(継ぎ目)が見えた(ライトでは光った管の上の明るい線と中空の管の中の灰色の線、ダークでは琥珀の
  上の暗い線 — レビューのスクリーンショット)。そこで `round()` のあるブラウザーでは、1 マスと盤の余白を整数の
  CSS px に切り下げる(`@supports (width: round(down, 1px, 1px)) and (height: 100svh)`、式は下の「盤の大きさの式」
  と同じ)。ヘッドレスの Chromium 1194 で、整数の 1 マスでは継ぎ目が消えた(1px の重ねと `crispEdges` では
  消えなかった — レビューの試行)。**継ぎ目が残りうる場所**: `round()` の無いブラウザー(Chromium 88 を含む。
  式のままの端数の 1 マスになる)と、装置の画素比が整数でない画面(整数の CSS px でも装置の画素では端数)。
  どちらも実機では見ていない(未検証)。端は中心に丸い蓋(半径 21)、ほかの型は継ぎ目の丸(半径 12)。
  水源の印は `--ink` の輪と点で、管とは別の層(回らない)。水源のタイルはいつも光っているので点はいつも琥珀の
  管の上にあり、ダークでは点(明るい `--ink`)と管の対比が約 1.7:1 しかなかった(レビューのスクリーンショットの
  画素の読み取り)。点に地の色(`--surface`)の縁取り(太さ 4、`paint-order: stroke`)を付けて管から離した
  (輪の内側の縁 28.5 に対して縁取りの外側は 12 で、輪には掛からない)。Hint の薄い図は `--accent-ring-soft` の芯と `--accent` の破線。CSS に色の
  直書きは無い(共通トークンだけ)。
- **盤の大きさの式**(`ui/pipe-link.css`): 1 マス = clamp(34px, min((幅 − 26px) ÷ (列 + 0.4), (高さ − 320px −
  下の安全域) ÷ (行 + 0.4)), 76px)。320px は Bridges の同じ枠(上のバー・Undo / Hint の列・注記 2 行・余白・
  Web の広告の予約 116px)の値をそのまま使った。下限 34px は Box Regions / Shape Regions の 1 マスの下限で、
  それ未満にはしない(横持ちはスクロールする)。`round()` のあるブラウザーでは、この 1 マスと余白(1 マスの

  悪くならない。測った値は §1 と §14。
- **回転の演出**: 状態はタップで即座に変わる。表示角は**累積で持ち**(270° → 0° で逆回りさせない)、演出は

  点灯も演出なしで即時、完成の塗りも出ず、結果カードも即時。連続再描画をしない(時計は再描画しない)。
- 完成の一拍と結果カードまでは既存ゲームと同じ(`useResultReveal`)。
- **読み上げ**: タイルは 1 枚 1 `<button>`。行・列・型・今つながっている方向(管を出している方向)・点灯か・
  水源か・Hint の印かを読み上げる(文言は Phase 3)。盤は `role="group"` で「盤面、W × H」。回転のたびに、
  読み上げにだけ新しい向きを知らせる(`aria-live="polite"`。画面には出さない)。Undo も同じ文で戻した後の向きを
  知らせる。
- **大きさ**: 1 マス = min(幅の取り分, 高さの取り分)。画面高は `svh` で測り(`@supports (height: 100svh)` で
  選び分ける — Bridges §13 の教訓)、横持ちでつぶれない下限を置く(Loop Puzzle §13・Bridges §13)。8×8 の

- **回転の表示角**は盤(`PipeBoard.tsx`)がタイルごとに累積で持ち、直前の回転の向き(`spin`)の方へ回す

- **点灯の演出を時計に見せない**(水が時間とともに流れ出す表現をしない — §12)。点灯は回転の結果で、時間では

### 比較対象との対応

この節だけが外の製品名を書く([BRAND.md](BRAND.md)「自社タイトルと比較対象の名前」)。アプリ内・ストア文言・
i18n には書かない。**どの記述も筆者の記憶によるもので、出典で確かめていない(確認日なし — この作業の環境は
ネットワーク不可。2026-10-22 時点で未確認)。**

- **形式**: タイルを回して 1 本の水源から全タイルをつなぐ、一般に「パイプを回してつなぐ」と呼ばれる形式。
  Simon Tatham 氏の MIT ライセンスのパズル集(Portable Puzzle Collection)の **Net** が同じ形式である(記憶による)。
  - **同じにしたもの**: 型(端・直線・エルボ・T)、全タイルが水源につながって完成、一意解の出題、水源が中央
    寄り(記憶では Net の水源は中央)。
  - **変えたもの**(記憶による Net の形との比較): Net には盤の端の折り返しの選択肢と、タイル間の障壁
    (barrier)の選択肢と、タイルのロック(印を付けて回らなくする)がある — Pipe Link はどれも持たない
    (§12・§15)。Net の操作の割り当て(記憶では左右のクリックで回す向きが分かれ、中ボタンでロック)は写して
    いない — Pipe Link は左クリック・タップが時計回りで、右クリックが反時計回り(§3。Minesweeper / Nonogram の
    右クリックの契約に合わせた)。難易度を要る推論の段(L1〜L3)で分けるのは Pipe Link の作り方で、Net の
    難易度の作り方は確かめていない。
  - **複製していないこと**: Net のコード・盤面・画面・配色は見ていないし写していない(MIT でも写さない —
    計画のリスク ③)。生成器・ソルバーは自前(§4)。
- **Pipe Mania**(一般にパイプを置いて流れ出す水を導く形式として知られる製品。記憶による): 時間とともに
  流れ出す水の前に、列から来る部品を**置いていく**遊びで、Pipe Link とは**別の遊び**である。Pipe Link は部品を
  置かず(全マスに最初からある)、回すだけで、時間制限・部品の列・流れ出す水を持たない。点灯の演出を時計に
  見せない(§10)。
- **題の確認**: 冒頭の「題の確認」— 未確認、製品オーナーの確認待ち。

### 関連する既存ゲームとの違い

論理の棚の 16 本目で、推論の型が [Bridges](BRIDGES_RULES.md)・[Loop Puzzle](LOOP_PUZZLE_RULES.md) と**重なる**。
それを隠さずに書く:

| ゲーム        | 盤に書くもの             | 手がかり                     | 解の形                                 | 操作                                     | Hint の根拠                                    |
| ------------- | ------------------------ | ---------------------------- | -------------------------------------- | ---------------------------------------- | ---------------------------------------------- |
| **Pipe Link** | **タイルの向き**(全マス) | **タイルの形そのもの**と水源 | **全マスを結ぶ木**(閉路なし・分岐あり) | タップで時計回り・右クリックで反時計回り | 型だけの盤からの技法 L1→L2→L3 の順(§6)         |
| Loop Puzzle   | 格子の辺の線と ×         | マスの数字(0〜3)             | 1 本の閉じたループ(分岐なし)           | 辺のタップで 空 → 線 → × → 空            | 誤りの印 → 技法 T1→T3 → 解の 1 辺(§6)          |
| Bridges       | 島の間の橋(0〜2 本)      | 島の数字(1〜8)               | 全島がつながるネットワーク(ループ可)   | 島を選んで相手の島をタップ               | 多すぎる辺 → 1 島で確かめる手 → 技法(§9)       |
| Number Path   | マスを通る 1 本の道      | 番号のマス                   | 全マスを番号順に通る一筆書き(分岐なし) | なぞる                                   | ([NUMBER_PATH_RULES.md](NUMBER_PATH_RULES.md)) |

- **推論の重なり**: L2 の「閉路を作る向きを捨てる」は Loop Puzzle T1 の「ループの規則」(鎖の両端を結ぶ辺)と、
  L2 の「閉じた集まりを作る向きを捨てる」は Bridges T3 の「閉じたグループの回避」と同じ型の推論である。L3 の
  「仮定 1 回」は Loop Puzzle T3・Bridges T4 と同じ型。L1 の噛み合わせは、Loop Puzzle の点の数え(線 2 本の点)や
  Bridges の数える(T1)に相当する、局所の整合の推論である。
- **違い**: Pipe Link が書くのは**向き**で、手がかりは**タイルの形そのもの**(数字が無い)、解は**木**(Loop
  Puzzle は閉路そのもの、Bridges はループを許す)。プレイヤーは線を引かず、決まった部品を回すだけである。
- 保存・コード・ルールはどのゲームとも共有しない(`games/A` は `games/B` を import しない —
  `importBoundaries.test.ts`。`game/rng.ts` は Bridges からの写し)。

## 13. 検証の範囲

**段 1 の結果(2026-10-22)**: `src/games/pipe-link/game/` に `tiles.ts`(型・向き・回転)・`board.ts`(盤のモデル・
点灯・行き止まり・勝利判定)・`solver.ts`(技法 L1〜L3 の伝播ソルバーと、解の個数の数え上げ。テストと説明のために L1 の不動点と L2 の 1 回の見渡しを `l1Fixpoint` / `l2Eliminations` として出す)・`rng.ts`
(Bridges からの写し。段 2 の生成器が使う)と、テストだけが使う `test-helpers.ts` を置いた。テストの件数と
結果は §14 の末尾。

**段 1 のテストで確かめたこと**(`pnpm exec vitest run src/games/pipe-link` のたびに走る):

- **回転**(`tiles.test.ts`): 型ごとの周期(直線 2・ほか 4 — 時計回りを周期の回数で元に戻り、それより少ない
  回数では戻らない)、反時計回り = 時計回りの逆(全型・全向き)、管の集合の時計回りの写像(上 → 右 → 下 →
  左)、向き 0 の管の集合、型ごとに向きと管の集合が 1 対 1、管の集合から型と向きへの逆引き(1〜3 本の 14 通りの
  集合すべて。0 本と 4 本は型にならない)。
- **点灯と勝利判定**(`board.test.ts`、手で作った盤): 水源から届くタイルだけが点灯すること、片側だけが向けた
  管ではつながらないこと、盤の外へ向いた管、行き止まりの数え方、閉路のある配置・行き止まりのある全点灯の
  配置が `isSolved` でないこと(口の総数が 2 × (n − 1) でない手作りの盤)、盤のモデルの拒否(大きさ・型の列の
  長さ・水源の位置)。
- **全点灯 ⇔ `isSolved`(全回転の総当たり)**(`exhaustive.test.ts`): 2×2・3×2・2×3 の次数 3 以下の全域木
  すべてについて、水源を全マスに置き、型の取りうる向きの**全部の組み合わせ**で「全点灯」と `isSolved` が一致する
  こと。3×3 は 176 本の木のうち 10 本(列挙の順で 0・20・40・…・160・175 番目)について、水源を中央に置いて同じ
  こと。どの木でも口の総数は 2 × (n − 1) で、全配置のうち `isSolved` の数が下の総当たりの解の数と一致する。
- **技法の単体**(`solver.test.ts`、手で作った小さな盤): L1 が盤の端の向きを捨てること・決まった辺を隣へ両側で
  渡すこと・空のドメインを矛盾として返すこと、L1 だけで解ける盤で `level` 1。L2 の閉路だけで進む盤と、孤立だけで
  進む盤(どちらも L1 では止まる 4×4)で、その理由の除外だけが出て、どれも L1 の後になお取りえた向きであること。
  1 ホップが要る例(2×2 の端 4 枚 — 向かい合う 2 枚の閉じた組)。L2 が要る盤は L1 で止まり `level` 2 で解けること。

  全マスを並べ、`stageOf` が順に下がらず 1 で始まり 3 で終わること。2 解の盤 2 つ(4×3 と、L3 を使った後で
  止まる 4×4)が `stuck` で、両方の解がドメインに残ること(健全)。L2 の除外がどの解も消さないこと(例の盤
  すべてで総当たりと照合)。仕事量の上限で `aborted`(上限を 1 歩より多く越えない)。

  解の無い盤(2×2 のエルボ 4 枚)で 0。**ノード上限での正直さ**: 2 解の盤で、上限なしに要ったノード数 N を上限に
  すると 2 解・`complete: true`、N − 1 にすると `complete: false`・**1 解だけ見つけた状態**で `isUnique` は偽(見つけた 1 解は一意の
  証明ではない)、上限 1 では 0 解・`complete: false` で、「解なし」とも読まない。仕事量の予算が尽きると `complete: false`。

  型の並びについて、**ソルバーとは別に書いた総当たり**(`test-helpers.ts`。自前の管の表で、行優先に向きを置き、
  盤の端と左・上の隣との噛み合わせだけで刈り、葉で自前の幅優先探索で連結と木を確かめる。`tiles.ts` /
  `board.ts` / `solver.ts` を使わない)の解と、`countSolutions` の数(2 まで)・`complete`・見つけた解が一致する
  こと。技法ソルバーの結論 — `solved` ならその配置が総当たりの唯一の解、`stuck` ならどの解もドメインの中に
  残っていること(健全性)— が総当たりと矛盾しないこと。`contradiction` / `aborted` は 1 つも出ないこと。全数の
  数(木の数・段ごとの数・ノードと仕事量の最大)は §14 で、テストがその数を固定する(4×4 は 16 に分けた
  各件が自分の分の段ごとの数を固定し、その和が §14 の行になることを定数だけで確かめる — どの件もほかの件が
  埋めた集計を読まないので、1 件だけ `-t` で走らせても順を入れ替えても同じ結果になる。4×4 の `[pipe-link]` の
  行と census の行は、全部の件が走ったときだけ出力する)。
- **決定性**: 例の盤で技法ソルバーと数え上げを 2 回回して、結果(`order` まで)が同じになること。
