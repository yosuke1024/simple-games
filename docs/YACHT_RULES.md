# Yacht — 正式ゲームルール

このドキュメントが Yacht の仕様の正本である。実装
(`apps/simple-games/src/games/yacht/`)、テスト、Quick Rules はここに従う。
コードはここへ `§n` で言及する。挙動を変えるときは、同じコミットでこの文書を直す。

ブランド原則([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md))はこの文書より上位にある。

ゲーム ID は `yacht`、i18n キーの接頭辞は `yacht`、保存キーの接頭辞は `yt.` である。
Web 版の先行公開(ベータ)タイトルで、アプリには正式収録していない
([WEB_VERSION.md](WEB_VERSION.md)「先行公開(ベータ)」)。

## 1. 用具と対局者

- サイコロ 5 個(`game/types.ts` の `DICE_COUNT`)。目は 1〜6。
- 採点表は 12 欄(§3)、対局者ごとに 1 枚。
- **対戦相手は CPU 1 つだけである。あなたが先攻で、1 欄ずつ交互に手番を取る**
  (12 手番ずつ、合計 24 手番でゲームが終わる)。ローカル対人戦もオンライン対戦もない
  (§11)。
- **先攻は常にあなた。** 選択肢を用意しない: Yacht では両者の 12 手番が互いの盤面に
  干渉せず、後攻が得られる情報は最終手番での相手の合計だけで、CPU はそれを使わない
  ("そのために作らない機能" — Built by subtraction)。だから先後を選ぶ画面もない。
- 盤面(サイコロと採点表)に翻訳の要る文字は置かない。目は点(ピップ)で描き、
  点数は ASCII の数字で書く。欄の名前だけが言語ごとに訳される。

## 2. 一手の解決(手番の流れ)

手番を持つのはプレイヤーか CPU かのどちらか一方だけで(`toMove`、§1)、流れそのものは
どちらが持っていても同じである。

1. **最初の 1 投は必ず振る。** 振るまで採点表は押せない(`rollsUsed === 0` の間、
   欄はすべて無効)。1 投目は 5 個すべてを振る — キープは前の手番から持ち越さない。
2. 1 投目・2 投目のあと、サイコロをタップすると**キープ**になる(もう一度で解除)。
   次の投擲では、キープしていないサイコロだけを振り直す。
3. **1 手番に振れるのは 3 回まで**(`ROLLS_PER_TURN`)。3 投目のあとは振れない。
   3 投目のあとはキープの切り替えもできない — 次に振ることがないので、キープには
   意味がない(`toggleHold` は null を返す)。
4. **5 個すべてをキープしているときは振れない**(振るものがない)。
5. 手番を終えるのは、**未使用の欄を 1 つ選ぶ**ことだけである。条件を満たさない欄を
   選んでもよく、その欄は 0 点で埋まる。欄は 1 回しか使えない。
6. 欄を選ぶとキープはすべて解除され、次の手番——もう一方の対局者の手番——が
   1 投目から始まる。
7. **CPU の手番は 1 拍ごとに 1 歩ずつ進む**(`applyCpuStep`、`CPU_DELAY_MS` = 450ms):
   投げる・キープをまとめて決める・投げる・キープ・投げる・欄を選ぶ、と 3〜7 拍
   かけて進み、連続する決断が一度に見えることはない(§5、
   [GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「CPU 探索」)。
8. 両方の採点表が 12 欄埋まった時点でゲームは終わる(`status === 'finished'`)。
   状態も手番も、保存された値ではなく両方の採点表から導出する
   (`turnsPlayed`・`toMove`・`statusOf`)。

## 3. 採点

Yacht の伝統的な 12 欄。**上段ボーナスは置かない**(§11)。プレイヤーと CPU、
どちらの採点表もこの表に従い、それぞれ独立に 12 欄を埋める。

| 欄(id)                            | 条件                         | 点                     |
| --------------------------------- | ---------------------------- | ---------------------- |
| Ones〜Sixes(`ones`〜`sixes`)      | なし                         | その目のサイコロの合計 |
| Full House(`fullHouse`)           | ちょうど 3 個 + 2 個(目は別) | 5 個の合計             |
| Four of a Kind(`fourOfAKind`)     | 同じ目が 4 個以上            | その目 × 4             |
| Little Straight(`littleStraight`) | 1-2-3-4-5                    | 30                     |
| Big Straight(`bigStraight`)       | 2-3-4-5-6                    | 30                     |
| Choice(`choice`)                  | なし                         | 5 個の合計             |
| Yacht(`yacht`)                    | 5 個すべて同じ目             | 50                     |

- 条件を満たさない欄は 0 点。
- **境界**: 5 個同じ目は Four of a Kind の条件を満たす(その目 × 4、5 個目は数えない)。
  **Full House は 5 個同じ目では成立しない**(「3 個 + 2 個」は別の 2 つの目のこと)。
- 一方の採点表の合計は 12 欄の和。欄ごとの最大は 5 / 10 / 15 / 20 / 25 / 30 / 28 /
  24 / 30 / 30 / 30 / 50 で、**片方の採点表の最大合計は 297**(`MAX_TOTAL`。欄ごとに
  別の手番で取るので、欄ごとの最大の和がそのまま最大合計になる — `engine.test.ts`
  が全出目の列挙で確かめる)。プレイヤーと CPU、双方の採点表に同じ上限が独立に
  あてはまる。着手時の計画書(`docs/plans/2026-09-27-…`)は「最大 318」と書いていたが、
  この表の採点からは 318 は出ない。正はこの文書の 297 である。
- 採点は `game/engine.ts` の `scoreFor(category, dice)` だけが決める。表示と確定は
  常にこの 1 関数を通る: 未使用欄の「今の目で入る点」の先読み(§6)も、CPU の探索
  (§5)も、確定した点も、すべて同じ呼び出しである。

## 4. 出目

- 各投擲の目は `createRng(`${seed}:roll:${rollIndex}`)` から決める。1 投ごとに
  乱数を 5 回引き、`Math.floor(r * 6) + 1` を位置 0〜4 に順に割り当て、**キープして
  いない位置にだけ**当てる(キープした位置は元の目のまま)。プレイヤーの投擲でも
  CPU の投擲でも、この関数は同じである——投げているのが誰かは出目に関係しない。
- 5 個ぶんは**キープの有無にかかわらず毎回すべて引く**。だから、ある投擲の各位置の
  候補の目はシードと `rollIndex` だけで決まり、キープの仕方によって列がずれない。
- `rollIndex` は**プレイヤー・CPU どちらの投擲でも** +1 され、ゲームの間戻らない
  (両者の手番をまたいだ、対局全体を通しての番号)。次に来る出目の半分を表す
  (§9 の検証はこれを使う)。
- シードはゲームごとに新しい: `yacht-${token}`(`newSeedToken` は時刻と
  `Math.random` から作る)。同じシードなら同じ出目——`game/compatibility.test.ts`
  が 2 つのシードの最初の 3 投を固定する。同じシードは CPU の応手も固定する(§5)。
- 物理エンジンは使わない。サイコロは転がる絵であって、転がり方は結果に関係しない。

## 5. CPU

CPU は探索木も難易度の段階も持たない、決定的な「1 手先の期待値」計算である
(`game/cpu.ts` の `chooseCpuAction`)。盤サイズという別の遊びの選択肢を持つ
Dots and Boxes([DOTS_AND_BOXES_RULES.md](DOTS_AND_BOXES_RULES.md)§4・§11)と違い、
Yacht には難易度以外に差を作れる次元がなく、サイコロの出目そのものが十分な分散を
持ち込む——だから強さは 1 段階だけで、CPU は**自分の採点表しか見ない**(プレイヤーの
採点表を読んでも、最後の 1 手を除いて何も変わらない、§1)。

### 5.1 後悔ベースライン

ある欄を今の出目で確定させることの価値は、生の点数ではなく**ベースラインとの差**
(`scoreFor(category, dice) - BASELINE[category]`)で測る。ベースラインは「その欄に
平均的な 1 手を費やしたときの見込み値」——上段はその目 × 2.1(3 投のチェイスで
その目が集まる平均的な数)、他は 3 投の大まかな平均である。

| 欄(id)           | ベースライン |
| ---------------- | ------------ |
| `ones`           | 2.1          |
| `twos`           | 4.2          |
| `threes`         | 6.3          |
| `fours`          | 8.4          |
| `fives`          | 10.5         |
| `sixes`          | 12.6         |
| `fullHouse`      | 8            |
| `fourOfAKind`    | 6            |
| `littleStraight` | 9            |
| `bigStraight`    | 9            |
| `choice`         | 22           |
| `yacht`          | 2.5          |

Ones で 0 点を取ることは 2.1 点の損、Sixes で 0 点を取ることは 12.6 点の損——だから
外れた手番は最も損の小さい欄に捨てる。逆に、同じ 16 点でも Fours(16 − 8.4 = 7.6)
より Four of a Kind(16 − 6 = 10)の方が高く評価される: Fours の箱は大きな出目が
出たときのために取っておく方が得、という意図した振る舞いである。

### 5.2 immediate と一手先の期待値

- **`immediate(dice)`** — 開いている自分の欄のうち、上のベースライン差が最大の欄
  (同点は `CATEGORIES` の並び順で先の欄)。
- サイコロは**昇順にソートした多重集合**として扱う: 5 個の出目の組み合わせは
  ちょうど 252 通りあり、モジュール読み込み時に 1 度だけ列挙してインデックスを
  振る。`k = 0..5` 個を振ったときの出目(と確率 `k! / Π count_f! / 6^k`)も同様に
  1 度だけ列挙する。
- ある状態 `D` に対する**キープの選び方 `K`**は、5 個の位置の部分集合(最大 32
  通り)を、キープする値の多重集合で重複排除したもの——`K = D`(全部キープ = 振ら
  ない)と `K = ∅` も候補に含む。
- **`E1(D)`**(残り 1 投): `K` を選んで残りを振ったときの `immediate` の期待値の
  最大——`max_K Σ_o P(o)・immediate(K ∪ o)`。
- **`E2(D)`**(残り 2 投): 同じ形で 1 段深く——`max_K Σ_o P(o)・E1(K ∪ o)`。
- `immediate` と `E1` は 1 回の `chooseCpuAction` 呼び出しの中で、252 状態ぶんの
  配列に**遅延メモ化**する(開いている欄はその手番の途中で変わらないので、呼び出し
  をまたいで使い回すことはしない)。

### 5.3 決定

`rollsUsed`(その手番で使った投数)で分岐する:

- **0** → 必ず振る(1 投目は義務、§2)。
- **3** → 必ず欄を選ぶ。`immediate(dice)` の argmax の欄を取る。
- **1 か 2** → `stop = immediate(dice)` と、`K ≠ D`(全部キープは「振らない」ことに
  なるので除く)の中で期待値最大の `best`(`rollsUsed === 1` なら `E2` の項、
  `2` なら `E1` の項で比較)を比べる:
  - `stop.value ≥ best.value` → 今すぐ欄を選ぶ(`stop` の欄)。
  - そうでなく、今の `held` がすでに `best` のキープと同じ位置なら → 振る。
  - そうでなければ → `best` のキープに**一度で**揃える(`setHolds`、§2)。
- 同点は、`immediate` は `CATEGORIES` の並びで先の欄、`best` のキープはより多く
  キープする方、それでも同点なら先に見つかった方を選ぶ。
- キープの位置は、サイコロを左から順に見て、まだ必要なその目のサイコロを先着順に
  キープする形で一意に決める(`maskFor`)。

### 5.4 決定性と仕事量

- **乱数は使わない。** 同じ入力は常に同じ手を返す——`game/compatibility.test.ts` が
  1 局まるごとの CPU の採点表を固定する。
- **仕事量は有界である。** `cpuCost.work` が、`immediate` の評価 1 回と、期待値の
  和に加えた項 1 つごとに増える(`game/cpu.test.ts` の門)。半分埋まった採点表・
  252 状態すべて・`rollsUsed` の 3 通りで測った最悪値は **256,034**(上限
  1,000,000 の四分の一程度)、1 回あたり平均 9ms 弱——450ms の「間」に十分収まる
  (壁時計は記録するだけで、門にはしない。docs/SUDOKU_RULES.md §7 と同じ規律)。
- 探索はプレイヤーの着手ではなく CPU 自身の手番のタイマー(`CPU_DELAY_MS`)の中で
  同期的に走る([GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「CPU 探索」)。

## 6. 助けの形

- **Undo も Hint も作らない。** 振った目は情報であり、欄の選択は決断である。
  戻せば次の出目を覗くことになり、Hint は決断を代わりにすることになる。
- **振り直し 3 回と、未使用欄の先読み表示がこのゲームの助けの形である**(§10)。
  「今の目ならこの欄は何点か」は計算の手間であって判断ではないので、自分の手番の
  間、自分の採点表の全欄に常に出す。どの欄を選ぶべきかは示さない。CPU の手番では
  誰の欄にも先読みは出ない——押せるものではないので、計算の手間を肩代わりする
  相手がいない。
- 広告視聴や課金による振り直しは作らない([ADS_POLICY.md](ADS_POLICY.md))。

## 7. スコアと統計

- スコアは自分の採点表 12 欄の合計(§3)。
- 統計(`yt.stats` v2)は全体で 1 組: `played`(始めたゲーム数)・`completed`
  (両方の採点表が 12 欄埋まったゲーム数)・`bestScore`(完了したゲームの自分の
  最高点、無ければ null)・`totalScore`(完了したゲームの自分の合計点の和。平均の
  分子)・`totalPlaySeconds`・**`wins` / `losses` / `draws`**(完了したゲームの
  結果の内訳)。
  - v1(CPU 導入前の一人用の記録)から移行したレコードは `wins` / `losses` /
    `draws` が 0 のまま——それらの記録には対戦相手がいなかったので、勝敗が付いて
    いない。`completed`・`totalScore`・`bestScore` はそのまま引き継ぐので、平均と
    自己ベストは失われない。したがって `completed` が
    `wins + losses + draws` より大きい記録がありうる——それは移行前の記録の分だけ
    である。
- 平均点は `totalScore / completed`(四捨五入)。完了が 0 なら出さない。
- ストリークは数えないし表示しない。
- 途中のゲームを放棄して新しく始めた場合、プレイ時間だけを計上する(`played` には
  始めた時点で数えている)。点数も勝敗も計上しない——途中の対局は結果ではない。
- 結果カードは両者の合計と自己ベストの一言だけを出す(§10)。ベストとの差
  (`BestDelta`)は出してよいが、目標や残りの点として出さない。
- プレイ時間は逐次計上(bookedRef 方式、Connect Four §7 と同じ)。
- 両方の採点表が 12 欄埋まってゲームが終わったとき、ストアレビューの条件
  (`recordGameCompleted()`)に 1 回数える。

## 8. 中断と再開

- **途中保存する。** 保存して開き直したゲームは、保存した瞬間と同じである。
- 保存スロットは 1 つ(`yt.saveGame` v2): `seed` / `rollIndex` / `dice`(5 個、
  1..6)/ `held`(5 個)/ `rollsUsed`(0..3)/ `scores`(プレイヤーの 12 欄、整数
  または null)/ **`cpuScores`(CPU の 12 欄、同じ形)**/ `elapsedSeconds` /
  `savedAt`。手番数・終局・双方の合計は 2 枚の採点表から導出するので保存しない。
  `dice` / `held` / `rollsUsed` は「今どちらの手番か」に関わらず 1 組だけ——
  テーブルの上に今ある状態であって、席の持ち物ではない(`game/session.ts`)。
- **v1(CPU 導入前の一人用のシート)はそのまま読み捨てる。移行はしない。** v1 の
  保存は対局ではなく一人用の途中経過であり、対局として再開できるものではない
  (`cpuScores` が存在しない)。一人用の形が Web 版の先行公開に載っていた期間は
  長くても 1 日(収録は 2026-09-27、同日に対 CPU へ変更)なので、v1 の保存を読み
  捨てても失われるのは途中経過だけで、完了した記録(`yt.stats`)は §7 のとおり残る。
- キープを切り替えるたび、振るたび、欄を選ぶたびに保存する——手番がプレイヤーの
  ものでも CPU のものでも同じである。
- **検証は fail-closed**。次のどれかに当たる保存は読み捨てて、ホームへ戻る
  (勝手に新しい対局を始めない):
  - 形が合わない(配列の長さ・型・範囲。`scores` と `cpuScores` の両方に適用)。
  - `rollsUsed` が 0 なのにキープがある(キープは 1 投目のあとにしか生まれない)。
  - どちらかの採点表の欄の値が、その欄が取りうる値ではない(どの出目からも
    生まれない点。`isPossibleScore` が 252 通りの出目の組み合わせを列挙して判定
    する)。
  - **2 枚の採点表が噛み合っていない**: プレイヤーは常に先攻で 1 欄ずつ交互だから、
    埋まった欄の数はプレイヤーが CPU と同じか、ちょうど 1 つ多いかのどちらかで
    なければならない(§1)。CPU の方が多い、あるいはプレイヤーが 2 つ以上多いのは、
    プレイから生まれない。
  - `rollIndex` が、両方の採点表を合わせた埋まった欄の数と今の手番の投数から
    説明できない(1 欄につき 1〜3 投なので、
    `双方の埋まった欄の合計 + rollsUsed ≤ rollIndex ≤ 3 × 双方の埋まった欄の合計 + rollsUsed`)。
    `rollIndex` は以後の出目の半分(§4)なので、食い違う保存はプレイから生まれない。
  - **両方の採点表が埋まっている**(終局済みのゲームは戻る先ではない — 次の対局は
    新しく始まる)。
- `rollsUsed` が 0 のときの `dice` は前の手番の目のまま残っているが、画面には
  出さない(§10)。値は 1..6 であれば何でもよい。
- 起動時の再開は Connect Four §8 と同じ: ホーム画面ショートカットから開いたとき
  だけ、保存があれば直接ゲーム画面を開く(issue #113)。Quick Rules を見ていない
  起動では、先に Quick Rules を出す。

## 9. Quick Rules(アプリ内チュートリアル)

3 ステップ・図中心・各 1〜2 文(初回起動時に表示、以後はホームから):

1. 5 個を振って、残したいサイコロをタップする(もう一度で戻す)。
2. 残さなかったサイコロを振り直す。1 手番に 3 回まで振れる。
3. 空いている欄を 1 つ選んで点を入れ、手番を終える。CPU と 12 手番ずつ、合計が
   高いほうの勝ち。

図はサイコロの絵と数字だけで描く(翻訳の要る文字を置かない)。
初回に最後まで進むと、そのまま最初の対局が始まる(保存中の対局があれば
それを再開し、黙って置き換えない)。ガイドを公開するまで「詳しく見る」は出さない
(`src/ui/landing.ts`)。

## 10. 演出とアクセシビリティ

- 画面は上から: 上部バー(戻る・「手番 n / 12」・自分の合計・新しい対局)、サイコロ列
  (5 個の大きなボタン)、Roll ボタン(残り投数を併記)、採点表(2 列 × 6 行の
  ボタン。左列が Ones〜Sixes、右列が Full House〜Yacht)。**採点表の各欄は
  「あなた・CPU」の 2 つの数字を持つ**——見出し行「あなた ・ CPU」を列の上に
  1 度だけ置き(高さ予算に約 20px 追加)、CPU の数字は確定した点だけを示して押せ
  ない。**360×640 でスクロールなしに収める**(Web 版の広告アンカー用の 116px の
  予約と、見出し行の追加を含めて)。高さ 600px 未満では採点表の行を詰め、320×568
  でも収める。上部バーの「新しい対局」とホームの「新しい対局」は、途中の対局を
  置き換える前に確認する。
- **Roll ボタンは CPU の手番の間、手番の案内を兼ねる。** CPU が着手している間は
  「CPU の番…」を表示して無効になり、プレイヤーの手番が戻るとボタンに戻る。
- **CPU の手番の間、サイコロはボタンのまま CPU の出目とキープを映すが、押せない。**
  投げる・キープする・欄を選ぶという CPU の一歩ずつが、プレイヤーの手番と同じ
  見た目で 1 拍ごとに進む(§2、§5)。
- **時計を出さない。** 経過時間は統計にだけ残る。
- サイコロはボタンで、「サイコロ 3: 5、キープ中」のように位置・目・キープを
  読み上げる。キープは `aria-pressed` と、**持ち上げ + 枠**の 2 つで示す(色だけに
  頼らない)。1 投目の前のサイコロは目を描かず、無効にする。CPU の手番の間は
  読み上げの内容は同じだが、操作はできない。
- 自分の手番の間、未使用の自分の欄は、振ったあと「今の目で入る点」を**淡く先読み**
  して表示し、押せる。使用済みの欄(自分のものでも CPU のものでも)は確定点を
  濃く表示し、押せない。1 投目の前は未使用欄に点を出さない。CPU の手番の間、
  自分の欄にも先読みは出さない——今動かせるのは CPU の手であって、自分の手では
  ない。
- **欄が埋まった側に、600ms のフラッシュを 1 回だけ出す。** キーは両方の採点表を
  合わせた埋まった欄数——一度に埋まる欄は 1 つだけなので必ず 1 増え、同じ手番の
  再描画で繰り返さない。Reduced Motion では出さない(即時表示ではなく、フラッシュ
  そのものを出さない)。
- 出目のアニメーションは Ludo §12 と同じ: 振り直したサイコロだけが 220ms 以内の
  CSS で 1 回転がる(`rollIndex` をキーにした 1 回。再描画では繰り返さない)。
  プレイヤーの投擲でも CPU の投擲でも同じ見た目である。Reduced Motion(アプリ設定
  または OS)では出さず、目はすぐに出ている。粒子も画面揺れもない。
- **終局から結果カードが出るまでに約 1 秒置く**(`ui/useResultReveal.ts`)。
  埋まった採点表を見る時間であり、その間に押せるものはない。Reduced Motion では
  即時。結果カードは「勝ち」「負け」「引き分け」のいずれかと、両者の合計、自分の
  自己ベストを出す(§7)。
- キーボード(issue #93、タップと同じハンドラーへのアダプター): `1`〜`5` で
  サイコロのキープ切り替え、`R` で振る。欄はボタンなので Tab と Enter / Space で
  選べる。修飾キー付き・キーリピートは無視する。ダイアログの間、および CPU の
  手番の間は何もしない(対応するボタンが無効なので、操作は自然に無視される)。
- 効果音は既存の合成音(`services/sound`)のみ、設定に従う: 自分が振ると
  `select`、自分が欄を埋めると `match`、CPU が欄を埋めると `select`、CPU が
  振っても音は出さない。ゲームが終わると、勝ちなら `clear`、負けか引き分けなら
  `gameOver`。

## 11. 意図的な差分

**ブランド原則により合わせないもの**

- **振り直しの追加・目の変更を広告や課金に結び付けない。** 3 回はすべての人に同じ。
- ランキング・オンライン対戦・デイリーはない。記録は端末の中だけにある(§7)。

**設計判断として合わせないもの**

- **一人用から CPU 対戦に変えた(2026-09-27)。** プレイテストの声
  ——「これは対 CPU で遊ぶべきだ」——を受けての最終判断であり、一人用のスコア
  アタックは残さない。ローカル対人戦も作らない: 一台の画面を挟んで交互に操作する
  形は他のどのゲームにもなく、単純さを崩すだけで得るものがない。
- **CPU の強さは 1 段階。** 盤サイズという別の遊びの選択肢を持つ Dots and Boxes
  (§4・§11)と違い、Yacht には難易度以外に差を作れる次元がなく、サイコロの出目
  そのものが対戦相手として十分な分散を持ち込む。複数段の強さを作れば、それは
  実力の差ではなく確率の演出にしかならない。
- **先攻は固定。** 両者の 12 手番は互いの盤面に干渉せず、後攻が得られる情報は
  最終手番での相手の合計だけで、CPU はそれを読まない。差のない選択肢を見せる
  理由がない(§1)。
- **上段ボーナス(Ones〜Sixes の合計が一定以上で加点)を置かない。** 伝統的な
  Yacht の 12 欄に揃える。ボーナスは 6 欄を横断する「あと何点」の目標を常に
  画面に出させ、1 手番ごとの判断をひとつの目標へ寄せる。
- **Undo も Hint も作らない**(§6)。
- **物理演算のサイコロを作らない**(§4)。低スペック端末の床と、「転がり方は結果に
  関係しない」ことの正直さのため。
- **一般名の Yacht の規則で作る。** 商標のある派生ゲームの欄名・点数(例: 上段
  ボーナス、3 of a Kind、Small Straight の 4 連、追加の Yacht ボーナス)には
  合わせないし、その名前をアプリ内にもストア文言にも書かない。
