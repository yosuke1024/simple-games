## 1. 盤面

- **数字のタイル n 枚と、目標 1 つと、演算子のボタン 4 つ**(`+` `−` `×` `÷`)。n はティアが決める
  (§7。v1 は Easy 4 / Medium 4 か 5 / Hard 5)。保存と表示の形式は n = 6 まで受け入れられる形にしておく
  (`MAX_TILES` = 6。計画の「4〜6 枚」の上限で、手の文字列のスロット番号が `0`〜`5` で足りる — §10)が、
  v1 のどのティアも 6 枚を配らない(§7 — 計画の「4〜6 枚」からの差分)。`missed` のときだけ、演算子の行の
  場所に**盤の外の**パネルが出る(§4)。パネルは翻訳した文とボタンを持つので盤には数えない(§12)。
- **スロット**: 盤には n 個の固定の位置(スロット 0〜n−1)がある。配った時点では、数字を**昇順に**
  スロット 0, 1, …, n−1 へ置く(同じ数字が複数あってもよい)。問題は数字の多重集合と目標で決まり、
  並びは昇順に正規化する(保存と比較が一意になる)。
- **まとめた結果の置き場所**: 2 枚をまとめると、**先に選んだタイル(左の項)のスロットは空になり、
  後に選んだタイル(右の項)のスロットに結果が入る**。空いたスロットは空のまま残り、ほかのタイルは
  動かない(位置を詰めない)。理由: 結果が最後に触れた指の下に出る / 手のたびに盤の並びが変わらない /
  保存の手をスロット番号で書ける(§10)。Undo は 2 枚を元のスロットへ戻す。
- **数の範囲**: 配る数字は 1〜10(Hard だけ 11〜25 を 1〜2 枚混ぜる — §7)。目標はティアの帯の中の
  正の整数(§7)。**途中の値は 1 以上の整数**(§2)で、上の上限は置かない。**算術では**、正の整数
  a, b について a + b ≤ max(a,2)·max(b,2)、a × b ≤ max(a,2)·max(b,2)、a − b < a、a ÷ b ≤ a なので、
  どの手順でも途中の値は ∏ max(vᵢ, 2) を超えない。v1 の範囲では Easy 10⁴ = 10,000(5 桁)、Medium
  10⁵ = 100,000(6 桁)、Hard 25·25·10³ = 625,000(6 桁)が上限で、タイルは 6 桁まで描ければ足りる
  (n = 6 を戻すなら 25·25·10⁴ = 6,250,000、7 桁)。どれも 32 ビット整数に収まる。上限そのものは上の
  算術の証明で、テストは反例が無いことを見るだけである。**Phase 2 のテストで実測**: 4 枚・1〜10 の全多重
  集合 715 組の全手順で、途中の値の最大は 10,000(10 × 10 × 10 × 10。上限に等しい — `guarantee.test.ts`)。
  1,000 seed で受け入れた問題の全手順(記憶化しない別実装の数え直しで、目標に届かない手順の値も見た —
  `quality.*.test.ts`)では Easy 7,290・Medium(5 枚を含む)64,800(上限 100,000)・Hard 562,500(上限
  625,000)、デイリー 365 日は 45,000 で、どの問題もそれぞれの ∏ max(vᵢ, 2) を超えなかった。5 枚の側は
  受け入れた問題の標本であって全数ではない。
- **目標**は盤の上、タイルの列の上に、アクセントの枠で囲んだ 1 つの数として置く。タイルとは形
  (枠の太さと、数の前に置く小さな的のインライン SVG)で区別し、押せない(ボタンではない)。
- **盤面に翻訳の要る文字を置かない。**盤に出すのは数字(ASCII の 0〜9)と演算子 `+` `−`(U+2212)
  `×`(U+00D7)`÷`(U+00F7)と、式の行(§4)の `=` だけで、[QUICK_MATH_RULES.md](QUICK_MATH_RULES.md)
  §1「式は翻訳しない」と同じ記号である。読み上げの名前(「目標」「足す」など)は i18n キーで持ち、盤には
  出さない(§12)。翻訳した文とボタンは、盤の外の `missed` のパネル(§4)にだけ出る。

## 2. 規則(まとめる手と終わり方)

- **1 手 = 2 枚を 1 つの演算子でまとめること。**手は「左の項のスロット a・演算子 o・右の項のスロット b」
  の 3 つで書く(a ≠ b、どちらも数字のあるスロット)。結果は r = (a の値) o (b の値)。
- **合法な手**(`engine.ts` の `isLegalMove` が 1 か所で持つ)。まず**スロットの条件**: a ≠ b で、どちらも
  盤の範囲(0〜n−1)にあり、いま数字のあるスロットであること — 同じスロットどうし・範囲外・空いた
  スロットの手は拒む(キーボードや保存の手の文字列が作りうる手なので、画面が押せなくしていることに
  頼らない — §10)。そのうえで演算子ごとの条件。左の値を x、右の値を y とする:
  - `+`: いつでも合法(x + y)。
  - `−`: **x > y のときだけ**合法(x − y ≥ 1)。x = y は結果が 0 になるので打てない。x < y は負になる
    ので打てない — **向きは選んだ順で決まる**(先に選んだほうが左)。
  - `×`: いつでも合法(x × y)。
  - `÷`: **y が x を割り切るときだけ**合法(x mod y = 0。結果は x ÷ y ≥ 1)。x < y は分数になるので
    打てない。
  - `×1` と `÷1` は合法である(結果は変わらないが、1 を 1 枚使い切る手)。x ÷ x = 1 も合法(2 枚が 1 に
    なる)。規則に例外を置かない — [QUICK_MATH_RULES.md](QUICK_MATH_RULES.md) §5-7「問いになっていない
    問題を出さない」は出題の規則で、手の規則ではない。
  - これは [QUICK_MATH_RULES.md](QUICK_MATH_RULES.md) §5 の不変条件 2「引き算は負にならない」・
    3「割り算は必ず割り切れる」と同じ線で、さらに 0 も作らない。
- **使った 2 枚は消え、結果が新しい 1 枚になる**(§1 の置き場所)。各数字は 1 回だけ使う。
- **n 枚なら n−1 手で必ず 1 枚になる。**`+` はどの 2 枚でも合法なので、1 枚になるまで打てる手が無く
  なることは無い — 途中の行き止まりは存在しない。提案の「行き止まりがある(Peg Solitaire と同型)」は
  正確ではなく、[PEG_SOLITAIRE_RULES.md](PEG_SOLITAIRE_RULES.md) §3 の終局(跳べる手が無くなる)とは
  形が違う(計画で訂正済み)。
- **数字は全部使う。**最後に残った 1 枚が目標と等しければ**クリア**(`solved`)。途中で目標と同じ数の
  タイルができても、ほかのタイルが残っている間はクリアではない(何も示さない)。
- 最後の 1 枚が目標と違えば**届かなかった**(`missed`)。これは負けではなく、打てる手が無くなった
  という盤面の事実である。Undo で戻って別の組み方を探す(§4「届かなかったとき」、§5)。
- **途中の局面が「もう目標に届かない」ことは示さない。**それは「まだ解けるか」の表示であり、
  [PEG_SOLITAIRE_RULES.md](PEG_SOLITAIRE_RULES.md) §6 が作らないと決めたものと同じ(§5「Hint は
  作らない」)。
- セッションの状態は `playing` / `missed` / `solved` / `revealed`(解を見て終えた — §5)の 4 つ。
  `missed` は Undo で `playing` に戻る。`solved` と `revealed` は終局で、手も Undo も受け付けない。
- 時間制限・手数制限・ライフ・ゲームオーバーは無い。

## 3. 操作

**タップ(クリック)だけで全部に届く。**キーで届くものは画面にも必ずある
([RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md) §5.13)。ドラッグ・長押し・ダブルタップ・2 本指の操作は
作らない。盤は `onPointerDown` を取らず `click` だけを聞くので、`src/test/pointerContractWiring.test.ts`
の対象にならない(将来ドラッグを足すなら `pointercancel` の配線が要る — [ARCHITECTURE.md](ARCHITECTURE.md)
「指を取り上げられたときの契約」)。

- **順は「数字 → 演算子 → 数字」**(式が左から読め、− と ÷ の向きが選んだ順で決まる)。
  - 何も選んでいないとき、タイル X を押すと X が選ばれる。
  - X を選んでいて演算子を選んでいないとき: X をもう一度押すと解除。別のタイル Y を押すと選択が Y へ
    移る。
  - X を選んでいるとき演算子 o を押すと o が選ばれる。同じ o をもう一度押すと o だけ解除(X は残る)。
    別の演算子を押すと入れ替わる。
  - X と o を選んでいるとき、X 以外のタイル Y を押す: **X o Y が合法ならまとめる**(§2。選択はすべて
    消える)。**合法でなければ何も変わらない** — 盤も選択もそのまま(X と o は選ばれたまま)で、警告の
    文言も音も出さない(静かに拒む)。X をもう一度押すと選択をすべて解除する。
  - 演算子のボタンは、タイルを 1 枚も選んでいない間は無効(押しても何も起きないことを無効の見た目で
    示す)。
  - まとめた後は何も選ばれていない状態から始まる(結果のタイルを自動で選ばない)。
  - 2 枚目を選ぶ前に「その演算子で合法にならないタイル」へ印を付けるかは **Phase 3 で 360 幅の試遊を
    見てから決める**(付けるなら Peg §5 の跳べる先の印と同じ「ルールの可視化」で、Hint ではない)。
    v1 の既定は**印を付けない**(§17)。計画の選択肢は「2 枚目を選んだ時点で、結果が正の整数にならない
    演算子を押せなくする」だったが、この順(数字 → 演算子 → 数字)では 2 枚目を選ぶ時点で演算子はもう
    選ばれているので、同じ「ルールの可視化」を、**演算子を選んだ後の、そのタイルへの印**に読み替えた
    (選んだ順に合わせた適応で、合法でない手を先に見せるという計画の趣旨は変えていない)。
  - **向きの確かめ**: − と ÷ の向き(先に選んだ数が左)が 360 幅で摩擦にならないかは、計画のリスク ④ として
    **Phase 3 で確かめる**(§15)。摩擦なら、順を変える前にこの文書を直す。向きは Quick Rules の 1 でも
    示す(§11)。
- 空いたスロットは押せない(ボタンを置かない)。`missed` / `solved` / `revealed` の間は盤のタイルも
  演算子も押せない。
- **キーボード**: 盤(タイル)は 1 つのタブ位置(roving tabindex)で、←↑ で前の・→↓ で次の数字のある
  スロットへ、Home / End で最初・最後へ移る(スロット番号の順に 1 本の列として動き、タイルが 1 行でも
  2 行でも変わらない。↑↓ は行の移動ではない — §12)。Enter / Space でフォーカスのあるタイルを押す(タップと
  同じ)。`+`、`-`、`*` と `x` / `X`、`/` で演算子(`event.key` で読むので、テンキーとシフト付きの `+`
  も同じ)。`Ctrl/Cmd+Z` で Undo。Escape で選択をすべて解除。フォーカスが盤の外にあるとき(↻ の
  ダイアログが閉じた後など)、最初の矢印キーはフォーカスを最初の数字のスロットへ移すだけ。
  - **押しっぱなしのキーリピート(`event.repeat`)では何もしない**(タイル・演算子・Undo・結果カードの
    ボタンも)。
  - ダイアログ(↻ の `RestartDialog`・解を見る確認)が開いている間、盤は
    `inert` で、キーは盤に届かない(難易度の置き換えの確認はホームに出る — §8 — ので、盤の話ではない)。
    そのときの Escape はダイアログのキャンセルで、選択は残る
    (`useDialogDismiss` の契約。[ARCHITECTURE.md](ARCHITECTURE.md)「Escape は Cancel」。Bridges /
    Unblock Puzzle / Peg Solitaire の Escape と同じ形)。結果カードの間も同じ。
- **Undo** は盤の下のボタン(と `Ctrl/Cmd+Z`)。`missed` の間は、このボタンを隠し(場所は空けたまま
  にして盤を動かさない)、パネルの Undo(§4)が同じ働きをする — 画面に同じ名前のボタンを 2 つ置かない。
  隠すのは `hidden` 属性と `ui/make-the-target.css` の `.tg-actions .action-btn[hidden] { visibility: hidden }`
  の組で行う(属性だけでは、ブラウザ既定の `[hidden] { display: none }` が共有の
  `.action-btn { display: flex }` に負けて見えたままになる。`visibility: hidden` は場所を残し、タブ順と
  読み上げの木からも外す)。
  ヘッダの ↻ は `RestartDialog`(§5)。Back の持ち主は GameContext だけ。

## 4. 表示(選択・式の行・届かなかったとき)

- **選択中のタイルと演算子**は、色だけでなく**太いインクの枠と浮き上がり**で示し、`aria-pressed` を
  持つ。アクセント(紺桔梗)は選択中のタイルの面と目標の枠が着る。
- **式の行**: 打った手を、盤の下に**1 手 1 行**で並べる(`7 × 3 = 21` の形。記号は §1 と同じ)。
  最大 n−1 行(v1 は 4 行)。盤面に既に起きた事実の繰り返しで、Undo で何が戻るか(最後の行)が見える。
  行は順序つきの一覧(`<ol>`)で、読み上げでは式として読む(§12)。360×640 に盤・演算子(`missed` では
  そのパネル)・式の行・Undo がスクロールなしに収まることは Phase 3 で測って書く(収まらなければ行の
  組み方を変え、この節を先に直す)。
- **届かなかったとき**(`missed`): 盤(目標とタイル)はそのまま見えており(押せないタイルも薄くしない —
  共有の `button:disabled` の 0.4 の不透明度を `.tg-tile:disabled` で 1 に戻す。`solved` の一拍と `revealed`
  の盤も同じ)、演算子の行の場所に
  **モーダルでない**パネルが出る。パネルは**盤の外**にあり(§1)、演算子の行の欄を**同じ固定の高さで
  置き換える**(演算子の 4 つはこの間は出ない。欄の高さは言語でも状態でも変えず、盤とその下は動かない)。
  パネルは事実だけを言い(en 案「That makes {value}, not {target}.」)、文は**2 行以内**(Loop Puzzle
  §14 の下の 1 行と同じ作法。最長の訳でも 3 行目へ折り返さないように訳し、14 言語の確認で測る — §12)、
  ボタンは 1 行に並べる。ボタンは **Undo(第一。フォーカスを移す。盤の下の Undo はこの間は隠れる —
  §3)**と、Free Play だけ**「解を 1 つ見る」**(第二。§5)。デイリーは Undo だけ。音は鳴らさない
  (`gameOver` の音は負けの音なので使わない)。読み上げは live region がパネルの文を 1 回読む。
  ヘッダの ↻ とホームへの戻りはそのまま使える。
- **不成立の手**(§3)では何も表示しない。
- **クリア**(`solved`): 最後の 1 枚が目標と同じになった瞬間、目標の枠がアクセントの面になる
  (動きは無い)。結果カードは `useResultReveal` の一拍(0.9 秒、`RESULT_REVEAL_MS`)の後に出る。
  Reduced Motion では即時。一拍の間に押せるものは無い。
- 盤には時計も手数も出さない(§9)。

## 5. Undo・Restart・放棄後の解(Hint は作らない)

### Undo

- **無料・無制限。**1 回で 1 手(1 回のまとめ)を戻す: 右の項のスロットに元の値が戻り、左の項の
  スロットに元のタイルが戻る。式の行も 1 行消える。
- 履歴は**打った手の列そのもの**(最大 n−1 手)で、保存にも入る(§10)。**中断から再開しても最初まで
  戻せる**(Peg §6 / Unblock §6 と同じ)。
- `missed` からも戻せる(最後の手が戻り `playing` に戻る)。
- **クリアした後は戻せない。**クリアへの遷移は 1 回だけ起こり、統計への計上もその 1 回だけ
  (Unblock Puzzle §6 の形)。別の組み方を試したいなら同じ問題の再挑戦で足りる(§17 — 計画の未決事項を
  推奨どおりに決めた)。
- Undo は選択を解除する。

### Restart(ヘッダの ↻)

- 共有の `RestartDialog`(`src/test/restartDialogWiring.test.ts` の形)。「同じ問題で再挑戦」は
  セッションが持っている問題(数字・目標・保存する解)をそのまま使い、手の列と経過秒を空にする
  (`restartSession`。**作り直さず、探索は走らない**)。Free Play で `solved` のセッションから作り直す
  とき(結果カードの再挑戦)は、`repeat`(解いた問題の再挑戦 — §9・§10)を真にし、再挑戦の再挑戦にも
  引き継ぐ(デイリーは `dailyTimes` のキーで決める — §9)。Free Play では同じダイアログが「新しい問題」
  (§6 の生成。探索が走る)も出し、結果カードの「新しい問題」と同じ offer を `newBoard` に渡す。
  デイリーは再挑戦だけ(`newBoard` を渡さない 2 択の形)。
- `missed` の間も、プレイ中も開ける。`solved` の後は結果カードのボタンが同じ役(再挑戦と新しい問題)を
  する。`revealed` の後のカードは「新しい問題」と「ホーム」だけで、再挑戦は無い(下)。
- 再挑戦も新しい問題も、統計では新しい 1 回である(§9)。ただし**解いた問題の再挑戦**は、プレイ回数と
  時間は数えるが、自己ベストと達成日の記録を動かさない(§9)。

### Hint は作らない

盤面は完全に見えており、隠れた情報が無い。「次にどの 2 枚をまとめるか」「この局面からまだ届くか」を
教える機能は、組み方の判断そのものを肩代わりする([PEG_SOLITAIRE_RULES.md](PEG_SOLITAIRE_RULES.md)
§6「Hint は作らない」と同じ判断。PRODUCT_PRINCIPLES.md の Sliding Puzzle の例)。列挙のソルバー
(`solver.ts`、§6)はテストと生成のためだけにあり、画面からは呼ばない。慣例だけに頼らず、
`game/index.ts` はソルバー・生成器・同梱の問題・`newSession.ts` のどれも再輸出せず、境界テスト
(`game/searchBoundary.test.ts`)が、ui/・state/・storage/・i18n/ がソルバー・生成器・同梱の問題を
import していないこと(相対パス・`@/` の別名・動的 `import()` のどれでも)、`newSession.ts` を開くのは
state/ だけであること、保存を読み込む経路(`game/restore.ts`、§10)が生成器・ソルバー・同梱の問題・
`newSession.ts` を(推移的にも)import していないことを確かめる。

**`game/` のモジュールの境界**(この線で置かないと上の境界テストが通らない。§7 の `TIERS` もここで置く):

- `game/tiers.ts` — **葉**。ティアの表(`TIERS`)・ティアの形の判定(`isDealableShape`)・受け入れの

- `game/session.ts` — セッションの遷移(選択・手・Undo・再挑戦・解の表示)と seed の形(`freeSeed`・

- `game/newSession.ts` — セッションの「新しい問題」(`newFreeSession` / `newDailySession`)。**`game/` の中で
  生成器を import するのはこのモジュールだけ**で、ソルバーと同梱の問題を import するのは生成器だけである
  (生成器は上限に届くと自分で同梱へ落ちる — §6)。state の層はこのモジュールを名指しで import し、

### 放棄したあとに解を 1 つ見る(暫定 — 製品オーナーの確認待ち)

計画は「案を記録する」(製品オーナーの指示)としており、提案はこれを決定として書いていた。ここでは
計画の推奨どおり**最小の形で作る**と暫定で決め、§17 に確認待ちとして置く。

- **入口は 1 つだけ**: `missed` のパネル(§4)の第二のボタン「解を 1 つ見る」(Free Play だけ)。
  盤に「ギブアップ」ボタンは置かない。途中で詰まったプレイヤーも、どの 2 枚でも `+` でまとめれば
  n−1 手以内にこのパネルに届く(§2)。
- 押すと確認(`ConfirmDialog`。en は題「Show a solution?」・本文「This problem ends here and is not
  counted as solved.」・確定「Show」 — 案の "board" を、このゲームの言葉の "problem" にした。Escape = Cancel)。確認すると、その問題は終わる(`revealed`)。
- `game/` の側でもこの入口を守る: 解を式の行にする `solutionLines` は、セッションが `revealed` のときだけ
  行を返し、ほかの状態(`playing` / `missed` / `solved`)では null を返す(`session.test.ts`)。画面が
  途中で解を出す道を、慣例に頼らず塞ぐため。
- 見せるのは**生成のときに保存した解 1 つだけ**(§6 の構成した解。同梱の問題なら同梱の解)で、
  **探索は走らない**([GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「CPU 探索」)。プレイヤーの手から
  続く解ではなく、配った数字からの解を 1 行 1 手の式で示す。「最短の」「唯一の」解とは言わない
  (§7 のとおり、ふつう解は複数ある)。
- 解を見た問題は `played` には数えるが(始めたときに数え済み)、**`solved` にも最短時間にも数えない**。
  経過秒は合計プレイ時間に 1 回だけ足す(§9)。中断の保存はその場で消す(終わった問題は再開する
  ものではない)。
  放棄や解の表示の回数は数えない(Hit & Blow §7「放棄したゲームは解けなかった記録にしない」と同じ
  考え — 数えると、記録が「何回あきらめたか」になる)。
- 解を見た後のカード: **結果カードの変種**で、`ui/components/ResultOverlay.tsx` の同じコンポーネントが
  `revealed` の形で出す(`ShareAction` は `Result*Overlay.tsx` にしか置けない —
  `src/test/shareWiring.test.ts` — ので、`RevealCard.tsx` のような別ファイルのカードにしない)。見出し
  (en 案「One way to make {target}」)、解の式の行、ボタンは**「新しい問題」(第一。自動フォーカス)**と
  「ホーム」だけ — 同じ問題の再挑戦は出さない(答えを見た問題の再挑戦は答えの書き写しになる。**解いた
  問題の再挑戦も、同じ理由で記録を動かさない** — §9)。共有は `ShareAction` の `played`(`details` は
  難易度・枚数の 2 つ。時間は出さない)。`useResultReveal` の**一拍は待たない**: 一拍はクリアの瞬間に

  出る)。カードは他の結果カードと同じモーダルで、下の盤は `inert`。
- **デイリーには出さない。**デイリーの記録は「その日に達成した」の 1 つで、見た後の達成を数えないため。
- 作らないと決め直すなら、Hit & Blow §5 と同じ「New Board で手放す」形にし、理由を §14 に書く。

## 6. 生成と Seed

すべての問題は seed から決定的に作る(`generator.ts` の `generateProblem(seed, difficulty)`、デイリーは
`dailyProblem(date)`)。乱数は `game/rng.ts`(xmur3 + mulberry32。既存のゲームから**コピーする** —
共有しない)。時刻と乱数の種(token)は状態の層が渡し、`game/` の中では時計も `Math.random` も読まない。

### 数え方(`solver.ts` の `countWays`)

生成とテストが使う全列挙。画面からは呼ばない(§5)。

- **値の手**: 多重集合の中の 2 つの**値**の組と演算子。+ と × は順を区別しない(x + y と y + x は
  1 つ)。− と ÷ は大きいほうが左(合法な向きは 1 つしかない — §2)。同じ値の 2 つ(x = y)の
  x + x・x × x・x ÷ x も 1 つずつ。同じ値のタイルが 2 枚あっても、どちらを使うかは区別しない。
- **手順**: 値の手の列で、n−1 手の後の 1 つが目標になるもの。**手順の数(`ways`)**はその列の数、
  **÷ を使わない手順の数(`waysWithoutDivision`)**は ÷ を 1 度も使わない列の数。互いに関係しない
  2 つのまとめを入れ替えた順は**別の手順**に数える(例: 1, 2, 3, 4 で 21 を作る (1+2)×(3+4) は、
  1+2 を先にする列と 3+4 を先にする列の 2 手順)。逆に、**値の列が同じになる別の式は 1 つに数える**
  (手は値で区別し、タイルは区別しない): 上の「1+2 を先にする列」[1+2, 3+4, 3×7] は、(1+2)×(3+4) の
  列であると同時に ((1+2)+4)×3 の列でもある。だから `ways` は「式の木の数 × 入れ替えの数」ではなく、
  手で確かめるときは木を数えずに値の列を数える。1, 2, 3, 4 で 21 を作る手順は全部で **6 つ**(`ways` = 6。
  ÷ は使わないので `waysWithoutDivision` も 6): 1+2・3+4・3×7 / 3+4・1+2・3×7 / 1+4・2+5・3×7 /
  2+3・4×5・1+20 / 2+4・1+6・3×7 / 2×4・8−1・3×7(**Phase 2 のテストで実測**: `solver.test.ts` の
  golden が、`countWays` の `ways` = 6・`waysWithoutDivision` = 6 と、記憶化しない別実装(タイル単位の
  全手順の列挙)が出すこの 6 つの値の列そのものの両方で再現した)。式の木の数ではなく
  列の数を数えるのは、記憶化した深さ優先で正確に数えられ、別実装(素朴な列挙)と
  突き合わせられるため。**列の数は「解の数」ではない**: 5 枚の式の木 1 本は 1〜3 通りの列を数え(互いに
  関係しない 2 つのまとめの置き方の数。算術では)、値の列が同じ別の式は 1 つにまとまる(上)。そのため
  手順の数は枚数とともに大きくなり、帯(§7)は枚数ごとの分布を見て置く。画面には出さない。
- **列挙**: 残っている値の多重集合(昇順に整列した列)を鍵に記憶化した深さ優先。1 つの多重集合に
  ついて、異なる値の組 × 合法な演算子を全部たどり、手順の数と ÷ を使わない手順の数を同時に数える。
  記憶は 1 問(1 つの目標)ごとに作り直す。
- **仕事量**: 展開した多重集合(2 つ以上の値を持ち、記憶に無かったもの)の数(`states`)。上限
  `budget` を超えそうになったら(次の 1 つを展開すると `budget` を超えるなら)、その時点で止めて `capped`
  を返し、手順の数は返さない(数え途中の値を答えにしない)。端数のある上限はその整数部分と同じに働く
  (1.5 なら 1 つまで)。上限が 1 未満や NaN なら何も数えずに `capped`。
- **算術では**、向きのある 6 演算の素朴な木の葉は 4 枚で 3,888・5 枚で 233,280・6 枚で約 2,100 万
  (計画)。**提案時の試作では**(整列した多重集合で記憶化し、正の整数に枝刈りした深さ優先、1〜13 の
  数を 300 組)、訪れた状態は 4 枚で最悪 276・5 枚で 2,701・6 枚で 28,601 だった(計画)。**この文書を
  書くときの試作では**(§15、上の定義、§7 のティアの数の範囲)1 回の列挙の最悪は Easy 129・Medium
  1,443・Hard(5 枚)1,868・6 枚 約 2.4 万。**Phase 2 のテストで実測**(同じ定義)では、1 回の列挙の最悪は
  Easy 131(1,000 seed — `quality.easy.test.ts`。4 枚・1〜10 の全数でも 131 — `guarantee.test.ts`)・
  Medium 1,443・Hard(5 枚)1,868(どちらも 1,000 seed — `quality.*.test.ts`)・6 枚 23,456(帯に入った
  候補 300 個 — `hard6.measure.test.ts`)。

### 生成の手順(`generator.ts`)

1. **試行**: k = 0, 1, 2, … の順に、試行ごとの乱数 `createRng(seed + '#' + k)` で 1 問を組む
   (試行は互いに独立で、どの試行も seed だけから再現できる)。
2. **枚数と数字**: ティアの枚数(§7)から 1 つを等確率に選び、ティアの範囲から数字を引いて昇順に
   並べる。
3. **解を先に組む**: 配った n 枚の上で、n−1 回「数字のある 2 つのスロットを等確率に選び、その 2 つで
   合法な演算子(ティアの「組むときの演算子」に入っているもの)から**等確率に** 1 つを選んで、まとめる」を
   繰り返す(左の項は大きいほう。同じ値なら番号の小さいスロット)。Medium の「÷ の要る回」(§7)だけ、÷ が
   まだ使われておらず、その 2 つで合法なとき、まず確率 1/2 で ÷ を選ぶ。選ばなかった残りの 1/2 は、÷ を
   除いた合法な演算子(+ − × のうち合法なもの)から等確率に選ぶ。÷ がもう使われている・その 2 つで ÷ が
   合法でないときは、ほかの回と同じに、合法な演算子から等確率に選ぶ。乱数を引く順番は実装が決めて golden
   が固定する(下)が、**どの演算子をどの確率で選ぶか**はここが決める。最後の値を**目標の候補**にし、
   打った手の列を**保存する解**にする。解の存在はこの構成で保証される(計画の未決事項「目標の作り方」を推奨どおりに
   決めた — 目標を先に引いて解を数える順だと、解の無い組を捨てる試行が増える)。
4. **目標の帯**: 候補がティアの目標の帯(§7)に無ければ、この試行を捨てて次へ(列挙はしない)。
   Medium の「÷ の要る回」では、組んだ解が ÷ を使っていなければ、これも列挙せずに捨てる(Phase 2 で
   決めた): その解自身が ÷ を使わない手順なので `waysWithoutDivision` ≥ 1 で、列挙しても受け入れられ
   ない。仕事量を減らすだけで、上限に届かない seed の問題は変わらない。**試作では**(この枝刈りを足す前の
   実装の版で、同じ 1,000 seed を走らせた出力。その版はもう無く、いまのテストは再現しない)÷ の要る回の
   5 seed が上限に届いて同梱へ落ちた。足した後のいまの実装では 0(`quality.medium.test.ts` が 0 を固定する)。
5. **列挙**: `countWays`(残りの仕事量を上限に)で手順の数と ÷ を使わない手順の数を数える。構成した
   1 つの解はティアを決めない — ティアを決めるのは列挙の数である。
6. **ティアの条件**(§7)を満たせば、その問題を返す。満たさなければ次の試行へ。Medium の条件は 1 つの
   述語(§7)で、「÷ の要る回」(手順 3)に組んだ問題はそのうち `waysWithoutDivision` = 0 の項を、それ以外の
   回に組んだ問題は `ways` ≤ 200 かつ Easy でない項を満たしたものだけを受け入れる。
7. **仕事量の上限**: 1 問に予算 1 本で、全試行の合計で数える(Bridges §6「予算は仕事量で門にする」と
   同じく)。1 試行は 1 と、その試行の列挙の `states` を足した値を使う(帯で捨てた試行も 1 を使うので、
   試行の数にも上限がかかる)。上限は **`WORK_LIMIT` = 50,000**(計画の初期値のまま。変えたらここを直す)。
   **Phase 2 のテストで実測**: 1,000 seed × 3 ティアとデイリー 365 日で上限に届いた問題は 0、1 問の
   仕事量の最大は Easy 248・Medium 48,238・Hard 13,678・デイリー 29,208(`quality.*.test.ts`。どれも
   決定的なので、テストが同梱へ落ちた数 0 とこれらの値を固定する — 上限を下げて 1 問でも落ちれば
   落ちる)。Medium の
   最悪は上限の 96% に当たるので、1,000 より大きな標本では上限に届く seed がありうる(その率は未検証)。
   合計が上限に届いたら、推測で問題を作らず**同梱の問題へ落ちる**(下)。
8. 返す値(`generateProblem(seed, difficulty, budget = WORK_LIMIT)`): 問題(数字・目標・保存する解・
   ティア)と、`ways`・`waysWithoutDivision`・`fallback`(同梱へ落ちたか)・`work`(使った仕事量)・
   `attempts`・`worstCount`(1 回の列挙の最大の状態数)・`divisionRound`。上限で落ちずに `null` を返す
   形が `generateFresh`、試行の繰り返しそのものが `searchProblem`(6 枚の測定 — §7 — が同じコードを
   6 枚の形で走らせるため)。落ちたときの `ways` / `waysWithoutDivision` は同梱の表に記録した値で、
   落ちるときに探索は走らない。`divisionRound` は「出した問題を Medium の ÷ の要る回で組んだか」で、
   落ちたときは偽(同梱の問題はその seed の回で組んだものではなく、÷ が要るとは限らない)。壁時計は測って
   出力するだけで、門にしない。

乱数の消費の順番(どの試行で何を何回引くか)は実装が決め、`compatibility.test.ts` の seed の golden
(ティアごとと、デイリーの日付)が固定する。golden を変える変更は、正式収録の後は `schemaVersion` と
同じく扱う(保存した問題は seed からではなく保存した数字から戻すので、中断は失われない — §10)。

### 同梱の問題(`bundled.ts`)と探索の走るとき

- **同梱の検証済み問題をティアごとに同数**持つ: **v1 は各 24 問(計 72 問)**。どれもこの生成器が
  記録した seed `make-the-target-bundled-<difficulty>-<k>`(k = 1, 2, …。上限に届いたものと、前の行と
  同じ数字・目標になったものは飛ばす — 後者は Phase 2 で決めた。同じ問題が 2 行あれば表が小さくなるだけ
  だから)から作った問題で、1 行は「k・数字・目標・保存する解・`ways`・`waysWithoutDivision`」。
  **Phase 2 で作った表**: Easy は k = 1〜25(k = 18 が k = 13 と同じ問題で飛ばした)、Medium と Hard は
  k = 1〜24(飛ばしたもの無し)。表は `bundled.generate.test.ts`(環境変数 `MAKE_THE_TARGET_BUNDLED=write`
  のときだけ書く)が書き、手では直さない。`bundled.test.ts` が、表が同じ seed から生成器が作る問題と
  一致すること(出所)と、72 問が互いに重ならないことを確かめ、全 72 問を**記憶化しない別実装の
  列挙**(§15)で数え直し(表の `ways` / `waysWithoutDivision` とも一致)、ティアの条件(Medium は回の
  枝を見ない 1 つの述語 — §7。同梱の問題は回の枝を持たない)・解の合法性・目標への到達を 1 問ずつ
  確かめる。
- **落ち方**: その seed の `hashSeed(seed)` をティアの問題数で割った余りの番号の問題を配る(seed から
  決定的)。デイリーも同じで、日付の seed から決まる。
- **探索が走るのは「新しい問題」とデイリーを開くときだけ**(どちらもタップの結果 —
  [GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「CPU 探索」)。ポーリング・先読み・Worker は使わない。
  **読み込みでは走らない**: 中断の再開・同じ問題の再挑戦・解の表示は、保存した数字と手を再生するだけで
  ある(§10。Bridges / Loop Puzzle の「開くときの再証明」— GAME_LIFECYCLE.md の暫定の例外 — には
  乗らない)。

## 7. ティア(難易度)

ティアは**枚数・数の範囲・目標の帯・組むときの演算子・受け入れの条件**で決める(`game/tiers.ts` の
`TIERS`。生成器も復元も読む葉のモジュール — §5)。下の値は計画の推奨から置いた初期値で、Phase 2 の
1,000 seed の測定(§15)で分布(手順の数・÷ の要る割合・同梱へ落ちる率・仕事量)を見て、**そのまま
確定した**(変えた値は無い)。変えるときはこの表を先に直す。

| ティア | 枚数           | 数                                        | 目標    | 組むときの演算子 | 受け入れの条件                                                                                            |
| ------ | -------------- | ----------------------------------------- | ------- | ---------------- | --------------------------------------------------------------------------------------------------------- |
| Easy   | 4              | 1〜10                                     | 10〜24  | + − ×            | `ways` ≥ 4 かつ `waysWithoutDivision` ≥ 1                                                                 |
| Medium | 4 か 5(等確率) | 1〜10                                     | 10〜60  | + − × ÷          | 1 ≤ `ways` かつ、(a) `waysWithoutDivision` = 0、または (b) `ways` ≤ 200 で**Easy の条件を満たさない**(下) |
| Hard   | 5              | 11〜25 を 1 か 2 枚(等確率)、残りは 1〜10 | 50〜300 | + − × ÷          | 1 ≤ `ways` ≤ 40                                                                                           |

**Phase 2 のテストで実測**(seed `make-the-target-<difficulty>-x<k>`、k = 1〜1,000 — 試作と同じ seed —
とデイリー 2026-10-21 からの 365 日。どの問題も記憶化しない別実装で数え直し、受け入れの述語・保存する
解の再生・途中の値の上限を確かめた — `quality.easy.test.ts` / `quality.medium.test.ts` /
`quality.hard.test.ts` / `quality.daily.test.ts`。生成は決定的なので、表の値(÷ の要る問題の `ways` の
分布、1 回の列挙の最悪、途中の値の最大も)はテストが固定する。値が動けばテストが落ちる):

| ティア   | `ways` p10 / p50 / p90 / 最大 | ÷ の要る問題(うち ÷ の要る回) | 枚数               | 試行 p50 / p99 / 最大 | 仕事量 p50 / p99 / 最大 | 同梱へ落ちた |
| -------- | ----------------------------- | ----------------------------- | ------------------ | --------------------- | ----------------------- | ------------ |
| Easy     | 6 / 18 / 36 / 66              | 0(0)                          | 4 枚 1,000         | 3 / 16 / 24           | 87 / 197 / 248          | 0 / 1,000    |
| Medium   | 2 / 12 / 140 / 200            | 347(324 回)                   | 4 枚 558・5 枚 442 | 5 / 184 / 431         | 811 / 18,437 / 48,238   | 0 / 1,000    |
| Hard     | 7 / 21 / 37 / 40              | 31(—)                         | 5 枚 1,000         | 5 / 28 / 52           | 1,742 / 9,490 / 13,678  | 0 / 1,000    |
| デイリー | 2 / 13 / 149 / 200            | 118(106 回)                   | 4 枚 200・5 枚 165 | 5 / 175 / 318         | 831 / 19,537 / 29,208   | 0 / 365      |

壁時計(門にしない。テストは出力するだけで、確かめない): この開発用コンテナでの 1 回の実行(2026-10-21、
`src/games/make-the-target` 全体を 4 コア並列で)の例は、1 問の生成が Medium p99 13.98 ms・最大 33.40 ms、
デイリー p99 15.54 ms・最大 23.31 ms、Hard p99 6.36 ms・最大 9.25 ms。走らせるたびに、機械の混み具合で
変わる(同じ日の別の実行では Medium の最大 30.85 ms・Hard の p99 7.04 ms、レビューでの実行では Medium の
最大 49.80 ms・Hard の p99 8.63 ms と報告された)。実機の時間は未検証(§15)。

- **「÷ の要る問題」は「÷ を使わない手順が 0」**と読む(計画の推奨)。**帯は重ねない**: Easy には ÷ の
  要る問題を入れない(受け入れの条件が `waysWithoutDivision` ≥ 1 を求め、組むときも ÷ を使わない)。
  Medium は、÷ を使わずに解ける問題でも Easy の条件をすべて満たすものは入れない。Medium と Hard は数の
  範囲(Hard は必ず 11〜25 の数を含み、Easy と Medium は 1〜10 だけ)で重ならない。
- **Medium の受け入れは、問題の数だけで決まる 1 つの述語**(上の表)である: 数字・目標・`ways`・
  `waysWithoutDivision` から決まり、seed も「÷ の要る回」の枝も入力に含まない。「Easy の条件を満たさない」
  は、4 枚・目標 24 以下・`ways` ≥ 4・÷ なしで解ける、のどれかが欠けること。だから、回の枝を知らない
  同梱の問題(§6)も、生成の出力も、同じ述語で数え直して確かめる(`bundled.test.ts`・`quality.*.test.ts`)。
  ÷ の要る問題(`waysWithoutDivision` = 0)には `ways` の上限を置かない(÷ が唯一の道なので、手順が多くても
  ÷ の要る問題である)。**Phase 2 の分布を見て、上限は置かないと決めた**: ÷ の要る Medium の `ways` は
  1,000 seed で p10 2 / p50 4 / p90 26 / 最大 137、デイリー 365 日で最大 156 で、(b) の 200 を超えたものは
  無かった。
- **Medium の「÷ の要る回」**は、述語ではなく生成器が組む側の選択である: `createRng(seed)` の最初の値が
  1/3 未満なら、その問題は ÷ の要る問題として組み(§6 手順 3)、`waysWithoutDivision` = 0 の問題だけを
  受け入れる。それ以外の回は `ways` ≤ 200 で Easy でない問題を受け入れる(§6 手順 6)。どちらの回の出力も
  述語を満たす(÷ の要る回でない回は、(a) だけを満たす問題 — ÷ が要り `ways` が 200 を超えるもの — を
  受け入れない)。デイリーも Medium なので同じ割合で ÷ の要る日がある。**この文書を書くときの試作では**、
  この割合で受け入れた 1,000 問のうち ÷ の要る問題は 363 だった(§15)。**Phase 2 のテストで実測**:
  1,000 seed のうち ÷ の要る回は 324、受け入れた ÷ の要る問題は 347(残る 23 は ÷ の要る回でない回が
  (b) で受け入れた問題)。デイリー 365 日では 106 回・118 問(上の表)。
- **解の一意は約束しない。**このパズルでは解が複数あるのがふつうで、約束するのは「解けること」
  (保存する解がその証拠)と「ティアの条件を満たすこと」(列挙で数えた)だけである。
- **Hard の「解が少ない」の測り方(計画からの差分)**: 計画の Hard の初期案は「解が 1 通りに近い」、
  推奨の言い方は「解の数が少ない」だが、v1 は**手順の数の上限(`ways` ≤ 40)**に置き換えた。手順の数は
  解(式の木)の数ではない(§6: 木 1 本が 1〜3 通りの列を数え、値の列が同じ別の式は 1 つにまとまる)ので、
  `ways` ≤ 40 は「組み方の手順が少ない」という上限で、「解が少ない」の近似にすぎず、**「解が 1 通りに
  近い」とは言わない**。**試作では** Hard(5 枚)の手順の数は p50 = 20、**Phase 2 のテストで実測**では
  p10 7 / p50 21 / p90 37 / 最大 40 だった(上の表)が、これが式の木にして何通りかは数えていない
  (未検証)。木の数(重複を除いた式の数)で帯を置くには、素朴な木の列挙が別実装に要る
  (計画のオラクルは「素朴な木」だったが、この文書は列挙の突き合わせを「素朴な列挙」に替えた — §15・
  §17)。**v1 は木では置き直さない**(Phase 2 で決めた): 手順の数の帯で Hard の問題は作れており(1,000 seed で
  帯のために同梱へ落ちた seed は 0、`ways` は帯の中に散らばる)、木の数を数える別実装を足す理由が分布からは
  出なかった。置き直すなら §6・§7・§15 を先に直す。
- **Hard の 6 枚(計画からの差分 — v1 は 5 枚。理由は Phase 2 の測定で確かめた)**:
  計画の推奨は「6 枚の列挙が上限 50,000 状態に収まれば 6 枚を出す。収まらなければ v1 の Hard は 5 枚に
  し、ルール文書に理由を書く。上限を緩めるより先に枚数を減らす」。**この文書を書くときの試作では**、1 回の列挙は 6 枚でも最悪約 2.4 万状態で、計画の
  基準(1 回の列挙が上限に収まるか)だけを見れば 6 枚を出せる。それでも 5 枚にしたのは、6 枚の問題は
  互いに関係しないまとめの入れ替えで手順の数が大きく(帯を置かないと p10 = 291)、Hard の帯 `ways` ≤ 40
  を満たす問題が 6 枚ではほとんど見つからず(6 枚だけで組むと 300 seed 中 298 seed が上限 50,000 の中で
  見つけられずに同梱へ落ちた)、帯を外せば Medium と難しさで分けられないため。そこで v1 の Hard は
  **5 枚**にした(5 枚では 1,000 seed で同梱へ落ちたのは 0)。**ただしこの理由は、この文書が選んだ 2 つに
  支えられている**: 帯が手順の数(入れ替えで増える列の数 — 上の「測り方」)であること、そして 1 回の列挙が
  約 2.4 万状態なので 1 問の予算 50,000 では列挙が約 2 回しかできないこと。298 / 300 は「`ways` ≤ 40 の
  問題がどれだけ稀か」と「予算が尽きた」を分けて測っておらず、2 つが混ざっている。数値はリポジトリの
  外の試作のもので、そこで Phase 2 に**6 枚の測定のテスト**(`hard6.measure.test.ts`。6 枚は出荷しないが、
  決まった seed と出荷するコードで測るので値は決定的で、下に引く値をテストが固定する)を置き、6 枚の側を
  稀さと予算切れに分けて測った。**Phase 2 のテストで実測**:
  (a) **稀さ** — 6 枚で組んだ目標が帯に入った候補 300 個(引いた 875 個の中)を、上限に当たらない予算で
  数えると、1 ≤ `ways` ≤ 40 は **0 個**で、`ways` は p10 360 / p50 1,217 / p90 2,899 / 最大 8,040。
  (b) **予算** — 1 回の列挙は p10 5,232 / p50 10,823 / p90 17,307 / 最大 23,456 状態(平均 10,910)で、
  50,000 の中で約 4 回しか数えられない。(c) **両方** — 出荷する試行の繰り返し(`generator.ts` の
  `searchProblem`)を 6 枚の形と Hard の受け入れ(1 ≤ `ways` ≤ 40)で 100 seed 走らせると、99 seed が
  上限に届いた。(a) が 300 個中 0 なので、予算を緩めても帯 `ways` ≤ 40 の 6 枚の問題はほとんど作れない
  — 試作の 298 / 300 の主因は稀さで、予算の小ささはそれに重なっていた。**測定はこの判断を支える**ので
  v1 の Hard は 5 枚にする。ただし帯が手順の数(入れ替えで増える列の数)であることはこの文書の選択なので、
  計画からの差分(§17 の ①)として残す。6 枚を戻すなら、木の数で帯を置く案から(先にこの節と §17 を
  直す)。標本は計画の例(2,000 個・300 seed)より小さい(テストを速く保つため。§15)。
- 枚数の多いティアほど手数も多い(Easy 3 手 / Medium 3〜4 手 / Hard 4 手)。手数は枚数で決まるので
  記録しない(§9)。

## 8. モードとデイリー

- **Free Play**: Easy / Medium / Hard を選び、いつでも新しい問題を引ける。seed は
  `make-the-target-<difficulty>-<token>`(token = 時刻 + 乱数、`newSeedToken(now, random)` —
  `<now の 36 進>-<乱数の 36 進>`。状態の層が `Date.now()` と `Math.random` を渡す)。同じ seed なら
  同じ問題。レベル・ステージ・星の評価は作らない。
- **デイリー**: 1 日 1 問。seed は `make-the-target-daily-<YYYY-MM-DD>`(**端末のローカル日付だけ**。
  サーバー時刻もネットワークも使わない)。**毎日 Medium 固定**(曜日で当たり外れを作らない)。デイリーの
  ↻ は再挑戦だけで、`missed` のパネルに「解を 1 つ見る」は出ない(§5)。
- **デイリーは今日の 1 問だけ**([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md)「デイリーは今日の 1 問」)。
  過去の日付には遡れず、一覧も入口も持たない。日付が今日でない中断中のデイリー(過ぎたものも、時計を
  戻した端末で先の日付になったものも)は、次にゲームを開いたときにレコードごと捨て、ホームの
  「デイリーチャレンジ」はつねに今日の問題へ向く。遊んでいる最中の問題は日付が変わっても取り上げず、
  日付をまたいで終えたときも、その問題の日付(セッションの `dailyDate`)の達成として記録する(§9)。
  達成した日の記録は残す(§9)。
- **ストリークは数えない・表示しない。**残り時間・期限も出さない。
- 中断は Free Play 用・デイリー用の **2 スロットを独立して保持**する(§10)。
- **結果カードの第一ボタン(暫定 — 製品オーナーの確認待ち)**: Free Play は「新しい問題」が第一
  (自動フォーカス)、「同じ問題で再挑戦」が第二、「ホーム」。同じ棚の Unblock Puzzle §9 と同じ形で、
  解けた問題は組み方が分かった後なので同じ問題の再挑戦の価値が薄い(計画の推奨)。デイリーは
  「同じ問題で再挑戦」と「ホーム」。前例はゲームごとに割れており(計画 2026-10-17「ゲームの作業が
  オーナーの判断に残した点」)、オーナーが 1 つの規則を決めればそれに従い、4 つ目の形を作らない(§17)。
  どの形でも、結果カードからの再挑戦は**解いた問題の再挑戦**で、プレイ回数と時間は数えるが、自己ベストと
  達成日の記録は動かさない(§9。組み方が分かった後の入力の速さを記録にしない)。
- 最後に選んだ難易度は `tg.prefs` に残る(初期値 Easy)。初回の Quick Rules の直後に始まる問題も
  この難易度。ただし Free Play の中断中の問題があれば(`tg.flags` だけが失われて Quick Rules がもう一度
  出た場合)、新しく作らずにその問題を難易度にかかわらず再開する(黙って置き換えない)。
- ホームで中断中と違う難易度を選んだときは、置き換えてよいかを確認する(`ConfirmDialog`)。
- ホーム画面のショートカットは、中断中の問題がちょうど 1 つのときだけ盤へ直接入る(2 つなら推測に
  なるのでホームへ。初回は Quick Rules が先)。

## 9. 統計と時計

- **プレイ中に時計も手数も表示しない。**経過秒は内部で記録し、結果カードと統計でのみ見せる(ホームの
  難易度のボタンにも最短の秒を出さない — Loop Puzzle と Bridges はホームに静かに出しているが、その 2 本の
  ルール文書も「結果画面と統計でのみ見せる」と書いており、文書にない前例なので、このゲームは文のほうに
  従う。§17)。
  **自己ベストは経過秒**だけ(手数は問題の枚数で決まるので比べない — 計画の決定)。**スコアは作らない。**
  比べる相手は自分の記録だけ。
- 時計は盤の画面が見えている間(`visibilityState` が `visible`)だけ 1 秒ずつ ref に足し、再描画しない。
  セッションは時計を読まない(持ち主から経過秒を受け取り、減る方向の値は無視する)。
- `tg.stats`(§10)の中身(**デイリーの数え方は暫定 — 製品オーナーの確認待ち**):
  - `easy` / `medium` / `hard`(Free Play だけ): `played`(新しい問題と再挑戦で数える。再開では
    数えない)/ `solved`(クリアした回数。解を見た問題は数えない。解いた問題の再挑戦でのクリアは
    数える)/ `totalPlaySeconds` / `bestSeconds`(最短のクリアの秒、未クリアは `null`。**解いた問題の
    再挑戦でのクリアでは更新しない** — 下)。
  - `daily`: `played` / `totalPlaySeconds`。**デイリーは Medium に混ぜない** — Bridges §11 と同じ
    別の枠(計画の推奨: 分けた数は後で足せるが、混ぜた数は後から分けられない。Unblock Puzzle と
    Loop Puzzle は Medium に数えるので、規則は 3 本で揃っておらず、オーナーが 1 つの規則を決めるまでの
    暫定)。
  - `dailyTimes`: 達成した日 → その日の最初のクリアの秒。日付の**集合**で、連続は数えない。達成日数は
    この件数。**キーはセッションの `dailyDate`(問題の日付)**で、日付をまたいで終えても、始めた日の
    問題の日の達成として記録する(終えた時刻の日付ではない。Loop Puzzle の `statsLogic` と同じ。
    PRODUCT_PRINCIPLES.md の「終えればその日の達成として記録する」はこう読む)。その日のキーが既にある
    ときのクリア(同じ日の 2 回目以降 — ホームから開き直した場合も結果カードの再挑戦の場合も)は、
    値を動かさない(下)。
  - **累計プレイ時間**は 4 つの `totalPlaySeconds` の和で、別に保存しない。
  - **解いた問題の再挑戦は、最短と達成日の記録を動かさない**(計画に無い規則 — §17)。解いた問題の
    再挑戦は解の書き写しになりうる(§5 が、答えを見た問題の再挑戦を出さないのと同じ理由)。書き写しの
    速さが `bestSeconds` に入ると、新しい問題のたびにそれと比べる `BestDelta` と、日ごとの `dailyTimes`
    が、組み方を探した時間ではなく入力の時間になる。規則: Free Play では、セッションの `repeat`(解いた
    問題の再挑戦か)が真のクリアは、`played`(再挑戦を始めたときに数え済み)・`solved`・
    `totalPlaySeconds` には数えるが、`bestSeconds` を更新しない。`repeat` は、`solved` のセッションから
    「同じ問題で再挑戦」したときに真になり、その後の再挑戦(`missed` からの ↻ を含む)にも引き継がれ、
    中断の保存にも入る(§10 — 再挑戦の途中で離れて再開しても抜け道にならない)。まだ解いていない問題の
    再挑戦(`missed` からの ↻ など)は `repeat` ではなく、クリアすれば記録の対象になる。デイリーは
    `repeat` を使わず、**その日の `dailyTimes` のキーが既にあるか**で決める(あれば値を動かさない)。
    この規則は統計の層(`state/statsLogic.ts`)が持ち、`statsLogic.test.ts` が確かめる(§15)。
- **時間の計上**: 未計上の秒だけを、背景へ回るとき・ホームやコレクションへ戻るとき・クリアのとき・
  解を見たとき・遊んでいる問題を ↻ で替えるとき(`bookReplacedBoard` — 置き換わる問題の未計上の秒を
  先に足してから新しい問題の時計を 0 から始める。Loop Puzzle §10)に足し(bookedRef 方式)、同じ秒を
  二度数えない。ブラウザの戻るや別のゲームへのショートカットでアンマウントされるときも、プロバイダが
  同じ同期処理を走らせる(`useOnUnmount(syncActiveGame)` を 1 回。スキャフォールドの
  `state/GameContext.tsx` が最初から持つ。門は `src/test/unmountBookingWiring.test.ts`、
  [GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「アンマウントで計上する」)。解いた問題は解いた時点で計上
  済みなので、結果カードからの再挑戦では何も足さない。
- 戻ってきたとき(`visibilitychange`・アプリの再開)は何も進めない。盤はプレイヤーの手でだけ変わる。
- **結果カード**(`ui/components/ResultOverlay.tsx`。解を見た後のカード(§5)も同じコンポーネントの
  変種): 見出しは事実だけ(en「Target made.」。
  スキャフォールドの `makeTheTargetResultTitle` "Nice work" は称賛語なので Phase 3 で置き換えた(キーも
  `makeTheTargetSolvedTitle` に替えた) — PRODUCT_PRINCIPLES「手応えは、盤面に既に見えている事実をもう一度
  言う形に限る」)。事実の一覧は 1 行に 1 つで、難易度(デイリーは「Daily」)・枚数・目標・時間の 4 行(Phase 3 で
  決めた: 共有の `details` の 3 つ — 難易度・時間・枚数 — は `ShareAction` の契約で「その画面が見せている事実」で
  なければならないので、目標・時間に難易度と枚数を足した)。自己ベストは Loop Puzzle §10 の形で、`statsLogic` の `applySolved` と同じく
  記録を破るのは秒が**厳密に小さい**ときだけ。比べる記録は Free Play がそのティアの `bestSeconds`、
  デイリーがその日(`dailyDate`)の `dailyTimes`。場合ごとに、「Your fastest yet.」・今の最短・差
  (`BestDelta`)が出るか:
  - **初めてのクリア**(比べる記録が無い): 「Your fastest yet.」を出す。**差は出さない**(`BestDelta` は
    前の記録が無いと何も描かない)。記録を書く。
  - **記録より速い**(秒が厳密に小さい): 「Your fastest yet.」を出し、前の記録との差(`−0:05` の形)を
    添える。記録を更新する。
  - **記録と同じ秒**: 「Your fastest yet.」は**出さない**(破っていない)。今の最短だけを出し、**差は
    出さない**(`BestDelta` は 0 を描かない)。記録は動かさない。
  - **記録より遅い**: 「Your fastest yet.」は出さない。今の最短と、それとの差(`+0:18` の形)を出す。
    記録は動かさない。
  - **解いた問題の再挑戦でのクリア**(上の「解いた問題の再挑戦」): 自己ベストの行も差も出さない
    (記録を動かさないものを記録と比べない)。事実の 4 行(難易度・枚数・目標・時間)はいつもどおり出す。
  - デイリーで起きるのは「初めてのクリア」と「再挑戦」の 2 つだけ(同じ日の 2 回目以降は再挑戦で、記録と
    比べない)。星・紙吹雪・称賛は作らない。
- **共有**: `ShareAction`。クリアは `completed`、解を見た問題は `played`(§5)。クリアの `details` は
  最大 3 つで、難易度(デイリーは「デイリー」)・時間・枚数。
- **統計画面**: ティアごとに プレイ回数・クリア数・最短クリア・合計プレイ時間、デイリーの プレイ回数・
  達成日数・合計プレイ時間、「すべてのモード」の合計プレイ時間。ストリークも順位も無い。統計と結果の
  見出しの言い方は、前例がそろうまで Bridges に合わせる(暫定 — 製品オーナーの確認待ち。§17)。

## 10. 中断と再開(保存)

保存キーは `tg.saveGame` / `tg.saveDaily` / `tg.stats` / `tg.flags` / `tg.prefs` の **5 つ**
(`storage/keys.ts`、import ゼロの葉。キーの葉の名前は順に `game` / `dailyGame` / `stats` / `flags` /
`prefs`)。スキャフォールドの `tg.stats` / `tg.flags` と仮の Stats / Flags、`gameKeys.test.ts` の行
(`['tg.stats', 'tg.flags']`)は、Phase 3 でこの 5 キーに置き換えた(`gameKeys.test.ts` の行と理由は同じコミット。
[storage-keys.md](architecture/storage-keys.md) の表の行は統合の段で直す)。
ほかのゲームのキーには触れない。**ベータ中はスキーマを凍結しない** — 変えるときは `WebBetaNotice` の
告知の範囲でリセットを許す([WEB_VERSION.md](WEB_VERSION.md)「保存データ」)。正式収録の時点で凍結し、
以後は移行だけで変える。

**計画の食い違い**: 計画「決定事項」は「`storage/keys.ts` と `gameKeys.test.ts` の行は、ルール文書の保存の
節と同じコミットで増やす」、同じ計画の 53 節は「Phase 3 で 5 キーに置き換える」と言う。この文書は**後者
(Phase 3)に従った** — 保存の節を書いたコミットでは、キーも行も増やしていない。理由:
`src/backup/keys.test.ts` が、レジストリが宣言した全キーが持ち主のスキーマに解決されることを求めるので、
キーはスキーマ(`storage/schemas.ts`)と同じ段で増やすほうが、宣言だけあって検証するものの無いキーを
作らない。

- **2 スロット規則**: どのスロットのレコードかを決めるのはキーである(`gameSlotSchema(key, expectedMode)`、
  `storage/slots.test.ts`、`src/test/savedGameSlots.test.ts` が強制。デイリー用のキーの葉は
  `dailyGame`)。
- 背景へ回るとき・ゲームを離れるとき・アンマウントのとき、問題の保存と未計上秒の計上を同じ同期処理で
  行う(§9)。保存の失敗でゲームを止めない。バリデータは例外を投げない。
- 保存するのは**配った問題と手の列**で、途中の盤面ではない。再開時は手の列を規則に通して再生し、
  画面の盤はその結果である。だから再開後も Undo が最初まで効く(§5)。**読み込みでは探索しない**(§6)。
- `game/` の側の入口(Phase 2): `game/restore.ts` の `toRecord(session, savedAtMs)`(下の表のレコード全体を
  書く。`solved` / `revealed` のセッションには null を返す — 終わった問題は保存しない)、
  `restoreSession(value)`(セッションか null)と `checkRecord(value)`(同じ検査で、拒否の理由を返す —
  テストが条件ごとに理由を確かめるため)。`schemaVersion` と `savedAt` も `restoreSession` が自分で
  確かめる。キーと `mode` の照合と今日でないデイリーは保存の層の仕事で、`game/` は持たない。選択中の
  タイルと演算子は保存しない(再開は何も選ばれていない状態から)。

### 手の文字列

- **1 手 = 3 文字**: 左の項のスロットの数字(`0`〜`5`)・演算子(`+` `-` `*` `/` の ASCII 1 字)・
  右の項のスロットの数字。例 `0*3` は「スロット 0 の値 × スロット 3 の値」で、結果はスロット 3 に入り、
  スロット 0 が空く(§1)。保存の演算子は ASCII で、画面の記号(`−` `×` `÷`)とは別のもの。
- **手の列** = 手の文字列を区切りなしにつないだもの。長さは 3 の倍数で、最大 3(n−1) 文字
  (v1 は 12 文字)。保存する解も同じ形(ちょうど 3(n−1) 文字)。

### 中断レコード(`tg.saveGame` / `tg.saveDaily`、schemaVersion 1)

| フィールド       | 型                     | 内容                                                 |
| ---------------- | ---------------------- | ---------------------------------------------------- |
| `schemaVersion`  | `1`                    |                                                      |
| `mode`           | `'free'` \| `'daily'`  | キーと一致しなければ破損として捨てる                 |
| `seed`           | string(空でない)       | §8 の形                                              |
| `difficulty`     | `easy`/`medium`/`hard` | デイリーは `medium` だけ                             |
| `dailyDate`      | `YYYY-MM-DD` \| null   | デイリーだけが持つ。Free Play は null                |
| `numbers`        | 整数の配列             | 配った数字(昇順)                                     |
| `target`         | 整数                   | 目標                                                 |
| `solution`       | string                 | 保存する解(手の列、3(n−1) 文字)。§5 の解の表示に使う |
| `moves`          | string                 | 打った手の列(Undo の履歴を兼ねる)                    |
| `repeat`         | boolean                | 解いた問題の再挑戦か(§9)。デイリーは偽だけ           |
| `elapsedSeconds` | 0〜10⁹ の整数          | 書く側は範囲に収める(下)                             |
| `savedAt`        | 0〜10¹⁵ の整数(ms)     | 保存の層が書く時刻。書く側は範囲に収める             |

状態(`playing` / `missed`)は保存しない(手の列の再生から決まる)。Undo の履歴も別に持たない。
`solved` と `revealed` の問題は保存しない(その時点でスロットを消す)。

**書く側は、受け入れられる形しか書かない**: `toRecord` は経過秒を 0〜10⁹ の整数秒にして書く(端数は
切り捨て、負や数でない値は 0、上限を越えたら上限 — Peg Solitaire §11 の `wholeElapsedSeconds` と同じ)。
`savedAt` も、保存の層が時刻(ms)を 0〜10¹⁵ の整数に収めて書く。状態の層がどんな時計を持っていても、
書いた記録が範囲外で自分に捨てられることはない(`schemas.test.ts` が確かめる — §15)。`game/` の側では、
遊びが届くセッション(`newSession.ts` の 2 つの入口が作り、セッションの関数で動かしたもの)の記録はどれも
`restoreSession` が読む(`newSession.test.ts`・`properties.test.ts`)。そのために `newFreeSession` は空の
token を拒む(§5)。手で組んだ不正な seed のセッションまでは `toRecord` は確かめない。

### fail-closed の条件

次のどれかに当たるレコードは読み捨て、プレイヤーはゲームのホームに着く(**黙って新しい問題を
始めない**)。**検査はすべてスロットのスキーマの `validate` が行う**(`storage/schemas.ts` の
`gameSlotSchema(key, expectedMode)`)。`validate` は、形(型・範囲・必須フィールド)と「キーとの
食い違い」を見たうえで、ゲーム側の復元(`game/restore.ts` の `restoreSession`)を呼ぶ。
`restoreSession` は純粋で探索を持たず(§6。手の列と保存した解を問題の上で再生する — 仕事量は最大
n−1 手 + n−1 手)、**それに頼らず**全フィールドの型と範囲を自分で確かめ、どんな値を渡されても例外を
投げずに null を返す。各フィールドは最初に 1 回だけ読み、`numbers` は写してから確かめて、確かめた値だけを
使う(読むたびに値の変わる getter や配列で、確かめた値と遊ぶ値が食い違わないように。JSON から読んだ値には
getter は無いが、慣例に頼らない)。`validate` も例外を投げず、通らなければ null を返す
([architecture/backup.md](architecture/backup.md) の契約)。`restoreSession` の外で読むフィールド
(`schemaVersion`・`seed`・`savedAt`)もあるので、`storage/schemas.ts` の 4 つの `validate`(2 つのスロット・
stats・flags・prefs)は本体を `try` で包み、どこで例外が起きても null にする(読み込みの側
`src/storage/repo.ts` も `validate` を `try` で包むが、約束はスキーマ自身が持つ)。ゲームがスロットを読み込むとき
(`storage/gamePersistence.ts`)は、検証を通った記録から同じ `restoreSession` で盤を組み立てる。
**`validate` の外に置くのは「今日でないデイリー」だけ**: 今日を知っているのは読み込みの側で
(`validate` は日付に依存せず、バックアップの復元でも同じ答えを返す)、そこでレコードごと消す(§8)。

- 形が違う: 型・範囲・必須フィールドの欠落・`schemaVersion` が 1 でない。`mode` が `free` / `daily`
  以外、`difficulty` がこのゲームに無い値、`seed` が空か 120 文字を超える(`MAX_SEED_LENGTH`。Free Play の
  seed は約 40 文字、デイリーは 32 文字 — Phase 3 でスキーマの形の検査に足した)、`elapsedSeconds` が 0〜10⁹ の、`savedAt` が
  0〜10¹⁵ の整数でない(NaN・負・小数・無限大・範囲を超える大きな数 — `1e300` は「0 以上の整数」を
  通ってしまうので、上限まで見る)、`numbers` が整数の配列でない、`solution` / `moves` が文字列でない、
  `repeat` が真偽値でない。
- `mode` がキーと食い違う。デイリーなのに日付が無い(実在の `YYYY-MM-DD` でない)、Free Play なのに
  日付がある、デイリーなのに `medium` でない、デイリーなのに `repeat` が真(デイリーの再挑戦は
  `dailyTimes` のキーで決まる — §9)。
- `seed` がそのモードの形でない: デイリーはその日付の seed(`dailySeed(dailyDate)`)と一致しなければ
  ならず、Free Play は `make-the-target-<difficulty>-<token>` の形(token は空でない)で、難易度が
  記録の `difficulty` と一致しなければならない。
- **問題がいまのティアの形でない**(`isDealableShape` — `game/tiers.ts`。復元から呼ぶので生成器を
  import しない — §5): `numbers` の長さがそのティアの枚数に無い
  (v1 では 6 枚は必ず捨てる)・昇順でない・範囲外の数(Hard は 11〜25 の数がちょうど 1 か 2 枚で、
  残りが 1〜10)・`target` が帯の外。
- **`solution` が解でない**: 長さが 3(n−1) でない・3 文字に分かれない・存在しないスロットや空いた
  スロットを指す・同じスロットどうし(`0+0…` のような手)・規則が拒む手(§2。`isLegalMove` がスロットの
  条件も持つので、`moves` と同じ関数が拒む)・最後の値が `target` でない。
- **`moves` が再生できない**: 長さが 3 の倍数でない・3(n−1) を超える・存在しないスロットや空いた
  スロット・同じスロットどうし・規則が拒む手(`solution` と同じ `isLegalMove`)。
- 再生した結果がクリア済み(n−1 手で目標に等しい)— 終わった問題は履歴であって再開するものでは
  ない。`restoreSession` 自身が null を返す。n−1 手で目標と違う(`missed`)レコードは正しい中断と
  して読む(§4 のパネルから再開する)。
- 今日でないデイリー — **これだけは `validate` の外**で、読み込み側(`gamePersistence.ts`)が見て、
  レコードごと消す(§8)。日付を見るのは `validate` を通ったレコードだけである。`validate` が拒んだ
  デイリーは、日付にかかわらず、ほかの読み捨てたレコードと同じく消さずに残り(下)、スロットは空として
  扱われ、次のデイリーが上書きする(Loop Puzzle と同じ順)。

**確かめないこと(正直に)**: 読み込みでは列挙しないので、`ways` の帯(§7)と Medium の「Easy の
条件を満たさない」は確かめない。またデイリーの問題がその日の生成器の問題と同じかも確かめない
(確かめるには生成 = 探索が要る)。細工した保存は、ティアの形と解の正しさを満たすが帯の外の問題を
持ち込める。持ち込まれても起きるのは「その問題が帯より易しい・難しい」ことだけで、解けることは
保存した解の再生で確かめてある。デイリーの日ごとの最短秒は自分の端末の記録で、ほかのプレイヤーとは
比べない(Club House に登録しない — §16)ので、この緩さを受け入れる。

`validate` が読み捨てたレコードはストアに**残る**(消さない)が、そのスロットは空として扱う(ホームに
「続きから」は出ず、ショートカットもホームへ着く)。次にそのスロットで問題を始めたときに上書きされる。
読み捨てても統計には何も足さない。壊れたレコードがほかのゲームを止めることはない(各ゲームの保存領域は
独立 — [ARCHITECTURE.md](ARCHITECTURE.md))。ティアの表(§7)を変えた版では、それより前の中断のうち新しい
形に入らないものが読み捨てられ、その中断を含むバックアップは復元全体が拒否される(下の「検証の置き場所」)。
ベータ中はこれを許す(上の「凍結しない」)。

- **検証の置き場所**(Web 先行公開の 4 本 — Snake / Loop Puzzle / Bridges / Peg Solitaire — に共通の
  規則で、各ルール文書の保存の節が同じことを書く。**Unblock Puzzle は形の検査を `SchemaDef`、再生を
  `restoreSession`(`gamePersistence.ts` の呼び出し)に分けているが、この文書は 4 本に従う** — 計画
  「保存と統計」も「検証はスキーマの `validate` の中で、問題の上で手の列を再生して終える」と書く):
  - **仕事量が盤の大きさで決まる検査は、規則の検査も含めてすべてスキーマの `validate` に置く。**
    手の列の再生(最大 n−1 = 4 手)と保存した解の再生(同じく 4 手)は、盤の枚数(最大 6)で仕事量が
    決まる。ティアの形の判定も表の引きだけである。バックアップの書き出しと復元は、レコードを持ち主の
    `validate` だけに通す([architecture/backup.md](architecture/backup.md)「検証は各レコードの持ち主が
    行う」)。だから**ルールから生まれえない中断(違法な手・解でない解・ティアの形でない問題・クリア済みの
    盤)は書き出しに入らず**、それを含むバックアップの復元は「壊れている」(`backupFileDamaged`)として
    全体を拒否し、何も書かない。形だけをスキーマに置き再生を読み込み側に置く形(Unblock 型)にすると、
    そうした記録がバックアップに入り、復元が成功と出たのに開くときに黙って捨てられる。
  - **スキーマの外に残すのは、仕事量をノード数の上限が抑える探索だけ**(Bridges の一意性の再証明、
    Loop Puzzle の計数探索)。このゲームの読み込みにはそのような探索が無く、スキーマ以上のことは検査しない
    (`gamePersistence.ts` が `restoreSession` をもう一度呼ぶのは、盤を組み立てるためである)。
  - **読み捨てた記録はストレージから消さない**(上。今日でないデイリーは §8 のとおり消す)。消さないのは、
    スキーマが読めない記録は新しい版が書いたものかもしれないから(backup.md は「新しすぎる」と「壊れて
    いる」を分ける)。プレイヤーはホームに着き、新しい問題を始めれば置き換わるので行き止まりにはならない。
  - 再生はスロット番号・手の規則(§1・§2)・ティアの表(§7)をそのまま使うので、それらを変えると、変える前に
    保存した中断の一部が検証を通らなくなり、その中断を含む変える前のバックアップは復元全体が拒否される。
    ベータ中はこれを許す。正式収録の後は、変える前に互換のテスト(Peg Solitaire の
    `compatibility.test.ts` の形)を置く。
  - `validate` 1 回の時間は測っていない(Phase 3 でも測らなかった。再生は最大 8 手で、仕事量は手数で
    決まる)。

### `tg.stats` / `tg.flags` / `tg.prefs`

- `tg.stats`(schemaVersion 1): `easy` / `medium` / `hard` ごとに `played` / `solved` /
  `totalPlaySeconds` / `bestSeconds`(null 可)、`daily` に `played` / `totalPlaySeconds`、と
  `dailyTimes`(`YYYY-MM-DD` → 秒の疎な表、最大 2,000 件)。各行は整数で、`played` / `solved` は
  0〜10⁹、`totalPlaySeconds` は 0〜10¹²、`bestSeconds` と `dailyTimes` の秒は 0〜10⁹(`bestSeconds` は
  null 可。Loop Puzzle / Unblock Puzzle と同じ範囲)。どれかが壊れていれば記録全体を既定値に戻す
  (fail-closed)。`dailyTimes` だけは読めない 1 件を捨てて残りを守る。
- `tg.flags`(schemaVersion 1): `tutorialCompleted`(boolean)だけ。
- `tg.prefs`(schemaVersion 1): `difficulty`(最後に選んだ難易度。初期値 `easy`)だけ。問題の遊び方を
  変えるものは何も入れない。フィールドが無い・難易度でない値は既定値に戻す。

## 12. 演出とアクセシビリティ

- **アクセントは目標の枠と選択中のタイル(とクロム)だけ**(`--accent`、紺桔梗。`styles.css` に登録
  済み)。ほかのタイルは中立の面色に枠線。**色だけに頼らない**: 選択は太い枠と浮き上がりと
  `aria-pressed`、目標は枠の太さと的の印、無効の演算子は無効の見た目と `disabled`、クリアは目標の枠の
  面と結果カード。ライト / ダークの両方で [BRAND.md](BRAND.md) のコントラストを守る。
- **360×640 でスクロールなし**に、目標・タイル(v1 は最大 5 枚)・演算子 4 つ(`missed` ではその欄に出る
  パネル)・式の行・Undo が収まる(Web は下の広告の予約 116px 込み — `:root[data-sg-web-ads]`)。タイルと
  演算子の的は 48px を下回らない。6 桁の数がタイルに収まる(桁数で文字を小さくする — 4 桁 21px・5 桁 18px・
  6 桁 15px)。**並びは 1 行**(Phase 3 で決めた。v1 は最大 5 枚)。**算術では**(`ui/make-the-target.css` の
  寸法から): 360×640・Web の予約 116px 込みで、上のバー 64px と Undo のバー 77px を除いた 383px に、盤の列
  (目標 52・タイル 56・演算子の欄 100・式の行 4 × 21 と間隔・余白)が最大 338px で収まる。タイルの幅は 5 枚で
  (360 − 32 − 4 × 8) / 5 ≈ 59px、6 枚でも 48px、演算子は 64 × 56px。**実機の実寸は測っていない**(Phase 3 ではブラウザで測らなかった。Phase 4 の統合でヘッドレス Chromium の
  360×640 で Quick Rules・ホーム・盤面にスクロールが出ないことだけ見た — 計画「Phase 2〜4 の実施結果」。§15)。矢印キーの動きは並びに依らず、スロット番号の順に 1 本の列を進む
  (§3。2 行のときも ↑↓ は行の移動にしない)。盤(目標・タイル・演算子)の大きさは言語で変わらない
  (盤に文字が無い)。
- **`missed` のパネル**(§4)は盤の外にあり、演算子の行の欄に**同じ固定の高さ**(100px)で入る(文 2 行
  以内 = 15px の文字で 2 × 19px + ボタンの 1 行 48px。算術では収まる。実寸は測っていない)。パネルの文は言語で長さが変わるので、**14 言語の確認で、各言語の
  最長の文(`That makes {value}, not {target}.` の訳に、最大の桁数の値を入れたもの)を差し込み、360 幅で
  2 行以内に収まり、盤とその下が動かない**ことを測る(Loop Puzzle §14 の確認の形)。ボタン(Undo・
  解を 1 つ見る)のラベルも 1 行に収まる長さで訳す。この間、盤の下の Undo は隠れる(§3)。
- **読み上げ**: 盤は `role="group"`(名前は「数字」の i18n キー)。各タイルはボタンで、値と選択中か
  (`aria-pressed`)を読む。演算子のボタンは名前(足す・引く・掛ける・割る)を i18n キーで読む。目標は
  「目標 {target}」。手を打つたびに、live region(polite)が式の行(「7 × 3 = 21」を読み上げの名前で)を
  1 回読む。Undo のときは戻した式を読む。`missed` のパネルは §4(読むのは手の式とパネルの文を 1 文にした
  `makeTheTargetSpokenMissed`)。数字は ASCII で、文言は `{var}` の埋め込み(連結しない)。式の行は演算子
  ごとに文全体を 1 つのキーにする(`makeTheTargetSpokenLine_add` / `_subtract` / `_multiply` / `_divide` —
  演算子の語だけを別の文に差し込むと、助詞や格で文を変える言語が訳せない)。live region は `.game-content`
  の外に置く(クリアの手で `.game-content` が `inert` になり、inert の中身は支援技術から隠れるので、中に
  置くと最後の式が読まれない)。
- **演出**: まとめの演出は、先に選んだタイルが後に選んだタイルへ寄る CSS の短い遷移だけ。**状態は
  タップで即座に変わり**、演出の終わりを待たせない(連打してよい)。Reduced Motion(OS の設定と
  アプリの設定 `data-reduced-motion`)では演出なし。クリアの一拍も Reduced Motion では即時。称賛・星・
  紙吹雪・タイマー表示は作らない。連続再描画はしない(盤は手のときだけ描き直す)。
- 押下のフィードバックは地色の切り替えで出す(`filter` は使わない)。続けて押すボタン(タイル・演算子・
  盤の下の Undo・パネルの Undo)は `touch-action: manipulation`(共有の CSS はどこにも付けないので、
  `ui/make-the-target.css` が 4 つとも付ける)。
- **音**は既存の `services/sound.ts` だけ: タイルと演算子を選んだとき `sounds.select`、Undo で
  `sounds.undo`、クリアで `sounds.clear`。不成立の手・`missed`・解の表示では鳴らさない。新しい音・画像・
  アセットは足さない。
- CSS は `ui/make-the-target.css`(css-split の窓の中。共有トークンだけで、自前の色値は書かない —
  [architecture/css-split.md](architecture/css-split.md))。

## 14. 意図的な差分

### ブランド原則により合わせないもの

- 制限時間・カウントダウン・時間切れ(作らない。§2・§9)
- 近い数への部分点・得点(作らない。比べるのは自分の経過秒だけ — §9)

**計画からの差分の中身**:

- **① Hard の 6 枚**: 計画の推奨は「6 枚の列挙が上限 50,000 状態に収まれば 6 枚を出す」。Phase 2 の実測でも
  1 回の列挙は最悪 23,456 状態で収まるので、この基準だけなら 6 枚を出せる。v1 が 5 枚なのは、Hard の帯
  (`ways` ≤ 40)を満たす 6 枚の問題がほとんど無いためで、Phase 2 の 6 枚の測定のテスト(§7・§15)が稀さと予算を
  分けて測った: 帯に入った 6 枚の候補 300 個のうち `ways` ≤ 40 は 0 個(予算に関係なく)、50,000 の予算では
  列挙が約 4 回、出荷する試行の繰り返しでは 100 seed 中 99 seed が上限に届いた。この判断は**文書の著者の
  もの**で、帯を手順の数で置くという選択(②)に支えられている。6 枚を戻すなら、木の数で帯を置く案から。
- **② Hard の「解が少ない」**: 計画の Hard の初期案「解が 1 通りに近い」・推奨の「解の数が少ない」を、v1 は
  手順の数の上限(`ways` ≤ 40)に置き換えた。手順の数は式の木の数ではなく(§6)、`ways` ≤ 40 は「解が
  1 通りに近い」を意味しない。計画の全数のオラクル「素朴な木」も「素朴な列挙」に替えた(§15)。Phase 2 の
  分布を見て、v1 は木で置き直さないと決めた(§7。手順の数の帯で Hard は作れており、1,000 seed で帯のために
  落ちた seed は 0)。木の数は数えていない(未検証)。
- **③ 題の確認の時期**: 計画の期限は「scaffold の後・実装の前」(共通要件。題の確認の推奨は「Phase 2 の
  前」)。この環境にネットワークが無く検索できなかったため、実装(Phase 2・3)は確認なしで進む。新しい
  期限は「正式収録とストア掲載の前」(冒頭・§14)。オーナーには、実装が確認なしで進んだことを知らせる。

この文書で新たに決めたこと(計画に無かった選択): 結果の置き場所(右の項のスロット、§1)、手順の数の
定義(値の手の列、§6)、仕事量の数え方(展開した多重集合 + 試行ごとに 1、§6)、解を組むときの演算子の選び方
(等確率、「÷ の要る回」だけ ÷ を先に 1/2、§6)、Medium の「÷ の要る回」1/3 と受け入れの述語(§7)、同梱の
問題数(各 24、§6)、`missed` のパネルをモーダルにせず盤の外に置くこと(§4)、解の表示の前の確認(§5)と

**Phase 2(ロジック)で決めたこと**(この文書が決めていなかったところ。どれもオーナーの判断を要する
種類ではないと考える):

- Medium の「÷ の要る回」では、÷ を使わずに組んだ解の候補を列挙せずに捨てる(§6 手順 4。受け入れられない
  候補の列挙を省くだけで、上限に届かない seed の問題は変わらない)。
- ÷ の要る問題には `ways` の上限を置かない(§7。測った最大 137 / デイリー 156)。
- 同梱の表は、前の行と同じ数字・目標になった seed も飛ばす(§6。Easy の k = 18)。表は各行に `ways` /
  `waysWithoutDivision` を持ち、落ちるときに探索しない。
- バレル(`game/index.ts`)はソルバーのほかに生成器・同梱の問題・`newSession.ts` も再輸出しない。生成器は
  上限で自分で同梱へ落ちるので、同梱の問題を import するのは生成器だけ(§5)。
- 押しても何も変わらない押下(空いたスロット・タイルなしの演算子・拒まれる手・終わった盤)では、
  セッションの関数は渡されたのと同じオブジェクトを返す(§5 の実装の形。画面が描き直さずに済む)。
- `restartSession` は `revealed` のセッションには null を返す(解を見た問題には再挑戦が無い — §5)。
  `toRecord` は `solved` / `revealed` に null を返し、`restoreSession` は `schemaVersion` と `savedAt` も
  確かめる(§10)。
- 全数のオラクルと 1,000 seed の数え直しは別の 2 つの別実装(タイル単位の素朴な列挙と、値単位の記憶なしの
  列挙)で、後者は前者と全数で突き合わせた(§15)。
- 6 枚の測定の標本は候補 300 個・100 seed(計画の例は 2,000 個・300 seed。テストの時間のため — §15)。

**Phase 3(画面・保存・状態)で決めたこと**(この文書が決めていなかったところ。どれもオーナーの判断を
要する種類ではないと考える):

- 保存のスキーマの形の検査に seed の長さの上限(120 文字、`MAX_SEED_LENGTH`)を足した(§10)。`restoreSession`
  の検査はそのまま。
- 選択(タイル・演算子)だけが変わったときは保存を書かない。保存は手の列が変わったときと、離れる・背景に回る
  ときの同期だけ(選択は保存しない — §10 — ので、書いても同じ記録になる)。
- `missed` の問題は「遊んでいる問題」として扱う: 保存・再開・ショートカットの「中断」・プレイ時間の時計の
  どれでも `playing` と同じ(Undo 1 回で遊びに戻るため)。
- 並びは 1 行(§12)。押したタイルの音(`sounds.select`)はタイルや演算子を選んだ・解除したとき、`playing`
  に留まるまとめのときに鳴らし、まとめが `missed` になる手では鳴らさない(§12「`missed` では鳴らさない」)。
  まとめが `solved` になる手は `sounds.clear` だけ。
- まとめの演出は、答えの入ったタイルが左の項のスロットの位置から 160ms で寄る CSS の遷移(`tg-arrive`)。
  Reduced Motion(OS とアプリの設定)では描かない。
- 結果カードの事実は難易度・枚数・目標・時間の 4 行(§9)。解を見た後のカードは解の行と難易度・枚数。
- 統計画面の「クリア数」は en「Problems solved」(Bridges の「Boards solved」の形 — §9・§17 の暫定)。
- 13 言語のファイルは型を通すために `en` の値を写した仮文にした(§13)。これは Phase 3 の間だけの
  つなぎで、下の訳の段で `ja` と 12 言語の訳に置き換えた。
- ホームの難易度のボタンに最短の秒を出さない(§9。Loop Puzzle / Bridges の前例とは違える)。
