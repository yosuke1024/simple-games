ゲーム ID は `tangram`、i18n キーの接頭辞は `tangram`、保存キーの接頭辞は `tn.`、カテゴリは `puzzle`、No. 56。

7 枚の駒を回し・裏返し・自由に置いて、出題の影絵(シルエット)を隙間なく埋める一人用のパズル(一般に

最小の盤だけの試作(`apps/simple-games/prototypes/phase0/tangram-board.html`、使い捨て)を実機 2 台で触って
確かめる(Phase 0)。通過条件は「7 枚を 45° 刻みで回し・裏返し・吸着させて、Easy の影絵 3 つを 360 幅で
誤操作なく埋められる」。**2026-10-21 の時点で実機での試行は行っていない**(試作とヘッドレスの検査は済み —
計画の「Phase 0 の試作」)。Phase 2 は「通る」と仮定して進めるので、**§4 の操作は「暫定(Phase 0 未実施)」**
で、試行の結果で直しうる。**通らなければ Tangram は Three Peaks**(cards・id `three-peaks`・保存接頭辞 `tp.`・
i18n 接頭辞 `threePeaks*`)**に差し替え、この文書は `docs/THREE_PEAKS_RULES.md` のスタブに置き換わる**
(差し替え PR が変える接続点は、計画の「Phase 0 と差し替え」)。差し替えを安くするため、このゲームのコードは

## 1. 規則

- 影絵が 1 つ出題される。駒は 7 枚: **大三角 2・中三角 1・小三角 2・正方形 1・平行四辺形 1**(§5 の表)。
- **7 枚すべてを、重ねず・はみ出さず・隙間なく**影絵の中に置けば完成。
  - 置いた駒は影絵の中になければならない(辺や頂点が影絵の縁に接するのはよい)。
  - 置いた駒どうしは重ならない(辺や頂点で接するのはよい)。
  - 算術では 7 枚の面積の和は影絵の面積と等しい(§2 の不変条件)ので、7 枚がこの 2 つを満たして置かれた
    時点で隙間は無い。**完成は「7 枚とも置かれている」ことと同じ**である(§5「完成」)。
- 回転は 45° 刻みの 8 方向。**裏返せるのは平行四辺形だけ**(ほかの 6 枚は鏡に映した形が回転で出るので、
  裏返しに意味が無い。平行四辺形の鏡像は回転では出ない — §5)。
- 駒の形は伝統どおり。小三角の脚を 1 とすると、中三角の脚 √2、大三角の脚 2、正方形の辺 1、平行四辺形の
  辺 1 と √2(内部の単位はその 2 倍 — §5)。
- **完成は幾何で判定する。**カタログに書いた解とは比べない。影絵は複数の解を持ちうるので、駒の順序・
  同じ形の 2 枚の入れ替え・別解のどれでも完成になる。
- 時間制限・手数制限・得点・星は無い。負けも無い(終わり方は完成だけ)。
- 遷移は `game/session.ts` の `status`(`'playing' | 'complete'`)で一度だけ起きる。完成した局は
  それ以上変わらない(Undo もできない — §3)。

## 2. 図形(カタログと由来)

**影絵は実行時に生成しない。**同梱のカタログ(`game/catalog.ts`)から出す。駒を無作為に並べて影絵を作ると、
抽象的な塊になる・辺がわずかにずれた微小な段ができる・「解けること」を確かめる探索の仕事量が要る —
同梱ならどれも起きない。前例は Unblock Puzzle の同梱の一覧(UNBLOCK_PUZZLE_RULES.md §8)と Peg Solitaire の
Triangle の表(PEG_SOLITAIRE_RULES.md §8)。**実行時の探索は 1 つも無い**(§5)。

### 1 図形の形式

座標の表し方は §5(`Pt` = `[xa, xb, ya, yb]`、x = xa + xb√2、y = ya + yb√2。単位は小三角の脚の半分)。

```ts
type PieceId = 'L1' | 'L2' | 'M' | 'P' | 'SQ' | 'S1' | 'S2';
type Pt = readonly [xa: number, xb: number, ya: number, yb: number];
interface Pose {
  readonly r: number; // 0..7。45° × r、画面で時計回り
  readonly f: 0 | 1; // 裏返し。1 は P だけ
  readonly at: Pt; // 駒の頂点 0 の位置(§5「姿」)
}
interface Figure {
  readonly id: string; // 安定した文字列 /^[a-z][a-z0-9-]{1,31}$/。番号ではない
  readonly tier: 'easy' | 'medium' | 'hard';
  readonly outline: readonly Pt[]; // 影絵の輪郭。1 本の単純多角形
  readonly solution: Readonly<Record<PieceId, Pose>>; // 検証用の解(と Easy の内側の線)
  readonly fixed: readonly PieceId[]; // Medium だけ 2 枚。Easy / Hard は []
  readonly origin: 'original'; // v1 は自作だけ(下の「由来」)
}
```

- `FIGURES` は 1 本の配列で、**ティアごとの並び順がそのまま出題の順**(§6)。画面に出す番号は、その
  ティアの中で何番目か(1 始まり)。並び順を変えると番号は変わるが、保存と記録は `id` で結ぶので壊れない。
- 図形の **id はベータの間に座標を直しても変えない**。図形を消したら、その id の保存は読み捨て、記録は
  その件だけ捨てる(§7・§8)。id は画面にも読み上げにも出さない(名前は出さない — §12)。

### カタログの不変条件(`game/catalog.test.ts` が全図形について確かめる)

- **輪郭**: 頂点 3〜32 個。**単純多角形**(隣り合わない辺どうしは端点も含めて交わらず、隣り合う辺は共有の
  頂点だけで接する)。同じ頂点を 2 度通らない(頂点だけで接する「くびれ」も、穴も、この形式では書けない —
  §12)。どの辺も 8 方向のどれか(Δx = 0・Δy = 0・Δx = ±Δy が厳密に成り立つ)。続く 2 辺が同じ向きに並ば
  ない(途中の頂点を持たない)。**画面で時計回り**(y は下向き。靴紐公式の和が正)。外接矩形の左上が原点
  (x の最小 = 0、y の最小 = 0)で、最初の頂点は y が最小のうち x が最小のもの。
- **大きさ**: 外接矩形の幅と高さはどちらも **13 単位以下**(小三角の脚 6.5 本ぶん。厳密な比較)。360 幅・
  盤 328 px・余白 16 px なら使える幅は 296 px で、算術では、上限いっぱいの幅 13 単位の影絵の小三角の脚は
  296 ÷ 13 × 2 ≈ 45.5 px。試作では、幅 8√2 ≈ 11.3 単位の影絵の脚が 52 px になった。計画が目安にした
  「幅 9.5u 前後」(試作の u は √2 単位なので約 13.4 単位)は、算術では脚が約 44.1 px で、**脚が 43 px を
  切るのは幅が約 13.77 単位(9.73u)を越えてから**(計画の「9.5u を超えると 43 px を切る」は 1 px ほど厳しい
  値)。実機で 45 px や 52 px でも小さすぎれば、この上限を下げる(§13)。
- **面積**: 輪郭の面積は **32 単位²**(厳密。脚 1 を単位にとると 8)。
- **解**: 7 枚ぶんちょうど(キーが 7 つの `PieceId`)。`r` は 0〜7 の整数、`f` は 0 か 1 で、1 は `P` だけ。
  各駒が輪郭の中にあり(§5「内包」)、どの 2 枚も重ならない(§5「重なり」)。これと面積 32 から、**影絵は
  解の 7 枚の和に等しい**(7 枚の面積の和が 32 なので — §5「完成」)。
- **座標の大きさ**: 輪郭と解の `at` の各成分の絶対値は 64 以下(§5「範囲」)。
- **座標の偶奇**: 輪郭の頂点の有理部(`xa`・`ya`)と解の `at` の有理部はどれも**偶数**。吸着で生まれる姿の
  頂点はすべて有理部が偶数の点に乗る(§5「吸着」の補足)ので、輪郭が偶数なら、吸着で組める配置はこの条件を
  満たし、保存の検証が同じ条件を求めても(§8 `bad-piece`)落ちない。
- **固定の 2 枚**: Medium は異なる 2 枚(既定は `L1` と `P` — §3)、Easy と Hard は空。
- **吸着だけで組めること**: 影絵の頂点と置いた駒の頂点だけを吸着先にして(§5「吸着」の頂点吸着だけ)、
  解の 7 枚をある順に置けること — Medium は固定の 2 枚を先に置いた状態から。順は貪欲に探す(置ける駒は
  後でも置けるので、貪欲で決まる)。算術では、完成した配置ならどれでもこの順が存在する(§5「吸着」の
  補足)。テストはそれを図形ごとに確かめる(**Phase 2 のテストで実測**: 34 図形すべてで、`snapPose` の頂点
  吸着 — 解の位置ちょうどの望みに許容 0 で — だけで解の 7 枚を置き切れた)。
- **重複なし**: id が一意。どの 2 図形も、平行移動・45° 刻みの回転・鏡映(計 16 通り)で重ならない
  (輪郭を正規化して厳密に比べる)。
- **デイリーの刻み**: Medium の図形数とデイリーの刻み 7,919 が互いに素(§6)。
- **由来**: v1 の全図形が `origin: 'original'`。

### 由来

- **v1 に伝統図形は入れない。**計画が候補に挙げた刊本(19 世紀初めの中国の図譜・欧州の刊本、
  Sam Loyd、H. E. Dudeney)は、**出典を実際に確かめるまで使わない**。この環境ではネットワークが使えず
  確かめていない(§12「比較対象との対応」)。確かめた図形を足すときは `origin` に `'traditional'` を
  加え、出典・刊行年・確認日を §12 に書き、座標は刊本の図を見て自分で起こす。
- 自作の図形は、7 枚の駒の配置から自分で起こす。既存アプリの図形データ・画像・配色は見ない・写さない。
  `square` は 7 枚の駒を切り出す元の正方形そのもの(この形式の定義)で、`triangle` / `parallelogram` は
  その 2 つの半分を写して作った(試作の作り方)。

## 3. ティアと助け

### ティア

Easy / Medium / Hard は**カタログの分類**で、図形ごとに著者が決める。**難しさを測るテストは無い**(§13)。
目安:

- **Easy**: 凸か凸に近く、大三角 2 枚の置き場が一目で分かる図形。**影絵の内側に解の 1 つの区切りを薄い線で
  示す**(解の 7 枚の辺のうち輪郭でないもの)。置いた駒の下では消える(駒が覆う。2 段目の濃さの駒・固定の
  駒の薄い面の下にも地の色の不透明な面を敷くので、線は駒を透けない — §10)。線は見せるだけで、
  **吸着先ではない**(§5「吸着」 — 線に吸着させると解の枠へ引き込まれ、置き場を選ぶ判断が消える。試作の
  比較用の規則 `guide=1` がそれで、判定には使わない)。**Easy は形合わせとして作ってある**(計画のティアの
  定義)— 区切りの線は駒ごとの置き場を、形と向きを合わせれば示す。下の「Hint は作らない」の理屈は
  Medium と Hard に当てはまり、Easy には当てはまらない。
- **Medium**: **解の 2 枚を最初から置いた状態で出す**(固定。どの 2 枚かは図形ごとにカタログの `fixed`。
  既定は大三角 1 枚 `L1` と平行四辺形 `P` — 裏表の判断を 1 つ外す。**どの 2 枚が遊びやすいかは Phase 0 の
  試作で Medium の図形を 1〜2 つ触って決める予定のもので、その実機の試行はまだ — 暫定(Phase 0)、§12**)。
  固定した駒は動かせず(ドラッグ・タップ・回転・裏返しでは姿が変わらない)、Undo でも ↻ でも戻らない。
  **押す・フォーカスすると選ばれる**(読み上げと太い枠のため。選ぶだけで姿も履歴も変えない。選ばれている間
  は回転・裏返しのボタンが押せない — §4)。読み上げで「固定」と言い、見た目は点線の枠と沈んだ面で分ける
  (色だけに頼らない — §10)。
- **Hard**: 影絵だけ。平行四辺形の裏表と小三角の向きが決まりにくい図形。

デイリーは Medium の図形を出す(§6)。

### Undo

- **無料・無制限**(履歴の上限は 2,000 操作 — `UNDO_HISTORY_LIMIT`。越えたら最も古いものから捨てる。
  Block Puzzle §7 と同じ形)。1 回の Undo で 1 操作ぶん戻る。**1 操作**は次のどれか 1 つ:
  - 置く(トレイ → 盤)/ 置き直し(盤 → 盤の別の位置。「戻す + 置く」をまとめて 1 操作)
  - 回す(盤の上でも、トレイでも)/ 裏返す(同じ)
  - トレイへ戻す(Escape、盤の駒を置けない位置で離したとき、盤の駒を運んでいる途中の `pointercancel` —
    どれも §4)。**トレイへ戻った駒は、盤の上にあったときの向き (r, f) のままトレイに並ぶ**(既定の向きへは
    戻さない。試作もそう)。
- 何も変えなかった入力は操作に数えない: 置けない位置で離したトレイの駒、置けない姿になる盤の上の回転、
  **盤の駒を同じ姿(r・f・at がすべて同じ)に置き直すこと** — 吸着した点が違って支点だけが違っても同じで、
  支点は元のまま(履歴にも音にも出ない)、固定の駒への入力(押す・フォーカスするは選ぶだけ)。
- Undo は盤の駒の姿・支点(§5)・トレイの駒の向きを、その操作の直前へ戻す。置く操作の Undo は駒を置く
  前の向きでトレイへ戻し、トレイへ戻す操作の Undo は駒を盤の元の姿と支点へ戻す(トレイの向きの記録も
  操作の前の値へ戻る)。固定の 2 枚には触れない。
- **履歴は保存しない**(§8)。再開した局はその配置から始まり、Undo は空。置いた駒はいつでも持ち上げ直せる
  ので、失うものは小さい。Unblock Puzzle §11 / Peg Solitaire §6 は手の列を保存して再開後も Undo できる形
  だが、ここでは採らない — 局面が手の列から一意に決まる盤と違い、この盤の状態は 7 枚の姿そのもので、
  操作の列を保存してもそれを検証する以上のことが得られないため。
- **完成した局は Undo できない**。完成で局は終わり(§1)、保存も消す(§8)。2048 などの慣例どおりで、
  Peg §6 の「終局後も戻せる」は、完成に「別の終わり方」が無いので採らない。
- Undo の回数は記録しない(無料の Undo を使わせない圧になる — Schulte §9 と同じ理由)。
- 広告視聴や課金による Undo は作らない([ADS_POLICY.md](ADS_POLICY.md))。

### Hint は作らない

影絵も駒も全部見えていて、隠れた情報が無い。「どの駒をどこに置くか」を教えることはパズルそのものを
肩代わりする(PEG_SOLITAIRE_RULES.md §6、[PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md)「必須原則」の
Sliding Puzzle の判断と同じ理由)。解の自動配置・「あと何枚で合うか」・置けない理由の説明も作らない。
置けない位置を枠だけで描くことと、置ける位置に吸着することは**ルールの可視化**で、最善手の提案ではない
(Peg §6 が跳べる先の印について言うのと同じ線)。Easy の内側の線と Medium の固定の 2 枚はティアの定義で、
押して呼ぶ助けではない。**はっきり言えば、Easy の全区切りの線は置き場の手がかりそのものである** — Easy は
形合わせとして作るティアで(上)、「どの駒をどこに置くか」を教えないという理屈を守るのは Medium と Hard。
Easy の線の一部だけ(たとえば大三角 2 枚の線だけ)を見せる形にするかは、製品オーナーが望めば変えられる
(v1 は全部を見せる)。

## 4. 操作 — 暫定(Phase 0 未実施)

**この節は凍結していない。**Phase 0 の実機の試行(計画「Phase 0 の試作」の表)がまだで、ここに書くのは
試作が選んだ解釈と既定値を出発点にしたものである。試行が通れば値を試行から採って凍結し、通らなければ
Three Peaks に差し替える(冒頭)。試行の結果で変えうるのは、吸着の許容・タップの遊び・持ち上げ量・置けない
位置の扱い・裏返しの入口・Medium の固定の 2 枚(§12 の確認待ち)。

**試作と違う点が 2 つある。**この文書が意図して変えたもので、Phase 0 の試行(試作のまま)はこの 2 点を
測らない:

1. **辺吸着の位置は目盛りだけ**(§5「吸着」)。試作は吸着先の辺の上の最も近い点(`closestOnSeg`)に吸着する。
   厳密な Z[√2] の座標で判定し保存するには、辺の上の位置が離散でなければならず、最も近い点はふつう
   Z[√2] の点にならないため。
2. **支点はつねに吸着した点**(§5「吸着」)。試作の `pivotOf` は、保存した支点が駒の頂点でなくなって
   いるとき(吸着先の頂点が駒の辺の途中に来たとき)、吸着先の頂点と重なる駒の頂点があればそれを優先
   する。この文書は、保存する座標が厳密になり、回す前後で支点が変わらないよう、吸着した点を使い続ける。

したがって、試作のままの実機の試行は、この 2 点の手触り(目盛りの間隔が指に合うか・回したときの支点)を
証明しない。**試行の前に、試作を目盛り吸着とこの支点の規則へ直す**(`apps/simple-games/prototypes/phase0/
tangram-board.html` は共有のファイルなので、統合の作業で直す)。直さずに試行するなら、結果がこの 2 点に
及ばないことを試行の記録に書く。

### タッチとマウス

- **ドラッグで置く**: トレイの駒を押さえて盤へ運び、離すと吸着した位置に置かれる。吸着先は**影絵と、置いた
  駒(固定の駒を含む)の頂点と辺**だけ(§5「吸着」)。トレイから運ぶ駒は、頂点の平均が指の
  `TRAY_LIFT_PX` = 24 px 上に来る(指で隠れないように)。盤の上の駒を運び直すときは、押さえた点と駒の
  位置関係を保つ。
- **運んでいる間は、吸着先に置かれた姿で描く**(Block Puzzle §3「盤面のマス目に吸着した実物として
  描かれる」と同じ考え方)。置ける姿はアクセントの面と枠、吸着先が無い・重なる・はみ出す位置では、指の
  位置に枠だけで描く。**離したときに起きるのは、最後に画面に描いた姿**(描く処理が確定した姿 — React の
  コミットの後の姿。同じフレームのうちに動かして離し、その動きの描画がまだ確定していなければ、その位置では
  判定せず、確定している直前の姿で決める。離した位置は使わない)。確定とブラウザが実際に塗るまでの間に
  離した場合は、確定済みでまだ塗っていない姿で決まりうる(この差はテストでは測れない — §13)。
- **置けない位置で離したとき**: トレイの駒は何も起きない(トレイへ戻り、盤は変わらず、操作にも
  数えない)。**盤の駒はトレイへ戻る(1 操作)**: 元の位置には戻さず、盤の上にあったときの向き (r, f)
  のままトレイに並ぶ。Undo で戻せる 1 操作(§3)。叱らない・音も鳴らない(Block Puzzle §3)。
- **手に持っている駒は UI だけの状態**: ドラッグ中・キーボードで持ち上げ中の駒は、離す・置く・Escape・
  `pointercancel` で決まるまで、セッションの上では**持ち上げる前の姿のまま**(§8「手にある駒」)。
- **タップで 45° 時計回り**(トレイでも盤の上でも)。動きが `TAP_SLOP_PX` = 6 px 以下ならタップ、越えたら
  ドラッグ。盤の上の駒は**支点**(その駒を置いたときに吸着した点 — §5)を中心に回り、横へずれない。8 回で
  元の姿に戻る。回した姿が置けない(はみ出す・重なる)なら何も起きない。トレイの駒は形だけで判定が無いので
  いつでも回る。
- **裏返しはボタンだけ**。選んでいる駒が平行四辺形(固定でない)のときだけ有効で、盤の上では支点を中心に
  裏返す(置けない姿になるなら何も起きない)。計画の元になった提案の「ダブルタップ(またはボタン)」の
  ダブルタップは、タップが回転である以上「2 回の回転」と区別できないので採らない(§12)。
- **選んでいる駒**: 最後に押した駒(タップ・ドラッグ・キーボードのフォーカス)。太い枠で示す。固定の駒も
  押す・フォーカスすると選ばれるが、読み上げと枠のためだけで、ほかには何も起きない(§3)。
- **盤の下の 3 ボタン**: 回転(選んでいる駒をタップと同じに回す)・裏返し・Undo。駒が選ばれていない、
  または固定の駒が選ばれているとき、回転と裏返しは押せない。Undo は履歴が空のとき押せない。
- **操作は 1 本の指のもの**: 押さえた `pointerId` を覚え、2 本目の指(主でないポインタ — `isPrimary` が偽)は
  何もしない(運んでいる駒の上でも)。2 本指の回転ジェスチャーは作らない(Sliding Puzzle §3、issue #187)。
  運んでいる間は 3 ボタンも答えない。
- **離す知らせが届かなかった押下は残さない**(Unblock §5 と同じ形): 押下が記録されている間に新しい**主の**
  ポインタが押されたら、前の押下は離す知らせを失ったものとして**放棄**し(操作を記録しない。運んでいた駒は
  持ち上げる前の姿のまま)、新しい押下を始める。記録している `pointerId` の `lostpointercapture` が離す前に
  届いたときも同じく放棄する(離した後の `lostpointercapture` は、押下がもう無いので何もしない)。放棄した
  押下に後から届く `pointerup` / `pointercancel` は無視し、残る click は食べる。
- 盤とトレイは `touch-action: none`(Block Puzzle §12)、押下は押した駒の要素で `setPointerCapture` する
  (盤の外へ出た指も追う)。**押せる範囲は駒の多角形そのもの**(§10)。
- **`pointercancel`**(通知シェード・着信など — [ARCHITECTURE.md](ARCHITECTURE.md)「指を取り上げられたときの
  契約」): 運んでいる駒はトレイへ戻る(盤の上から運んでいた駒は 1 操作。トレイから運んでいた駒は何も
  変わらない)。画面が離れる(`visibilitychange` の hidden・戻るボタンなど)ときの扱いはこれとは別で、
  手の中の駒を放棄して操作を記録しない(§8「手にある駒」)。`onPointerUp` を聞く要素には `onPointerCancel` を
  並べ、自分のテストで `fireEvent.pointerCancel` を駆動する(`src/test/pointerContractWiring.test.ts`)。
- **ドラッグの後に残る `click`**: 同じ駒が drag と tap(click)の両方を聞くので、ドラッグが残す click は
  「使った」と印を付けて食べ、回転させない(`event.detail > 0` のときだけ。キーボードの活性化は食べない —
  Sliding Puzzle §3)。印は次の押下で捨てる。「押す → 同じ要素を click」がタップとして 1 回だけ回ることも
  テストする。試作では、ドラッグを離した直後(およそ 0.3 秒以内)のタップに Chromium が click を出さず
  「回らない」ことがあった(ヘッドレスで観測。実機では未確認 — §13)。
- マウスは主ボタンだけ。右クリックの契約は持たない(副操作が無い)。
- 完成から結果カードまでの間と、ダイアログ・結果カードが開いている間、盤とトレイは `inert`。

### キーボード

- **Tab** で駒を巡る(トレイと盤の 7 枚。固定の駒も読み上げのためにフォーカスは受ける)。
- **Enter / Space**: フォーカスしている駒を持ち上げる(固定の駒には何も起こさない)。持ち上げている間の
  駒の位置を**仮の位置**(駒の頂点の平均。浮動小数)と呼ぶ。仮の位置は**持ち上げた姿から始まる** — 盤の
  駒はいまの位置、トレイの駒は頂点の平均が影絵の外接矩形の中心に来る位置。**矢印キー**は仮の位置を
  **ちょうど 1 単位**(小三角の脚の半分 — §5)ずつ動かし、**描いた吸着後の姿には引き寄せない**(吸着した
  姿から次の矢印を数えると、刻みと許容がどちらも 1 単位なので、いまの位置が最も近い候補に残って離れ
  られなくなりうる)。その仮の位置から、許容 1 単位(距離が**許容以下**の候補を含む — §5)で吸着先を探し、
  置ける姿を描く。もう一度 **Enter / Space** で描いている姿に置く(吸着先が無ければ何も起きず、持ち上げた
  まま)。
- **R** で回転、**F** で裏返し(持ち上げている間は、仮の位置を保ったまま運んでいる姿の向きを変えるだけ —
  セッションは変えない。持ち上げていなければタップと同じ — 盤の上では支点を中心に)。
- **Escape**: 持ち上げている駒を置かずに戻す(トレイから持ち上げた駒はトレイのまま。盤から持ち上げた駒は
  トレイへ — 1 操作。向きは持ち上げる前の (r, f) で、持ち上げ中の R / F は捨てる)。持ち上げていなければ、
  フォーカスしている盤の駒(固定の駒を除く)をトレイへ戻す(1 操作)。ダイアログが開いている間は答えない
  (`useDialogDismiss` が Escape を capture で取る — ARCHITECTURE.md「Escape は Cancel」)。
- **Ctrl/Cmd+Z** で Undo(持ち上げている間・押さえている間は効かない)。
- 持ち上げている間の Tab はフォーカスを動かさない(Escape で抜ける。試作の形)。
- `useGameKeys` を使い、`enabled` はダイアログと結果カードの間は偽(`src/test/modalIsolationWiring.test.ts`)。
  **キーリピートでは持ち上げ・置き・回転・裏返し・Escape・Undo をしない**(Peg §4 と同じ。矢印の移動は
  リピートで続けてよい)。
- 置いたあとはフォーカスを盤の上のその駒に、トレイへ戻したあとはトレイのその駒に置く。押したボタンが
  消える操作(結果カード・↻ の答え)のあとは盤の最初の駒に置く(Peg §4「フォーカスを失わせない」の形)。
- **Phase 2 のテストで実測**(`session.test.ts`。合成の入力で、画面と実機は Phase 3 以降):
  - 矢印 1 回(仮の位置が 1 単位動く)+ 吸着で、1 単位の刻みでは直接届かない √2 ≈ 1.41 単位ずれた位置
    (影絵の角)に届く。
  - 仮の位置は吸着後の姿に引かれないので、矢印を続ければ吸着先から離れられる。**細目の決定**: 吸着した
    直後の 1 回目の矢印では、元の吸着先がちょうど 1 単位 = 許容の境界にあって(境界を含む)、ほかに近い候補が
    無ければ同じ姿に吸着したままになる。2 回目で離れる(`rectangle` の角の `S1` で、1 回目は同じ姿、2 回目は
    辺の目盛りへ)。仮の位置を吸着後の姿に引き戻す形では、同じ条件で何回押しても離れない(同じテストが
    確かめる)。「次の矢印で離れられる」は「続く矢印で離れられる」と読む。
  - キーボードの操作(R / F・矢印・Enter)だけで `square` を完成できる(7 回の Enter で 7 枚)。

## 5. 幾何と判定

すべて `game/`(Pure TypeScript。React も DOM も使わない)。**置けるか・完成か・保存した配置が正しいかの
判定と、保存する座標は浮動小数を使わない。**浮動小数を使うのは、指(とキーボードの仮の位置)から吸着の
候補を選ぶ距離の比較だけで、その結果は必ず下の厳密な候補のどれかになる。

### 単位と数

- **単位** = 小三角の脚の半分(小三角の脚 = 2 単位)。試作の座標(大きな正方形 = [0,4]²、「u」)とは
  1 u = √2 単位の関係にある。
- 座標の各成分は **Z[√2]** の数 a + b√2(a, b は整数)で、`[a, b]` の組で持つ(`game/z2.ts`)。
  - 和・差: 成分ごと。積: (a + b√2)(c + d√2) = (ac + 2bd) + (ad + bc)√2。
  - 等しい: a と b がどちらも等しい(√2 は無理数なので、表し方は一意)。
  - **符号**: a と b が同符号(0 を含む)ならその符号。a > 0 > b なら a² − 2b² の符号、a < 0 < b なら
    2b² − a² の符号(整数で a² = 2b² になるのは a = b = 0 だけなので、0 にはならない)。大小は差の符号。
  - 算術では、成分の絶対値を下の「範囲」の上限 256 に収めれば(内包の判定で 4 倍しても 1,024、差で
    2,048)、判定の途中の外積の成分は約 2.5 × 10⁷ 以下、符号のための 2 乗は約 6.3 × 10¹⁴ 以下で、JS の安全な
    整数(2⁵³ ≈ 9 × 10¹⁵)に収まる。BigInt は使わない。**Phase 2 のテストで実測**(`z2.test.ts`): 0 にごく
    近い組(99 − 70√2 > 0、140 − 99√2 < 0、19601 − 13860√2 ≈ 2.6 × 10⁻⁵ > 0 など)の符号と、成分が約
    2.5 × 10⁷ の組(外積が上限で取りうる大きさ)の符号が正しく、その 2 乗が安全な整数に収まる。
  - 負のゼロは作らない(符号を反転する式は `0 - v`、積は `+ 0` で終える)。保存も比較も −0 を見ない。
- **点** = (x, y)、y は画面で下向き。カタログと保存では `[xa, xb, ya, yb]` の 4 整数(§2)。

### 駒

`game/pieces.ts`。

駒ごとに、頂点 0 を原点に置いた**局所の形**(r = 0・裏返しなし)を持つ。頂点は画面で時計回り。

| id         | 駒         | 局所の頂点(単位。r = √2)    | 面積(単位²) | 裏返し |
| ---------- | ---------- | --------------------------- | ----------- | ------ |
| `L1`, `L2` | 大三角     | (0, 0) (4, 0) (0, 4)        | 8           | なし   |
| `M`        | 中三角     | (0, 0) (2r, 0) (0, 2r)      | 4           | なし   |
| `S1`, `S2` | 小三角     | (0, 0) (2, 0) (0, 2)        | 2           | なし   |
| `SQ`       | 正方形     | (0, 0) (2, 0) (2, 2) (0, 2) | 4           | なし   |
| `P`        | 平行四辺形 | (0, 0) (2, 0) (4, 2) (2, 2) | 4           | あり   |

算術では面積の和は 8 + 8 + 4 + 2 + 2 + 4 + 4 = **32**。三角形の頂点 0 は直角、平行四辺形の頂点 0 は 45° の角。
トレイの並びは `L1 L2 M P` / `SQ S1 S2`(試作の 4 + 3)。

### 姿(回転・裏返し・位置)

- 盤の上の駒の**姿**は (r, f, at): 世界座標の頂点 i = at + Rʳ(F(局所の頂点 i))。F は f = 1 のとき
  x → −x(`P` だけ)、R は**画面で時計回りに 45°**: R(x, y) = ((x − y)/√2, (x + y)/√2)。
- Z[√2] の成分で書くと、x = x₀ + x₁√2、y = y₀ + y₁√2 に対して
  R(x, y) = ((x₁ − y₁) + ((x₀ − y₀)/2)√2, (x₁ + y₁) + ((x₀ + y₀)/2)√2)。
  **x₀ と y₀ の偶奇が等しい**とき割り算は割り切れ、結果も同じ性質を持つ(新しい有理部は x₁ − y₁ と
  x₁ + y₁ で、偶奇が等しい)。局所の形の全頂点はこの性質を持つ(上の表で確かめられる)ので、**どの向きでも
  全頂点が Z[√2] の点に乗る**。脚を 1 単位にとるとこの性質が崩れる(45° 回した脚の成分が √2/2)ので、脚を
  2 単位にとった。
- 算術では、R を 8 回で元に戻り、F は 2 回で元に戻る。三角形と正方形は鏡像が回転で出る(だから裏返しを
  持たない)。平行四辺形は鏡像が回転で出ない(8 通りの回転と 2 通りの裏表で、形として 8 通り — 180° 回すと
  同じ形)。正方形は形として 2 通り(90° で同じ形)。形として同じでも (r, at) は違いうるので、判定は
  頂点の集合で行い、姿どうしを比べない。

### 判定

`game/geometry.ts`(判定)と `game/snap.ts`(置ける姿・吸着・支点)。

駒は 7 枚とも凸で、辺は 8 方向だけ。だから**分離軸は 4 本**で足りる: (1, 0)・(0, 1)・(1, 1)・(1, −1)
(長さをそろえない軸。射影 x・y・x + y・x − y はどれも Z[√2] の数)。

- **区間の厳密な重なり**: 2 つの射影 [a₀, a₁] と [b₀, b₁] が「厳密に重なる」= **a₀ < b₁ かつ b₀ < a₁**。
  幅のある 2 つの区間(a₀ < a₁ かつ b₀ < b₁)なら max(a₀, b₀) < min(a₁, b₁) と同じだが、片方が 1 点
  (a₀ = a₁ = p)のときは違う: max < min の形では p < p になって決して成り立たず、この形では
  b₀ < p < b₁(p がもう一方の区間の内側にある)になる。**駒どうしの重なりにも、線分と駒の内包にも、この
  1 つの述語を使う**(max < min で書くと、線分の自分の法線の軸で必ず偽になり、辺が駒の内部を通っても
  検出されず、内包が条件 2 だけに縮む)。
- **重なり**(2 枚の駒): 4 本の軸のすべてで厳密に重なるとき、かつそのときだけ、内部が重なる。辺で接する・
  頂点で触れる・辺が一直線に並んで接するは、どれかの軸で区間の端が一致する(a₁ = b₀ か b₁ = a₀)ので、
  厳密には重ならず、重ならない。
- **内包**(駒 P が影絵 S の中): 次の 2 つがどちらも成り立つ。
  1. S のどの辺(線分)も、P の内部と交わらない — 線分と P を同じ 4 本の軸に射影し、**すべての軸で厳密に
     重なる辺が 1 本も無い**。辺は 8 方向のどれかなので、法線がちょうど 4 本の軸のどれかに当たり、**その
     1 本の軸でだけ射影が 1 点**(a₀ = a₁ = p)になる。そこでは上の述語が b₀ < p < b₁ — p が P の射影の
     開区間の中にあること — を見る(辺が P の縁に沿うだけなら p = b₀ か p = b₁ で、交わらない)。
  2. P の内部の 1 点が S の中にある。点は q/4 で、q は三角形なら 2·v₀ + v₁ + v₂、四角形なら v₀ + v₁ + v₂ + v₃
     (重みが正なので内部)。分数を避けるため、q を S の頂点を 4 倍した多角形に対して判定する。判定は半開
     区間の規則の交差数で、辺の左右は向きの符号(外積)で厳密に決める。1 が成り立てば q は S の縁の上に
     無いので、境界の曖昧さは起きない。
  - 1 だけでは「P が S の外にまるごとある」と区別できず、2 だけでは「S の角が P に食い込む」「頂点は全部
    S の縁にあるのに、P が S の凹みを覆っている」を見逃す。テストはこの 2 つの形を含む(§13)。
- **置ける姿**: S の中にあり(内包)、盤の上のほかのどの駒(固定の駒を含む)とも重ならない。
- **完成**: 7 枚とも盤の上にある。置ける姿にしか置けないので、7 枚は互いに重ならずすべて S の中にあり、
  面積の和(32)が S の面積(32、§2)に等しいので、S から 7 枚を除いた部分は面積 0 — S は閉じた多角形
  なので、7 枚の和は S そのものになる(算術の議論。完成の判定は念のため 7 枚の重なりと内包を全部確かめ
  直す)。保存した解とは比べない。

### 吸着

指(またはキーボードの仮の位置)は浮動小数の「望みの姿」(r と f は決まっていて、位置だけが浮動小数)を
出す。`game/snap.ts` の吸着 `snapPose` はそれと許容(単位。画面の `SNAP_PX` を盤の倍率で割った値、
キーボードでは 1)を受け取り、**厳密な姿と支点**か「無し」を返す。

- **吸着先**: S の頂点と辺、盤の上のほかの駒(固定を含む)の頂点と辺。Easy の内側の線は吸着先にしない。
- **頂点吸着**: 運んでいる駒の頂点 i を吸着先の頂点 t に合わせる姿(at = t − Rʳ(F(局所の頂点 i))。厳密)。
  距離は「望みの姿の頂点 i」と t の距離。
- **辺吸着**(頂点吸着で置ける候補が 1 つも無いときだけ): (a) 運んでいる駒の頂点を吸着先の辺の上へ、
  (b) 吸着先の頂点を運んでいる駒の辺の上へ。辺の上の位置は**目盛り**に限る: 辺の端(どちらの端からでも)から
  **2m + 2n√2 単位**(m, n ≥ 0 の整数。小三角の脚 2 と斜辺 2√2 の和 — 駒の辺の長さはどれもこの形)の点で、
  辺の内側にあるもの。軸に沿った辺ではその点は端 + (2m + 2n√2, 0) などで、斜めの辺では
  (2m + 2n√2)/√2 = m√2 + 2n なので、**どちらも Z[√2] の点**になる。距離は、(a) は望みの頂点と目盛り、(b) は
  望みの辺の上の目盛りと吸着先の頂点。**目盛りに限るのは試作と違う意図した差分**(試作は辺の上の最も近い点
  に吸着する — §4)。
- **選び方**: 許容の内側(**距離 ≤ 許容**。境界を含む)の候補を距離の近い順に並べ、**最初に置ける姿に
  なるもの**を採る。距離は **2 乗で比べ**(`sqrt` も `hypot` も使わない — 処理系によって丸めが違い、数学的に
  等しい距離が不等に比べうる)、2 乗の差が `SNAP_EPS` = 10⁻⁹ 単位² 以内なら等しい距離とみなす(許容との比べ
  も同じ。浮動小数の丸めで、許容ちょうどの候補が外れたり順位が入れ替わったりしないため)。等しい距離の順は、
  頂点吸着では運んでいる駒の頂点の番号、次に吸着先の順 — S の輪郭の順、次に盤の駒を `L1 L2 M P SQ S1 S2` の
  順(同じ駒の中は頂点の番号順)。辺吸着では (a) を (b) より先、(a) は運んでいる駒の頂点の番号・吸着先の辺の
  順(辺 i = 頂点 i から i + 1)・目盛りの順、(b) は運んでいる駒の辺の番号・吸着先の頂点の順・目盛りの順。**目盛りの順**は、その辺の始点(辺 i の頂点 i の側)からの距離が小さい
  順で、終点から数えた目盛りは始点からの距離に直して並べる(同じ点は 1 つ)。
- **細目の決定(Phase 2)**:
  - 候補の距離は、望みの `at` と候補の `at` の距離に等しい(どの候補も駒を平行移動するだけなので、頂点・
    目盛りどうしの距離と同じ値)。
  - 「等しい距離」の束ね方: 距離の 2 乗で並べ(同じ値なら列挙の順)、並びの先頭から、その束の**最初の候補との**
    差が `SNAP_EPS` 以内のものを 1 つの束にして、束の中を列挙の順に並べ直す。隣どうしの差で束ねると、少しずつ
    違う候補が鎖のように 1 つの束になりうるので採らない。どの処理系でも同じ並びになる(`rankCandidates`)。
    数学的に等しい距離が浮動小数で 7 × 10⁻¹⁵ だけ違う場合に、列挙の順が勝つことを `snap.test.ts` が確かめ、
    束ねなければ落ちることも確かめた。
  - 運んでいる駒自身の盤の上の姿は吸着先にしない(盤の駒を置き直すとき)。
  - 辺の端の目盛りは頂点と同じ点で、頂点吸着と同じ姿になる候補は「同じ姿は 1 度だけ」で飛ばす(予算を使わない)。
  - 成分の上限を越える候補は、判定 1 回ぶんを使って「置けない」とする。
  - 返す値: 姿と支点、吸着先の種類(§10 の読み上げ用。(b) は吸着先の頂点の種類)、どちらの段で見つけたか、
    数えた候補と判定の回数、上限で終わったか。
- **仕事量の上限**: 厳密な判定(内包と重なり)は 1 回の問い合わせで、**頂点吸着と辺吸着を合わせて**最大
  `SNAP_CHECK_LIMIT` = 32 回まで(予算は 1 つ)。頂点吸着の途中で使い切ったら、辺吸着へは進まず「無し」を
  返す(頂点吸着で置ける候補が無いと確かめていないので、辺吸着の条件を満たさない)。越えたら正直に「無し」
  を返し、推測で置かない。同じ姿になる候補は 1 度だけ判定する(予算にも 1 回ぶんだけ数える)。
- **支点**: 吸着した点(頂点吸着なら t、辺吸着なら接した目盛りの点か吸着先の頂点)。その駒の境界の上の
  厳密な点で、駒と一緒に保存する(§8)。**駒の頂点か、駒の辺の上の目盛り(その辺のどちらの端からでも
  2m + 2n√2 単位、m, n ≥ 0 の整数)のどちらかに限られる** — 頂点吸着の t と辺吸着 (a) の目盛りの点は駒の
  頂点に、辺吸着 (b) の吸着先の頂点は駒の辺の目盛りに当たる。**つねに吸着した点を使う**(試作の `pivotOf`
  は、保存した支点が駒の頂点でなくなると、吸着先の頂点と重なる駒の頂点を優先する — 試作と違う意図した差分、
  §4)。
- **盤の上の回転と裏返し**: 支点が動かないように姿を決め直す — 駒の局所の座標で支点に当たる点 l を求め
  (l は頂点か目盛りなので、l の成分も偶奇の性質を持つ: 有理部 x₀・y₀ が偶数で、√2 の部分 x₁・y₁ の偶奇が
  等しい。算術では R と F はこの性質を保つ。支点が辺の途中の任意の位置だと崩れる — たとえば軸に沿った辺の
  端から 1 単位の点は x₀ − y₀ が奇数で、回すと (x₀ − y₀)/2 が割り切れず Z[√2] から出る)、新しい (r, f) で
  l が支点に来るように `at` を決める。結果が置ける姿でなければ何も起きない。回転を 8 回続ければ元の姿に
  戻る。
- 算術での補足(**頂点吸着だけで、どの完成も組める**): 完成した配置で、駒の頂点 v は、ほかの駒か S の
  頂点と必ず重なる(v の角は 180° 未満なので、v のまわりの残りの角を、v を辺の途中に持つ駒 1 枚だけでは
  埋められない)。さらに、まだ置いていない駒の和の輪郭の角は、置いた駒か S の頂点でなければならない
  (そうでなければ、その角のまわりを置いた駒の辺だけで 180° ちょうどに埋めることになり、角にならない)。
  だから、置いた駒が完成のどれかの一部である限り、頂点吸着で次に置ける駒が必ずある。辺吸着は「置く順を
  選ばずに済む」ための便宜で、無くても完成には届く。§2 の「吸着だけで組めること」はこの主張をカタログの
  全図形について確かめる。
- 算術での補足(**吸着で生まれる姿の頂点は、有理部がすべて偶数**): 輪郭の頂点の有理部が偶数なら、頂点吸着の
  `at` = t − Rʳ(F(局所の頂点)) も、辺吸着の目盛りの点(端の点から、軸に沿った辺なら一方の成分が
  2m + 2n√2、斜めの辺なら両方の成分が 2n + m√2 だけ動いた点)も、有理部が偶数のままになる(局所の頂点と目盛りは、有理部が偶数で √2 の部分の偶奇が
  等しく、R はこの性質を保つため)。保存の検証が `at` の有理部の偶数を求めるのはこのため(§8)。

### 範囲と仕事量

- **成分の上限**: 受け入れる座標(保存の `at` と支点、吸着の候補)の成分は絶対値 256 以下。越える候補は
  置けない姿として扱い、越える保存は読み捨てる(§8)。カタログは 64 以下(§2)。算術では、影絵が 13 単位
  以内で、駒の頂点が吸着先から駒の辺の長さの和だけ離れた点に来る限り、成分はこの上限よりずっと小さい。
- **実行時の探索は無い**。仕事は 1 回の入力につき、吸着の候補の列挙(輪郭の頂点 ≤ 32 と駒の頂点 ≤ 24、
  それぞれの辺の目盛り。算術では(**Phase 2 のテストで実測** — `geometry.test.ts` が厳密な列挙で数える)、
  片端からの目盛りは端の点を含めて、長さ 13 以下の軸に沿った辺で 21 個、
  13 × 13 の外接矩形に収まる斜めの辺(長さ ≤ 13√2 ≈ 18.4)で 38 個、駒の辺(長さ ≤ 4√2)ではもっと少ない。
  許容の外の目盛りは数えない)と、厳密な判定 ≤ 32 回で、1 回の判定は 4 本の軸 × (輪郭の辺 ≤ 32 + 駒 ≤ 6 枚)で
  終わる。[GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)
  「CPU 探索」の Web 先行公開の列挙には Phase 4 で「実行時の探索なし」と足す(共有ファイル — 統合の作業)。
  **Phase 2 のテストで実測**(`snapWork.test.ts`): 34 図形それぞれで、解を頂点吸着で組む順の各段階に、

  頭打ちにする(`ui/layout.ts` の `pointerTolerance` — `min(SNAP_PX ÷ 盤の px/単位, 1)`)。だから盤がどれだけ
  小さくなっても、ポインタの問い合わせは上の測定(許容 ≤ 1 単位)の内側に収まる(`ui/layout.test.ts`)。
  Web の広告の予約込みの 360×640 では、算術では盤の倍率は最も大きい図形でも約 18.7 px/単位で、14 px は
  約 0.75 単位 — 頭打ちは効かない(§10)。

## 6. モードとデイリー

### Free Play(Easy / Medium / Hard)

- ティアごとに**順番のある列**(カタログの並び順)。解放は作らない — どの図形も「次の図形」でいつでも
  たどり着ける。影絵のギャラリー(一覧画面)は v1 では作らない([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md)
  「未達成の一覧は持たない」の側)。
- **次の図形** `next(tier, last)`: L をそのティアの列、`last` をそのティアで最後に始めた図形とする。
  1. `last` が L に無い(初めて・消えた id)なら、L を先頭から見て**最初の未解決**(`tn.progress` に記録の無い
     図形)。無ければ L の先頭。
  2. `last` が L の k 番目なら、k + 1, k + 2, …(末尾の次は先頭へ戻る)と見て、`last` 自身を除いた
     **最初の未解決**。無ければ L の (k + 1) 番目(末尾なら先頭。列が 1 つなら `last` 自身)。
     **計画の推奨は「すべて解いていれば先頭へ戻る」だが、ここは (k + 1) 番目にする — 推奨との差(§12)。**
     先頭へ戻すと、全部解いたあとは結果カードの「次の図形」もホームのティアのボタンも先頭の図形を開き
     続け(先頭の図形の結果カードからも先頭が出る)、列をたどれなくなるため。
  - デイリーの完成は `tn.progress` に入れない(§7)ので、未解決の判定に効かない。`last` を書くのも Free Play
    の開始だけで、デイリーの開始・再挑戦は書かない(§7)。
- **ホーム**: 中断中の Free Play の局があれば、主ボタンは「再開」(ティアと番号を添える)。Easy / Medium /
  Hard の各ボタンは、そのティアの `next(tier, last)` を始める。中断中の局があるときは、どのティアのボタンでも
  **確認してから置き換える**(保存スロットは 1 つ。`ConfirmDialog` で「いまの図形」と「次の図形」を名指す —
  Peg §7 / Mancala のホームの形)。同じティアのボタンでも置き換える(その図形をやめて次へ進む道がここ
  しか無いため)。続けたいときは「再開」を押す。中断中の局が無いときは、**最後に選んだティア**
  (`tn.prefs`、初期値 Easy)のボタンを主ボタンにする。`tn.prefs` を書くのは、ホームのティアのボタンで
  始めたときだけ。
- **ホームの「デイリーチャレンジ」**: `tn.saveDaily` に**今日の日付**(`dailyDate === today`)のレコードが
  あれば、押すとそれを**再開**する(ボタンに「再開」を添える。確認は要らない — スロットが別なので何も置き
  換えない)。無ければ(始めていない・完成した・日付が今日と違う記録は読み込みで捨て済み)、**今日の図形を
  新しく始める**(played が 1 増える)。完成した日にもう一度押すと新しい局が始まり、その日の最短秒は速く
  なったときだけ更新される(§7)。Free Play だけが中断中のときも、デイリーだけが中断中のときも、主ボタンは
  上の規則のまま(中断中の Free Play があればその「再開」、無ければ最後に選んだティア)で、デイリーが
  中断中ならデイリーのボタンが「再開」を添える。
- 結果カードの「次の図形」は `next(tier, いまの図形)`(下)。

### デイリー

- **今日の 1 問だけ**。端末のローカル日付で決まり、過去の日付には遡れず、一覧も入口も持たない。今日と
  違う日付の中断中のデイリー(過ぎた日付も、端末の時計を戻したときの未来の日付も)は次に読み込むとき
  (起動・ゲームを開く)にレコードごと捨て、ホームの「デイリーチャレンジ」はつねに今日の図形へ向く。遊んでいる最中の局は日付が変わっても
  取り上げない。ストリークは数えない・表示しない([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md)「デイリーは今日の 1 問」)。
- **毎日 Medium**(固定 2 枚つき)。曜日で当たり外れを作らない。同じバッチの Make the Target、前例の
  Unblock / Loop / Bridges、47〜51 の Pipe Link と同じ「Medium 固定」。
- **日付 → 図形**: d をその日付の通し日数(1970-01-01 を 0。ローカル日付の年月日を `Date.UTC` に通して
  86,400,000 で割る)、N を Medium の図形数として、Medium の列の **(d × 7,919) mod N 番目**(0 始まり。
  `dailyFigure`、Unblock Puzzle の `dailyEntry` と同じ形)。暦の日付でない文字列(`'garbage'`、`2026-02-30`
  など)には図形を返さず `null`(`dayNumber` も `null`、`createDailySession` も `null` — UI はホームへ。
  推測した日で始めない)。7,919 は素数で N(< 7,919)と互いに素なので、
  算術では**続く N 日は毎日違う図形**になる。**Phase 2 のテストで実測**(`catalog.test.ts`): v1 の Medium 12 で、
  4 つの始まりの日(1970-01-01・2026-10-21・2026-12-25・2031-02-27)から続く 12 日が、どれも 12 種の図形だった。
  12 日で一巡する — Medium を増やせば延びる(7,919 mod 12 = 11 なので、日が進むと列を 1 つずつ戻る)。決めた
  数日の図形は `compatibility.test.ts` が固定する。`next` は `nextFigure`(`nextFigure(tier, last, isSolved)`)で、`nextFigure` と `dailyFigure` は `game/catalog.ts`。
- カタログを直すと(ベータの間)、デイリーの図形が日によって変わりうる(§8・§12)。

### ↻ と結果カード

- **ヘッダの ↻** は共有の `RestartDialog` で、**同じ図形で再挑戦だけ**を問う(`newBoard` を渡さない —
  `ui/components/RestartDialog.tsx` の「a numbered level's "other board" is another level」の形。
  `src/test/restartDialogWiring.test.ts` は `tryAgain` の ↻ に `RestartDialog` を求め、結果カードが
  `onNewBoard` / `onNewDeal` / `onNewFree` を渡すときだけ `newBoard` の一致を求める。「次の図形」は
  それらの名前を使わない)。再挑戦は、固定でない駒をすべてトレイへ戻し(トレイの向きは既定へ)、Undo の
  履歴を空にし、経過秒を 0 から始める(置き換わる局の未計上の秒は先に計上する — §7)。
- **結果カードのボタン(暫定 — 製品オーナーの確認待ち)**: Free Play は「次の図形」(主ボタン・自動
  フォーカス)→「同じ図形で再挑戦」→「ホーム」。デイリーは「同じ図形で再挑戦」→「ホーム」。42〜46 で
  結果カードの第一ボタンの形が分かれたまま、オーナーの判断の記録が無い(計画「共通要件」)ので、決まる
  までは列の形(Sudoku のレベルと同じ側)を採る(§12)。

## 7. 統計

- **プレイ中に時計を出さない**。経過秒は内部で測り、結果カードと統計でだけ見せる。時計は画面が見えて
  いる間だけ 1 秒ずつ ref を進め(再描画しない)、見えていない間は進まない。戻ってきても何も進めない。
- **played** は局を始めたとき(ホームのティアのボタン・結果カードの次の図形・再挑戦・デイリーの開始・初回の
  Quick Rules の後の開始)に 1 増え、再開では増えない。**solved** は完成したときに 1 増える(同じ図形を
  何度完成させても、その回数)。
- **計上**: 背景へ回る・画面を離れる・↻ で局を置き換える・完成・アンマウント(`useOnUnmount(syncActiveGame)` を
  1 回 — [GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「アンマウントで計上する」、`src/test/unmountBookingWiring.test.ts`)
  の各時点で、まだ計上していない秒だけを足す(bookedRef 方式。同じ秒を二度数えない)。起動時の時計の種は
  そのマウントが持つ局の `elapsedSeconds`(`src/test/playClockSeed.test.ts`)。
- **`tn.progress`**(図形ごとの記録): Free Play で完成した図形 id → その図形の最短秒、と、ティアごとに最後に
  始めた図形 id(`last`、§6 の `next`)。デイリーの完成は入れない。**`last` を書くのは Free Play で局を始めた
  ときだけ**(ホームのティアのボタン・結果カードの「次の図形」・再挑戦)。デイリーは Medium の図形だが、
  その開始と再挑戦は `last.medium` を書かない — ホームの Medium のボタンと `next('medium', …)` は、デイリー
  に動かされない。
- **`tn.stats`**: ティアごとに played / solved / 合計プレイ秒、デイリーの played / 合計プレイ秒、デイリーの
  達成日 → その日の最短秒(日付の**集合**。連続は数えない)。**デイリーは Medium の行に混ぜない**(Bridges と
  同じ別の枠)。Unblock Puzzle と Loop Puzzle はデイリーを Medium の行に数え、42〜46 で分かれたままなので、
  **製品オーナーの確認待ち**(計画「共通要件」。分けた数は後で足せる — §12)。累計プレイ時間は 4 つの合計
  プレイ秒の和で、別に保存しない。
- **統計画面**: ティアごとに 始めた数・完成した数・解いた図形の数(`tn.progress` の件数。「n / 全体」の形
  では出さない — 未達成を数えて見せないため)・合計プレイ時間。デイリーは 始めた数・達成した日数・合計
  プレイ時間。「すべて」の合計プレイ時間。ストリークも順位も無い。
- **結果カード**(`ui/components/ResultOverlay.tsx`): 見出しは事実だけ(「完成」 — スキャフォールドの
  "Nice work" は称賛語なので Phase 3 で置き換える)。図形(ティアと番号。デイリーは日付)と時間を出す。
  **2 回目以降だけ**自己ベストとの差を符号付きで添える(`BestDelta`。Free Play はその図形の最短秒、
  デイリーはその日の最短秒。初めての完成は記録を作るだけで何も添えない)。スコア・星・称号は作らない。
  共有(`ShareAction`)は `outcome: 'completed'`(負けも引き分けも無いので `played` は使わない)、`details` は
  図形の番号・ティア(デイリーは日付)・時間の 3 つまで。カードが表示している値から作り、計算し直さない。
- 完成は、シェルのレビュー質問が数える「勝った局」(`services/review` の `recordGameCompleted`)に 1 回数える。
  **どのプラットフォームでも完成のたびに呼ぶ**(数えるだけで、条件で囲まない)。質問を出すのはアプリ版
  だけ(`shouldPromptReview` が native でだけ真になる)で、このゲームは Web ベータなので質問が出る場面は
  無いが、呼び出しは Web でも省かない(Peg §10 と同じ形)。完成した局は終わるので、1 局につき 1 回。
- 計算は `state/statsLogic.ts`(純粋な関数)、書き込みは `state/GameContext.tsx` の 1 か所。

## 8. 中断と再開

### キー

保存キーは **`tn.saveGame` / `tn.saveDaily` / `tn.progress` / `tn.stats` / `tn.flags` / `tn.prefs` の 6 つ**
(`storage/keys.ts`、import ゼロの葉。キーの葉の名前は順に `game` / `dailyGame` / `progress` / `stats` /
`flags` / `prefs`)。スキャフォールドは `tn.stats` / `tn.flags` だけで、残りの 4 つは**保存の段
(Phase 3 の `storage/`)でスキーマと同じコミットで** `storage/keys.ts` と `src/app/gameKeys.test.ts` の
`RELEASED_KEYS['tangram']`(この順)に足した — キーだけを先に足すと、`src/test/resetLocalDataWiring.test.tsx`
が「スキーマの無いキー」として落とすため。**これは計画の決定事項からの意図した差分である**(決定事項は、各
ゲームの `storage/keys.ts` と `gameKeys.test.ts` の自分の行を「ルール文書の保存の節と同じコミット」= Phase 2
で足すとする)。差分の理由は、`registry` の `storageKeys` が `Object.values(TN_STORAGE_KEYS)` で、足したキーには
スキーマが要る(上の `resetLocalDataWiring`)のに、スキーマは Phase 3 で書くから。`gameKeys.test.ts` 自身のコメントも「保存の節に
Phase 2/3 で育つ」と書く。他のゲームのキーには触れない。**ベータ中はスキーマを凍結しない** —
変えるときは `WebBetaNotice` の告知の範囲でリセットを許す([WEB_VERSION.md](WEB_VERSION.md)「保存データ」)。
正式収録で凍結し、公開済みの Web 版から採取した payload で `storage/releasedRecords.test.ts` を作る。

### 2 スロット

- Free Play 用 `tn.saveGame` とデイリー用 `tn.saveDaily` を**独立して保持**する。**どのスロットのレコードかを
  決めるのはキー**(`gameSlotSchema(key, expectedMode)`。`src/test/savedGameSlots.test.ts` と自分の
  `storage/slots.test.ts`)。
- ホーム画面のショートカットは、中断中の局がちょうど 1 つのときだけ盤へ直接入る(2 つならホームへ。初回は
  Quick Rules が先 — `src/test/shortcutResumeWiring.test.ts`)。
- 初回の Quick Rules を終えると、Free Play の中断中の局があればそれを再開し(新しく始めて上書きしない)、
  無ければ `tn.prefs` のティアの `next` を始める。

### 中断レコード(`tn.saveGame` / `tn.saveDaily`、schemaVersion 1)

形の例(`square` の `L1` と `S1` を解の位置に置いた局。`schemaVersion` と `savedAt` を除いた部分 —
`game/session.ts` の `toRecord` が書くもの — の JSON を `compatibility.test.ts` が固定する):

```json
{
  "schemaVersion": 1,
  "mode": "free",
  "tier": "easy",
  "figure": "square",
  "dailyDate": null,
  "pieces": {
    "L1": { "r": 5, "f": 0, "at": [0, 2, 0, 2], "pv": [0, 0, 0, 0] },
    "S1": { "r": 7, "f": 0, "at": [0, 3, 0, 1], "pv": [0, 4, 0, 0] }
  },
  "elapsedSeconds": 42,
  "savedAt": 1792500000000
}
```

| フィールド       | 型・形                                                                                    |
| ---------------- | ----------------------------------------------------------------------------------------- |
| `mode`           | `'free'` / `'daily'`。キーと一致しなければ破損                                            |
| `tier`           | `'easy'` / `'medium'` / `'hard'`。カタログのその図形のティアと一致。デイリーは `'medium'` |
| `figure`         | 図形の id                                                                                 |
| `dailyDate`      | デイリーは `YYYY-MM-DD`(実在の日付)、Free Play は `null`                                  |
| `pieces`         | **盤の上の固定でない駒だけ**。id → `{ r, f, at, pv }`(`pv` = 支点)。無い駒 = トレイ       |
| `elapsedSeconds` | 0〜10⁹ の整数(この局で計上済みの秒)                                                       |
| `savedAt`        | 0〜10¹⁵ の整数(ms。保存層。読むだけで使わない)                                            |

- **トレイの駒の向きは書かない**(再開するとトレイの駒は既定の向き)。Undo の履歴も書かない(§3)。
  **Medium の固定の 2 枚も書かない**(カタログから決まる)。状態(プレイ中 / 完成)も書かない。
- **fail-closed**: 次のどれかに当たるレコードは読み捨て、プレイヤーはゲームのホームに着く(黙って新しい局を
  始めない)。理由は `RestoreRejection` として返り、`restoreSession` は何を渡されても例外を投げない:
  - `not-a-record`: 記録(配列でないオブジェクト)でない
  - `bad-mode`: `mode` / `tier` / `dailyDate` の形が違う、デイリーなのに `medium` でない、デイリーなのに日付が
    無い・Free Play なのに日付がある
  - `unknown-figure`: `figure` がカタログに無い(`'toString'` のような、どのオブジェクトにもある名前も含む。
    ベータ中に消した図形も)、または `tier` がその図形のティアと違う
  - `wrong-daily-figure`: デイリーの `figure` が、その日付の図形(`dailyFigure(dailyDate)`)でない
  - `bad-piece`: `pieces` がオブジェクトでない、知らない駒の id、`r` が 0〜7 の整数でない、`f` が 0 か 1 でない・
    `P` 以外で 1、`at` / `pv` が 4 つの整数の配列でない・成分が 256 を越える、**`at` の有理部(`at[0]` と
    `at[2]`)が偶数でない**(駒の頂点はどれも `at` から有理部が偶数だけ離れた点なので、`at` が奇数なら頂点も奇数の
    有理部になり、吸着からは生まれない — §5)、**支点が駒の頂点でも、駒の辺の上の目盛り(その辺のどちらの端からでも
    2m + 2n√2 単位)でもない**(境界の上の点でも、たとえば軸に沿った辺の端から 1 単位の点は目盛りでなく、
    次の回転が Z[√2] から出る — §5「盤の上の回転と裏返し」)
  - `fixed-piece`: Medium の図形の固定の駒が `pieces` にある(固定の駒が動いた形)
  - `outside`: どれかの駒が影絵の中に無い
  - `overlap`: どれか 2 枚が重なる(固定の駒を含めて)
  - `finished`: 7 枚がすべて盤の上にある(完成した局。完成の時点で計上済みで、再開するものではない)
  - `bad-elapsed`: 経過秒が 0 以上 10⁹ 以下の整数でない
  - 保存層が見るもの: `schemaVersion` が 1 でない、`savedAt` の範囲、キーとモードの食い違い、**今日と違う
    日付のデイリー**(過去も、端末の時計を戻したときの未来も。読み込みでレコードごと消す — §6。日付は形の
    検証より先に見る。再開に出すのは `dailyDate === today` のレコードだけ)。
- **検証はスキーマの `validate` 自身が行う**(Peg §11「検証の置き場所」と同じ規則)。仕事量は駒 7 枚 ×
  輪郭の辺の数で決まり、探索は無い。読み込み(`loadSavedGames(kv, today)`)だけでなく、バックアップの
  復元も同じ検証を通るので、座標の上で成り立たない局 — はみ出す・重なる・厳密でない座標・割り切れない支点 —
  はバックアップからも入らない([architecture/backup.md](architecture/backup.md)「検証は各レコードの持ち主が
  行う」)。**駒が吸着先に着いているかまでは調べない**(調べるのは候補の探索になる)ので、保証するのは
  「その配置が置ける姿であり、次の回転が厳密に計算できること」まで。`validate` は例外を投げず、通らなければ
  null を返す。
- **置き場所(Phase 2 で決めた)**: レコードの形と検証 — `toRecord` / `restoreSession` / `RestoreRejection` —
  は **`game/session.ts`**(純粋な関数。Peg Solitaire / Unblock Puzzle が `game/session.ts` に `restoreSession`
  を置くのと同じ。上の拒否の理由の判定はすべてここ)。`schemaVersion` と `savedAt` を足す・外す変換、2 スロットの
  読み込み(`loadSavedGames(kv, today)`)、今日と違う日付のデイリーの削除は **`storage/gamePersistence.ts`**、
  スキーマの `validate` は `restoreSession` を呼ぶ(`storage/schemas.ts`。どちらも Phase 3)。
  `src/test/shortcutResumeWiring.test.ts` は、キーの `.save…` の有無と `gamePersistence.ts` の有無が食い違わない
  ことを求める。
- **細目の決定(Phase 2)**: 拒否の判定は上の一覧の順に行い、最初に当たった理由を返す(`bad-piece` は全部の
  駒の形を見てから、`fixed-piece` → `outside` → `overlap` → `finished` → `bad-elapsed`)。レコードと駒の
  記録に知らない欄があっても無視する(前例の `restoreSession` と同じ。欄を足すのはスキーマの変更 — 冒頭
  「ベータ中はスキーマを凍結しない」)。`pieces` の知らない駒の id は `bad-piece`。座標の −0 は 0 として
  読む。`restoreSession` は内部で例外が起きても `not-a-record` を返す(何を渡されても投げない)。固定の駒の
  支点はその駒の頂点 0(`at`)とする(固定の駒は回らず、保存もしないので、値は表に出ない)。
- **読み捨てた記録はストレージから消さない**(今日と違う日付のデイリーを除く)。そのスロットは空として扱い
  (ホームに「再開」は出ず、ショートカットもホームへ)、次にそのスロットで局を始めたときに置き換わる。
- 書く側は受け入れられる形しか書かない: 経過秒は 0〜10⁹ の整数秒にして書く(端数は切り捨て、負や数でない
  値は 0、上限を越えたら上限)。
- **保存の時機**: 局を始めたとき(0 枚の局も 1 局として保存する)、操作と Undo のたび、背景へ回るとき
  (`visibilitychange` の hidden、アプリ版は `pause`)、画面を離れるとき、アンマウントのとき。背景へ回るとき
  は盤の保存と未計上の秒の計上を同じ同期処理で行う。**完成した局は保存しない** — 完成の時点でそのスロットを
  消す。保存の失敗でゲームを止めない。
- **手にある駒**: ドラッグ中・キーボードで持ち上げ中の駒は **UI だけの状態**で、セッションにも履歴にも入ら
  ない(§4)。セッションの駒は、離す・置く・Escape・`pointercancel` で決まるまで**持ち上げる前の姿のまま**
  (盤の上の駒は元の位置と支点、トレイの駒はトレイ)で、運んでいる姿・仮の位置・持ち上げ中の R / F は
  保存に入らない。1 操作が記録されるのは、決まった時点(§3)。
- **決まる前に画面が離れたとき** — `visibilitychange` の hidden・アプリ版の `pause`・画面を離れる・Android
  の戻るボタン・アンマウント — は、手の中の駒を**放棄する**: 操作は記録せず(Undo の履歴にも入らず、音も
  振動も無い)、保存は**持ち上げる前の姿**を書く。盤の上から持ち上げていた駒は、再開すると元の位置にある
  (トレイには行かない)。押下の記録は放棄で捨て、そのあとに届いた `pointerup` / `pointercancel` は無視する
  (ARCHITECTURE.md「押下の記録は誰のものか」)。画面が見えている間に届いた `pointercancel`(通知シェード
  など)は別で、トレイへ戻す(§4)。
- **Android の戻るボタンはゲーム画面・統計・Quick Rules からゲームのホームへ(盤を保存して)、ホームから
  コレクションへ。リスナーは GameContext の 1 つだけ**で、native でだけ登録する
  (`src/test/gameBackButtonWiring.test.ts` が、ゲームごとにちょうど 1 つの native ガード付き
  `CapacitorApp` の `backButton` リスナーを求める。Quick Rules からの戻りが初回の Quick Rules を完了扱いに
  することは `src/test/tutorialBackWiring.test.tsx`)。ゲーム画面から戻るとき、手にある駒は上のとおり放棄
  され、ホームの「再開」で持ち上げる前の姿から続けられる。
- **カタログを直したときの扱い(ベータの間)**: 座標を直した図形の中断は、駒が新しい輪郭からはみ出せば
  `outside` で読み捨てる(はみ出さなければそのまま再開できる)。図形を消せば `unknown-figure`。デイリーの
  対応を変えれば、その日のデイリーの中断は `wrong-daily-figure`。どれも `WebBetaNotice` の告知の範囲
  (Loop Puzzle §12「ベータ中のスキーマ」と同じ扱い)。

### `tn.progress` / `tn.stats` / `tn.flags` / `tn.prefs`(schemaVersion 1)

```json
{ "schemaVersion": 1, "best": { "square": 95, "triangle": 140 }, "last": { "easy": "triangle" } }
```

- `tn.progress`: `best` は図形 id → 0〜10⁹ の整数秒(最大 1,000 件)、`last` は `easy` / `medium` / `hard` の
  それぞれに図形 id(無くてよい)。**カタログに無い id の件は、その件だけ捨てて残りを守る**(ベータ中に
  図形を消しうるため)。形の壊れた記録は全体を既定値(空)に戻す。

```json
{
  "schemaVersion": 1,
  "easy": { "played": 5, "solved": 3, "totalPlaySeconds": 610 },
  "medium": { "played": 2, "solved": 1, "totalPlaySeconds": 420 },
  "hard": { "played": 0, "solved": 0, "totalPlaySeconds": 0 },
  "daily": { "played": 2, "totalPlaySeconds": 380 },
  "dailyTimes": { "2026-10-21": 185 }
}
```

- `tn.stats`: 各欄は 0〜10⁹ の整数(合計プレイ秒は 0〜10¹²)。`dailyTimes` は `YYYY-MM-DD` → 秒の疎な表で最大
  2,000 件。読めない 1 件はその件だけ捨て、記録全体は捨てない。**欄どうしを突き合わせない**(`solved >
played` を拒否しない — Peg §11 と同じ理由: 統計と中断は別のキーで、それぞれ単独で既定値に戻りうる)。
  それ以外の形の誤りは全体を既定値に戻す。他のキーには波及しない。
- `tn.flags`: `{ "schemaVersion": 1, "tutorialCompleted": boolean }`。
- `tn.prefs`: `{ "schemaVersion": 1, "tier": "easy" | "medium" | "hard" }`。**最後に選んだティアだけ**(初期値
  `easy`)。盤の遊び方を変える設定は 1 つも入れない。不正な値(`'toString'` などを含む)は既定値。

## 12. 意図的な差分

**ブランド原則により合わせないもの**

- 時間制限・手数制限・得点・星・称号(作らない — §1、§7)。プレイ中の時計(出さない)。
- Undo を広告視聴・コイン・回数制限に結び付けること(しない — §3)。
- 図形の解放制(作らない。どの図形も「次の図形」でいつでも遊べる — §6)。影絵のギャラリーと「n / 全体」の
  達成率(作らない — 未達成の一覧を持たない)。
- ストリーク・ログインボーナス・過去のデイリー(作らない — §6)。オンラインランキング(作らない)。

**設計判断として合わせないもの**

- **Hint・解の自動配置・「あと何枚」の表示**(作らない — §3)。
- **ダブルタップの裏返し**(採らない — §4)。計画の元になった提案は「ダブルタップ(またはボタン)」だった。
  タップが回転である以上、ダブルタップは 2 回の回転と区別できない。提案からの意図的な差分。
- **2 本指の回転ジェスチャー**(作らない — §4。1 本の指の契約)。
- **浮いた配置**(吸着しない駒を盤の上に残すこと。作らない — §4・§5)。吸着した位置にだけ置けるので、
  保存は常に厳密な座標で、キーボードの操作も吸着先の候補で閉じる。Phase 0 で「トレイへ戻される」ことが
  誤操作に数えられるほど多ければ、浮いた配置を許す(その位置は盤の相対座標を 1/10 単位に丸めて保存し、
  §5 と §8 を直す)— 暫定。
- **影絵の穴とくびれ**(入れない — §2)。穴のある影絵・頂点だけで接する影絵は 1 本の単純多角形で書けず、
  形式が拒む。内包の判定が単純になる。伝統図形の大半は穴を持たないが、くびれを持つ図形はある — 入れる
  なら形式と内包の判定を広げ、テストを足してから。
- **影絵の名前**(v1 では出さない — §11)。正式収録の前に決める(確認待ち)。
- **7 色の塗り分け**(しない — §10)。形で区別し、アクセントの濃淡だけを使う。
- **実行時の図形の生成**(しない — §2)。
- **Undo の履歴の保存と、完成後の Undo**(しない — §3)。
- **トレイの駒の向きの保存**(しない — §8)。再開したトレイは既定の向き。

- **ティアの難しさ**: Easy / Medium / Hard は著者の判断(§3 の目安)で、**難しさも難しさの分布も測って
  いない**。共通のテスト ⑨(問題の質・難易度の分布)の対応物は、ティアごとの頂点数・凹の頂点の数・外接矩形を
  出力するところまで(上の `catalog.test.ts`)。§3 の Easy の目安「凸に近い」を門にする代理(凹の頂点が k 個
  以下)は、k を決める根拠が無いので置かない。ただし v1 の Easy は §2 で凸の形に決めたので、凹の頂点 0 を §2 の
  分類の規則として門にした(凸でない図形を Easy に足すなら、§2 とこの門を一緒に直す)。これは難しさの測定では
  ない。
- **キーボードだけの完成の読み上げ**: 持ち上げ中の「置ける / 置けない」の読み上げ(§10)は、実際のスクリーン
  リーダーで聞いていない。
- **古い WebView**(Chromium 88 相当)と iOS 14 の Safari での動作。実機のフォントとグリフのフォールバック。
- **実機の大きさ**: 360 幅で小三角の脚 52 px が指に足りるか(§2 の大きさの上限)。算術では、v1 で外接矩形が
  最も大きい `heron`(高さ約 12.49 単位)で、使える幅 296 px の盤の脚は約 47 px。Web の広告の予約込みの
  360×640 では盤の脚は約 37 px、トレイの脚は約 24 px(§10、算術)— 実機で足りるかは未検証。
- **実ブラウザでのレイアウトと当たり判定**: 360×640(広告の予約込み)でスクロールが出ないこと、多角形の外の
  押下が下の駒か盤に届くこと、`clip` しない回転の演出の見た目、駒の下の不透明な面で Easy の線が透けない
  こと(§3・§10)は、この環境にブラウザが無く確かめていない(算術と CSS の読み取りだけ — 上)。
- **Quick Rules の 360×640**: Web の広告の予約と先行公開のお知らせ込みで 3 ステップがスクロールなしに収まる
  ことは**算術だけ**(CSS の読み取りからの見積もり。ステップ 3 の正方形の図は幅 260 px のままだと約 36 px
  はみ出す見積もりだったので、図の高さを `30vh`(640 px で 192 px)で頭打ちにした)。実ブラウザで測って
  いない。
- **横持ちと低い画面**(既知の制限。直していない): 盤には下限 160 px(`BOARD_MIN_PX`)があり、遊ぶ領域の
  高さが 240 px 未満だとトレイが `.tn-play` の `overflow: hidden` で下が切れ、168 px 以下ではトレイが丸ごと
  見えない(`ui/layout.test.ts` が 640 幅で固定する算術)。ネイティブは縦持ちに固定されている
  (`AndroidManifest.xml` の `screenOrientation="portrait"`、`Info.plist`)ので、これは **Web の版**(横持ちの
  スマートフォン、低いブラウザの窓)の制限: 640×360 の横持ちでは、上のバー 64 px・3 ボタンの列 69 px・広告の
  予約 116 px を引いた遊ぶ領域は 111 px で、トレイが見えず**遊べない**(広告の無い Web でも 227 px でトレイの
  下が切れる)。横持ちでトレイを盤の横へ回す配置は作っていない。実ブラウザでは未確認。
- **翻訳**: `ja` と 12 言語の訳(2026-10-21)は誰も読んでいない — 作者もネイティブも(§11)。どの言語も
  画面で見ておらず、折り返し・はみ出し・デーヴァナーガリーとタイ文字の上下の字形・OS の文字サイズ拡大は未確認。
  スクリーンリーダーでの実際の読み上げ(どの言語でも)。
- **題と伝統図形の出典**(§12。ネットワーク不可)。
- 低スペック実機での入力 1 回あたりの時間(実行時の探索は無く、仕事量はテストで数える)。

## 14. Club House

**登録しない**(registry の `challenge` を持たない)。ベータの間は結果の形も保存の形も動きうること、
カタログを直すとデイリーの図形が変わりうること(§8)、順位の軸(図形ごとの時間か、デイリーの時間か)と
