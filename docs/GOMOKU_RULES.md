# Gomoku — 正式ゲームルール

このドキュメントが Gomoku の仕様の正本である。実装(`apps/simple-games/src/games/gomoku/`)、
テスト、Quick Rules はここに従う。コードはここへ `§n` で言及する。挙動を変えるときは、
同じコミットでこの文書を直す。

ブランド原則([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md))はこの文書より上位にある。

ゲーム ID は `gomoku`、i18n キーの接頭辞は `gomoku`、保存キーの接頭辞は `gm.` である。
規則は **freestyle(自由五目)**を採る — 五以上並べば勝ち、連珠の禁手は実装しない(§11)。

## 1. 盤面と対局者

- 15×15 の 225 交点(`game/types.ts`。行優先の配列、0 = 空、1 = 黒、2 = 白。行 0 が最上段)。
  石は交点の上に置く。
- **黒が先手**で、これは設定ではなくルールである。したがって**手番は石数から導出できる**
  (黒と白が同数なら黒番、黒が 1 つ多ければ白番)。パスは存在しない — 空点がある限り必ず
  打てる。盤面は手番を覚えない(`sideToMove`)。
- **黒か白かはプレイヤーが選ぶ**(ホーム画面。既定は黒)。黒が先手なので、**色の選択が
  そのまま先攻・後攻の選択である** — 画面のボタンにも「黒(先手)」「白(後手)」と書き、
  プレイヤーがその対応を知っている前提に立たない。選択は次の対局に適用される設定であり、
  **対局中のゲームには触らない**。保存キーは `gm.prefs`、セッションは `playerColor` を
  持ち、CPU は残りの色を持つ(`cpuColorOf`)。対局相手は CPU だけである — オンライン対戦も
  ローカル対人戦も作らない([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md)
  「初期リリースで実装しないもの」)。
- 石は白黒だけを描く。文字も数字も置かない — 盤面は全言語で同じに読める
  ([I18N_POLICY.md](I18N_POLICY.md))。盤は木地に罫線と 5 つの星点。

## 2. 一手の解決

- 空いている交点ならどこにでも置ける。禁じ手はない(§11)。
- **置くのは 2 度タップである。**1 度目で交点に印(これから置く石のゴースト)が付き、
  2 度目の同じ交点で確定する。別の交点をタップすれば印がそちらへ移る。
  **理由は物理である**: シリーズが下限とする 320px 幅の端末では交点の間隔が約 19px に
  なり、1 タップ即確定は「置くつもりのなかった石」を量産する装置になる。Sudoku の
  「選択 → 入力」やカードの「選択 → 行き先」と同じ二段の言語である。
- 印を付けるだけの操作では音を鳴らさない — まだ何も起きていない。確定で `select`。
- 石が置かれている交点は押せない(ボタンが無効)。**無効な操作を叱らない**(§10)。

## 3. 終了条件

- 縦・横・斜めのいずれかに自分の石が **5 つ以上**並んだ側の勝ち。**長連(6 以上)も勝ち**
  であって禁手ではない(§11)。勝ち筋は盤面上でリングで示し、他の石を薄くする。
- 225 交点が埋まって五がなければ引き分け。
- 遷移は `status`(`'playing' | 'won' | 'lost' | 'draw'`)で一度だけ起きる
  (`game/session.ts`)。負けを叱る文言は書かない。

## 4. CPU

- 探索は**プレイヤーの着手を起点にのみ**走る。ポーリングも先読みもしない
  ([GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「CPU 探索」)。
- **候補は既に石がある交点の周囲 2 リング内の空点だけ**(`candidateMoves`)。空の半面に
  打つ石は、この手番でも次の手番でも何も作らないし何も止めない。盤面が空のときは天元。
- 難易度は 3 つ(`easy` / `normal` / `hard`):
  - **easy** — 周囲 **1 リング**内の空点からシード決定的にランダムで選ぶ。近くしか見ない
    ことが、そのまま弱さである。
  - **normal** — 候補を 1 手ぶん読んで静的評価が最善のものを選ぶ。**自分の五は取り、
    相手の五は止める**(この 2 つはテストで固定している)。
  - **hard** — 反復深化 α–β(最大 6 プライ)。各ノードで読むのは「石が近い順」の上位 8。
    ノード上限 `HARD_NODE_LIMIT`(8,000)に達したら**完了済みの深さの最善で打つ**。
    深さ 1 は必ず完了するので、hard が浅い読みより弱くなることはない。
- **五が絡む局面では、評価より先に手が決まる**(`forcedMoves` / `collectCandidates`)。
  normal と hard は候補を weigh る前に、①自分がこの手で五を作れるならそれを、
  ②作れず相手が次の手で五を作れるならそれを塞ぐ手を、**候補リストそのものと差し替える**。
  これは根でもノードでも同じ規則である。
  **上の「自分の五は取り、相手の五は止める」は評価値には出せない**、というのがこの規則が
  ある理由である。相手の四を止める手は自分の形をほとんど良くしないので概ね 8,000 点、
  一方で自分の活四を作る手は 100,000 − 1.15 × 12,000 = 86,200 点になる。
  点数だけを比べる CPU は自分の四を作り、次の手で五を打たれて負ける。
  `DEFENCE = 1.15` はこの差を埋められない — **即負けは重みでは表現できない**。
  同じ理由で、**五を作る交点は枝刈りの対象にしない。**ノードの候補は「石が近い順」で
  上位 8 だけを読むが、相手の勝ち筋の交点がその 8 に入る保証はない
  (実際、修正前の再現局面では空点のうち **12 番目**だった)。順位で落とすと、
  探索はどれだけ深く読んでもその手を見ない。
- 評価は連の形を数える: 五 / 活四 / 死四 / 活三 / 死三 / 活二 / 死二。**両端が空いているか
  どうかがこのゲームの全部**で、活四は止められず、死四は受ければ済む。相手の脅威は
  自分のものより **1.15 倍**重く見る — 等価に見る CPU は、自分の四を作る手を選んで
  次の手番で負ける。
- **評価は増分で持つ。**石を 1 つ置いて変わるのはその交点を通る 4 本のラインだけなので、
  make / unmake がその 4 本を引いて足し直し、葉での評価は引き算 1 回になる。
  **最初の実装は毎ノードで盤面全体を数え、1 手に 5 秒かかった** — この設計はその実測から
  来ている。ノードごとの並べ替えも同じ理由で外し、根だけが評価順に並べる。
- 同点の候補はセッションのシードと手数から決定的に選ぶ:
  `createRng(`${seed}:cpu:${moveCount}`)`。同じシードで同じ手順を踏めば、CPU は必ず
  同じ手を返す。ゴールデンテスト(`game/compatibility.test.ts`)が固定する。
- **ノード上限は既存の CPU 対局 2 本を基準に決めた。**同じ環境で Reversi の hard が
  約 248ms、Connect Four の hard が約 301ms かかるのに対し、この上限での応答は約 283ms
  である。既に出荷されている 2 本の間に収まることが、**出荷済みの CPU と同じくらいの
  コスト**だと言える正直な言い方である。(五の判定を各ノードに入れる前は約 256ms だった。
  深く読めても終局手を見ない探索は、強い CPU ではなく負ける CPU なので、この差は払う価値がある。)
- **探索は 450ms の「間」の中では走らない。**`CPU_DELAY_MS` は 1 本の timeout を張り、
  探索はその**中**で走る(`state/GameContext.tsx`。Reversi と Connect Four も同じ形)。
  つまり着手が現れるのは概ね **450ms + 探索時間**であって、450ms の内側ではない。
  上限を「間に収まるか」ではなく既存 2 本を基準に決めたのはこのためで、
  あの 2 本が「待ち時間全体の体感」の既に出荷された基準だからである。
  **ただしこの実測値を CI の判定に使わない。**
  `game/cpu.bench.test.ts` が見るのは「訪問ノード数が上限以内で、実行ごとに同じで、
  少なくとも 1 局面は上限を使い切る」という決定的な仕事量で、壁時計はログに出すだけで
  ある。共有ランナーの壁時計はランナーを測っているにすぎず、生成コストのテストが既に
  「**壁時計は判定していない**」と決めている([RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md)、
  [SUDOKU_RULES.md](SUDOKU_RULES.md) §7)。実測値は機械で動く — CI の遅いランナーでは
  同じ上限で **417ms** だった。**出荷済みの CPU と同程度のコストで収まる範囲でいちばん強い
  CPU** がこの選択であって、そこからはみ出す強さは採らない(issue #26 非目標)。
  低スペック実機での体感は、このドキュメントではなく**実機確認(リリース Gate)で見る**。
- CPU の着手は約 450ms 置いてから現れる(`CPU_DELAY_MS`)。アンマウント・Undo・新規対局は
  この遅延を破棄する。

## 5. Undo

- **無制限・無料**。自分の直前の決定点まで戻す — CPU の応手と自分の一手がまとめて
  取り消される。CPU の手番の途中には戻さない。
- Undo は振り直しではない: 戻して同じ交点に置けば、CPU も同じ手を返す(§4 の決定性)。
- 広告視聴や課金による Undo は作らない([ADS_POLICY.md](ADS_POLICY.md))。

## 6. 助けの形

- 助けは Undo(§5)ひとつ。無料で、無制限で、初回起動から使える。
- **Hint は作らない**: 盤面は完全に見えており、隠れた情報がない。次の一手を教える機能は
  CPU がプレイヤーの側でも打つことになる(REVERSI_RULES.md §7 / CONNECT_FOUR_RULES.md §6
  と同じ判断)。
- 合法手の表示も作らない — 空いている交点はすべて合法で、示す情報がない。置き間違いへの
  助けは 2 度タップ確定(§2)が担う。

## 7. スコアと統計

- スコアという数はない。対局の結果は勝ち / 負け / 引き分けだけである。
- 統計は難易度ごとに `played`(開始した回数)・`wins`・`losses`・`draws`、全体で
  `totalPlaySeconds`。ストリークは数えないし表示しない。
- 対局を放棄して新しく始めた場合、負けには数えない(`played` には既に数えている)。
  記録されるのは実際に終局した対局だけ — 統計が脅しになってはならない。
- プレイ時間は逐次計上(bookedRef 方式、2048 と同じ)。

## 8. 中断と再開

- **途中保存する。** 盤面はターン制で、保存して開き直した盤面は保存した瞬間と同じである
  (GAME_2048_RULES.md §10 と同じ理由)。
- 保存スロットは 1 つ(`gm.saveGame`)。盤面(225 文字、交点ごとに `0`/`1`/`2`)・
  **プレイヤーの色**(`playerColor`)・難易度・シード・手数・経過秒を持つ
  (`game/serialize.ts`)。**手番は保存しない** — 黒先手でパスがないので石数から導出できる。
- **Undo 履歴は保存しない**。再開した対局はその局面から始まる。
- 壊れた保存は読み捨てて、ホームへ戻る(勝手に新しい対局を始めない)。検証は fail-closed:
  駒種以外の文字・**黒と白の枚数差が 0 でも 1 でもない盤面**・**手数が盤面の石数と
  一致しない保存**・五連が既に存在する(終局済み)保存は破棄する。石は 1 手につき
  ちょうど 1 つ増え、決して減らないので、手数と石数は必ず一致する。手数は CPU の抽選の
  半分(§4)なので、食い違う保存を受け入れると、保存した対局とは違う応手を返す盤面を
  再開させてしまう。

## 9. Quick Rules(アプリ内チュートリアル)

3 ステップ・図中心・各 1 文(初回起動時に表示、以後はホームから):

1. 1 回目のタップで狙い、2 回目で置く。
2. 縦・横・斜めのどれかに五つ並べたら勝ち(六つ以上でも勝ち)。
3. 相手の「両端が空いた三」は先にふさぐ。

詳細は Landing Page へ。ガイドを公開するまで「詳しく見る」は出さない
(`src/ui/landing.ts`)。オフラインでは何も起きない(ゲームは止めない)。

## 10. 演出とアクセシビリティ

- 石は DOM 要素。置いた石は 120ms のポップ。要素は増やさない — 粒子も画面揺れもない。
- Reduced Motion(アプリ設定または OS)ではポップを無効にし、石は置かれた位置に
  すでにある状態で描かれる。
- 勝った並びはリングで示し、他の石を薄くする。色だけに頼らない。
- **決着してから結果カードが出るまでに約 1 秒置く**(`ui/useResultReveal.ts`)。五つの並びを
  見る時間であり、その間に押せるものはない。Reduced Motion では従来どおり即時に出す。
- 最後に置かれた石には小さな印を付ける(CPU の手を見失わないため)。印は相手側の石の色で
  描く — 1 色では白と黒の両方の上で読めないため。
- 盤面は 225 個のボタン。各交点は「行・列: 空 / 自分の石 / CPU の石 / もう一度タップで置く」
  を読み上げる。石のある交点は無効になる。
- ターン行は高さを固定し、手番・確認待ちのどちらを言っても盤面が跳ねない。
- **時計を出さない**。経過時間は統計にだけ残る。
- 効果音は既存の合成音(`services/sound`)のみ: 確定で `select`、勝ちで `clear`、
  負け・引き分けで `gameOver`。設定に従う。印を付けるだけでは鳴らさない。

## 11. 意図的な差分

市中の五目並べ / Gomoku / Renju 系アプリを調べたうえで、意図的に合わせないものを記録する。

**ブランド原則により合わせないもの**

- **Undo・強さ解放を広告や課金に結び付けない**。難易度は最初から全部選べる。
- レーティング・ランキング・オンライン対戦はない。記録は端末の中だけにある(§7)。
- デイリーやストリークで毎日呼び戻さない。

**設計判断として合わせないもの**

- **連珠の禁手(三三・四四・長連禁)を実装しない。**禁手は人間同士の対局で先手の有利を
  削るための均衡装置であり、CPU 対局ではその役を難易度が担う。freestyle として出す。
  長連は勝ちであって反則ではない(§3)。
- **盤面サイズは 15×15 だけ**。13×13 や 19×19 は別の遊びになる。v1 では 1 つに絞る
  (CONNECT_FOUR_RULES.md「盤面サイズは 7×6 だけ」と同じ判断)。
- **最強 CPU を作らない**。先手必勝が理論上知られているゲームであり、完全読みの CPU は
  「勝てない相手」にしかならない。hard は上限付き探索で止める(§4、issue #26)。
- **定石データベースを積まない**。序盤も同じ探索で打つ。
- **棋譜・解析・形勢グラフを持たない**。対局が終わったら結果だけが残る。
- **1 タップ即着手にしない**(§2)。交点の物理的な狭さに対する答えであり、
  設定で切り替えられるようにもしない — 片方だけが正しいなら、選ばせるのは責任の転嫁である。
