# Hearts — 正式ゲームルール

このドキュメントが Hearts の仕様の正本である。実装(`apps/simple-games/src/games/hearts/`)、
テスト、Quick Rules はここに従う。コードはここへ `§n` で言及する。挙動を変えるときは、
同じコミットでこの文書を直す。着手前の計画は
[docs/plans/2026-08-08-hearts-and-gin-rummy.md](plans/2026-08-08-hearts-and-gin-rummy.md)
にあるが、実装後はこの文書が勝つ。

ブランド原則([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md))はこの文書より上位にある。

ゲーム ID は `hearts`、i18n キーの接頭辞は `hearts`(名称キーは `heartsName`)、保存キーの
接頭辞は `ht.` である。タイトルは全言語で `Hearts`(固有名詞は訳さない
— [I18N_POLICY.md](I18N_POLICY.md))。対局相手の表記も全言語で `CPU 1` / `CPU 2` /
`CPU 3` — こちらは固有名詞だからではなく、**席は方角であって名前ではない**からで、
14 言語のどの読者も同じ位置に同じ数字を見る。

**採ったルールの出典**: 標準的な 4 人ハーツ(Hoyle 系のルール集に載る 13 枚配り・
3 枚パスの輪番・2♣ 強制リード・♥ 1 点 / Q♠ 13 点・ムーンは他 3 席に +26・
100 点到達で終局)に従う。地方変種のうち採らなかったものは §12 に列挙する。

姉妹タイトルの Gin Rummy は同じ「対戦カード」だが 2 人制のドロー & メルドで、
隠れた情報の量も助けの形も違う([GIN_RUMMY_RULES.md](GIN_RUMMY_RULES.md))。
FreeCell / Solitaire / Spider は 1 人用のペイシェンスである。同じ棚に並ぶ
5 本の設計が違うのは意図であって、機能一覧を揃えないという方針そのものである
([FREECELL_RULES.md](FREECELL_RULES.md) §8)。

## 1. 場と対局者

- **4 人**。下があなた、**左が CPU 1・対面が CPU 2・右が CPU 3**(`game/types.ts` の
  `YOU = 0`、席は 0 → 1 → 2 → 3 の時計回り)。3 席とも CPU で、3 席とも選択中の
  同じ難易度で打つ。**オンライン対戦もローカル対人戦も作らない**
  ([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md))。
- 席が方角であることは規則にも効く。**次の席は左の席**なので、パスの向き(§2.1)は
  席番号の足し算そのものになる。
- **52 枚**。カードは 1 つの整数 `スート × 13 + (ランク − 1)` で持つ
  (`game/cards.ts`)。表裏の別も持ち主も持たないので、カードが自分の居場所と
  食い違うことがない。スートは 0 スペード / 1 ハート / 2 ダイヤ / 3 クラブ。
- **A は最高位**。ランク 1 が 2、ランク 13 が A で、回り込みはどこにもない。トリックは
  リードスートの最大が取るので、そのスートの A は必ず取る。Gin Rummy のコピーは
  A を最低位に持つ — 同じ「カードは整数」でも 2 本は A の価値について合意していない
  ので、表は共有せず**コピーしてある**。
- **点札は 14 枚だけ**(`penaltyPointsOf`)。♥ が 1 枚 1 点 × 13、Q♠ が 13 点。残り
  38 枚は 0 点で、**トリックを負けるためだけに存在する**。1 ハンドの点は必ず
  合計 26 点になる(`HAND_PENALTY_TOTAL`)。
- **配り**: 52 枚を 13 枚ずつ、あなたの席から 1 枚ずつ回して配る(`HAND_SIZE = 13`)。
  山札も台札も残らない。
- **配札はシード決定的**。`createRng(`` `${seed}:deal:${handNumber}` ``)` で配るので、
  同じシードは同じマッチの同じハンド番号で必ず同じ配札になる
  (`game/compatibility.test.ts` が v1 の並びを golden で固定する)。
- **配り手はいない。**パスの向きはハンド番号で決まり、リードは 2♣ の持ち主が取る
  (§2)。決めるものが無いので、**配り手も先手選択の画面も存在しない**。
- 難易度はホーム画面で選ぶ(既定 `normal`、保存キー `ht.prefs`)。選択は**次の
  対局に適用される設定**であり、**進行中のマッチには触らない** — 始めた相手のまま
  終わる。
- 場は DOM とインライン SVG のスートで描く。カード面には言語に依存する文字を
  置かない(ランクは全言語 ASCII の `2…10 J Q K A`)。

## 2. 一手の解決

ハンドは 3 つの局面を進む(`Phase`: `passing` → `playing` → `over`)。

### 2.1 パス(`passing`)

- **3 枚ちょうど**を選んで渡す(`PASS_SIZE = 3`)。2 枚はパスではない。
- **向きはハンド番号の輪番**で、`PASS_CYCLE = [1, 3, 2, 0]`(`game/types.ts`):

  | ハンド | 1        | 2        | 3          | 4        | 5 …    |
  | ------ | -------- | -------- | ---------- | -------- | ------ |
  | 向き   | **左へ** | **右へ** | **対面へ** | **なし** | 左へ … |

  席の足し算で言えば +1 が左、+3 が右(時計回りに 3 席は 1 席戻る)、+2 が対面、
  0 が誰も渡さないハンドである(`passReceiverOf`)。

- **なしのハンドはパス局面自体を飛ばす。**何も動かないものを座って待つ意味が
  無いので、`dealHand` はそのまま `playing` で配る。
- **交換は 4 席同時に解決する**(`confirmPass`)。4 人目の確定が 12 枚を一度に
  動かす。1 席ずつ解決すると別のゲームになる — 先に渡した席は、他席が変えたあとの
  手札から選ぶことになる。
- 選ぶ・戻すは**着手ではない**(`doSelectPassCard` / `doUnselectPassCard`)。場に出る
  ものが変わらないので**手数を進めず**、CPU のタイブレーク列(§4)も動かない。
  ただし保存はされる — 選びかけで殺されても、選びかけのまま戻る(§9)。
- CPU の 3 席は、あなたが選んでいる間に順に確定する(`cpuSeatToAct` は未確定の
  最小席番号)。台のふるまいがそうだからである。
- **確定ボタンは常に画面にあり、3 枚目で押せるようになる。** Gin Rummy の Knock
  ボタン(不在がそのまま「まだできない」の表示)とは逆の作法で、こちらは**パス
  自身の進捗**である — 何枚選べば終わるのかを、ボタンが現れるのを待たずに見せる。

### 2.2 出せる札

規則は 4 つで、適用順に並ぶ(`legalPlaysIn`。実装はエンジンと CPU の**両方**が
同じ 1 本を呼ぶので、相手が別のルールで打つことがない):

1. **ハンドの最初のリードは 2♣ だけ。**他の札は 1 枚も出せない。
2. **リードスートを追う。**追える限り追う。**この規則にだけ例外が無い** — 以下の
   規則はすべて「そのスートを持っていない席」にしか出番が無い。
3. **初トリックは点札を出せない。**スートが無くて捨てる席も、♥ と Q♠ は置けない。
   **例外は点札しか持っていない席**で、これは配られ得る手なので、規則を
   デッドロックさせるより曲げる(`engine.test.ts` が固定)。そうして出た ♥ は
   本当に ♥ をブレイクする。
4. **♥ は 1 枚出るまでリードできない。**例外はリーダーの手札が ♥ だけのとき。
   **Q♠ は ♥ ではないので、ブレイクに数えないし、いつリードしてもよい**
   (`playCard` が `isHeart` でだけブレイクを立てる)。

- 操作は**二度タップ確定**。1 度目で札が持ち上がり、2 度目で確定する(Gomoku の
  前例。3 段に重なった手札で誤爆しないため)。
- **無効な操作は叱らない**。出せない札は沈んで(`ht-sunk`)押せなくなるだけで、
  無効音も無効振動も鳴らない。

### 2.3 トリックの解決

- **リードスートの最大が取る**(`trickWinnerOf`)。**切り札は無い**ので、他スートの
  札はどれだけ大きくても勝てない — ボイドに価値があるのはそのためである。
- **4 枚目は自動で回収されない。**`playCard` は札を場に置くだけで、`collectTrick` が
  別の拍として畳む。**4 枚が表で並んでいる状態が状態として存在する**ので、画面は
  それを見せてから動かせる(§11.2)。
- 取り主が次をリードする。**13 トリック目で手札は全部空になり、52 枚は 13 の
  トリックの中にある**(`engine.test.ts` が保存則として固定)。

## 3. 終了条件

### 3.1 ハンドの終わり

**ハンドは 13 トリックで必ず終わる。**Gin Rummy の「ハンド無効」に当たるものは
無い — 引く山が無く、全員が最後の 1 枚まで出すからである。

### 3.2 採点(`scoreHand`)

- **♥ 1 枚 = 1 点、Q♠ = 13 点。**1 ハンドは必ず 26 点で、取った席の点になる。
- **ムーン(1 席が 26 点すべてを取る)は、他 3 席に +26。**取った席は 0 点。
- **自席から 26 点を引く選択式は作らない**(§12)。選択と言っても常に有利な方を
  選ぶだけで、決めるところが無く、画面が説明すべき採点経路だけが 1 本増える。
- **Q♠ だけを取った 13 点はムーンではない。**半分であって全部ではない
  (`engine.test.ts` が明示的に固定している)。
- 点はハンドが終わった瞬間にマッチの点へ入る(`session.ts` の `advanced`)。清算
  画面が出しているのは**もう動いたあとの本当の順位**である。

### 3.3 マッチの終わり

- **ハンドが終わった時点で誰かが 100 点(`MATCH_TARGET`)以上なら終局。**勝つのは
  **最少点**である。
- 勝敗はあなたの側から言う(`statusOf`):
  - **あなたが単独で最少 = 勝ち**(`won`)
  - **あなたを含む同点で最少 = 引き分け**(`draw`)
  - **あなたが最少でない = 負け**(`lost`)。CPU 2 席が同点最少でも、あなたが最少で
    ない以上それは負けである。
- **4 席あるので引き分けは珍しくない。**Gin Rummy(2 人・先に 100 点)に引き分けが
  存在しないのと対照的で、統計の列もそれに従う(§8)。
- 終局の瞬間に 4 席の最終スコアを**少ない順**に出す。負けを叱る文言は書かない。
  次のマッチは無料である(復活の課金も広告視聴もない —
  [ADS_POLICY.md](ADS_POLICY.md))。

## 4. CPU

- **探索はしない。**すべてヒューリスティックで、いちばん重い処理でも「13 枚と
  出た札を数える」に収まる。ボード 4 本のようなノード上限を持たないのは、上限に
  当たる探索が無いからである([GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「CPU 探索」)。
- **拍は 1 つずつ、`CPU_DELAY_MS`(450ms)のタイマー 1 本。**この棚で**最初の連鎖
  手番**である: あなたが 1 枚出すと、残り 3 席が順に出し、完成したトリックが
  畳まれ、取ったのが CPU ならそのまま次のリードへ続く。それでもタイマーは 1 本で、
  effect がセッション自身に依存しているだけである(`state/GameContext.tsx`)。
  ポーリングも先読みもしない。着地したタイマーは「**いま**何が owing か」を
  ref で確かめてから打つ。
- **拍の順序**は `beatOwed` が決める: 清算済みのハンド → 完成トリックの回収 →
  CPU の手番。**先頭で意図的に止まる** — 次のハンドを配るのは**あなたのタップ**で
  あって、タイマーではない。このゲームで読む価値のある唯一の画面を、勝手に
  消さないためである。
- **保存から CPU の手番で再開しても専用の経路は要らない。**effect は渡された
  セッションを見るだけで、それが配札から来たか保存から来たかを知らない。
- **難易度は 3 つ**(`easy` / `normal` / `hard`)。違いは「何を見るか」であって
  「どれだけ長く考えるか」ではない(`game/cpu.ts`)。

### 4.1 パスで何を渡すか(`passUrgencyOf`)

|                  | easy           | normal                                                                                           | hard                                   |
| ---------------- | -------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------- |
| 札の値付け       | **ランクだけ** | 下記のとおり                                                                                     | normal と同じ + 短スート               |
| Q♠               | ただの Q       | **最優先で渡す**(100)                                                                            | 同左                                   |
| A♠ / K♠          | ただの大札     | **Q♠ を捕まえる札として渡す**(60 + ランク)。ただし ♠ が 5 枚以上あれば隠れられるのでランクのまま | 同左                                   |
| ♥ の Q 以上      | ただの大札     | やや渡したい(20 + ランク)                                                                        | 同左                                   |
| 3 枚以下のスート | 見ない         | 見ない                                                                                           | **ボイドを作りに行く**(+8 ×(4 − 枚数)) |

easy は「K は 5 より大きい」しか知らない。だから A♠・K♠・A♥ を投げて Q♠ を抱える
— それが easy である。3 番目の札が同点になったときだけ、タイブレークのコインが
どれを渡すかを決める(`chooseCpuPass`)。

### 4.2 プレイで何を出すか(`chooseCpuPlay`)

| 局面                       | easy                 | normal                                                                           | hard                                                                                      |
| -------------------------- | -------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| **リードする**             | **いちばん大きい札** | 小さい札。Q♠ 未出なら A♠ / K♠ を避け(+40)、Q♠ 自身(+10)と ♥(+6)も避ける          | 同左 + **まだ上位が残っているスートを歓迎**(−20)、他席がボイドと分かるスートを避ける(+12) |
| **追随する(抜けるとき)**   | いちばん大きい札     | **勝っている札の下でできるだけ高く抜く**。**Q♠ が下に落とせるなら最優先**(−1000) | 同左                                                                                      |
| **追随する(必ず取るとき)** | いちばん大きい札     | **点の少ない札を、そのなかで小さく**(点 × 10 + ランク)                           | 同左                                                                                      |
| **捨てる(ボイド)**         | いちばん大きい札     | **Q♠ → A♠ / K♠ → ♥ の順に危険な札から捨てる**                                    | 同左 + **2 枚以下のスートを空けに行く**                                                   |

- **ムーンの検知は 3 難易度すべてに効く。**点を取っている席が 1 つだけで、その席が
  12 点(`MOON_ALERT`)以上を取っていれば、**その席が取っているトリックへ点札を
  投げない**(`FEEDS_A_SHOOTER`)。
- **取り返す妨害は hard だけ**(`blocksMoon`)。ムーンを狙っている席がトリックの
  上にいるとき、リードスートで上回れる**いちばん小さい札**で取り上げる。他に手が
  あるなら Q♠ は使わない。
- **CPU 自身はムーンを狙わない**(`moonThreatOf` は自席を返さない)。狙う CPU は
  「3 席が結託して 1 人を狙う」ことと区別がつかない。
- **同点候補はシード決定的**に選ぶ: `createRng(`` `${seed}:cpu:${moveCount}` ``)` の
  1 つの float で等価な候補から選ぶ。同じ保存を再開すれば、CPU は同じ手を返す。
- 長時間 CPU を占有する「強い CPU」は作らない(issue #26 非目標)。hard が数える
  のは「見えた札」までで、そこで止まる。

## 5. CPU が見ているもの

このゲームは**不完全情報**である。「CPU はこちらの手札を覗いているのでは」という
疑いは議論では晴れないので、**型で決着させている**。

- `game/cpu.ts` が読むものはすべて **`CpuView`** として渡る。`CpuView` に**他席の
  手札を置く場所も、他席が選んだパスを置く場所もない**。追加すればその差分に
  覗きがそのまま現れる — 型が存在する理由がそれである。
- 完全な `HandState` から `CpuView` への橋は **`buildCpuView` ただ 1 つ**で、参照では
  なく**コピー**を渡す(ビューから元のハンドへ戻れない)。テストは隠された札を
  すべて配り直しても view が変わらないこと、他席のパス選択が見えないことを
  確かめる(`game/cpu.test.ts`)。
- `CpuView` が実際に持つのは、この 13 フィールドだけである:

  | フィールド      | 中身                                                     |
  | --------------- | -------------------------------------------------------- |
  | `seat`          | 自席。以下の席番号はすべてこれと突き合わせて読む         |
  | `difficulty`    | 自分の強さ                                               |
  | `phase`         | いまの局面(`passing` / `playing` / `over`)               |
  | `turn`          | 誰の番か。パス中とトリックの合間は null                  |
  | `hand`          | **自席の手札**(昇順)                                     |
  | `passOffset`    | 今ハンドのパスの向き。0 は誰も渡さないハンド             |
  | `passSelection` | **自席が**選んだパスの札。**他席のものは決して入らない** |
  | `tricks`        | 完了したトリック(古い順)と、それぞれの取り主             |
  | `trickLeader`   | 場のトリックをリードした席                               |
  | `trickCards`    | いま場に出ている札、リードから順に                       |
  | `heartsBroken`  | ♥ が割れているか                                         |
  | `scores`        | マッチの点数、席ごと                                     |
  | `taken`         | このハンドでここまでに取った点、席ごと                   |

- **公開履歴は `tricks` そのものである。**Hearts では公開の場で起きることが
  「札がトリックに出る」の 1 種類しかないので、Gin Rummy のような別のログを
  持たない(`game/types.ts`)。台にいた人が見たものと、この配列は同じである。
- CPU はそこから「出た札」「まだ出ていない札」「リードを追えなかった席のボイド」
  「Q♠ が出たか」を導く(`knowledgeOf`)。使うのは hard だけである。
  **人間の熟練者が覚えていられる情報は CPU も覚えてよい。それ以上は持てない。**
- **そして 1 つ、熟練者なら覚えているのに CPU が覚えないものがある** —
  **自分がパスで渡した 3 枚**である。交換が済むと `selected` は空になり、
  `passSelection` にはもう何も残らない。左隣に Q♠ を渡したことを人間は覚えているが、
  この 3 席は覚えていない。**プレイヤー有利に倒した意図的な判断**であり、
  取り消すなら §12 に足すのではなくこの行を消すことになる。
- **配札のシードは cpu.ts に渡らない。** 決定的なのは配札も CPU も同じだが、CPU が
  シードから配札を逆算する経路はない — 同点タイブレーク用の float は配札とは
  独立の系(`${seed}:cpu:${moveCount}`)から 1 つだけ渡る。**鍵ではなく数**である。

## 6. Undo — 作らない

**このゲームに Undo はない。**ボード 4 本(Reversi / Checkers / Connect Four /
Gomoku)の Undo が成立していたのは、**両者が同じ盤面を見ている**からである。

ここには隠れた情報があり、しかも**応手は 3 つ返ってくる**。3 席の答えを見てから
自分の 1 枚を戻せば、「そのスートは誰が切れていたか」「Q♠ はどこにあったか」を
知ったまま同じ局面へ戻れる。**戻せるのは手であって、知ってしまったことでは
ない。**取り消せない漏れを生む機能は作らない(Minesweeper の「取り消せるなら
賭けが残らない」と同族の判断)。

`game/session.ts` は Undo を提供せず、`state/GameContext.tsx` にもそれを足す場所は
ない。助けは §7 の形で来る。広告視聴や課金による Undo も、もちろん作らない。

## 7. 助けの形 — ルールの可視化だけ

助けは 1 つだけで、**「ルールが許す札」であって「次の一手」ではない**。

**出せる札の常時表示**(`state/GameContext.tsx` の `playable`)。ルールが許す札は
そのまま押せて、それ以外は沈む。§2.2 の 4 規則 — スートを追う義務・初トリックの
点札禁止・ブレイク前の ♥ リード禁止・2♣ の強制リード — が**知っていなければ
ならないもの**から**見えているもの**に変わる。Checkers の「動かせる駒の表示」と
同じ、ルールの可視化である。

**どの札が良い札かは何も言わない。**沈んでいない札は全部同じ顔をしている。

**Hint(次の一手の提案)は作らない。**何を渡し・いつ抜け・いつ取るかがこのゲーム
そのものであり、それを教えることはゲームを肩代わりすることになる
([FREECELL_RULES.md](FREECELL_RULES.md) §8 と同じ判断)。**Gin Rummy のような
「手札の自動整理」も無い** — 並びはスート順 → ランク順で固定であり(§11.2)、
そこに判断は含まれていない。

助けはすべて無料で、初回起動から使える。広告視聴や課金の報酬にはしない。

## 8. スコアと統計

- **点はルールが定める対局の中身である。** ♥ の 1 点も Q♠ の 13 点もムーンの
  26 点もルールの一部であって、遊びの外から足した数ではない(2048 のスコアと
  同じ扱い)。**それとは別の発明数値 — ベスト記録・平均点・最短ハンド数・
  レーティングは持たない。**
- 統計は難易度ごとに `played`(始めた回数)・`wins`・`losses`・**`draws`**、全体で
  `totalPlaySeconds`(`storage/schemas.ts`)。
- **`draws` の列がある。**Gin Rummy には無い(2 人で先に 100 点を越えるのは必ず
  片側)。Hearts は 4 席の最少点争いなので、あなたを含む同点最少は**ルールが実際に
  produce する結果**であり(§3.3)、勝ちにも負けにも丸めずに列を持つ。
- **ハンドは記録しない。** ハンドはマッチの中の回であり、ハンド勝利を数えると
  一晩を十数回数えることになって、他のゲームの「勝ち」と意味が揃わない。
- マッチを放棄して新しく始めた場合、負けには数えない(`played` には既に数えて
  いる)。記録されるのは実際に終局したマッチだけ — 統計が脅しになってはならない。
- ストリークは数えないし表示しない。
- プレイ時間は逐次計上(bookedRef 方式)。ゲーム画面が見えている間だけ進み、
  **プレイ中に時計は出さない**。
- レビュー依頼(`recordGameCompleted`)は**マッチに勝ったときだけ**呼ぶ。ハンドの
  勝ちでも引き分けでも呼ばない([REVIEW_PROMPT_POLICY.md](REVIEW_PROMPT_POLICY.md))。

## 9. 中断と再開

- **途中保存する。**保存スロットは 1 つ(`ht.saveGame`)で、**ハンドだけでなく
  マッチ全体**を持つ: シード・難易度・ハンド番号・4 席の点数・手数・経過秒、
  そして符号化したハンド(`game/serialize.ts` の 12 フィールド — 版・フラグ・
  4 席の手札・4 席のパス選択・場の札・完了したトリック)。
- 符号化したハンドには**完了したトリックも入る**。それが CPU の記憶そのもの
  (§5)なので、これを捨てて再開すると「あなたがどのスートを切っていたか忘れた
  CPU」= 中断したときとは別の相手になる。
- **デコードは fail-closed。**そして Hearts では fail-closed が特別に強い意味を
  持つ:

  **保存されたハンドは、エンジンで最初から再生して検証する**(`isValidHand` の
  `isValidPlay`)。パス以降に各席が何を持っていたかは「いま持っている札 + その席が
  出した札」から復元できるので、**全トリックを `playCard` に通し直す**。したがって
  次のような保存は**復元されない**:

  - **リボーク** — リードスートを持っていたのに追わなかったトリック
  - **不正なリード** — 初トリックが 2♣ でない、ブレイク前に ♥ をリードしている、
    初トリックに点札が落ちている
  - **偽の取り主** — 記録された `leader` が、再生した結果の取り主と食い違う
  - 52 枚の過不足・重複、順序が壊れた手札、局面が許さないパスのフラグ

- **`moveCount` は下限ではなく厳密検査**(`storage/gamePersistence.ts` の
  `expectedMoveCount`)。Hearts では**打った拍がすべて局面に現れている** —
  ハンドは出た札と取ったトリックを持ち、それ以前のハンドは 13 トリックずつ
  打ち切られており、各ハンドのパスの向きは番号で決まる(`passOffsetOf`)ので、
  推測の余地が無い。手数は CPU のタイブレーク列の半分(`${seed}:cpu:${moveCount}`)
  なので、**自分の履歴と食い違う手数の保存は、置いたときとは違う答えを返す
  マッチになる**。だから直さずに捨てる。
- **パスの向きが番号と食い違う保存も捨てる。**向きはハンド番号だけで決まるので、
  食い違えばそのハンドは配られていない。
- **終局済みのマッチは復元しない。**どこかの点が 100 以上の保存は、そもそも
  プレイから生まれえない(越えた時点でマッチが終わる)ので破棄する。schema と
  session の**両方**が同じ規則を持ち、どちらも相手に依存していない。
- 壊れた保存は読み捨ててホームへ戻る(**勝手に新しい対局を始めない**)。
- アプリがバックグラウンドへ回るとき(`visibilitychange` と Capacitor の `pause`)、
  盤面の保存と**プレイ時間の計上を同じ同期処理で**行う。OS は別のイベントなしに
  バックグラウンドのアプリを終了できるため、盤面だけを保存すると前回の同期以降の
  秒数が永久に失われる。復元した経過秒は「計上済み」として扱い、二重計上しない。
- CPU の手番でも、**まだ誰も取っていない完成トリックの上でも**そのまま保存され、
  再開時に §4 の effect がそこから拾う。復元専用の経路は無い。
- パスを選びかけたところで離れた場合、選んだ札ごと保存される。選ぶことは着手では
  ないので、手数は選んでいない保存と同じである(§2.1)。
- **Undo 履歴は保存しない** — そもそも存在しない(§6)。

## 10. Quick Rules(アプリ内チュートリアル)

3 ステップ・図中心・各 1 文(初回起動時に表示、以後はホームから):

1. **3 枚をパス** — ほとんどのハンドの最初に 3 枚選んで渡す。左 → 右 → 対面 →
   誰も渡さないハンド、の順に回る。
2. **スートを追う** — 最初に出た札のスートが基準で、持っている限り合わせて出す。
   そのスートのいちばん強い札がトリックを取る。
3. **最少点が勝ち** — 取った ♥ は 1 枚 1 点、Q♠ は 13 点。誰かが 100 点を超えた
   時点で最も少ない点が勝つ。

図は場と同じカード部品で描くので、図が実装から乖離しない。そして**図自身がルールに
従っている** — 「3 枚をパス」の図はちょうど 3 枚であり、「スートを追う」の図は
本当に同じスートの追随(♣4 → ♣8)であり、「最少点」の図は本物の値札
(♥A に +1、♠Q に +13)である。

詳細は Landing Page へ。ガイドを公開するまで「詳しく見る」は出さない
(`src/ui/landing.ts`)。オフラインでは何も起きない(ゲームは止めない)。

初回チュートリアルを終えたときだけ、いちばん優しい相手で 1 局が始まる。

## 11. 演出とアクセシビリティ

### 11.1 手札は 3 段(5 + 4 + 4)— 実測で決めた

計画はこの数を開けたまま、**先に測ってから決める**とだけ書いていた
(2026-08-08)。算術が決めた答えは 3 である。

n 枚を重ねた 1 段は「見えている帯 (n − 1) 本 + 丸ごとのカード 1 枚」なので
`(n − 1)·s + w = A`。A はファン自身の幅 `min(100% − 12px, 420px)` で、vw は使わない
([ARCHITECTURE.md](ARCHITECTURE.md) の盤面幅の教訓)。二度タップの 1 度目が
落ちるのは**帯**なので、タップ標的は s であり、シリーズの床は `--tap-size: 48px`
である。

| 1 段 13 枚        | A = 308(320px) | A = 348(360px) | A = 408(420px) |
| ----------------- | -------------- | -------------- | -------------- |
| 最大の帯 s = A/13 | 23.7px ✗       | 26.8px ✗       | 31.4px ✗       |

13 枚 1 段は近くもないし、札を縮めて解決する問題でもない。**2 段(7 + 6)も
成立しない** — 7 枚の行は**カードの幅に関係なく** 320px で床を割る。7 本の帯が
48px ずつで 336px を要するのに、ファンには 308px しか無いからである。

そこで**重なりの向きを 90 度倒した**。手札は**3 段・各 5 枚まで**(`MAX_PER_ROW`)
で、5 枚は幾何が閉じる数である: カード幅をファンの 20% にすると
`5 × 20% = 100%` で、**横の重なりはゼロ**になる。代わりに**縦に重ねる** —
行のピッチはファン幅の 18%(カード高 28% との差 10% が重なり)で、下に行がある行は
**上帯**を見せる。そこはランクの角が印刷されている場所であり、横の重なりが
していた議論をそのまま縦にしたものである。タップ標的は s × p の長方形になり、
**両辺とも床を超える**:

| 3 段(5 + 4 + 4) | A = 308(320px) | A = 348(360px) | A = 408(420px) |
| --------------- | -------------- | -------------- | -------------- |
| カード w = 20%  | 61.6px         | 69.6px         | 81.6px         |
| 帯 s = 20%      | **61.6px** ✓   | 69.6px ✓       | 81.6px ✓       |
| 上帯 p = 18%    | **55.4px** ✓   | 62.6px ✓       | 73.4px ✓       |
| カード高 28%    | 86.2px         | 97.4px         | 114.2px        |
| ファン高 64%    | 197.1px        | 222.7px        | 261.1px        |

このカードは Gin Rummy の手札カードと**どの幅でも同じ大きさ**になる。壊す価値の
ない一致である — 2 本が違うのは手札の枚数であって、カードの大きさではない。

**札が減ると `ceil(n / 5)` で再配行する。**10 枚で 2 段、5 枚で 1 段になり、
**卓の高さはトリックが積み上がるのと同じ速さでトリック領域へ返る**(パス中は
3 枚がトレイに出ているので、その間も 10 枚の 2 段である)。行の枚数は前の行から
埋めるので、13 枚は 5 + 4 + 4 になる。

**並びはスート順 → ランク順**で固定である。`hands[seat]` が既にその順で持っている
(カードは `スート × 13 + ランク − 1`)し、トリックテイキングが欲しい順でもある
— スートを追うとはスートを探すことなので、群はスートである。Gin Rummy がメルド順
で並べるのは、あちらの群がメルドだからである。新しいスートの先頭はカード左端へ
フェルト色の細い影を落とし、何も動かさずに群を切る。

### 11.2 その他

- **トリックは十字に置く。**あなたが下、CPU 1 が左、CPU 2 が上、CPU 3 が右で、
  **席が出した札はその席の側に着地する**。「誰が Q♠ を出したか」が説明なしで
  読めることが、行ではなく十字にした理由のすべてである。取り主が決まると、
  4 枚はその方角へ 380ms で畳まれる(次の拍 450ms より短いので、必ず畳み終わって
  から次の札が落ちる)。
- **相手席が見せるのは枚数と、このハンドで取った点、そしてマッチの点だけ。**
  実際の台で公開されている事実がそれだけだからである。裏向きのカードは**枚数分
  並べず 1 枚**にする — 3 席とテーブル幅 18% の列に 13 枚ずつ置く場所は無く、
  そもそも知られているのは数だけである(Gin Rummy は相手が 1 人で横幅が使えるので
  枚数ぶん並べられる。同じ絵を無理に揃えない)。
- **直前のトリックを取った席に小さな印**を付ける(ボード 4 本の「最後に動いた駒の
  印」の同型)。次にリードするのが誰かは、拍の合間にいちばん見失う事実である。
- **カード面は両テーマとも紙のまま。**赤と黒の区別が読めないカードは手札ではない。
  ダークテーマでは紙を暗く沈ませ、フェルトを暗くする(反転させない)。これは
  ゲーム CSS が色を書く例外であり、理由をファイル冒頭に書く
  ([ARCHITECTURE.md](ARCHITECTURE.md))。フェルトは**青灰色**で、Reversi の緑盤、
  Gin Rummy の暖色の卓、FreeCell の中間灰のどれとも違う — 4 つの面が取り違え
  られないようにしてある。
- 選択は**浮き上がり + 輪郭 + リング**で示す。色だけを唯一のチャンネルにしない。
  出せない札は沈める(彩度と不透明度)。
- **Reduced Motion**(アプリ設定または OS)では、140ms の持ち上がりも 380ms の
  畳みも止まる(シリーズ共通規則)。粒子も画面揺れもない。
- 場もファンも `min(100%, 420px)`。ビューポート由来の幅は使わない。
- タップの落ちる場所はすべてボタンで、読み上げラベルを持つ。カードは
  「ランクとスート」で読み上げる — **スート名は翻訳キー**であり、記号の読み上げに
  任せない。**出せない札は「いまは出せません」と読み上げる** — 沈めた見た目と
  同じ事実を、目で見ていない人にも渡す。これは**札についての事実**であって、
  どれを出すべきかという助言では**ない**(§7)。
- 画面上部には自分のマッチ点と、このハンドで取った点が常時出る。これは急かす表示
  ではなく現在の形勢である。**時計は出さない。**経過時間は統計にだけ残る。
- ハンドの清算画面は**タップを待つ**。タイマーで勝手に消えない — このゲームで
  読む価値のある唯一の画面だからである。ムーンのときは 1 行の説明を足す:
  自分の点だけ動かなかった理由を、読み手に推理させない。
- **最後のトリックが畳まれてから清算画面が出るまで、マッチが決まってから結果カードが
  出るまでに、それぞれ約 1 秒置く**
  (`ui/useResultReveal.ts`)。畳まれた場を見る時間であり、その間に押せるものはない。
  Reduced Motion では従来どおり即時に出す。
- 清算は 4 席ぶんの表で見せる。**このハンドの点**と**マッチの点**の 2 列は
  どちらも要る — 前者は何が起きたか、後者はそれが何を意味するかである。
- 効果音は既存の合成音(`services/sound`)のみ: 着手と CPU の各着手とトリックの
  回収で `select`、ハンドが清算されて `match`、マッチに勝って `clear`、負けと
  引き分けで `gameOver`。設定に従う。

## 12. 意図的な差分

市中のハーツ実装・ルール集を調べたうえで、意図的に合わせないものを記録する。

**ブランド原則により合わせないもの**

- **Undo・強さ解放・「もう 1 ハンド」を広告や課金に結び付けない**。難易度は最初から
  全部選べる([ADS_POLICY.md](ADS_POLICY.md))。
- レーティング・ランキング・オンライン対戦はない。記録は端末の中だけにある(§8)。
- **ローカル対人戦も作らない。**席は 4 つだが、座るのは 1 人と 3 つの CPU である。
- デイリーやストリークで毎日呼び戻さない(このゲームにデイリー配札は無い)。
- 統計は勝敗・引き分けと時間だけ。ベスト記録も平均点も持たない(§8)。

**ルールとして採らなかった変種**

- **ムーンの「自席から −26」を作らない。**ムーンは常に他 3 席へ +26 である(§3.2)。
  選択式は、常に有利な方を選ぶだけで決めるところが無い。
- **J♦ ボーナス(−10)を採らない。**点札は ♥ 13 枚と Q♠ の 14 枚だけで、
  **マイナスの札は 1 枚も無い**(`penaltyPointsOf`)。
- **変則パスを作らない。**輪番は 左 → 右 → 対面 → なし の 4 周期に固定で、
  4 枚パス・「ホールド」・配り手が向きを選ぶ流儀は採らない。
- **Q♠ はハートをブレイクしない。**「Q♠ が出ればブレイク」とする流儀は採らない
  (§2.2)。同様に、**Q♠ のリードはブレイク前でも許す。**
- **初トリックの点札は全面禁止。**「初トリックに Q♠ だけは落としてよい」とする
  流儀は採らない。曲がるのは「点札しか持っていない席」の 1 点だけである(§2.2)。
- **Q♠ が出た時点でハンドを打ち切らない。**13 トリックを最後まで打つ — ムーンが
  最後の 1 トリックで壊れることがあるからである。
- **終局は 100 点固定。**50 点戦・500 点戦の変種は作らない。
- **配り手を作らない。**リードは 2♣ の持ち主が取る(§1)。

**設計判断として合わせないもの**

- **Undo を作らない**(§6)。ボード 4 本との最大の違いであり、隠れた情報がある
  ゲームでの意図的な差である。
- **Hint を作らない**(§7)。助けは「ルールが許す札」の表示に限る。
- **手札の手動並べ替えを作らない**(§11.1)。並びはスート順 → ランク順で固定で、
  そこに判断は含まれない。Gin Rummy の「メルドの自動整理」に当たるものも無い。
- **ドラッグ&ドロップを作らない。**二度タップ確定のみ(§2.2)。
- **時計を出さない**(§8)。
- **スコア以外の発明数値を持たない**(§8)。
- **CPU にパスの記憶を持たせない**(§5)。人間の熟練者なら覚えている情報を
  1 つだけ落としてあり、それはプレイヤー有利の側である。
- **最強 CPU を作らない**(§4)。決定化ロールアウトも定石データベースも積まない。
- **棋譜・解析・確率表示を持たない。**対局が終わったら結果だけが残る。完了した
  トリックは CPU の記憶として保存されるが、プレイヤー向けの一覧としては出さない —
  覚えていられる範囲で戦うのがこの遊びだからである。
