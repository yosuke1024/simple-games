# Snake — 正式ゲームルール

このドキュメントが Snake の仕様の正本である。実装
(`apps/simple-games/src/games/snake/`)、テスト、Quick Rules はここに従う。
コードはここへ `§n` で言及する。挙動を変えるときは、同じコミットでこの文書を直す。

ブランド原則([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md))はこの文書より上位にある。
Pause と Restart は無料・無制限で、広告視聴や課金に結び付けない。ストリーク・時間制限・
通知で急かさない。

ゲーム ID は `snake`、i18n キーの接頭辞は `snake`、保存キーの接頭辞は `sn.` である。
**Web 先行公開(ベータ)の新作**(No. 43、registry の `channel: 'web-beta'`。
[WEB_VERSION.md](WEB_VERSION.md)「先行公開(ベータ)」、計画は
[plans/2026-10-17-unblock-snake-loop-bridges-peg.md](plans/2026-10-17-unblock-snake-loop-bridges-peg.md))。
アプリには正式収録していない。Club House には登録しない(registry の `challenge` を持たない)。

「Snake」は 1970 年代のアーケードから続く、伸びる線を操るゲーム形式の一般名称であり、
特定の製品名ではない。特定の製品(携帯電話の内蔵ゲームなど)の名前・画面・図柄・
効果音は複製しない。盤面・規則の数値・見た目はすべてこの文書で自前に決めたものである。

**実装状況(2026-10-17)**: ゲームロジック(`game/`。§1〜§9 と、§11 の規則による検証)、
保存(`storage/`)・状態管理(`state/`)・画面(`ui/`)を実装し、§16 の範囲を検証した。
文言(`i18n/`)は 14 言語すべてを書いた: `en` が原文、`ja` は AI が書いて作者はまだ
読んでいない、残る 12 言語は `machine`(AI が書き、ネイティブは誰も読んでいない)(§14)。
独立レビュー 2 本の指摘(盤に重ねたカードが盤を隠す・横向きの電話の配置・フォーカスの
枠のコントラストほか)を同じ日に直した(§13、§16)。

## 1. 盤面

- **14×14 = 196 マス**(`BOARD_SIZE`、`game/types.ts`)。マスは左上から行優先に
  0〜195 の番号で持つ(`cellAt(row, col) = row × 14 + col`)。
- **外周が壁**。盤の端はつながっていない — 右端から出て左端に現れることはない
  (行の最後のマスと次の行の最初のマスは隣ではない)。
- 障害物・パワーアップ・特別な食べ物・課金アイテムは**作らない**。盤の上にあるのは
  ヘビと食べ物 1 つだけ。
- 盤面に文字は描かない(翻訳の要る文字も数字も置かない)。スコアは盤の外に出す(§13)。

なぜ 14×14 か:

- **360 幅に収まる**: 左右 16px の余白を除いた 328px で 1 マス約 23px。盤面の下に
  方向ボタン(§13)を置き、高さが足りないときは盤のほうを縮める(§13「寸法」)。
  360×640 では盤と方向ボタンがスクロールなしに収まることを実測した(Web 版の下端の
  広告の予約 116px を引いて盤は 270px、1 マス約 19px。§13「寸法」)。タブレット・PC では
  盤を大きく描く(マスの数は変えない)。
- **偶数 × 偶数**: すべてのマスを 1 回ずつ通る閉路(ハミルトン閉路)を持つ。これが
  「どの seed でも満杯クリアに到達できる」ことの根拠になる(§4)。奇数 × 奇数の盤には
  そのような閉路が存在しない。
- **満杯クリアの検証が現実的**: 満杯まで食べ物 193 個。§4 の閉路をなぞる自動操縦で
  約 9,500 移動(中央値、§17)。テストはこれを毎回 200 seed ぶん実際に走らせる(§16)。

## 2. 初期状態

- ヘビは**長さ 3**(`INITIAL_LENGTH`)。上から 7 行目(行 6 — 中央 2 行のうち上側)の
  列 2〜4 に横たわり、頭は列 4、**右向き**(`INITIAL_DIRECTION`)。体は頭から順に
  `[cellAt(6,4), cellAt(6,3), cellAt(6,2)]`(`INITIAL_BODY`)。
- 食べ物は盤上に常に **1 つ**。最初の 1 個はヘビのいないマスに seed から決まる(§8)。
- 状態は **`ready`**: 盤面が**全部**見えていて(盤の上には何も重ねない、§13)、何も
  動かない。最初の入力(Start か方向、§5・§6)まで tick は何もしない。開いただけで
  ランを失うことはない。

## 3. 1 tick の解決

ヘビは tick ごとに**必ず 1 マス進む**(止まらない、斜めには進まない)。tick の間隔は
速度で決まり、ランの間は一定である(§7)。1 tick は次の順で解決する
(`game/session.ts` の `tick`、移動そのものは `game/engine.ts` の `moveSnake`)。

1. **向きを決める。** 入力キュー(§5)の先頭を 1 つ取り出して進行方向にする。キューが
   空なら直前の向きのまま。
2. **新しい頭の位置を求める。** 今の頭から進行方向へ 1 マス。盤の外なら**壁への衝突**。
3. **食べるかどうか。** 新しい頭が食べ物のマスなら「食べる」。食べるときは**尾が残る**
   (体が 1 マス伸びる)。食べないときは**尾が 1 マス抜ける**。
4. **衝突判定は尾が抜けたあとの体に対して行う。** 食べない tick では、**今の尾のマスへ
   頭が入るのは合法**である(その tick に尾がそのマスを空けるため — 長さ 4 のヘビは
   2×2 の輪を永遠に回れる)。食べる tick では尾も含めた体全体が残る(ただし食べ物は
   空きマスにしか出ないので、食べる tick に頭が体に入ることは起こらない)。残った体に
   頭が入れば**自分への衝突**。
5. **確定する。** 頭を加え、(食べなければ)尾を外す。食べたらスコア +1。体が 196 マス
   すべてを占めたら**クリア**(§4)。そうでなければ空きマスに次の食べ物を出す(§8)。

- **衝突した tick にヘビは動かない。** 体はその直前の位置に残り、`direction` は
  ぶつかろうとした向きになる(表示で頭がぶつかった先を向くため)。衝突は移動に
  数えない(`ticks` は増えない)。
- 体は「頭が通った跡」そのものである: 体の i 番目のマスは、i 回前の移動で頭が
  いたマス(最初の移動より前は初期の体)。保存の検証はこの性質を使う(§11)。
- 正反対への方向転換は入力の段階で捨てるので(§5)、頭が首のマスへ戻ることは起こらない。
  キューに正反対が紛れ込んだ不正な状態を手で作っても、`tick` はそれを無視して直進する
  (防御。テストで固定)。

## 4. 終了条件

- **ゲームオーバー**: 壁か自分に衝突したとき(§3)。理由は `crash`(`'wall'` / `'self'`)に
  残る。ライフ・残機・コンティニューは無い。
- **クリア**: 体が盤面全体を占めたとき(長さ 196、スコア 193 = `MAX_SCORE`)。最後の
  食べ物を食べた tick で終わる — 次の食べ物を置くマスが無い。`food` は -1 になる。
- 終了は `status` の遷移(`'running'` → `'over'` / `'cleared'`)として一度だけ起きる。
  終わったランは方向・Start・Pause・Resume・tick のどれも受け付けない(同じ状態を返す)。

### 満杯クリアはどの seed でも到達できる

14×14 には、すべてのマスを 1 回ずつ通って元に戻る閉路がある。たとえば
「行 0 を左から右へ → 行 1〜13 を列 1〜13 の範囲で蛇行(奇数行は右から左、偶数行は
左から右)→ 列 0 を下から上へ」(`game/test-helpers.ts` の `hamiltonianCycle`)。
初期のヘビ(行 6 の列 2→3→4)はこの閉路の上に、尾から頭への順で乗っている。

閉路をなぞり続けるヘビは、体がつねに閉路上の連続した区間になる。次に入るマスは閉路上で
頭の前にあり、そこは空きマスか(食べない tick には)いま抜ける尾なので、**壁にも自分にも
決して当たらない**。空きマスはすべて閉路上で頭と尾のあいだにあるので、1 周
(196 移動)以内に必ず食べ物に着く。よって**食べ物がどこに出ても**、193 個すべてを
食べて盤を埋められる。運で詰む盤面は存在しない(上限は 193 × 196 = 37,828 移動)。

これは「到達できる」ことの保証であって、遊び方の指示ではない。閉路をなぞるのは時間が
かかる(§17)ので、人はふつう近道をして、その代わりに体で自分を閉じ込める危険を負う。
アプリはこの自動操縦を持たない(テストだけが使う。§9)。

## 5. 方向入力

- 方向は上下左右の 4 つ。入力経路はスワイプ・画面上の方向ボタン・矢印キー / WASD(§13)。
  どの経路も同じ関数(`turn`)に入る。
- **方向入力は次の tick で適用する。** 押した瞬間にはヘビは動かず、頭の向きも変わらない
  (頭の向きはいつも「最後に動いた向き」)。一時停止中に選んだ向き(下記)だけは、頭の
  向きとは別の印で盤に出す(§13)。

### 入力キュー(走っている間)

- 走っている間の入力は**キュー**に積む。上限は **3**(`INPUT_QUEUE_LIMIT`)。
- 積むとき、**直前に積んだ方向**(キューが空なら今の進行方向)と比べる:
  - 正反対 → 捨てる(**180 度転換の禁止**)
  - 同じ → 捨てる(同じキーの連打でキューの枠を使わない)
  - キューが満杯 → 捨てる
  - それ以外 → 末尾に積む
- tick ごとに先頭を 1 つ使う(§3 手順 1)。
- 各入力は「その直前の入力」に対して検証済みなので、**1 tick の間に何度押しても、
  tick をまたいでも、連続する 2 回の移動が正反対になることはない**。
  - 例: 右へ進行中に「上 → 左」をすばやく押す → 1 tick 目に上、2 tick 目に左
    (U ターン)。2 つ目の入力を「今の進行方向(右)」とだけ比べて上書きする実装では、
    左が上を消して首に突っ込む。この形の不具合をキューが構造的に防ぐ。
  - 例: 「上 → 下」→ 下は上の正反対なので捨てる。1 tick 目に上へ曲がるだけ。
- 上限が 3 である理由: 2 つで U ターン、3 つで S 字(上 → 右 → 上)まで先回りできる。
  4 つ目は 3 tick 以上先(Fast で 300ms、Slow で 660ms)への入力で、もう画面の盤面を
  見て押したものではない。

### 走っていないときの入力

- **`ready`**: 正反対(初期は左)以外の方向を押すと**ランが始まり**、最初の tick でその
  方向へ進む(今の向きと同じなら直進)。Start を押さずに始められる(手数を減らす)。
  正反対は何もせず、盤は待ち続ける。
- **`paused`**: **再開しない**。押した方向は「再開後の最初の向き」の選び直しになる —
  最後の入力が勝つ(キューに 2 つ以上は積まない)、正反対は捨てる、今の向きと同じなら
  選び直しを取り消す。止まった盤面を見て逃げ道を決めてから Resume できるようにする
  ためで、壁の 1 マス手前で止まったランでも、再開した瞬間の反射は求められない(§6)。
  - **選んだ向きは隠さない。** 盤の上に印で示し(§13「見た目」)、選んだとき・取り消した
    ときに読み上げる(§13「スクリーンリーダー」)。復帰した直後に迷い込んだスワイプや
    キーが向きを変えても、それは Resume を押す前に盤に見えている。
  - **選んだ向きは保存に残る**(`sn.saveGame` の `next`、§11)。止まっている間にアプリが
    バックグラウンドへ行き、OS がそのまま閉じても、戻ったランは同じ向きを選んだまま
    `paused` で始まり、閉じられなかったランと 1 tick ずつ同じに動く(テストで固定、§16)。
    ビュー・保存が読むのは `pendingHeading`(`game/session.ts`)で、`paused` のときの
    キューの先頭だけを返す(走っている間のキューは「選んだ向き」ではない)。
- **`over` / `cleared`**: 何もしない。

## 6. ランの状態と Start / Pause / Resume / Restart

状態は `ready` → `running` ⇄ `paused` → `over` | `cleared`(`RunStatus`)。

- **Start**(`start`): `ready` → `running`。方向入力でも始まる(§5)。
- **Pause**(`pause`): `running` → `paused`。**入力キューを空にする** — 止める前に
  押した先回りの入力を、止めたあとまで持ち越さない(再開直後の tick が、もう覚えて
  いない入力で曲がることを防ぐ)。方向で始めた直後、最初の移動より前に止まった場合も
  同じで、その入力は捨てられ、盤は初期の右向き・選んだ向きなしで止まる(盤の表示も
  そのとおりになる、§13)。止まってから押した方向は §5 の「選び直し」になる。
  回数・長さの制限は無く、確認も無い。止めたランはその時点で保存する(§11)。
- **Resume**(`resume`): `paused` → `running`。再開は**プレイヤーの操作だけ**で起きる。
  最初の tick は再開から 1 間隔後。
- **Restart**: ヘッダの ↻ から `RestartDialog` の 3 ボタン形(「同じ盤面で再挑戦」・
  「新しいゲーム」・「キャンセル」)。結果カードも同じ 2 つの続け方を同じラベル・同じ関数で
  出す(docs/ARCHITECTURE.md「ヘッダの ↻ は結果カードと同じ 2 択」— Endless には
  いつでも別の seed があるので、`newBoard` を渡す側に入る)。
  - 「同じ盤面で再挑戦」(共有の `tryAgain`、`retryRun`)は、**同じ seed・同じ速度**で
    `ready` の盤を最初から始める — 盤・初期のヘビ・最初の食べ物が同じで、同じ動きをすれば
    同じ食べ物が続く(§8)。ボタンの言葉どおり「同じ盤面」である。
  - 「新しいゲーム」(共有の `newGame`、`startNewRun`)は、ホームの「新しいゲーム」と
    同じ関数で、**新しい seed** の `ready` の盤を **`sn.prefs` の速度**で出す(§7。
    中断から戻したランの速度が prefs と違えば、新しい盤は prefs の速度になる — ホームと
    同じ扱い)。
  - 経緯: 最初の版は「もう一度 = 新しい seed」と書いていた。画面の実装(2026-10-17)で、
    共有ダイアログの第一ボタンの言葉「同じ盤面で再挑戦」に合わせて同じ seed に変え、
    新しい seed はホームからだけにした。レビューで、共有の `RestartDialog` には第二の
    選択肢(`newBoard`)があり、ARCHITECTURE は「別の盤面を持つモードはそれを出す」と
    していることを指摘され、両方を出す形にした(同日)。どちらを第一にするか・両方を出すか
    は**製品オーナーの確認待ち**である(2048 は結果カードの第一が新しいゲーム)。
  - ダイアログを開いた時点で走っているランは `paused` になる(§13)。**「キャンセル」で
    閉じても `paused` のまま**で、再開は Resume(または Space)だけ — ダイアログを
    閉じたことで勝手に走り出さない。
  - 「同じ盤面で再挑戦」と「新しいゲーム」は、捨てるランのスコアで `bestScore` を更新し
    (§10)、**同じ時点で `sn.saveGame` を消す**(§11)。新しい `ready` の盤は保存しない
    ので、消さなければ捨てたランがあとで「続きから」やショートカットで戻ってくる。
    ダイアログそのものが確認なので、↻ からの「新しいゲーム」はホームの `ConfirmDialog` を
    重ねない。
- **ホームでの新しいラン**: 中断中のランがあるとき、ホームは「続きから」(スコアと速度を
  添える)と「新しいゲーム」を出す。「新しいゲーム」は `ConfirmDialog` で確かめてから
  (2048 と同じ形)、Restart と同じ記録の更新・スロットの削除をして、**新しい seed** の
  `ready` の盤を `sn.prefs` の速度で出す。中断中のランが無ければ、確認なしで新しい盤に
  なる。
- **バックグラウンド**(`visibilitychange` の hidden、native の pause)では、走っていれば
  必ず `paused` にして保存する。**復帰しても再開しない** — 再開は Resume のタップ
  (または Space キー)だけ。ゲーム画面から離れたとき(ホームへ・Back)も同じく `paused`
  にして保存する。
- **ウィンドウがフォーカスを失ったとき**(`window` の `blur`。PC で隣の別のウィンドウへ
  移った・広告の枠をタップした等、画面は見えたまま)も、**走っていれば** `paused` にして
  保存する。操作する人がもう盤を見ていないのはバックグラウンドと同じだからで、フォーカスが
  戻っても再開しない。止まっているランには何もしない(書き込みも無い)。既存のアーケード
  3 本は `blur` で止めないので、ここは Snake だけの差分である(§15)。
- **保存から戻したランは常に `paused`** で始まる(§11)。
- `ready` / `paused` / 終局の間、`tick` は**何も変えない**(同じ状態をそのまま返し、
  `event: 'none'`)。遅れて着いたタイマーが止まったヘビを動かすことはない。
- 各関数は何も変えないとき**同じオブジェクト**を返す(無視された入力・2 回目の Pause・
  止まっている間の tick)。画面は再描画の理由を持たない(§13)。

## 7. 速度とスコア

| 速度         | tick 間隔 | 毎秒のマス数 | 盤を横切る時間 |
| ------------ | --------- | ------------ | -------------- |
| Slow         | 220 ms    | 約 4.5       | 約 3.1 秒      |
| Normal(既定) | 150 ms    | 約 6.7       | 約 2.1 秒      |
| Fast         | 100 ms    | 10           | 1.4 秒         |

(`TICK_MS`。「盤を横切る時間」は 14 マスを進む時間。)

- **速度はランの開始時に決まり、ランの間は変わらない**(長さや時間で加速しない)。
  盤・食べ物・規則は 3 速度で同じで、違うのは tick の間隔だけ — **難易度は速度だけが
  決める**。Fast が Slow より難しいのは、1 マスごとの判断に使える時間が 100ms 対 220ms で
  あるからで、それ以外の差は作らない。
- 選んだ速度は `sn.prefs` に残り、**既定は Normal**。ホームで選べるが、**選ばなくても
  始められる**(最初から選択を強制しない)。中断中のランは自分の速度を持ち(§11)、
  あとから prefs を変えても変わらない。
- **スコア = 食べた数**(1 個 1 点、最大 193)。長さ = 3 + スコア。時間・速度・移動数からは
  作らない。記録は速度ごとに分ける(§10)— Fast の 50 点と Slow の 50 点は同じ重さでは
  ないため。

## 8. 食べ物の生成と seed

- **seed** は `snake-<token>`。token は起動時刻(base36)+ 乱数で、ランごとに新しい
  (`newSeedToken` / `snakeSeed`、`game/session.ts`。2048 と同じ形)。時計と乱数は
  `state/` が読んで渡す(`newSeedToken(Date.now(), Math.random)`)。`game/` の中には
  時計も `Math.random` も無く、`createSession` は seed を必ず受け取る — 同じ引数から
  いつも同じランになる。
- **n 番目の食べ物**(n = 0 が盤上の最初の 1 個)は、`createRng(`${seed}:food:${n}`)` の
  最初の 1 値 r から決める(`game/food.ts` の `drawFood`): ヘビのいないマスを行優先に
  並べ、その `floor(r × 空きマス数)` 番目。**空きマスに一様**で、ヘビの上には決して
  出ない。空きマスが 0 なら(満杯)-1 を返す。
- **PRNG の状態は (seed, n) の組だけで完全に決まる。** n = それまでに出した食べ物の数 =
  スコア + 1(クリア時はスコア)。だから保存は seed とスコアを持てば乱数の状態も
  持ったことになり(§11)、**同じ状態からは同じ食べ物が出る**(保存 → 復元 → 続きを
  遊んだランが、止めなかったランと 1 tick ずつ一致することをテストで確かめる。§16)。
- 乱数は xmur3 + mulberry32(`game/rng.ts`。他ゲームと同じものの写しで、共有しない)。
- **仕事量の上限は構造で決まる。** 1 回の抽選はヘビの印付け(長さぶん、最大 195)+
  盤面 1 走査(最大 196 マス)で、**試行の繰り返し(棄却サンプリング)を持たない** —
  上限を超えて回り続ける経路そのものが無い(`FOOD_DRAW_WORK_LIMIT` = 391 ステップ。
  `drawFoodCounted` が実際の数を返し、テストが全長さで上限以内を確かめる)。探索・
  ソルバー・生成のやり直しはこのゲームに存在しないので、「上限に達したら見つからな
  かったと言う」場面も、同梱盤面へのフォールバックも無い。
- tick 1 回の仕事量: 衝突判定(長さ − 1 マス以下)+ 体の写し(長さぶん)+ 食べた tick
  だけ抽選 1 回。いずれもヘビの長さ(≤ 196)に比例する。
- **golden**(`game/compatibility.test.ts`)が seed `snake-golden` の最初の食べ物、固定の
  入力列の結果(食べる・尾の追いかけ・壁)、閉路の自動操縦での最初の 12 個の食べ物と
  自分への衝突、満杯までの移動数(9,132)を固定する。乱数・抽選の順序・盤・初期の
  ヘビ・衝突の順序を変える改修は、事故ではなく決定でなければならない。これらは
  保存の検証(§11)にも効く — 変えると、変える前に保存した中断中のランの一部が検証を
  通らなくなるので、変えるときは `sn.saveGame` の版を上げ、移行するか読み捨てるかを決める。

## 9. 助けの形(Undo / Hint を作らない)

- **Undo は作らない。** リアルタイムの反射が遊びの中身で、一手戻せばその中身が空になる。
- **Hint は作らない。** 盤面はすべて見えていて、隠れた情報が無い。次の一手を教えるのは
  「アプリが代わりに遊ぶ」ことになる。§4 の自動操縦をアプリに入れないのも同じ理由。
- 代わりの助けは**無料・無制限の Pause と Restart**(§6)。Pause はいつでも、何度でも、
  確認なしに押せる。止まっている間に次の向きを選べる(§5)。
- コンティニュー・復活・広告視聴での続行は作らない。終わったら次のランが無料で始まる。

## 10. 統計

- **速度別に** 4 つ: `played`(始めたラン数)/ `bestScore` / `cleared`(満杯クリアの回数)/
  `totalPlaySeconds`。ストリークは持たない(どの日に遊んだかを知る理由が無い)。
- `played` はランが始まったとき(`ready` → `running` の 1 回)に数える。中断から戻した
  ランは数え直さない。
- `bestScore` は、ランが終わったとき(ゲームオーバー・クリア)と、途中のランを捨てたとき
  (Restart、または中断中のランを置き換えて新しいランを始めたとき)に、そのランの
  スコアで更新する。中断して保存してあるランのスコアは、そのランが終わるか捨てられる
  まで記録に入れない。捨てるときは、同じ時点で `sn.saveGame` を消す(§6・§11)。
- `totalPlaySeconds` は**走っている間だけ**数える(`paused`・`ready`・結果画面は数えない)。
  時計はタイマーではなく、走り始めた時刻(`performance.now()`)とそれまでに走った秒数の
  2 つ(§13「描画とループ」)。計上は逐次(bookedRef 方式): Pause・バックグラウンド・
  フォーカスを失ったとき・退出・アンマウント・終局・ランを捨てたときの各時点で、まだ計上
  していない秒だけを足す。ランの `elapsedSeconds` は整数秒で持つ(保存は端数を切り捨てて
  書く、§11)が、**時計は端数を持ち続ける**: 同じ起動の中でホームへ出て「続きから」で
  戻っても、時計は保存の切り捨てた値で置き直さない(0.6 秒 + 0.6 秒は 1 秒になる。
  テストで固定)。切り捨てで失うのは、アプリを閉じて開き直したときの 1 秒未満だけである。
- 結果カードはスコアと、その速度の自己ベスト(記録との差を符号付きで添える
  `BestDelta`。記録がまだ 0 のうちは添えない)。比べる相手は自分の記録だけ。
- オンラインランキングは無い。

## 11. 中断と再開(保存)

**途中保存する。** 盤面はマス目の上の離散的な状態で、保存した瞬間とまったく同じ局面に
戻せる。アーケードの 3 本(Bunny Hop / Brick Breaker / Sky Fighter)が保存を作らない理由
(「復元した瞬間に球が降ってくる」— [BRICK_BREAKER_RULES.md](BRICK_BREAKER_RULES.md) §10)は、
**戻したランを必ず `paused` で始める**ことでここには当てはまらない: 再開するまで何も
動かず、再開する前に向きも選べる(§5)。

- 保存キーは **4 つ**: `sn.saveGame` / `sn.stats` / `sn.flags` / `sn.prefs`(この順で
  `storage/keys.ts` に宣言する)。他ゲームのキーには触れない。
- **書くのは** Pause・バックグラウンド・走っている間にフォーカスを失ったとき(§6)・退出
  (ホーム・Back)・アンマウントのとき。**毎 tick は書かない**(`sn.saveGame` も
  `sn.stats` も。`sn.stats` を書くのはランが動き出したとき・上の各時点・終局・ランを
  捨てたときだけ)。一度も始めていない(`ready` のままの)盤面は保存しない
  (`toSnapshot` が null を返す)。
- **スロットを消すのは**次の 2 つのとき。`ready` の盤面は保存しないので、新しい盤が
  古い記録を上書きすることは無い(2048 とはここが違う)— 消すことを明示しなければ、
  捨てたランが戻ってくる。
  - 終局(`over` / `cleared`)したとき。
  - 中断中のランを捨てたとき: Restart の「同じ盤面で再挑戦」「新しいゲーム」と、ホームの
    「新しいゲーム」(§6)。
    `bestScore` の更新(§10)と同じ時点で消す。そのあと何も動かさずに画面を離れても、
    「続きから」もショートカットからの再開も出ない(状態管理のテストで固定する、§16)。
- 中断スロットは 1 つなので、ホーム画面ショートカットは中断中のランがあれば盤面へ
  直接入る(`paused` のまま)。無ければゲームのホームへ。
- 保存の失敗はゲームを止めない。バリデータは例外を投げない(`null`・配列・数など、
  何を渡しても null を返す)。

### `sn.saveGame`(中断中のラン、v1)

| フィールド       | 型                                          | 意味                                                                 |
| ---------------- | ------------------------------------------- | -------------------------------------------------------------------- |
| `schemaVersion`  | `1`                                         |                                                                      |
| `seed`           | string                                      | ランの seed(§8)                                                      |
| `speed`          | `'slow' \| 'normal' \| 'fast'`              | ランの速度(§7)                                                       |
| `body`           | string                                      | 体。頭から順に 1 マス 2 文字の base36(`00`〜`5f`)                    |
| `food`           | int                                         | 食べ物のマス                                                         |
| `score`          | int                                         | 食べた数                                                             |
| `ticks`          | int                                         | 移動した回数                                                         |
| `elapsedSeconds` | int                                         | 走っていた秒数(統計用。整数秒、端数は切り捨てて書く)                 |
| `next`           | `'up' \| 'down' \| 'left' \| 'right'`(任意) | 一時停止中に選んだ、再開後の最初の向き(§5)。選んでいなければ書かない |
| `savedAt`        | int                                         | 保存した時刻(ms)                                                     |

初期のヘビは `body: '2g2f2e'`。`score`・`ticks`・`elapsedSeconds` は 0 以上 10 億
(`MAX_RECORD_COUNT`)以下の整数 — 10 億移動は Fast で休まず 3 年で、プレイでは届かない。

**保存しないもの**と、その理由:

- 向き — 首から頭への向きで決まる(§3)。
- 食べ物を出した回数 n — スコア + 1 で決まる(§8)。
- 走っている間の入力キュー(先回りの入力)— Pause がキューを空にするのと同じ扱いで
  捨てる。走っているランを渡されても `toSnapshot` は `next` を書かず、戻したランは
  `paused` で先回りの入力を持たない。一時停止中に選んだ向きはキューの残りではなく、
  盤に見えている選択なので `next` に残す(§5)。
- 状態 — 戻したランは常に `paused`。
- Undo 履歴 — そもそも無い(§9)。

**検証は fail-closed。** 次のどれかに当たるレコードは読み捨て、プレイヤーは**ゲームの
ホームに着く**(黙って新しいランを始めない)。型の検査は `storage/` の `SchemaDef`、
規則の検査は `game/serialize.ts` の `restoreSession` が行う。

- オブジェクトでない(`null` を含む)、JSON が壊れている、`schemaVersion` が 1 でない、
  型が違う、整数でない・負の数・10 億を超える
- `seed` が空か 200 文字を超える。`speed` が 3 つのどれでもない
- `body` が符号として読めない(長さが奇数・`[0-9a-z]` 以外の文字・大文字・196 以上の値・
  空・392 文字超)
- `body` が盤上の道になっていない: 同じマスが 2 回、隣り合う 2 マスが上下左右に
  1 マス離れていない(行の折り返しも隣ではない)
- `body` の長さが 3 未満、または **196(満杯 = 終局済み)**
- 長さ ≠ 3 + `score`(1 点につき 1 マス、ほかに伸びる理由は無い)
- `food` が盤の外か、ヘビの上にある
- `score` > `ticks`(1 点ごとに 1 移動は要る)
- **食べていない(`score` = 0)のに、食べ物が最初の抽選結果でない**: 最初の食べ物は
  初期の体に対する抽選 `drawFood(seed, 0, 初期の体)` で決まり、食べるまで動かない(§8)。
- **体が示す移動の履歴がありえない**(`game/history.ts`)。体は頭の通った跡なので(§3)、
  記録は「初期の頭から `ticks` 回動き、最後の(長さ)回ぶんの頭の位置が体になった」と
  言っている。
  - **履歴が全部体に残っている**(`ticks` ≤ 長さ): 初期の盤からその seed でその道を
    実際に遊び直し(`replayMatches`。tick はゲームと同じ関数)、体・スコア・食べ物が
    記録と一致しなければ捨てる。エンジンは決定的で、食べ物を踏めば必ず食べるので、
    その道から生まれるランは 1 つしかない。180 度の転換(最初の移動で左へ、など)・壁・
    自分への衝突・食べ物の取り違えは、すべてここで見つかる。
  - **履歴の前のほうが失われている**(`ticks` > 長さ): 尾のマスまでの
    `ticks − (長さ − 1)` 回の移動は、初期の頭から右向きで始まり、盤の外へ出ず、
    **正反対へ曲がらない**歩みでなければならず、尾から次のマスへの 1 歩も、尾に着いた
    ときの向きの正反対であってはならない(`canReachTail`)。食べていなければ、その歩みは
    食べ物のマスを踏まない(踏めば食べている)。ありえる (マス, 向き) の組 784 個を
    1 移動ずつ層にして調べ、ある層が 2 つ前の層と同じになったら(以後は 2 層の繰り返し。
    どの「避けるマス」でも 19 層以内で、上限 `WALK_LAYER_LIMIT` = 64 層には届かない、
    §16)、それより先の移動数は偶奇で読む。上限に達したら記録を捨てる(fail-closed)。
- `next` がある: 4 方向のどれでもない、今の向きと同じ、今の向きの正反対(`turn` は
  これらを残さない、§5)

読み込めるのは、検証を通ったうえで `paused` に戻したランだけである。

**どこまで確かめられるか。** プレイから到達できる局面は必ず検証を通る(誤って捨てない。
§16 の全数と標本)。そのうえで:

- **正確に判定する**(到達できない記録はすべて捨てる)のは、食べていない記録
  (`score` = 0)と、履歴が全部体に残っている記録(`ticks` ≤ 長さ)。食べていなければ
  ヘビはずっと長さ 3 で、長さ 3 のヘビにとって自分の体は頭の後ろの 2 マスだけなので、
  「正反対へ曲がらない・盤を出ない・食べ物を踏まない」歩みがそのまま規則のすべてになる。
- **必要条件だけを確かめる**のは、食べたことがあり(`score` ≥ 1)、履歴の前のほうが
  失われた記録 — 長く遊んだランの保存はほとんどこれである。次は確かめない:
  - 食べた食べ物と今の食べ物が、その seed のその時点の抽選結果だったか — 抽選が
    依存する当時の体が残っていない(2048 が盤面を「2 の累乗だけ」で検証し、各タイルの
    抽選までは追わないのと同じ範囲)。
  - 失われた部分で、伸びたあとの体に頭が入らなかったか、まだ食べていない食べ物を
    踏まなかったか。

  最初の 8 移動を全数で調べた計測(§17)では、この種の記録で受け入れたが到達できない
  ものはほぼすべて「食べ物の位置が seed と合わない」もので、食べ物をどこに置いても
  作れない形は 7 移動で 2 個、8 移動で 8 個だった。

- **`ticks` と `elapsedSeconds` の整合は確かめない。** tick を進めるタイマーと統計の
  時計は別物で、タイマーの遅れ・計上の端数・端末の時計の扱いで比がぶれる。下限を
  課すと、そのぶれが中断中のランを失わせる。ありえない組を受け入れても、統計に入るのは
  そのラン 1 つぶんの秒数(上限 10 億秒)にとどまる。

検証はエンジンと抽選(§3・§8)をそのまま使うので、それらを変えると、変える前に保存した
ランの一部が検証を通らなくなる(§8 の golden がその変更を事故にさせない)。

### `sn.stats`(v1)

`{ schemaVersion: 1, slow, normal, fast }`。各速度は `{ played, bestScore, cleared,
totalPlaySeconds }`(すべて 0 以上の整数、`bestScore` ≤ 193、`cleared` > 0 なら
`bestScore` = 193)。どれかが合わなければレコードごと既定値(すべて 0)に倒す(共有の
`loadRecord` の扱い)。

`cleared` ≤ `played` は**課さない**(この節の前の版は課していた)。中断中のランは始まった
ときに `played` に数えられているが、そのあと統計のレコードだけが失われ(読めずに既定値に
倒れた等)、保存したランが残ることはありうる。そのランを最後まで埋めれば `played` 0・
`cleared` 1 の記録ができ、これは実際のプレイの結果なので、捨ててはならない。

### `sn.flags`(v1)

`{ schemaVersion: 1, tutorialCompleted }`。初回の Quick Rules を見たか(§12)。

### `sn.prefs`(v1)

`{ schemaVersion: 1, speed }`。最後に選んだ速度だけ。既定(と読めなかったとき)は
`'normal'`。

ベータ中はスキーマを変えうる(告知は `WebBetaNotice`。[WEB_VERSION.md](WEB_VERSION.md)
「先行公開(ベータ)」)。正式収録でスキーマを凍結し、以後は移行だけで変える。

## 12. Quick Rules(アプリ内チュートリアル)

3 ステップ・図中心・各 1 文(初回はゲームを開いたときに表示し、以後はホームから):

1. スワイプ(または方向ボタン・矢印キー)で曲がる — ヘビは 1 マスずつ進み続ける。
2. 食べ物を取ると 1 マス伸びて 1 点。
3. 壁か自分の体に当たると終わり — 盤を埋めればクリア。

- 図は盤面と同じ部品(`SnakeBoard` に盤の一部の窓を渡す)で描く: 1 は上へ曲がる矢印と
  その先の食べ物、2 は頭の 1 マス先の食べ物、3 は右の壁にぶつかって × の付いた頭。
- 初回の Quick Rules を終えると(「さっそく遊ぶ」)、新しい seed の `ready` の盤が開き、
  Start のタップか方向 1 つで動き出す(既存ゲームの初回フローと同じ)。Back で抜けても
  「見た」扱いにする。
  - ただし**中断中のランが残っているとき**(`sn.flags` だけが失われた・読めなかった等で
    初回扱いになったが `sn.saveGame` は無事)は、新しい盤ではなく**そのランに `paused` で
    戻る**。新しい盤を出すと、ホームが「新しいゲーム」の前に確かめることをせずにランを
    捨ててしまう(§6・§11 の「黙って置き換えない」)。2048 の初回フローはここで新しい盤を
    出すが、それには合わせない。
- Learn More は出さない(ガイドが無い — `ui/landing.ts` の `PUBLISHED_GAME_IDS` に入れない)。

## 13. 画面・操作・アクセシビリティ

### 画面の構成

- **上段(ヘッダ)**: ← ホームへ / スコア(その下の 1 行に、その速度の自己ベストとランの
  速度 — 記録がまだ 0 のうちは速度だけ。`paused` の間はその行が「❚❚ 一時停止中」になる)/
  ↻(Restart、§6)。↻ は盤が一度も動いていない `ready` の間は押せない(捨てるものが無い)。
  スコアの下の行はどの状態・どの言語でも 1 行で、止めても上段の高さは変わらない(盤が
  動かない)。
- **中段**: 盤面。**盤の上には何も重ねない**(下記「盤には何も重ねない」)。
- **下段**: 方向ボタンの十字。十字の中央が Start / Pause / Resume の切り替え(下記)。
- PC と横長のタブレット(幅 900px 以上かつ横長)、および**横向きの電話**(横長で高さ
  540px 以下)では十字を盤の右に置き、盤は高さいっぱい(上限 760px)まで大きくする。
  幅 600px 以上ではボタンを一回り大きくする(横向きの電話では大きくしない — 高さが
  すべて盤のものだから)。

### 操作

- **スワイプ**: 盤面の上で。`pointerdown` で開始点を `pointerId` と一緒に記録し、測るのは
  その指の移動だけ(新しい押下が来たら記録はそちらに移る — 2048 と同じ、issue #187。離す
  イベントが届かなかった指の記録が盤を塞がないため)。**指を離すのを待たない**: 同じ指の
  `pointermove` で、開始点からの移動量の大きい方の軸が **24px に達した時点で**その向きを
  1 回入力する(縦横は移動量の大きい方 — 判定は 2048 §3 と同じ)。入力したらその位置を
  新しい開始点にするので、指を離さずに曲がり続ければ(L 字・U 字)曲がるたびに 1 回ずつ
  入る。同じ向き・正反対は §5 のキューの規則がそのまま捨てる。マウスでは左ボタンだけ。
  - 2048 の「離したときに入る」を写さない理由: 2048 はターン制なので離すまで待っても
    失うものが無いが、ここでは指を離すまでの残りの動き(ふつう 80〜150ms)だけ入力が
    遅れ、Fast の 1 tick(100ms)では 1 tick 遅れて壁に当たる。リアルタイムのゲームでは、
    入力は判定に達した瞬間に入れる。
  - `pointerup` と `pointercancel` で記録を捨てる。判定に達する前の `pointercancel` では
    何も入らない(すでに入れた向きは取り消さない — ボタンで押した入力と同じく、もう
    キューにある)。盤面は `touch-action: none` で、`setPointerCapture` で盤の外へ出た
    指(マウス)も追う。`pointerContractWiring` と [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md)
    §5.12 に従い、指とスクロールの取り合いは実機で確かめる(未実施、§16)。
  - スワイプを聞くのは盤の箱全体(`ui/components/SnakeStage.tsx`)。その中にも上にも
    クリックを聞く要素は無い(Start / Resume は十字の中央)。
- **方向ボタン**: 盤面の下に ↑ ← → ↓ の 4 つ(十字形)。各 56×50px(幅 600px 以上で
  64×56px)。タップだけで遊べる経路であり、名前つきのボタンなので支援技術からも押せる。
  - **押した瞬間(`pointerdown`)に入力する。** 指を離すまで(click まで)待つとスワイプと
    同じ理由で 1 tick 遅れる。押下が残す click は**使い切る** — ただし `event.detail > 0` で、
    同じボタンの押下から 1 秒以内のものだけ(docs/ARCHITECTURE.md「押下の記録は誰のものか」)。
    キーボードの Enter / Space や支援技術の起動は押下を伴わない click なので、そのまま入力に
    なる。`pointercancel` で印を捨てる。
  - マウスの押下ではフォーカスを取らない(`mousedown` の既定動作を止める)。PC で
    クリックしたボタンにフォーカスが残ると、Space(Pause)をそのボタンが受けてしまうため。
  - キーボードのフォーカスの枠は**アクセントの実線**(3px、2px 離す)。前の版の半透明の
    `--accent-ring` は背景に対して約 1.7:1(ライト)/ 2.1:1(ダーク)で、非テキストの
    3:1(WCAG 1.4.11)に届かなかった。実線はライト 5.25:1 / ダーク 6.72:1(実測の色から
    計算)。塗りつぶしの中央のボタンでは 2px の隙間が枠を読ませる。
  - `ready` と `paused` の間は、押しても何も起きない向き(今の向きの正反対)のボタンを
    無効の表示にする(`aria-disabled` と、薄くするだけでなく**破線の枠**)— 押して何も
    起きない理由が見える。走っている間は無効にしない(比べる相手がキューで変わり、tick
    ごとにちらつく)。
- **十字の中央**: 1 つのボタンが `ready` で Start、`running` で Pause、`paused` で Resume
  (▶ と ❚❚ の図と、それぞれの名前)。終局後は無効。親指の届く場所に止める手段を置くため、
  スコアの行ではなくここに置く。丸く、塗りつぶし、方向ボタンより小さい(48px)— 向きの
  ボタンではないことが形でわかる。画面上の Start / Resume は**これだけ**である(盤に
  カードを重ねない)。同じことをするキーを `aria-keyshortcuts="Space P"` で名乗る。
  - **フォーカスの置き場所**: 結果カードの「同じ盤面で再挑戦」「新しいゲーム」や ↻ の
    ダイアログで次の盤に進むと、押したボタンはカードやダイアログと一緒に消える。
    フォーカスが `<body>` に落ちたときだけ、それを**十字の中央(Start)**へ移す(`ready`
    の盤では ↻ は押せない)。ダイアログを「キャンセル」(か外側のタップ)で閉じたときは、
    問いを開いた **↻** へ戻す。スクリーンリーダーの利用者が、次に押すものを探し直さずに
    済むようにするため。フォーカスがほかの場所にあれば動かさない。
- **キーボード**: 矢印キーと W A S D で方向。W A S D は印字ではなく**キーの位置**で読む
  (`KeyboardEvent.code`。AZERTY 配列なら Z Q S D)。**Space**(と P)で Start / Pause /
  Resume を切り替える。押しっぱなしの repeat は入力にしない(1 回押せば 1 入力)。矢印と
  W A S D は常に既定動作を止める(ページがスクロールしない)。**Space はフォーカスのある
  ボタン等に任せて二重に処理しない**(P はボタンの操作キーではないので常にゲームが受ける)。
  ダイアログと結果カードの間はキーのリスナーを外す(`useGameKeys` の `enabled`)。
  Space と P は画面には書いていない(Quick Rules も矢印キーだけを言う)。見つけ方は
  中央のボタンの `aria-keyshortcuts` と、Tab で中央のボタンに着くこと。
- **盤には何も重ねない**: `ready` でも `paused` でも、盤の上にはカード・帯・半透明の幕の
  どれも置かない。最初の食べ物、とぐろのどの 1 マス、一時停止中に選んだ向きの矢印も、
  何かの下に入ることがない。`ready` は「始める前に盤面を確認する」ための状態で、
  `paused` は「止まった盤を見て逃げ道を決めてから再開する」ための状態だから(§2・§5)、
  盤の一部でも隠せばその目的が欠ける。
  - 状態は盤の外で示す: `paused` は上段の「❚❚ 一時停止中」(文字と記号、インクの色の
    太字)、Start / Resume は十字の中央の ▶(名前つきのボタン)。選んだ向きは盤の矢印と
    読み上げで示し、文字の「次の向き: 上」は画面には出さない — 矢印はもう何にも隠れず、
    上段の 1 行には収まらない言語がある(320 幅で上段の 2 つのボタンの間は 200px。
    「一時停止中 · 次の向き: …」は fr 225px・es 222px・vi 230px・de 202px と実測で
    はみ出す)。
  - 経緯: 前の版は `ready` と `paused` の盤に、Start / Resume のボタンと「❚❚ 一時停止中」・
    「次の向き」の文を載せた不透明のカードを重ね、頭のいない半分に置いて頭と矢印だけは
    隠さないようにしていた。独立レビュー 2 本(2026-10-17)が、カードが**食べ物や体を
    隠す**ことを実際の盤で示した(360×640 で Start のカードは盤の約 12%、一時停止の
    カードは約 25% を覆い、新しい盤のおよそ 5 枚に 1 枚は最初の食べ物がカードの下にある。
    盤が 260px より小さい画面では頭と矢印も隠した)。カードをやめ、上のとおり盤の外へ
    移した。
- **Restart**: ヘッダの ↻ → `RestartDialog`(§6。同じ盤面で再挑戦 / 新しいゲーム /
  キャンセル)。ダイアログを開いた時点でランを止める(Pause と同じく保存する)。
  **「キャンセル」で閉じても止まったまま**で、再開は Resume か Space だけ。

### 描画とループ

- **tick は 1 本の連鎖タイマー**(tick ごとに次の `setTimeout` を 1 つ張る)が進める
  (`state/GameContext.tsx` の effect)。その effect はゲーム画面に走っているランがある間
  だけ存在し、Pause・バックグラウンド・終局・ダイアログ(開くと Pause)・画面を離れる・
  アンマウントで消える。着いたタイマーは ref のセッションを読み直し、走っていなければ
  何もしない。**requestAnimationFrame の常時ループは持たない。**
- 走った時間の時計もタイマーではない: 走り始めた時刻(`performance.now()`、壁時計の
  跳びを数えないため)と、それまでに走った秒数の 2 つだけを持ち、止めるたびに足す(§10)。
- **盤の描画は、盤の見た目が変わったときだけ更新する。** 盤の部品(`SnakeStage` と
  `SnakeBoard`、`React.memo`)が受け取るのは体・食べ物・状態・向き・衝突・一時停止中に
  選んだ向き(`pendingHeading`)だけで、キューは渡さない。走っている間の方向入力は
  セッションを新しいオブジェクトにするが、体の配列は同じなので盤は描き直されない
  (`SnakeStage.test.tsx` が描画の回数を数えて確かめる)。体の各マスはマス番号を key に
  持つので、1 移動で DOM が変わるのは新しい頭・抜けた尾・首になった前の頭だけ。ヘビは
  マスからマスへ移り、間を補間するアニメーションは作らない。
- **止まっている盤は何も描かず、何も予約しない**: `ready` と `paused` の間、時間が
  いくら過ぎても React の描画は 0 回、保留中のタイマーは 0 個(Root のテストが偽の時計で
  20 秒進めて確かめる)。
- 盤面はインライン SVG で描く(単位はマス、`viewBox` で拡大縮小)。画像・フォントの
  アセットは足さない。

### 見た目(色だけに頼らない)

- アクセントは 1 色(`styles.css` に登録済みの `snake` の色、`var(--accent)`)。ライト /
  ダーク両方で、色はすべて共有のトークン(`--surface` `--line` `--ink` `--ink-soft`
  `--accent` `--accent-ink`)から取り、ゲームの CSS に色の値を書かない。
- **頭**は体より大きい角丸の四角で、進行方向の側に目が 2 つ。**体**は角を丸めた四角の
  連なりで、連続する 2 マスだけを細い「首」でつなぐ — とぐろの中で隣り合っていても
  つながっていないマスの間には隙間が見える。**食べ物**はインクの色の円で、盤の上で
  唯一の丸い形。**衝突**した頭は目の代わりに × を描く。**壁**は盤の縁の太い実線。
- **一時停止中に選んだ向き**(§5)は、頭からその向きへ出る矢印(インクの色)で示す。
  頭の目は動いた向きのままなので、「いま向いている向き」と「再開後に曲がる向き」が
  形で分かれる。選んでいなければ矢印は無い。
- 一時停止中は上段の「❚❚ 一時停止中」の文字と記号(インクの色の太字)と、十字の中央が
  ▶ に変わること、ゲームオーバー・クリアは × と結果カードの見出しで示す(色の変化だけに
  しない)。
- 盤には文字も数字も描かない(§1)。

### スクリーンリーダー

- 盤面は `role="img"` で、盤の大きさと状態を名前に持つ(「Snake board, 14 by 14: paused」)。
  リアルタイムの盤をマスごとに読み上げることはしない。SVG 自体は `aria-hidden`。
- 丁寧(polite)なライブリージョン(`role="status"`)で、**スコアが変わったとき**と
  **状態が変わったとき**(開始・一時停止中とスコア・再開・ゲームオーバーとその理由と
  スコア・クリア)と、**一時停止中に向きを選んだとき・取り消したとき**だけを読み上げる。
  毎 tick は読まない。ライブリージョンは `.game-content` の外に置く — 結果カードが出て
  盤が `inert` になっても終わり方が聞こえる。
- 十字は 1 つのグループ(名前は「Controls」— 中に Start / Pause / Resume も入るので、
  前の版の「Direction buttons」から改めた)。方向ボタンと Start / Pause / Resume は
  それぞれ名前つきのボタンで、中央のボタンは `aria-keyshortcuts` でキーを名乗る。
- 次の盤に進んだときと ↻ の問いを閉じたときのフォーカスの置き場所は「操作」の
  「十字の中央」。

### Reduced Motion

- tick による移動は**ゲームそのもの**なので止めない(Bunny Hop §12 と同じ線引き)。
- 補助的な演出は**最初から持たない**(食べたときの拡大・点滅・画面揺れ・粒子なし)。
  決着から結果カードまでの間(約 1 秒、`useResultReveal`)は、アプリ設定または OS の
  Reduced Motion で即時にする(既存ゲームと同じ)。

### 音

- 既存の合成音(`services/sound`)のみ。食べたとき(`select` の短い 1 音)・ゲームオーバー
  (`gameOver`)・クリア(`clear`)の 3 か所で、設定に従う。曲がるたびには鳴らさない。

## 14. i18n

- 文言は 14 言語。ゲーム専用カタログ `src/games/snake/i18n/*.ts`、キーの接頭辞は `snake`。

  - 他の 12 言語(de / es / fr / hi / id / ko / pt-br / th / tr / vi / zh-hans / zh-hant)=

- 高リスク文言(無料・オフライン・課金・広告・削除・保存の約束)はゲームの文言に書かない。

  - 見たもの: スクリーンショットを読んだうえで、DOM でも横スクロール・はみ出し・切れ・
    文字どうしの重なり・クリップする祖先の外に出た字形を数えた — **どの言語・どの画面でも

  - 直したこと: 一時停止のカードが頭と矢印を隠していた(§13 — 言語によらない。この

## 15. 意図的な差分

**このジャンルの他の実装と合わせないもの**

- **壁の折り返し(端から端へ抜ける)は無い。** 外周は壁である(§1)。
- **加速しない。** 長さや時間で速くならない。難しさは選んだ速度だけ(§7)。
- **障害物・ステージ・特別な食べ物(時間で消えるボーナス等)・パワーアップ・ライフは無い。**
  時間で消える食べ物は時間制限であり、急かす仕組みになる。
- **スコアは食べた数だけ**(速度や長さで倍率を掛けない)。速度ごとの記録で比べる(§10)。
- **デイリーもステージも無い。** Endless だけ。生成は seed 決定的なので、必要になれば
  後から足せる。
- **ポーズに制限が無い**(回数・時間・ペナルティなし)。復帰で自動再開しない(§6)。

**既存の収録ゲームとの違い**

- **Bunny Hop / Brick Breaker / Sky Fighter**(アーケード): あちらは途中保存を作らない
  (§11 の冒頭)。Snake はマス目の離散状態なので、戻したランを `paused` で始めることで
  正直に再開できる。描画も、あちらの Canvas + RAF ループに対し、こちらは tick ごとに
  変わる DOM / SVG で、tick の間は何も描かない。あちらはウィンドウがフォーカスを失っても
  止まらないが、こちらは走っていれば止めて保存する(§6)— PC で別のウィンドウへ移った
  キーボードの人が、戻ったらぶつかっていた、を起こさないため。
- **始める前・止めている間に盤へ何も重ねない**(§13)。止まった盤を見ることがこの 2 つの
  状態の目的だから。
- **2048**: 保存スロット 1 つ・スワイプ・ショートカットからの直接復帰は同じ形。
  Undo は持たない(2048 の唯一の助けが Undo なのに対し、こちらは Pause と Restart)。
- **Number Path** など線を引くパズルとは別物で、規則もコードも共有しない。

**ブランド原則により作らないもの**

- 復活・コンティニュー・追加ライフの販売や広告視聴での解放。
- ストリーク、ログインボーナス、通知での呼び戻し、オンラインランキング。

## 16. 検証の範囲

このゲームには「生成した盤面」が無い(盤はいつも同じ空のグリッド)。seed が決めるのは
食べ物の並びだけで、それはプレイ中にその場で 1 個ずつ引かれる。したがって「全盤面を
解いて確かめた」という形の主張はせず、何を**全数**で、何を**標本**で確かめたかを
次に書く(ルールのテストは `game/*.test.ts`、保存・状態・画面のテストは `storage/`・`state/`・
`ui/` の `*.test.ts(x)` で、どれも毎回の `pnpm test` で走る)。

- **満杯クリアはどの seed・どの食べ物の出方でも到達できる。** 根拠は §4 の構成的な証明で、
  全 seed に効く。証明の前提(閉路が全マスを 1 回ずつ通り、隣り合うマスだけでつながり、
  最後から最初へ戻り、初期のヘビが尾から頭の順で乗っている)は、エンジンを使わない
  検査で確かめる(`guarantee.test.ts`)。そのうえで閉路の自動操縦を実際に満杯まで走らせる:
  テストで **200 seed**(`snake-pilot-0〜199`、うち 10 seed は全 tick で不変条件も検査)、
  計測で別の **1,000 seed**(§17)。すべてクリア、衝突 0、移動数は上限 37,828 以内。
- **エンジンが §3・§8 のとおりに動く。** 独立に書いた第 2 の実装(行・列の組、尾が先、
  占有グリッド、空きマスのリスト — 共有するのは PRNG だけ。`test-helpers.ts`)と、
  1 tick ずつ体・食べ物・スコア・向き・終わり方(壁 / 自分 / クリア)を突き合わせる。
  **200 ラン**: 乱数でさまよう 100 本を衝突まで、閉路で 500〜8,500 移動ぶん長くしてから
  さまよわせる 100 本(長い体での尾の追いかけと自分への衝突)、加えて満杯クリア 1 本。
- **180 度転換が起きない。** tick と tick の間に最大 4 回押す**全組み合わせ**
  (1 + 4 + 16 + 64 + 256 = 341 通り)を 4 方向それぞれから 5 tick 走らせ、連続する
  2 回の移動が正反対にならないことを確かめる(長さ 5 のまっすぐなヘビ、盤の中央)。
  加えて、tick ごとに 0〜5 回のランダム入力を入れる **300 ラン**で同じことと不変条件を
  確かめる。
- **食べ物はヘビの上に出ない。** 不変条件の検査(上の 10 seed と 300 ランの全 tick)、
  独立実装との一致(独立実装は空きマスのリストからしか選ばない)、長さ 3〜195 を 7 刻みに
  した体で 30 抽選ずつ、空きが 1 マスだけの体(16 通り)で必ずそのマスを選ぶこと。
- **食べ物は空きマスに一様。** カイ二乗(自由度 192、上限は平均 + 5 標準偏差): 初期の体で
  38,600 抽選(1 マス 200 回)、9,650 seed の最初の食べ物(1 マス 50 回)。seed は固定
  なので、結果は揺れない 1 つの数である。
- **抽選の仕事量は 391 以内。** 長さ 3〜196 のすべての体で 3 抽選ずつ数える。
- **保存 → 復元で同じランに戻る(乱数の状態も)。** 900 移動目で保存 → JSON → 復元し、
  止めなかったランと同じ操作で最大 4,000 移動続けて、毎 tick の体・食べ物・出来事が一致する。
  一時停止中に向きを選んだラン(右の壁の 1 マス手前で上を選んだ)も、保存 → JSON →
  復元して止めなかったランと 400 移動続けて一致する(再開後の最初の移動は壁ではなく上)。
  端数の秒は切り捨てて書かれ、読める。
- **到達できる局面は復元の検証を通る(誤って捨てない)。** **最初の 8 移動は全数**:
  12 seed で、すべての入力の組み合わせから到達できる局面 17,730 個が検証を通り、元の
  ランと同じに戻る(`history.test.ts`)。長いランは標本: さまよう 60 ランで 25 移動ごと
  (600 局面以上)と、満杯の 1 個手前の局面。
- **壊れた・ありえない保存は捨てる。** §11 の条件を 1 つずつ破った記録(個別の例)、
  記録でないもの(`null`・配列・数など。例外を投げない)、上限を超える数、最初の食べ物
  以外の食べ物(全マス)、選んだ向きの不正な値、そしてレビューで見つかった「どのマスも
  距離と偶奇は合うのに、履歴が 180 度曲がっている」記録 5 例。
- **正確に判定する範囲(§11)は全数で確かめる。** 食べていない記録と履歴が全部体に残って
  いる記録について、6 移動までのすべての候補(各マスが初期の頭からの距離と偶奇の条件を
  満たす体すべて — 検証を通る体はかならずこの中にある)で、「受け入れる ⇔ 実際の
  プレイで到達できる」を確かめる。食べ物は 3 移動まで全マス、それより先は本物と 3 つの
  誤り。テストの外の計測では 8 移動まで・食べ物も全マスで、誤りは 0(§17)。
- **層の探索(§11)は独立の数え方と一致する。** 素朴な全列挙(9 移動まで)と、文字列の
  集合で 1 層ずつ作った層(45 移動まで、4 通りの「避けるマス」)と突き合わせる。どの
  「避けるマス」(193 通りと「無し」)でも 19 層以内に落ち着くことを全数で確かめる
  (上限 64 層には届かない)。届かない上限の**断る側の枝**は、上限を 3 層に下げて走らせ、
  探索が null を返し、本来なら届く尾が「届かない」と答えられる(記録は捨てられる)ことを
  確かめる。
- **同じ seed と同じ操作は同じランになる。** 50 seed を 2 回ずつ走らせて比べる、golden(§8)。

## 17. 実測(仕事量と壁時計)

**門は仕事量で、壁時計は出力するだけ**([ARCHITECTURE.md](ARCHITECTURE.md)「CI / リリース」)。
このゲームの仕事量はすべて構造で上限が決まっている(§8): 1 tick ≤ 衝突判定 195 + 体の写し
196 + 抽選 391。復元の検証は、遊び直しなら 195 移動以内、層の探索なら 784 状態 × 19 層以内
(上限 64 層)。生成・やり直しのループは無く、層の探索の上限はどの記録でも届かないことを
全数で確かめてあるので(§16)、「上限に達した」ことが起きる経路が無く、フォールバック率は
