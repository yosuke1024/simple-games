## 1. 盤面と対局者

- 盤は 81 マス = 小盤 9 × マス 9(`game/types.ts`)。**添字は小盤優先**で、マス `i`(0〜80)は
  `i = 9·b + c` — `b` は大盤の中の小盤の位置、`c` は小盤の中のマスの位置で、どちらも 0〜8 の行優先
  (0 = 左上、4 = 中央、8 = 右下)。画面の行・列は `row = 3·⌊b/3⌋ + ⌊c/3⌋`、
  `col = 3·(b mod 3) + (c mod 3)`。送り(§2)が `c` だけで決まるので、この添字にすると送り先は
  `i mod 9` で読める。
- マスは 0 = 空、1 = ✕、2 = ○ の 3 値。エンジンは印(✕ / ○)で考え、「自分」と「CPU」はセッションが
  対応づける。
- **✕ が先手**で、これは設定ではなく規則である(三目並べの慣習)。パスは存在しない(打てる小盤が 1 つでも
  あれば、必ず打てるマスがある — §2)ので交互は崩れず、**手番は手数から導出する**(手数が偶数なら ✕、
  奇数なら ○)。手番は保存しない(Checkers §8 / Gomoku §8 と同じ理由)。
- 小盤の状態は 4 つ: **未決**(まだ打てる)/ **✕ が取った** / **○ が取った** / **引き分け**(9 マスが
  埋まってラインが無い)。どれも 81 マスの印から導出できる。取られた小盤と引き分けの小盤をまとめて
  **閉じた小盤**と呼ぶ(§2)。
- **盤面の印だけでは局面は決まらない。**次に打てる小盤は最後の 1 手から導出する(§2)ので、局面は
  「着手の列」で表す(§8)。
- **先手か後手かはプレイヤーが選ぶ**(ホーム。既定は先手)。先手 = ✕、後手 = ○ で、ボタンには**形で描いた
  印(盤と同じ SVG — §10)と、翻訳した「先手」「後手」の語**を並べ、プレイヤーが対応を知っている前提に
  立たない(Reversi §1 の「黒(先攻)」と同じ)。ボタンに ✕ や ○ の**文字は置かない**(§12・§16)。選択は
  `nt.prefs` に置く**次の対局の設定**で、**進行中の対局には触らない** — 始めた側のまま終わる。**新しい
  対局は、ホームの難易度ボタン・ヘッダの ↻・結果カードの「新しい対局」のどれから始めても、先後を
  `nt.prefs` から読む**(Reversi の `startNewGame` が `prefsRef` を読むのと同じ)。ホームで先後を変えた
  あとに進行中の対局を再開しても、その対局は始めた側のままで、変えた側になるのはその次の新しい対局からで
  ある。難易度は、ホームでは押したボタンのもの、↻ と結果カードでは直前の対局のもの。セッションは
  `playerGoesFirst` を持ち、CPU は残りの印を持つ。
- 難易度は Easy / Normal / Hard で、最初から全部選べる(§4)。ホームの難易度ボタンがそのまま対局を始め、
  進行中の対局があれば、同じ難易度なら再開し、違う難易度なら先に確認する(Reversi の
  `ui/screens/HomeScreen.tsx` の形)。
- 対局相手は CPU だけである — オンライン対戦もローカル対人戦も作らない
  ([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md)「初期リリースで実装しないもの」)。1 局だけで、デイリー・
  時計・レーティング・ストリークは無い。
- 印は**形**で描く(✕ = 斜めの 2 本、○ = 輪)。文字は置かない — 盤面は全言語で同じに読める
  ([I18N_POLICY.md](I18N_POLICY.md))。ホームの先後のボタンも同じ形を描き、読み上げは翻訳した印の名で
  言う(§10・§12 の用語集の「印」)。色は役割色で、**自分 = アクセント**、**CPU = インク**(§10)。
  先後で印の形が入れ替わっても、自分の色は変わらない。

## 2. 一手の解決(送り)

1. **初手は 81 マスのどこでも打てる。**
2. 2 手目以降、手番の側は**直前に打たれたマスの `c`(小盤の中の位置)と同じ位置の小盤** `b = c` に
   打つ(**送り**)。例: 相手が小盤 0 の右下(`c` = 8)に打ったら、次は右下の小盤 8 に打つ。
3. **送り先の小盤が閉じていれば、閉じていないどの小盤のどの空きマスにも打てる**(自由手)。
4. **閉じた小盤には打てない。**取られた小盤の空きマスにも、以後どちらも打てない。閉じた小盤は送り先にも
   ならない(3 に落ちる)。
5. 打ったマスで、その小盤の縦・横・斜め(8 ライン: 行 `{0,1,2}` `{3,4,5}` `{6,7,8}`・列 `{0,3,6}`
   `{1,4,7}` `{2,5,8}`・斜め `{0,4,8}` `{2,4,6}`)のどれかに同じ印が 3 つ並べば、**その小盤を取る**。
   取った瞬間に小盤は閉じるので、1 つの小盤を両方が取ることは起こりえない。
6. 9 マス目を埋めた手がラインを作れば、**取りが優先**する(引き分けの小盤にはならない)。ラインが無いまま
   9 マスが埋まった小盤は引き分けで、どちらのものでもない。

合法手は `legalMoves` の 1 か所だけが決める(`game/engine.ts`)。**局面が終局している(§3 の判定で勝ちか
引き分けが出ている)ときは空の配列を返す** — 大盤で 3 つ並んだ後は、未決の小盤が残っていても打てない。
終局していなければ、手数 0 なら空きの 81 マス、そうでなければ送り先 `last mod 9` の小盤が未決ならその
小盤の空きマス、閉じていれば未決の全小盤の空きマス。**未決の小盤には必ず空きマスがある**(満杯なら取られたか
引き分けで閉じている — 上の 6)ので、終局していない限り合法手は 1 つ以上ある。画面と CPU と保存の検証
(§8)は、同じ関数を使う。1 マスについて尋ねる `isLegalMove`(画面の着手と保存の再生が使う)は、0〜80 の整数か
を確かめたあとは `legalMoves` に入っているかを見るだけで、規則の 2 つ目の書き下しではない。

- 自分の手で自分の送り先を閉じることがある。小盤 `b` のマス `c = b` に打ってその小盤を取る(または埋める)と、
  送り先は閉じたばかりの小盤 `b` になり、相手は自由手になる。規則どおりで、特別扱いはしない。
- **打てるマスだけが押せる**(§10)。閉じた小盤・送り先以外の小盤・埋まったマスを押しても、何も起きず音も
  鳴らない。拒否ではなく、そもそも提示していない(Checkers §6「無効な操作を叱らない」)。
- **置くのは 1 タップである**(Gomoku §2 の 2 度タップにしない)。算術ではマスは 360 幅で約 35px、シリーズの
  下限の 320 幅で約 31px(§10 — 幅だけで決まる場合の算術)で、Gomoku の交点の間隔(約 19px)とは事情が
  違う。置き間違いは Undo(§5)で無料で戻せる。**2 度タップへ切り替えるかどうかは、実機で触る確認で決める
  — 製品オーナーが持つ確認待ちである**(§16)。Phase 3 が見たのは Chromium の 320 幅のタッチの模擬までで、
  マスの大きさ(30px)と、タップがそのマスに届くことは測れたが、指での置き間違いの多さは測れない(§13)。それまでは 1 タップ。
  誤操作が目立てば 2 度タップへ切り替え、ここを直す。Overtake / Tangram の Phase 0 と同様に製品オーナーが
  実機で行う確認だが、このゲームの分は計画にまだ無い。

## 3. 終了条件

1. **取った小盤を大盤で 3 つ並べた側の勝ち**(大盤の 8 ラインは §2 の 5 と同じ形を、小盤の位置 `b` に当てた
   もの)。引き分けの小盤はどちらのラインにも数えない。
2. **全小盤が閉じて大盤にどちらのラインも無ければ引き分け。**「取った小盤の多い側の勝ち」は採らない(§11・
   §14)。
3. 判定は着手のたびに 1 → 2 の順で行う。小盤を取った手が大盤のラインを完成させれば、ほかの小盤が残って
   いても、その場で勝ち。最後の小盤を閉じた手がラインも完成させれば、勝ち(引き分けより先に見る)。
4. **大盤で両者ともラインを作れなくなっても、全小盤が閉じるまで続ける**(早仕舞いの引き分けは作らない)。
   計画の凍結した規則は「全小盤が閉じて大盤にラインが無ければ引き分け」を定めるだけで、打ち切りの有無は
   定めていない。これはこの文書の解釈で、操作を増やす側のコストを伴う、製品オーナー向けの選択である
   (§11・§16)。
5. 対局は最大 81 手で必ず終わる(1 手で空きマスが 1 つ減り、81 手目の後は全小盤が閉じている)。
6. 勝敗はプレイヤーの側から見た `status`(`'playing' | 'won' | 'lost' | 'draw'`)で、一度だけ遷移する
   (`game/session.ts`。Reversi §3 の形)。**終局した対局には打てない。**負けを叱る文言は書かない。

## 4. CPU

- 探索は**プレイヤーの着手を起点にのみ**走る。ポーリングも先読みもしない
  ([GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「CPU 探索」)。CPU の手番は `state/GameContext.tsx` の effect が
  張る 1 本の timeout(`CPU_DELAY_MS` = 450ms)で、effect はセッションを依存に取り、アンマウント・Undo・
  新規対局・画面遷移の cleanup がそれを外す。着地したタイマーは「いま本当に CPU の手番か」を ref で確かめて
  から打つ。探索はその timeout の**中**で同期に走る(Worker も先読みも無い — GAME_LIFECYCLE
  「新しいゲームを足すときのチェックリスト」5)。着手が現れるのは概ね **450ms + 探索時間**である(Reversi §5)。
- 後手を選んだ対局の初手、CPU の手番で離れた対局の再開(§8)、ショートカットからの再開も、同じ 1 本の
  タイマー・同じ上限で打つ(GAME_LIFECYCLE「CPU 探索」の例外の形)。
- effect はページが見えているかも依存に取る: バックグラウンドの間はタイマーを張らず、戻ったらタップなしに
  同じ 450ms で張り直す。**これは共通要件「復帰しても勝手に再開しない」からの外れで、製品オーナーの確認待ち**
  (§16「Phase 3 の実装で決めたこと」の最初の項)。
- ルールは `game/engine.ts` の 1 セットだけで、探索用の速いコピーを持たない。探索は 1 つの `Int8Array(81)` と
  小盤の状態 9 個の上で着手と復元(make / unmake)を行い、盤を作り直さない(Reversi §5)。

### 4.1 難易度ごとの読み

3 つとも、まず**その手で勝てる手(大盤の 3 つ目を取る手)があれば必ずそれを打つ**(候補が複数なら下の同点の
規則で選ぶ)。この確認は、合法手を 1 つずつ「大盤のラインが完成するか」と `engine.ts` で見るだけで、探索関数を
呼ばないので**ノードに数えない**(最大 81 回の判定)。Phase 2 のテストで確かめた(`cpu.test.ts` — 全難易度で、
勝てる手が 1 つの局面ではその手を、複数の局面では下の同点の規則どおりの手を選び、どちらもノードは 0)。

次に、**合法手が 1 つしかなければ、どの難易度もそれを打つ**(点も付けず、探索もしない — ノードは 0)。選びようの
ない手に上限いっぱいの探索を使わないためである(Phase 2 で決めた。`cpu.test.ts` が全難易度で確かめる)。

- **easy** — 1 手読み + seed の揺らぎ。**探索はしない。**各合法手を打った直後の局面を静的評価(§4.2)する
  だけで、相手の応手は読まない。§4.2 の値は手番の側から見たもので、CPU が打った直後の手番はプレイヤーなので、
  **手の点は `score(手) = −eval(その手を打った直後の局面)`**、つまり CPU から見た値にする(符号を反転しないと、
  プレイヤーにとって最善の手を選んでしまう)。`score` の高い順(同点はマス番号の小さい順)に並べ、先頭から
  `EASY_TOP_CHOICES` 手(初期値 3。合法手がそれより少なければ全部)を切り出す。**並べ方も切り出しの境も、この
  `score` と同点の規則だけで決まる**(3 位と 4 位が同点なら、マス番号の小さいほうが残る)。切り出した手の中から、
  下の乱数で等確率に 1 つ選ぶ(並べた順の `⌊r × 手数⌋` 番目)。
  **easy は相手の応手を探索しないが、静的評価の項は見える。**§4.2 の「送り先の価値」(相手を自由手にする・
  相手が次の手で取れる小盤がある)と、相手の小盤内の 2 つ並びは、打った直後の局面の特徴として数えられる。
  つまり「送った先で相手が小盤を取れる」ことを**その局面の 1 項としては**見るが、相手が実際にそう打つかを
  読んで確かめることはしない。Connect Four の easy と同じく、自分の手の直後の局面を評価するだけの 1 手読みで、
  違うのは、最善の 1 手ではなく上位 3 手から乱数で選ぶ点である。計画の推奨の「相手のリーチは見えない」からは、
  この静的評価の項の分だけ外れる(§16)。
- **normal** — 反復深化 α–β で、最大の深さ `NORMAL_MAX_DEPTH`(初期値 3 プライ)。下のノード上限の中で
  走り、上限に達したら完了済みの深さの最善で打つ(自由手の局面では深さ 3 が完了しないことがある — 算術では、
  枝刈りなしの葉の数は、根が自由手でその先が送り先の 1 小盤(9 マス)だけなら、深さ 3 で 81 × 9 × 9 = 6,561、
  深さ 4 で 81 × 9 × 9 × 9 = 59,049 で、その先が自由手ならさらに増える)。計画の推奨は「固定深さ 3〜4(上限の
  内側)」だったが、固定深さは自由手の局面で上限を超えるか、上限で止める仕組みが別に要る。hard と同じ反復深化に
  深さの上限を付ければ仕組みは 1 つで済むので、そうした(§16 — 推奨から外れた点)。3〜4 のうち 3 を初期値に
  したのは、上の算術で深さ 4 が上限の内側に収まる保証が無いためである。上限 40,000(§4.3)の下では、
  `cpu.bench.test.ts` の 12 局面で hard が完了した深さは 4〜6、§4.3 の計測の 213 局面のうち即決の 3 を除く 210
  局面では 4〜7 で(どちらも Phase 2 のテストで実測 — 後者は `NT_SELFPLAY=full` のときだけ走る)、それらの局面では
  深さ 4 が上限の内側に収まった。局面の全体で 4 が収まるかは未検証で、3 のまま自己対局で順序が出た(下・§13)
  ので変えていない。
- **hard** — 反復深化 α–β で、深さの上限はノード上限だけが決める(反復の深さの上限は残りの空きマスの数で、
  定数ではなく `decideCpuMove` がその場で数える)。
  ノード上限 `HARD_NODE_LIMIT`(値は §4.3)に達したら**完了済みの深さの最善で打つ**。完了した深さで
  勝ちを読み切ったら、それ以上深くしない — 完了した深さの最善値が `WIN − 81` 以上(81 手の内のどこかで勝ちに
  届く値)なら止める(Phase 2 で決めた判定。normal にも同じ判定がかかる)。
- normal と hard は同じノード上限を使う。違うのは深さの上限だけなので、**hard が normal より浅く読むことは
  ない**。順序(hard > normal > easy)は自己対局で測る。**「順序が出る」とは、組ごとに、強いほうの勝ちが
  弱いほうの勝ちより多いこと**(引き分けは数えない。各組 40 局、着手列が同じ対局は 1 局に数えて重ねない —
  手順と結果は §13)。出なければ `NORMAL_MAX_DEPTH`・`EASY_TOP_CHOICES`・§4.2 の重みを変えて測り直し、決めた
  値をここに書き直す。**Phase 2 のテストで実測して順序が出た**(hard 35 勝・normal 3 勝・引き分け 2、
  normal 39 勝・easy 1 勝・引き分け 0 — 各組 40 局、重複なし。§13)ので、`NORMAL_MAX_DEPTH` = 3・
  `EASY_TOP_CHOICES` = 3・§4.2 の重みは初期値のまま確定した。

探索の詳細:

- **ノードの数え方**: 探索関数の 1 回の呼び出し(根の手ごとの呼び出し・葉を含む。根の手を順に回す反復の
  ループ自体は数えない)を 1 ノードと数える。**カウンタは CPU の 1 手につき 1 本で、反復深化の全反復にまたがって
  累積する**(反復ごとに戻さない。深さ 1 の最大 81 ノードも含む)。数は決定的で、`game/cpu.bench.test.ts` が
  見るのは、この 1 手分の合計である。勝てる手の確認(上)と easy の静的評価は探索関数を呼ばないので数えない
  (easy の仕事量は合法手の数、最大 81 回の評価で頭打ちになるので、上限は要らない)。探索関数は呼び出しの
  前に `nodes ≥ 上限` を調べてから数える(Connect Four / Checkers と同じ)ので、カウンタは上限を超えない。
  例外は、深さ 1(下)が上限の判定を受けないために、上限が 81 未満のテスト用の値のときだけ超えうることである
  (§4.3 の候補は 5,000 以上)。
- **深さ 1 は必ず完了する**: 上限の判定は深さ 2 以上の反復の中でだけ行う(深さ 1 は最大 81 ノード。カウンタには
  数える)。深さ `d`(≥ 2)の途中で上限に達したら、その反復の途中結果を捨て、深さ `d − 1` の結果を使う。
- **手の順序**(枝刈りのため。決定的): 手は次の 3 つの組の**ちょうど 1 つ**に入る。まず ① 小盤を取る手かを
  見て、そうなら ①。そうでなければ、③ 取らずに相手を自由手にする手(手を打った後の局面で送り先の小盤 `c` が
  閉じている手 — 打った小盤を埋めて引き分けにして閉じる場合を含む)かを見て、そうなら ③。残りが ②。並べる順は
  ① → ② → ③。**① が ③ に優先する**: 小盤 `b` のマス `c = b` に打ってその小盤を取る手(§2 の、自分で自分の
  送り先を閉じる手)は必ず ① に入り、① の中で相手が自由手になるかは区別しない。同じ組の中は、小盤の中の位置で
  中央(`c` = 4)→ 角(0, 2, 6, 8)→ 辺(1, 3, 5, 7)、同じ位置どうしは小盤の番号の小さい順。角どうし・辺どうしは
  位置の番号の小さい順で、位置の順は 4, 0, 2, 6, 8, 1, 3, 5, 7 の 1 列になる(Phase 2 で決めた読み — `cpu.ts` の
  `orderedMoves`。`cpu.test.ts` が、実装の式ではなく組の定義どおり — 手を打ってみて、その小盤を取ったか、相手の
  送り先が閉じたか — で組を数え、300 局面で照合する)。順序は枝刈りを通じて
  ノード数を、したがって上限の下で完了する深さと選ばれる手を変えるので、`compatibility.test.ts` のゴールデンと
  `cpu.bench.test.ts` のノード数は、この順序を前提に固定する。
- **根の探索**(Connect Four の `bestAtDepth` と同じ形): 反復の深さごとに、**根の合法手を 1 つずつ、窓
  (−∞, +∞)で探索する**。α を根で狭めない。根の手の値はどれも正確になり、下の「ちょうど同じ値」が定義できる
  (狭めた窓の fail-hard / fail-soft が返す境界値を、同点と取り違えない)。代わりに根の手の間の枝刈りが無く、
  同じ上限で読める深さは浅くなる。**根の手の順序は、値にもノード数にも効かない**(1 つずつ独立に探索し、途中で
  上限に達した反復は丸ごと捨てる)ので、前の反復の最善手を先頭に回す処理は持たない — 最善手が同点で複数あるとき
  「前の最善手」がどれか決まらない問題も起きない。次の反復へ引き継ぐものは、カウンタのほかに無い。
- 終局は探索の中でも終局として読む(勝ち・引き分けの判定は §3 と同じ `engine.ts` の関数)。
- 置換表(Zobrist)は v1 では持たない。Phase 2 では足していない — 置換表なしで自己対局の順序が出た(§13)。
- **同点の規則**: 上の根の探索で、完了した最も深い反復の最善値とちょうど同じ値の手を、マス番号の小さい順に
  並べ、`createRng(`${seed}:cpu:${moveCount}`)` の最初の値 `r` で `⌊r × 候補数⌋` 番目を選ぶ。勝てる手が複数
  あるときも同じ規則で選ぶ。easy の揺らぎも同じ乱数の最初の値を使う。`game/rng.ts` は各ゲームが自分の写しを
  持つ(Reversi / Checkers / Gomoku / Connect Four と同じ)。**同じシードで同じ手順なら、CPU は必ず同じ手を
  返す**(§5 の Undo が振り直しにならない根拠)。ゴールデンは `game/compatibility.test.ts`。
- シードは対局ごとに 1 つで、`nested-tic-tac-toe-<token>`(`<token>` は Reversi の `newSeedToken` と同じ形 —
  時刻の 36 進 + 乱数)。使うのは CPU の同点と easy の揺らぎだけ。初期局面は空の 1 つなので、生成も同梱盤面も
  フォールバックも要らない。

### 4.2 評価関数(形も重みも確定 — Phase 2 の自己対局)

小盤 1 つを大盤の 1 マスとして見て、大盤を Connect Four §4 の窓の数え上げの形で数える。値は手番の側から
見た「自分 − 相手」(negamax)。下の重みは初期値として置いた値で、**Phase 2 の自己対局で順序が出たので調整せずに
確定した**(§4.1・§13。`compatibility.test.ts` が値を固定する)。

- **終局**: 勝ち `+(WIN − ply)`、負け `−(WIN − ply)`、引き分け 0(`WIN` = 1,000,000。`ply` は根からの
  深さ — 早い勝ちと遅い負けを選ぶ)。
- **大盤のライン**(8 本): 引き分けの小盤を含むライン、両者の取った小盤を含むラインは 0。それ以外で、片側が
  取った小盤が 1 つなら `BIG_1`(初期値 40)、2 つなら `BIG_2`(初期値 300)をその側に足す。
- **取った小盤**: 小盤 `b` を通る大盤のラインの本数 `w(b)`(角 3・辺 2・中央 4)を重みに、
  `BOARD_OWN × w(b)`(初期値 `BOARD_OWN` = 25)をその側に足す。
- **未決の小盤の中**: 相手の印を含まない小盤のライン 1 本ごとに、自分の印が 2 つなら `SMALL_2 × w(b)`
  (初期値 6)、1 つなら `SMALL_1 × w(b)`(初期値 1)を足す。相手について同じ値を引く。
- **送り先の価値**: 手番の側が自由手(初手を含む)なら `FREE_MOVE`(初期値 15)を手番の側に足す。手番の側が
  打てる小盤のどれかに「自分の 2 つ + 空き 1」のラインがあれば(次の手で取れる)、`TAKE_NEXT`(初期値 20)を
  足す。相手を自由手にする手・相手が取れる小盤へ送る手が損になるのは、この 2 項を相手の手番で数えるから
  である。`TAKE_NEXT` は、打てる小盤が自由手でいくつあっても 1 回だけ足す(Phase 2 で決めた読み)。
- 評価関数が見るのは終局していない局面だけである。大盤のラインに片側の取った小盤が 3 つある局面は終局なので、
  探索は終局の値(上)で読み、評価関数を呼ばない。easy(§4.1)では、引き分けで終わる手の点を 0 とする(勝ちで
  終わる手は先の「勝てる手の確認」で選ばれている)。
- 静的な値は `cpu.test.ts` で手計算と照合した: 空の盤は `FREE_MOVE` の 15 だけ、✕ が小盤 4 の中央に打った
  直後(○ の手番、小盤 4 へ送られる)は −16(中央を通る 4 本 × `SMALL_1` × `w(4)` = 4)。ほかに、着手の列で
  作った局面で、手番の側が取った小盤 1 つ(`BIG_1` × 3 本 + `BOARD_OWN` × 3 — 186)、大盤の 1 本に相手の取った
  小盤 2 つと小盤内の 2 つ並び(`BIG_2`・`SMALL_2` — −494)、送られた小盤で次に取れる(`TAKE_NEXT` — 32)、自由手で
  取れる小盤が 2 つあっても `TAKE_NEXT` は 1 回(224)を手計算と照合した。引き分けの小盤を含む大盤のライン・両者の
  取った小盤を含むラインが 0 になることは、この節を文書のとおりに書き下したテストの中の評価(盤の状態と合法手は
  エンジンでなく `test-helpers.ts` の判定から取る)と、seed つきのランダム対局 300 局の全局面で値が一致すること
  (その中に両方の形が 100 局面以上ずつある)で確かめた。

### 4.3 ノード上限(`HARD_NODE_LIMIT` = 40,000 — 段 1 の Node の暫定値)

**ノード上限は低スペック実機の p95 で決める**(製品オーナーのブリーフ)。提案時の試作の「Node で 100k ノード
p50 37ms」は使わない。低スペック実機で CPU の探索を測った前例は無く(出荷済みの 4 本は開発機の実測か、
出荷済みの hard との同じ環境での比較で決めている — Checkers §4 / Gomoku §4)、この環境には実機も無い。
そこで次の 3 段で決め(下)、**どの段で決めた値かをここに書く**(§16 — 実機の段取りは製品オーナーの確認待ち)。

**値を選ぶのは計測であって、テストではない。**選ぶには出荷済みの hard 4 本を同じ環境で動かす必要があるが、
`src/games/nested-tic-tac-toe/` の下のテストは他のゲームを import できない
(`src/test/importBoundaries.test.ts` の規則 1)。計測は**リポジトリの外の作業ディレクトリのスクリプト**で行い
(自己対局 — §4.1・§13 — と同じ扱い。2026-10-17 計画「性能」も「スクリプトと結果は作業ディレクトリに置き、
リポジトリには入れていない」)、手順・環境(Node の版・機種)・結果の表をこの節に書く。ゲームのテスト
(`cpu.bench.test.ts`)が見るのは、決まった値の下でのノード数の決定性と上限だけである(下)。3 段は次のとおり:

1. **Phase 2(暫定値、Node)**: 同じ Node の上で、出荷済みの hard 4 本(Reversi 12,000 / Connect Four 30,000 /
   Checkers 26,000 / Gomoku 8,000)と、候補をはめた Nested の hard を、**同じ手順**で測る。局面は、ゲームごとに
   seed `measure-<id>-1`〜`measure-<id>-40` の 40 局(両者ランダムな合法手 — §13 のファズと同じ打ち方)から、
   手数 4・12・20・28・36 の局面(その手数までに終局していれば除く)で、最大 200 局面。Nested は自由手の局面を
   20 以上含める(足りなければ自由手の局面だけを足す — 分岐が最大 81 になり、同じ上限でも読める深さが大きく
   変わるため)。各局面で hard の 1 手(CPU の選択の関数 1 回)を 3 回測って中央値を取り、局面数ぶんの中央値の

   最大値とほぼ同じになるので、判定に使わない。**候補(5,000 / 10,000 / 20,000 / 40,000 / 80,000)のうち、

   `CPU_DELAY_MS` = 450ms 後)のコールバックの中の探索である。**2026-10-17 計画「性能」が数えた Event Timing の
   `duration`(タップから次の描画)は、この探索を含まない — 探索は 450ms 後のタイマーの中で走り、その
   `duration` の外にある — ので、同じ測り方では探索を測り損なう。代わりに、探索を含む **Long Task**
   (`PerformanceObserver` の `longtask`。タップから `CPU_DELAY_MS` 以降に始まる最初のもの)の長さを取る。
   Long Task は 50ms 未満だと報告されないので、出なかった手は「50ms 未満」と数える。局面は、手順 1 の局面から
   40 局面(自由手の局面を 10 以上)を選び、**CPU の手番で離れた保存(`nt.saveGame` — §8.3)を再開して**その
   局面に着く(UI を手で操作せず、再開の 450ms 後に CPU が打つ経路をそのまま通る)。各局面 3 回の中央値の p95

  訪問ノード数(§4.1 の 1 手分のカウンタの合計 — 反復をまたいで累積した値)が上限以内・実行ごとに同じで、
  **12 局面すべてで上限を使い切る**こと、完了した深さが局面の順に 4, 4, 5, 5, 6, 5, 5, 5, 6, 6, 6, 6 であることを
  判定する(Phase 2 のテストで実測)。壁時計はログに出すだけで、判定に使わない
  ([RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md)、[SUDOKU_RULES.md](SUDOKU_RULES.md) §7)。
- 決めた値は [GAME_LIFECYCLE.md](GAME_LIFECYCLE.md)「CPU 探索」のノード上限の列に足す(統合の作業 —
  計画「文書」)。
- **「強い CPU」は作らない**(issue #26 非目標)。上限は正直に守り、強さを売りにしない。画面にも公開文面にも
  「強い」「AI」と書かない(PRODUCT_PRINCIPLES は「AI 機能」を採用しない。BRAND.md は未検証の性能を公開文面に
  書かせない)。

## 5. Undo

- **無制限・無料**。自分の直前の決定点まで戻す — **着手の列の末尾から、プレイヤーの手を 1 つ取り除くまで
  手を取り除く**(`game/session.ts` の `undo`)。CPU が応手を打った後なら、CPU の応手と自分の 1 手がまとめて
  戻る。CPU の 450ms の間に押せば、自分の 1 手だけが戻り、張られていたタイマーは cleanup で外れる。
- 列にプレイヤーの手が 1 つも無ければ戻せない(ボタンは無効)。**後手で始めた対局の CPU の初手は戻らない**
  — 自分の決定点が無いため。
- Undo は振り直しではない: 戻して同じ手を打てば、CPU は同じ手を返す(§4 の決定性 — CPU の乱数は seed と
  手数だけで決まる)。
- 終局した対局は戻さない。決着から結果カードまでの間(§10)にも押せるものは無く、統計は終局で計上済み
  である(§7)。
- **再開した対局でも戻せる**(§8)。保存が着手の列なので、追加の保存なしで履歴がそのまま戻る。盤面 4 本
  (Undo 履歴を保存しない — Reversi §9)との意図的な違いである(§11)。
- Undo は統計に触れない。Ctrl/Cmd+Z でも押せる(`useGameKeys` — キーリピートは無視する)。
- 広告視聴や課金による Undo は作らない([ADS_POLICY.md](ADS_POLICY.md))。

## 6. 助けの形

- **打てる小盤は常に盤面に示す**(枠。§10)。手番行の文言でも、送られた盤があるときは「枠の盤に打つ」、
  自由手のときは「空いている盤のどこにでも」と言う(文言は §10 の 1 か所に置く)。初めての人が最初に躓くのは
  「どこに打てるか」という規則の読み取りであり、これは規則の可視化であって最善手の提案ではない(Reversi §7 の
  合法手の点と同じ側)。
- **Hint は作らない**: 盤面は完全に見えており、隠れた情報が無い。次の一手を教える機能は CPU がプレイヤーの
  側でも打つことになる(Reversi §7 / Connect Four §6 / Checkers §6 と同じ判断)。
- **作らない**: 評価バー・棋譜・「取られる」警告・投了・引き分けの提案。投了の代わりは新しい対局で、負けには
  数えない(§7)。
- 助けは Undo(§5)と打てる小盤の表示だけ。どちらも無料で、初回起動から使える。

## 7. スコアと統計

- スコアという数は無い。対局の結果は勝ち / 負け / 引き分けと、取った小盤の数(自分 n – CPU m)だけである。
- 統計(`nt.stats`)は難易度ごとに `played`(開始した回数)・`wins`・`losses`・`draws`、全体で
  `totalPlaySeconds`(記録の形と範囲は §8.5)。ストリークは数えないし表示しない。`totalPlaySeconds` は
  計画の表に無いが、盤面 4 本と同じ計上を引き継ぐ(Reversi §8)。
- `played` は対局を始めたときに数える(再開では数えない)。対局を放棄して新しく始めた場合、負けには数えない —
  記録されるのは実際に終局した対局だけで、統計が脅しになってはならない。
- プレイ時間は逐次計上(bookedRef 方式、2048 と同じ)。退出の同期は `useOnUnmount(syncActiveGame)` を 1 回
  (`src/test/unmountBookingWiring.test.ts`)。
- 結果カードの `BestDelta` は使わない — 時間も点も記録しない(盤面 4 本と同じ)。

## 8. 中断と再開(保存)

**途中保存する。**ターン制で、保存して開き直した局面は保存した瞬間と同じである(GAME_2048_RULES §10 /
Reversi §9 と同じ理由)。デイリーが無いので 2 スロット規則はかからない(`src/test/savedGameSlots.test.ts` は
`dailyGame` を持つゲームだけを検査する)。

保存キー(`storage/keys.ts`。`gameKeys.test.ts` の自分の行にも同じものを置く)。**宣言の順は `saveGame`、
`stats`、`flags`、`prefs`** — レジストリが `Object.values(NT_STORAGE_KEYS)` をそのまま `storageKeys` にし、
`gameKeys.test.ts` の行がその順で比べるため:

| キー          | 中身                                          |
| ------------- | --------------------------------------------- |
| `nt.saveGame` | 中断中の 1 局(1 スロット)                     |
| `nt.stats`    | §7 の統計(形は §8.5)                          |
| `nt.flags`    | `tutorialCompleted`(スキャフォールドのまま)   |
| `nt.prefs`    | 先後だけ(`playerGoesFirst`。難易度は持たない) |

スキャフォールドの `nt.stats`(`{ schemaVersion: 1, played }`)は形を §8.5 に置き換える。どのビルドにも出て
いない(`'in-development'`)ので、移行の要る保存は存在しない。

**キーが入る順(計画の「同じコミット」からの外れ — §16)。**この文書の保存の節が先に入り、`keys.ts` と
`gameKeys.test.ts` の行は、この節を書いたコミットでは足さなかった(スキャフォールドの `stats` / `flags` の
まま)。`nt.saveGame` と `nt.prefs` は、**Phase 3 で、次を全部そろえた 1 つのコミットで**入れた:

- `storage/gamePersistence.ts` — `.save*` のキーを宣言すると、`src/test/shortcutResumeWiring.test.ts` が
  このモジュールの存在を要求する(キーの形とモジュールの有無が食い違うと落ちる)。
- `entry` の配線 — Root と provider の `entry?: 'collection' | 'shortcut';` の宣言、provider の
  `entry === 'shortcut'`、ゲームのテストの中の `entry="shortcut"`(同じ門が要求する)。
- 両方の SchemaDef(`storage/schemas.ts`) — `src/test/resetLocalDataWiring.test.tsx` は宣言したキーすべてに
  SchemaDef を要求する。
- `gameKeys.test.ts` の自分の行(上の順)。

`saveGame` のキーだけを先に足すと `shortcutResumeWiring` が落ちるため、計画の「各ゲームの `storage/keys.ts` と
`gameKeys.test.ts` の自分の行は、ルール文書の保存の節と同じコミットで増やす」からは外れ、保存の節が先、
実装(Phase 3)が後になる。

### 8.1 `nt.saveGame`(v1)

```ts
{
  schemaVersion: 1,
  seed: string,              // 1〜64 文字
  difficulty: 'easy' | 'normal' | 'hard',
  playerGoesFirst: boolean,  // true = 自分が ✕(先手)
  moves: number[],           // マス番号 0〜80(§1 の添字)の列。長さ 0〜81(形の上限。読み込めるのは
                             // 終局していない列なので、実際は 80 まで)
  elapsedSeconds: number,    // 0〜1e9 の整数
  savedAt: number,           // 0〜1e15 の整数
}
```

- 中身は**着手の列**で、盤の文字列を持たない。手番は手数から、送り先は最後の手から導出する(§1)。盤面 4 本は
  盤の文字列を保存するが、ここでは最後の手が無いと規則が復元できないので列にする(47〜51 の Chess の計画と
  同じ形)。列なので Undo の履歴も戻る(§5)。
- 保存の時機: 対局の開始、各着手(自分と CPU)、Undo、退出の同期。終局したらスロットを消す。
- 書き手(`game/serialize.ts` の `toSavedGame`)は読み手(§8.2)と対称にする: 終局した対局にはレコードを作らず
  (null)、`elapsedSeconds` と `savedAt` は整数に切り下げて 0〜上限に収め、有限でない値は 0 と書く。書いたレコードを
  自分の読み手が捨てることはない(`serialize.test.ts` が範囲の端・NaN・無限大で往復を確かめる)。
- CPU の 450ms の間に離れた対局は、CPU の手番のまま保存される。

### 8.2 読み込み(fail-closed)

読み込みでは、**同じ `engine.ts` で空の盤から列を 1 手ずつ再生して検証する。**次のどれか 1 つでもあれば
レコードを読み捨て、ホームへ戻る(黙って新しい対局を始めない — Reversi §9 / Checkers §8):

- スキーマの形が合わない(未知の `schemaVersion`、型違い、範囲外の数、整数でない数、`moves` が配列でない、
  **長さ 82 以上** — 要素を 1 つも読まずに落とす。合法な列はその長さにならないので、これは結果を変えない多重の
  守りで、巨大な配列の再生に時間を使わないためにある、空の seed)
- **非合法手** — 埋まったマス・閉じた小盤のマス・送り先以外の小盤のマス(§2)
- **終局後の手**(勝ちか引き分けで終わった後に続く手)
- 再生し終えた局面が終局している(終局した対局は保存されない — §8.1)

「非合法手」と「終局後の手」は、同じ検査 — 各手が、その手の直前の局面の `legalMoves` に入っているか
(`isLegalMove` — §2)— で落ちる。終局した局面では `legalMoves` が空(§2)なので、終局後の手は必ず落ちる。
理由を分けて挙げるのは、テストで別々の例にするためである。

再生は最大 81 手で、探索は走らない(GAME_LIFECYCLE「読み込み時の再証明」のような例外には当たらない)。

### 8.3 再開

- **CPU の手番で離れた対局は、再開の 450ms 後に CPU が打つ**(Reversi §9。ホームの再開でもショートカットからも
  同じ 1 本のタイマー — GAME_LIFECYCLE「CPU 探索」の例外)。
- スロットが 1 つなので、ホーム画面ショートカットは中断中の対局へ直接入る(`entry` と
  `storage/gamePersistence.ts`。`src/test/shortcutResumeWiring.test.ts`)。
- 初回の Quick Rules を終えると、中断中の対局があればそれを再開する(新しく始めて上書きしない — フラグと
  保存は別々の記録なので、フラグの記録だけが失われたり読めなくなったりすることがある。Reversi §9)。

### 8.4 `nt.prefs`(v1)と `nt.flags`(v1)

- `nt.prefs`: `{ schemaVersion: 1, playerGoesFirst: boolean }`、既定 `true`。**難易度は入れない** —
  盤面 4 本(Reversi / Gomoku は `playerIsBlack`、Checkers / Connect Four は `playerGoesFirst`)と同じく、
  難易度はホームのボタンで選ぶ。名前は Checkers / Connect Four の `playerGoesFirst` に揃える(印の色ではなく
  先後が選択の中身であるため)。壊れた値は既定に戻す(進行中の対局には関係しない)。
- `nt.flags`: `{ schemaVersion: 1, tutorialCompleted: boolean }`。

### 8.5 `nt.stats`(v1)

```ts
{
  schemaVersion: 1,
  totalPlaySeconds: number,  // 0〜1e12 の整数
  easy:   { played: number, wins: number, losses: number, draws: number },
  normal: { played: number, wins: number, losses: number, draws: number },
  hard:   { played: number, wins: number, losses: number, draws: number },
}
```

- 各難易度の `played`・`wins`・`losses`・`draws` は 0〜1e9 の整数、`totalPlaySeconds` は 0〜1e12 の整数
  (Reversi の統計と同じ形と範囲)。整数でない数・範囲外・欠けた難易度・型違い・未知の `schemaVersion` が 1 つでも
  あれば**レコード全体を無効**とし、既定(すべて 0)に戻す(読めた部分だけを拾わない)。
- `schemaVersion` は **1 のまま**。スキャフォールドの `{ schemaVersion: 1, played }` を置き換えるが、どのビルドにも
  出ていない(§8)ので移行は要らない。開発中の端末にスキャフォールドの形が残っていても、難易度のキーが無いので
  無効として既定に戻る。

## 9. Quick Rules(アプリ内チュートリアル)

3 ステップ・図中心・各 1 文(初回起動時に表示、以後はホームから)。**送りを先頭に置く。**ホームと Quick Rules に
`WebBetaNotice` を出す(`src/test/webBetaNoticeWiring.test.ts`)。

1. 打ったマスの位置が、相手が次に打つ小さな盤を決める。
2. 送られた盤が取られているか埋まっていれば、空いている盤のどこにでも打てる。
3. 小さな盤で 3 つ並べればその盤を取り、取った盤を 3 つ並べれば勝ち。

`en` が原文で、意味は次のとおり(文面は Phase 3 の i18n で決める): 1. Where you play inside a small board
picks the board your opponent plays in next. 2. If that board is taken or full, play in any open board. 3. Three in a row takes a small board; three taken boards in a row wins.

- 2 は計画の文案の「閉じていれば」を「取られているか埋まっていれば」に開いた — 「閉じた盤」は定義の要る語で、
  1 文で済むなら定義を持ち込まない。3 は計画の文案「小さな盤を 3 つ並べて取れば勝ち」が「小盤を 3 つ並べる
  こと = 取ること」と読めるので、2 段を 1 文に分けて書いた。
- 図: 1 は小盤の右下に打った印から、大盤の右下の小盤へ矢印。2 は取られた小盤へ送られ、開いている全小盤に
  枠。3 は小盤の中の 3 つ並びと、大盤の 3 つ並び。図の中に文字は置かない。**どの図も着手の列を規則で再生した
  局面**で(`ui/components/RulesFigure.tsx` の `FIGURE_MOVES`)、印・取った小盤・枠・勝ちラインは列から導く。
  2 は ○ が上中の小盤の縦の中央を取り、その最後の印(上中のマス)が ✕ をその盤へ送り返す 6 手、3 は ✕ が左上・中央・
  右下の小盤を取って斜めがそろう 17 手(○ はどの小盤も取らない)。再生できること・図が言うことを示していること
  (送り先・自由手・勝ちライン)は `RulesFigure.test.tsx` が確かめる(Phase 3 のレビューで、2 の旧図が実戦で
  ありえない局面、3 の旧図が下のマスの無い取った盤だったため直した)。
- 詳細は Landing Page へ。ガイドを公開するまで「詳しく見る」は出さない(`src/ui/landing.ts`)。

## 10. 画面・演出・アクセシビリティ

### 画面の構成

- ゲーム画面は上から: ヘッダ(戻る・題・↻)/ 手番行 / 盤 / Undo。360×640(Web では広告の予約 116px 込み —
  `:root[data-sg-web-ads]`)で、盤・手番行・Undo がスクロールなしに収まること。タブレット・PC では幅を使う。
- **盤の DOM は入れ子である。**盤の外枠(`role="group"`。外枠は `repeat(3, 1fr)` の格子)の中に小盤が 9 個、各小盤は
  `role="group"`(小盤も `repeat(3, 1fr)` の格子)で、その中にマスの `<button>` が 9 個。**DOM の順は §1 の添字の
  順**(小盤 0 のマス 0〜8、小盤 1 のマス 0〜8、…)で、**Tab の順も読み上げの順もこれに従う** — 小盤ごとに
  まとまる(下の「操作」「読み上げ」)。Sudoku のように 81 マスを `repeat(9, 1fr)` の 1 枚の格子に並べる形は採ら
  ない: 打てる小盤の枠・取られた小盤の印・小盤ごとのラベルは、どれも小盤という 1 つの要素に付けたく、平らな格子
  では小盤の位置に別の要素を重ねて位置を合わせることになり、読み上げのまとまりも作れないためである。枠・印・
  勝ちラインの輪郭は、小盤の要素の属性(打てる / 取られた / 引き分け / 勝ちライン)から CSS で描き、別に位置を
  合わせた要素は置かない(下の「盤の見た目」)。
- 盤の一辺は `min(画面幅 − 左右 16px × 2, 他の要素を引いた高さ, 400px)`。小盤の境は 3px の太い線、マスの境は
  1px。**算術では**一辺 328px(360 幅)のときマスは (328 − 3×2 − 1×6) ÷ 9 ≈ 35px(外枠の線を除く)、320 幅
  (一辺 288px)で約 31px。**これは幅だけで決まる場合の算術である。**Web 版には広告の予約 116px があり、盤は幅
  でなく高さで決まりうる(Loop Puzzle は 360×640 + 予約で、幅の算術の 328px でなく 319px になった —
  [LOOP_PUZZLE_RULES.md](LOOP_PUZZLE_RULES.md) §4)。
- **実装の寸法(Phase 3 — 計測では。開発サーバーの Web 版を Chromium で開き、DPR 2・タッチの模擬で測った値。実機では
  見ていない — §13)。**盤の一辺は外枠の 3px を含めて `min(画面幅 − 32px, 画面の高さ − 他の要素の高さ, 400px)`
  (`ui/nested-tic-tac-toe.css` の `--nt-size`。他の要素の高さ `--nt-chrome` は 264px — 上の帯 64・手番行 36・
  すき間と余白 22・Undo の帯 77 の 200px に、アプリの `BannerSlot` が `.game-content` の中に取る 64px を足した値。
  バナーの欄の無い Web 版で広告の予約がある場合は 200 + 116 = 316px)で、マスは (一辺 − 外枠 3×2 − 小盤の境 3×2 − マスの境 1×6) ÷ 9。360×640 の広告の予約なしでは一辺 328px・
  マス約 34.4px、**広告の予約ありでは高さで決まって一辺 324px・マス 34px**(手番行・盤・Undo が文書の高さ 640 の
  まま収まり、Undo の下端は 524px = 640 − 116)。320×640(予約あり)では幅で決まって一辺 288px・マス 30px で、
  スクロールなし。幅 600px 以上では上限を 520px にする(768×1024 で一辺 520px)。高さは `svh` を読める
  ブラウザでは `svh` で読む(幅 600px 以上の規則でも — 動的なツールバーのあるタブレットや横持ちで Undo が
  見える範囲の外へ押し出されないため)。
- **アプリ(ネイティブ)の高さは測っていない。**上の計測はどれも Web 版で、バナーの欄は出ていない。`--nt-chrome`
  にバナーの 64px を含めたのは**算術では**: 360 幅で盤が幅で決まる 328px のままでいられる WebView の高さは
  264 + 328 = 592px 以上で、それより低い端末(システムバーを残した 640dp の電話は CSS の高さが約 568〜592)では
  盤が高さで縮み、盤の欄の中でスクロールして盤の下端が切れることは無い — はずだが、端末では見ていない。バナーを
  外した場合(`BannerSlot` が出ない)は、高さで決まる画面で盤が 64px ぶん控えめになるだけである。Phase 3 の
  レビューで、Web だけを測ったために 200px がバナーを数えていなかったことが分かって直した。
- **盤には下限がある**: マスは 30px より小さくしない(CSS の `--nt-floor` = 9 × 30 + 18 = 288px。境の線 12px に
  外枠の 6px を足した一辺。コードの定数として決めた値で、320 幅の幅だけの算術の約 31px を下回らない最小)。高さが足りない画面(横持ちの
  640×360 など)では盤を縮めずに、画面がスクロールする(Web では広告の予約を含めてページが、アプリでは盤の欄が
  縦に — LOOP_PUZZLE_RULES.md §13「大きさ」の形)。下限が無いと高さだけで縮み、横持ちの 640×360 で盤が 39px に
  なって操作できなくなった前例がある(Loop Puzzle、同 §4)。**360×640 では下限に当たらず、スクロールなしに
  収まる**ことを Phase 3 で測った(上)。横持ちの 640×360(予約あり)では、盤は下限の 288px・マス 30px のままで、
  ページが縦にスクロールする(文書の高さ 603px — 計測では)。

### 盤の見た目(色だけに頼らない)

- 印は形(✕ = 斜めの 2 本、○ = 輪)で、CSS / インライン SVG で描く。アセットは足さない。自分の印は
  アクセント(海老茶 `#633b36` / ダーク `#c3a59d`)、CPU の印はインク(`--ink`)。形が違うので色だけに
  頼らない。計画の本文は CPU を「このゲームの第 2 色」としていたが、Phase 1 のアクセント選定の記録が
  「相手 = インク」で見込みを立てているので、そちらに揃えた(第 2 色を足さない — §16)。
- **打てる小盤**(自分の手番で、送られていればその 1 つ、自由手なら未決の全部)は、**形で示す: 小盤の縁の内側に、
  アクセントの輪(2px)を、太い境の線(3px)との間に 2px のすき間をあけて描く — 二重の枠**。打てない小盤は境の
  線 1 本だけなので、**線の本数(二重か 1 本か)が形の手がかり**で、色を取り除いても(グレースケールでも、
  インクに近いダークのアクセントでも)見分けられる。`--accent-soft` の地は補助である。CPU の手番には枠も地も
  出さない。輪は小盤の要素の疑似要素(`pointer-events: none`、読み上げの対象外)で、外周のマスの縁に重なるが、
  印はマスの 6 割までに収めるので輪に触れない(算術では 31px のマスで、印の両側に約 6px 余る)。
- **取られた小盤**には、取った側の印を小盤いっぱい(約 8 割)に重ねて描き(小盤の要素の子の SVG。`aria-hidden`、
  `pointer-events: none`。SVG の箱が小盤の 80% で、印はその箱の縁まで — `NestedMark` の `big`。**算術では**外形が
  箱の約 98%、小盤の約 79%。マスの印と同じ形を箱に入れていた最初の実装は約半分で、Phase 3 のレビューで直した)、下のマスは薄く残す(経緯が見える)。**引き分けの小盤**は印を重ねず、マスを薄く
  するだけ — 9 マスが埋まっていることが形の手がかりになる。
- **大盤の勝ちライン**は、3 つの小盤を輪郭で囲み(各小盤の要素に付ける輪郭)、他を薄くする(Connect Four §10 の形)。
  1 手で 2 本が同時に完成したとき(例: 中央の小盤を取って行と斜めがそろう)は、`LINES` の順(行 → 列 → 斜め)で
  最初の 1 本だけを囲む(`engine.ts` の `winningLine`。Connect Four の `lineThrough` も最初に見つけた 1 本を返す)。
  勝ちは勝ちで、2 本目を囲まなくても結果は変わらない。
- **最後の手**のマスには小さな印(マスの下辺の短い棒)を付ける。CPU の手を見失わないため(Reversi §11)。
- アクセントのダーク `#c3a59d` は 56 色中 2 番目に静かで、インクとの差が小さい(計画「Phase 1 の実施結果」)。
  自分と CPU の印は形で分かれるが、ダークで自分の印が薄く見えないかと、打てる小盤の二重の枠が判別できるかを、
  Phase 3 のグレースケールとダークの撮影で見た(§13)。
- **勝ちラインの外の小盤は、印だけを薄くする**(Phase 3 で決めた)。小盤そのものを半透明にすると、下の太い線の色が
  透けて、ダークでは薄くした小盤のほうが明るく — 目立って — 見えた(Chromium の撮影)。

### 操作

- マスは `<button>`。押せるのは打てるマスだけで、ほかは `disabled`(フォーカスも当たらない)。タップ・
  クリック 1 回で打つ(§2)。キーボードは **Tab で打てるマスだけに止まり、順は DOM の順 = §1 の添字の順**(小盤ごとに
  まとまる。送られた盤があれば、止まるのはその盤の中だけ)、Enter / Space で打つ。Undo は Ctrl/Cmd+Z
  (`useGameKeys`。Reversi / Checkers と同じ)。矢印キーの移動は作らない(盤面 4 本と同じ)。
- ドラッグは無い(足すなら `src/test/pointerContractWiring.test.ts` の配線が要る)。

### 読み上げ

- 盤の外枠と各小盤は `role="group"` で、読み上げの順は DOM の順(上の「盤の DOM」)。各小盤のまとまりのラベルは
  「小さな盤 n: 未決 / あなたが取った / CPU が取った / 引き分け(閉じている)」で、**自分の手番に打てる小盤は
  「小さな盤 n: 未決、ここに打てる」**(`nestedTicTacToeSmallPlayable` / `en`: Small board {board}: open, play
  here)。手番行の「枠の盤に打つ」の枠は見た目だけの手がかり(CSS の疑似要素)なので、耳で聞く人には、まとまりの
  ラベルがその枠に当たる語を言う(WCAG 1.3.3 — 感覚的な特徴だけに頼らない)。手番行の文は変えない(送られた盤の
  番号を手番行で言う案もあったが、枠と語の両方が既にあるので文を 1 つに保った — Phase 3 のレビューで決めた)。各マスは「小さな盤 n・マス m:
  空 / あなたの{印の名} / CPU の{印の名} / ここに打てる」の形で読む(n, m は 1〜9 で左上から読む順。印は先後で
  入れ替わる)。「小さな盤」は §12 の用語集の「小盤」の `ja` の語で、他の言語もその言語の用語集の語を使う。
  `{印の名}` は §12 の用語集の「印」(`en` は cross / circle)で、✕ ○ の文字は読み上げ名に使わない(文字の名は
  スクリーンリーダーが別の語で読む恐れがある — 未検証)。盤の縁に座標の文字は置かない(盤面 4 本と同じ)。

### 演出と音

- 置いた印は 120ms のポップ(Reversi §11 の置いた石と同じ桁)、小盤を取る印は 200ms のフェードで重なる。
  要素は増やさない — 粒子も画面揺れも無い。
- Reduced Motion(アプリ設定または OS)ではどちらも無効で、印は置かれた状態で描く。
- **決着してから結果カードが出るまでに約 1 秒置く**(`ui/useResultReveal.ts`、`RESULT_REVEAL_MS` = 900)。
  最後の手と大盤のラインを見る時間であり、その間に押せるものは無い(手番行は空 — 上)。Reduced Motion では即時。
- **時計を出さない。**経過時間は統計にだけ残る。
- 効果音は `services/sound.ts` の既存の合成音だけ: 着手で `select`、その手で小盤を取ったときは `select` の後に
  `match`(Reversi の返りと同じ形)、Undo で `undo`、勝ちで `clear`、負け・引き分けで `gameOver`。無効な操作
  では鳴らさない(そもそも押せない)。設定に従う。

## 11. 意図的な差分

**ブランド原則により合わせないもの**

- **Undo・強さの解放を広告や課金に結び付けない。**難易度は最初から全部選べる。
- レーティング・ランキング・オンライン対戦・対人戦は無い。記録は端末の中だけにある(§7)。
- デイリーやストリークで毎日呼び戻さない。時計・持ち時間は無い。

**設計判断として合わせないもの**

- **変種の規則を採らない**(§14): 取った小盤の数で引き分けを割らない(§3)。取られた小盤の残りのマスには
  打てない(§2)。規則を 1 つに絞り、設定で切り替えさせない — 片方だけが正しいなら、選ばせるのは責任の転嫁で
  ある(Gomoku §11 と同じ判断)。
- **早仕舞いの引き分けを作らない。**どちらも大盤のラインを作れなくなった後も、全小盤が閉じるまで打つ(§3)。
  終局の条件を規則 1 つ(全小盤が閉じる)に保ち、「もう勝てない」の判定を規則に足さない。**ただし、結果を
  変えられない手にもタップと判断を求めるので、PRODUCT_PRINCIPLES の物差し(操作・判断を減らすか増やすか)では
  増やす側である。**製品オーナー向けの選択として、代案つきで §16 に置く。続ける手が退屈かはプレイテストで見る
  (§16)。
- **Hint・評価バー・棋譜・投了・引き分けの提案を作らない**(§6)。
- **最強 CPU を作らない。**hard は上限付き探索で止め、定石や終盤のデータベースを積まない(§4、issue #26)。
- **2 度タップにしない**(§2)。算術では 320 幅のマス(約 31px)が Gomoku の交点の間隔(約 19px)の約 1.6 倍あり、
  誤操作は Undo で戻せる。
- **盤のサイズは 3×3 の 3×3 だけ。**4×4 などは別の遊びになる(Connect Four「盤面サイズは 7×6 だけ」と同じ判断)。

**盤面 4 本との意図的な違い**

- 保存が盤の文字列ではなく着手の列(§8)。最後の手が無いと送り先が分からないため。
- **再開後も Undo できる**(§5)。列から追加の保存なしで戻るので、「Undo は無制限」をそのまま守る。
- CPU の印の色がこのゲームの第 2 色ではなくインク(§10)。

この文書で足した判断(計画に無い、または計画の中で食い違っていた点):

  操作・判断・通信・待ち時間・中断を減らすか、増やすか」では、操作を増やす側である。**採った理由**: 終局の条件が
  規則 1 つで済む。**代案**: 8 本の大盤のラインのすべてが、引き分けの小盤を含むか、両者の取った小盤を両方含む
  ようになった時点で引き分けにする。判定は取った小盤と引き分けの小盤だけから決まり、探索ではないが、終局の
  条件が 2 つになる。**プレイテストの条件は維持する**: 終盤が退屈と分かれば、規則の変更として改めて諮る。
- **Quick Rules の 2 と 3 の文面**(§9)を計画の文案から直した。
- **添字は小盤優先**(§1)、保存は `moves` の数の列(§8.1)、`nt.prefs` のキー名は `playerGoesFirst`(§8.4)。
- **保存キーが入る順**(§8): `nt.saveGame` と `nt.prefs` は `gamePersistence.ts`・`entry` の配線・SchemaDef と同じ
  コミット(Phase 3)で入れる。計画の「保存の節と同じコミット」から外れる(`saveGame` だけ先に足すと
  `shortcutResumeWiring` が落ちるため)。
- **探索の取り決め**(§4.1): 根の手を 1 つずつ全幅の窓で探索し、前の反復の最善手を先頭に回さない。ノードの
  カウンタは CPU の 1 手につき 1 本で、反復をまたいで累積する。手の順序は ① 小盤を取る手が ③ に優先する。
- **盤の DOM は入れ子**で、Tab と読み上げは小盤ごとにまとまる(§10)。**打てる小盤は二重の枠**で形として示し、
  **マスは 30px を下限**とする(§10)。新しい対局の先後は、どこから始めても `nt.prefs` から読む(§1)。
- **商標とストアの検索**(§14)は、ネットワークが使える環境で行うまで確認待ち。結果が悪ければ製品オーナーに
  戻す。

**Phase 3 の実装で決めたこと**(この文書が決めていなかった点):

- **CPU のタイマーはバックグラウンドの間は張らず、戻ったらタップなしに張り直す**(§4)— **共通要件からの外れで、
  製品オーナーの確認待ち。**effect はセッション・画面に加えてページが見えているか(`visibilitychange`)を依存に
  取り、隠れたら cleanup で外し、戻ったら同じ 450ms で張り直す(`state/GameContext.tsx`)。共通要件の全文は
  「時間で進むものはバックグラウンドと Back で止まり、**復帰しても勝手に再開しない**」で、前半(止まる)は守るが、
  後半には当たる: 復帰の後、プレイヤーが何も押さなくても CPU が 1 手打つ。GAME_LIFECYCLE.md「CPU 探索」も、探索は
  明示的なタップのときだけ走り、例外はショートカットの再開 1 つ(「タップの代わり」ではなく「タップの続き」)と
  書いており、**バックグラウンドからの復帰はその一覧に無い新しい起点である。** **採った理由**: 手番は
  プレイヤーの着手(タップ)の後ずっと CPU にあり、張り直すのはそのタップが張った 1 本のタイマーで、ショート
  カットの再開と同じ「タップの続き」と読める。盤面 4 本(Reversi など)は effect が可視を読まないので、バック
  グラウンドに入る前に張ったタイマーを外さない — **コードを読む限り**、いつ着地するか(Web では隠れている間に
  間引かれて着地しうる、アプリでは WebView が戻ったとき)は環境次第で、戻った後にタップなしで打つ点は同じであり、
  このゲームのほうが厳しい(隠れている間には決して打たず、戻ってから必ず 450ms 置く — 端末では見ていない)。
  **代案**: (a) 盤面 4 本に合わせて可視でタイマーを外さない、(b) 復帰後は手番行を「CPU の番」のまま止めておき、
  盤へのタップで張る(共通要件の後半を文字どおり守るが、「CPU の番」なのに押せるものが要る)。統合で、
  GAME_LIFECYCLE.md「CPU 探索」の例外の一覧に「バックグラウンドからの復帰で CPU の応手を張り直す(Nested
  Tic-Tac-Toe)」をショートカットの再開と並べて書くか、(a) に戻すかを決める(下の一覧)。
- **結果カードの事実のラベル**は「あなたの盤」「CPU の盤」「難易度」(`en`: Your boards / CPU boards / Difficulty。
  難易度はシェルの `difficulty` の語。`ja` の訳は「あなたが取った盤」「CPU が取った盤」— §12)。カードには Reversi の対戦成績の注記を置かない(§10 の事実は 3 つだけ)。
