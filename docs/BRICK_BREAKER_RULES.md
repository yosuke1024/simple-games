# Brick Breaker — 正式ゲームルール

このドキュメントが Brick Breaker の仕様の正本である。コードはここへ `§n` で
言及する。挙動を変えるときは、同じコミットでこの文書を直す。

## 1. 盤面

- 論理盤面は 360×640。8 列のブロックが上部に積まれる。
- 配置はレベル番号とシード `BOARD_SEED`(`game/constants.ts`)から決定的に
  生成される(`game/generator.ts`)。全プレイヤーが同じレベルで同じ壁を見る。
  ゴールデンテスト(`game/compatibility.test.ts`)が配置を固定しており、
  変更は事故ではなく決定でなければならない。
- 行は中央列で左右対称に生成される。狙う価値のある「形」に見せるため。

## 2. 終了条件

- **クリア**: すべてのブロックを壊す。
- **失敗**: (a) 最後の球を落としてライフが尽きる、または
  (b) 生きているブロックが 1 つでも下限線(§6)に達する。
- 終了はエンジン(`game/engine.ts`)の `status` 遷移として一度だけ起きる。

## 3. 操作

- パドルはドラッグ追従(指の x 座標に一致)と ← → キー(A / D も同じ)の
  両対応。
- タップ / Space で待機中の球を発射。
- 反射角はパドルの当て位置で決まる: 中央で真上、端に寄るほど急角度
  (最大 ±60°、`MAX_BOUNCE_ANGLE`)。これがこのゲームの照準である。

## 4. 球と加速

- ブロックを 1 つ壊すごとに球は少し速くなる(`game/levels.ts` の
  `speedPerBrick`)。盤面が空くほど楽になる、を打ち消すための中核レバー。
- 速度には上限がある(`maxSpeed`)。飛行中の球にも加速は即時反映される。

## 5. ボールブロック

- 枠だけで描かれたブロックは、壊すと球を 1 つ放出する(最大 3 球)。
- 球を 1 つ失ってもライフは減らない。**最後の 1 球を失ったときだけ**
  ライフが減り、球はパドル上に再装填される。
- 配置上、ボールブロックは山の下半分に置かれる。届くこと自体が小さな
  目標になるように。
- 無料・面内で完結・持ち越しなし・上限あり。広告や課金に将来も接続しない
  (docs/PRODUCT_PRINCIPLES.md)。

## 6. 壁のせり下がり

- 生きている壁全体が毎秒数 px 下がる(`descentSpeed`、レベルで増加)。
- パドル上方の下限線に生きたブロックが触れたら、ライフに関係なく失敗。
- **時計を出さないための設計である**: 数字のカウントダウンも点滅もなく、
  盤面そのものが残り時間になる。人工的な緊急性(ストリーク・エナジー・
  期間限定)とは別物として整理する(docs/PRODUCT_PRINCIPLES.md)。
- 全球がパドル上で待機している間(発射前)はシミュレーションを進めない。
  **狙っている時間は無料**であり、壁もその間は止まる。

## 7. レベルと難易度

- レベルは 100(`LEVEL_COUNT`)。クリアで次が開放され、既クリアの
  レベルはいつでも再挑戦できる。開放の最前線が戻ることはない。
  最後のレベルをクリアすると最前線は 101 に進む — そこでは「開放」ではなく
  「全部クリアした」を意味し(Bubble Pop と同じ持ち方)、ホームの Levels チップの
  `n/100` が 100/100 に届く。ホームのボタンとレベル選択は 100 を指し続ける。
- 難易度レバーは `game/levels.ts` に集約: 行数・密度・ボールブロック数・
  パドル幅・初速・加速量・せり下がり速度。**すべて level に対して連続で、
  100 まで飽和しない**(エンジンテストが固定)。
- レベル番号は 1..100 にクランプされ、外挿しない。

## 8. 助けの形(Undo / Hint を作らない)

- Undo は作らない: リアルタイムの盤面に「一手戻す」は存在しない。
- Hint は作らない: 盤面は完全に見えており、隠れた情報がない。
- 代わりの助けは **即時・無料・同一盤面のリトライ**である。失敗した壁は
  次の挑戦でも同じ壁で、覚えたことがそのまま効く。
- 広告視聴や課金による救済(コンティニュー・追加ライフ)は作らない。

## 9. 統計

- `played`(挑戦数)・`cleared`(クリア数)・`totalPlaySeconds` のみ。
  スコアは持たない(§13)。ストリークなし。
- プレイ時間は盤面が動いている間だけ数える。発射前の照準時間は含めない。
- 計上は逐次(bookedRef 方式): バックグラウンド移行・画面離脱・終了の
  各時点で確定秒を加算する。OS がアプリを殺しても計上済みの時間は残る。

## 10. 中断と再開

- **途中保存は作らない。** リアルタイム盤面の復元は、復元した瞬間に
  球が降ってくる「保存」にしかならず、正直な再開ではないため。
- バックグラウンドではループを完全停止する(ポーズ)。復帰すればその場から
  続く。ゲーム画面から離れた場合、その挑戦は破棄される(リトライは無料)。
- 統計・進行(§9)は常に保存され、破棄されるのは挑戦中の盤面だけである。

## 11. Quick Rules(アプリ内チュートリアル)

3 ステップ・図中心・各 1 文(初回起動時に表示、以後はホームから):

1. パドルで狙う — 中央は真上、端は急角度。
2. 枠だけのブロックは球入り — 最後の球を失ったときだけライフが減る。
3. 壁は少しずつ下がる — 点線に触れる前に全部崩す。

詳細は Landing Page(`https://pixapps.ai/simple-games/games/brick-breaker/<locale>/`)へ。
チュートリアルの「詳しく見る」から開く。オフラインでは何も起きない(ゲームは止めない)。

## 12. 演出とアクセシビリティ

- 壊れたブロックは 150ms かけて縮みながら消える。要素は追加しない —
  すでにある物が時間をかけて消えるだけ(粒子・フラッシュ・画面揺れなし)。
- Reduced Motion(アプリ設定または OS)では消滅演出をスキップする。
  ゲームプレイ自体のリアルタイム性は演出ではないため対象外。
- **最後のブロックが消えて(または最後の球を失って)から結果カードが出るまでに約 1 秒置く**
  (`ui/useResultReveal.ts`)。空になった壁(または止まった盤面)を見る時間であり、その間に押せるものはない。
  Reduced Motion では従来どおり即時に出す。
- 効果音は既存の合成音(services/sound)のみ。設定に従う。
- canvas の色は共有アクセントトークン(`data-game`)から読む。テーマ変更に
  即時追従する。shadowBlur / ctx.filter は使わない(低スペック床)。
- 下限線は細いヘアライン+わずかな陰で描き、警告灯にはしない。
- ループはゲーム画面が見えている間だけ回る。決着後・バックグラウンド・
  アンマウントで停止する(低消費電力原則)。
- **盤の大きさ**(2026-10-30): 盤(`.bb-canvas`、描画は 9:16)は幅 336px なら高さ 597px を求めるが、短い画面では盤
  に残る高さが足りず、`max-height: 100%` が箱を高さだけ切り詰めて、描画を縦に押しつぶしていた。画面 360×640 で
  は、Android エミュレータのアプリ(ノッチ 37px・下端 24px)で 336×435(バナーの枠 64px)/ 336×409(枠 90px)— 縦に約
  27% / 32% つぶれ、広告で枠が伸びるとさらにつぶれた —、広告を削除したアプリを模すと 336×523(約 12%)。Web ビルド
  (ヘッドレス Chromium)では、広告の予約がないと 336×560、予約があるとページが伸びて盤が 336×597 になり、盤の下
  145px が予約(116px)の上端より下に出ていた(パドルは盤の下から 36/640 の位置)。スマホのブラウザはバーのぶん縦が
  短いので、背の高い端末でも同じことが起きていた(390×664 で、予約なしは 360×584、予約ありは盤の下 164px が予約の
  上端より下。412×780 でも予約ありで 48px)。いまは盤の幅を「(画面の高さ − 盤以外の縦の並び − 上下の端)× 0.5625」
  でも抑え、ふつうの状態では `max-height` が効かないようにしている(式は `ui/brick-breaker.css` の
  `.bb-canvas`)。盤以外の縦の並びは定数 `--bb-chrome` = 84px(上部バー 64 — 14 言語とも同じ — と本体の余白 16 の
  80px に、余裕の 4px)。上下の端はノッチ(上端の safe area)と、画面の下が確保する高さ `--bb-reserve` の和で、後者
  はアプリでは枠の最悪値 `--sg-app-banner-reserve`(90px + 下端の safe area)、Web 版で広告の予約があるときはその
  116px + 下端の safe area、広告を削除したアプリと予約のない Web 版では下端の safe area。どの場合も、その高さは
  盤の下の何かが空ける — 枠とその下の余白、Web の予約の余白、どちらも無いときはプレイ画面自身の下の余白
  (`ui/styles.css`、2026-10-31 から)。それまでは最後の場合だけ盤の周りの何も下端の safe area を空けず、canvas が
  その高さを下の余白(`--bb-unheld`)として持っていた。持たないと、中央に置かれた盤が safe area にかかる(画面
  360×640 の 24px のジェスチャー領域に 2px、48px の 3 ボタンのナビゲーションバーなら 14px。直す前の 336×523 は
  16px — どれも寸法からの計算で、ヘッドレス Chromium で再現した)。下の余白を持った箱を中央に置くのと、その高さだけ
  低い領域の中央に置くのは同じなので、画面へ移しても盤の大きさと位置は変わらない。上部バーが余裕を超えて高くなった
  とき(OS の大きい文字)は、`max-height` が箱を超えたぶん縦に縮め、中央の盤は上部バーにはみ出さない。幅 600px 以上の段も、
  Web の高さの項(230px / 210px)を上限に残したまま同じ予算を 1 項足した。Web の広告ありでこれが効くのは上下の
  safe area の和が 10px(900px 未満と縦向きでは 30px)を超えるときだけで、iPad の横向き(下端 20px)では広告ありの
  ページが画面より 6px 長く、そのホーム画面の Web アプリ(上端 24px も)では盤が予約に 22px 入っていた。直した後の
  盤は、アプリの画面 360×640 で枠が 64px のときも 90px のときも 227.8×405、広告を削除したアプリで 278.4×495(下端
  は safe area の 10px 上)、画面 411×700 でそれぞれ 260×462・310.6×552、画面 411×914 ではどれも 360×640(直す前と
  同じ)。Web ビルドは 360×640 で予約ありなら 247.5×440(盤の下端 514px、予約の上端 524px より上)、予約なしなら
  312.8×556、390×664 で 261×464 / 326.3×580。390×844・412×915 と、safe area のない幅 600px 以上(2560×1440 まで)
  は予約あり・なしとも公開版(pixapps-landing `dcb9a887`)と同じ箱で、safe area のある予約なしの画面は大きさが同じ
  まま、盤が safe area の半分だけ上がる。測ったどの大きさでも盤は 9:16 のまま予約(予約がなければ下端の safe
  area)の約 10px 以上上に収まり(Web ビルドはどれも 10px 以上、エミュレータの 411×700 は 9.8px)、ページはスクロー
  ルしない。アプリでは(上部バーが定数に収まっている間は)広告で枠が伸びても大きさも形も変わらず、動き得るのは位置
  だけである(docs/ADS_POLICY.md「バナー広告の仕様」)。代わりに、背の低い画面では盤が小さくなる(アプリの 360×640
  で幅 336px → 約 228px、Web 版の 390×664 で予約ありなら 360px → 261px)。CSS だけの変更で、論理盤面(§1)とルール
  は変わらない。広告を削除したアプリはエミュレータで属性を外し枠を隠して模した。上部バーはヘッドレス Chromium で
  14 言語・100 面目の表示とも 64px(幅 280〜360px)。OS の大きい文字で上部バーが余裕を超えると、アプリと予約のな
  い画面では盤が超えたぶん縦に縮み、Web 版の広告ありではページが伸びて盤が予約にかかる(上部バーの文字を 2 倍にし
  た模擬の 360×640・safe area 24 / 48 で 25px。公開版は 254px)。実際の広告・実機のブラウザ・iOS・実機での他の言
  語では確かめていない。

## 13. 意図的な差分

- **スコアなし**: このゲームの達成は「壁を崩し切ったか」。数字を足すと
  角度当ての面白さが点数稼ぎに置き換わるため、v1 では持たない。
- **デイリーなし**: v1 では見送り。生成はシード決定的なので、必要になれば
  water-sort と同じ形で後から足せる。
- **途中保存なし**(§10)・**リトライ確認ダイアログなし**(挑戦は数十秒で、
  失うものが小さいため)。
- ホームの「あと n 回」等の煽り表示は作らない。
