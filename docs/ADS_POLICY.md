# Simple Games — 広告ポリシー

## 適用範囲

**「基本方針」から「同意(UMP)」までは Android アプリの広告について定める。**
同じソースから配信するブラウザ版(`https://pixapps.ai/simple-games/play/`)は
役割が違い、広告方針も別 — 本文書末尾の「[Web 版](#web-版pixappsai)」節が定める
(役割分担と配信構成は [WEB_VERSION.md](WEB_VERSION.md))。下の「禁止する広告
フォーマット」は**アプリの禁止事項**であり、Web 版はディスプレイ・アンカー・
Vignette を制限付きで用いる(2026-07-31 決定)。

版をまたいで例外なく成立するのは次の 1 点である: **広告視聴や課金でゲーム機能を
解放しない。** どちらの版でも、Hint / Undo / Continue を広告や支払いの対価にしない。

## 基本方針

- 使用する広告は **Anchored Adaptive Banner のみ**(画面下部・オンライン時のみ)。
- **広告はゲーム機能の解放条件にしない。** Hint / Undo / Add Numbers / Continue を
  広告視聴の対価にしない。
- オフライン時は広告を表示せず、**広告リクエスト自体を行わない**
  (リトライループも作らない — 低消費電力、OFFLINE_POLICY.md)。
- 広告取得を待たせるローディングを作らない。広告・同意処理のあらゆる失敗で
  ゲームを止めない(失敗は静かに握りつぶし、ログのみ)。

## 禁止する広告フォーマット(アプリ)

以下は初期リリースに限らず**アプリでは今後も採用しない**。「未使用」ではなく
「不在」であること — アプリのビルドにこれらのコードが含まれないこと — が約束であり、
CI の原則ガードが `apps/*/src` を走査して検証する。

- Interstitial / Rewarded / Rewarded Interstitial / App Open / Native 広告
- ゲーム盤・操作領域に重なる広告
- ゲームの進行を止める広告
- 広告視聴による機能解放・報酬(**これは Web 版でも禁止**)

## バナー広告の仕様

- Anchored Adaptive Banner をゲーム画面下部に置く。ゲーム盤・操作ボタンに重ねない。
  広告と操作領域の間に余白を設ける。Safe Area を考慮。
- **レイアウトシフト防止方式**: 「広告領域を常に確保する」方式を採用する。
  ネイティブ環境でバナーが有効な場合、画面下部に固定高のスロット(`BannerSlot`)を
  画面表示時から確保し、以後この高さを縮めない(実広告の高さがスロットを超える場合のみ
  拡大を許す)。広告が取得できない間・オフライン時は静かな空き領域のままにする。
  盤面は決して動かない。
  比較検討: 「表示前にレイアウト確定」案はロード完了時点で盤面が動くため不採用。
- AdMob の初期化は起動後の fire-and-forget。完了を UI 描画・ゲーム開始の条件にしない。

## 広告削除の買い切りとの関係

- 「Remove Ads & Support Simple Games / 広告を削除して Simple Games を支援」
  (基準価格 USD 3.99、一度だけ、サブスクではない)を購入すると、
  バナーを永久に表示しない。**スロットごと取り除く**(空き領域も残さない)。
  将来追加されるゲームにも適用。購入復元あり。
- 購入済み状態は端末内キャッシュ(`sg.iap`)で判定し、オフラインでも有効。
  購入済みなら広告リクエストを行わない。
- ゲーム機能は無料ユーザーと完全に同一。広告の有無だけが変わる。

## 文言と導線(静かに、正直に)

- 広告・購入への言及は謝罪調・強制調にしない。事実だけを静かに述べる。
- 初回起動時に購入ダイアログを出さない。購入を繰り返し促さない。
  導線は設定 / About の「Remove Ads & Support Simple Games」行に置く。
- 説明文の正文:

英語:

> Simple Games is supported by a small banner ad while you're online. It helps
> us maintain and improve the app. Prefer no ads? A single $3.99 purchase
> removes them permanently.

日本語:

> Simple Gamesでは、アプリの維持と改善のため、オンライン時のみ小さなバナー広告を
> 表示しています。広告を表示したくない場合は、$3.99相当の一度だけの購入で永久に
> 削除できます。

## 広告 ID の管理

- 開発環境では Google 公式のテスト広告 ID のみ使用する
  (`VITE_ADMOB_USE_TEST_ADS` で明示的に切り替え可能)。
- 本番広告 ID はコードへ直接埋め込まず、ビルド時に環境変数で注入する。
  - バナー広告ユニット ID(Web 側): `VITE_ADMOB_ANDROID_BANNER_ID` /
    `VITE_ADMOB_IOS_BANNER_ID`。未設定の場合、広告は表示しない
    (ゲームは通常動作)。
  - AdMob アプリケーション ID(ネイティブ側): Android は `ADMOB_ANDROID_APP_ID`
    (Gradle manifestPlaceholder)、iOS は `ADMOB_IOS_APP_ID`(Xcode のビルド設定 →
    `Info.plist` の `GADApplicationIdentifier`)。どちらも未設定ならその OS の
    テスト用 app ID にフォールバックする。
- **ID の名前にはプラットフォームを含める。** AdMob のアプリ ID・ユニット ID は
  OS ごとに別であり、`ADMOB_IOS_*` は Android の名前を使い回さずに並んでいる。
  **選択は実行時に `Capacitor.getPlatform()` で行う**(`services/ads/banner.ts`)。
  ネイティブの JS バンドルは 1 つを両 OS へコピーする作りなので、「iOS ビルドに
  Android の ID が含まれない」ことはリリースレーンが片方しか注入しないことで、
  「iOS が Android のユニットを**配信しない**」ことはこの実行時分岐で守る
  (後者を `banner.test.ts` が検査する)。
- テスト広告 ID も OS ごとに別である(Google 公式のアダプティブバナー用を各 OS で
  使う)。ここを共有すると、テスト中だけ通って本番で別 OS の在庫を引く。
- インタースティシャル用の ID・シークレットは存在しない。

## 同意(UMP)

実装は `src/services/ads/consent.ts`(バナー本体とは別モジュール。答える問いが
違う — こちらは「リクエストしてよいか」、`banner.ts` は「出したいか」)。

- 広告同意が法的に必要な地域では UMP の同意フォームを表示する。
- **UMP が `canRequestAds` を真と答えるまで広告をリクエストしない。**
  同意が取れないことは「同意なしで広告を出す」ではなく「広告を出さない」に倒す。
- 同意処理はゲーム初期化と切り離す。同意フォームの取得・表示の失敗で
  ゲームを止めない・遅らせない。オフライン時は同意処理も行わない。
- **リトライループを作らない。** 試行は 1 起動あたり最大 2 回(起動時と、
  最初にバナーが要求されたとき)。オフラインでの見送りは試行に数えない —
  通信を 1 件も出していないため。オフラインで起動して後からオンラインになった
  回でも広告が出るのは、この 2 回目の枠による。
- **Privacy Options** が UMP から required と返ったときだけ、設定 / About に
  「Ad Privacy Options」の行を出す(`adPrivacyOptions`)。required でない地域では
  行そのものを描かない — 説明のつかない行を並べないため。

### ATT(App Tracking Transparency)を使わない

**iOS で ATT の許可ダイアログを出さない。** `NSUserTrackingUsageDescription` を
`Info.plist` に置かず、`AdMob.requestTrackingAuthorization` を呼ばない。

理由: ATT が必要になるのは **IDFA を使って他社のアプリ・サイトをまたいで
ユーザーを追跡する**場合である。この製品は analytics SDK を native ビルドに
入れず(`check-principles.sh`)、広告はコンテキスト連動のバナー 1 枠だけで、
追跡のための識別子を必要としていない。許可を求めないので IDFA は取得できず、
App Store の「トラッキング」の申告も「しない」で一貫する。

インストール計測は **SKAdNetwork** が担う(`Info.plist` の `SKAdNetworkItems`)。
これは端末が署名済みの集計値をアドネットワークへ返す仕組みで、ユーザー単位の
識別子は端末から出ない — だから ATT なしで同居できる。

**この判断は覆せる。** ATT を出すのは技術的には数行だが、出した瞬間に
「追跡しない」という申告と製品の説明が変わる。変えるなら
[PRIVACY_POLICY.md](PRIVACY_POLICY.md) の公開ページと App Store の申告を
同じ回で直すこと。ATT を導入する場合でも、**拒否がゲーム機能・広告削除の購入・
オフラインプレイに影響してはならない**(拒否は正常系である)。

## ストア表現

広告が存在するため、"Ad-free" / "No ads" 等の表現を使用しない。
広告削除の買い切りが存在するため、"No purchases" / "No in-app purchases" /
「課金なし」の無条件表現も使用しない(BRAND.md 参照)。

## Web 版(pixapps.ai)

`https://pixapps.ai/simple-games/play/` で配信するブラウザ版の広告方針
(2026-07-31 決定、Phase A の技術基盤を 2026-08-02 実装)。上のアプリの各節は
この節の影響を受けない。**版をまたいで例外なく成立するのは 1 点 — 広告視聴や
課金でゲーム機能を解放しない。**

### 形式と場所(2026-08-02 改訂: アンカー常時方針)

- **アンカー(Auto ads)— 常時。プレイ中も出てよい**(2026-08-02 決定。初版の
  「ゲーム中は非表示」を撤回)。Google が画面下端に重ねる形式で、表示の出し入れと
  頻度は AdSense コンソール側にある。**Auto ads で有効にするのはアンカーのみ**
  (ページ内自動配置・Vignette 等は当面すべてオフ)。ユーザーは Google 標準の
  ハンドルで畳める。プレイ体験の約束はレイアウトで守る — 下の「退避余白」参照。
- **ディスプレイ(手動ユニット、固定サイズ)**:
  - ホーム: リスト下 1 枠(320×100 / 728×90 をマウント時に確定)。
  - リザルト画面: **3 局に 1 回だけ**(セッション最初のリザルトには出さない。
    定数は `services/ads/web/resultCadence.ts` の `RESULT_AD_EVERY` の 1 箇所)。
    ダイアログのカードの外側・操作ボタンから離して置き、320×100 固定。
    毎回のリザルトに広告を出すことはこの定数に関わらず禁止。
  - デスクトップのサイドレール: 保留(必要になったら検討)。
- **Vignette(スキップ可の全画面)**: 未実装。前提として書いていた
  「hash ナビゲーション導入後」は、2026-08-30 の `?game=<game-id>` +
  History API 遷移([WEB_VERSION.md](WEB_VERSION.md)「URL(ゲーム別の入口)」)で
  形の上は満たされた —— ただし Auto ads がこの遷移を区切りとして拾うかは
  未検証で、判断は [plans/2026-07-31-web-play.md](plans/2026-07-31-web-play.md)
  M4 のまま。入れるときも条件は変えない: 自然な区切りのみ、最短 15 分間隔、
  初回セッションなし、1 セッション最大 2 回程度。
- **自前のプレイ中バナー枠は作らない**(アンカーと二重の下部バナーになるため。
  唯一の例外は下の「フォールバック」のアンカー代替バー — AdSense が読み込めず
  Google のアンカーが存在し得ないときの代替であり、二重にならない)。
- 出さない場面(割り込み系): 初回訪問時 / ゲーム開始直前 / プレイ途中の割り込み /
  Undo・Hint 操作時 / ゲームオーバー直後の毎回 / ブラウザの戻る操作時。

### 二つのネットワーク(AdSense / 忍者AdMax)— 2026-08-23 改訂

**どちらが配信するかはビルドが持つ ID で決まる**(`services/ads/web/config.ts`)。
実行時のスイッチもアカウント状態の判定も作らない — 判断は人間が公開時に行い、
その結果はビルドログに残る。

| ビルドが持つもの | 配信 |
| --- | --- |
| AdSense client(+ 枠 slot) | **AdSense が主**。忍者AdMax は下の実行時フォールバック |
| AdSense client なし + AdMax 枠 | **忍者AdMax が全面を配信**。Google へのリクエストは 1 件も出ない |
| どちらも無い | 広告なし(広告コードは 1 行も動かない) |

初版(2026-08-18)は「実行時フォールバックのみ」で、AdMax が単独で出ることは
無かった。これを**撤回**した理由は実測に基づく: AdSense の審査が通っていない
状態のローダーは `onerror` も `unfilled` も出さず、空応答(346B・iframe 0×0)を
返すだけで、下の 2 条件のどちらにも当たらない。結果として AdMax の t.js は
1 度も読み込まれず、掲載が検知されないため AdMax 側の審査も始まらなかった
(2026-08-23 に本番で確認)。**「AdSense が使えない」の実体は失敗ではなく沈黙**
であり、沈黙は実行時に判定するより公開時に人間が決めるほうが正しい。

- **枠・頻度・レイアウトの規則はネットワークに依らない**。ホーム 1 枠 /
  リザルト 3 局に 1 回 / 下端のアンカー、固定サイズ、退避余白 — すべて上の
  各節のまま。変わるのは中身を誰が配信するかだけである。
- **アンカーの形だけは違う**: AdSense では Google の Auto ads オーバーレイ、
  AdMax には相当する形式が無いため、画面下端の固定バー(`.web-admax-anchor`)を
  自前でマウントして枠を 1 つ置く。バーは全画面が最初のペイントから確保する
  退避余白(116px + safe area)の内側に収まるため、構造的に操作を覆えない。
  サイズはマウント時にビューポートから確定(728×90 / 320×100)し、以後動かない。
  Google のアンカーが存在し得ない場合にだけ出すので、二重にはならない。
- **AdMax 単独ビルドでは Google に一切接続しない**(ローダーも読まない)。
- **狭い画面のリザルト枠は空のまま**: オーバーレイの余白 48px を引くと 360px 幅の
  端末では 312px となり、選ばれるサイズは 234×60。AdMax にこのサイズは無いため、
  AdSense 不在のビルドでは 368px 幅未満の端末でリザルト枠は出ない。枠を予約して
  から畳むのではなく、**最初のペイント前に畳む**(`AdUnit` の layout effect)。

#### 実行時フォールバック(AdSense 主のビルドでのみ動く)

- **発火条件は 2 つだけ**:
  1. AdSense ローダー(adsbygoogle.js)の読込失敗(`onerror`)。
  2. ディスプレイ枠の `data-ad-status="unfilled"`(在庫なし)。
  上記のとおり**空応答は発火しない**。審査落ち・未承認のときは実行時に粘らず、
  AdMax 単独ビルドで公開する。
- **ディスプレイ枠**: 同じ予約ボックス内で**同サイズ**の AdMax 枠に差し替える。
  AdMax の枠はサイズ固定なので使うのは 728×90 / 320×100 のみ — 234×60 は
  AdMax に存在せず、そのサイズはこれまで通り静かに畳む。差し替えは
  1 マウントにつき一方向(ネットワーク間を行き来しない)。
- **アンカー相当**: ローダー読込失敗のときだけ(Auto ads のアンカーに枠単位の
  unfilled 信号は無い)、上の固定バーを AdMax 単独ビルドと同じ形でマウントする。
- **二段目の失敗は静かに畳む**: AdMax の t.js まで失敗した場合(典型は
  広告ブロッカー)、ディスプレイ枠は unfilled と同様に畳み、アンカーバーは
  取り除く。リトライループは作らない(OFFLINE_POLICY.md と同じ)。
#### 共通の規則

- **ID の管理**: AdSense と同じ規則 — ソースには一切書かず、production ビルド時に
  環境変数で注入する: `VITE_ADMAX_SLOT_HOME_728X90` /
  `VITE_ADMAX_SLOT_HOME_320X100` / `VITE_ADMAX_SLOT_RESULT_320X100` /
  `VITE_ADMAX_ANCHOR_728X90` / `VITE_ADMAX_ANCHOR_320X100`。無い ID は
  その置き場所×サイズが出ないだけ。枠は**置き場所×サイズごとに別に作る**
  (同一枠 ID を 1 ページに 2 回置かない — ホーム枠とアンカーは同時に見える)。
  ローカルでは `.env` ではなく **`.env.web`** に置く(モード名付きの env ファイルは
  そのモードでしか読まれないので、native ビルドが拾えない)。
- **テストモード**: どちらのネットワークにも一切接続しない(ローカルのプレースホルダのみ)。
- アプリとの分離は機械検証:
  `.github/scripts/check-dist-ads-separation.sh` が native 成果物に
  `admax` / `shinobi` の不在、web 成果物に統合の存在を検査する。
  ただし**AdMax の枠 ID は `ca-pub-` のような見分けの付く接頭辞を持たない**ため、
  grep では不在を証明できない。そこで共有モジュール(native にも載る
  `config.ts`)には ID を渡さず、ビルド時定数 `__SG_AD_FRAMES__`
  (`vite.config.ts`、web モード以外では常に全 false)だけを渡す。ID を読むのは
  native から到達不能な `admax.ts` のみで、分離は規約ではなく構造で保つ。
  この定数は**面ごとに 1 つずつ**(アンカー / ホーム / リザルト)である。
  一部の枠だけ設定した状態は正当な設定であり、まとめた 1 つのフラグにすると
  枠の無い面まで「ある」と答えてしまう — 埋まらないアンカーのために余白を
  確保し続けたり、遅延読込のユニットが最初のペイント後に枠を引っ込めたりする。

### レイアウトとオフライン(アプリと同じ原則)

- **退避余白**: アンカーは重なり型なので、web ビルドは**すべての画面の下端に
  固定の余白を最初のペイントから確保**し、盤面・操作ボタンがアンカーに覆われることを
  構造的に不可能にする(`data-sg-web-ads` + styles.css。広告の読み込みで何かが
  動くことはない — `BannerSlot` と同じ規則)。
  確保量は**最悪ケース**で決める: ネイティブの `BannerSlot` と違いサイズ通知が
  無く、実際のユニットは Google が選ぶため。最大は 100px(モバイルの 320×100。
  デスクトップの 728×90 はこれより低い)で、これに広告と操作領域の間隔 16px を
  足した **116px + safe area** を画面に、**140px + safe area**(24px の
  ガター込み)をダイアログのオーバーレイに確保する。オーバーレイは
  `position: fixed` なので画面側の余白を継承しない — 別途必要である。
  テスト用プレースホルダも**最大の 100px** で描く(実際より低いプレースホルダは、
  本番が安全でないのに開発中は安全に見せてしまう)。
- ディスプレイ枠の高さは固定で、枠を出すかどうかはビルド/起動時に確定する。
  読み込み中・取得失敗・オフラインでゲームリストや盤面が動くことはない。
- オフライン時・取得失敗時は静かな空きのまま。**広告リクエストを 1 件も送らず、
  リトライループも作らない**(OFFLINE_POLICY.md と同じ)。広告のあらゆる失敗は
  ゲームを止めない。
- **空振りだったら畳む — 余白ごと**(2026-08-23 決定)。AdMax は AdSense の
  `data-ad-status` に相当する通知を持たず、在庫が無いときも iframe だけは
  書き込む(本番実測: ある表示では Criteo の 0×0 同期フレームだけが入り、
  次の表示では実クリエイティブが入った)。そのため**枠の中身を見て**判定する
  (`adMaxUnitRendered`): 画像も、サイズのある入れ子フレームも、文字も無ければ
  空とみなし、要求から 6 秒後に一度だけ確認して畳む。判定できないもの
  (クロスオリジンの中身など)は**埋まっている扱い**にする — 実広告を誤って
  畳むほうが損失が大きい。
  アンカーが空だった場合は、バーだけでなく**下端の退避余白も解放する**
  (`data-sg-web-ads` を外す)。これは上の「広告の読み込みで何かが動くことは
  ない」の**唯一の例外**であり、意図的な取引である: 何も出ないと確定した後に
  全画面の下端へ無地の帯を残し続けるほうが、一度きりのレイアウト変化より悪い。
  解放後にアンカーが再び現れることはない(そのページ表示中は何もマウントしない)。

### 広告 ID の管理(AdSense)

- AdSense には AdMob と違い**公式のテスト用 client ID が存在しない**。そのため
  テスト表示はローカルのプレースホルダで行い、広告ネットワークには一切接続しない
  (`VITE_ADSENSE_USE_TEST_ADS=true`。dev サーバーでは既定でオン)。
- 本番 ID はビルド時に環境変数で注入する: `VITE_ADSENSE_CLIENT`(client。
  これだけでアンカーが有効になる — アンカーに slot ID は存在しない)と、
  ディスプレイ枠ごとの `VITE_ADSENSE_SLOT_HOME` / `VITE_ADSENSE_SLOT_RESULT`。
  client が無ければ **AdSense** は一切動かない(そのビルドで広告が出るかどうかは
  忍者AdMax の枠次第 — 上の「二つのネットワーク」)。slot が無い枠は AdSense
  では出ない(空箱も確保しない)。
- client / slot ID はテスト用が存在しない以上、**ソースには一切書かない**。
  CI の原則ガード(`check-principles.sh`)が不在を検査する。

### アプリとの分離(機械検証)

AdSense 統合は `vite build --mode web`(成果物 `dist-web/`)のみに同梱され、
既定の native ビルド(`dist/`、`cap sync` が拾う側)には**不在**。この分離は
ソースの規約ではなくビルド成果物で証明する —
`.github/scripts/check-dist-ads-separation.sh` が CI で native 側の不在と
web 側の存在を両方検査する。

### ビルドと切り替え

GitHub Actions「Web build」(workflow_dispatch)が広告モードを選んで成果物を作る:
`test`(プレースホルダ、既定)/ `production`(secrets の AdSense ID)/
`disabled`。Android 側は「Android release」の `ads` input(`production` /
`test`)で同様に切り替える。**配信はどちらも人間の手順のまま**(Play への
アップロード、landing リポジトリの同期)。

### 本番有効化の前提(人間作業 — 完了まで secrets を設定しない)

1. AdSense コンソールでの pixapps.ai サイト追加・審査。
2. Web 版のプライバシー文言(AdSense のクッキー・同意・パーソナライズ広告)を
   公開ページ <https://pixapps.ai/simple-games/privacy> の日英に追記(**実施済み**
   2026-08-02)。アプリはこのページへリンクするだけで、文面を同梱しない。
3. Privacy & messaging(GDPR 同意メッセージ)の設定。
4. 広告レビューセンターで不適切カテゴリのブロック(ゲームは子どもも遊ぶ)。
5. Auto ads の設定で**アンカーのみを有効化**し、ページ内自動配置・Vignette 等を
   オフにする(この設定が済むまで client の secret を入れない — Auto ads の既定は
   全フォーマット有効で、入れた瞬間に約束外の広告が出るため)。
6. フォールバックの忍者AdMax を使う場合はさらに(2026-08-18 に AdMax
   コンソールの実画面で確認した手順):
   - **枠は 5 つ、すべて「インライン」タイプで作る**。AdMax はカテゴリが
     PC サイト向け / スマホサイト向けに分かれ、サイズのラインナップも違う
     (728×90 は PC のみ、320×100 はスマホのみ)ため、対応は次で固定:
     `ADMAX_SLOT_HOME_728X90` / `ADMAX_ANCHOR_728X90` → **PC サイト向け・
     インライン・728×90**、`ADMAX_SLOT_HOME_320X100` /
     `ADMAX_SLOT_RESULT_320X100` / `ADMAX_ANCHOR_320X100` → **スマホサイト
     向け・インライン・320×100**。固定表示系(オーバーレイ・下固定・
     サイドスライダー・インタースティシャル)は**使わない** — 位置は
     こちらのコードが決める(アンカー代替バーも中身はインライン枠)し、
     下固定 300×250 は退避余白 116px を超え、割り込み系は方針違反。
   - **枠ごとの設定**: 「自動リサイズをする」**オフ**(サイズはこちらの
     予約ボックスで固定 — 勝手に伸縮されるとレイアウト約束が壊れる)、
     「オーバーレイ広告を表示する」**オフ**(AdMax 自身に浮かせない。
     **どちらも既定でオンなので明示的に外す**)、サイト属性は一般、
     「アダルト・出会い等の広告を表示しない」**オン**(ゲームは子どもも遊ぶ)。
   - <https://pixapps.ai/ads.txt> に AdMax の行(コンソールの
     「ads.txt を取得」)を追記する(**実施済み** 2026-08-18)。
   - プライバシーページ <https://pixapps.ai/simple-games/privacy> の日英に
     忍者AdMax(運営: 忍者ツールズ株式会社)のクッキー・第三者配信の記載を
     追記してから `ADMAX_*` の secrets を設定する(記載が済むまで secrets を
     入れない — 入れた瞬間に配信経路が生きるため。**実施済み** 2026-08-18、
     AdMax 単独配信への切り替えに合わせて 2026-08-23 に改訂)。
   - **AdMax の枠審査は「掲載の検知」から始まる**。枠を作っただけでは
     「審査中」のまま動かず、実際にタグが読み込まれて広告リクエストが出て
     初めて審査が始まる(2026-08-23 に実測)。AdSense 主のビルドで公開すると
     フォールバックは発火しないため t.js は 1 度も読まれない — AdMax を
     使うなら **AdSense client を注入しないビルドで公開する**(publish
     workflow の `network` 入力)。コンソールに登録するサイト URL も、
     タグが実際に載る <https://pixapps.ai/simple-games/play/> に合わせる。

### 文言(アプリと同じ「静かに、正直に」)

- 広告の説明に「サーバー費用のため」と書かない(静的配信の実態と合わず、
  クリック誘導と取られる表現も禁止)。支援の説明は About 相当の場所にのみ置き、
  特定の広告のすぐ近くには置かない。
