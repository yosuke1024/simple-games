# Simple Games — 成長計測(Web)

**次にどのゲームへ手を入れるかを、記憶ではなく観測で決めるための文書である**
(2026-08-30 決定 / issue #84)。30 本の収録が終わった時点で、本数を増やすより、
実際に需要と継続のある上位ゲームを見つけてそこへ品質を集中したい。その判断を
一人の印象ではなく、いつでも同じ手順で再現できる形にする。

計測の**方針**(何を送る / 送らない、どのビルドに置く)を定めるのは
[WEB_VERSION.md](WEB_VERSION.md)「計測」であり、この文書はその**運用** —
GA4 と Search Console の読み方、判断の手順、そしてこのデータで言えないこと —
を持つ。方針とぶつかったら方針が勝つ。

**アプリには Analytics を入れない。** これは Simple Games の約束であり
([PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md)「適用範囲」)、この文書は
その境界を動かさない。Android / iOS へ SDK・イベント・識別子を足さずに、
Web 版の集計と Play Console の集計だけで次の投資先を決められる状態を作る。

## 答えたい問い

1. 検索で見つかっているゲームはどれか
2. Web 版で実際に開かれているゲームはどれか
3. 開いたあとの滞在が長いゲームはどれか
4. 新規だけでなく、再訪した人にも開かれているゲームはどれか
5. 国・言語・端末種別で需要に差があるか
6. 次に集中して直す上位 3 ゲームはどれか

**Web の結果はアプリ利用の代理ではない。**「ゲーム別の需要を比べるために
観測できる指標」であって、それ以上のものとして扱わない。限界は下の「この
データで言えないこと」に全部書く。

## 送るもの

`--mode web` ビルドだけが送る。native 成果物には 1 バイトも入らない
(CI が成果物で検証 — `.github/scripts/check-dist-ads-separation.sh`)。

| イベント     | いつ                       | パラメータ                                                                 |
| ------------ | -------------------------- | -------------------------------------------------------------------------- |
| `page_view`  | ページ読み込み時           | `content_group` = `simple_games_play` / `content_type` = `game_collection` |
| `game_open`  | ゲームを開いたとき         | `content_group` / `content_type` = `game` / `content_id` / `game_id`       |
| `game_close` | ゲームから一覧へ戻ったとき | 上記に加えて `play_duration_ms` / `engagement_time_msec`                   |

`page_view` は独立したイベントではなく、`gtag('config', ...)` から Google タグが
自動で導く。**明示的な `page_view` イベントを足してはいけない** — 足した瞬間に
ページビューが 2 倍になる。

`game_id` はレジストリの ID(`sudoku` / `kakuro` / `bunny-hop` …)そのままで、
30 本すべてが同じ語彙で並ぶ。`content_id` は同じ値の GA4 側の推奨名で、
Exploration ではどちらを使ってもよい。

## 送らないもの

盤面・配札・手数・スコア・レベル・ヒント回数・デイリーの成績・保存データ・
ユーザー ID・ログイン・広告 ID。**プレイの中身は版をまたいで一切外へ出ない。**
イベントを送るのはシェルだけで(起動時は `main.tsx`、ゲームの出入りは
`app/App.tsx`)、`games/*/game/` は Pure TypeScript のまま計測を知らない。

上の表を増やしたくなったら、まず「その問いは 6 つのうちどれか」を確認する。
先行公開の正式収録判断([WEB_VERSION.md](WEB_VERSION.md)「先行公開」)の
ためにこの範囲を広げない、というのは既に決めてある。

## GA4 の準備(1 回だけの人間作業)

プロパティ / Web ストリームは `pixapps`(測定 ID `G-V1BJW2MQ2D`)。サイト共通の
GA4 と同じ 1 つのプロパティで、play だけを別に持たない。

1. **カスタムディメンション** — 「管理 > カスタム定義 > カスタムディメンション」で
   `game_id` を登録する。範囲は**イベント**、イベントパラメータは `game_id`。
2. **カスタム指標** — 同じ画面の「カスタム指標」で `play_duration_ms` を登録する。
   範囲は**イベント**、測定単位は**ミリ秒**。単位を「標準」にすると平均が
   桁違いの数字として出るので、ここは間違えると気付きにくい。
3. **登録は遡らない。** 登録より前に届いたイベントの `game_id` は探索で使えない。
   だから順序は「受信を確認する → 登録する → 14 日待つ」であって、逆にしない。
4. `engagement_time_msec` は**登録できない**。GA4 の予約パラメータで、
   エンゲージメント計算への入力であって読み戻せる項目ではない。ゲーム別に
   読めるのは `play_duration_ms` だけである。

## 保存する Exploration

「探索」で 1 つ作り、**保存して名前を付ける**(手元でその場限りに組み直さない —
同じ数字を次の月にもう一度出せることが、この文書の目的である)。

- **フィルタ**: `content_group` が `simple_games_play` に完全一致。これで
  ハブ・ガイド・トップのページビューが混ざらない。
- **行**: `game_id`
- **列**: なし(セグメントで切る)
- **値**: `イベント数` / `総ユーザー数` / `play_duration_ms` の平均と合計

| 観点       | 見るもの                                                     |
| ---------- | ------------------------------------------------------------ |
| プレイ開始 | `game_open` のイベント数とユーザー数                         |
| 終了到達   | `game_close` のイベント数とユーザー数                        |
| 滞在       | `play_duration_ms` の平均と合計                              |
| 再訪       | セグメント「Returning users」を当てた `game_open`            |
| セグメント | `国` / `言語` / `デバイス カテゴリ`                          |
| 品質確認   | `game_close` ÷ `game_open`(下の「このデータで言えないこと」) |

**率だけを並べない。** 低母数では率が跳ねるので、どの行も**件数を併記**する。
100 分の 60 と 5 分の 3 を同じ 60% として並べた表は、事実としては正しくても
判断材料としては嘘に近い。

**滞在の数字には必ず `game_close` ÷ `game_open` を並べる。** 滞在は「戻る
ボタンを押した人」だけの数字であり、その比が分かって初めて読める(下の
「このデータで言えないこと」)。比が 1 を超えたら二重送信、`play_duration_ms`
の付いていない `game_close` があれば対応する `game_open` を取り逃している
サインで、どちらも数字より先に直す。

**滞在は平均より中央値で読む。** `play_duration_ms` に上限は無く、平均は
放置タブ 1 つで動く。ゲーム同士を比べるなら中央値、分布を見るなら
上位 25% を別に見る。

**`play_duration_ms` と GA4 のエンゲージメント時間は、互いの裏取りにならない。**
`game_close` に載せる `engagement_time_msec` は自分たちが送った値であり、
GA4 の数字はそれを足したものだからである。ただし GA4 側は `game_close` が
出なかったプレイの前面時間も(タグ自身の計測で)拾うので、**`game_close` が
落ちやすいゲームの取りこぼしはこちらのほうが小さい** — 別の物差しではなく、
欠け方の違う物差しとして併読する。

## Search Console の読み方

ゲーム別のガイドページが検索の入口であり、URL からゲームが読める。

- **URL の形は `https://pixapps.ai/simple-games/games/<game-id>/<locale>/`**
  (`ui/landing.ts` の `gameLandingUrl()` が組み立てている形と同じ)。
  **`<game-id>` が先、`<locale>` が後**である — issue #84 の本文は
  `/simple-games/games/<locale>/<game-id>/` と書いているが、実際は逆で、
  この文書の形が正しい。
- 30 本すべてにガイドがあり、言語は `ui/landing.ts` の `PAGE_LOCALES` の
  10 言語(en / ja / es / pt-br / fr / id / de / th / vi / ko)。アプリの
  14 ロケールとは一致しないので、**言語別の需要は「ガイドがある 10 言語」に
  偏る** — 残り 4 言語の読者は英語ページを見ている。
- ゲーム 1 本を見る: 「ページ」→ フィルタ「URL を含む」→ `/games/<game-id>/`。
  言語まで絞るなら `/games/<game-id>/ja/`。
- 見る指標は 表示回数 / クリック数 / CTR / 平均掲載順位。国とクエリは
  同じ画面のタブで切る。
- **「ルールを知りたい検索」と「今すぐ遊びたい検索」を混ぜない。**
  `how to play …` / `… rules` / `… 遊び方` は前者、`… online` /
  `play … free` / `… 無料` は後者で、**同じゲームでも意味が違う**。前者が多い
  ゲームはガイドが強く、後者が多いゲームは play への導線が効く。ひとつの
  「需要」に足し合わせると、どちらの手を打つべきかが消える。

**ガイドから起動までを 1 本で確かめるのは、まだできない。** ゲーム別 URL
(`?game=` 等)は issue #83 の仕事で、このリポジトリには実装がない
(`location.search` を読む箇所が 1 つも無いことで確認できる)。#83 が入るまで、
ガイドの検索需要と `game_open` は**別々の表**であり、間をつないだ数字を作らない。
#83 が入ったら、代表ゲーム 1 本で ガイド → `?game=` → `game_open` が
つながることを実地で確認し、その結果をここに追記する。

## 上位 3 ゲームの選び方

**単一の指標で決めない。自動でも決めない。** 次の 6 つを並べて、人間が読む。

1. Search 需要(表示回数・クリック・順位。ルール検索とプレイ検索を分けて)
2. Web での開始数(`game_open` のイベント数とユーザー数)
3. 滞在(`play_duration_ms`。下の限界を読んだうえで)
4. 再訪(Returning users の `game_open`)
5. レビューと不具合(Play Console / App Store Connect / issue)
6. 改善余地と実装コスト(直せるものが残っているか)

**平均滞在時間が長い = 面白い、ではない。** 難しくて手が止まっている、
盤面が読みにくくて時間がかかっている、タブを開いたまま席を立った —
どれも同じ「長い」として出る。順位を作るための重みを決め打ちしないのは、
その重みが正しいと言える根拠がまだ無いからである。

**見る期間は原則として最低 14 日。** それより短い窓で「上がった / 下がった」を
言わない。母数が小さいゲームは 14 日でも足りないので、件数が判断に耐える
まで延ばす。基準の日数を縮める理由になるのは、期間ではなく件数である。

変更を入れたあとも同じ — **14 日ぶんの有効なデータが貯まるまで、その変更の
成否を結論にしない。**

## このデータで言えないこと

**すべて「観測できるが偏っている」であって、「無い」ではない。** 偏りを
知ったうえで使う。

- **Web はアプリの代理ではない。** ブラウザで来る人とストアから来る人は
  動機も端末も滞在も違う。Web で強いゲームがアプリでも強いとは限らず、
  逆も同じ。ここで決めるのは「次に手を入れる順番」であって、
  「アプリでの人気」ではない。
- **`game_close` は「一覧へ戻る」でしか出ない。** タブを閉じた、別のページへ
  移った、端末が寝た — どれも `game_close` を出さない。したがって
  `game_close` は `game_open` より**構造的に少なく**、`play_duration_ms` は
  **「戻ってきた人」だけの分布**である。比が低いことは、そのゲームが悪いことを
  意味しない(離脱の形が違うだけのことがある)。比が**極端に**低いゲームだけを
  「読み違いの候補」として見る。
- **放置したタブは長時間プレイとして数えられる。** 滞在はゲームを開いてから
  戻るまでの実時間で、バックグラウンドのタブも席を立った時間も含む。
  平均は外れ値に弱いので、**平均と中央値を並べて見るか、極端に長い値を
  外して比べる**。
- **`engagement_time_msec` には実時間を渡していない**(2026-08-30 修正)。
  この名前は GA4 のもので、渡した値は プロパティ全体の エンゲージメント時間・
  エンゲージメント率・エンゲージのあったセッション に足し込まれる —
  pixapps.ai の他のページと同じ 1 つのプロパティなので、実時間を渡すと
  **開きっぱなしのタブがサイト全体のエンゲージメントとして計上される**。
  そこで前面にあった時間だけを数えて渡している(`visibilitychange` を
  シェル常駐で 1 本だけ張る — [GAME_LIFECYCLE.md](GAME_LIFECYCLE.md) の
  音サービスと同じ扱い)。**`play_duration_ms` とは別の数字であり、
  必ずそれ以下になる。**
- **前面にあることは、見ていることではない。** 補正後も、開いたまま眺めても
  いないタブは前面時間として数える。入力の有無を追えばもっと正確になるが、
  それは個人の行動追跡であり、この製品では採らない。
- **届かないブラウザがある。** 広告ブロッカー・企業プロキシ・トラッキング
  防止機能で、タグが読まれないか、送信が落ちる。オフラインの初回アクセスでは
  そもそもタグを読み込まない(再接続してもリトライしない —
  [OFFLINE_POLICY.md](OFFLINE_POLICY.md) と同じ原則)。**欠けた分は
  「遊ばれていない」ではない。**
- **同意の状態で数え方が変わる。** GDPR 同意を扱う CMP は AdSense と共通で
  運用する予定だが、まだ実施の記録がない([WEB_VERSION.md](WEB_VERSION.md)
  「計測」実装状況)。ここが動くと、国別の数字は前後で比較できなくなる。
- **人を追いかけていない。** ユーザー ID もログインも無く、端末とブラウザを
  またいだ同一人物は分からない。「再訪」は GA4 のブラウザ単位の判定であって、
  リテンションコホートではない。
- **低母数で断定しない。** 件数が 2 桁のゲームで率を語らない。

## 実施していない検証を成功扱いにしない

[PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md) の原則をこの文書にも当てる。
**成果物にイベント名が入っていることは、届いていることの証明ではない。**
2026-08-30 まではまさにその状態だった(下の「なぜ静かに壊れたか」)。

本番で確かめるとき、ブラウザで見るのは次の 5 点。

1. `script[data-simple-games-ga4]` が Google タグを読み込んでいること。
   失敗していれば同じ要素に `data-simple-games-ga4-failed` が付く。
2. Network に `collect` リクエストが出ること(記録 ON・Preserve log ON)。
3. `page_view` / `game_open` / `game_close` の各リクエストが 2xx(通常 204)。
4. `game_open` の宛先が `G-V1BJW2MQ2D` で、正しい `game_id` を含むこと。
   `game_close` は正しい `game_id` と 0 以上の `play_duration_ms` を含むこと。
5. 1 回の開始・終了で各イベントが 1 回だけ出ること。

キューの中身だけを見て満足しない。開発者コンソールで確かめるなら:

```js
window.dataLayer.map((c) => Object.prototype.toString.call(c));
// すべて '[object Arguments]' であること。'[object Array]' が 1 つでも
// あれば、そのコマンドは Google タグに実行されていない。
```

GA4 の Realtime か DebugView で `game_open` / `game_close` を目で見るまでは、
「計測できている」と書かない。カスタム定義の登録と Exploration の作成は、
**受信を確認したあと**に行う(登録は遡らないので、順序が逆だと最初の
数日ぶんが `game_id` 無しで積まれる)。

## なぜ静かに壊れたか(2026-08-30)

読み方を書く前に、一度全部が黙って落ちていた理由をここに残す。**測定 ID も
イベント名も成果物にあり、`dataLayer` にコマンドも積まれていて、それでも
`collect` は 1 件も出ていなかった。**Google タグはキューの要素を
`arguments` オブジェクトのときだけコマンドとして実行し、独自シムが積んでいた
**通常の配列は黙って捨てていた**。中身は正しく、形だけが違った。

この壊れ方は、既存のユニットテストにも成果物検査にも映らなかった — どちらも
**中身**を見ていたからである。直したあとは形を見る。**ただし、何がどこで
守られているかを正確に書く**(この文書で over-claim したら、それは #84 と
同じ間違いを、それを戒める文書の中で繰り返すことになる):

- **すべての PR** — `web.test.ts` が `Array.isArray(command) === false` と
  `[object Arguments]` を固定し、`window.dataLayer` の型
  (`IArguments[]`)が配列を積むシムを `tsc` の段階で拒む。
- **すべての PR(成果物)** — `check-dist-ads-separation.sh` が `dist-web/` に
  `push(arguments)` があることを見る。計測チャンクは測定 ID の無いビルドにも
  入っているので、この検査は既定 OFF の CI ビルドでも動く。
- **CI が守らないもの** — 実際に届いたかどうか。`collect` が出ることも、GA4 が
  受け取ることも、機械では判定できない。だから下の「実装状況」は、そこを
  **未実施**のまま置いてある。

**「ある」と「届く」は別の検査である**というのが、この事故から持ち帰る規律で、
上の検証手順が全部ブラウザ側の観測になっているのはそのためである。
